# 07. Component Library — Бібліотека компонентів

## 1. Що таке Component Library?

**Component Library (бібліотека компонентів)** — це набір повторно використовуваних UI-компонентів, які мають узгоджений вигляд, поведінку та правила використання.

Замість того щоб створювати кожну кнопку, картку або поле введення окремо, команда використовує готові компоненти.

Наприклад, бібліотека може містити:

- ✔ Buttons — кнопки.
- ✔ Inputs — поля введення.
- ✔ Checkboxes — прапорці.
- ✔ Radio Buttons — перемикачі.
- ✔ Selects — випадаючі списки.
- ✔ Cards — картки.
- ✔ Modals — модальні вікна.
- ✔ Dropdowns — випадаючі меню.
- ✔ Tabs — вкладки.
- ✔ Alerts — повідомлення.
- ✔ Badges — невеликі інформаційні позначки.
- ✔ Avatars — аватари користувачів.
- ✔ Navigation — навігаційні елементи.

**Головна ідея:** компонент створюють один раз, а потім використовують у різних частинах продукту без необхідності щоразу відтворювати його з нуля.

---

## 2. Навіщо потрібна бібліотека компонентів?

Без бібліотеки компонентів кожна сторінка може мати власні варіанти кнопок, полів введення, відступів і кольорів.

Наприклад, у різних частинах сайту можуть з'явитися кнопки:

- з різною висотою;
- з різними радіусами заокруглення;
- з різними відтінками одного кольору;
- з неоднаковими станами наведення;
- з різними розмірами тексту.

Це створює непослідовний інтерфейс.

Component Library допомагає вирішити цю проблему.

Основні переваги:

- **Consistency — послідовність.** Компоненти мають узгоджений вигляд.
- **Reusability — повторне використання.** Один компонент можна застосовувати багато разів.
- **Maintainability — зручність підтримки.** Зміни в одному компоненті можуть оновити всі його використання.
- **Scalability — масштабованість.** Нові сторінки створюються на основі вже готових елементів.
- **Efficiency — ефективність.** Дизайнери та розробники витрачають менше часу на повторювані завдання.
- **Accessibility — доступність.** Можна централізовано впроваджувати правила доступності.
- **Collaboration — співпраця.** Команда працює з узгодженими компонентами та правилами.

## 3. Component Library, Design System і UI Kit

Ці поняття пов'язані між собою, але не є тотожними.

### 3.1. UI Kit

**UI Kit** — набір готових візуальних елементів і шаблонів для створення інтерфейсів.

Зазвичай він містить:

- кольори;
- текстові стилі;
- кнопки;
- поля введення;
- картки;
- іконки;
- інші візуальні елементи.

UI Kit може бути просто набором компонентів у Figma без детально визначених правил їх використання.

### 3.2. Component Library

**Component Library** — організована бібліотека компонентів із повторно використовуваними елементами, їхніми варіантами та станами.

Вона може існувати:

- у Figma як бібліотека дизайнерських компонентів;
- у коді як бібліотека React-компонентів;
- в обох середовищах одночасно.

Наприклад, дизайнер створює компонент `Button` у Figma, а розробник реалізує відповідний компонент `Button` у React.

### 3.3. Design System

**Design System (дизайн-система)** — ширша система правил, принципів, токенів, компонентів і рекомендацій для створення інтерфейсів.

Вона може містити:

- дизайн-токени;
- типографічну шкалу;
- систему кольорів;
- систему відступів;
- правила заокруглення;
- тіні;
- бібліотеку компонентів;
- правила доступності;
- документацію;
- принципи використання компонентів.

### Порівняння

| Поняття | Основне призначення |
|---|---|
| UI Kit | Готові візуальні елементи |
| Component Library | Повторно використовувані компоненти |
| Design System | Цілісна система правил і компонентів |

У реальних проєктах ці поняття можуть частково перетинатися. Межі між ними залежать від команди та організації роботи.

## 4. Анатомія компонента

Кожен компонент має певну структуру, властивості та правила поведінки.

Розглянемо кнопку.

Вона може складатися з таких частин:

- Container — зовнішня область кнопки.
- Label — текст кнопки.
- Icon — необов'язкова іконка.
- Padding — внутрішні відступи.
- Border Radius — заокруглення кутів.
- Background — фон.
- Text Style — стиль тексту.
- State — поточний стан компонента.

Приклад структури:

    Button
    ├── Icon (optional)
    └── Label

Не кожен компонент має однакову структуру. Наприклад, картка може містити зображення, заголовок, опис і дії.

Важливо визначити:

1. З яких частин складається компонент.
2. Які частини обов'язкові.
3. Які частини необов'язкові.
4. Які властивості можна змінювати.
5. Які стани компонент підтримує.
6. Як компонент поводиться на різних розмірах екрана.

## 5. Component Variants — варіанти компонентів

**Component Variants** — це узгоджені варіанти одного компонента, які відрізняються зовнішнім виглядом або призначенням.

Наприклад, кнопки можуть мати різні варіанти.

### За призначенням

- `primary` — основна дія.
- `secondary` — другорядна дія.
- `tertiary` — менш акцентна дія.
- `danger` — потенційно небезпечна дія.
- `ghost` — кнопка без виразного фону.
- `link` — дія, стилізована як посилання.

### За розміром

- `sm` — маленька.
- `md` — середня.
- `lg` — велика.

### За станом

- `default` — звичайний стан.
- `hover` — наведення курсора.
- `focus` — клавіатурний фокус.
- `active` — натискання.
- `disabled` — недоступний стан.
- `loading` — виконання операції.

Приклад системи варіантів:

    Button
    ├── Variant
    │   ├── primary
    │   ├── secondary
    │   ├── danger
    │   └── ghost
    ├── Size
    │   ├── sm
    │   ├── md
    │   └── lg
    └── State
        ├── default
        ├── hover
        ├── focus
        ├── active
        ├── disabled
        └── loading

У Figma варіанти можна організувати через компонентні властивості. У React подібні відмінності часто передають через props.

Важливо: не потрібно створювати окремий компонент для кожної можливої комбінації. Краще використовувати зрозумілу систему варіантів.

## 6. Component Properties — властивості компонентів

**Component Properties** — налаштування, які дозволяють змінювати певні характеристики компонента без створення його копії.

У Figma та в коді ці механізми мають свої особливості, але загальний принцип схожий.

Типові властивості:

- Variant — варіант компонента.
- Size — розмір.
- Label — текст.
- Icon — наявність або вибір іконки.
- Disabled — доступність для взаємодії.
- Loading — стан завантаження.
- Selected — вибраний стан.
- Error — стан помилки.

Наприклад, кнопка може мати властивості:

    Button
    ├── variant: primary | secondary | danger
    ├── size: sm | md | lg
    ├── disabled: true | false
    ├── loading: true | false
    └── icon: true | false

У React ці властивості зазвичай реалізують за допомогою props.

Приклад:

    type ButtonProps = {
      variant?: "primary" | "secondary" | "danger";
      size?: "sm" | "md" | "lg";
      disabled?: boolean;
      children: React.ReactNode;
    };

    function Button({
      variant = "primary",
      size = "md",
      disabled = false,
      children,
    }: ButtonProps) {
      return (
        <button
          className={`button button--${variant} button--${size}`}
          disabled={disabled}
        >
          {children}
        </button>
      );
    }

Використання:

    <Button variant="primary" size="md">
      Зберегти
    </Button>

    <Button variant="danger" size="sm">
      Видалити
    </Button>

Це спрощений навчальний приклад. У реальному компоненті потрібно також продумати передачу стандартних атрибутів кнопки, обробники подій, фокус, іконки та інші потрібні можливості.

## 7. Component States — стани компонентів

Компонент має не лише зовнішній вигляд, а й поведінку в різних ситуаціях.

Наприклад, кнопка може виглядати по-різному залежно від взаємодії користувача.

Основні стани:

| Стан | Значення |
|---|---|
| Default | Звичайний стан |
| Hover | Курсор наведений на елемент |
| Focus | Елемент має фокус |
| Active | Елемент натискають або активують |
| Disabled | Елемент недоступний |
| Loading | Виконується операція |
| Selected | Елемент вибраний |
| Error | Виникла помилка |
| Success | Операція завершилася успішно |

Не кожен компонент потребує всіх цих станів.

Наприклад:

- Кнопка може мати `hover`, `focus`, `active`, `disabled` і `loading`.
- Checkbox може мати `checked`, `unchecked`, `disabled` та `focus`.
- Поле введення може мати `default`, `focus`, `error`, `disabled` і `read-only`.

Під час створення бібліотеки потрібно описувати ті стани, які мають значення для конкретного компонента.

Докладніше про це дивись у розділі `06-component-states`.

## 8. Design Tokens у бібліотеці компонентів

**Design Tokens** — це іменовані значення дизайну, які компоненти використовують повторно.

Наприклад:

- кольори;
- розміри шрифтів;
- відступи;
- радіуси;
- тіні;
- тривалість анімацій.

Замість того щоб жорстко прописувати всі значення в кожному компоненті, їх можна зберігати у спільних змінних.

Приклад:

    :root {
      /* Colors */
      --color-primary: #2563eb;
      --color-danger: #dc2626;
      --color-text: #1f2937;
      --color-surface: #ffffff;

      /* Spacing */
      --spacing-1: 4px;
      --spacing-2: 8px;
      --spacing-3: 12px;
      --spacing-4: 16px;

      /* Radius */
      --radius-sm: 4px;
      --radius-md: 8px;
      --radius-lg: 12px;

      /* Shadows */
      --shadow-sm: 0 2px 8px rgb(0 0 0 / 10%);
      --shadow-md: 0 4px 16px rgb(0 0 0 / 12%);
    }

Компонент використовує токени:

    .button {
      padding: var(--spacing-2) var(--spacing-4);
      border-radius: var(--radius-md);
      background: var(--color-primary);
      color: white;
    }

    .card {
      padding: var(--spacing-4);
      border-radius: var(--radius-lg);
      background: var(--color-surface);
      box-shadow: var(--shadow-sm);
    }

Переваги:

- ✔ Узгоджений дизайн.
- ✔ Менше повторення значень.
- ✔ Простіша зміна стилів.
- ✔ Зручніше підтримувати світлу й темну теми.
- ✔ Легше масштабувати проєкт.

Бібліотека компонентів використовує токени, щоб її елементи належали до однієї дизайн-системи.

## 9. Atomic Design — атомарний підхід

**Atomic Design** — це один із підходів до організації інтерфейсів за рівнями складності.

Він описує п'ять основних категорій.

### 9.1. Atoms — атоми

Найменші базові елементи інтерфейсу.

Приклади:

- кнопка;
- текстове поле;
- іконка;
- текстова мітка;
- базовий текстовий стиль.

### 9.2. Molecules — молекули

Невеликі групи компонентів, які разом виконують певну функцію.

Приклад: поле пошуку, що складається з текстового поля та кнопки.

    SearchForm
    ├── Input
    └── Button

### 9.3. Organisms — організми

Складніші компоненти, які об'єднують кілька груп елементів.

Приклади:

- шапка сайту;
- навігаційна панель;
- форма реєстрації;
- список карток товарів.

### 9.4. Templates — шаблони

Структури сторінок, які визначають розташування основних блоків.

Наприклад, шаблон сторінки каталогу може містити:

- шапку;
- бічну панель фільтрів;
- область результатів;
- пагінацію;
- підвал.

### 9.5. Pages — сторінки

Конкретні сторінки з реальним контентом.

Наприклад:

- сторінка каталогу товарів;
- сторінка профілю;
- сторінка реєстрації.

Умовна схема:

    Atoms
      ↓
    Molecules
      ↓
    Organisms
      ↓
    Templates
      ↓
    Pages

Atomic Design — це корисна модель мислення, але не обов'язкова структура для кожного проєкту. У невеликому React-застосунку можна організувати компоненти простіше.

## 10. Як організувати бібліотеку компонентів у Figma

У Figma компоненти допомагають створювати повторно використовувані елементи дизайну.

Рекомендований порядок роботи:

1. Визнач основні компоненти, потрібні продукту.
2. Створи базові стилі й токени.
3. Створи компоненти для найчастіших елементів.
4. Додай потрібні варіанти.
5. Визнач властивості компонентів.
6. Опиши стани взаємодії.
7. Перевір адаптивність і довгі тексти.
8. Додай приклади правильного використання.
9. Перевір, чи не дублюються компоненти.
10. Організуй бібліотеку так, щоб команда могла швидко знайти потрібний елемент.

Приклад організації сторінок Figma:

    Design System
    ├── Foundations
    │   ├── Colors
    │   ├── Typography
    │   ├── Spacing
    │   ├── Border Radius
    │   └── Shadows
    ├── Components
    │   ├── Buttons
    │   ├── Forms
    │   ├── Cards
    │   ├── Navigation
    │   ├── Feedback
    │   └── Overlays
    ├── Patterns
    └── Examples

Це лише один із можливих варіантів організації.

Назви, групування й кількість сторінок залежать від масштабу проєкту.

## 11. Як організувати бібліотеку компонентів у React

У React бібліотека компонентів може бути частиною застосунку або окремим пакетом.

Для навчального проєкту можна почати з такої структури:

    src/
    ├── components/
    │   ├── ui/
    │   │   ├── Button/
    │   │   │   ├── Button.tsx
    │   │   │   ├── Button.module.css
    │   │   │   └── index.ts
    │   │   ├── Input/
    │   │   │   ├── Input.tsx
    │   │   │   ├── Input.module.css
    │   │   │   └── index.ts
    │   │   └── Card/
    │   │       ├── Card.tsx
    │   │       ├── Card.module.css
    │   │       └── index.ts
    │   └── layout/
    │       ├── Header.tsx
    │       └── Footer.tsx
    ├── styles/
    │   └── tokens.css
    └── app/

Пояснення:

- `components/ui/` — базові повторно використовувані компоненти.
- `components/layout/` — компоненти структури сторінки.
- `tokens.css` — спільні дизайн-токени.
- `app/` — маршрути або сторінки застосунку, залежно від архітектури.

Наприклад, компонент кнопки:

    // Button.tsx

    import type { ButtonHTMLAttributes, ReactNode } from "react";
    import styles from "./Button.module.css";

    type ButtonVariant = "primary" | "secondary" | "danger";
    type ButtonSize = "sm" | "md" | "lg";

    type ButtonProps = ButtonHTMLAttributes<HTMLButtonElement> & {
      variant?: ButtonVariant;
      size?: ButtonSize;
      children: ReactNode;
    };

    export function Button({
      variant = "primary",
      size = "md",
      children,
      className,
      ...props
    }: ButtonProps) {
      const classes = [
        styles.button,
        styles[variant],
        styles[size],
        className,
      ]
        .filter(Boolean)
        .join(" ");

      return (
        <button className={classes} {...props}>
          {children}
        </button>
      );
    }

CSS Modules:

    /* Button.module.css */

    .button {
      display: inline-flex;
      align-items: center;
      justify-content: center;
      gap: var(--spacing-2);
      border: 0;
      border-radius: var(--radius-md);
      font: inherit;
      cursor: pointer;
      transition: background-color 150ms ease;
    }

    .primary {
      background: var(--color-primary);
      color: white;
    }

    .secondary {
      background: #e5e7eb;
      color: #1f2937;
    }

    .danger {
      background: var(--color-danger);
      color: white;
    }

    .sm {
      min-height: 32px;
      padding: 6px 10px;
    }

    .md {
      min-height: 40px;
      padding: 8px 16px;
    }

    .lg {
      min-height: 48px;
      padding: 12px 20px;
    }

    .button:focus-visible {
      outline: 3px solid #93c5fd;
      outline-offset: 2px;
    }

    .button:disabled {
      opacity: 0.5;
      cursor: not-allowed;
    }

Приклад експорту:

    // index.ts

    export { Button } from "./Button";

Використання:

    import { Button } from "@/components/ui/Button";

    export default function ExamplePage() {
      return (
        <div>
          <Button variant="primary">Зберегти</Button>
          <Button variant="secondary" size="sm">
            Скасувати
          </Button>
          <Button variant="danger">Видалити</Button>
        </div>
      );
    }

Це навчальна реалізація. У реальному проєкті потрібно також перевірити кольори, контраст, поведінку під час завантаження, інтеграцію з формами та вимоги до доступності.

## 12. Документація компонентів

Бібліотека компонентів повинна пояснювати не лише те, як виглядає компонент, а й те, як його правильно використовувати.

Для кожного компонента корисно описати:

- Назву.
- Призначення.
- Доступні варіанти.
- Розміри.
- Стани.
- Обов'язкові властивості.
- Необов'язкові властивості.
- Приклади використання.
- Правила доступності.
- Обмеження та типові помилки.

Наприклад, документація для `Button`:

    # Button

    ## Purpose
    Виконує дію після взаємодії користувача.

    ## Variants
    - primary
    - secondary
    - danger

    ## Sizes
    - sm
    - md
    - lg

    ## States
    - default
    - hover
    - focus
    - active
    - disabled
    - loading

    ## Usage
    Використовуй primary для основної дії.
    Використовуй secondary для другорядної дії.
    Використовуй danger для деструктивних операцій.

    ## Accessibility
    - Кнопка повинна мати зрозумілу назву.
    - Клавіатурний фокус має бути видимим.
    - Disabled-стан не повинен бути єдиним способом пояснення помилки.

Документація може бути в Figma, README-файлах, Storybook або на окремому сайті документації.

## 13. Component Library і Storybook

**Storybook** — інструмент для розробки, перегляду та документування UI-компонентів ізольовано від основних сторінок застосунку.

Він дозволяє показувати різні варіанти компонентів і перевіряти їхню поведінку.

Наприклад, для кнопки можна створити приклади:

- Primary Button.
- Secondary Button.
- Danger Button.
- Small Button.
- Large Button.
- Disabled Button.
- Button with Icon.
- Loading Button.

Переваги:

- ✔ Компоненти можна переглядати окремо.
- ✔ Зручно перевіряти різні стани.
- ✔ Легше документувати props.
- ✔ Можна демонструвати приклади команді.
- ✔ Можна організувати візуальні перевірки компонентів.

Для невеликого навчального проєкту Storybook не є обов'язковим. Спочатку достатньо створити кілька компонентів і сторінку, де можна побачити їхні варіанти.

Коли бібліотека починає зростати, окрема документація стає значно кориснішою.

## 14. Правила створення якісної бібліотеки

### 14.1. Повторне використання

Створюй компонент, якщо елемент повторюється або має спільну поведінку, яку потрібно підтримувати в одному місці.

Але не потрібно перетворювати кожен HTML-елемент на окремий складний компонент без реальної потреби.

### 14.2. Узгодженість

Компоненти повинні використовувати спільні токени кольорів, відступів, типографіки, радіусів і тіней.

### 14.3. Передбачувані властивості

Назви props мають бути зрозумілими.

Наприклад:

    <Button variant="primary" size="md">
      Продовжити
    </Button>

Краще, ніж набір незрозумілих булевих прапорців, які не пояснюють призначення.

### 14.4. Композиція

Компоненти повинні за потреби поєднуватися між собою.

Наприклад, картка може містити заголовок, опис і кнопку, не вимагаючи створення окремої версії картки для кожної комбінації контенту.

### 14.5. Доступність

Використовуй семантичні HTML-елементи й перевіряй клавіатурну взаємодію, фокус, назви елементів та контраст.

### 14.6. Масштабованість

Бібліотека має дозволяти додавати нові компоненти без хаотичного збільшення кількості стилів і варіантів.

### 14.7. Документування

Компонент без зрозумілих правил використання може бути реалізований технічно правильно, але використовуватися неправильно.

## 15. Типові помилки під час створення Component Library

### Помилка 1. Дублювання компонентів

Для кожної сторінки створюють власну кнопку або картку, хоча вони майже однакові.

**Рішення:** визнач спільний компонент і його варіанти.

### Помилка 2. Надмірна універсальність

Один компонент отримує десятки props і складну логіку, щоб підтримувати будь-який можливий сценарій.

**Рішення:** підтримуй реальні потреби проєкту. Складні компоненти за необхідності розділяй на менші.

### Помилка 3. Занадто багато варіантів

Для кожного незначного візуального відхилення створюють новий варіант.

**Рішення:** перевір, чи справді відмінність потрібна, і чи не можна використати наявні токени або властивості.

### Помилка 4. Відсутність системи токенів

Кольори, відступи й радіуси прописують окремо в кожному компоненті.

**Рішення:** створи спільні дизайн-токени.

### Помилка 5. Ігнорування станів

Компонент добре виглядає у звичайному стані, але не має стилів для фокуса, помилки або недоступності.

**Рішення:** продумай потрібні стани до завершення компонента.

### Помилка 6. Відсутність документації

Команда не знає, коли використовувати `primary`, а коли `secondary`.

**Рішення:** додай правила використання та приклади.

### Помилка 7. Сліпе копіювання дизайну

Компонент виглядає правильно, але не має семантики, доступності або коректної поведінки.

**Рішення:** перевіряй не лише зовнішній вигляд, а й функціональність.

### Помилка 8. Передчасне ускладнення

Невеликий проєкт отримує складну архітектуру, яку важко підтримувати.

**Рішення:** починай із базових компонентів і розширюй бібліотеку за потреби.

## 16. Практичний мініпроєкт: власна бібліотека UI-компонентів

Мета: створити невелику бібліотеку компонентів для навчального вебзастосунку.

### Крок 1. Створи дизайн-токени

    :root {
      --color-primary: #2563eb;
      --color-primary-hover: #1d4ed8;

      --color-text: #1f2937;
      --color-surface: #ffffff;
      --color-border: #d1d5db;

      --spacing-1: 4px;
      --spacing-2: 8px;
      --spacing-3: 12px;
      --spacing-4: 16px;
      --spacing-6: 24px;

      --radius-sm: 4px;
      --radius-md: 8px;
      --radius-lg: 12px;

      --shadow-sm: 0 2px 8px rgb(0 0 0 / 10%);
    }

### Крок 2. Створи базові компоненти

Почни з трьох компонентів:

    Button
    Input
    Card

Не потрібно відразу створювати велику бібліотеку.

### Крок 3. Визнач варіанти

Для `Button`:

    variant:
      - primary
      - secondary
      - danger

    size:
      - sm
      - md
      - lg

Для `Input`:

    state:
      - default
      - focus
      - error
      - disabled

Для `Card`:

    variant:
      - default
      - elevated
      - outlined

Ці варіанти є прикладом. Обирай їх відповідно до потреб інтерфейсу.

### Крок 4. Створи демонстраційну сторінку

На одній сторінці покажи всі варіанти компонентів.

Приклад структури:

    UI Library Demo
    ├── Buttons
    │   ├── Primary
    │   ├── Secondary
    │   └── Danger
    ├── Inputs
    │   ├── Default
    │   ├── Error
    │   └── Disabled
    └── Cards
        ├── Default
        ├── Elevated
        └── Outlined

### Крок 5. Перевір компоненти

Переконайся, що:

- усі кнопки мають передбачуваний вигляд;
- поля введення мають зрозумілі стани;
- картки використовують спільні токени;
- клавіатурний фокус помітний;
- компоненти не ламаються через довгі тексти;
- бібліотеку легко розширити.

### Крок 6. Напиши README

Опиши призначення бібліотеки, її структуру, доступні компоненти, варіанти та правила використання.

Це допоможе закріпити знання і стане корисною документацією для майбутніх проєктів.

## 17. Як зрозуміти, що компонент готовий?

Перед додаванням компонента до бібліотеки перевір такі питання:

- ✔ Чи зрозуміле його призначення?
- ✔ Чи використовує він дизайн-токени?
- ✔ Чи визначені необхідні варіанти?
- ✔ Чи описані важливі стани?
- ✔ Чи має він передбачувані властивості?
- ✔ Чи можна його повторно використовувати?
- ✔ Чи підтримує він потрібні розміри й обсяг контенту?
- ✔ Чи доступний він для клавіатури, якщо передбачає взаємодію?
- ✔ Чи є зрозуміла документація?
- ✔ Чи не дублює він інший компонент без потреби?

Це не формальна вимога для кожного маленького елемента, а практичний список для контролю якості.

## Висновок

**Component Library — це організований набір повторно використовуваних компонентів, який допомагає створювати послідовні, масштабовані та зручні для підтримки інтерфейси.**

Для дизайнера вона забезпечує узгодженість макетів у Figma. Для frontend-розробника — повторне використання компонентів у коді. Для команди — спільні правила роботи з інтерфейсом.

Починай із базових компонентів, використовуй дизайн-токени, визначай необхідні варіанти й стани та документуй правила використання.

**Головне правило:** хороша бібліотека компонентів — це не найбільша кількість компонентів, а набір елементів, які зрозумілі, послідовні, доступні та справді корисні для проєкту.
