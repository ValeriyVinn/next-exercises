# 02. User Tasks

User Tasks (завдання користувача) — це конкретні дії або послідовності дій, які користувач виконує для досягнення певної мети під час взаємодії з вебсайтом, застосунком або іншим цифровим продуктом.

У UI/UX Design розуміння User Tasks допомагає створювати інтерфейси, у яких користувач може виконувати потрібні дії зрозуміло, послідовно, ефективно та без зайвих перешкод.

Наприклад, користувач хоче записатися до лікаря.

Його User Goal:

    Записатися на прийом до лікаря.

Його User Tasks:

    1. Знайти потрібного спеціаліста.
    2. Переглянути доступні дати.
    3. Вибрати час.
    4. Ввести контактні дані.
    5. Підтвердити запис.
    6. Переконатися, що запис створено.

Кожне завдання є частиною шляху до досягнення головної мети.

User Tasks допомагають відповісти на запитання:

    Що користувач хоче зробити?
    Які дії для цього потрібні?
    У якій послідовності їх виконувати?
    Яка інформація потрібна на кожному кроці?
    Які перешкоди можуть виникнути?
    Як користувач зрозуміє, що завдання виконано?

## Що потрібно пам'ятати

• User Task — це дія або послідовність дій, які користувач виконує для досягнення результату.

• User Goal описує бажаний результат, а User Task — дії, необхідні для його досягнення.

• Один User Goal може включати декілька User Tasks.

• Завдання можуть складатися з менших кроків — Task Steps.

• Task Flow описує послідовність дій і можливі переходи між ними.

• Task Analysis допомагає зрозуміти, як користувач виконує завдання та які труднощі виникають.

• Happy Path — основний сценарій успішного виконання завдання без помилок і відхилень.

• Alternative Flow описує інший можливий шлях виконання завдання.

• Error Flow описує ситуації, коли виникають помилки або завдання не виконується за очікуваним сценарієм.

• Хороший UI допомагає користувачу зрозуміти наступний крок.

• Не кожне завдання потребує окремої сторінки або окремого екрана.

• Кількість кроків важлива, але менша кількість кроків не завжди означає кращий UX.

• Завдання має бути достатньо простим, щоб користувач міг його виконати, але достатньо повним, щоб отримати правильний результат.

• Інтерфейс повинен надавати зрозумілий feedback після важливих дій.

• Користувач повинен мати можливість виправити помилки та відновити виконання завдання.

• Task Completion Rate показує частку завдань, які користувачі успішно завершили.

• Task Success Rate та інші показники допомагають оцінювати ефективність інтерфейсу.

• Завдання потрібно перевіряти на реальних користувачах, а не лише на основі припущень дизайнера.

# User Task

User Task — дія або послідовність дій, які користувач виконує для досягнення певного результату.

Приклади:

    Знайти товар.
    Зареєструватися.
    Увійти в обліковий запис.
    Записатися до лікаря.
    Завантажити документ.
    Створити нотатку.
    Знайти розклад богослужінь.
    Змінити пароль.
    Оформити замовлення.

Завдання може бути простим або складним.

## Simple Task

Simple Task — завдання, яке потребує невеликої кількості дій.

Наприклад:

    User Task:
    Змінити тему інтерфейсу.

    Steps:
    1. Відкрити налаштування.
    2. Вибрати тему.
    3. Підтвердити вибір, якщо потрібно.

## Complex Task

Complex Task — завдання, яке містить декілька етапів, залежностей або рішень.

Наприклад:

    User Task:
    Оформити замовлення в інтернет-магазині.

    Steps:
    1. Знайти товар.
    2. Перевірити характеристики.
    3. Вибрати кількість.
    4. Додати товар до кошика.
    5. Переглянути кошик.
    6. Ввести адресу доставки.
    7. Вибрати спосіб доставки.
    8. Вибрати спосіб оплати.
    9. Перевірити замовлення.
    10. Підтвердити покупку.
    11. Переглянути результат.

Складне завдання може потребувати декількох екранів, перевірок, рішень і повідомлень.

Мета дизайну — зробити цей процес зрозумілим і керованим.

# User Goal vs User Task

User Goal і User Task пов'язані, але не є одним і тим самим.

**User Goal** — те, чого користувач хоче досягти.

**User Task** — те, що користувач робить для досягнення мети.

Наприклад:

    User Goal:
    Навчитися JavaScript.

    User Tasks:
    1. Знайти навчальний матеріал.
    2. Прочитати пояснення.
    3. Переглянути приклади.
    4. Написати код.
    5. Виконати практичні завдання.
    6. Перевірити результати.

Інший приклад:

    User Goal:
    Дізнатися час богослужіння.

    User Tasks:
    1. Відкрити сайт парафії.
    2. Знайти розділ розкладу.
    3. Вибрати потрібну дату.
    4. Переглянути час початку.

Спрощена модель:

    User Goal
        ↓
    User Tasks
        ↓
    Task Steps
        ↓
    Task Completion
        ↓
    User Outcome

Не потрібно плутати завдання з окремою технічною дією.

Наприклад:

    Натиснути кнопку «Увійти»
        ↓
    User Action

    Увійти до свого облікового запису
        ↓
    User Task

    Отримати доступ до особистих навчальних матеріалів
        ↓
    User Goal

---

# User Action

User Action — конкретна дія користувача під час взаємодії з інтерфейсом.

Приклади:

    Натиснути кнопку.
    Ввести текст.
    Вибрати пункт меню.
    Відкрити картку товару.
    Перемістити повзунок.
    Підтвердити дію.
    Прокрутити сторінку.
    Вибрати дату.

Одна User Task може включати декілька User Actions.

Наприклад:

    User Task:
    Знайти потрібний курс.

    User Actions:
    1. Відкрити каталог.
    2. Ввести назву курсу.
    3. Натиснути кнопку пошуку.
    4. Переглянути результати.
    5. Відкрити картку курсу.

User Action — найменший практичний елемент взаємодії в цьому прикладі.

Проте не кожне натискання є окремим змістовним завданням.

Під час проєктування потрібно розуміти зв'язок між діями та результатом.

---

# Task Step

Task Step — окремий крок у виконанні завдання.

Наприклад:

    User Task:
    Записатися до лікаря.

    Task Steps:
    1. Вибрати спеціаліста.
    2. Вибрати дату.
    3. Вибрати час.
    4. Заповнити контактні дані.
    5. Підтвердити запис.

Кожен крок повинен допомагати просуватися до кінцевого результату.

Якщо крок не має зрозумілого призначення, потрібно перевірити, чи справді він необхідний.

## Хороший Task Step

    Показує зрозумілу дію.
    Надає потрібну інформацію.
    Допомагає рухатися до результату.
    Не вимагає зайвих зусиль.

## Проблемний Task Step

    Не має зрозумілої мети.
    Вимагає повторно вводити ті самі дані.
    Не пояснює, що потрібно зробити.
    Блокує подальший рух без зрозумілої причини.

Наприклад, якщо користувач уже ввів адресу доставки, повторно запитувати ту саму адресу на наступному кроці без необхідності — зайве навантаження.

# Task Flow

Task Flow — послідовність кроків і переходів, які користувач проходить для виконання завдання.

Task Flow допомагає зрозуміти:

    з чого починається завдання;
    які кроки виконує користувач;
    де потрібно прийняти рішення;
    які існують альтернативні шляхи;
    що відбувається після помилки;
    як завершується завдання.

Приклад: вхід до облікового запису.

    START
      ↓
    Відкрити сторінку входу
      ↓
    Ввести email
      ↓
    Ввести пароль
      ↓
    Натиснути «Увійти»
      ↓
    Перевірка даних
      ↓
    Дані правильні?
      ├── Так → Відкрити обліковий запис
      └── Ні → Показати повідомлення
                    ↓
              Виправити дані
                    ↓
              Повторити спробу

Task Flow показує не тільки основний шлях, а й те, як система реагує на різні ситуації.

---

# Task Flow vs User Flow

Ці поняття часто використовуються в UX-проєктуванні, і їхні значення можуть частково перетинатися.

## Task Flow

Task Flow зазвичай зосереджується на послідовності дій для виконання конкретного завдання.

Наприклад:

    User Task:
    Відновити пароль.

    Task Flow:
    1. Відкрити відновлення пароля.
    2. Ввести email.
    3. Надіслати запит.
    4. Відкрити лист.
    5. Перейти за посиланням.
    6. Створити новий пароль.
    7. Побачити підтвердження.

## User Flow

User Flow описує шлях користувача через екрани, сторінки та точки взаємодії продукту для досягнення певної мети.

Наприклад:

    Головна сторінка
        ↓
    Сторінка входу
        ↓
    Відновлення пароля
        ↓
    Підтвердження email
        ↓
    Створення нового пароля
        ↓
    Успішне відновлення

Task Flow акцентує увагу на виконанні завдання.

User Flow частіше показує шлях через інтерфейс і взаємозв'язки між екранами.

На практиці ці підходи можуть використовуватися разом.

# Task Analysis

Task Analysis — аналіз того, як користувач виконує певне завдання.

Мета — зрозуміти послідовність дій, необхідну інформацію, рішення, труднощі та можливі помилки.

Task Analysis допомагає відповісти на запитання:

    Яка мета завдання?

    З чого починає користувач?

    Які кроки він виконує?

    Яку інформацію використовує?

    Які рішення приймає?

    Які помилки можуть виникнути?

    Які кроки можна спростити?

    Як перевірити успішне завершення?

## Приклад Task Analysis

Завдання:

    Оформити замовлення.

Аналіз:

    1. Знайти потрібний товар.
    2. Перевірити характеристики.
    3. Додати товар до кошика.
    4. Перевірити кількість.
    5. Вказати адресу доставки.
    6. Вибрати спосіб доставки.
    7. Вибрати спосіб оплати.
    8. Перевірити підсумок.
    9. Підтвердити замовлення.

Можливі проблеми:

    користувач не бачить повної вартості;
    не розуміє умови доставки;
    випадково змінює кількість товарів;
    не може виправити адресу;
    не знає, чи завершилося оформлення.

Можливі покращення:

    показати повну вартість до підтвердження;
    пояснити способи доставки;
    дозволити редагувати кошик;
    надати зрозумілий спосіб змінити дані;
    показати підтвердження після успішного замовлення.

# Hierarchical Task Analysis (HTA)

Hierarchical Task Analysis (HTA) — метод аналізу, за якого велике завдання розбивають на підзавдання та окремі кроки.

Цей підхід допомагає зрозуміти структуру складного процесу.

Наприклад:

    Головне завдання:
    Пройти онлайн-курс.

        1. Знайти курс.
            1.1. Відкрити каталог.
            1.2. Знайти категорію.
            1.3. Переглянути курси.
            1.4. Вибрати курс.

        2. Розпочати навчання.
            2.1. Увійти в обліковий запис.
            2.2. Відкрити перший урок.
            2.3. Переглянути матеріал.

        3. Виконати практику.
            3.1. Відкрити завдання.
            3.2. Написати відповідь.
            3.3. Надіслати відповідь.
            3.4. Переглянути feedback.

        4. Завершити курс.
            4.1. Виконати підсумкову роботу.
            4.2. Перевірити результат.
            4.3. Переглянути статус завершення.

HTA допомагає виявити:

    залежності між кроками;
    надто складні підзавдання;
    непотрібні дії;
    точки, де потрібні підказки;
    можливості автоматизації.

Не кожне завдання обов'язково виконується строго послідовно.

Деякі підзавдання можуть бути необов'язковими або виконуватися в іншому порядку.

# Happy Path

Happy Path — основний сценарій, у якому користувач успішно виконує завдання без помилок, відмов системи або непередбачених відхилень.

Наприклад:

    User Task:
    Зареєструватися на платформі.

    Happy Path:
    1. Відкрити форму реєстрації.
    2. Ввести коректний email.
    3. Створити пароль, який відповідає вимогам.
    4. Прийняти необхідні умови.
    5. Надіслати форму.
    6. Завершити потрібне підтвердження.
    7. Побачити успішний результат.

Happy Path важливий, оскільки допомагає визначити основний шлях виконання завдання.

Але проєктувати лише Happy Path недостатньо.

Потрібно також враховувати:

    неправильні дані;
    пропущені поля;
    втрату з'єднання;
    недоступність сервісу;
    переривання процесу;
    повторне надсилання;
    потребу повернутися до попереднього кроку.

---

# Alternative Flow

Alternative Flow — альтернативний сценарій виконання завдання, який відрізняється від основного, але все ще може привести до бажаного результату.

Наприклад, під час пошуку товару користувач може:

    відкрити категорію;
    скористатися пошуком;
    перейти з рекомендацій;
    відкрити збережений товар.

Усі ці шляхи можуть приводити до сторінки товару.

Інший приклад:

    User Task:
    Увійти до облікового запису.

    Alternative Flow:
    1. Користувач не пам'ятає пароль.
    2. Відкриває відновлення пароля.
    3. Підтверджує свою особу.
    4. Створює новий пароль.
    5. Повертається до входу.

Alternative Flow потрібен для ситуацій, які не належать до основного сценарію, але є нормальними та передбачуваними.

---

# Error Flow

Error Flow — сценарій, який описує поведінку системи, коли завдання не може бути виконане звичайним способом через помилку або іншу перешкоду.

Наприклад:

    User Task:
    Увійти до облікового запису.

    Error Flow:
    1. Користувач вводить неправильний пароль.
    2. Система перевіряє дані.
    3. Вхід не виконується.
    4. Система показує зрозуміле повідомлення.
    5. Користувач може виправити пароль
       або відновити доступ.

Хороший Error Flow повинен:

    пояснювати, що сталося;
    допомагати зрозуміти причину;
    показувати можливий наступний крок;
    зберігати вже введені дані, якщо це безпечно;
    не створювати зайвих перешкод.

Поганий варіант:

    Something went wrong.

Краще, якщо це відповідає реальній ситуації:

    Не вдалося увійти.
    Перевірте email і пароль або відновіть доступ.

Повідомлення не повинно розкривати чутливу інформацію або деталі, які можуть створити ризик для безпеки.

---

# Decision Point

Decision Point — точка в Task Flow, де користувач або система має вибрати один із можливих варіантів подальшої дії.

Наприклад:

    Користувач вибирає спосіб доставки.

    Доступні варіанти:
    - Кур'єр.
    - Пункт видачі.
    - Самовивіз.

Вибір може змінити подальші кроки.

Наприклад:

    Вибрано «Кур'єр»
        ↓
    Ввести адресу доставки.

    Вибрано «Пункт видачі»
        ↓
    Вибрати пункт видачі.

    Вибрано «Самовивіз»
        ↓
    Переглянути адресу магазину.

Decision Points потрібно проєктувати так, щоб користувач розумів:

    які є варіанти;
    чим вони відрізняються;
    які наслідки має вибір;
    чи можна змінити рішення пізніше.

---

# Entry Point та Exit Point

## Entry Point

Entry Point — точка, з якої користувач починає виконувати завдання.

Приклади:

    Головна сторінка.
    Каталог товарів.
    Сторінка пошуку.
    Email-повідомлення.
    Посилання на конкретний курс.
    Сторінка входу.

Користувач не завжди починає шлях із головної сторінки.

Він може перейти безпосередньо до потрібної сторінки з пошукової системи, повідомлення або зовнішнього посилання.

Тому інтерфейс повинен враховувати різні точки входу.

## Exit Point

Exit Point — точка, у якій користувач завершує завдання або залишає відповідний сценарій.

Приклади:

    Сторінка підтвердження замовлення.
    Повідомлення про успішну реєстрацію.
    Завершене завантаження.
    Збережений документ.
    Сторінка з результатом пошуку.

Exit Point має відповідати реальному результату.

Якщо замовлення ще не підтверджено сервером, не можна показувати повідомлення, що покупку успішно завершено.

---

# Prerequisites та Postconditions

## Prerequisites

Prerequisites — умови, які повинні виконуватися перед початком завдання або певного кроку.

Наприклад:

    User Task:
    Зберегти особисті налаштування.

    Prerequisites:
    Користувач відкрив налаштування.
    Користувач має відповідні права доступу.
    Потрібні поля доступні для редагування.

Не кожне завдання потребує входу до системи.

Необхідні попередні умови залежать від функції та рівня ризику.

## Postconditions

Postconditions — умови, які повинні виконуватися після завершення завдання.

Наприклад:

    User Task:
    Змінити пароль.

    Postconditions:
    Новий пароль збережено.
    Система підтвердила зміну.
    Користувач розуміє, що робити далі.

Приклад для замовлення:

    Prerequisites:
    Товар доступний.
    Дані замовлення можна перевірити.

    Task:
    Підтвердити замовлення.

    Postconditions:
    Замовлення створено.
    Користувач отримав підтвердження.
    Система зберегла інформацію про замовлення.

---

# Task Complexity

Task Complexity — складність виконання завдання.

Вона залежить не лише від кількості кроків.

На складність можуть впливати:

    кількість рішень;
    складність інформації;
    незнайомі терміни;
    кількість полів;
    залежність між діями;
    необхідність запам'ятовувати дані;
    наслідки помилки;
    доступність підказок;
    досвід користувача;
    умови використання.

Наприклад:

    Task A:
    Змінити колір інтерфейсу.

    Task B:
    Подати заявку на фінансову послугу.

Task B може вимагати більше інформації, перевірок і рішень, а також мати серйозніші наслідки помилки.

Тому складність потрібно оцінювати з урахуванням контексту.

## Як зменшити Task Complexity

    Розділити складне завдання на логічні етапи.
    Прибрати непотрібні кроки.
    Використовувати зрозумілі назви.
    Групувати пов'язані поля.
    Показувати потрібну інформацію вчасно.
    Надавати корисні підказки.
    Зберігати введені дані, коли це доречно.
    Пояснювати наслідки важливих рішень.
    Допомагати виправляти помилки.

Важливо не приховувати необхідну інформацію лише заради спрощення інтерфейсу.

Справжнє спрощення означає зменшення непотрібних зусиль, а не вилучення важливих кроків.

---

# Task Frequency

Task Frequency — частота, з якою користувач виконує певне завдання.

Завдання можуть бути:

    частими;
    періодичними;
    рідкісними;
    одноразовими.

Приклади:

    Часте:
    Переглядати список повідомлень.

    Періодичне:
    Перевіряти щомісячний звіт.

    Рідкісне:
    Змінювати налаштування безпеки.

    Одноразове:
    Створювати обліковий запис.

Частота впливає на дизайнерські рішення.

Для частих завдань особливо важливі:

    швидкий доступ;
    ефективність;
    зручність повторення;
    можливість використовувати клавіатуру;
    мінімум зайвих кроків.

Для рідкісних або складних завдань важливішими можуть бути:

    зрозумілі інструкції;
    контекстні підказки;
    попередження;
    підтвердження;
    можливість повернутися до попереднього кроку.

Часте завдання не завжди важливіше за рідкісне.

Наприклад, відновлення доступу може використовуватися нечасто, але бути критично важливим, коли користувач втрачає доступ до облікового запису.

---

# Task Priority

Task Priority — пріоритет завдання з погляду потреб користувачів, частоти використання, важливості результату та інших критеріїв.

Під час визначення пріоритетів можна враховувати:

    важливість для користувача;
    частоту виконання;
    вплив на досягнення основної мети;
    наслідки невиконання;
    бізнес-вимоги;
    доступність альтернатив;
    ризики помилок.

Наприклад, для інтернет-магазину:

    Високий пріоритет:
    Знайти товар.
    Перевірити ціну.
    Оформити замовлення.

    Середній пріоритет:
    Порівняти додаткові характеристики.
    Зберегти товар у вибране.

    Нижчий пріоритет у конкретному сценарії:
    Змінити декоративний вигляд карток.

Це лише приклад. Реальні пріоритети потрібно визначати на основі конкретного продукту та його користувачів.

Основна мета — зробити важливі завдання доступними та зрозумілими, не створюючи непотрібних перешкод.

---

# Task Duration

Task Duration — час, необхідний для виконання завдання.

Наприклад:

    User Task:
    Знайти розклад богослужінь.

    Task Duration:
    Час від початку пошуку
    до знаходження потрібної інформації.

Під час usability testing можна вимірювати:

    час до першої правильної дії;
    загальний час виконання;
    час, витрачений на окремі кроки;
    час на виправлення помилок;
    час пошуку потрібної інформації.

Але швидкість не є єдиним критерієм якості.

Для важливих завдань користувачеві може знадобитися більше часу, щоб перевірити дані та уникнути помилок.

Наприклад:

    Швидко підтвердити неправильний платіж
        ↓
    Не є успішним UX.

    Перевірити реквізити та підтвердити правильний платіж
        ↓
    Може бути кращим результатом,
    навіть якщо це займає більше часу.

---

# Task Efficiency та Task Effectiveness

Ці поняття допомагають оцінювати виконання завдань.

## Task Effectiveness

Task Effectiveness — наскільки успішно користувач досягає потрібного результату.

Приклади запитань:

    Чи завершив користувач завдання?

    Чи отримав правильний результат?

    Чи припустився критичної помилки?

    Чи зміг завершити завдання самостійно?

## Task Efficiency

Task Efficiency — скільки часу, зусиль або інших ресурсів потрібно для досягнення результату.

Приклади запитань:

    Скільки часу зайняло завдання?

    Скільки кроків виконав користувач?

    Скільки разів він повертався назад?

    Скільки помилок виникло?

    Чи довелося вводити дані повторно?

Приклад:

    Interface A:
    Користувач успішно виконав завдання
    за 8 кроків.

    Interface B:
    Користувач успішно виконав те саме завдання
    за 5 кроків.

Якщо обидва варіанти забезпечують правильний результат, варіант B може бути ефективнішим.

Проте потрібно також перевірити, чи не погіршилися зрозумілість, доступність або безпека.

---

# Task Completion

Task Completion — факт завершення користувачем певного завдання.

Наприклад:

    User Task:
    Завантажити документ.

    Task Completion:
    Документ успішно завантажено
    та доступний користувачу.

Завершення завдання повинно визначатися реальним результатом, а не лише натисканням кнопки.

Наприклад:

    Користувач натиснув «Зберегти»
        ↓
    Запит ще обробляється
        ↓
    Дані збережено
        ↓
    Завдання завершено

Якщо запит завершився помилкою, завдання не можна вважати успішно виконаним.

## Completion Feedback

Після завершення завдання інтерфейс має повідомити користувача про результат.

Приклади:

    «Зміни збережено».

    «Документ завантажено».

    «Замовлення оформлено».

    «Запис на прийом підтверджено».

Feedback повинен відповідати реальному стану системи.

---

# Task Completion Rate

Task Completion Rate — показник, який відображає частку користувачів, які успішно завершили конкретне завдання.

Формула:

    Task Completion Rate =
    (Кількість успішно завершених завдань /
    Загальна кількість спроб) × 100%

Приклад:

    Кількість спроб: 100.
    Успішно завершено: 85.

    Task Completion Rate =
    (85 / 100) × 100% = 85%

Отже, 85% спроб завершилися успішно.

Для коректного вимірювання потрібно визначити:

    що саме вважається завданням;
    що вважається успішним результатом;
    хто входить до вибірки;
    як обробляються повторні спроби;
    чи враховуються частково виконані завдання.

Task Completion Rate допомагає зрозуміти, чи можуть користувачі досягати своїх цілей за допомогою інтерфейсу.

Однак сам показник не пояснює, чому інші користувачі не завершили завдання.

Для цього можуть знадобитися спостереження, інтерв'ю та аналіз помилок.

---

# Task Success Rate

Task Success Rate — показник успішності виконання завдання.

У різних дослідженнях його можуть визначати по-різному. Наприклад, можна враховувати лише повністю успішні спроби або окремо класифікувати частковий успіх.

Приклад:

    Учасники тестування: 20.
    Повністю успішно: 16.
    Частково успішно: 2.
    Неуспішно: 2.

Якщо критерієм є лише повне успішне завершення:

    Task Success Rate =
    (16 / 20) × 100% = 80%

Якщо частковий успіх потрібно враховувати окремо, його слід чітко визначити в методиці дослідження.

Не варто порівнювати показники з різних тестів, якщо вони використовують різні правила оцінювання.

---

# Task Flow Diagram

Task Flow Diagram — схема, яка показує послідовність кроків, рішень і переходів під час виконання завдання.

Основні елементи:

    Start — початок.
    Action — дія.
    Decision — точка вибору.
    Flow — напрямок переходу.
    Error — помилка.
    End — завершення.

Приклад: пошук товару.

    START
      ↓
    Відкрити каталог
      ↓
    Ввести пошуковий запит
      ↓
    Показати результати
      ↓
    Товар знайдено?
      ├── Так → Відкрити товар
      │            ↓
      │       Переглянути характеристики
      │            ↓
      │       END
      │
      └── Ні → Змінити запит
                   ↓
              Повторити пошук

Task Flow Diagram допомагає виявити:

    непотрібні переходи;
    тупикові сценарії;
    відсутні альтернативи;
    складні точки вибору;
    помилки в логіці;
    відсутність зрозумілого завершення.

---

# User Scenario

User Scenario — опис ситуації, у якій користувач взаємодіє з продуктом, щоб досягти певної мети.

Сценарій зазвичай описує:

    хто користувач;
    у якій ситуації він перебуває;
    чого хоче досягти;
    які обмеження має;
    який результат очікує.

Приклад:

    Користувач:
    Людина, яка планує відвідати лікаря.

    Situation:
    Вона має обмежений час
    і хоче знайти доступний прийом.

    Goal:
    Записатися на зручну дату.

    Scenario:
    Користувач відкриває сайт клініки,
    знаходить потрібного спеціаліста,
    переглядає доступні години,
    вибирає час і підтверджує запис.

    Expected Outcome:
    Запис створено,
    а користувач бачить підтвердження.

User Scenario допомагає зрозуміти контекст завдання до того, як починається проєктування інтерфейсу.

---

# Interaction Cost

Interaction Cost — зусилля, які користувач витрачає на виконання завдання.

Це можуть бути:

    кліки;
    натискання клавіш;
    введення тексту;
    переходи між сторінками;
    прокручування;
    запам'ятовування інформації;
    прийняття рішень;
    виправлення помилок;
    очікування відповіді системи.

Наприклад:

    Варіант A:
    Щоб змінити мову, потрібно відкрити
    чотири рівні налаштувань.

    Варіант B:
    Налаштування мови доступне
    безпосередньо в профілі.

Для відповідного сценарію варіант B може мати меншу вартість взаємодії.

Проте важливо враховувати контекст.

Деякі дії повинні містити додаткові перевірки, якщо помилка може мати серйозні наслідки.

Мета UX-дизайну — не просто зменшити кількість кліків, а зробити шлях до результату зрозумілим, ефективним і безпечним.

---

# Cognitive Load під час виконання завдань

Cognitive Load — когнітивне навантаження, тобто розумові зусилля, потрібні для обробки інформації та виконання завдання.

Навантаження може зростати, якщо користувач повинен:

    запам'ятовувати багато даних;
    розуміти незнайомі терміни;
    порівнювати забагато варіантів;
    переходити між різними екранами;
    самостійно здогадуватися про наступний крок;
    інтерпретувати незрозумілі повідомлення.

Наприклад:

    Поганий варіант:
    Користувач має запам'ятати адресу,
    перейти на іншу сторінку
    і повторно ввести її у форму.

    Кращий варіант:
    Система зберігає введену адресу
    та дозволяє використати її повторно,
    якщо це доречно й безпечно.

Способи зменшення зайвого когнітивного навантаження:

    групувати пов'язані поля;
    використовувати зрозумілі назви;
    показувати контекстні підказки;
    зберігати введені дані;
    надавати видимі варіанти вибору;
    показувати прогрес у складних процесах;
    уникати зайвої інформації;
    забезпечувати послідовність інтерфейсу.

Докладніше Cognitive Load розглядається в розділі:

    03-cognitive-load

---

# Task-Oriented Design

Task-Oriented Design — підхід до проєктування інтерфейсу, у якому структура та функції організовані навколо завдань, які користувач хоче виконати.

Замість запитання:

    Які компоненти потрібно додати на сторінку?

Потрібно запитати:

    Яке завдання виконує користувач?

    Яка інформація йому потрібна?

    Які дії він має виконати?

    Який результат очікує?

    Що може завадити?

Приклад: сторінка особистого кабінету студента.

Можливі основні завдання:

    Переглянути навчальні курси.
    Продовжити незавершений урок.
    Виконати завдання.
    Перевірити результати.
    Переглянути прогрес.

Інтерфейс може підтримувати ці завдання через:

    зрозумілу навігацію;
    список курсів;
    помітну дію «Продовжити навчання»;
    статус виконання;
    доступ до практичних завдань;
    зрозумілі повідомлення про результати.

Компоненти обираються відповідно до завдань, а не додаються лише заради візуального оформлення.

# Як проєктувати Task Flow

Використовуй послідовний алгоритм.

## Крок 1. Визначити User Goal

    Чого користувач хоче досягти?

Наприклад:

    Знайти відповідний навчальний курс.

## Крок 2. Визначити User Task

    Яке конкретне завдання потрібно виконати?

Наприклад:

    Знайти курс для початківців
    і перевірити його програму.

## Крок 3. Визначити Entry Point

    Звідки користувач починає?

Наприклад:

    Головна сторінка.
    Каталог.
    Пошукова система.
    Пряме посилання на курс.

## Крок 4. Розкласти завдання на кроки

    1. Відкрити каталог.
    2. Вибрати категорію.
    3. Застосувати фільтр рівня.
    4. Переглянути результати.
    5. Відкрити сторінку курсу.
    6. Переглянути програму.

## Крок 5. Знайти Decision Points

    Чи відповідає курс потрібному рівню?

    Чи містить він потрібні теми?

    Чи потрібно повернутися до результатів пошуку?

## Крок 6. Визначити Alternative Flows

    Користувач може шукати за назвою.
    Може змінити фільтри.
    Може перейти до іншої категорії.

## Крок 7. Визначити Error Flows

    Пошук не дав результатів.
    Каталог не завантажився.
    Сторінка курсу недоступна.

## Крок 8. Визначити завершення

    Користувач знайшов курс,
    переглянув програму
    та може прийняти рішення.

## Крок 9. Перевірити Task Flow

    Чи можна виконати завдання без пояснень?

    Чи зрозумілий кожен крок?

    Чи є тупикові сценарії?

    Чи зрозуміло, як повернутися назад?

    Чи підтверджується результат?

## Крок 10. Покращити інтерфейс

    Прибрати непотрібні кроки.
    Уточнити назви елементів.
    Покращити видимість наступної дії.
    Додати потрібні стани та повідомлення.
    Перевірити зміни на користувачах.

# Практичний приклад: User Task для реєстрації

## User Goal

    Створити обліковий запис
    і отримати доступ до платформи.

## User Task

    Зареєструватися.

## Prerequisites

    Користувач має доступ до платформи.
    Реєстрація доступна для його сценарію.

## Happy Path

    1. Відкрити сторінку реєстрації.
    2. Ввести email.
    3. Створити пароль.
    4. Заповнити інші обов'язкові поля.
    5. Погодитися з необхідними умовами.
    6. Надіслати форму.
    7. Виконати потрібне підтвердження.
    8. Побачити результат.

## Alternative Flow

    Користувач уже має обліковий запис.

    Він переходить до сторінки входу,
    а не створює новий обліковий запис.

## Error Flow

    Email має неправильний формат.
        ↓
    Система показує повідомлення.
        ↓
    Користувач виправляє email.

    Пароль не відповідає вимогам.
        ↓
    Система пояснює вимоги.
        ↓
    Користувач змінює пароль.

## UI-рішення

    Зрозумілий заголовок.
    Лише необхідні поля.
    Видимі вимоги до пароля.
    Повідомлення про помилки біля відповідних полів.
    Збереження коректно введених даних.
    Доступний спосіб переходу до входу.
    Підтвердження успішного завершення.

## Success Criteria

    Обліковий запис успішно створено.
    Необхідні перевірки завершено.
    Користувач розуміє, що робити далі.

# Практичний приклад: User Task для пошуку розкладу

Продукт:

    Вебсайт парафії.

## User Goal

    Дізнатися час богослужіння
    на конкретну дату.

## User Task

    Знайти потрібний запис у розкладі.

## Entry Point

    Головна сторінка сайту.

## Task Steps

    1. Відкрити розділ «Розклад богослужінь».
    2. Знайти потрібну дату.
    3. Переглянути назву богослужіння.
    4. Знайти час початку.

## Possible Pain Points

    Розділ важко знайти.
    Дати розташовані без зрозумілого порядку.
    Час початку недостатньо помітний.
    Актуальні записи змішані з минулими.
    На смартфоні текст важко читати.

## UI-рішення

    Зрозуміла назва розділу.
    Послідовний порядок дат.
    Виразне відображення часу.
    Зрозуміле розділення актуальних і минулих записів.
    Адаптивний макет.
    Читабельна типографіка.

## Success Criteria

    Користувач знайшов потрібну дату.
    Правильно визначив час початку.
    Зрозумів, до якого богослужіння належить запис.

## Usability Test

    Завдання учаснику:
    «Знайдіть час богослужіння на вказану дату».

    Спостерігати:
    Чи швидко користувач знаходить розклад?
    Чи правильно розуміє інформацію?
    Чи робить помилки?
    Чи потребує допомоги?

    Придбати потрібний товар.

    Користувач бачить підтвердження.
    Подальші дії зрозумілі.

# Usability Testing для User Tasks

Usability Testing — перевірка того, наскільки легко користувачі можуть виконувати конкретні завдання за допомогою інтерфейсу.

Замість запитання:

    «Вам подобається цей дизайн?»

краще запропонувати конкретне завдання:

    «Знайдіть потрібний курс
    і з'ясуйте, які теми він містить».

Під час тестування потрібно спостерігати за реальною поведінкою.

## Що перевіряти

    Чи завершив користувач завдання?

    Чи правильно зрозумів інструкцію?

    Чи знайшов потрібну функцію?

    Чи обрав правильний шлях?

    Чи виникли помилки?

    Чи повертався він до попередніх кроків?

    Чи потребував допомоги?

    Чи зрозумів результат?

## Що вимірювати

    Task Completion Rate.
    Час виконання.
    Кількість помилок.
    Кількість повторних спроб.
    Кількість запитів про допомогу.
    Кількість повернень назад.

## Як формулювати завдання

Завдання має описувати мету, але не підказувати конкретний шлях.

Невдалий приклад:

    «Натисніть меню Courses,
    потім фільтр Beginner,
    а потім відкрийте першу картку».

Краще:

    «Знайдіть курс для початківців,
    який містить уроки з React».

Другий варіант дає змогу перевірити, чи може користувач самостійно знайти потрібну інформацію.

Докладніше Usability Testing розглядається в розділі:

    09-usability-testing

# Типові помилки під час проєктування User Tasks

## 1. Плутати User Goal із User Task

Неправильно:

    User Goal:
    Натиснути кнопку «Зберегти».

Краще:

    User Goal:
    Зберегти внесені зміни.

Натискання кнопки — лише одна дія в процесі.

## 2. Пропускати необхідні кроки

Якщо між вибором товару та підтвердженням замовлення відсутні необхідні перевірки, користувач може припуститися помилки.

Потрібно визначити всі кроки, необхідні для коректного результату.

## 3. Додавати зайві кроки

Наприклад:

    1. Ввести email.
    2. Натиснути «Продовжити».
    3. На наступному екрані повторно ввести email.

Якщо повторне введення не потрібне, такий крок створює зайве навантаження.

## 4. Проєктувати тільки Happy Path

Інтерфейс також повинен враховувати:

    помилки;
    відсутність результатів;
    недоступність функцій;
    втрату з'єднання;
    скасування;
    повторні спроби.

## 5. Не показувати результат дії

Після натискання «Зберегти» користувач повинен розуміти, чи зміни збережено.

Якщо результат не зрозумілий, людина може повторити дію або залишити сторінку з невпевненістю.

## 6. Використовувати незрозумілі назви

Неправильно:

    Execute.
    Process.
    Continue.

Такі назви можуть бути незрозумілими без контексту.

Краще використовувати назви, які пояснюють результат:

    Зберегти зміни.
    Переглянути замовлення.
    Перейти до оплати.

## 7. Не передбачати повернення назад

У складних процесах користувач може захотіти змінити попередній вибір.

Потрібно вирішити:

    чи можна повернутися;
    чи збережуться введені дані;
    чи потрібно повторити перевірки;
    чи не буде втрачено важливий прогрес.

## 8. Зменшувати кількість кроків за будь-яку ціну

Менше кроків не завжди означає кращий UX.

Наприклад, перед фінансовою операцією перевірка отримувача та суми може бути необхідною.

Мета — усунути непотрібні дії, зберігаючи необхідні перевірки.

## 9. Ігнорувати різні точки входу

Користувач може почати завдання не з головної сторінки.

Він може перейти безпосередньо до товару, курсу або форми з іншого джерела.

Потрібно перевіряти різні сценарії входу.

## 10. Вважати завершенням натискання кнопки

Натискання кнопки не гарантує, що система виконала операцію.

Завдання вважається успішним лише тоді, коли досягнуто визначеного результату.

## 11. Не перевіряти завдання на користувачах

Дизайнер може вважати шлях очевидним, але користувачі можуть інтерпретувати його інакше.

Task Flow потрібно перевіряти через реальні сценарії та usability testing.

## 12. Орієнтуватися тільки на кількість кліків

Важливі також:

    правильність результату;
    зрозумілість;
    час;
    когнітивне навантаження;
    кількість помилок;
    доступність;
    безпека.

Це спрощена модель для проєктування інтерфейсів. У реальних продуктах завдання можуть містити альтернативні шляхи, повторні спроби, повернення назад і взаємозалежні підзавдання.

---

# Головне

• User Task — це завдання, яке користувач виконує для досягнення результату.

• User Goal описує бажаний результат, а User Task — дії для його досягнення.

• User Action — конкретна дія користувача в інтерфейсі.

• Task Step — окремий крок у виконанні завдання.

• Task Flow показує послідовність кроків і можливі переходи.

• Task Analysis допомагає зрозуміти структуру завдання та знайти проблеми.

• Hierarchical Task Analysis дозволяє розкласти складне завдання на підзавдання.

• Happy Path описує основний успішний сценарій.

• Alternative Flow описує альтернативний шлях.

• Error Flow описує поведінку під час помилок або перешкод.

• Decision Point — місце, де користувач або система обирає подальший шлях.

• Entry Point — точка початку завдання.

• Exit Point — точка завершення або виходу зі сценарію.

• Prerequisites — умови, необхідні перед початком завдання.

• Postconditions — умови, які повинні виконуватися після завершення.

• Task Complexity залежить від кількості рішень, складності інформації, досвіду та інших чинників.

• Task Frequency описує, наскільки часто виконується завдання.

• Task Priority допомагає визначити, які завдання потребують особливої уваги.

• Task Efficiency описує витрачені ресурси, а Task Effectiveness — успішність досягнення результату.

• Task Completion Rate показує частку успішно завершених завдань.

• Не потрібно скорочувати кількість кроків ціною зрозумілості або безпеки.

• Хороший Task Flow має враховувати не тільки основний сценарій, а й помилки та альтернативи.

• Після важливої дії користувач повинен розуміти, що відбулося.

• Завершення завдання потрібно визначати за фактичним результатом, а не лише за натисканням кнопки.

• Task Flow потрібно перевіряти на реальних користувацьких сценаріях.

• Основна мета UX-дизайнера — допомогти користувачу виконати потрібне завдання зрозуміло, ефективно, доступно та без зайвих перешкод.

• Головне запитання під час проєктування User Tasks:

    «Чи може користувач самостійно виконати
    потрібне завдання, зрозуміти результат
    і відновитися, якщо щось піде не так?»
