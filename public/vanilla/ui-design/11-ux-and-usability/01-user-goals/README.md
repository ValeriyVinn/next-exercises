# 01. User Goals

User Goals (цілі користувача) — це результати, яких користувач хоче досягти за допомогою продукту, вебсайту, застосунку або певної функції.

У UI/UX Design розуміння цілей користувача допомагає створювати інтерфейси, які не просто виглядають привабливо, а й допомагають людям виконувати потрібні дії зрозуміло, швидко та без зайвих перешкод.

Наприклад, користувач відкриває інтернет-магазин не просто для того, щоб переглядати картки товарів. Його мета може полягати в тому, щоб знайти потрібний товар, порівняти ціни та оформити замовлення.

Інтерфейс має підтримувати цю мету.

User Goals допомагають відповісти на запитання:

    Хто користувач?
    Чого він хоче досягти?
    Навіщо йому це потрібно?
    Який результат він очікує?
    Як інтерфейс може допомогти йому досягти цього результату?

Основні поняття:

    User Need
    User Motivation
    User Intent

## Що потрібно пам'ятати

• User Goal — це результат, якого користувач хоче досягти.

• User Need — це потреба, яку користувач прагне задовольнити.

• User Motivation — причина, через яку користувач хоче виконати певну дію.

• User Intent — намір користувача в конкретній ситуації.

• User Task — конкретна дія або послідовність дій, необхідних для досягнення мети.

• User Outcome — результат, отриманий користувачем після виконання дій.

• User Value — користь, яку користувач отримує від продукту.

• Business Goal — результат, якого прагне досягти бізнес.

• Інтерфейс має допомагати користувачу досягати його цілей, а не змушувати пристосовуватися до внутрішньої структури продукту.

• Одна й та сама функція може підтримувати різні цілі різних користувачів.

• Користувач не завжди може точно сформулювати свою справжню потребу.

• Не можна автоматично вважати, що всі користувачі мають однакові цілі.

• User Goals потрібно досліджувати, а не лише припускати.

• Хороший UI скорочує шлях до бажаного результату та усуває непотрібні перешкоди.

• Успіх дизайну визначається не тільки зовнішнім виглядом, а й тим, наскільки добре користувач може досягти своєї мети.

# User Goal

User Goal — кінцевий результат, якого користувач хоче досягти за допомогою продукту.

Наприклад, користувач відкриває освітню платформу.

Його ціль:

    Зрозуміти тему JavaScript
        ↓
    Знайти навчальний матеріал
        ↓
    Пройти урок
        ↓
    Виконати практичне завдання
        ↓
    Перевірити свої знання

Головна мета тут не просто натиснути кнопку або відкрити сторінку.

Головна мета — навчитися певної теми.

Інтерфейс має підтримувати весь цей процес.

## Приклади User Goals

### Інтернет-магазин

    User Goal:
    Купити потрібний товар.

Можливі дії:

    знайти товар;
    переглянути характеристики;
    порівняти ціни;
    додати товар до кошика;
    оформити замовлення.

### Освітня платформа

    User Goal:
    Навчитися певної теми.

Можливі дії:

    знайти курс;
    переглянути урок;
    виконати вправу;
    отримати зворотний зв'язок;
    перевірити прогрес.

### Банківський застосунок

    User Goal:
    Переказати гроші іншій людині.

Можливі дії:

    відкрити перекази;
    вибрати отримувача;
    ввести суму;
    перевірити дані;
    підтвердити операцію.

### Медичний вебсайт

    User Goal:
    Записатися на прийом до лікаря.

Можливі дії:

    знайти спеціаліста;
    вибрати дату;
    вибрати час;
    ввести контактні дані;
    підтвердити запис.

### Церковний вебсайт

    User Goal:
    Знайти розклад богослужінь.

Можливі дії:

    відкрити розклад;
    знайти потрібну дату;
    переглянути час служби;
    дізнатися про особливості богослужіння.

# User Goal vs User Task

User Goal і User Task пов'язані, але це різні поняття.

**User Goal** — те, чого людина хоче досягти.

**User Task** — те, що вона робить для досягнення цієї мети.

Наприклад:

    User Goal:
    Знайти відповідний навчальний курс.

    User Tasks:
    1. Відкрити каталог.
    2. Вибрати категорію.
    3. Застосувати фільтри.
    4. Переглянути результати.
    5. Відкрити сторінку курсу.
    6. Порівняти програми.
    7. Вибрати курс.

Ще один приклад:

    User Goal:
    Дізнатися час наступного богослужіння.

    User Tasks:
    1. Відкрити сайт парафії.
    2. Знайти розділ розкладу.
    3. Вибрати потрібну дату.
    4. Переглянути час.

Мета пояснює, навіщо користувач взаємодіє з продуктом.

Завдання пояснюють, що саме він робить.

Важливо не плутати ціль із натисканням кнопки.

Наприклад:

    Натиснути кнопку «Увійти»
        ↓
    User Task

    Отримати доступ до власних навчальних матеріалів
        ↓
    User Goal

---

# User Goal vs User Need

User Need — потреба користувача, яку він хоче задовольнити.

User Goal — бажаний результат, який допомагає задовольнити цю потребу.

Наприклад:

    User Need:
    Отримувати знання.

    User Goal:
    Навчитися працювати з React.

    User Tasks:
    Знайти курс, пройти уроки, виконати проєкт.

Інший приклад:

    User Need:
    Почуватися впевнено під час планування поїздки.

    User Goal:
    Знайти надійний готель із відповідною ціною.

    User Tasks:
    Ввести місце призначення, вибрати дати,
    порівняти варіанти та прочитати умови.

Need відповідає на запитання:

    Яка потреба стоїть за поведінкою користувача?

Goal відповідає на запитання:

    Якого результату користувач хоче досягти?

Task відповідає на запитання:

    Які дії користувач виконує?

Спрощена модель:

    User Need
        ↓
    User Goal
        ↓
    User Tasks
        ↓
    User Outcome

# User Motivation

User Motivation — причина, через яку користувач хоче досягти певної мети.

Два користувачі можуть мати однакову мету, але різну мотивацію.

Наприклад:

    User Goal:
    Вивчити англійську мову.

    User A:
    Хоче спілкуватися під час подорожей.

    User B:
    Хоче отримати роботу в міжнародній компанії.

    User C:
    Хоче читати технічну документацію.

Мета в усіх однакова, але мотивація відрізняється.

Це може впливати на дизайн продукту.

Користувачу, який вивчає англійську для роботи, можуть бути важливі:

    професійна лексика;
    технічні тексти;
    моделювання робочих ситуацій;
    підготовка до співбесід.

Користувачу, який готується до подорожей, можуть бути важливі:

    повсякденні діалоги;
    запитання про дорогу;
    спілкування в готелі;
    ситуації в ресторані.

Дизайн має враховувати не тільки бажаний результат, а й причину, через яку він важливий користувачу.

---

# User Intent

User Intent — намір користувача в конкретний момент взаємодії з продуктом.

Наприклад, користувач відкриває інтернет-магазин.

Його можливі наміри:

    знайти конкретний товар;
    порівняти два товари;
    перевірити наявність;
    дізнатися умови доставки;
    купити товар;
    перевірити статус замовлення.

Одна людина може мати різні наміри під час різних відвідувань сайту.

Наприклад:

    Відвідування 1:
    Дослідити доступні товари.

    Відвідування 2:
    Порівняти характеристики.

    Відвідування 3:
    Оформити замовлення.

Інтерфейс повинен допомагати користувачу виконувати поточний намір.

Якщо людина хоче перевірити статус замовлення, їй не потрібно спочатку проходити весь каталог товарів.

---

# User Outcome

User Outcome — результат, який отримує користувач після взаємодії з продуктом.

Наприклад:

    User Goal:
    Записатися до лікаря.

    User Tasks:
    Вибрати спеціаліста, дату та час.

    User Outcome:
    Запис успішно створено,
    а користувач отримав підтвердження.

Результат може бути позитивним або негативним.

### Успішний outcome

    Користувач вибрав потрібний товар.
    Замовлення оформлено.
    Система підтвердила покупку.

### Негативний outcome

    Користувач не знайшов потрібний товар.
    Не зрозумів умови доставки.
    Покинув процес оформлення.

Під час проєктування UI потрібно враховувати обидва варіанти.

Недостатньо створити послідовність екранів.

Потрібно переконатися, що користувач може завершити процес і зрозуміти його результат.

---

# User Value

User Value — користь, яку користувач отримує від продукту.

Наприклад, освітня платформа може надавати такі цінності:

    доступ до навчальних матеріалів;
    зрозумілу структуру курсу;
    можливість практикуватися;
    швидкий зворотний зв'язок;
    відстеження прогресу.

Користувач оцінює продукт не лише за кількістю функцій.

Важливо, чи допомагають ці функції досягати потрібного результату.

Наприклад:

    20 складних фільтрів
        ↓
    Не обов'язково велика користь.

    4 зрозумілі фільтри,
    які допомагають швидко знайти товар
        ↓
    Можливо, більша користь для користувача.

User Value може включати:

    економію часу;
    зменшення зусиль;
    зниження невизначеності;
    отримання потрібної інформації;
    підвищення впевненості;
    успішне виконання завдання.

---

# User Context

User Context — обставини, у яких користувач взаємодіє з продуктом.

Контекст може змінюватися залежно від ситуації.

Основні складові:

    фізичне середовище;
    пристрій;
    доступний час;
    рівень знань;
    досвід роботи з подібними продуктами;
    емоційний стан;
    доступність інтернету;
    доступність інтерфейсу;
    мета поточного відвідування.

Наприклад, людина хоче знайти адресу лікарні.

Ситуація A:

    Користувач сидить удома.
    Має достатньо часу.
    Використовує ноутбук.

Ситуація B:

    Користувач перебуває на вулиці.
    Використовує смартфон.
    Потребує швидкої відповіді.

В обох випадках мета може бути однаковою, але інтерфейс повинен підтримувати різні умови використання.

Для мобільного сценарію особливо важливими можуть бути:

    помітна адреса;
    зрозуміла кнопка побудови маршруту;
    читабельний текст;
    мінімальна кількість зайвих дій;
    зручні інтерактивні елементи.

# Functional, Emotional та Social Goals

Цілі користувача можуть мати різну природу.

## Functional Goals

Functional Goal — практичний результат, якого користувач хоче досягти.

Приклади:

    переказати гроші;
    знайти товар;
    забронювати готель;
    створити документ;
    пройти навчальний тест;
    знайти розклад богослужінь.

Такі цілі пов'язані з виконанням конкретної роботи.

## Emotional Goals

Emotional Goal — емоційний результат, якого користувач хоче досягти.

Приклади:

    почуватися впевнено;
    зменшити тривогу;
    уникнути невизначеності;
    відчувати контроль над процесом;
    бути впевненим у правильності своїх дій.

Наприклад, під час банківського переказу користувач хоче не тільки переказати гроші, а й переконатися, що кошти надійдуть правильному отримувачу.

Для підтримки цієї мети інтерфейс може показувати:

    ім'я отримувача;
    суму переказу;
    комісію;
    підсумок перед підтвердженням;
    статус операції.

## Social Goals

Social Goal — результат, пов'язаний із взаємодією з іншими людьми, соціальним сприйняттям або належністю до певної спільноти.

Приклади:

    поділитися власною роботою;
    співпрацювати з командою;
    отримати відгук;
    продемонструвати професійні навички;
    підтримувати зв'язок із друзями.

Наприклад, у навчальному застосунку користувач може хотіти не лише вивчити тему, а й показати результати навчання викладачу.

Одна й та сама ситуація може включати декілька типів цілей.

    Functional:
    Завершити навчальний курс.

    Emotional:
    Відчути впевненість у своїх знаннях.

    Social:
    Продемонструвати результати навчання.

# Primary Goal та Secondary Goals

Primary Goal — головна мета користувача в конкретному сценарії.

Secondary Goals — додаткові цілі, які підтримують основну.

Наприклад, сторінка товару в інтернет-магазині.

    Primary Goal:
    Вирішити, чи варто купувати товар.

    Secondary Goals:
    Дізнатися ціну.
    Переглянути характеристики.
    Перевірити наявність.
    Прочитати відгуки.
    Дізнатися умови доставки.

Другий приклад — сторінка розкладу богослужінь.

    Primary Goal:
    Дізнатися час служби.

    Secondary Goals:
    Знайти адресу храму.
    Перевірити дату.
    Дізнатися про святкові особливості.
    Знайти контактну інформацію.

Під час дизайну важливо визначити головну мету сторінки.

Якщо всі елементи виглядають однаково важливими, користувачеві складніше визначити, з чого почати.

Візуальна ієрархія повинна допомагати досягати primary goal.

Наприклад:

    Заголовок сторінки
        ↓
    Основна інформація
        ↓
    Головна дія
        ↓
    Додаткова інформація

---

# Explicit та Implicit Goals

## Explicit Goals

Explicit Goal — мета, яку користувач може прямо сформулювати.

Наприклад:

    «Я хочу знайти курс React для початківців».

    «Я хочу записатися до стоматолога».

    «Я хочу перевірити розклад на неділю».

Такі цілі часто можна виявити через інтерв'ю, опитування або аналіз запитів.

## Implicit Goals

Implicit Goal — мета, яка не завжди прямо озвучується, але може випливати з поведінки, контексту або потреб користувача.

Наприклад, користувач хоче оформити замовлення.

Окрім очевидної мети, він може також прагнути:

    не помилитися з адресою;
    не переплатити за доставку;
    бути впевненим у безпеці платежу;
    розуміти, коли прибуде товар.

Ці додаткові цілі можуть не бути озвучені.

Проте вони впливають на досвід взаємодії.

Важливо: implicit goals — це гіпотези, які потрібно перевіряти. Не можна вважати припущення про користувача доведеним фактом.

# Short-Term та Long-Term Goals

## Short-Term Goals

Short-Term Goal — мета, яку користувач хоче досягти за короткий проміжок часу або в межах однієї взаємодії.

Приклади:

    знайти потрібну сторінку;
    завершити оплату;
    завантажити документ;
    знайти відповідь на запитання.

## Long-Term Goals

Long-Term Goal — довгостроковий результат, для якого користувач може регулярно використовувати продукт.

Приклади:

    опанувати нову професію;
    вивчити іноземну мову;
    покращити фізичну форму;
    систематично вести фінансовий облік;
    організувати навчання протягом року.

Наприклад, освітній застосунок:

    Long-Term Goal:
    Опанувати JavaScript.

    Short-Term Goal:
    Зрозуміти цикли.

    User Tasks:
    Прочитати матеріал.
    Переглянути приклади.
    Написати код.
    Виконати вправи.

Дизайн має допомагати користувачу як виконувати окремі завдання, так і рухатися до довгострокового результату.

---

# User Goals та Business Goals

User Goal і Business Goal не завжди збігаються.

**User Goal** — результат, якого прагне користувач.

**Business Goal** — результат, якого прагне організація або власник продукту.

Наприклад, інтернет-магазин.

    User Goal:
    Швидко знайти потрібний товар
    і придбати його за прийнятною ціною.

    Business Goal:
    Збільшити кількість успішних замовлень
    і підтримувати прибутковість.

Інший приклад — освітня платформа.

    User Goal:
    Навчитися програмувати.

    Business Goal:
    Залучати студентів,
    підтримувати якість навчання
    та отримувати дохід від курсів.

Цілі можуть підтримувати одна одну.

Наприклад, зрозумілий процес оформлення замовлення допомагає користувачу завершити покупку та може сприяти бізнес-результату.

Однак конфлікти також можливі.

Наприклад:

    Користувач хоче:
    Швидко знайти потрібну інформацію.

    Бізнес хоче:
    Показати більше рекламних пропозицій.

Якщо реклама заважає виконати завдання, бізнес-рішення може погіршити UX.

Хороший дизайн має враховувати інтереси бізнесу, але не повинен без потреби створювати перешкоди для користувача.

Особливо важливо уникати dark patterns — оманливих або маніпулятивних дизайнерських рішень, які підштовхують людей до дій, що суперечать їхнім інтересам.

---

# Goal-Oriented Design

Goal-Oriented Design — підхід до проєктування, за якого рішення приймаються з урахуванням цілей користувача.

Замість запитання:

    Які екрани ми хочемо створити?

Потрібно спочатку запитати:

    Чого користувач хоче досягти?

    Які проблеми заважають йому?

    Які дії потрібні для досягнення результату?

    Яка інформація допоможе прийняти рішення?

    Як зрозуміти, що мету досягнуто?

Приклад.

Потрібно створити сторінку запису до лікаря.

Не варто починати лише з розміщення кнопок, карток і полів форми.

Спочатку визначаємо цілі:

    User Goal:
    Записатися до потрібного лікаря
    на зручний час.

    User Needs:
    Знайти відповідного спеціаліста.
    Перевірити доступні години.
    Зрозуміти умови запису.

    User Tasks:
    Вибрати спеціаліста.
    Вибрати дату.
    Вибрати час.
    Ввести необхідні дані.
    Підтвердити запис.

    Expected Outcome:
    Запис створено.
    Користувач бачить підтвердження.

Тепер можна визначати структуру сторінки, поля форми, кнопки, повідомлення та стани інтерфейсу.

---

# User-Centered Design

User-Centered Design (UCD) — підхід до розробки продуктів, у якому потреби, цілі, можливості та обмеження користувачів враховуються протягом усього процесу проєктування.

Основні принципи:

    1. Розуміти користувачів.
    2. Досліджувати їхні цілі та потреби.
    3. Враховувати контекст використання.
    4. Створювати й перевіряти дизайнерські рішення.
    5. Покращувати продукт на основі результатів перевірки.

Спрощений процес:

    User Research
        ↓
    Визначення User Goals
        ↓
    Формування вимог
        ↓
    Створення структури та UI
        ↓
    Прототипування
        ↓
    Usability Testing
        ↓
    Аналіз результатів
        ↓
    Покращення дизайну

User-Centered Design не означає, що потрібно виконувати кожне побажання кожного користувача.

Потрібно розуміти реальні проблеми, знаходити закономірності та приймати обґрунтовані рішення.

---

# Як визначати User Goals

Для визначення цілей можна використовувати декілька методів дослідження.

## User Interviews

User Interview — інтерв'ю з користувачем, яке допомагає зрозуміти його потреби, мотивацію, поведінку та проблеми.

Корисні запитання:

    Чого ви намагалися досягти?

    Що спонукало вас виконати цю дію?

    Як ви вирішували це завдання раніше?

    Що було найскладнішим?

    Якої інформації вам бракувало?

    Що ви вважали б успішним результатом?

    Що ви робили, коли не могли знайти потрібну функцію?

Краще запитувати про реальний досвід, ніж лише про гіпотетичні бажання.

Наприклад, запитання:

    «Розкажіть, як ви востаннє записувалися до лікаря».

часто дає більше корисної інформації, ніж:

    «Чи хотіли б ви мати зручний сайт для запису?»

## Observation

Observation — спостереження за тим, як користувач виконує реальні завдання.

Наприклад, користувачу пропонують знайти потрібний курс на навчальному сайті.

Дослідник спостерігає:

    куди користувач дивиться;
    які елементи відкриває;
    де зупиняється;
    які помилки робить;
    яку інформацію шукає;
    як розуміє результат.

Спостереження допомагає виявити проблеми, про які користувач може навіть не згадати під час інтерв'ю.

## Surveys

Survey — опитування, яке допомагає зібрати відповіді від більшої кількості людей.

Можна досліджувати:

    найважливіші цілі;
    частоту виконання завдань;
    типові труднощі;
    популярні функції;
    рівень задоволеності.

Опитування корисні для виявлення загальних тенденцій, але не завжди пояснюють причини поведінки.

## Analytics

Product Analytics — аналіз даних про використання продукту.

Можна досліджувати:

    які сторінки відвідують;
    які функції використовують;
    де користувачі залишають процес;
    скільки часу займають окремі кроки;
    як часто завершують цільову дію.

Наприклад, аналітика показує, що багато користувачів починають оформлення замовлення, але не завершують його.

Це сигнал для подальшого дослідження.

Сам по собі показник не пояснює причину. Потрібно перевірити, чи проблема пов'язана з формою, ціною доставки, помилками або іншими чинниками.

## Usability Testing

Usability Testing — перевірка того, наскільки добре користувачі можуть виконувати завдання за допомогою інтерфейсу.

Наприклад:

    Завдання:
    Знайдіть найближчий доступний час
    для запису до лікаря.

Під час тестування дослідник перевіряє:

    чи зрозуміла структура;
    чи легко знайти потрібну інформацію;
    чи зрозумілі елементи керування;
    чи може користувач завершити завдання;
    чи виникають помилки;
    чи зрозумілий кінцевий результат.

Usability Testing допомагає перевірити, чи відповідає реальний інтерфейс цілям користувача.

---

# Jobs to Be Done (JTBD)

Jobs to Be Done — підхід, який допомагає зрозуміти, яку роботу користувач намагається виконати за допомогою продукту.

Основна ідея:

    Користувач обирає продукт не просто через його функції.
    Він хоче досягти певного результату в конкретній ситуації.

Наприклад, людина користується застосунком для нотаток.

Її справжня мета може бути не в тому, щоб створювати нотатки.

Вона хоче:

    не забути важливі справи;
    зберегти ідею;
    підготуватися до зустрічі;
    організувати робочі завдання.

Функція нотаток є засобом досягнення результату.

## Формула JTBD

Один із поширених способів сформулювати job:

    Коли [ситуація],
    я хочу [мотивація або дія],
    щоб [очікуваний результат].

Приклад:

    Коли я готуюся до співбесіди,
    я хочу організувати навчальні матеріали,
    щоб швидко повторювати потрібні теми.

Інший приклад:

    Коли я планую відвідування храму,
    я хочу швидко знайти розклад,
    щоб знати, коли починається богослужіння.

JTBD допомагає не зосереджуватися виключно на функціях продукту.

Він спрямовує увагу на ситуацію, мотивацію та бажаний результат.

---

# User Goals та User Persona

User Persona — узагальнений образ типового представника певної групи користувачів, створений на основі досліджень.

Персона може включати:

    контекст використання;
    потреби;
    цілі;
    поведінку;
    досвід;
    проблеми;
    мотивацію.

Приклад:

    Persona:
    Початківець у програмуванні.

    Context:
    Вивчає JavaScript після роботи.

    User Need:
    Мати зрозумілий шлях навчання.

    User Goal:
    Навчитися самостійно створювати прості застосунки.

    Pain Points:
    Занадто складні пояснення.
    Відсутність практичних завдань.
    Невизначеність щодо наступного кроку.

    Design Opportunities:
    Послідовна структура уроків.
    Невеликі практичні завдання.
    Зрозумілий зворотний зв'язок.
    Видимий прогрес навчання.

Персона не повинна бути вигаданим набором стереотипів.

Вона має відображати реальні дослідницькі дані або чітко позначені гіпотези, які ще потрібно перевірити.

---

# User Journey та User Goals

User Journey — шлях користувача під час взаємодії з продуктом для досягнення певної мети.

Наприклад, користувач хоче пройти навчальний курс.

    1. Дізнається про платформу.
    2. Переглядає каталог курсів.
    3. Обирає курс.
    4. Реєструється.
    5. Починає навчання.
    6. Виконує завдання.
    7. Відстежує прогрес.
    8. Завершує курс.

На кожному етапі можуть виникати різні потреби.

    Каталог:
    Знайти відповідний курс.

    Реєстрація:
    Створити обліковий запис без зайвих перешкод.

    Навчання:
    Зрозуміти матеріал.

    Практика:
    Перевірити свої знання.

    Завершення:
    Переконатися, що курс пройдено.

User Journey допомагає побачити не тільки окрему сторінку, а й увесь процес досягнення мети.

---

# Pain Points

Pain Point — проблема, перешкода або джерело незручності, яке заважає користувачу досягти мети.

Приклади:

    не може знайти потрібну сторінку;
    не розуміє назви пунктів меню;
    не знає, які поля форми обов'язкові;
    не розуміє повідомлення про помилку;
    не може відновити пароль;
    не бачить підтвердження завершення дії;
    змушений повторно вводити вже надані дані.

Приклад для навчальної платформи:

    User Goal:
    Знайти наступний урок.

    Pain Point:
    Уроки розташовані без зрозумілого порядку.

    Design Solution:
    Показати послідовність уроків,
    поточний урок і наступну рекомендовану дію.

Важливо розрізняти проблему та її можливе рішення.

Наприклад:

    Pain Point:
    Користувачі не можуть швидко знайти
    потрібну категорію товарів.

    Можливе рішення:
    Переглянути структуру навігації.

Не потрібно відразу припускати, що єдине правильне рішення — додати нову кнопку.

Спочатку потрібно зрозуміти причину проблеми.

---

# Success Criteria

Success Criteria — критерії, за якими визначають, чи вдалося користувачу досягти мети.

Наприклад:

    User Goal:
    Оформити замовлення.

    Success Criteria:
    Замовлення створено.
    Користувач бачить підтвердження.
    Дані замовлення доступні для перевірки.

Для навчальної платформи:

    User Goal:
    Завершити практичне завдання.

    Success Criteria:
    Користувач надіслав відповідь.
    Система перевірила результат.
    Користувач отримав зрозумілий feedback.

Критерії можуть бути кількісними та якісними.

## Quantitative Criteria

Кількісні показники:

    task completion rate;
    кількість помилок;
    час виконання завдання;
    кількість невдалих спроб;
    частка користувачів, які залишили процес.

## Qualitative Criteria

Якісні показники:

    чи розуміє користувач наступний крок;
    чи впевнений він у правильності своїх дій;
    чи зрозумілий результат;
    які труднощі він описує;
    які елементи викликають плутанину.

Не потрібно автоматично оптимізувати інтерфейс лише за швидкістю.

Для банківського переказу, наприклад, додаткова перевірка реквізитів може бути корисною, навіть якщо вона збільшує час виконання.

Критерії успіху мають враховувати контекст і ризики завдання.

---

# Перетворення User Goals на UI-рішення

Під час проєктування потрібно простежувати зв'язок між метою, проблемою та рішенням.

Приклад: сторінка розкладу богослужінь.

## Крок 1. Визначити User Goal

    Користувач хоче дізнатися,
    коли відбудеться богослужіння.

## Крок 2. Визначити User Needs

    Знайти потрібну дату.
    Побачити час початку.
    Зрозуміти, яке саме богослужіння заплановано.

## Крок 3. Визначити Pain Points

    Розклад важко знайти.
    Дати розташовані незрозуміло.
    Час початку не виділений.
    Старі записи складно відрізнити від актуальних.

## Крок 4. Визначити UI-рішення

    Зрозуміла назва розділу.
    Послідовний порядок дат.
    Помітний час початку.
    Чітке розділення актуальних і минулих записів.
    Адаптивний макет для смартфонів.

## Крок 5. Визначити Success Criteria

    Користувач може знайти потрібну дату.
    Час богослужіння зрозумілий.
    Користувач не плутає актуальний розклад
    із застарілою інформацією.

## Крок 6. Перевірити рішення

    Запропонувати користувачам знайти
    час конкретного богослужіння.

    Спостерігати, чи виконують вони завдання
    без додаткових пояснень.

    За результатами покращити інтерфейс.

---

# Приклад: User Goals для інтернет-магазину

## Початкові дані

Продукт:

    Інтернет-магазин побутової техніки.

Користувач:

    Людина, яка хоче придбати чайник.

User Goal:

    Знайти відповідний чайник
    і придбати його.

## User Needs

    Дізнатися ціну.
    Порівняти характеристики.
    Перевірити наявність.
    Дізнатися умови доставки.
    Переконатися, що обрано правильний товар.

## User Tasks

    1. Відкрити категорію.
    2. Знайти чайники.
    3. Застосувати фільтри.
    4. Відкрити картку товару.
    5. Перевірити характеристики.
    6. Додати товар до кошика.
    7. Оформити замовлення.

## Pain Points

    Незрозумілі фільтри.
    Недостатньо характеристик.
    Прихована вартість доставки.
    Складна форма замовлення.
    Відсутність підтвердження покупки.

## UI-рішення

    Чіткі назви категорій.
    Зрозумілі фільтри.
    Видима ціна.
    Основні характеристики в картці товару.
    Прозорі умови доставки.
    Зрозумілий процес оформлення.
    Повідомлення про успішне замовлення.

## Success Criteria

    Користувач знайшов відповідний товар.
    Зрозумів його характеристики.
    Побачив повну вартість.
    Завершив оформлення.
    Отримав підтвердження.

# Приклад: User Goals для освітньої платформи

Продукт:

    Навчальна платформа з програмування.

User Goal:

    Вивчити тему та навчитися
    застосовувати знання на практиці.

## User Needs

    Зрозуміти структуру навчання.
    Знайти потрібний матеріал.
    Перевірити розуміння.
    Виправити помилки.
    Бачити прогрес.

## User Tasks

    1. Відкрити курс.
    2. Вибрати тему.
    3. Прочитати пояснення.
    4. Переглянути приклад.
    5. Виконати вправу.
    6. Перевірити відповідь.
    7. Перейти до наступної теми.

## Pain Points

    Занадто великі блоки тексту.
    Незрозумілі інструкції.
    Відсутність практики.
    Незрозумілі повідомлення про помилки.
    Відсутність видимого прогресу.

## UI-рішення

    Логічна структура уроків.
    Невеликі тематичні блоки.
    Приклади коду.
    Практичні завдання.
    Зрозумілий feedback.
    Позначення завершених тем.
    Видимий наступний крок.

## Success Criteria

    Користувач знайшов потрібну тему.
    Зрозумів інструкцію.
    Виконав практичне завдання.
    Зрозумів результат перевірки.
    Може продовжити навчання.

# Типові помилки під час визначення User Goals

## 1. Плутати мету з функцією

Неправильно:

    User Goal:
    Натиснути кнопку пошуку.

Краще:

    User Goal:
    Знайти потрібний товар.

Кнопка пошуку — інструмент для досягнення мети.

## 2. Плутати мету із завданням

Неправильно:

    User Goal:
    Заповнити форму.

Краще:

    User Goal:
    Зареєструватися на курс.

Заповнення форми є одним із завдань у процесі реєстрації.

## 3. Вважати власні припущення фактами

Неправильно:

    Користувачам точно потрібна
    окрема сторінка з усіма фільтрами.

Краще:

    Гіпотеза:
    Користувачам складно знаходити потрібні фільтри.

    Як перевірити:
    Провести інтерв'ю та usability testing.

## 4. Зосереджуватися тільки на бізнес-цілях

Неправильно:

    Збільшити кількість натискань
    на рекламні пропозиції.

Краще:

    Допомогти користувачеві знайти
    релевантну пропозицію без перешкод
    для виконання основного завдання.

## 5. Визначати занадто багато головних цілей

Якщо всі цілі позначені як primary, стає важко визначити пріоритети.

Потрібно з'ясувати:

    Яка мета головна в цьому сценарії?

    Які цілі її підтримують?

    Які елементи можна зробити другорядними?

## 6. Ігнорувати контекст

Одна й та сама мета може вимагати різних UI-рішень залежно від умов використання.

Наприклад:

    Пошук адреси на ноутбуці
    та пошук адреси на смартфоні в дорозі.

Контекст впливає на розмір елементів, обсяг інформації, навігацію та кількість кроків.

## 7. Вважати, що одна мета підходить усім

Різні користувачі можуть використовувати один продукт по-різному.

Наприклад, на освітній платформі:

    Початківець хоче зрозуміти основи.

    Досвідчений користувач хоче швидко
    знайти конкретну довідкову інформацію.

Інтерфейс повинен враховувати важливі відмінності між групами користувачів.

## 8. Не перевіряти досягнення мети

Наявність кнопки або завершеного екрана не гарантує успішного результату.

Потрібно перевірити, чи справді користувач:

    виконав потрібне завдання;
    зрозумів результат;
    не припустився критичної помилки;
    зміг продовжити свій шлях.

## 9. Додавати функції без визначеної потреби

Нова функція не обов'язково покращує UX.

Перед її створенням потрібно відповісти:

    Яку User Goal вона підтримує?

    Яку проблему вирішує?

    Для кого вона потрібна?

    Як перевірити її корисність?

# Практичний алгоритм визначення User Goals

Використовуй цей алгоритм під час проєктування будь-якої сторінки або компонента.

    Крок 1. Визначити користувача.

    Хто використовуватиме продукт?

    Крок 2. Визначити контекст.

    У якій ситуації людина використовує продукт?

    Крок 3. Визначити потребу.

    Яку проблему або потребу має користувач?

    Крок 4. Сформулювати мету.

    Якого результату він хоче досягти?

    Крок 5. Визначити завдання.

    Які дії потрібні для досягнення мети?

    Крок 6. Знайти перешкоди.

    Що може завадити користувачу?

    Крок 7. Запропонувати UI-рішення.

    Як інтерфейс може допомогти?

    Крок 8. Визначити критерії успіху.

    Як зрозуміти, що мету досягнуто?

    Крок 9. Перевірити гіпотези.

    Чи можуть реальні користувачі виконати завдання?

    Крок 10. Покращити дизайн.

    Що потрібно змінити на основі результатів?

# Міні-проєкт: User Goals для сторінки курсу

Завдання:

    Спроєктувати сторінку курсу
    з JavaScript для початківців.

## 1. Визначення користувача

    User:
    Людина, яка починає вивчати JavaScript.

## 2. Визначення мети

    User Goal:
    Зрозуміти, чого навчає курс,
    і вирішити, чи підходить він їй.

## 3. Визначення потреб

    Дізнатися рівень складності.
    Переглянути програму.
    Зрозуміти формат навчання.
    Дізнатися, що потрібно для початку.

## 4. Визначення завдань

    Переглянути опис.
    Переглянути навчальні модулі.
    Ознайомитися з вимогами.
    Переглянути приклади уроків.
    Прийняти рішення про початок навчання.

## 5. Визначення UI-рішень

    Зрозумілий заголовок.
    Короткий опис курсу.
    Видимий рівень складності.
    Структурована програма.
    Інформація про необхідні знання.
    Помітна основна дія.

## 6. Визначення критеріїв успіху

    Користувач розуміє призначення курсу.
    Може знайти програму навчання.
    Розуміє вимоги.
    Може прийняти обґрунтоване рішення.

## 7. Перевірка

    Дати користувачу завдання:
    «З'ясуйте, чи підходить вам цей курс».

    Перевірити:
    Чи знайшов користувач потрібну інформацію?
    Чи правильно зрозумів рівень курсу?
    Чи зміг пояснити, що вивчатиме?

# Основна модель User Goals

    USER CONTEXT
         ↓
    USER NEED
         ↓
    USER MOTIVATION
         ↓
    USER GOAL
         ↓
    USER TASKS
         ↓
    USER OUTCOME
         ↓
    SUCCESS CRITERIA

Це спрощена модель для аналізу користувацького сценарію. У реальних продуктах потреби, мотивація, завдання та результати можуть впливати одне на одного, а не утворювати лише лінійну послідовність.

# Головне

• User Goal — це результат, якого користувач хоче досягти.

• User Need — потреба, що стоїть за бажаним результатом.

• User Motivation пояснює, чому результат важливий.

• User Intent описує поточний намір користувача.

• User Task — конкретна дія або послідовність дій.

• User Outcome — фактичний результат взаємодії з продуктом.

• User Value — користь, яку отримує користувач.

• User Context описує обставини використання продукту.

• Functional Goals пов'язані з практичними результатами.

• Emotional Goals пов'язані з емоційним станом користувача.

• Social Goals пов'язані із соціальною взаємодією та сприйняттям.

• Primary Goal — головна мета в конкретному сценарії.

• Secondary Goals — додаткові цілі, що підтримують основну.

• User Goals можуть бути явними або неявними, короткостроковими або довгостроковими.

• User Goals і Business Goals можуть збігатися, але іноді конфліктують.

• Goal-Oriented Design починається з розуміння результату, а не з малювання екранів.

• User-Centered Design враховує потреби, цілі, контекст і обмеження користувачів.

• User Research допомагає зрозуміти реальні потреби, а не покладатися лише на припущення.

• JTBD допомагає визначити, яку роботу користувач хоче виконати за допомогою продукту.

• Pain Points показують, що заважає досягти мети.

• Success Criteria допомагають визначити, чи досягнуто бажаного результату.

• UI-рішення повинні мати зрозумілий зв'язок із потребами та цілями користувачів.

• Не кожна функція корисна лише тому, що її можна додати до інтерфейсу.

• Візуальна ієрархія має допомагати користувачу визначати головну інформацію та наступну дію.

• Інтерфейс потрібно перевіряти на реальних користувацьких завданнях.

• Головне запитання UX-дизайнера:

    «Як допомогти користувачу досягти
    потрібного результату зрозуміло,
    ефективно та без зайвих перешкод?»
