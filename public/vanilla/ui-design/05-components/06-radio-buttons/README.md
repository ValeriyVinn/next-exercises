# Radio Buttons — Радіокнопки

> Радіокнопки (Radio Buttons) — це елементи інтерфейсу, які дозволяють користувачу вибрати **один варіант із кількох взаємовиключних варіантів**.
>
> Основна мета — зробити вибір зрозумілим, показати всі доступні варіанти та дати користувачу можливість легко змінити своє рішення.

---

## 1. Що таке Radio Buttons

Radio Button — це елемент керування, який зазвичай відображається як невелике кругле поле з можливістю вибрати один варіант.

Наприклад, користувач обирає спосіб оплати:

- Готівка.
- Банківська картка.
- Банківський переказ.

Одночасно можна вибрати лише один варіант.

### Приклад

    Спосіб оплати

    (●) Банківська картка
    ( ) Готівка
    ( ) Банківський переказ

У цьому прикладі вибрано `Банківська картка`.

### Основні властивості

✔ Вибір одного варіанта в межах групи.

✔ Відображення всіх доступних варіантів одночасно.

✔ Можливість змінити вибір.

✔ Чітке позначення активного варіанта.

✔ Підтримка клавіатури та допоміжних технологій.

✔ Використання у формах, налаштуваннях, опитуваннях і фільтрах.

---

## 2. Radio Buttons, Checkboxes і Switches

Ці елементи можуть виглядати схоже за призначенням, але вирішують різні завдання.

| Елемент | Призначення | Приклад |
|---|---|---|
| Radio Button | Вибрати один варіант із групи | Спосіб доставки |
| Checkbox | Незалежно ввімкнути або вимкнути один чи кілька параметрів | Обрати додаткові послуги |
| Switch | Увімкнути або вимкнути параметр | Темна тема |

### Radio Buttons

    Спосіб доставки

    (●) Кур'єр
    ( ) Поштомат
    ( ) Самовивіз

Можна вибрати лише один спосіб доставки.

### Checkboxes

    Додаткові послуги

    [x] Подарункове пакування
    [ ] Страхування
    [x] SMS-повідомлення

Можна вибрати кілька незалежних параметрів.

### Switches

    Темна тема                       [ ON ]

Перемикач керує станом одного параметра.

### Що запам'ятати

- Radio Button — **один варіант із групи**.
- Checkbox — **один або кілька незалежних варіантів**.
- Switch — **увімкнення або вимкнення параметра**.

Не вибирай компонент лише за зовнішнім виглядом. Визначай його за поведінкою та змістом.

---

## 3. Коли використовувати Radio Buttons

Радіокнопки найкраще підходять, коли користувач повинен вибрати один варіант із невеликого списку.

### Типові сценарії

**1. Спосіб оплати**

    Спосіб оплати

    ( ) Готівка
    (●) Картка
    ( ) Банківський переказ

**2. Спосіб доставки**

    Доставка

    (●) Кур'єр
    ( ) Поштомат
    ( ) Самовивіз

**3. Рівень складності**

    Рівень складності

    ( ) Початковий
    (●) Середній
    ( ) Просунутий

**4. Налаштування профілю**

    Хто може бачити профіль?

    (●) Усі
    ( ) Лише зареєстровані користувачі
    ( ) Тільки я

**5. Формат відповіді**

    Формат результату

    ( ) PDF
    (●) HTML
    ( ) JSON

### Коли Radio Buttons недоречні

Не використовуй радіокнопки автоматично в кожному випадку, де є вибір.

| Ситуація | Кращий варіант |
|---|---|
| 2–5 простих видимих варіантів | Radio Buttons |
| Багато варіантів у компактному просторі | Select |
| Можна вибрати кілька варіантів | Checkboxes |
| Потрібно ввімкнути або вимкнути функцію | Switch |
| Потрібно вибрати дату | Date Picker |
| Потрібно вибрати значення на шкалі | Slider |

Це орієнтири, а не суворі правила. Остаточний вибір залежить від контексту та складності інтерфейсу.

## 4. Анатомія Radio Button

Типова радіокнопка складається з кількох частин.

    (●) Банківська картка
     ↑          ↑
     |          |
     |          └── Label — текст варіанта
     |
     └── Radio Indicator — індикатор вибору

### Основні частини

**1. Radio Indicator**

Графічний індикатор, який показує, чи вибрано варіант.

**2. Label**

Текст, який пояснює значення варіанта.

**3. Radio Group**

Група взаємопов'язаних радіокнопок, з якої можна вибрати лише один варіант.

**4. Group Label**

Заголовок, який пояснює призначення всієї групи.

**5. Description**

Додаткове пояснення для окремого варіанта або групи.

**6. Error Message**

Повідомлення про помилку, наприклад, якщо обов'язковий вибір не зроблено.

### Приклад структури

    Спосіб доставки
    Оберіть один із доступних варіантів.

    (●) Кур'єр
        Доставка за вашою адресою.

    ( ) Поштомат
        Отримання у зручному поштоматі.

    ( ) Самовивіз
        Отримання у пункті видачі.

Заголовок пояснює призначення групи, а підписи та описи допомагають розрізняти варіанти.

## 5. Візуальні стани Radio Buttons

Компонент повинен мати зрозумілий вигляд у різних станах взаємодії.

### 5.1. Unchecked — не вибрано

    ( ) Кур'єр

Користувач ще не вибрав цей варіант.

### 5.2. Checked — вибрано

    (●) Кур'єр

Варіант активний.

Вибір має бути зрозумілим не лише за кольором, а й за формою індикатора.

### 5.3. Hover — наведення

Коли користувач наводить курсор на інтерактивний елемент, інтерфейс може показувати:

- зміну кольору;
- зміну фону;
- легке посилення контрасту;
- зміну вигляду всієї області кліку.

Hover — це додатковий зворотний зв'язок, а не єдиний спосіб показати доступність елемента.

### 5.4. Focus — фокус

Фокус показує, який елемент зараз активний для взаємодії з клавіатури.

    ( ) Кур'єр
        └── Видима рамка фокусу

Фокус повинен бути помітним і не зникати лише заради декоративної чистоти дизайну.

### 5.5. Disabled — недоступний

    ( ) Доставка літаком
        Тимчасово недоступно

Недоступний варіант не можна вибрати.

Важливо:
- візуально відрізняти його від активних варіантів;
- не покладатися лише на низьку прозорість;
- пояснювати причину недоступності, якщо це важливо для користувача.

### 5.6. Error — помилка

    Спосіб оплати

    ( ) Готівка
    ( ) Картка

    Будь ласка, оберіть спосіб оплати.

Помилка повинна мати зрозуміле текстове повідомлення. Червоний колір сам по собі не пояснює, що потрібно зробити.

### 5.7. Checked + Focus

Вибраний варіант може одночасно перебувати у фокусі.

Дизайн повинен дозволяти розрізнити обидва стани: вибір і фокус.

### 5.8. Checked + Disabled

Вибраний варіант може стати недоступним через зміну умов.

Такий стан потрібно проєктувати обережно: користувач має розуміти, що саме сталося з вибором.

### Підсумок станів

| Стан | Що показує |
|---|---|
| Unchecked | Варіант не вибрано |
| Checked | Варіант вибрано |
| Hover | Курсор над елементом |
| Focus | Елемент отримав клавіатурний фокус |
| Disabled | Вибір недоступний |
| Error | Вибір не відповідає вимогам форми або не зроблений |
| Checked + Focus | Варіант вибрано та сфокусовано |

## 6. Правила групування

Radio Buttons повинні бути логічно об'єднані.

### 6.1. Один вибір — одна група

У межах однієї групи можна вибрати лише один варіант.

    Спосіб оплати

    ( ) Готівка
    ( ) Картка
    ( ) Банківський переказ

Якщо користувач вибирає картку, а потім готівку, вибір картки скасовується.

### 6.2. Незалежні питання — різні групи

    Спосіб оплати

    (●) Картка
    ( ) Готівка

    Тип отримання чека

    ( ) Електронний
    (●) Паперовий

Користувач може вибрати картку та паперовий чек одночасно, оскільки це різні питання.

### 6.3. Заголовок групи

Заголовок повинен пояснювати, що саме потрібно вибрати.

Погано:

    Варіант

    ( ) A
    ( ) B

Краще:

    Спосіб доставки

    ( ) Кур'єр
    ( ) Самовивіз

### 6.4. Послідовність варіантів

Розташовуй варіанти у зрозумілому порядку:

- за частотою використання;
- за логічною послідовністю;
- за зростанням або спаданням значення;
- за важливістю для користувача.

Не змінюй порядок без потреби, особливо якщо користувач регулярно працює з формою.

### 6.5. Кількість варіантів

Radio Buttons добре працюють із невеликими групами.

Наприклад, 2–5 варіантів часто зручно показувати безпосередньо у формі.

Якщо варіантів багато, розглянь Select, пошук або інший компонент. Не існує універсальної максимальної кількості: враховуй довжину підписів, пристрій і складність вибору.

## 7. Розташування та композиція

### 7.1. Вертикальне розташування

Найпоширеніший варіант для форм.

    Спосіб доставки

    ( ) Кур'єр
    ( ) Поштомат
    ( ) Самовивіз

Переваги:

- легко читати;
- зручно на мобільних пристроях;
- підписи можуть бути довгими;
- варіанти легко переглядати зверху вниз.

### 7.2. Горизонтальне розташування

    Рівень:   (●) Легкий   ( ) Середній   ( ) Складний

Підходить для коротких підписів і невеликої кількості варіантів.

Не використовуй горизонтальне розташування, якщо на мобільному екрані підписи стають надто тісними.

### 7.3. Картки з радіокнопками

    Спосіб підписки

    ┌──────────────────────────┐
    │ (●) Щомісячно             │
    │     Оплата кожного місяця│
    └──────────────────────────┘

    ┌──────────────────────────┐
    │ ( ) Щорічно               │
    │     Оплата раз на рік    │
    └──────────────────────────┘

Картки корисні, коли кожен варіант має додатковий опис, ціну або переваги.

Важливо:

- індикатор вибору повинен залишатися помітним;
- вся картка може бути клікабельною;
- активна картка повинна мати чіткий візуальний стан;
- текст не повинен перевантажувати картку;
- картка не повинна виглядати як вибрана, якщо варіант не активний.

### 7.4. Відступи

Потрібно розрізняти:

- відстань між індикатором і текстом;
- відстань між сусідніми варіантами;
- відстань між заголовком групи та варіантами;
- відстань між групами різних питань.

Приклад дизайн-токенів:

    :root {
      --radio-size: 20px;
      --radio-label-gap: 10px;
      --radio-option-gap: 12px;
      --radio-group-gap: 24px;
    }

Це лише стартові значення. Підбирай їх відповідно до типографіки, розміру екрана та дизайн-системи.

## 8. Розмір і зона взаємодії

Сам індикатор може бути невеликим, але натискати на нього має бути зручно.

### Рекомендації

✔ Зроби всю область підпису клікабельною.

✔ Не змушуй користувача натискати точно в маленьке коло.

✔ Залиш достатньо відстані між сусідніми варіантами.

✔ Не зменшуй елементи настільки, що ними важко користуватися на сенсорному екрані.

✔ Враховуй мобільні пристрої та користувачів із порушеннями моторики.

Для сенсорних інтерфейсів корисним орієнтиром є зона взаємодії близько 44 × 44 CSS px, хоча конкретні рекомендації залежать від стандарту та платформи. Це не означає, що саме коло радіокнопки обов'язково повинно мати такий розмір: збільшуй область натискання через підпис і контейнер.

## 9. Колір і візуальна ієрархія

Радіокнопка має гармонійно вписуватися в дизайн системи.

### Що потрібно визначити

- колір межі неактивного індикатора;
- колір активного індикатора;
- колір внутрішньої точки;
- колір фокусу;
- кольори недоступного стану;
- кольори помилок;
- фон вибраної картки, якщо використовується картковий варіант.

### Приклад CSS-змінних

    :root {
      --radio-border: #737373;
      --radio-checked: #2457c5;
      --radio-focus: #7c3aed;
      --radio-disabled: #b8b8b8;
      --radio-error: #b42318;
    }

Не використовуй колір як єдиний спосіб передавання стану.

Вибір повинен бути видимим завдяки формі індикатора, а помилка — пояснена текстом.

### Контраст

Текст повинен залишатися читабельним на тлі.

Для звичайного тексту WCAG 2.2 AA рекомендує контраст щонайменше 4.5:1, а для великого тексту — 3:1. Для меж та індикаторів інтерактивних елементів також важлива достатня контрастність щодо сусідніх кольорів.

## 10. Тексти та мікрокопірайтинг

Текст радіокнопки повинен пояснювати, що означає вибір.

### Погані підписи

    ( ) Варіант 1
    ( ) Варіант 2
    ( ) Інше

Такі підписи не допомагають прийняти рішення, якщо немає додаткового контексту.

### Кращі підписи

    Формат документа

    ( ) PDF — для друку та перегляду
    ( ) HTML — для перегляду в браузері
    ( ) JSON — для обробки програмою

### Правила написання

✔ Використовуй короткі, зрозумілі формулювання.

✔ Пояснюй незнайомі терміни.

✔ Формулюй варіанти в однаковому стилі.

✔ Уникай неоднозначних підписів.

✔ Додавай опис, якщо назви недостатньо.

✔ Не змушуй користувача здогадуватися про наслідки вибору.

### Формулювання запитання

Краще:

    Як ви хочете отримати замовлення?

Гірше:

    Замовлення

Зрозуміле питання зменшує когнітивне навантаження.

## 11. Початковий стан і значення за замовчуванням

Не кожна група повинна автоматично мати вибраний варіант.

### Коли можна встановити значення за замовчуванням

- варіант є очевидним для більшості користувачів;
- вибір легко змінити;
- початкове значення не створює небажаних наслідків;
- поведінка системи прозора.

### Коли краще залишити групу незаповненою

- рішення має фінансові наслідки;
- вибір є важливим для приватності;
- жоден варіант не є очевидно кращим;
- користувач повинен свідомо підтвердити рішення.

Наприклад, спосіб оплати або згоду з важливими умовами не варто вибирати за користувача без вагомої причини.

### Важливо

HTML-атрибут `required` не змушує браузер вибрати варіант автоматично. Він вимагає, щоб у групі було зроблено вибір перед відправленням форми.

## 12. Доступність (Accessibility)

Radio Buttons повинні працювати для користувачів миші, клавіатури, сенсорних пристроїв і допоміжних технологій.

### Основні правила

✔ Використовуй справжній HTML-елемент `<input type="radio">`, коли це можливо.

✔ Пов'язуй кожну радіокнопку з текстовим підписом.

✔ Об'єднуй логічні групи за допомогою `<fieldset>` і `<legend>`.

✔ Забезпечуй видимий фокус клавіатури.

✔ Не видаляй стандартний індикатор без створення доступної заміни.

✔ Не покладайся лише на колір.

✔ Підтримуй клавіатурну навігацію.

✔ Повідомляй про помилки зрозумілим текстом.

✔ Переконайся, що назва групи читається скринридером.

### Клавіатурна взаємодія

Для стандартної групи нативних радіокнопок браузер зазвичай забезпечує таку поведінку:

- `Tab` — перехід до групи або з неї;
- стрілки — переміщення між варіантами групи та вибір відповідного варіанта;
- `Space` — вибір сфокусованого варіанта, якщо це дозволяє поточний стан.

Точні деталі залежать від браузера, операційної системи та способу реалізації.

### HTML-приклад доступної групи

    <fieldset>
      <legend>Спосіб доставки</legend>

      <label>
        <input
          type="radio"
          name="delivery"
          value="courier"
          required
        />
        Кур'єр
      </label>

      <label>
        <input
          type="radio"
          name="delivery"
          value="locker"
        />
        Поштомат
      </label>

      <label>
        <input
          type="radio"
          name="delivery"
          value="pickup"

Тут:

- `<fieldset>` об'єднує варіанти;
- `<legend>` задає назву групи;
- `<label>` забезпечує текстовий підпис;
- однаковий `name="delivery"` об'єднує радіокнопки в одну групу;
- `value` визначає значення вибраного варіанта;
- `required` вимагає вибору перед відправленням форми.

## 13. HTML: базова реалізація

### 13.1. Мінімальний приклад

    <form>
      <fieldset>
        <legend>Рівень складності</legend>

        <label>
          <input
            type="radio"
            name="difficulty"
            value="easy"
          />
          Початковий
        </label>

        <label>
          <input
            type="radio"
            name="difficulty"
            value="medium"
          />
          Середній
        </label>

        <label>
          <input
            type="radio"
            name="difficulty"
            value="hard"
          />
          Просунутий
        </label>

        <button type="submit">Зберегти</button>
      </fieldset>
    </form>

### 13.2. Чому `name` має значення

Однаковий атрибут `name` об'єднує радіокнопки в одну групу.

    <input type="radio" name="payment" value="cash" />
    <input type="radio" name="payment" value="card" />

Це одна група.

    <input type="radio" name="payment" value="cash" />
    <input type="radio" name="delivery" value="courier" />

Це дві різні групи.

Не використовуй однакове ім'я для незалежних питань в одній формі.

### 13.3. Чому потрібен `value`

`value` визначає значення, яке передається під час відправлення форми.

Наприклад, якщо вибрано картку:

    payment=card

Текст підпису не замінює атрибут `value`.

### 13.4. Чому потрібен `label`

Підпис збільшує зручну область натискання та дає елементу доступну назву.

Можна використовувати вкладений `input`:

    <label>
      <input type="radio" name="theme" value="light" />
      Світла тема
    </label>

Або явний зв'язок через `id` і `for`:

    <input
      id="theme-light"
      type="radio"
      name="theme"
      value="light"
    />
    <label for="theme-light">Світла тема</label>

Обидва варіанти коректні.

## 17. Radio Buttons у React і Next.js

У React радіокнопки зазвичай керуються спільним станом групи.

### 17.1. Приклад на TypeScript

    "use client";

    import { useState } from "react";

    type PaymentMethod = "card" | "cash" | "transfer";

    export default function PaymentForm() {
      const [payment, setPayment] =
        useState<PaymentMethod | "">("");

      return (
        <form
          onSubmit={(event) => {
            event.preventDefault();

            if (!payment) {
              return;
            }

            console.log("Payment method:", payment);
          }}
        >
          <fieldset>
            <legend>Спосіб оплати</legend>

            <label>
              <input
                type="radio"
                name="payment"
                value="card"
                checked={payment === "card"}
                onChange={() => setPayment("card")}
                required
              />
              Банківська картка
            </label>

            <label>
              <input
                type="radio"
                name="payment"
                value="cash"
                checked={payment === "cash"}
                onChange={() => setPayment("cash")}
              />
              Готівка
            </label>

            <label>
              <input
                type="radio"
                name="payment"
                value="transfer"
                checked={payment === "transfer"}
                onChange={() => setPayment("transfer")}
              />
              Банківський переказ
            </label>
          </fieldset>

          <button type="submit">Продовжити</button>
        </form>
      );
    }

### Пояснення

**`useState`**

Зберігає поточний вибір.

**`PaymentMethod`**

Обмежує допустимі значення типом TypeScript.

**`checked`**

Визначає, яка радіокнопка вибрана.

**`onChange`**

Оновлює стан після вибору користувачем.

**`name`**

Зберігає семантичне групування радіокнопок на рівні HTML.

**`required`**

Бере участь у нативній перевірці форми.

### Чому `checked`, а не `defaultChecked`

- `checked` використовують для контрольованої радіокнопки, коли її стан зберігається в React;
- `defaultChecked` задає початковий стан неконтрольованого елемента.

У контрольованій групі джерелом істини є стан React.

### 17.2. Відокремлення компонента

Якщо радіокнопки повторюються в багатьох частинах застосунку, можна створити універсальний компонент або компонент групи.

Але не створюй абстракцію лише заради абстракції. Для маленької форми простий HTML усередині компонента сторінки може бути кращим рішенням.

## 18. Radio Buttons і перевірка форми

Радіокнопки часто використовуються як частина форми.

### Типовий сценарій

1. Користувач відкриває форму.
2. Переглядає доступні варіанти.
3. Вибирає один варіант.
4. Відправляє форму.
5. Система перевіряє дані.
6. Сервер обробляє результат.

### Приклад HTML

    <form>
      <fieldset>
        <legend>Оберіть формат документа</legend>

        <label>
          <input
            type="radio"
            name="documentFormat"
            value="pdf"
            required
          />
          PDF
        </label>

        <label>
          <input
            type="radio"
            name="documentFormat"
            value="html"
          />
          HTML
        </label>
      </fieldset>

      <button type="submit">Створити документ</button>
    </form>

### Що перевіряти

- чи зроблено обов'язковий вибір;
- чи є значення допустимим;
- чи не суперечить вибір іншим полям;
- чи доступний відповідний варіант;
- чи може сервер безпечно обробити отримане значення.

**Важливо:** клієнтська перевірка не замінює серверну. Сервер повинен самостійно перевіряти, чи дозволене отримане значення.

## 19. Умовні поля залежно від вибору

Іноді вибір одного варіанта показує додаткові поля.

Наприклад:

    Спосіб доставки

    (●) Кур'єр
        Адреса доставки: [____________]

    ( ) Самовивіз

Якщо користувач вибирає кур'єра, відображається поле адреси.

### Принципи реалізації

✔ Показуй лише ті поля, які справді потрібні.

✔ Не приховуй важливу інформацію про наслідки вибору.

✔ Перевіряй обов'язковість умовних полів.

✔ Не залишай приховані поля в стані, який випадково блокує відправлення форми.

✔ Враховуй, що вибір може змінитися після заповнення додаткових полів.

У React для цього використовують стан вибору та умовний рендеринг.

## 20. Радіокнопки у фільтрах

Radio Buttons можуть застосовуватися у фільтрах, якщо дозволений лише один варіант.

### Приклад

    Статус курсу

    (●) Усі
    ( ) Активні
    ( ) Завершені
    ( ) Архівні

Після вибору статусу список курсів може оновлюватися.

### Правила

- варіант «Усі» повинен мати зрозуміле значення;
- вибраний фільтр має бути візуально помітним;
- зміна фільтра не повинна несподівано скидати інші параметри;
- якщо фільтр одразу застосовується, це має бути зрозуміло;
- якщо потрібна кнопка застосування, поясни цей крок.

Для компактних панелей фільтрів іноді краще підходять сегментовані кнопки, але їхня семантика та клавіатурна поведінка повинні відповідати призначенню компонента.

## 22. Поширені помилки

### Помилка 1. Однаковий `name` у незалежних групах

Через це браузер може сприймати варіанти як одну групу.

**Правильно:** використовуй однаковий `name` лише для взаємовиключних варіантів одного питання.

### Помилка 2. Різні `name` у межах однієї групи

Браузер дозволить вибрати кілька радіокнопок, хоча за змістом це один вибір.

**Правильно:** усі варіанти однієї групи повинні мати однаковий `name`.

### Помилка 3. Відсутній підпис

Користувач не розуміє призначення індикатора, а допоміжні технології можуть не отримати доступної назви.

**Правильно:** пов'язуй кожен `input` з `label`.

### Помилка 4. Немає заголовка групи

Незрозуміло, на яке питання відповідає вибір.

**Правильно:** використовуй змістовний заголовок, а в HTML — зазвичай `<fieldset>` і `<legend>`.

### Помилка 5. Надто багато варіантів

Користувачу важко переглянути довгий список.

**Правильно:** розглянь Select, пошук або інший спосіб подання.

### Помилка 6. Відсутній стан фокусу

Користувач клавіатури не бачить, де перебуває.

**Правильно:** забезпечуй помітний `:focus-visible`.

### Помилка 7. Вибір показано лише кольором

Частина користувачів може не розрізнити стани.

**Правильно:** використовуй чіткий індикатор вибору та достатній контраст.

### Помилка 8. Надто маленька область натискання

Користувачеві важко вибрати варіант на мобільному пристрої.

**Правильно:** роби підпис і контейнер інтерактивними.

### Помилка 9. Незрозумілі значення

Наприклад, `value="1"` і `value="2"` без зрозумілого змісту в коді.

**Правильно:** використовуй змістовні значення, наприклад `courier`, `pickup`, `card`.

### Помилка 10. Автоматичний вибір без причини

Користувач може випадково погодитися з небажаним варіантом.

**Правильно:** залишай вибір порожнім, якщо рішення повинно бути свідомим.

### Помилка 11. Повністю власний компонент без перевірки доступності

Декоративний елемент може втратити клавіатурну поведінку або доступну назву.

**Правильно:** починай із нативного HTML і кастомізуй лише за потреби.

### Помилка 12. Перевірка лише на клієнті

Користувач може надіслати значення, яке не дозволене сервером.

**Правильно:** перевіряй допустимі значення також на сервері.

Чи потрібно вимагати свідомого вибору?

- порядок варіантів;
- підписи;
- описи;
- відступи;
- спосіб розташування.

### Крок 6. Визнач стани

Спроєктуй:

- unchecked;
- checked;

## 24. Мініпроєкт: вибір рівня складності

Мета — створити невелику форму з трьома варіантами та показувати поточний вибір.

### Вимоги

✔ Заголовок групи.

✔ Три радіокнопки.

✔ Один вибір одночасно.

✔ Помітний вибраний стан.

✔ Зрозумілі підписи.

✔ Клавіатурна навігація.

✔ Виведення поточного значення.

### HTML

    <form id="difficulty-form">
      <fieldset>
        <legend>Оберіть рівень складності</legend>

        <label class="radio-option">
          <input
            type="radio"
            name="difficulty"
            value="easy"
            required
          />
          Початковий
        </label>

        <label class="radio-option">
          <input
            type="radio"
            name="difficulty"
            value="medium"
          />
          Середній
        </label>

        <label class="radio-option">
          <input
            type="radio"
            name="difficulty"
            value="hard"
          />
          Просунутий
        </label>
      </fieldset>

      <button type="submit">Підтвердити</button>
    </form>

    <p id="result" aria-live="polite">
      Рівень ще не вибрано.
    </p>

### JavaScript

    "use strict";

    const form = document.querySelector("#difficulty-form");
    const result = document.querySelector("#result");

    if (!(form instanceof HTMLFormElement)) {
      throw new Error("Difficulty form not found");
    }

    if (!(result instanceof HTMLParagraphElement)) {
      throw new Error("Result element not found");
    }

    form.addEventListener("change", (event) => {
      const target = event.target;

      if (
        !(target instanceof HTMLInputElement) ||
        target.type !== "radio" ||
        target.name !== "difficulty"
      ) {
        return;
      }

      const labels: Record<string, string> = {
        easy: "Початковий",
        medium: "Середній",
        hard: "Просунутий",
      };

      result.textContent =
        `Вибраний рівень: ${labels[target.value]}`;
    });

    form.addEventListener("submit", (event) => {
      event.preventDefault();

      if (!form.reportValidity()) {
        return;
      }

      const data = new FormData(form);
      const difficulty = data.get("difficulty");

      result.textContent =
        `Підтверджено рівень: ${String(difficulty)}`;
    });

> Примітка: приклад JavaScript використовує синтаксис TypeScript (`Record<string, string>`). Для звичайного файлу `.js` прибери тип `Record<string, string>`. Для файлу `.ts` цей тип підходить, якщо налаштовано DOM-типи TypeScript.

## 25. Як тестувати Radio Buttons

Перед завершенням перевір компоненти за конкретними сценаріями.

### Функціональні тести

- [ ] Можна вибрати один варіант.
- [ ] Після вибору іншого попередній вибір скасовується.
- [ ] Незалежні групи не заважають одна одній.
- [ ] Значення форми відповідає вибору.
- [ ] Обов'язкова група не проходить перевірку без вибору.
- [ ] Недоступний варіант не можна вибрати.

### Тести доступності

- [ ] У кожної радіокнопки є зрозумілий підпис.
- [ ] У групи є змістовний заголовок.
- [ ] Працює навігація клавіатурою.
- [ ] Фокус помітний.
- [ ] Вибір зрозумілий без розрізнення кольорів.
- [ ] Текст помилки пояснює проблему.
- [ ] Стан доступний для допоміжних технологій.

### Візуальні тести

- [ ] Варіанти вирівняні.
- [ ] Відступи послідовні.
- [ ] Підписи не обрізаються.
- [ ] Вибраний варіант помітний.
- [ ] Стан disabled не плутається зі звичайним.
- [ ] Мобільний вигляд зручний.
- [ ] Контраст достатній.

## 26. Що потрібно запам'ятати

✔ Radio Buttons призначені для вибору одного варіанта з групи.

✔ Взаємовиключні варіанти одного питання мають однаковий `name`.

✔ Незалежні питання повинні мати різні групи.

✔ `value` визначає значення вибраного варіанта.

✔ `label` пов'язує текст із радіокнопкою.

✔ `<fieldset>` і `<legend>` допомагають семантично об'єднати групу.

✔ Не кожна група повинна мати вибраний варіант за замовчуванням.

✔ Користувач повинен бачити вибраний стан і клавіатурний фокус.

✔ Не використовуй колір як єдиний спосіб показати стан.

✔ Робити всю область підпису клікабельною — хороша практика.

✔ Нативний HTML зазвичай є найкращою відправною точкою.

✔ Кастомний компонент потребує особливої уваги до доступності.

✔ Клієнтська перевірка не замінює серверну.

✔ Radio Buttons доречні для невеликих груп, але кількість варіантів сама по собі не є абсолютним правилом вибору компонента.
