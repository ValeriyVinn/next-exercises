# 03. Inputs — Поля введення даних

> **Inputs (поля введення)** — це UI-компоненти, за допомогою яких користувач вводить, редагує або вибирає дані в інтерфейсі: текст, числа, дати, паролі, пошукові запити та іншу інформацію.
>
> Мета дизайну полів введення — зробити взаємодію зрозумілою, передбачуваною, доступною та зручною, а також допомогти користувачеві правильно заповнити форму.

---

## 1. Що потрібно знати про Inputs

Поля введення — одна з основних груп UI-компонентів. Вони зустрічаються майже в кожному застосунку:

- реєстрація та авторизація;
- створення й редагування профілю;
- пошук;
- оформлення замовлень;
- налаштування;
- фільтрація даних;
- введення чисел, дат та інших значень;
- адміністративні панелі й освітні платформи.

**Головне завдання:** користувач повинен розуміти, які дані потрібно ввести, у якому форматі та як виправити помилку.

### Основні поняття

- ✔ **Input** — компонент для введення або вибору значення.
- ✔ **Text field** — поле для введення тексту.
- ✔ **Label** — назва поля, що пояснює його призначення.
- ✔ **Placeholder** — тимчасова підказка всередині порожнього поля.
- ✔ **Helper text** — додаткове пояснення під полем.
- ✔ **Validation** — перевірка правильності введених даних.
- ✔ **Error message** — повідомлення про помилку.
- ✔ **Required field** — обов'язкове поле.
- ✔ **Optional field** — необов'язкове поле.
- ✔ **Input state** — стан поля: звичайний, у фокусі, заповнений, помилковий тощо.
- ✔ **Affordance** — візуальна підказка, яка показує, як взаємодіяти з елементом.
- ✔ **Accessibility** — доступність компонента для людей із різними потребами та способами взаємодії.
- ✔ **Form field** — поле форми разом із назвою, підказками, повідомленнями та самим елементом введення.

---

## 2. Input, Label, Placeholder і Helper Text

Ці елементи можуть розташовуватися поруч, але виконують різні функції.

### 2.1. Input

Сам елемент, у який користувач вводить значення.

Приклади:

- ім'я;
- електронна пошта;
- пароль;
- кількість товарів;
- пошуковий запит.

### 2.2. Label

Назва поля. Вона повинна залишатися зрозумілою навіть після введення даних.

Приклади:

- Ім'я
- Електронна пошта
- Дата народження
- Кількість учнів

**Правило:** не використовуй placeholder як єдину назву поля.

Поганий варіант:

    ┌──────────────────────────────┐
    │ Введіть електронну пошту     │
    └──────────────────────────────┘

Після введення адреси підказка зникає, і користувач може забути призначення поля.

Кращий варіант:

    Електронна пошта
    ┌──────────────────────────────┐
    │ user@example.com             │
    └──────────────────────────────┘

### 2.3. Placeholder

Placeholder — коротка підказка всередині порожнього поля.

Використовуй його для прикладу значення або уточнення формату.

    Дата народження
    ┌──────────────────────────────┐
    │ ДД.ММ.РРРР                   │
    └──────────────────────────────┘

Placeholder не повинен замінювати Label, тому що:

- зникає під час введення;
- може мати недостатній контраст;
- часто сприймається як уже введене значення;
- не завжди доступний для зручного повторного перегляду.

### 2.4. Helper Text

Helper text — пояснення, яке допомагає правильно заповнити поле.

    Пароль
    ┌──────────────────────────────┐
    │ ••••••••••                  │
    └──────────────────────────────┘
    Використайте щонайменше 12 символів.

Helper text може пояснювати:

- потрібний формат;
- правила введення;
- обмеження довжини;
- причину запиту даних;
- вимоги до пароля;
- допустимі значення.

### 2.5. Error Message

Повідомлення про помилку пояснює, що потрібно виправити.

    Електронна пошта
    ┌──────────────────────────────┐
    │ user@                        │
    └──────────────────────────────┘
    Помилка: введіть коректну електронну адресу.

Хороше повідомлення про помилку:

- конкретне;
- зрозуміле;
- пояснює проблему;
- за можливості пропонує спосіб виправлення;
- не покладається лише на червоний колір.

### Порівняння

| Елемент | Основна функція |
|---|---|
| Label | Називає поле |
| Placeholder | Показує приклад або коротку підказку |
| Helper text | Пояснює правила введення |
| Error message | Пояснює, що потрібно виправити |
| Input value | Містить введені користувачем дані |

## 3. Основні типи полів введення

Різні типи даних потребують різних компонентів.

### 3.1. Text Input

Поле для короткого тексту.

Використання:

- ім'я;
- прізвище;
- назва курсу;
- місто;
- коротка відповідь.

    Ім'я
    ┌──────────────────────────────┐
    │ Олександр                    │
    └──────────────────────────────┘

### 3.2. Email Input

Поле для електронної адреси.

    Електронна пошта
    ┌──────────────────────────────┐
    │ user@example.com             │
    └──────────────────────────────┘

Дизайн повинен:

- чітко позначати призначення поля;
- дозволяти зручно вводити адресу;
- показувати зрозумілі помилки;
- не вимагати від користувача зайвих дій.

### 3.3. Password Input

Поле для введення пароля.

    Пароль
    ┌──────────────────────────────┐
    │ ••••••••••••           ◉     │
    └──────────────────────────────┘

Корисні можливості:

- приховування введених символів;
- перемикач показу пароля;
- зрозумілі вимоги до пароля;
- повідомлення про помилки;
- збереження введеного значення, якщо це безпечно й доречно.

Не роби правила пароля надмірно складними без потреби.

### 3.4. Number Input

Поле для числового значення.

    Кількість учнів
    ┌──────────────────────────────┐
    │ 25                           │
    └──────────────────────────────┘

Залежно від задачі можуть бути потрібні:

- мінімальне значення;
- максимальне значення;
- крок зміни;
- одиниці вимірювання;
- перевірка діапазону.

Наприклад, для кількості учнів допустимі лише цілі додатні числа, тоді як для ціни або ваги можуть бути дозволені десяткові значення.

### 3.5. Search Input

Поле для пошуку інформації.

    ┌──────────────────────────────────┐
    │ 🔍 Пошук курсів...               │
    └──────────────────────────────────┘

Рекомендації:

- розташовуй поле там, де користувач очікує знайти пошук;
- використовуй зрозумілу назву або підказку;
- за потреби показуй кнопку очищення;
- передбачай стан завантаження;
- пояснюй, якщо результатів не знайдено.

### 3.6. Textarea

Багаторядкове поле для довшого тексту.

    Коментар
    ┌──────────────────────────────────┐
    │ Напишіть свій коментар...        │
    │                                  │
    │                                  │
    └──────────────────────────────────┘

Використовуй для:

- описів;
- коментарів;
- повідомлень;
- відгуків;
- довгих відповідей.

Textarea може мати фіксовану висоту або автоматично збільшуватися під час введення.

### 3.7. Date Input

Поле для введення або вибору дати.

    Дата народження
    ┌──────────────────────────────┐
    │ 12.05.1995              📅   │
    └──────────────────────────────┘

Важливо враховувати:

- формат дати;
- локальні звички користувачів;
- доступність календаря;
- можливість введення з клавіатури;
- обмеження допустимого діапазону.

### 3.8. Інші типи

- **Tel** — номер телефону.
- **URL** — вебадреса.
- **Search** — пошуковий запит.
- **Time** — час.
- **Checkbox** — вибір або підтвердження незалежної опції.
- **Radio button** — вибір одного варіанта з групи.
- **Select** — вибір зі списку.
- **Range / Slider** — вибір значення в діапазоні.
- **File input** — завантаження файлу.

Checkbox, radio, select та slider теж є елементами введення даних, але мають власні особливості дизайну й взаємодії.

## 4. Структура якісного поля

Типове поле складається з кількох частин.

    Назва поля *
    ┌────────────────────────────────┐
    │ Введіть значення               │
    └────────────────────────────────┘
    Пояснення щодо формату значення.

Основні частини:

1. Label — назва.
2. Required indicator — позначення обов'язкового поля, якщо воно потрібне.
3. Input control — сам елемент введення.
4. Leading icon — необов'язкова іконка на початку.
5. Trailing icon — необов'язкова іконка в кінці.
6. Helper text — додаткове пояснення.
7. Error message — повідомлення про помилку.
8. Character counter — лічильник символів, якщо він корисний.

Не кожне поле потребує всіх цих елементів. Додавай лише ті, що допомагають користувачеві.

### Приклад структури

    Електронна пошта *
    ┌────────────────────────────────┐
    │ user@example.com               │
    └────────────────────────────────┘
    Використовується для входу в акаунт.

Зірочка може позначати обов'язковість поля, але її значення потрібно пояснити на рівні форми, якщо воно не очевидне.

## 5. Розміри та пропорції

Розмір поля впливає на зручність введення та загальний вигляд інтерфейсу.

### 5.1. Висота

У дизайні часто використовують кілька розмірів:

- Small — для компактних інтерфейсів;
- Medium — стандартний розмір;
- Large — для помітних або сенсорно орієнтованих інтерфейсів.

Приклад умовної шкали:

    Small:   32 px
    Medium:  40 px
    Large:   48 px

Це лише приклад системи розмірів, а не універсальний стандарт. Реальні значення залежать від шрифту, відступів, платформи та вимог доступності.

### 5.2. Ширина

Ширина поля повинна відповідати призначенню.

- Поле пошуку може займати значну частину доступного простору.
- Поле для поштового індексу може бути коротшим.
- Поле для довгого імені або адреси має дозволяти вводити відповідні дані.
- На мобільних пристроях поля часто займають майже всю ширину контейнера.

Не роби всі поля однакової ширини автоматично. Спочатку врахуй зміст і сценарій використання.

### 5.3. Внутрішні відступи

Padding визначає відстань між текстом і межами поля.

    ┌──────────────────────────────┐
    │  Значення                    │
    └──────────────────────────────┘
      ↑                          ↑
      внутрішні відступи

Надто малі відступи роблять поле тісним. Надто великі — зменшують простір для введення тексту.

### 5.4. Радіус кутів

Border radius формує характер компонента:

- малий радіус — строгий, технічний інтерфейс;
- середній радіус — універсальний сучасний стиль;
- великий радіус — м'який, дружній стиль;
- повністю округлена форма — доречна для окремих компактних елементів.

Використовуй спільну шкалу радіусів у межах дизайн-системи.

### 5.5. Відстані між елементами

Поля повинні бути достатньо відокремлені одне від одного.

    Label

    ┌────────────────────────────┐

    Helper text


    Наступний Label

    ┌────────────────────────────┐

Занадто щільне розташування підвищує ризик помилок і ускладнює сканування форми.

## 6. Візуальні стани Input

Поле має показувати, що зараз відбувається.

### 6.1. Default

Звичайний стан поля, готового до взаємодії.

    Електронна пошта
    ┌──────────────────────────────┐
    │                              │
    └──────────────────────────────┘

### 6.2. Hover

Стан, коли вказівник миші наведено на поле.

Зазвичай може змінюватися:

- колір межі;
- колір фону;
- тінь.

Hover не повинен бути єдиним способом показати інтерактивність, оскільки сенсорні пристрої не мають звичайного наведення.

### 6.3. Focus

Стан, коли поле отримало фокус клавіатури або іншого засобу взаємодії.

    Електронна пошта
    ┏━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━┓
    ┃                              ┃
    ┗━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━┛

Focus повинен бути добре помітним. Не прибирай стандартний індикатор фокусу без створення доступної заміни.

### 6.4. Filled

Поле містить введене значення.

    Ім'я
    ┌──────────────────────────────┐
    │ Олександр                    │
    └──────────────────────────────┘

Заповнене поле повинно залишатися читабельним і візуально відрізнятися від порожнього, якщо це потрібно для контексту.

### 6.5. Disabled

Поле тимчасово недоступне для взаємодії.

    Код підтвердження
    ┌──────────────────────────────┐
    │ Недоступно                   │
    └──────────────────────────────┘

Disabled-стан має бути візуально зрозумілим, але текст повинен залишатися читабельним.

Не використовуй disabled для приховування помилок або покарання користувача за неправильне введення.

### 6.6. Read-only

Поле показує значення, яке можна переглядати, але не редагувати безпосередньо.

    Номер замовлення
    ┌──────────────────────────────┐
    │ ORD-2026-0142                │
    └──────────────────────────────┘

Read-only і disabled — не одне й те саме:

- Read-only: значення можна переглядати та часто копіювати.
- Disabled: елемент вимкнений і зазвичай не бере участі у звичайній взаємодії.

### 6.7. Error

Поле містить некоректне значення або не пройшло перевірку.

    Електронна пошта
    ┌──────────────────────────────┐
    │ user@                        │
    └──────────────────────────────┘
    Введіть коректну електронну адресу.

Помилку варто показувати через поєднання сигналів:

- зміну межі;
- повідомлення;
- за потреби іконку;
- програмне повідомлення для допоміжних технологій.

Не покладайся лише на колір.

### 6.8. Success

Поле успішно пройшло перевірку.

    Електронна пошта
    ┌──────────────────────────────┐
    │ user@example.com         ✓   │
    └──────────────────────────────┘

Success-стан корисний, коли підтвердження допомагає користувачеві. Не потрібно показувати позитивну іконку для кожного правильно заповненого поля, якщо це створює зайвий візуальний шум.

### 6.9. Loading

Поле або пов'язаний із ним процес очікує результату.

Приклад: перевірка доступності імені користувача.

    Ім'я користувача
    ┌──────────────────────────────┐
    │ alexander              ◌     │
    └──────────────────────────────┘
    Перевіряємо доступність...

Індикатор завантаження не повинен без потреби блокувати введення даних.

### Таблиця станів

| Стан | Що означає | Що важливо |
|---|---|---|
| Default | Звичайний стан | Зрозумілі межі та призначення |
| Hover | Наведення | Ненав'язлива візуальна реакція |
| Focus | Активне поле | Помітний індикатор фокусу |
| Filled | Є значення | Читабельність введених даних |
| Disabled | Взаємодія вимкнена | Зрозуміла недоступність |
| Read-only | Значення не редагується | Можливість перегляду |
| Error | Некоректне значення | Пояснення та спосіб виправлення |
| Success | Перевірка успішна | Підтвердження, якщо воно потрібне |
| Loading | Очікується результат | Видимий стан очікування |

## 7. Валідація даних (Validation)

Validation — перевірка того, чи відповідають введені дані очікуваним правилам.

### 7.1. Основні види перевірки

- Required — чи заповнене обов'язкове поле.
- Type — чи відповідає значення типу даних.
- Format — чи правильний формат.
- Length — чи допустима довжина.
- Range — чи перебуває значення в дозволеному діапазоні.
- Business rules — чи відповідає значення правилам конкретної предметної області.

Приклад для віку:

- значення має бути числом;
- значення не повинно бути від'ємним;
- дозволений діапазон визначається вимогами застосунку.

### 7.2. Коли показувати помилку

Помилка, показана одразу під час першого натискання клавіші, може заважати користувачеві.

Залежно від поля використовують різні підходи:

- під час введення — для перевірок, які допомагають одразу;
- після втрати фокусу (blur) — коли користувач завершив роботу з полем;
- після натискання кнопки надсилання — для перевірки всієї форми;
- під час введення й після надсилання — якщо це справді покращує взаємодію.

Наприклад, не обов'язково показувати «Неправильна адреса» після введення лише першого символу електронної пошти. Краще дочекатися моменту, коли користувач завершив введення або намагається надіслати форму.

### 7.3. Хороше повідомлення про помилку

Погано:

    Помилка!

Краще:

    Введіть електронну адресу у форматі name@example.com.

Погано:

    Неправильно.

Краще:

    Пароль має містити щонайменше 12 символів.

Повідомлення повинно відповідати реальній проблемі та не створювати враження, що користувач винен у технічному збої.

### 7.4. Зберігай введені дані

Якщо користувач припустився помилки, не очищай усю форму без потреби.

Після невдалої перевірки користувач повинен мати можливість виправити лише проблемне поле, не вводячи решту даних заново.

### 7.5. Валідація на клієнті та сервері

У вебзастосунку перевірки можуть виконуватися:

- на клієнті — у браузері;
- на сервері — під час обробки запиту.

Клієнтська перевірка допомагає швидко показувати помилки, але не замінює серверну перевірку. Сервер не повинен довіряти даним лише тому, що вони пройшли перевірку в інтерфейсі.

## 8. Обов'язкові та необов'язкові поля

Користувач повинен розуміти, які дані необхідно надати.

### Варіант 1. Позначати обов'язкові поля

    Ім'я *
    Електронна пошта *
    Коментар

Якщо зірочка означає обов'язковість, поясни це в інтерфейсі, коли така домовленість може бути неочевидною.

### Варіант 2. Позначати необов'язкові поля

    Ім'я
    Електронна пошта
    Коментар (необов'язково)

Це може бути зручніше, коли більшість полів є обов'язковими, а винятків небагато.

### Рекомендації

- Не змушуй користувача здогадуватися.
- Не позначай поле як обов'язкове лише візуально, якщо цього не підтверджує логіка форми.
- Не вимагай даних, які не потрібні для виконання завдання.
- Пояснюй, навіщо потрібні чутливі або незвичні дані.

## 9. Іконки всередині полів

Іконки можуть допомагати користувачеві зрозуміти призначення поля або виконати дію.

### 9.1. Leading icon

Іконка на початку поля.

    ┌──────────────────────────────┐
    │ 🔍 Пошук курсів              │
    └──────────────────────────────┘

Може використовуватися для:

- пошуку;
- адреси електронної пошти;
- телефону;
- геолокації.

### 9.2. Trailing icon

Іконка в кінці поля.

    ┌──────────────────────────────┐
    │ ••••••••••••            ◉   │
    └──────────────────────────────┘

Приклади:

- показати або приховати пароль;
- відкрити календар;
- очистити поле;
- показати результат перевірки.

### 9.3. Правила використання

- Іконка повинна мати зрозуміле значення.
- Не додавай іконки лише для прикраси.
- Не дозволяй іконці перекривати текст.
- Інтерактивна іконка повинна мати достатню область натискання.
- Якщо дія неочевидна, використовуй доступну назву або підказку.
- Для декоративних іконок не потрібно створювати зайвий елемент для читання допоміжними технологіями.

## 10. Доступність полів введення (Accessibility)

Доступність — це не окрема прикраса компонента, а частина його правильної роботи.

### 10.1. Label повинен бути пов'язаний із полем

У HTML використовуй `label` та відповідний `id`.

    <label for="email">Електронна пошта</label>
    <input id="email" name="email" type="email" />

Такий зв'язок допомагає допоміжним технологіям визначити призначення поля. Крім того, натискання на Label може переміщувати фокус на відповідний елемент.

### 10.2. Не прибирай індикатор Focus

Користувачі клавіатури повинні бачити, яке поле зараз активне.

    input:focus-visible {
      outline: 3px solid #2563eb;
      outline-offset: 2px;
    }

Це приклад оформлення фокусу. Конкретний колір і товщина мають відповідати загальному дизайну та вимогам контрастності.

### 10.3. Забезпечуй достатній контраст

Перевіряй контрастність:

- тексту;
- меж поля;
- індикатора фокусу;
- повідомлень про помилки;
- іконок, що передають важливу інформацію.

Для звичайного тексту WCAG зазвичай рекомендує коефіцієнт контрастності щонайменше 4.5:1, а для великого тексту — 3:1. Для інших візуальних елементів діють окремі вимоги.

### 10.4. Не покладайся лише на колір

Погано:

    Червона межа без пояснення.

Краще:

    Червона межа + зрозумілий текст помилки.

Користувач повинен розуміти проблему незалежно від того, чи розрізняє він кольори.

### 10.5. Дозволяй клавіатурну взаємодію

Користувач повинен мати можливість:

- перейти до поля клавішею Tab;
- перейти до попереднього поля через Shift + Tab;
- вводити та редагувати значення;
- активувати пов'язані кнопки клавіатурою;
- зрозуміти, де перебуває фокус.

Не змінюй стандартну поведінку клавіатури без вагомої причини.

### 10.6. Повідомляй про помилки програмно

Повідомлення про помилку повинно бути пов'язане з відповідним полем. Для складніших форм можуть використовуватися `aria-describedby`, `aria-invalid` та інші засоби доступності.

Не додавай ARIA-атрибути механічно: спочатку використовуй правильну HTML-семантику.

### 10.7. Область взаємодії

Поле повинно мати достатню висоту й зручну область натискання, особливо на мобільних пристроях.

Не роби інтерактивні елементи настільки малими, що ними складно користуватися пальцем або іншим засобом введення.

---

## 11. Inputs у мобільному дизайні

Мобільний інтерфейс потребує особливої уваги до введення даних.

### Основні правила

- Використовуй ширину, що відповідає доступному простору.
- Не допускай горизонтального прокручування через поле.
- Забезпечуй достатню висоту елементів.
- Не розміщуй поля надто близько одне до одного.
- Враховуй появу екранної клавіатури.
- Не дозволяй клавіатурі перекривати важливі повідомлення або кнопки.
- Вибирай відповідний тип поля, щоб пристрій міг показувати зручну клавіатуру.
- Не використовуй складні багатоколонкові форми на вузькому екрані без необхідності.

### Правильний тип поля допомагає введенню

Наприклад, HTML `type="email"` може запропонувати зручнішу клавіатуру для введення електронної адреси, а `type="tel"` — клавіатуру для номера телефону.

Це покращує досвід користувача, але не замінює перевірку даних.

---

## 12. Форми та групування полів

Поля зазвичай працюють не окремо, а як частина форми.

### 12.1. Групуй поля за змістом

Наприклад, форма реєстрації може містити такі групи:

    Особисті дані
    ├── Ім'я
    ├── Прізвище
    └── Дата народження

    Дані для входу
    ├── Електронна пошта
    └── Пароль

Групування допомагає користувачеві зрозуміти структуру форми.

### 12.2. Порядок полів

Розташовуй поля в логічному порядку:

- від загальної інформації до специфічної;
- від простих запитань до складніших;
- відповідно до реального процесу користувача.

Не проси повторно вводити дані, які вже відомі застосунку й можуть бути безпечно використані.

### 12.3. Одноколонкові та багатоколонкові форми

Одноколонкова форма:

    Ім'я
    ┌────────────────────────────┐

    Електронна пошта
    ┌────────────────────────────┐

    Пароль
    ┌────────────────────────────┐

    [Створити акаунт]

Одноколонковий макет часто простіше читати, особливо на мобільних пристроях.

Кілька колонок можуть бути доречними для коротких взаємопов'язаних полів, наприклад міста й поштового індексу, якщо це не ускладнює заповнення.

### 12.4. Не перевантажуй форму

Якщо форма довга:

- розбий її на зрозумілі секції;
- прибери необов'язкові запитання, які не мають практичної мети;
- використовуй короткі пояснення;
- показуй прогрес, якщо процес складається з кількох етапів;
- зберігай введені дані під час переходів між кроками.

---

## 13. Візуальна ієрархія полів

Користувач повинен легко визначати, де назва, де поле, а де додаткова інформація.

### Приклад ієрархії

    Назва поля
    ┌──────────────────────────────┐
    │ Введіть значення             │
    └──────────────────────────────┘
    Коротке пояснення.

Візуальна ієрархія може створюватися за допомогою:

- розміру та насиченості шрифту;
- відстані між Label і Input;
- кольору межі;
- фону;
- відступів між полями;
- стилю допоміжного тексту;
- стилю повідомлень про помилки.

### Не роби всі елементи однаково помітними

Label повинен легко читатися, але не обов'язково бути більшим за введене значення.

Helper text може бути менш акцентним, однак його контрастність усе одно має забезпечувати читабельність.

Error message повинен привертати увагу, але не повинен візуально руйнувати всю форму.

## 14. Дизайн-система для Inputs

У великому застосунку поля повинні мати узгоджений вигляд.

### 14.1. Що визначити в дизайн-системі

- висоту полів;
- мінімальну ширину та правила адаптації;
- внутрішні відступи;
- радіус кутів;
- товщину межі;
- типографіку;
- кольори тексту й фону;
- кольори меж у різних станах;
- стилі Focus, Error, Disabled та Read-only;
- відстані між Label, Input і Helper text;
- правила використання іконок;
- поведінку на мобільних пристроях.

### 14.2. Приклад токенів

    :root {
      --input-height-sm: 2rem;

      --input-background: #ffffff;

      --input-focus-color: #2563eb;
      --input-error-color: #dc2626;
    }

Це приклад початкових значень. У реальному проєкті кольори й розміри потрібно перевіряти на контрастність, доступність та узгодженість із рештою інтерфейсу.

### 14.3. Варіанти компонента

Дизайн-система може передбачати:

    Input
    ├── Size
    │   ├── Small
    │   ├── Medium
    │   └── Large
    ├── State
    │   ├── Default
    │   ├── Focus
    │   ├── Error
    │   ├── Disabled
    │   └── Read-only
    └── Type
        ├── Text
        ├── Email
        ├── Password
        ├── Number
        └── Search

Не створюй окремий компонент для кожної комбінації без потреби. Краще мати спільні правила й керовані варіанти.

## 15. Реалізація Inputs у HTML та CSS

UI-дизайнеру корисно розуміти, як візуальні рішення відображаються в коді.

### 15.1. HTML

    <div class="form-field">
      <label for="username">Ім'я користувача</label>

      <input
        id="username"
        name="username"
        type="text"
        autocomplete="username"
        placeholder="Наприклад, alex"
        required
      />

      <p class="form-field__help">
        Використайте ім'я, за яким вас легко впізнати.
      </p>
    </div>

Тут:

- `label` — назва поля;
- `for` і `id` — зв'язок між назвою та полем;
- `name` — ім'я поля під час надсилання форми;
- `type` — тип введення;
- `autocomplete` — підказка браузеру щодо автозаповнення;
- `placeholder` — приклад значення;
- `required` — ознака обов'язкового поля.

### 15.2. CSS

    .form-field {
      display: grid;
      gap: 0.5rem;
    }

    .form-field label {
      font-size: 0.875rem;
      font-weight: 600;
    }

    .form-field input {
      width: 100%;
      min-height: 2.75rem;
      padding: 0.625rem 0.75rem;
      border: 1px solid #9ca3af;
      border-radius: 0.375rem;
      background: #ffffff;
      color: #111827;
      font: inherit;
    }

    .form-field input:focus-visible {
      outline: 3px solid #2563eb;
      outline-offset: 2px;
    }

    .form-field__help {
      margin: 0;
      color: #4b5563;
      font-size: 0.875rem;
    }

Це базовий приклад. Для реального застосунку потрібно додати стилі помилок, disabled-стану, темної теми та адаптивної поведінки, якщо вони потрібні.

### 15.3. Помилка у HTML

    <div class="form-field form-field--error">
      <label for="email">Електронна пошта</label>

      <input
        id="email"
        name="email"
        type="email"
        aria-invalid="true"
        aria-describedby="email-error"
        value="user@"
      />

      <p id="email-error">
        Введіть коректну електронну адресу.
      </p>
    </div>

`aria-invalid="true"` повідомляє допоміжним технологіям, що значення поля не пройшло перевірку. `aria-describedby` пов'язує поле з поясненням помилки.

У реальному застосунку ці атрибути потрібно встановлювати відповідно до фактичного стану поля, а не залишати помилку активною постійно.

### 15.4. Використання CSS-псевдокласів

    input:hover {
      border-color: #6b7280;
    }

    input:focus-visible {
      outline: 3px solid #2563eb;
      outline-offset: 2px;
    }

    input:disabled {
      cursor: not-allowed;
      opacity: 0.65;
    }

Псевдокласи допомагають оформлювати стандартні стани без створення зайвої JavaScript-логіки.

## 16. Inputs у React та Next.js

У React поля часто стають частиною повторно використовуваних компонентів.

### 16.1. Контрольоване поле

    "use client";

    import { useState } from "react";

    export default function NameInput() {
      const [name, setName] = useState("");

      return (
        <div>
          <label htmlFor="name">Ім'я</label>

          <input
            id="name"
            name="name"
            type="text"
            value={name}
            onChange={(event) => setName(event.target.value)}
          />

          <p>Введене ім'я: {name}</p>
        </div>
      );
    }

У контрольованому полі значення зберігається у стані React.

### 16.2. Компонент поля

    type TextFieldProps = {
      id: string;
      label: string;
      value: string;
      onChange: (value: string) => void;
      placeholder?: string;
      error?: string;
    };

    export function TextField({
      id,
      label,
      value,
      onChange,
      placeholder,
      error,
    }: TextFieldProps) {
      const errorId = `${id}-error`;

      return (
        <div className="form-field">
          <label htmlFor={id}>{label}</label>

          <input
            id={id}
            name={id}
            type="text"
            value={value}
            placeholder={placeholder}
            onChange={(event) => onChange(event.target.value)}
            aria-invalid={Boolean(error)}
            aria-describedby={error ? errorId : undefined}
          />

          {error && (
            <p id={errorId}>
              {error}
            </p>
          )}
        </div>
      );
    }

Цей приклад показує базову структуру повторно використовуваного компонента. У production-компоненті можуть знадобитися додаткові props, стилі, підтримка різних типів полів і повна інтеграція з бібліотекою форм.

### 16.3. Що важливо для UI-дизайнера

Навіть якщо ти не пишеш компонент самостійно, розумій:

- які props впливають на зовнішній вигляд;
- як передається стан помилки;
- як відображається disabled-стан;
- як поле пов'язується з Label;
- як повторно використовувати один компонент;
- як дизайн-токени перетворюються на CSS;
- як уникати різного вигляду однакових полів у різних частинах застосунку.

## 17. Поширені помилки в дизайні Inputs

### Помилка 1. Placeholder замість Label

Користувач втрачає назву поля після введення значення.

**Рішення:** використовуй постійний Label.

### Помилка 2. Незрозуміле повідомлення про помилку

Повідомлення «Неправильно» не пояснює, що робити.

**Рішення:** повідомляй про конкретну проблему та спосіб її виправлення.

### Помилка 3. Надто слабкий контраст

Межі, підказки та введений текст погано видно.

**Рішення:** перевіряй контраст і читабельність у різних станах.

### Помилка 4. Відсутній Focus

Користувач клавіатури не розуміє, де перебуває.

**Рішення:** забезпечуй чіткий індикатор фокусу.

### Помилка 5. Помилка позначається лише кольором

Не всі користувачі можуть розрізняти кольори однаково.

**Рішення:** поєднуй колір із текстом, іконкою або іншим сигналом.

### Помилка 6. Надто багато полів

Форма вимагає інформацію, яка не потрібна для виконання завдання.

**Рішення:** скорочуй форму та пояснюй незвичні запити даних.

### Помилка 7. Поля мають неправильний тип

Номер телефону вводиться у звичайне текстове поле без відповідних підказок, або дата вимагає незрозумілого формату.

**Рішення:** вибирай тип поля відповідно до даних і сценарію використання.

### Помилка 8. Відсутній стан Disabled або Error

Користувач не розуміє, чому поле недоступне або чому значення не приймається.

**Рішення:** передбачай усі необхідні стани ще на етапі дизайну.

### Помилка 9. Візуально однакові різні стани

Focus, Error і Default не відрізняються.

**Рішення:** визначай окремі правила для кожного стану.

### Помилка 10. Надто малі поля на мобільному пристрої

Натискати на поле незручно, а введений текст погано читається.

**Рішення:** перевіряй компоненти на реальних розмірах екрана й сенсорних пристроях.

### Помилка 11. Поле не має програмно доступної назви

Візуально назва є, але вона не пов'язана з елементом введення.

**Рішення:** використовуй правильний HTML `label` або відповідний доступний механізм для конкретного компонента.

### Помилка 12. Дані зникають після помилки

Користувач змушений заповнювати форму заново.

**Рішення:** зберігай введені значення, якщо немає обґрунтованої причини їх очищати.

## 18. Практичний алгоритм дизайну Input

Коли створюєш нове поле, рухайся послідовно.

1. **Визнач призначення.** Які саме дані потрібно отримати?
2. **Вибери тип.** Текст, число, дата, пароль чи інший компонент?
3. **Сформулюй Label.** Чи зрозуміле призначення поля без placeholder?
4. **Визнач обов'язковість.** Чи справді потрібне це значення?
5. **Продумай підказку.** Чи потрібен приклад або пояснення?
6. **Визнач правила перевірки.** Які значення допустимі?
7. **Створи стани.** Default, Focus, Filled, Error, Disabled та інші потрібні варіанти.
8. **Продумай повідомлення.** Як користувач зрозуміє помилку?
9. **Перевір доступність.** Контраст, клавіатура, Label, фокус.
10. **Перевір адаптивність.** Чи зручно користуватися полем на телефоні?
11. **Перевір поведінку.** Чи зберігаються дані, чи працює очищення, чи зрозуміле завантаження?
12. **Узгодь дизайн-систему.** Чи відповідає поле іншим компонентам застосунку?

## 19. Практичний мініпроєкт: форма реєстрації

Створи невелику форму реєстрації користувача.

### Завдання

Потрібні поля:

- Ім'я;
- Електронна пошта;
- Пароль;
- Підтвердження пароля.

Також потрібні кнопка надсилання та посилання на вхід для вже зареєстрованих користувачів.

### Етап 1. Структура

    Створення акаунта

    Ім'я
    [____________________________]

    Електронна пошта
    [____________________________]

    Пароль
    [____________________________]

    Підтвердження пароля
    [____________________________]

    [Створити акаунт]

    Уже маєте акаунт? Увійти

### Етап 2. Візуальний дизайн

Визнач:

- ширину форми;
- відстань між полями;
- висоту Inputs;
- розмір Label;
- стиль кнопки;
- кольори меж;
- оформлення Focus;
- оформлення Error;
- мобільний макет.

### Етап 3. Стани

Для кожного поля перевір:

- порожнє;
- у фокусі;
- заповнене;
- помилкове;
- недоступне, якщо такий стан потрібний.

### Етап 4. Поведінка

Переконайся, що:

- обов'язкові поля перевіряються;
- електронна адреса має прийнятний формат;
- пароль відповідає встановленим правилам;
- підтвердження пароля збігається з паролем;
- повідомлення про помилки зрозумілі;
- після помилки введені дані не зникають без потреби.

### Етап 5. Доступність

Перевір:

- чи кожне поле має Label;
- чи можна пройти форму клавіатурою;
- чи видно Focus;
- чи достатній контраст;
- чи не передаються помилки лише кольором;
- чи повідомлення про помилки пов'язані з відповідними полями.

### Етап 6. Адаптивність

Перевір форму на вузькому екрані:

- чи не з'являється горизонтальне прокручування;
- чи не обрізається текст;
- чи достатньо місця для натискання;
- чи видно кнопку під час введення;
- чи зручно користуватися формою однією рукою.

## 20. Чекліст готовності Input

Перед завершенням компонента перевір його за списком.

### Структура

- [ ] Призначення поля зрозуміле.
- [ ] Label присутній і пов'язаний із полем.
- [ ] Placeholder не замінює Label.
- [ ] Helper text використовується лише за потреби.
- [ ] Обов'язковість поля позначена зрозуміло.

### Візуальний дизайн

- [ ] Висота та ширина відповідають сценарію використання.
- [ ] Внутрішні відступи комфортні.
- [ ] Текст легко читати.
- [ ] Межі та фон достатньо помітні.
- [ ] Focus чітко відрізняється від Default.
- [ ] Error має зрозуміле візуальне оформлення.
- [ ] Disabled не виглядає активним.
- [ ] Компонент узгоджений із дизайн-системою.

### Поведінка

- [ ] Вибрано правильний тип поля.
- [ ] Перевірка даних відповідає вимогам.
- [ ] Помилки пояснюють, як виправити значення.
- [ ] Введені дані зберігаються після помилки.
- [ ] Завантаження та інші стани зрозумілі.
- [ ] Інтерактивні іконки виконують очікувані дії.

### Доступність

- [ ] Поле доступне з клавіатури.
- [ ] Focus добре помітний.
- [ ] Контраст відповідає вимогам.
- [ ] Помилки не передаються лише кольором.
- [ ] Повідомлення пов'язані з полями програмно.
- [ ] Інтерфейс придатний для використання на мобільних пристроях.

## 21. Що потрібно запам'ятати

1. **Input — це не лише прямокутник із текстом.** Це компонент зі структурою, поведінкою та різними станами.
2. **Label називає поле.** Placeholder не повинен бути єдиним поясненням його призначення.
3. **Правильний тип поля спрощує введення.** Використовуй відповідний тип для тексту, електронної пошти, пароля, числа та інших даних.
4. **Стани мають бути передбачуваними.** Default, Focus, Error і Disabled повинні відрізнятися зрозуміло.
5. **Помилка повинна допомагати.** Пояснюй проблему та спосіб її виправлення.
6. **Доступність починається з основ.** Правильний Label, клавіатурна взаємодія, видимий Focus і достатній контраст.
7. **Не перевантажуй форму.** Запитуй лише необхідні дані.
8. **Зберігай введене.** Не змушуй користувача повторно заповнювати всю форму через одну помилку.
9. **Мобільна взаємодія важлива.** Перевіряй розміри, клавіатуру та доступність елементів.
10. **Дизайн-система забезпечує послідовність.** Повторно використовуй розміри, кольори, стани й правила оформлення.

## 23. Рівні освоєння теми

### Beginner

Ти вмієш:

- розпізнавати основні типи Inputs;
- правильно використовувати Label і Placeholder;
- створювати прості поля;
- налаштовувати розміри, відступи, кольори та межі;
- розрізняти основні стани.

### Intermediate

Ти вмієш:

- проєктувати форми з кількох полів;
- створювати зрозумілі повідомлення про помилки;
- враховувати валідацію;
- проєктувати мобільні форми;
- враховувати клавіатурну взаємодію та контраст;
- створювати узгоджені варіанти компонента.

### Advanced

Ти вмієш:

- створювати масштабовані компоненти для дизайн-системи;
- узгоджувати дизайн і поведінку з розробниками;
- проєктувати складні сценарії введення даних;
- передбачати асинхронну перевірку та завантаження;
- проєктувати доступні форми;
- оцінювати форми за зручністю, кількістю помилок і завершенням користувацького сценарію.

## 24. Місце теми в UI Design

`05-components/03-inputs` — частина розділу **Components**, присвяченого повторно використовуваним елементам інтерфейсу.

Ця тема пов'язана з:

- `02-layout-and-composition` — розташуванням полів, відступами та структурою форми;
- `03-color` — контрастом, кольорами меж і станами помилок;
- `04-typography` — шрифтами, розмірами тексту та читабельністю;
- `05-components/01-buttons` — кнопками надсилання й очищення;
- `05-components/02-links` — посиланнями на вхід, реєстрацію та інші дії навігації;
- темами Forms and Accessibility — доступністю та перевіркою даних;
- React / Next.js — реалізацією повторно використовуваних компонентів;
- дизайн-системами — токенами, варіантами й станами компонентів.

**Головний принцип:** якісне поле введення не просто приймає дані, а допомагає користувачеві зрозуміти завдання, правильно ввести значення, побачити помилку та успішно завершити дію.
