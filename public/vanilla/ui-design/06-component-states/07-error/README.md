# 07. Error States — Стани помилок інтерфейсу

## 1. Що таке Error States?

**Error States (стани помилок)** — це стани інтерфейсу, які повідомляють користувачеві, що певна дія не вдалася, дані не вдалося отримати або система не може продовжити операцію в поточних умовах.

Помилки можуть виникати під час:
- завантаження даних із сервера;
- надсилання форми;
- авторизації користувача;
- реєстрації нового акаунта;
- пошуку;
- завантаження файлів;
- збереження налаштувань;
- оплати або оформлення замовлення;
- роботи з мережею;
- взаємодії з полями введення.

Наприклад, користувач заповнює форму реєстрації та вводить некоректну адресу електронної пошти. Інтерфейс повинен не просто повідомити, що сталася помилка, а й пояснити, яке поле потрібно виправити.

Погане повідомлення:

    Помилка!

Краще повідомлення:

    Введіть коректну адресу електронної пошти.

Головне завдання Error State — **пояснити, що не вдалося, чому це могло статися та як користувач може продовжити роботу**.

### Для чого потрібні Error States?

- ✔ Пояснюють причину невдалої операції.
- ✔ Допомагають користувачеві виправити помилку.
- ✔ Зменшують невизначеність і роздратування.
- ✔ Запобігають повторенню тієї самої помилки.
- ✔ Допомагають зберігати введені користувачем дані.
- ✔ Забезпечують зрозумілу поведінку застосунку в непередбачених ситуаціях.
- ✔ Підвищують доступність інтерфейсу.
- ✔ Допомагають відновити роботу після збою.

## 2. Основні типи Error States

Помилки відрізняються за причиною, місцем виникнення та способом виправлення.

### 2.1. Validation Error — помилка валідації

**Validation Error** виникає, коли введені користувачем дані не відповідають вимогам.

Приклади:
- поле обов'язкового імені порожнє;
- email має неправильний формат;
- пароль занадто короткий;
- користувач ввів від'ємну кількість товарів;
- дата завершення передує даті початку;
- значення не відповідає заданому діапазону.

Приклад інтерфейсу:

    Email

    ┌──────────────────────────────┐
    │ userexample.com              │
    └──────────────────────────────┘
    Введіть коректну адресу email.

Приклад HTML:

    <label for="email">Email</label>

    <input
      id="email"
      name="email"
      type="email"
      aria-invalid="true"
      aria-describedby="email-error"
    />

    <p id="email-error">
      Введіть коректну адресу електронної пошти.
    </p>

Атрибут `aria-invalid="true"` повідомляє допоміжним технологіям, що значення поля вважається некоректним.

`aria-describedby` пов'язує поле з поясненням помилки.

**Рекомендації:**
- повідомляйте, що саме потрібно виправити;
- розміщуйте пояснення поруч із відповідним полем;
- не покладайтеся лише на червоний колір;
- зберігайте вже введені дані;
- не показуйте помилку до того, як вона стане доречною;
- повторно перевіряйте дані після виправлення.

### 2.2. Network Error — помилка мережі

**Network Error** виникає, коли клієнт не може успішно виконати запит через проблеми з мережею або з'єднанням.

Можливі причини:
- відсутність підключення до інтернету;
- нестабільне з'єднання;
- переривання запиту;
- недоступність сервера;
- помилка DNS;
- блокування запиту браузером або політиками безпеки.

Приклад інтерфейсу:

    Не вдалося завантажити дані.

    Перевірте підключення до інтернету
    та спробуйте ще раз.

    [ Повторити ]

Рекомендації:
- пояснюйте, що операція не вдалася;
- пропонуйте повторну спробу, якщо вона доречна;
- не видаляйте введені користувачем дані;
- не показуйте технічні деталі, які не допомагають користувачеві;
- якщо доступні попередні дані, вирішіть, чи можна безпечно залишити їх на екрані.

Не кожна мережева помилка означає, що сервер недоступний. Наприклад, браузерний `fetch()` може завершитися помилкою через проблему з'єднання, скасування запиту або обмеження доступу.

### 2.3. Server Error — помилка сервера

**Server Error** виникає, коли сервер не може успішно виконати запит або повертає помилку під час обробки.

Наприклад, HTTP-статус `500 Internal Server Error` означає, що сервер зіткнувся з неочікуваною проблемою.

Приклад інтерфейсу:

    Щось пішло не так.

    Не вдалося завантажити ваші замовлення.
    Спробуйте ще раз пізніше.

    [ Повторити ]

Рекомендації:
- пояснюйте ситуацію простою мовою;
- не показуйте користувачеві stack trace;
- не розкривайте внутрішні шляхи, секрети або технічні деталі;
- зберігайте введені дані, якщо це можливо;
- пропонуйте повторну спробу, коли вона має сенс;
- реєструйте технічні подробиці в системі журналювання, а не в повідомленні користувачеві.

### 2.4. Authentication Error — помилка автентифікації

Виникає, коли користувач не може увійти в систему.

Можливі причини:
- неправильний пароль;
- некоректна адреса email;
- прострочена сесія;
- відсутність необхідного токена;
- завершення терміну дії посилання для входу.

Приклад:

    Не вдалося увійти.

    Перевірте email і пароль або
    скористайтеся відновленням пароля.

    [ Спробувати ще раз ]
    [ Забули пароль? ]

Для входу за паролем не завжди варто окремо повідомляти, чи існує певна адреса email. Це може допомогти зловмисникам визначати зареєстровані акаунти. Повідомлення слід узгоджувати з вимогами безпеки застосунку.

### 2.5. Permission Error — помилка доступу

Виникає, коли користувач не має необхідних прав для виконання дії.

Приклад:

    У вас немає доступу до цієї сторінки.

    Якщо ви вважаєте, що це помилка,
    зверніться до адміністратора.

    [ Повернутися назад ]

Можливі причини:
- користувач не ввійшов у систему;
- користувач має недостатню роль;
- доступ до ресурсу обмежений;
- сесія завершилася;
- ресурс доступний лише певній групі користувачів.

Важливо: інтерфейс може приховувати недоступні дії, але перевірка прав доступу обов'язково має виконуватися на сервері. Приховування кнопки не є механізмом безпеки.

### 2.6. Not Found — ресурс не знайдено

Цей стан показують, коли запитуваний ресурс відсутній або більше недоступний.

Наприклад:
- сторінку видалено;
- користувач перейшов за неправильним посиланням;
- товар більше не існує;
- запис не знайдено;
- маршрут не відповідає жодній сторінці.

Типовий HTTP-статус для сторінки, якої немає, — `404 Not Found`.

Приклад:

    Сторінку не знайдено.

    Можливо, адресу введено неправильно
    або сторінку було переміщено.

    [ На головну ]

Це не обов'язково означає, що застосунок зламався. Часто це окремий передбачений стан, для якого потрібен відповідний дизайн.

### 2.7. Empty State — це не Error State

**Empty State** — це стан, у якому дані успішно завантажено, але результат порожній.

Наприклад:

    У вас поки немає замовлень.

    Після оформлення замовлення
    воно з'явиться тут.

Це не помилка, якщо запит завершився успішно й справді повернув порожній список.

Порівняймо:

- `Loading` — результат ще очікується.
- `Success` — операція успішна.
- `Empty` — результат успішний, але даних немає.
- `Error` — операція не вдалася.

Не слід показувати повідомлення про помилку лише тому, що список порожній.

## 3. Рівні помилок у компонентах

Error State може стосуватися одного поля, окремого компонента, цілого розділу або всього застосунку.

### 3.1. Field-Level Error — помилка поля

Використовують для помилок конкретного поля форми.

    Пароль

    ┌──────────────────────────────┐
    │ 123                           │
    └──────────────────────────────┘
    Пароль має містити щонайменше
    8 символів.

Особливості:
- помилка розташована поруч із полем;
- поле має зрозумілий візуальний стан;
- повідомлення описує спосіб виправлення;
- введене значення зберігається, якщо це безпечно.

### 3.2. Component-Level Error — помилка компонента

Використовують, коли не працює один компонент, але решта сторінки залишається доступною.

Наприклад, не завантажилася статистика:

    Статистика

    Не вдалося завантажити дані.

    [ Повторити ]

Навігація, заголовок та інші блоки сторінки можуть продовжувати працювати.

### 3.3. Section-Level Error — помилка розділу

Виникає, коли неможливо завантажити великий блок сторінки.

Наприклад:

    Мої замовлення

    Не вдалося завантажити список замовлень.

    [ Спробувати ще раз ]

Такий стан має замінювати або доповнювати лише той розділ, який не вдалося відобразити.

### 3.4. Page-Level Error — помилка сторінки

Використовують, коли основний контент сторінки недоступний.

Приклади:
- сторінку не знайдено;
- неможливо завантажити критично важливі дані;
- користувач не має доступу до маршруту;
- сталася неочікувана помилка рендерингу.

Навіть у такому стані варто зберігати доступні елементи навігації, якщо це доречно.

### 3.5. System-Level Error — системна помилка

Це проблема, яка впливає на весь застосунок або велику його частину.

Наприклад:

    Сервіс тимчасово недоступний.

    Ми вже працюємо над відновленням.
    Спробуйте пізніше.

    [ Повторити ]

Такий стан повинен бути зрозумілим і не перевантажувати користувача технічними деталями.

## 4. Візуальний дизайн Error States

Помилка має бути помітною, але не повинна створювати зайву тривогу.

### 4.1. Колір

Червоний часто використовують для позначення помилок, але сам по собі колір не повинен бути єдиним сигналом.

Приклад CSS:

    .field-error {
      color: #b91c1c;
      font-size: 0.875rem;
      margin-top: 0.375rem;
    }

    .input-error {
      border: 1px solid #b91c1c;
    }

Потрібно враховувати:
- контраст тексту з фоном;
- контраст меж поля;
- видимість повідомлення;
- доступність для людей із порушеннями сприйняття кольорів;
- узгодженість із кольорами дизайн-системи.

Не варто покладатися лише на червону рамку. Додайте текст або інший зрозумілий сигнал.

### 4.2. Іконки

Іконки можуть допомогти швидко розпізнати тип помилки.

Приклади:
- знак оклику — загальне попередження;
- хрестик — невдала дія;
- знак питання — потреба в поясненні;
- іконка мережі — проблема з'єднання.

Іконка має доповнювати текст, а не замінювати його.

### 4.3. Типографіка

Повідомлення про помилку повинно:
- легко читатися;
- бути достатньо помітним;
- мати зрозуміле формулювання;
- не конкурувати з основним контентом;
- залишатися читабельним на мобільних екранах.

Для коротких помилок біля поля можна використовувати компактний текст. Для помилки сторінки потрібні виразніший заголовок і пояснення.

### 4.4. Відступи та розташування

Для помилок полів повідомлення зазвичай розташовують безпосередньо під полем.

Для системних помилок використовують окремий блок.

Приклад:

    ┌──────────────────────────────────┐
    │ ⚠ Не вдалося зберегти зміни.     │
    │                                  │
    │ Перевірте з'єднання та           │
    │ спробуйте ще раз.                │
    │                                  │
    │ [ Повторити ]                    │
    └──────────────────────────────────┘

Відступи допомагають зрозуміти, до якого елемента належить повідомлення.

## 5. Як правильно писати повідомлення про помилки

Хороше повідомлення допомагає користувачеві зрозуміти ситуацію та діяти далі.

### 5.1. Конкретність

Погано:

    Некоректні дані.

Краще:

    Введіть дату у форматі ДД.ММ.РРРР.

Погано:

    Помилка запиту.

Краще:

    Не вдалося завантажити список замовлень.

### 5.2. Зрозуміла мова

Не показуйте користувачеві технічні повідомлення без пояснення.

Погано:

    TypeError: Cannot read properties of undefined.

Краще:

    Не вдалося завантажити профіль.
    Спробуйте ще раз.

Технічну помилку можна записати в журнал для розробника, а користувачеві показати зрозуміле повідомлення.

### 5.3. Наступний крок

Якщо можливо, пояснюйте, що робити далі.

Приклади:

    Пароль закороткий.
    Використайте щонайменше 8 символів.

    Не вдалося завантажити файл.
    Перевірте формат і розмір файлу.

    Сесію завершено.
    Увійдіть знову, щоб продовжити.

Не кожна помилка потребує кнопки. Вона потрібна лише тоді, коли користувачеві справді є що зробити.

### 5.4. Нейтральний тон

Уникайте формулювань, які звинувачують користувача.

Погано:

    Ви неправильно заповнили форму!

Краще:

    Перевірте поле «Email» і введіть коректну адресу.

Повідомлення має допомагати виправити ситуацію, а не створювати додаткове роздратування.

### 5.5. Не обіцяйте того, чого система не робить

Не пишіть:

    Ми вже виправляємо проблему.

якщо система не має підстав стверджувати це.

Краще:

    Сервіс тимчасово недоступний.
    Спробуйте пізніше.

Текст має відповідати реальному стану системи.

## 6. Error States у формах

Форми потребують особливої уваги, оскільки користувач витрачає час на введення даних.

### 6.1. Коли показувати помилку?

Помилку можна показувати:
- після спроби надіслати форму;
- після втрати полем фокуса;
- під час введення, якщо перевірка допомагає користувачеві;
- після відповіді сервера.

Не потрібно відразу показувати помилки для кожного порожнього поля, якщо користувач ще не почав заповнювати форму.

### 6.2. Inline Validation

**Inline Validation** — перевірка значення поля безпосередньо в інтерфейсі форми.

Наприклад, користувач вводить пароль і бачить вимоги:

    Пароль

    Використайте щонайменше 8 символів.

Якщо поле вже заповнено некоректно, можна показати відповідне пояснення.

Inline Validation особливо корисна, коли:
- правила введення складні;
- помилку легко виправити;
- користувачеві важливо бачити вимоги заздалегідь.

### 6.3. Client-Side і Server-Side Validation

**Client-Side Validation** виконується в браузері.

Переваги:
- швидкий зворотний зв'язок;
- не потрібно чекати відповіді сервера;
- зручніше виправляти прості помилки.

**Server-Side Validation** виконується на сервері.

Потрібна для:
- перевірки правил бізнес-логіки;
- перевірки унікальності email;
- перевірки доступу;
- контролю цілісності даних;
- захисту від маніпуляцій із клієнтською частиною.

Перевірка лише в браузері не забезпечує безпеку. Користувач може змінити або обійти клієнтський код.

### 6.4. Приклад поля з помилкою

    <div className="field">
      <label htmlFor="email">Email</label>

      <input
        id="email"
        name="email"
        type="email"
        aria-invalid={Boolean(error)}
        aria-describedby={error ? "email-error" : undefined}
      />

      {error && (
        <p id="email-error" className="field-error">
          {error}
        </p>
      )}
    </div>

Це приклад JSX. Значення `error` має надходити зі стану компонента або системи валідації.

### 6.5. Помилка всієї форми

Якщо сервер відхилив запит, але помилку не можна прив'язати до одного поля, використовуйте загальне повідомлення.

    Не вдалося зберегти форму.

    Перевірте дані та спробуйте ще раз.

При цьому не очищайте всі поля автоматично, якщо для цього немає вагомої причини.

## 7. Error States і доступність (Accessibility)

Помилки повинні бути доступними для людей, які використовують клавіатуру, скринридери або інші допоміжні технології.

### 7.1. Не використовуйте лише колір

Червоне поле без пояснення не повідомляє всім користувачам, що саме не так.

Поєднуйте:
- видимий текст помилки;
- зрозуміле розташування;
- відповідний стан поля;
- семантичні атрибути HTML та ARIA.

### 7.2. `aria-invalid`

Вказує, що значення поля не пройшло перевірку.

    <input
      id="username"
      name="username"
      aria-invalid="true"
      aria-describedby="username-error"
    />

Використовуйте його тоді, коли поле справді перебуває в стані помилки, а не просто тому, що воно порожнє під час першого відображення форми.

### 7.3. `aria-describedby`

Пов'язує поле з додатковим текстом, зокрема з повідомленням про помилку.

    <label for="password">Пароль</label>

    <input
      id="password"
      type="password"
      aria-invalid="true"
      aria-describedby="password-error"
    />

    <p id="password-error">
      Пароль має містити щонайменше 8 символів.
    </p>

### 7.4. `role="alert"`

Для важливого повідомлення, яке потрібно оголосити негайно, може бути доречним `role="alert"`.

    <div role="alert">
      Не вдалося зберегти зміни.
    </div>

Не використовуйте його для кожної дрібної зміни форми: надмірні оголошення можуть заважати користувачам скринридерів.

Для менш термінових статусів може бути доречним `role="status"`.

### 7.5. Фокус після помилки

Якщо форма має багато полів і користувач натиснув «Надіслати», але кілька полів некоректні, потрібно допомогти йому знайти проблеми.

Можливі рішення:
- показати короткий список помилок на початку форми;
- перемістити фокус до першого поля з помилкою;
- надати посилання на відповідні поля;
- зберегти введені значення.

Не переміщуйте фокус несподівано під час звичайного введення, якщо це перериває роботу користувача.

## 8. Error States і Loading States

Error State та Loading State — різні частини життєвого циклу операції.

Типова послідовність:

    Idle
      ↓
    Loading
      ↓
    ┌───────────┐
    │           │
    Success    Error

Наприклад, застосунок запитує список користувачів:

- `idle` — запит ще не розпочався;
- `loading` — дані завантажуються;
- `success` — дані отримано;
- `empty` — запит успішний, але список порожній;
- `error` — отримати дані не вдалося.

Приклад моделі стану:

    const [status, setStatus] = useState("idle");
    const [data, setData] = useState([]);
    const [error, setError] = useState("");

Залежно від складності компонента можна використовувати:
- boolean для простої операції;
- статус із кількома значеннями;
- окрему модель стану для складного процесу.

Головне — не змішувати різні ситуації в одному стані.

Наприклад, `data.length === 0` не означає автоматично помилку. Список може бути порожнім і при цьому успішно завантаженим.

## 9. Retry — повторна спроба

**Retry** — можливість повторити операцію після невдачі.

Приклад:

    Не вдалося завантажити дані.

    [ Спробувати ще раз ]

Retry доречний, якщо:
- проблема може бути тимчасовою;
- операцію можна безпечно повторити;
- користувач розуміє, що саме буде повторено.

### 9.1. Ручний Retry

Користувач сам натискає кнопку повторної спроби.

Переваги:
- користувач контролює процес;
- зрозуміло, коли починається новий запит;
- легко пояснити поведінку.

### 9.2. Автоматичний Retry

Система повторює запит без додаткового натискання.

Може бути корисним для короткочасних мережевих збоїв, але потрібно враховувати:
- кількість повторів;
- затримку між спробами;
- загальний час очікування;
- можливість дублювання операції;
- те, чи може користувач скасувати процес.

Не всі запити безпечно повторювати автоматично.

Наприклад, повторне отримання списку зазвичай простіше зробити безпечним, ніж повторне створення платежу або замовлення. Для важливих операцій потрібні відповідні механізми на сервері.

### 9.3. Retry з експоненційною затримкою

У системах, які повторюють запити автоматично, іноді використовують експоненційне збільшення затримки.

Приклад принципу:

    Спроба 1 → очікування 1 секунду
    Спроба 2 → очікування 2 секунди
    Спроба 3 → очікування 4 секунди

На практиці потрібно обмежувати кількість спроб і максимальну затримку. Часто також додають випадкове відхилення (jitter), щоб багато клієнтів не повторювали запити одночасно.

Для простого інтерфейсу не обов'язково реалізовувати складну retry-логіку. Часто достатньо зрозумілої кнопки повторної спроби.

## 10. Error States у формах React

Приклад форми, яка показує помилку після невдалого надсилання.

    import { useState } from "react";

    export default function LoginForm() {
      const [email, setEmail] = useState("");
      const [password, setPassword] = useState("");
      const [status, setStatus] = useState("idle");
      const [error, setError] = useState("");

      async function handleSubmit(event) {
        event.preventDefault();

        if (status === "loading") {
          return;
        }

        setStatus("loading");
        setError("");

        try {
          const response = await fetch("/api/login", {
            method: "POST",
            headers: {
              "Content-Type": "application/json",
            },
            body: JSON.stringify({ email, password }),
          });

          if (!response.ok) {
            throw new Error("Не вдалося увійти.");
          }

          setStatus("success");
        } catch {
          setStatus("error");
          setError(
            "Не вдалося увійти. Перевірте дані та спробуйте ще раз."
          );
        }
      }

      return (
        <form onSubmit={handleSubmit}>
          <label htmlFor="email">Email</label>
          <input
            id="email"
            type="email"
            value={email}
            onChange={(event) => setEmail(event.target.value)}
            required
          />

          <label htmlFor="password">Пароль</label>
          <input
            id="password"
            type="password"
            value={password}
            onChange={(event) => setPassword(event.target.value)}
            required
          />

          <button type="submit" disabled={status === "loading"}>
            {status === "loading" ? "Вхід..." : "Увійти"}
          </button>

          {status === "error" && (
            <p role="alert">{error}</p>
          )}

          {status === "success" && (
            <p role="status">Вхід успішний.</p>
          )}
        </form>
      );
    }

Це навчальний приклад. У реальному застосунку потрібно враховувати формат відповіді API, правила автентифікації, обробку сесії та вимоги безпеки.

### Що демонструє приклад?

- `status` описує поточний стан форми;
- `loading` блокує повторне натискання;
- `error` зберігає зрозуміле повідомлення;
- `try/catch` обробляє помилки запиту;
- після успішної операції показується відповідний статус;
- введені значення не очищуються автоматично після помилки.

## 11. HTTP-помилки та повідомлення інтерфейсу

Під час роботи з API важливо розрізняти мережеві помилки та HTTP-помилки.

### 11.1. Що повертає HTTP?

Сервер може повернути HTTP-статус:

| Статус | Значення | Можлива поведінка інтерфейсу |
|---|---|---|
| `400` | Некоректний запит | Пояснити, які дані потрібно виправити |
| `401` | Необхідна автентифікація | Запропонувати увійти знову |
| `403` | Доступ заборонено | Пояснити відсутність прав |
| `404` | Ресурс не знайдено | Показати стан «Не знайдено» |
| `409` | Конфлікт із поточним станом | Пояснити конфлікт і запропонувати дію |
| `422` | Дані не пройшли перевірку | Показати помилки відповідних полів |
| `429` | Забагато запитів | Повідомити про обмеження частоти запитів |
| `500` | Внутрішня помилка сервера | Показати загальне повідомлення про збій |
| `503` | Сервіс тимчасово недоступний | Запропонувати спробувати пізніше |

Це типові приклади, а не універсальні правила для кожного API. Поведінка має відповідати документації конкретного сервера.

### 11.2. Важлива особливість `fetch()`

`fetch()` не відхиляє Promise автоматично лише тому, що сервер повернув статус `404` або `500`.

Тому зазвичай потрібно перевіряти `response.ok`.

    async function loadUsers() {
      const response = await fetch("/api/users");

      if (!response.ok) {
        throw new Error("Не вдалося завантажити користувачів.");
      }

      return response.json();
    }

Якщо запит завершився мережевою помилкою, `fetch()` може відхилити Promise. Якщо ж сервер повернув HTTP-помилку, її потрібно обробити відповідно до статусу.

### 11.3. Не показуйте сирі помилки API

Не варто автоматично виводити повідомлення сервера в інтерфейс.

Причини:
- воно може бути незрозумілим;
- може містити внутрішні технічні деталі;
- формат відповіді може змінитися;
- повідомлення може містити небажані дані.

Краще перетворювати відповіді API на зрозумілі користувацькі повідомлення, а технічні деталі записувати в журнал.

## 12. Error States у списках і картках

Коли список не завантажився, потрібно відрізняти помилку від порожнього результату.

Приклад React:

    function ProductList({ products, status, onRetry }) {
      if (status === "loading") {
        return <ProductSkeleton />;
      }

      if (status === "error") {
        return (
          <section>
            <p>Не вдалося завантажити товари.</p>
            <button onClick={onRetry}>
              Спробувати ще раз
            </button>
          </section>
        );
      }

      if (products.length === 0) {
        return <p>Товарів поки немає.</p>;
      }

      return (
        <ul>
          {products.map((product) => (
            <li key={product.id}>
              {product.name}
            </li>
          ))}
        </ul>
      );
    }

Тут:
- `status` описує стан запиту;
- `products` містить отримані дані;
- `onRetry` запускає повторне завантаження;
- `ProductSkeleton` показує тимчасову структуру контенту.

Для реального компонента потрібно узгодити можливі значення `status` і не дозволяти суперечливим станам, наприклад одночасному відображенню помилки й успішного результату.

## 13. Error States у Next.js

У Next.js App Router передбачені механізми для обробки помилок рендерингу.

### 13.1. Файл `error.tsx`

Файл `error.tsx` дозволяє визначити UI для помилок у відповідному сегменті маршруту, які обробляються механізмом Error Boundary Next.js.

Приклад структури:

    src/
    └── app/
        └── dashboard/
            ├── error.tsx
            ├── loading.tsx
            └── page.tsx

Приклад `error.tsx`:

    "use client";

    export default function Error({
      error,
      reset,
    }: {
      error: Error & { digest?: string };
      reset: () => void;
    }) {
      return (
        <main>
          <h2>Не вдалося завантажити сторінку.</h2>

          <p>
            Спробуйте повторити дію.
          </p>

          <button onClick={() => reset()}>
            Спробувати ще раз
          </button>
        </main>
      );
    }

У цьому прикладі `error` доступний для діагностики, але його не потрібно автоматично показувати користувачеві.

`reset()` просить Next.js повторно спробувати рендеринг відповідного сегмента. Це не гарантує успішного повторного виконання будь-якого зовнішнього запиту: логіка отримання даних має бути організована відповідно до застосунку.

### 13.2. `error.tsx` і `not-found.tsx`

Ці файли мають різне призначення.

- `error.tsx` — обробка помилок у відповідному сегменті.
- `not-found.tsx` — UI для ситуацій, коли ресурс або маршрут не знайдено.

Сторінка `404` — це не те саме, що неочікувана помилка сервера.

### 13.3. `error.tsx` і локальні помилки форм

Не кожна помилка повинна запускати Error Boundary.

Наприклад:
- неправильний email — локальна помилка поля;
- невдалий запит збереження — помилка операції;
- помилка рендерингу компонента — може оброблятися через Error Boundary.

Вибір залежить від типу помилки та того, яку частину інтерфейсу потрібно зберегти доступною.

## 14. Error States у дизайн-системі

У дизайн-системі варто створити узгоджені компоненти для різних типів помилок.

### Можливі компоненти

- `FieldError` — повідомлення біля поля;
- `FormError` — загальна помилка форми;
- `InlineAlert` — повідомлення всередині розділу;
- `ErrorCard` — помилка окремого компонента;
- `PageError` — помилка сторінки;
- `NotFoundState` — ресурс не знайдено;
- `NetworkErrorState` — помилка з'єднання;
- `ErrorSummary` — список помилок форми.

### Приклад CSS-змінних

    :root {
      --color-error: #b91c1c;
      --color-error-background: #fef2f2;
      --color-error-border: #fecaca;
      --color-error-text: #7f1d1d;
      --error-border-radius: 8px;
      --error-spacing: 12px;
    }

Ці значення наведено як навчальний приклад. У реальній дизайн-системі кольори мають відповідати загальній палітрі й вимогам контрастності.

### Що потрібно стандартизувати?

- колір помилки;
- колір фону та межі;
- типографіку;
- відступи;
- іконки;
- стиль кнопки повторної спроби;
- правила показу повідомлень;
- поведінку після виправлення помилки;
- доступні назви та ARIA-атрибути.

Стандартизація допомагає користувачам швидше розпізнавати помилки на різних сторінках застосунку.

## 15. Типові помилки в дизайні Error States

### Помилка 1. Загальне повідомлення без пояснення

Погано:

    Сталася помилка.

Краще:

    Не вдалося зберегти налаштування.
    Перевірте з'єднання та спробуйте ще раз.

### Помилка 2. Повідомлення не підказує, що робити далі

Погано:

    Неправильний пароль.

Краще:

    Не вдалося увійти.
    Перевірте дані або відновіть пароль.

### Помилка 3. Помилка позначена лише кольором

Користувач бачить червону рамку, але не знає причини.

**Як правильно:** додати текстове пояснення та доступний зв'язок із полем.

### Помилка 4. Усі помилки показуються однаково

Помилка поля, недоступність сервера й відсутність прав — різні ситуації.

**Як правильно:** обирати повідомлення відповідно до причини та масштабу проблеми.

### Помилка 5. Дані користувача зникають після помилки

Користувач заповнив довгу форму, але після невдалого запиту всі поля очищуються.

**Як правильно:** зберігати введені дані, якщо це безпечно та відповідає логіці операції.

### Помилка 6. Помилка залишається після виправлення

Користувач виправив поле, але попереднє повідомлення продовжує показуватися.

**Як правильно:** оновлювати стан помилки відповідно до актуальних даних.

### Помилка 7. Нескінченне повторення запитів

Інтерфейс автоматично повторює невдалу операцію без обмежень.

**Як правильно:** обмежувати кількість спроб і враховувати тип операції.

### Помилка 8. Технічні деталі показуються користувачеві

Інтерфейс відображає stack trace, SQL-помилку або внутрішню адресу сервера.

**Як правильно:** показувати безпечне й зрозуміле повідомлення, а технічні подробиці зберігати в журналі.

### Помилка 9. Помилка перекриває весь інтерфейс без потреби

Не завантажилася одна картка, але користувач втратив доступ до всієї сторінки.

**Як правильно:** показувати Error State на відповідному рівні компонента.

### Помилка 10. Кнопка Retry не працює

Інтерфейс пропонує повторити дію, але кнопка не запускає новий запит або не оновлює стан.

**Як правильно:** пов'язувати кнопку з реальною функцією повторної спроби та перевіряти результат.

## 16. Як тестувати Error States

Під час розробки потрібно перевіряти не лише успішні сценарії.

### Сценарії тестування

1. Користувач залишає обов'язкове поле порожнім.
2. Користувач вводить некоректний email.
3. Сервер повертає `400`.
4. Сервер повертає `401`.
5. Сервер повертає `403`.
6. Сервер повертає `404`.
7. Сервер повертає `500`.
8. Мережевий запит завершується помилкою.
9. Користувач натискає Retry.
10. Повторний запит завершується успішно.
11. Повторний запит знову завершується помилкою.
12. Користувач виправляє некоректне поле.
13. Форма зберігає введені дані після невдачі.
14. Повідомлення помилки доступне для скринридера.
15. Інші компоненти сторінки продовжують працювати, якщо це можливо.

### Що перевіряти в DevTools?

У вкладці Network можна перевірити:
- HTTP-статус;
- тіло відповіді;
- час запиту;
- повторні запити;
- скасовані запити.

У Console можна перевірити:
- помилки JavaScript;
- необроблені відхилення Promise;
- повідомлення, які допомагають знайти причину проблеми.

Увага: відсутність повідомлень у Console не означає, що Error State працює правильно. Потрібно перевірити й фактичну поведінку інтерфейсу.

## 17. Практичний мініпроєкт: Error State для завантаження профілю

### Завдання

Створити компонент профілю користувача, який:
- показує Loading State під час запиту;
- показує профіль після успіху;
- показує Error State після невдачі;
- має кнопку повторної спроби;
- не показує технічні подробиці користувачеві.

### Модель стану

    const [status, setStatus] = useState("loading");
    const [user, setUser] = useState(null);

Можливі значення:

    "loading"
    "success"
    "error"

### Логіка завантаження

    async function loadUser() {
      setStatus("loading");

      try {
        const response = await fetch("/api/user");

        if (!response.ok) {
          throw new Error("Request failed");
        }

        const data = await response.json();

        setUser(data);
        setStatus("success");
      } catch {
        setStatus("error");
      }
    }

### Відображення станів

    if (status === "loading") {
      return <ProfileSkeleton />;
    }

    if (status === "error") {
      return (
        <section>
          <h2>Не вдалося завантажити профіль.</h2>
          <p>Спробуйте ще раз.</p>
          <button onClick={loadUser}>
            Повторити
          </button>
        </section>
      );
    }

    return <ProfileCard user={user} />;

Це фрагменти для навчання, а не повний готовий компонент. Потрібно також викликати `loadUser()` під час відповідного життєвого циклу, реалізувати `ProfileSkeleton` і `ProfileCard`, а тип `user` визначити відповідно до структури API.

### Що потрібно перевірити?

- Loading State зникає після завершення запиту.
- Помилка не залишає інтерфейс у нескінченному завантаженні.
- Retry запускає новий запит.
- Після успішної повторної спроби показується профіль.
- Користувач бачить зрозуміле повідомлення.
- Інтерфейс не розкриває зайвих технічних деталей.

## 18. Практичний мініпроєкт: Error States для форми

### Завдання

Створити форму з такими станами:
- `idle` — форма готова;
- `loading` — запит виконується;
- `success` — дані збережено;
- `error` — збереження не вдалося.

### Приклад

    import { useState } from "react";

    export default function SettingsForm() {
      const [name, setName] = useState("");
      const [status, setStatus] = useState("idle");
      const [error, setError] = useState("");

      async function handleSubmit(event) {
        event.preventDefault();

        if (status === "loading") {
          return;
        }

        setStatus("loading");
        setError("");

        try {
          const response = await fetch("/api/settings", {
            method: "POST",
            headers: {
              "Content-Type": "application/json",
            },
            body: JSON.stringify({ name }),
          });

          if (!response.ok) {
            throw new Error("Save failed");
          }

          setStatus("success");
        } catch {
          setStatus("error");
          setError("Не вдалося зберегти налаштування.");
        }
      }

      return (
        <form onSubmit={handleSubmit}>
          <label htmlFor="name">Ім'я</label>

          <input
            id="name"
            value={name}
            onChange={(event) => setName(event.target.value)}
            required
          />

          <button type="submit" disabled={status === "loading"}>
            {status === "loading" ? "Збереження..." : "Зберегти"}
          </button>

          {status === "error" && (
            <p role="alert">{error}</p>
          )}

          {status === "success" && (
            <p role="status">Налаштування збережено.</p>
          )}
        </form>
      );
    }

### Що демонструє приклад?

- Форма має кілька окремих станів.
- Повідомлення про помилку показується лише після невдачі.
- Під час запиту кнопка недоступна.
- У разі помилки введене значення зберігається.
- Після успіху користувач отримує зворотний зв'язок.

Для реального застосунку потрібно також визначити, як сервер повертає помилки валідації, і показувати їх біля відповідних полів, якщо це можливо.

## 19. Що потрібно пам'ятати

✔ Error State повідомляє, що операція або дія не вдалася.

✔ Повідомлення повинно бути конкретним і зрозумілим.

✔ Якщо можливо, пояснюйте наступний крок.

✔ Validation Error, Network Error і Server Error — різні типи помилок.

✔ Empty State не є помилкою, якщо запит успішно повернув порожній результат.

✔ Error State потрібно показувати на відповідному рівні: поле, компонент, розділ або сторінка.

✔ Не покладайтеся лише на червоний колір.

✔ `aria-invalid` допомагає позначити некоректне поле.

✔ `aria-describedby` пов'язує поле з поясненням.

✔ `role="alert"` підходить для важливих термінових повідомлень, але не для кожної дрібної зміни.

✔ Після помилки варто зберігати введені дані, якщо це безпечно.

✔ Retry повинен запускати реальну повторну спробу.

✔ Не кожну операцію безпечно повторювати автоматично.

✔ `fetch()` потрібно перевіряти через `response.ok`, оскільки HTTP-статуси помилок не відхиляють Promise автоматично.

✔ `error.tsx` у Next.js обробляє помилки відповідного сегмента, а `not-found.tsx` призначений для стану «Не знайдено».

✔ Технічні подробиці потрібно журналювати, а користувачеві показувати безпечні повідомлення.

✔ Помилки клієнтської валідації не замінюють перевірку на сервері.

## 20. Типові питання на співбесіді

### 1. Що таке Error State?

Це стан інтерфейсу, який повідомляє про невдалу операцію та допомагає користувачеві зрозуміти, що робити далі.

### 2. Чим Validation Error відрізняється від Server Error?

Validation Error виникає, коли дані не відповідають вимогам. Server Error означає, що сервер не зміг успішно виконати запит або обробити його.

### 3. Чим Empty State відрізняється від Error State?

Empty State означає, що запит успішний, але даних немає. Error State означає, що операція не вдалася.

### 4. Що таке Inline Validation?

Це перевірка введених даних із повідомленням про результат безпосередньо в інтерфейсі форми.

### 5. Чому не можна покладатися лише на клієнтську валідацію?

Клієнтський код можна змінити або обійти. Сервер повинен самостійно перевіряти дані та права доступу.

### 6. Для чого потрібен `aria-invalid`?

Він повідомляє допоміжним технологіям, що поле має некоректне значення.

### 7. Для чого потрібен `aria-describedby`?

Він пов'язує елемент форми з текстом, який його описує, наприклад із повідомленням про помилку.

### 8. Чи потрібно показувати користувачеві текст винятку JavaScript?

Зазвичай ні. Краще показати зрозуміле повідомлення, а технічні подробиці зберегти для діагностики.

### 9. Що робить Retry?

Він дозволяє повторити невдалу операцію. Повторення має бути доречним і безпечним для конкретного типу запиту.

### 10. Для чого потрібен `error.tsx` у Next.js?

Він визначає інтерфейс обробки помилок рендерингу у відповідному сегменті App Router.

- Створювати повідомлення біля полів форми.
- Використовувати зрозумілі тексти помилок.
- Не покладатися лише на колір.

- Зберігати введені значення після невдачі.

- Відображати різні стани форми.

- Узгоджувати помилки валідації з API.
- Проєктувати Error States для великих сторінок.
- Передбачати повторні запити й скасування.
- Враховувати безпеку повідомлень.

- Стандартизувати повідомлення у дизайн-системі.

### Senior — архітектурний рівень

- Проєктувати єдину стратегію обробки помилок.
- Розрізняти очікувані помилки бізнес-логіки й неочікувані системні помилки.
- Узгоджувати UX, логування та моніторинг.
- Проєктувати безпечні механізми Retry.
- Забезпечувати доступність і зрозумілу поведінку у складних сценаріях.
- Визначати, коли помилку можна локалізувати, а коли потрібен стан цілої сторінки.
- Створювати узгоджені патерни Error States для всього продукту.

## 23. Головна думка

**Хороший Error State не просто повідомляє, що сталася помилка. Він допомагає користувачеві зрозуміти ситуацію, виправити проблему або безпечно продовжити роботу.**

Під час проєктування потрібно відповісти на п'ять запитань:

1. Що саме не вдалося?
2. Чи зрозуміло користувачеві, у чому проблема?
3. Чи може він самостійно виправити ситуацію?
4. Яку дію система пропонує виконати далі?
5. Чи збережено дані та чи залишається інтерфейс доступним?

Якщо ці питання вирішені, Error State стає повноцінною частиною UX, а не просто червоним текстом під полем.
