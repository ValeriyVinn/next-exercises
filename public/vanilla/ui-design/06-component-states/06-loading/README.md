# 06. Loading States — Стани завантаження інтерфейсу

## 1. Що таке Loading States?

**Loading States (стани завантаження)** — це стани інтерфейсу, які показують користувачеві, що система виконує певну операцію та результат ще не готовий.

Завантаження може відбуватися під час:
- отримання даних із сервера;
- надсилання форми;
- авторизації користувача;
- завантаження зображень і файлів;
- виконання пошуку;
- оновлення або збереження інформації;
- переходу між сторінками;
- обробки платежу або іншої важливої операції.

Головне завдання loading state — **пояснити користувачеві, що відбувається, і дати зрозуміти, що потрібно робити далі**.

Наприклад, користувач натискає кнопку `Save`. Якщо нічого не змінюється, він може подумати, що натискання не спрацювало, і натиснути ще раз.

Якщо ж кнопка показує `Saving...`, а поруч з'являється індикатор завантаження, користувач розуміє, що операція триває.

### Для чого потрібні Loading States?

- ✔ Пояснюють, що система виконує операцію.
- ✔ Зменшують невизначеність під час очікування.
- ✔ Запобігають повторним натисканням кнопок.
- ✔ Допомагають зрозуміти, яка частина інтерфейсу завантажується.
- ✔ Роблять очікування візуально зрозумілішим.
- ✔ Покращують сприйняття швидкодії застосунку.
- ✔ Допомагають зберігати контекст під час отримання даних.
- ✔ Підвищують доступність інтерфейсу.

## 2. Основні типи Loading States

У дизайні інтерфейсів немає одного універсального індикатора завантаження. Вибір залежить від характеру операції, очікуваної тривалості та того, яка частина інтерфейсу залишається доступною.

### 2.1. Spinner — обертовий індикатор

**Spinner** — це анімований елемент, який зазвичай обертається та повідомляє, що операція ще виконується.

    ┌────────────────────────────┐
    │                            │
    │          ◌                 │
    │      Завантаження...       │
    │                            │
    └────────────────────────────┘

Використовують для:
- коротких операцій;
- завантаження невеликого блока даних;
- надсилання форми;
- оновлення окремого компонента;
- дій, тривалість яких заздалегідь невідома.

Приклад CSS:

    .spinner {
      width: 24px;
      height: 24px;
      border: 3px solid #e5e7eb;
      border-top-color: #2563eb;
      border-radius: 50%;
      animation: spin 0.8s linear infinite;
    }

    @keyframes spin {
      to {
        transform: rotate(360deg);
      }
    }

**Переваги:**
- компактний;
- зрозумілий;
- займає мало місця;
- підходить для кнопок і невеликих блоків.

**Недоліки:**
- не показує реальний прогрес;
- не повідомляє, скільки часу залишилося;
- тривале очікування без пояснень може дратувати.

> Spinner повідомляє, що робота триває, але не показує її фактичний відсоток виконання.

### 2.2. Progress Bar — індикатор прогресу

**Progress Bar** — це смуга, яка показує перебіг операції.

    Завантаження файлу

    [████████████░░░░░░░░] 60%

Використовують, коли:
- відомий загальний обсяг роботи;
- можна виміряти виконання у відсотках;
- завантажується великий файл;
- виконується імпорт або експорт;
- відбувається інсталяція;
- система може повідомити про фактичний прогрес.

Приклад HTML:

    <div
      class="progress"
      role="progressbar"
      aria-label="Завантаження файлу"
      aria-valuemin="0"
      aria-valuemax="100"
      aria-valuenow="60"
    >
      <div class="progress__bar" style="width: 60%"></div>
    </div>

Приклад CSS:

    .progress {
      width: 100%;
      height: 8px;
      overflow: hidden;
      background-color: #e5e7eb;
      border-radius: 999px;
    }

    .progress__bar {
      height: 100%;
      background-color: #2563eb;
      border-radius: inherit;
      transition: width 200ms ease;
    }

Важливо: не можна показувати випадкові відсотки так, ніби вони відображають реальний прогрес. Якщо система не знає, скільки залишилося, краще використати індикатор невизначеного прогресу.

### 2.3. Skeleton Screen — скелетон

**Skeleton Screen** — це тимчасова структура, яка повторює приблизну форму майбутнього контенту.

    ┌──────────────────────────────────┐
    │  ▬▬▬▬▬▬▬▬▬▬▬                    │
    │                                  │
    │  ▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬            │
    │  ▬▬▬▬▬▬▬▬▬▬▬▬▬                  │
    │  ▬▬▬▬▬▬▬▬▬                      │
    │                                  │
    │  ▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬▬              │
    └──────────────────────────────────┘

Скелетон може імітувати:
- заголовки;
- абзаци;
- аватари;
- зображення;
- картки товарів;
- рядки таблиць;
- блоки панелі керування.

Приклад HTML:

    <article class="product-skeleton" aria-hidden="true">
      <div class="skeleton skeleton--image"></div>
      <div class="skeleton skeleton--title"></div>
      <div class="skeleton skeleton--text"></div>
      <div class="skeleton skeleton--text-short"></div>
    </article>

Приклад CSS:

    .skeleton {
      background-color: #e5e7eb;
      border-radius: 6px;
      animation: skeleton-pulse 1.5s ease-in-out infinite;
    }

    .skeleton--image {
      width: 100%;
      aspect-ratio: 4 / 3;
    }

    .skeleton--title {
      width: 70%;
      height: 20px;
      margin-top: 16px;
    }

    .skeleton--text {
      width: 100%;
      height: 12px;
      margin-top: 10px;
    }

    .skeleton--text-short {
      width: 45%;
      height: 12px;
      margin-top: 10px;
    }

    @keyframes skeleton-pulse {
      0%,
      100% {
        opacity: 1;
      }

      50% {
        opacity: 0.45;
      }
    }

**Переваги:**
- показує, де саме з'явиться контент;
- зберігає приблизну структуру сторінки;
- допомагає зменшити відчуття порожнього екрана;
- особливо корисний для карток, стрічок і списків.

**Недоліки:**
- потребує додаткового дизайну;
- може створювати зайвий візуальний шум;
- не завжди потрібний для дуже коротких операцій.

Скелетон варто робити схожим на майбутній контент, а не просто заповнювати екран випадковими сірими блоками.

### 2.4. Button Loading — завантаження всередині кнопки

Цей стан показує, що дія, пов'язана з кнопкою, ще виконується.

Звичайний стан:

    [ Зберегти ]

Стан завантаження:

    [ ◌ Збереження... ]

Приклад HTML:

    <button type="submit" disabled>
      <span class="spinner" aria-hidden="true"></span>
      <span>Збереження...</span>
    </button>

Застосовують для:
- входу в акаунт;
- реєстрації;
- надсилання форми;
- збереження налаштувань;
- створення запису;
- підтвердження дії.

Рекомендації:
- змінювати текст кнопки, якщо це додає ясності;
- показувати індикатор поруч із текстом;
- не допускати повторного виконання тієї самої операції;
- зберігати розміри кнопки, щоб інтерфейс не смикався;
- повертати кнопку до нормального стану після завершення операції;
- передбачати зрозуміле повідомлення про помилку, якщо дія не вдалася.

Не кожну кнопку потрібно вимикати під час завантаження. Це залежить від дії: наприклад, кнопку скасування довгої операції часто варто залишити доступною.

### 2.5. Full Page Loading — завантаження всієї сторінки

Використовують, коли основний вміст сторінки ще неможливо показати.

    ┌────────────────────────────────────┐
    │                                    │
    │                                    │
    │                ◌                   │
    │                                    │
    │       Завантажуємо сторінку...     │
    │                                    │
    │                                    │
    └────────────────────────────────────┘

Може бути доречним:
- під час початкового завантаження застосунку;
- під час переходу, коли без попередніх даних сторінку не можна відобразити;
- під час відновлення критично важливого стану.

Проте повноекранне завантаження не слід використовувати автоматично для кожного запиту.

Якщо навігація, заголовок або частина контенту вже доступні, краще показати їх і завантажувати лише потрібний блок.

### 2.6. Inline Loading — локальне завантаження

**Inline Loading** — це індикатор усередині конкретного елемента або поряд із ним.

Приклади:
- індикатор біля поля пошуку;
- завантаження коментарів під публікацією;
- оновлення кількості товарів у кошику;
- завантаження результатів у таблиці.

    Результати пошуку

    ┌──────────────────────────────┐
    │ Знайдено: ◌                  │
    └──────────────────────────────┘

Локальний індикатор дозволяє залишити інші частини інтерфейсу доступними.

### 2.7. Overlay Loading — накладений індикатор

**Overlay** — напівпрозорий шар поверх компонента або області сторінки.

    ┌──────────────────────────────┐
    │  Дані користувача            │
    │                              │
    │      ◌ Оновлення...          │
    │                              │
    └──────────────────────────────┘

Може використовуватися, коли:
- оновлюється таблиця;
- перераховуються результати;
- виконується операція над карткою;
- потрібно тимчасово заблокувати взаємодію з певною областю.

Не слід без потреби блокувати весь екран. Область блокування має відповідати області, яка справді недоступна.

## 3. Вибір індикатора залежно від ситуації

| Ситуація | Рекомендований підхід |
|---|---|
| Коротка дія в кнопці | Spinner усередині кнопки |
| Отримання списку даних | Skeleton або локальний Spinner |
| Завантаження карток | Skeleton Screen |
| Передавання файлу | Progress Bar, якщо відомий прогрес |
| Пошук | Inline Loading |
| Оновлення таблиці | Локальний Spinner або Overlay |
| Початкове завантаження застосунку | Компактний екран завантаження, якщо потрібен |
| Довга фонова операція | Статус операції та, за можливості, прогрес |
| Завантаження зображення | Заглушка або Skeleton для зображення |

**Основний принцип:** індикатор повинен відповідати масштабу операції.

Якщо завантажується один рядок таблиці, не потрібно блокувати всю сторінку. Якщо користувач завантажує великий файл, одного маленького Spinner може бути недостатньо.

## 4. Loading States як частина життєвого циклу компонента

Компонент інтерфейсу може переходити між кількома станами.

    Idle → Loading → Success
                  ↘ Error

Наприклад, форма має такі стани:

- `idle` — форма готова до роботи;
- `loading` — дані надсилаються;
- `success` — операція успішна;
- `error` — сталася помилка.

Список даних може мати іншу модель:

- `loading` — дані отримуються;
- `success` — дані отримано;
- `empty` — даних немає;
- `error` — отримати дані не вдалося.

Важливо розрізняти **Loading**, **Empty** та **Error**:

- `Loading` — результат ще очікується.
- `Empty` — запит завершився успішно, але даних немає.
- `Error` — запит не завершився успішно.

Не можна використовувати Skeleton нескінченно, якщо запит уже завершився помилкою.

### Приклад структури станів

    const state = {
      status: "loading",
      data: null,
      error: null,
    };

Тут `status` описує поточний стан, а `data` та `error` зберігають відповідні дані.

Для невеликого компонента можна використовувати окремий boolean:

    const [isLoading, setIsLoading] = useState(false);

Для складнішого компонента з кількома можливими результатами зручніше використовувати статус:

    const [status, setStatus] = useState("idle");

    // Можливі значення:
    // "idle", "loading", "success", "error"

Не потрібно створювати складну систему станів для кожної простої кнопки. Модель має відповідати реальній складності компонента.

## 5. Як проєктувати хороший Loading State

### 5.1. Повідомляйте, що відбувається

Самого індикатора іноді недостатньо.

Незрозуміло:

    ◌

Зрозуміліше:

    ◌ Завантаження профілю...

Для короткої операції може бути достатньо Spinner. Для довшої або важливої операції текст допомагає зменшити невизначеність.

Приклади текстів:
- `Завантаження...`
- `Зберігаємо зміни...`
- `Надсилаємо форму...`
- `Завантажуємо файл...`
- `Оновлюємо результати...`
- `Готуємо звіт...`

Текст має описувати реальну дію. Не варто повідомляти про відсоток або етап, якого система насправді не вимірює.

### 5.2. Не змінюйте різко геометрію інтерфейсу

Після появи Skeleton реальний контент не повинен без потреби змінювати всю структуру сторінки.

Для цього:
- задавайте приблизну висоту зображень;
- резервуйте місце під контент;
- використовуйте однакову структуру Skeleton і готового компонента;
- за потреби застосовуйте `aspect-ratio`;
- уникайте стрибків верстки.

Приклад:

    .product-image {
      width: 100%;
      aspect-ratio: 4 / 3;
      object-fit: cover;
    }

Фіксоване співвідношення сторін допомагає зберегти місце до завантаження самого зображення.

### 5.3. Враховуйте тривалість очікування

Різні операції потребують різного зворотного зв'язку.

**Коротка операція**
- компактний Spinner;
- індикатор у кнопці;
- мінімум додаткового тексту.

**Помітне очікування**
- Skeleton або локальний індикатор;
- пояснювальний текст;
- збереження доступності інших частин інтерфейсу.

**Тривала операція**
- статус операції;
- реальний прогрес, якщо він доступний;
- можливість скасування, якщо це підтримується;
- зрозуміле повідомлення, якщо операція затримується.

Не існує універсальної кількості мілісекунд, після якої обов'язково треба показувати конкретний індикатор. Це залежить від контексту, швидкодії та очікувань користувача.

### 5.4. Не приховуйте весь контент без необхідності

Якщо користувач оновлює список, попередні дані іноді краще залишити видимими, додавши індикатор оновлення.

Це особливо корисно, коли:
- оновлення коротке;
- старі дані ще мають цінність;
- користувач порівнює попередній і новий результат;
- перезавантаження всієї області створило б зайві візуальні зміни.

Однак для критично застарілих або потенційно небезпечних даних потрібно чітко позначати, що вони не є актуальними.

### 5.5. Передбачайте завершення операції

Після завантаження інтерфейс має перейти до відповідного стану:

- успіх — показати результат;
- порожній результат — показати Empty State;
- помилка — показати Error State;
- скасування — повернути компонент у придатний стан.

Loading не є кінцевим станом, якщо сама операція не виконується постійно.

## 6. Loading States та доступність (Accessibility)

Індикатор завантаження має бути зрозумілим не лише візуально.

### 6.1. Не покладайтеся лише на анімацію

Spinner може бути непомітним для користувача, який не бачить анімації або використовує допоміжні технології.

Якщо це важливо для розуміння дії, додайте текст:

    <div role="status">
      <span class="spinner" aria-hidden="true"></span>
      <span>Завантаження профілю...</span>
    </div>

`role="status"` допомагає допоміжним технологіям повідомляти про зміну статусу.

Декоративний Spinner має `aria-hidden="true"`, щоб його не озвучували як незрозумілий елемент.

### 6.2. Використовуйте `aria-busy`

`aria-busy="true"` може повідомляти допоміжним технологіям, що область інтерфейсу перебуває в процесі оновлення.

    <section aria-busy="true">
      <h2>Ваші замовлення</h2>
      <p>Завантаження замовлень...</p>
    </section>

Після завершення операції:

    <section aria-busy="false">
      <h2>Ваші замовлення</h2>
      <p>Замовлень поки немає.</p>
    </section>

Ставте `aria-busy` на ту область, яка справді оновлюється, а не на весь документ автоматично.

### 6.3. Не використовуйте `disabled` як єдиний сигнал

Якщо кнопка вимкнена під час завантаження, користувачеві все одно потрібно пояснити, чому вона недоступна.

    <button type="submit" disabled>
      Збереження...
    </button>

Для важливої дії корисно поєднати:
- стан недоступності;
- зрозумілий текст;
- візуальний індикатор;
- доступне повідомлення про статус.

### 6.4. Враховуйте `prefers-reduced-motion`

Деякі користувачі віддають перевагу інтерфейсам із мінімумом анімації.

    @media (prefers-reduced-motion: reduce) {
      .spinner {
        animation: none;
      }

      .skeleton {
        animation: none;
      }
    }

Якщо анімація вимкнена, індикатор усе одно має бути зрозумілим за формою, кольором або текстом.

## 7. Анімація Loading States

Анімація допомагає показати, що операція триває. Але вона не повинна відволікати від основного завдання.

### Основні принципи

- Анімація має бути плавною.
- Вона не повинна надмірно привертати увагу.
- Не варто використовувати багато одночасних рухомих елементів.
- Не можна створювати враження реального прогресу, якщо його немає.
- Потрібно враховувати налаштування зменшення руху.
- Анімація має бути доречною для тривалості операції.

### Приклади

Spinner:

    @keyframes spin {
      to {
        transform: rotate(360deg);
      }
    }

    .spinner {
      animation: spin 0.8s linear infinite;
    }

Пульсація Skeleton:

    @keyframes pulse {
      0%,
      100% {
        opacity: 1;
      }

      50% {
        opacity: 0.5;
      }
    }

    .skeleton {
      animation: pulse 1.5s ease-in-out infinite;
    }

Рухома смуга невизначеного прогресу:

    .progress-indeterminate {
      position: relative;
      overflow: hidden;
      height: 4px;
      background-color: #e5e7eb;
    }

    .progress-indeterminate::after {
      content: "";
      position: absolute;
      inset: 0 auto 0 0;
      width: 35%;
      background-color: #2563eb;
      animation: progress-move 1.2s ease-in-out infinite;
    }

    @keyframes progress-move {
      from {
        transform: translateX(-100%);
      }

      to {
        transform: translateX(300%);
      }
    }

Ці приклади показують три різні способи передавання стану: обертання, пульсацію та рух смуги.

## 8. Loading States у формах

Форми — одне з найважливіших місць для правильного відображення завантаження.

Типовий сценарій:

    Idle
      ↓
    User submits form
      ↓
    Loading
      ↓
    ┌─────────────┐
    │             │
    Success      Error

### Що потрібно передбачити?

1. Користувач натискає кнопку надсилання.
2. Форма перевіряє введені дані.
3. Якщо дані коректні, починається запит.
4. Користувач бачить стан завантаження.
5. Повторне випадкове надсилання тієї самої форми запобігається.
6. Після завершення показується успіх або помилка.

Приклад React:

    import { useState } from "react";

    export default function ContactForm() {
      const [isLoading, setIsLoading] = useState(false);
      const [message, setMessage] = useState("");

      async function handleSubmit(event) {
        event.preventDefault();

        if (isLoading) {
          return;
        }

        setIsLoading(true);
        setMessage("");

        try {
          // Тут виконується запит до сервера.
          await submitContactForm();

          setMessage("Повідомлення надіслано.");
        } catch {
          setMessage("Не вдалося надіслати повідомлення.");
        } finally {
          setIsLoading(false);
        }
      }

      return (
        <form onSubmit={handleSubmit}>
          <label>
            Email
            <input type="email" name="email" required />
          </label>

          <button type="submit" disabled={isLoading}>
            {isLoading ? "Надсилання..." : "Надіслати"}
          </button>

          <p role="status" aria-live="polite">
            {message}
          </p>
        </form>
      );
    }

У цьому прикладі `submitContactForm()` — умовна функція, яку потрібно реалізувати окремо.

**Що важливо:**
- `isLoading` керує відображенням стану;
- `try/catch/finally` обробляє успішне завершення та помилки;
- `finally` повертає кнопку до нормального стану;
- `disabled` зменшує ризик повторного надсилання;
- `role="status"` повідомляє про зміну статусу.

Перевірка `if (isLoading)` корисна як додатковий захист на рівні обробника, але не замінює серверні механізми запобігання дублюванню важливих операцій.

## 9. Loading States у списках і картках

У списках часто краще використовувати Skeleton, ніж великий Spinner.

Приклад React:

    function ProductList({ products, isLoading }) {
      if (isLoading) {
        return (
          <div className="product-list" aria-busy="true">
            <ProductSkeleton />
            <ProductSkeleton />
            <ProductSkeleton />
          </div>
        );
      }

      if (products.length === 0) {
        return <p>Товарів поки немає.</p>;
      }

      return (
        <div className="product-list">
          {products.map((product) => (
            <ProductCard key={product.id} product={product} />
          ))}
        </div>
      );
    }

Тут `ProductSkeleton` і `ProductCard` — компоненти, які потрібно створити окремо.

Послідовність відображення:

- `isLoading === true` — показати скелетони;
- завантаження завершилося, список порожній — показати Empty State;
- є дані — показати картки.

Для реального застосунку потрібно також передбачити стан помилки. Якщо `isLoading` — єдиний стан, компонент може не розрізнити порожній результат і невдалий запит.

## 10. Loading States у пошуку

Пошук часто запускається після введення тексту. Якщо запит надсилається на сервер, варто показати, що результати оновлюються.

Приклад:

    function SearchBox() {
      const [query, setQuery] = useState("");
      const [isLoading, setIsLoading] = useState(false);
      const [results, setResults] = useState([]);

      async function handleSearch() {
        setIsLoading(true);

        try {
          const data = await searchItems(query);
          setResults(data);
        } finally {
          setIsLoading(false);
        }
      }

      return (
        <div>
          <input
            value={query}
            onChange={(event) => setQuery(event.target.value)}
            placeholder="Пошук..."
          />

          <button onClick={handleSearch} disabled={isLoading}>
            {isLoading ? "Пошук..." : "Знайти"}
          </button>

          {isLoading && <p role="status">Шукаємо результати...</p>}

          {!isLoading && results.length === 0 && (
            <p>Результатів поки немає.</p>
          )}
        </div>
      );
    }

Це навчальний приклад: `searchItems()` потрібно реалізувати, а для повноцінного компонента додати `catch`, щоб обробляти помилки.

Для пошуку в реальному застосунку також можуть знадобитися:
- затримка перед надсиланням запиту (debounce);
- скасування застарілих запитів;
- захист від показу результатів попереднього пошуку;
- окремий стан помилки;
- розрізнення порожнього запиту та порожнього результату.

## 11. Loading States і продуктивність

Правильний дизайн завантаження не замінює оптимізацію продуктивності.

Якщо сторінка завантажується повільно, варто перевірити:
- розмір JavaScript-бандла;
- кількість мережевих запитів;
- час відповіді сервера;
- розмір зображень;
- кешування;
- повторні запити;
- завантаження непотрібних компонентів;
- блокування головного потоку.

Loading State лише пояснює, що відбувається. Він не робить повільну операцію швидшою.

### Важливе розрізнення

**Performance optimization** — скорочує час очікування.

**Loading state** — допомагає користувачеві зрозуміти очікування.

Найкращий результат досягається тоді, коли застосунок і швидкий, і зрозумілий у ситуаціях, коли очікування все ж виникає.

---

## 12. Типові помилки в дизайні Loading States

### Помилка 1. Вічний Spinner

Індикатор продовжує крутитися, хоча запит завершився помилкою.

**Як правильно:** переходити до Success, Empty або Error залежно від результату.

### Помилка 2. Повноекранний індикатор для локальної дії

Оновлюється одна таблиця, але вся сторінка стає недоступною.

**Як правильно:** показувати індикатор біля таблиці або всередині неї.

### Помилка 3. Немає пояснення для довгої операції

Користувач бачить лише Spinner протягом тривалого часу.

**Як правильно:** додати статус або пояснювальний текст, а для тривалих операцій — реальний прогрес, якщо він відомий.

### Помилка 4. Фальшивий відсоток прогресу

Progress Bar показує `90%`, хоча система не вимірює виконання.

**Як правильно:** використовувати невизначений індикатор, якщо фактичний прогрес невідомий.

### Помилка 5. Кнопка не змінюється після натискання

Користувач натискає `Save`, але не бачить жодної реакції.

**Як правильно:** показувати стан виконання та захищати від ненавмисного повторного надсилання.

### Помилка 6. Зміщення контенту після завантаження

Після появи даних елементи сторінки різко переміщуються.

**Як правильно:** резервувати місце та проєктувати Skeleton, який відповідає майбутній структурі.

### Помилка 7. Занадто багато анімації

Одночасно рухаються всі картки, заголовки й кнопки.

**Як правильно:** залишити мінімальну анімацію, яка допомагає зрозуміти стан.

### Помилка 8. Loading не має доступного тексту

Користувач бачить індикатор, але допоміжні технології не повідомляють про завантаження.

**Як правильно:** додати доступний статус, наприклад через `role="status"`.

### Помилка 9. Скелетон не відповідає контенту

Показуються випадкові блоки, які не нагадують майбутній інтерфейс.

**Як правильно:** відтворювати приблизні розміри та структуру реальних елементів.

### Помилка 10. Відсутній спосіб скасувати довгу операцію

Користувач не може зупинити операцію, хоча скасування технічно можливе.

**Як правильно:** передбачити кнопку `Скасувати`, якщо дія підтримує безпечне скасування.

## 13. Як перевіряти Loading States у DevTools

Під час розробки не варто перевіряти завантаження лише на швидкому локальному з'єднанні.

У браузерних DevTools можна:
- увімкнути обмеження швидкості мережі;
- подивитися, як змінюється інтерфейс під час повільного запиту;
- перевірити, чи блокується кнопка;
- перевірити обробку помилок у вкладці Network;
- перевірити, чи не запускається багато однакових запитів;
- перевірити, чи правильно приховується Spinner;
- перевірити адаптивність індикатора на мобільному екрані.

Корисні сценарії тестування:

1. Запит завершується швидко.
2. Запит триває кілька секунд.
3. Сервер повертає помилку.
4. Мережа недоступна.
5. Сервер повертає порожній список.
6. Користувач повторно натискає кнопку.
7. Користувач переходить на іншу сторінку до завершення запиту.
8. Запит скасовується, якщо скасування підтримується.

Це допомагає перевірити не лише зовнішній вигляд, а й правильність переходів між станами.

## 14. Практичний мініпроєкт: Loading States для картки профілю

### Завдання

Створити картку користувача, яка:
- показує Skeleton під час завантаження;
- показує профіль після успішного запиту;
- показує повідомлення про помилку;
- має кнопку повторного завантаження.

### Модель стану

    const [status, setStatus] = useState("loading");
    const [user, setUser] = useState(null);

Можливі значення `status`:

    "loading"
    "success"
    "error"

### Логіка

    async function loadUser() {
      setStatus("loading");

      try {
        const response = await fetch("/api/user");

        if (!response.ok) {
          throw new Error("Не вдалося завантажити профіль");
        }

        const data = await response.json();

        setUser(data);
        setStatus("success");
      } catch {
        setStatus("error");
      }
    }

### Відображення

    if (status === "loading") {
      return <ProfileSkeleton />;
    }

    if (status === "error") {
      return (
        <div>
          <p>Не вдалося завантажити профіль.</p>
          <button onClick={loadUser}>
            Спробувати ще раз
          </button>
        </div>
      );
    }

    return <ProfileCard user={user} />;

Для повного компонента потрібно викликати `loadUser()` під час відповідного життєвого циклу, наприклад через `useEffect`, а також реалізувати `ProfileSkeleton` і `ProfileCard`.

### Що потрібно перевірити?

- Skeleton зникає після завершення запиту.
- Дані профілю відображаються після успіху.
- Помилка не залишає користувача на нескінченному завантаженні.
- Повторна спроба запускає новий запит.
- Текст повідомлень зрозумілий.
- Стан завантаження доступний для допоміжних технологій.

## 15. Loading States у Next.js

У Next.js є вбудовані механізми відображення стану завантаження.

### 15.1. Файл `loading.tsx`

У Next.js App Router файл `loading.tsx` дозволяє визначити інтерфейс завантаження для маршруту.

Приклад структури:

    src/
    └── app/
        └── dashboard/
            ├── loading.tsx
            ├── page.tsx
            └── components/
                └── DashboardSkeleton.tsx

Приклад `loading.tsx`:

    export default function Loading() {
      return (
        <main aria-busy="true">
          <h1>Панель керування</h1>
          <p role="status">Завантаження...</p>
        </main>
      );
    }

Next.js може показувати цей UI, поки відповідний сегмент маршруту завантажується через механізми маршрутизації та потокового рендерингу.

### 15.2. Локальний стан компонента

Для дії всередині сторінки, наприклад збереження налаштувань, зазвичай використовують локальний стан компонента.

    "use client";

    import { useState } from "react";

    export default function SaveButton() {
      const [isLoading, setIsLoading] = useState(false);

      async function handleSave() {
        if (isLoading) {
          return;
        }

        setIsLoading(true);

        try {
          // Тут виконується операція збереження.
        } finally {
          setIsLoading(false);
        }
      }

      return (
        <button onClick={handleSave} disabled={isLoading}>
          {isLoading ? "Збереження..." : "Зберегти"}
        </button>
      );
    }

Цей приклад демонструє лише керування індикатором. Реальну операцію збереження потрібно реалізувати окремо, а її помилки — обробити через `catch` або інший відповідний механізм.

### 15.3. Коли використовувати `loading.tsx`, а коли локальний Spinner?

| Ситуація | Рішення |
|---|---|
| Завантаження маршруту | `loading.tsx` |
| Збереження форми | Локальний стан |
| Пошук у межах сторінки | Inline Loading |
| Завантаження карток | Skeleton |
| Оновлення одного віджета | Локальний Spinner |
| Завантаження окремої частини маршруту | Loading UI відповідного сегмента або компонента |

Не потрібно перетворювати кожен локальний запит на повноекранне завантаження.

## 16. Loading States у дизайн-системі

У дизайн-системі варто визначити єдині правила для станів завантаження.

### Компоненти

- `Spinner`
- `ProgressBar`
- `Skeleton`
- `ButtonLoading`
- `CardSkeleton`
- `TableSkeleton`
- `PageLoading`

### Токени дизайну

Приклад CSS-змінних:

    :root {
      --loading-color: #2563eb;
      --skeleton-color: #e5e7eb;
      --loading-duration: 800ms;
      --skeleton-duration: 1500ms;
      --loading-size-sm: 16px;
      --loading-size-md: 24px;
      --loading-size-lg: 40px;
    }

Ці значення є навчальним прикладом. У реальній дизайн-системі кольори, розміри та швидкості мають відповідати загальним правилам проєкту.

### Що потрібно стандартизувати?

- розміри Spinner;
- товщину лінії;
- колір індикатора;
- відступи;
- типи Skeleton;
- правила анімації;
- доступні текстові повідомлення;
- поведінку кнопок під час запиту;
- поведінку інтерфейсу за `prefers-reduced-motion`.

Перевага стандартизації полягає в тому, що різні сторінки застосунку демонструють завантаження послідовно.

## 17. Що потрібно пам'ятати

✔ Loading State повідомляє, що операція ще триває.

✔ Spinner підходить для компактного індикатора, але не показує реальний прогрес.

✔ Progress Bar використовують для вимірюваного прогресу.

✔ Skeleton відтворює приблизну структуру майбутнього контенту.

✔ Button Loading допомагає зрозуміти, що натискання спрацювало.

✔ Локальний індикатор часто кращий за блокування всієї сторінки.

✔ Loading, Empty і Error — різні стани.

✔ Кожен запит повинен завершуватися відповідним станом інтерфейсу.

✔ `aria-busy` та `role="status"` можуть допомогти зробити завантаження доступнішим.

✔ Анімації мають враховувати `prefers-reduced-motion`.

✔ Не можна видавати умовний відсоток за реальний прогрес.

✔ Skeleton не повинен створювати зайвих стрибків верстки.

✔ Loading State покращує зрозумілість очікування, але не замінює оптимізацію продуктивності.

✔ У Next.js `loading.tsx` підходить для завантаження маршруту, а локальний стан — для дій усередині компонента.

## 18. Типові питання на співбесіді

### 1. Що таке Loading State?

Це стан інтерфейсу, який повідомляє, що система виконує операцію й результат ще не готовий.

### 2. Чим Spinner відрізняється від Progress Bar?

Spinner показує, що операція триває, але зазвичай не відображає відсоток виконання. Progress Bar може показувати вимірюваний прогрес.

### 3. Що таке Skeleton Screen?

Це тимчасове представлення структури майбутнього контенту, яке показується до отримання реальних даних.

### 4. Чим Loading відрізняється від Empty State?

Loading означає, що результат ще очікується. Empty State означає, що запит завершився успішно, але даних немає.

### 5. Чому потрібно блокувати кнопку під час надсилання форми?

Щоб зменшити ризик повторного надсилання тієї самої дії. Проте для важливих операцій потрібен також захист на рівні сервера.

### 6. Чи потрібно завжди показувати Spinner?

Ні. Для карток і списків часто краще підходить Skeleton, а для тривалого вимірюваного процесу — Progress Bar.

### 7. Що робити, якщо завантаження триває довго?

Показувати зрозумілий статус, використовувати реальний прогрес за його наявності, зберігати доступність інших елементів і передбачати скасування, якщо воно можливе.

### 8. Що таке `aria-busy`?

Це ARIA-атрибут, який повідомляє допоміжним технологіям, що певна область перебуває в процесі оновлення.

### 9. Навіщо потрібен `prefers-reduced-motion`?

Він дозволяє адаптувати анімацію до системного налаштування користувача щодо зменшення руху.

### 10. Чи може Loading State замінити оптимізацію швидкодії?

Ні. Він робить очікування зрозумілішим, але не скорочує фактичний час виконання операції.

## 19. План вивчення за рівнями

### Core — базовий рівень

- Розуміти призначення Loading States.
- Розрізняти Spinner, Progress Bar і Skeleton.
- Створювати простий Spinner через CSS.
- Створювати Skeleton для картки.
- Додавати стан завантаження до кнопки.
- Розуміти різницю між Loading, Empty та Error.

### Junior — практичний рівень

- Реалізовувати Loading State через React `useState`.
- Обробляти запити через `async/await`.
- Використовувати `try/catch/finally`.
- Не допускати повторного надсилання форми.
- Створювати доступні індикатори.
- Тестувати завантаження за повільної мережі.
- Використовувати `loading.tsx` у Next.js.

### Middle — системний рівень

- Проєктувати узгоджені стани для складних компонентів.
- Створювати повторно використовувані Loading-компоненти.
- Передбачати скасування запитів.
- Уникати показу застарілих результатів.
- Зменшувати зміщення контенту під час завантаження.
- Узгоджувати Loading, Empty, Error і Success у дизайн-системі.
- Враховувати доступність та налаштування анімації.

### Senior — архітектурний рівень

- Проєктувати стратегію завантаження для всього застосунку.
- Визначати, коли показувати Skeleton, а коли зберігати попередні дані.
- Узгоджувати UX завантаження з кешуванням і потоковим рендерингом.
- Виявляти проблеми продуктивності за допомогою профілювання.
- Стандартизувати стани та поведінку компонентів у дизайн-системі.
- Оцінювати вплив станів завантаження на доступність і завершення користувацьких сценаріїв.

## 21. Головна думка

**Хороший Loading State не просто показує анімацію — він пояснює, що відбувається, зберігає контекст і допомагає користувачеві зрозуміти, чого очікувати.**

Під час проєктування потрібно відповісти на чотири запитання:

1. Що саме зараз завантажується?
2. Який індикатор найкраще відповідає цій операції?
3. Що побачить користувач після завершення, у разі помилки або відсутності даних?
4. Чи залишається інтерфейс зрозумілим і доступним під час очікування?

Якщо ці чотири питання вирішені, Loading State стає повноцінною частиною UX, а не просто декоративною анімацією.
