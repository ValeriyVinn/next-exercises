# 08. Success States — Стани успішного завершення

## 1. Що таке Success States?

**Success States (стани успіху)** — це стани інтерфейсу, які повідомляють користувачеві, що певна дія успішно завершилася або система досягла очікуваного результату.

Наприклад, користувач:
- успішно зареєструвався;
- увійшов до свого акаунта;
- зберіг налаштування;
- надіслав форму;
- створив новий запис;
- завантажив файл;
- оформив замовлення;
- оплатив покупку;
- скопіював текст;
- завершив навчальний урок.

Якщо після натискання кнопки нічого не змінюється, користувач може не зрозуміти, чи виконалася дія.

Success State дає чітку відповідь: **операцію завершено, результат отримано, можна продовжувати роботу**.

Наприклад:

    [ Зберегти ]

Після успішного збереження:

    ✓ Зміни збережено.

Або:

    [ Надіслати ]

Після успішного надсилання:

    ✓ Повідомлення надіслано.

### Для чого потрібні Success States?

- ✔ Підтверджують, що дія виконалася.
- ✔ Зменшують невизначеність.
- ✔ Допомагають користувачеві зрозуміти результат своїх дій.
- ✔ Запобігають зайвим повторним натисканням.
- ✔ Створюють відчуття контролю над інтерфейсом.
- ✔ Допомагають орієнтуватися у складних процесах.
- ✔ Підтримують зрозумілий перехід між станами компонента.
- ✔ Покращують загальний користувацький досвід (UX).

## 2. Основні типи Success States

Успіх може відображатися по-різному. Вибір залежить від важливості операції, тривалості процесу та того, наскільки помітним має бути результат.

### 2.1. Inline Success — вбудоване повідомлення

**Inline Success** — це коротке повідомлення, яке з'являється поруч із відповідним компонентом.

Приклад:

    Email

    ┌──────────────────────────────┐
    │ user@example.com              │
    └──────────────────────────────┘

    ✓ Email підтверджено.

Використовують для:
- підтвердження поля;
- перевірки введених даних;
- збереження окремого значення;
- копіювання тексту;
- невеликої операції всередині компонента.

Приклад HTML:

    <p role="status">
      Email успішно підтверджено.
    </p>

**Переваги:**
- займає мало місця;
- не перериває роботу;
- пов'язаний із конкретною дією;
- не перекриває основний контент.

Inline Success доречний, коли результат невеликий і не потребує окремого екрана.

### 2.2. Toast Success — коротке сповіщення

**Toast** — це тимчасове повідомлення, яке з'являється поверх інтерфейсу або в спеціально відведеній області.

Приклад:

    ┌────────────────────────────────┐
    │ ✓ Налаштування збережено.      │
    └────────────────────────────────┘

Toast часто використовують для:
- збереження налаштувань;
- копіювання тексту;
- додавання товару до кошика;
- оновлення запису;
- успішного виконання невеликої дії.

Приклад CSS:

    .toast {
      display: flex;
      align-items: center;
      gap: 8px;
      padding: 12px 16px;
      border-radius: 8px;
      background-color: #ecfdf5;
      color: #065f46;
      border: 1px solid #a7f3d0;
    }

**Рекомендації:**
- повідомлення має бути коротким;
- не перекривайте важливі елементи;
- не показуйте багато сповіщень одночасно;
- враховуйте доступність і керування клавіатурою;
- не зникайте надто швидко, якщо користувачеві потрібно прочитати текст.

Toast підходить для підтвердження, яке не потребує негайної відповіді.

### 2.3. Success Message — повідомлення про успіх

Це помітніше повідомлення, яке може залишатися на сторінці до наступної дії користувача.

Приклад:

    ✓ Налаштування успішно оновлено.

    Усі зміни збережено.

Використовують для:
- успішного надсилання форми;
- оновлення профілю;
- завершення налаштування;
- підтвердження email;
- виконання адміністративної дії.

На відміну від Toast, повідомлення не обов'язково має автоматично зникати.

### 2.4. Success Screen — екран успіху

**Success Screen** — окремий екран або великий блок, який показує завершення важливого сценарію.

Приклад:

    ┌──────────────────────────────────┐
    │                                  │
    │                 ✓                │
    │                                  │
    │       Замовлення оформлено!      │
    │                                  │
    │   Номер замовлення: #1024        │
    │                                  │
    │   [ Переглянути замовлення ]     │
    │                                  │
    └──────────────────────────────────┘

Використовують після:
- оформлення замовлення;
- оплати;
- реєстрації;
- завершення складного налаштування;
- надсилання важливої заявки;
- завершення навчального процесу.

Success Screen може містити:
- заголовок;
- короткий опис;
- підтвердження результату;
- номер операції;
- наступний крок;
- кнопку переходу до іншого розділу.

Не потрібно створювати окремий екран для кожної маленької дії. Масштаб підтвердження має відповідати важливості результату.

### 2.5. Success State кнопки

Кнопка може змінювати текст або вигляд після виконання операції.

До натискання:

    [ Зберегти ]

Під час операції:

    [ Збереження... ]

Після успіху:

    [ ✓ Збережено ]

Цей підхід доречний для:
- збереження налаштувань;
- додавання до обраного;
- підписки;
- копіювання;
- невеликих дій із миттєвим результатом.

Важливо: не кожна кнопка повинна залишатися у стані успіху назавжди. Якщо дія може виконуватися повторно, інтерфейс має чітко визначати, як повернутися до початкового стану.

### 2.6. Success State картки або списку

Успіх може відображатися без окремого повідомлення.

Наприклад:
- новий товар з'являється в кошику;
- створений запис з'являється у списку;
- змінене ім'я відображається в профілі;
- завершене завдання позначається галочкою;
- лічильник оновлюється після виконання дії.

У таких випадках сам результат може бути достатнім підтвердженням.

Проте для важливих або тривалих операцій корисно додати коротке текстове повідомлення.

## 3. Вибір Success State залежно від ситуації

| Ситуація | Рекомендований підхід |
|---|---|
| Копіювання тексту | Короткий Toast |
| Збереження налаштувань | Toast або Inline Success |
| Підтвердження поля | Inline Success |
| Надсилання контактної форми | Success Message |
| Реєстрація акаунта | Success Screen або повідомлення |
| Оформлення замовлення | Success Screen |
| Успішна оплата | Помітний Success Screen |
| Додавання товару до кошика | Toast і/або оновлення кошика |
| Завершення навчального уроку | Success State уроку |
| Виконання завдання у списку | Оновлений стан елемента |
| Оновлення профілю | Inline Success або Toast |

**Основний принцип:** підтвердження має відповідати важливості дії.

Для копіювання тексту достатньо короткого повідомлення. Для оплати потрібне чітке підтвердження, яке дозволяє користувачеві переконатися, що операція завершилася успішно.

## 4. Success States як частина життєвого циклу компонента

Компонент може переходити між кількома станами.

    Idle → Loading → Success
                  ↘ Error

Наприклад, кнопка збереження має такі стани:

- `idle` — кнопка готова до натискання;
- `loading` — збереження виконується;
- `success` — зміни збережено;
- `error` — збереження не вдалося.

Приклад:

    const [status, setStatus] = useState("idle");

Можливі значення:

    "idle"
    "loading"
    "success"
    "error"

### Чому важливо розділяти стани?

Якщо використовувати один boolean `isLoading`, він показуватиме лише те, чи триває операція.

Але він не пояснює:
- чи завершилася операція успішно;
- чи сталася помилка;
- чи потрібно показати підтвердження;
- чи можна повторити дію.

Для простого індикатора boolean може бути достатньо. Для форми або складнішого компонента з кількома результатами зручніше використовувати статус.

### Приклад логіки

    async function handleSave() {
      setStatus("loading");

      try {
        await saveData();
        setStatus("success");
      } catch {
        setStatus("error");
      }
    }

Тут `saveData()` — умовна функція, яка має виконувати реальне збереження даних.

## 5. Як проєктувати хороший Success State

### 5.1. Чітко підтверджуйте результат

Після завершення операції користувач повинен розуміти, що саме відбулося.

Незрозуміло:

    ✓ Готово.

Зрозуміліше:

    ✓ Налаштування збережено.

Для простих дій слово «Готово» може бути достатнім, якщо контекст однозначний. Для важливих операцій краще назвати конкретний результат.

Приклади:
- `Повідомлення надіслано.`
- `Профіль оновлено.`
- `Файл завантажено.`
- `Товар додано до кошика.`
- `Замовлення оформлено.`
- `Зміни збережено.`

### 5.2. Показуйте реальний успіх

Не показуйте повідомлення про успіх до підтвердження результату операції.

Поганий сценарій:

    Користувач натискає «Зберегти»
             ↓
    Інтерфейс одразу показує «Збережено»
             ↓
    Запит завершується помилкою

Це створює хибне враження, що дані збережено.

Кращий сценарій:

    Користувач натискає «Зберегти»
             ↓
    Loading State
             ↓
    Сервер підтверджує успіх
             ↓
    Success State

Для деяких застосунків можливе оптимістичне оновлення інтерфейсу, але тоді потрібно передбачити повернення до попереднього стану, якщо операція не вдалася.

### 5.3. Не перевантажуйте повідомлення

Погано:

    Вітаємо! Ваша дія була успішно виконана,
    і система завершила обробку всіх необхідних
    операцій, пов'язаних із вашим запитом.

Краще:

    ✓ Дані успішно збережено.

Коротке повідомлення легше прочитати та зрозуміти.

### 5.4. Пропонуйте наступний крок

Для важливих операцій користувачеві може бути потрібна додаткова дія.

Наприклад:

    Замовлення оформлено!

    Номер замовлення: #1024

    [ Переглянути замовлення ]
    [ Продовжити покупки ]

Наступний крок повинен відповідати контексту. Не додавайте кнопки лише для заповнення вільного місця.

### 5.5. Не змінюйте інтерфейс без потреби

Після успіху не варто:
- несподівано переносити користувача на іншу сторінку;
- очищувати форму без зрозумілої причини;
- приховувати важливі дані;
- змінювати розташування всіх елементів;
- показувати велику анімацію після кожної дрібної дії.

Інтерфейс має підтвердити результат, зберігаючи контекст.

## 6. Візуальний дизайн Success States

### 6.1. Колір

Зелений часто асоціюється з успіхом, але не є обов'язковим у кожному інтерфейсі.

Приклад CSS:

    .success-message {
      color: #166534;
      background-color: #f0fdf4;
      border: 1px solid #bbf7d0;
      padding: 12px 16px;
      border-radius: 8px;
    }

Колір має відповідати дизайн-системі та забезпечувати достатній контраст.

Не покладайтеся лише на зелений колір. Додавайте текст, іконку або інший зрозумілий сигнал.

### 6.2. Іконки

Для успіху часто використовують:
- галочку;
- коло з галочкою;
- символ завершення;
- іконку підтвердження.

Іконка допомагає швидко розпізнати стан, але не повинна замінювати важливий текст.

Приклад:

    ✓ Профіль оновлено.

### 6.3. Типографіка

Повідомлення має бути:
- читабельним;
- коротким;
- достатньо помітним;
- узгодженим з іншими повідомленнями;
- зрозумілим на мобільному екрані.

Для Toast достатньо короткого тексту. Для Success Screen можна використати заголовок, опис і додаткові деталі.

### 6.4. Анімація

Анімація може підкреслити завершення дії.

Наприклад:
- галочка плавно з'являється;
- кнопка змінює текст;
- Toast з'являється та зникає;
- кількість товарів у кошику оновлюється.

Але анімація не повинна:
- затримувати доступ до результату;
- відволікати від важливого контенту;
- бути надмірно довгою;
- створювати проблеми користувачам, чутливим до руху.

### 6.5. Відступи та розташування

Повідомлення має розташовуватися поруч із дією або результатом, до якого воно належить.

Наприклад:
- підтвердження поля — біля поля;
- підтвердження збереження — біля відповідного компонента або у Toast;
- підтвердження оплати — на окремому екрані результату.

Правильне розташування допомагає користувачеві зрозуміти, до чого належить повідомлення.

## 7. Toast Notifications: правила використання

Toast — один із найпоширеніших способів показати короткий успішний результат.

### 7.1. Коли використовувати Toast?

Toast доречний, коли:
- дія завершилася успішно;
- користувачеві не потрібно вводити додаткові дані;
- результат не потребує окремої сторінки;
- потрібно зберегти контекст поточного екрана.

Приклади:
- `Посилання скопійовано.`
- `Налаштування збережено.`
- `Товар додано до обраного.`

### 7.2. Коли не варто використовувати Toast?

Не варто покладатися лише на короткий Toast, коли:
- користувач повинен прочитати важливі деталі;
- операція має фінансові наслідки;
- потрібен наступний крок;
- результат потрібно зберігати на екрані;
- повідомлення містить складні інструкції.

Наприклад, після успішної оплати краще показати окремий екран із номером замовлення та подальшими діями.

### 7.3. Тривалість Toast

Тривалість залежить від:
- довжини повідомлення;
- важливості результату;
- кількості інформації;
- можливості повторити дію;
- вимог доступності.

Не потрібно встановлювати однаковий час для всіх повідомлень.

Якщо користувачеві потрібно прочитати деталі або виконати дію, краще не ховати повідомлення автоматично надто швидко.

### 7.4. Не створюйте потік сповіщень

Якщо кожна дрібна дія створює новий Toast, інтерфейс може перетворитися на постійний потік повідомлень.

Краще:
- об'єднувати пов'язані результати;
- не дублювати повідомлення;
- показувати лише важливі підтвердження;
- уникати багаторазових однакових сповіщень.

## 8. Success States у формах

Форми часто завершуються успішним надсиланням або збереженням.

Типовий сценарій:

    Idle
      ↓
    Користувач надсилає форму
      ↓
    Loading
      ↓
    Success
      або
    Error

### Що потрібно передбачити?

1. Користувач заповнює форму.
2. Дані проходять валідацію.
3. Запускається запит.
4. Інтерфейс показує Loading State.
5. Сервер підтверджує успішну операцію.
6. Інтерфейс показує Success State.
7. Користувач розуміє, що відбулося далі.

### Приклад React

    import { useState } from "react";

    export default function ContactForm() {
      const [status, setStatus] = useState("idle");
      const [message, setMessage] = useState("");

      async function handleSubmit(event) {
        event.preventDefault();

        if (status === "loading") {
          return;
        }

        setStatus("loading");
        setMessage("");

        try {
          const response = await fetch("/api/contact", {
            method: "POST",
            body: new FormData(event.currentTarget),
          });

          if (!response.ok) {
            throw new Error("Submission failed");
          }

          setStatus("success");
          setMessage("Повідомлення успішно надіслано.");
        } catch {
          setStatus("error");
          setMessage("Не вдалося надіслати повідомлення.");
        }
      }

      return (
        <form onSubmit={handleSubmit}>
          <label htmlFor="email">Email</label>
          <input
            id="email"
            name="email"
            type="email"
            required
          />

          <label htmlFor="message">Повідомлення</label>
          <textarea
            id="message"
            name="message"
            required
          />

          <button type="submit" disabled={status === "loading"}>
            {status === "loading" ? "Надсилання..." : "Надіслати"}
          </button>

          {status === "success" && (
            <p role="status">{message}</p>
          )}

          {status === "error" && (
            <p role="alert">{message}</p>
          )}
        </form>
      );
    }

Це навчальний приклад. Маршрут `/api/contact` потрібно реалізувати окремо.

### Що важливо?

- `status` описує поточний стан форми;
- `loading` показує виконання запиту;
- `success` підтверджує успішне надсилання;
- `error` показує невдалу операцію;
- `role="status"` допомагає повідомити про успіх;
- `role="alert"` доречний для важливої помилки.

Не потрібно очищувати форму автоматично в кожному випадку. Рішення залежить від того, чи може користувач захотіти переглянути або використати введені дані повторно.

## 9. Success States для кнопок

Кнопки часто потребують короткого підтвердження після дії.

### Приклад 1. Збереження

    Початковий стан:
    [ Зберегти ]

    Під час операції:
    [ Збереження... ]

    Після успіху:
    [ ✓ Збережено ]

### Приклад 2. Копіювання

    Початковий стан:
    [ Копіювати посилання ]

    Після успіху:
    [ ✓ Скопійовано ]

### Приклад 3. Підписка

    Початковий стан:
    [ Підписатися ]

    Після успіху:
    [ ✓ Ви підписані ]

При цьому потрібно розрізняти два сценарії:

- **Дія завершилася:** наприклад, текст скопійовано.
- **Стан змінився:** наприклад, користувач підписався.

У першому випадку кнопка може повернутися до початкового вигляду після короткого підтвердження.

У другому випадку новий стан може бути постійним, оскільки він відображає поточний стан системи.

### Приклад React

    import { useState } from "react";

    export default function SaveButton() {
      const [status, setStatus] = useState("idle");

      async function handleSave() {
        if (status === "loading") {
          return;
        }

        setStatus("loading");

        try {
          await saveData();
          setStatus("success");
        } catch {
          setStatus("error");
        }
      }

      return (
        <div>
          <button
            onClick={handleSave}
            disabled={status === "loading"}
          >
            {status === "loading" && "Збереження..."}
            {status === "success" && "✓ Збережено"}
            {status === "error" && "Спробувати ще раз"}
            {status === "idle" && "Зберегти"}
          </button>

          {status === "success" && (
            <p role="status">Зміни успішно збережено.</p>
          )}
        </div>
      );
    }

Функцію `saveData()` потрібно реалізувати окремо.

Зверни увагу: якщо `status === "error"`, повторне натискання викличе `handleSave()` знову. Для складнішого компонента потрібно також визначити, як очищується повідомлення про помилку та коли кнопка повертається до початкового стану.

## 10. Success States у списках і картках

Успіх часто найкраще показувати через безпосереднє оновлення даних.

Наприклад, користувач натискає «Додати до обраного»:

    До дії:
    ♡ Додати до обраного

    Після успіху:
    ♥ У вибраному

Або користувач завершує завдання:

    ☐ Підготувати звіт

    Після завершення:

    ☑ Підготувати звіт

У таких сценаріях змінений стан елемента сам по собі може підтверджувати дію.

### Коли потрібне додаткове повідомлення?

Додатковий Toast може бути корисним, якщо:
- дія не має очевидного візуального результату;
- оновлення відбувається далеко від кнопки;
- операція тривала;
- результат важливий для користувача.

Не потрібно дублювати кожну зміну великим повідомленням. Надмірні підтвердження можуть перевантажити інтерфейс.

## 11. Success States і доступність (Accessibility)

Успіх має бути зрозумілим користувачам, які не покладаються лише на візуальні зміни.

### 11.1. Не використовуйте лише зелений колір

Якщо кнопка просто змінює колір із синього на зелений, користувач може не зрозуміти, що операція завершилася.

Краще додати текст:

    ✓ Зміни збережено.

### 11.2. Використовуйте `role="status"`

Для повідомлень про успіх, які не потребують негайного переривання роботи, часто підходить `role="status"`.

    <p role="status">
      Налаштування збережено.
    </p>

Це дозволяє допоміжним технологіям повідомити про зміну статусу.

### 11.3. Використовуйте `aria-live` за потреби

Атрибут `aria-live` дозволяє повідомляти допоміжним технологіям про зміни в певній області.

    <p aria-live="polite">
      Файл успішно завантажено.
    </p>

`polite` зазвичай підходить для повідомлень, які можна оголосити без негайного переривання поточної роботи користувача.

Для багатьох звичайних статусних повідомлень достатньо `role="status"`. Не потрібно бездумно додавати всі ARIA-атрибути одночасно.

### 11.4. Не переміщуйте фокус без потреби

Після невеликої успішної дії не потрібно автоматично переносити фокус на повідомлення.

Для важливого сценарію з окремим екраном результату, наприклад після оформлення замовлення, перехід до нового заголовка або сторінки може бути доречним.

Головне — щоб користувач клавіатури розумів, де він перебуває і що сталося.

### 11.5. Враховуйте зменшення руху

Анімації успіху мають поважати системне налаштування `prefers-reduced-motion`.

    @media (prefers-reduced-motion: reduce) {
      .success-icon {
        animation: none;
      }

      .toast {
        transition: none;
      }
    }

Анімація може бути декоративною, але текстове підтвердження повинно залишатися зрозумілим і без неї.

## 12. Success States для важливих операцій

Деякі операції потребують докладнішого підтвердження.

### 12.1. Реєстрація

Після створення акаунта можна показати:

    Акаунт створено!

    Тепер ви можете увійти
    та почати користуватися сервісом.

    [ Перейти до входу ]

Якщо потрібне підтвердження email, не слід стверджувати, що адреса вже підтверджена. Краще написати:

    Акаунт створено.

    Перевірте пошту, щоб підтвердити адресу
    електронної пошти.

### 12.2. Оплата

Після успішної оплати важливо повідомити:
- що операцію підтверджено;
- суму, якщо це доречно;
- номер замовлення або транзакції;
- наступні кроки;
- де знайти деталі.

Приклад:

    Оплату підтверджено!

    Замовлення №1024

    Сума: 1 250 грн

    [ Переглянути замовлення ]

Не показуйте Success State оплати лише на основі натискання кнопки. Потрібне підтвердження від відповідної системи оплати або сервера.

### 12.3. Завантаження файлу

Після успішного завантаження можна показати:

    ✓ Файл завантажено.

    report.pdf

Якщо файл завантажено на сервер, переконайтеся, що сервер підтвердив успішний результат. Якщо файл лише вибрано у формі, це ще не означає, що його завантажено.

### 12.4. Видалення

Після видалення елемента можна показати:

    Елемент видалено.

Якщо система підтримує відновлення, можна запропонувати дію `Скасувати`.

Однак видалення не завжди можна скасувати, тому не слід показувати кнопку відновлення, якщо такої можливості немає.

## 13. Success States і помилки API

Успішне завершення операції потрібно визначати за фактичним результатом, а не лише за відсутністю помилки JavaScript.

### Приклад запиту

    async function saveSettings(settings) {
      const response = await fetch("/api/settings", {
        method: "POST",
        headers: {
          "Content-Type": "application/json",
        },
        body: JSON.stringify(settings),
      });

      if (!response.ok) {
        throw new Error("Не вдалося зберегти налаштування.");
      }

      return response.json();
    }

Після виклику цієї функції компонент може показати Success State лише тоді, коли операція успішно завершилася відповідно до контракту API.

### Чому це важливо?

Метод `fetch()` не відхиляє Promise автоматично для HTTP-статусів `400` або `500`.

Тому потрібно перевіряти `response.ok` або інший визначений контрактом критерій успіху.

Водночас не кожен успішний HTTP-статус означає, що у відповіді є JSON. Наприклад, `204 No Content` означає, що успішна відповідь не містить тіла. Код потрібно адаптувати до конкретного API.

### Що потрібно враховувати?

- відповідь сервера;
- HTTP-статус;
- структуру даних;
- можливу помилку мережі;
- дублювання операції;
- повторне натискання;
- коректне оновлення інтерфейсу.

## 14. Success States у Next.js

У Next.js App Router Success State зазвичай реалізується безпосередньо в компоненті або на сторінці результату.

### 14.1. Успішне збереження у клієнтському компоненті

    "use client";

    import { useState } from "react";

    export default function ProfileSettings() {
      const [status, setStatus] = useState("idle");

      async function handleSave() {
        setStatus("loading");

        try {
          const response = await fetch("/api/profile", {
            method: "POST",
          });

          if (!response.ok) {
            throw new Error("Save failed");
          }

          setStatus("success");
        } catch {
          setStatus("error");
        }
      }

      return (
        <section>
          <button
            onClick={handleSave}
            disabled={status === "loading"}
          >
            {status === "loading" ? "Збереження..." : "Зберегти"}
          </button>

          {status === "success" && (
            <p role="status">Профіль оновлено.</p>
          )}

          {status === "error" && (
            <p role="alert">Не вдалося оновити профіль.</p>
          )}
        </section>
      );
    }

Це демонстраційний приклад. У реальному застосунку потрібно передавати фактичні дані профілю, визначити контракт API та обробити відповідь відповідно до логіки проєкту.

### 14.2. Окрема сторінка результату

Для великих сценаріїв, наприклад оформлення замовлення, може бути окрема сторінка:

    src/
    └── app/
        └── checkout/
            └── success/
                └── page.tsx

Приклад:

    export default function CheckoutSuccessPage() {
      return (
        <main>
          <h1>Замовлення оформлено!</h1>
          <p>
            Дякуємо за покупку.
          </p>
          <a href="/orders">
            Переглянути замовлення
          </a>
        </main>
      );
    }

Це лише приклад інтерфейсу. У реальному застосунку сторінка повинна показувати підтверджений результат конкретного замовлення, а не вважати будь-який перехід на цей маршрут доказом успішної оплати.

### 14.3. Коли використовувати локальний Success State, а коли окрему сторінку?

| Ситуація | Рішення |
|---|---|
| Збереження налаштувань | Локальне повідомлення або Toast |
| Копіювання тексту | Короткий Toast |
| Зміна стану кнопки | Success State кнопки |
| Надсилання короткої форми | Повідомлення на сторінці |
| Оформлення замовлення | Окрема сторінка результату |
| Завершення складного процесу | Success Screen із наступними діями |

Не потрібно створювати окрему сторінку для кожної дрібної операції.

## 15. Success States у дизайн-системі

У дизайн-системі варто стандартизувати компоненти успішного завершення.

### Можливі компоненти

- `SuccessMessage` — повідомлення про успіх;
- `SuccessToast` — коротке сповіщення;

    :root {

Ці значення наведено як навчальний приклад. У реальній дизайн-системі потрібно враховувати палітру бренду, контрастність і узгодженість із компонентами помилок та попереджень.

- кольори;

- поведінку кнопок після успіху;

Стандартизація допомагає створювати передбачуваний інтерфейс у різних частинах застосунку.

## 16. Типові помилки в дизайні Success States

### Помилка 1. Успіх показується до завершення операції

Інтерфейс одразу повідомляє, що дані збережено, хоча запит ще виконується.

**Як правильно:** показувати Loading State, а успіх підтверджувати після завершення операції або використовувати оптимістичне оновлення з передбаченим відновленням у разі невдачі.

### Помилка 2. Надто загальне повідомлення

Погано:

    Готово!

Краще:

    Налаштування збережено.

### Помилка 3. Надмірні сповіщення

Кожна маленька дія супроводжується великим Toast.

**Як правильно:** показувати повідомлення лише тоді, коли воно додає користувачеві корисну інформацію.

### Помилка 4. Toast зникає надто швидко

Користувач не встигає прочитати повідомлення.

**Як правильно:** враховувати довжину тексту, важливість інформації та доступність.

### Помилка 5. Успіх позначається лише кольором

Кнопка стає зеленою, але немає тексту або іншого сигналу.

**Як правильно:** додавати зрозуміле текстове підтвердження або доступний статус.

### Помилка 6. Немає наступного кроку

Після важливої операції користувач не розуміє, куди рухатися далі.

**Як правильно:** пропонувати доречну дію, якщо вона потрібна.

### Помилка 7. Success State не відповідає реальному результату

Інтерфейс показує «Файл завантажено», хоча файл лише вибрано у файловому діалозі.

**Як правильно:** чітко розрізняти вибір файлу, початок завантаження та успішне завершення.

### Помилка 8. Підтвердження дублюються

Одночасно з'являються Toast, повідомлення під кнопкою й окреме модальне вікно для однієї простої дії.

**Як правильно:** обрати один основний спосіб підтвердження, якщо немає причини використовувати кілька.

### Помилка 9. Кнопка залишається у стані успіху без зрозумілої логіки

Користувач не розуміє, чи може повторити дію.

**Як правильно:** визначити, чи стан є тимчасовим підтвердженням, чи постійним відображенням нового стану системи.

### Помилка 10. Немає доступного повідомлення

Візуально з'являється галочка, але скринридер не повідомляє про успіх.

**Як правильно:** використовувати відповідне статусне повідомлення та перевіряти поведінку допоміжних технологій.

## 17. Як тестувати Success States

Потрібно перевіряти не лише вигляд повідомлення, а й те, чи відповідає воно реальному результату операції.

### Сценарії тестування

1. Операція завершується успішно.
2. Операція завершується помилкою.
3. Операція триває довше, ніж очікувалося.
4. Користувач повторно натискає кнопку.
5. Сервер повертає успішний HTTP-статус.
6. Сервер повертає HTTP-помилку.
7. Відповідь успішна, але не містить JSON.
8. Toast з'являється та зникає відповідно до правил.
9. Повідомлення читається на мобільному екрані.
10. Статус доступний для скринридера.
11. Користувач може продовжити роботу після завершення.
12. Важливі деталі результату залишаються доступними.
13. У разі помилки інтерфейс не показує хибного підтвердження.
14. Після оновлення сторінки результат не сприймається як успішний без підтвердження.

### Що перевіряти в DevTools?

У вкладці Network:
- чи завершився запит;
- який HTTP-статус повернув сервер;
- чи відповідає результат очікуванням;
- чи не виконується одна операція кілька разів.

У Console:
- чи немає помилок JavaScript;
- чи немає необроблених відхилень Promise;
- чи коректно обробляється результат запиту.

У самому інтерфейсі:
- чи з'являється повідомлення в правильний момент;
- чи зрозумілий його текст;
- чи не зникає воно занадто швидко;
- чи можна продовжити роботу.

## 18. Практичний мініпроєкт: Success State для збереження профілю

### Завдання

Створити кнопку збереження профілю, яка:
- показує Loading State;
- підтверджує успіх;
- показує Error State у разі невдачі;
- не дозволяє випадково запустити ту саму операцію повторно під час очікування.

### Модель стану

    const [status, setStatus] = useState("idle");

Можливі значення:

    "idle"
    "loading"
    "success"
    "error"

### Логіка

    async function saveProfile() {
      setStatus("loading");

      try {
        await updateProfile();
        setStatus("success");
      } catch {
        setStatus("error");
      }
    }

`updateProfile()` — умовна функція, яку потрібно реалізувати окремо.

### Відображення

    {status === "loading" && (
      <p role="status">Збереження...</p>
    )}

    {status === "success" && (
      <p role="status">Профіль успішно оновлено.</p>
    )}

    {status === "error" && (
      <p role="alert">Не вдалося зберегти профіль.</p>
    )}

### Що потрібно перевірити?

- Success State з'являється лише після успішного завершення.
- Loading State показується під час операції.
- Помилка не маскується повідомленням про успіх.
- Користувач розуміє, що відбулося.
- Кнопка має передбачувану поведінку після завершення.
- Статус доступний для допоміжних технологій.

## 19. Практичний мініпроєкт: Success Screen для замовлення

### Завдання

Створити сторінку, яка показує результат успішного оформлення замовлення.

### Структура сторінки

    ┌──────────────────────────────────┐
    │                                  │
    │                 ✓                │
    │                                  │
    │       Замовлення оформлено!      │
    │                                  │
    │       Номер: #1024               │
    │       Сума: 1 250 грн             │
    │                                  │
    │   [ Переглянути замовлення ]     │
    │   [ Продовжити покупки ]         │
    │                                  │
    └──────────────────────────────────┘

### Що потрібно реалізувати?

- заголовок успішного завершення;
- короткий текст;
- підтверджений номер замовлення;
- суму, якщо вона доступна;
- кнопку переходу до замовлення;
- кнопку повернення до каталогу.

### Що потрібно перевірити?

- сторінка відображається лише після підтвердження результату;
- дані замовлення відповідають реальній операції;
- користувач може перейти до наступного кроку;
- сторінка доступна на мобільному екрані;
- повідомлення зрозуміле без додаткових пояснень.

Не слід вважати сам факт переходу на URL сторінки успіху доказом того, що замовлення або оплата справді завершилися. Результат має підтверджуватися системою.

## 20. Що потрібно пам'ятати

✔ Success State підтверджує, що операція успішно завершилася.

✔ Підтвердження має відповідати реальному результату.

✔ Для невеликих дій часто достатньо Inline Success або Toast.

✔ Для важливих операцій доречний окремий Success Screen.

✔ Повідомлення має бути коротким і конкретним.

✔ За потреби потрібно пропонувати наступний крок.

✔ Не варто показувати успіх до підтвердження операції, якщо не використовується продумане оптимістичне оновлення.

✔ Toast не повинен зникати надто швидко.

✔ Не кожна дія потребує окремого повідомлення.

✔ Зміна самого компонента іноді достатня для підтвердження результату.

✔ `role="status"` підходить для багатьох повідомлень про успішне завершення.

✔ Колір та іконка мають доповнювати текст, а не замінювати його.

✔ Після успіху інтерфейс повинен залишатися передбачуваним.

✔ Для оплати, замовлень та інших важливих операцій потрібно показувати лише підтверджений результат.

✔ Success State має працювати разом із Loading та Error States.

## 21. Типові питання на співбесіді

### 1. Що таке Success State?

Це стан інтерфейсу, який повідомляє, що дія завершилася успішно або система отримала очікуваний результат.

### 2. Чим Toast відрізняється від Success Screen?

Toast — коротке сповіщення, яке не потребує окремої сторінки. Success Screen — окремий екран або великий блок для важливого результату та наступних дій.

### 3. Коли потрібно показувати Success State?

Після того, як система підтвердила успішне виконання операції або коли результат достовірно відомий.

### 4. Чи потрібно показувати Toast після кожної дії?

Ні. Якщо зміна компонента вже очевидно підтверджує результат, додаткове сповіщення може бути зайвим.

### 5. Для чого потрібен `role="status"`?

Він допомагає допоміжним технологіям повідомляти про зміну статусу без обов'язкового негайного переривання поточної роботи.

### 6. Чому не можна показувати успіх до відповіді сервера?

Тому що операція ще може завершитися помилкою. Передчасне підтвердження створює хибне враження про результат.

### 7. Що таке оптимістичне оновлення?

Це підхід, коли інтерфейс тимчасово відображає очікуваний результат до остаточної відповіді сервера. У разі невдачі потрібно передбачити відновлення стану або інший зрозумілий зворотний зв'язок.

### 8. Чи потрібна галочка в кожному Success State?

Ні. Іконка може допомогти, але головне — зрозумілий текст і відповідність результату дії.

### 9. Як відрізнити тимчасовий Success State від постійного?

Тимчасовий стан підтверджує завершення конкретної дії. Постійний відображає новий стан системи, наприклад «Ви підписані».

### 10. Як перевірити правильність Success State?

Переконатися, що повідомлення з'являється лише для успішного результату, відповідає реальним даним і доступне всім користувачам.

## 22. План вивчення за рівнями

### Core — базовий рівень

- Розуміти призначення Success States.
- Розрізняти Inline Success, Toast і Success Screen.
- Створювати прості повідомлення про успіх.
- Розуміти зв'язок між Loading, Success та Error.
- Використовувати зрозумілі тексти підтвердження.
- Не покладатися лише на зелений колір.

### Junior — практичний рівень

- Реалізовувати Success State через React `useState`.
- Обробляти результати запитів через `async/await`.
- Перевіряти успішність HTTP-відповідей.
- Створювати Toast та Inline Success.
- Використовувати `role="status"`.
- Розрізняти тимчасові підтвердження та постійні стани.
- Тестувати успішні й невдалі сценарії.

### Middle — системний рівень

- Створювати повторно використовувані Success-компоненти.
- Проєктувати стани для складних процесів.
- Узгоджувати Success State з API та бізнес-логікою.
- Враховувати доступність Toast і повідомлень.
- Розробляти Success Screen для важливих операцій.
- Запобігати дублюванню сповіщень.
- Стандартизувати успішні стани в дизайн-системі.

### Senior — архітектурний рівень

- Проєктувати послідовну модель станів для всього застосунку.
- Узгоджувати UX із фактичними результатами серверних операцій.
- Проєктувати оптимістичне оновлення та відновлення після помилок.
- Визначати, де достатньо локального підтвердження, а де потрібен окремий екран.
- Стандартизувати поведінку повідомлень у дизайн-системі.
- Враховувати доступність, продуктивність і надійність критичних сценаріїв.
- Забезпечувати узгоджений досвід для складних операцій.

## 24. Головна думка

**Хороший Success State не просто показує галочку — він підтверджує реальний результат, зберігає контекст і допомагає користувачеві зрозуміти, що робити далі.**

Під час проєктування потрібно відповісти на п'ять запитань:

1. Яку саме дію виконано успішно?
2. Чи підтверджений результат системою?
3. Який спосіб повідомлення найкраще підходить для цієї дії?
4. Чи потрібно користувачеві виконати наступний крок?
5. Чи залишається підтвердження зрозумілим і доступним?

Якщо ці питання вирішені, Success State стає повноцінною частиною UX, а не просто декоративною галочкою.
