# 07. Tables — Таблиці в інтерфейсі

> **Tables** — це компоненти інтерфейсу, які організовують дані у вигляді рядків і стовпців, допомагаючи користувачеві переглядати, порівнювати, шукати та аналізувати структуровану інформацію.

Таблиці особливо корисні в адміністративних панелях, CRM-системах, інтернет-магазинах, освітніх платформах, фінансових сервісах і системах керування даними.

---

## 1. Для чого потрібні таблиці

Таблиці допомагають представляти велику кількість однотипних даних у компактному й передбачуваному форматі.

Наприклад, в освітній платформі таблиця може містити:

    Ім'я             Клас       Оцінка      Статус
    ------------------------------------------------
    Олена Коваленко  8-А        10          Виконано
    Іван Петренко    8-Б        8           На перевірці
    Марія Шевченко   8-А        12          Виконано

Користувач може швидко:
- знайти потрібний запис;
- порівняти значення;
- визначити статус;
- відсортувати дані;
- переглянути деталі;
- виконати дію над конкретним рядком.

### Основні завдання таблиць

✔ Організація структурованих даних.

✔ Порівняння однотипних значень.

✔ Швидке сканування інформації.

✔ Пошук потрібних записів.

✔ Сортування та фільтрація.

✔ Виконання дій над окремими записами.

**Головний принцип:** таблиця повинна допомагати знаходити й розуміти дані, а не ускладнювати їх перегляд.

---

## 2. Основні частини таблиці

Типова таблиця складається з кількох основних елементів.

### 2.1. Table Header — заголовок таблиці

Заголовок визначає, яку інформацію містить кожен стовпець.

    Ім'я             Email                    Статус
    --------------------------------------------------
    Олена            olena@example.com        Активний
    Іван             ivan@example.com         Неактивний

Заголовки мають бути:
- короткими;
- зрозумілими;
- однозначними;
- послідовними за стилем.

Невдало:

    Name     Data 1     Info

Краще:

    Користувач   Дата реєстрації   Статус

Не використовуй незрозумілі скорочення, якщо користувач не знає їхнього значення.

### 2.2. Table Row — рядок

Рядок представляє один запис або одну сутність.

Наприклад, у таблиці користувачів кожен рядок відповідає одному користувачеві.

    ID    Ім'я             Роль
    -----------------------------
    1     Олена            Адміністратор
    2     Іван             Редактор
    3     Марія            Користувач

У межах одного рядка зазвичай розміщуються дані, які належать до одного об'єкта.

### 2.3. Table Cell — комірка

Комірка — це окрема область на перетині рядка та стовпця.

Комірка може містити:
- текст;
- число;
- дату;
- іконку;
- зображення;
- статус;
- посилання;
- кнопку;
- чекбокс.

Приклад:

    | Ім'я  | Статус   | Дія       |
    |-------|----------|-----------|
    | Олена | Активний | Перегляд  |

Не варто перевантажувати комірку багатьма незалежними елементами.

### 2.4. Table Footer — нижня частина таблиці

Footer може містити:
- підсумкові значення;
- загальну кількість записів;
- інформацію про вибрані рядки;
- навігацію між сторінками;
- додаткові дії.

Приклад:

    Усього користувачів: 128

У простих таблицях footer може бути відсутнім.

### 2.5. Caption — назва таблиці

Назва пояснює призначення таблиці.

Приклад:

    Список учнів 8-А класу

Вона особливо корисна, коли на сторінці розташовано кілька таблиць.

---

## 3. Типи таблиць

### 3.1. Data Table — таблиця даних

Використовується для відображення структурованої інформації.

Приклади:
- список користувачів;
- перелік товарів;
- список учнів;
- історія замовлень;
- журнал оцінок.

Типові можливості:
- сортування;
- пошук;
- фільтрація;
- пагінація;
- вибір рядків.

### 3.2. Comparison Table — порівняльна таблиця

Допомагає порівнювати характеристики кількох об'єктів.

Наприклад:

    Характеристика    Basic       Pro
    -------------------------------------
    Користувачі       1           10
    Сховище           5 GB        100 GB
    Підтримка         Email       Пріоритетна

Використовується для:
- порівняння тарифів;
- вибору продуктів;
- зіставлення характеристик;
- порівняння функцій.

Головне — забезпечити однакову структуру порівнюваних даних.

### 3.3. Financial Table — фінансова таблиця

Містить числові значення, суми, витрати, доходи або платежі.

Приклад:

    Дата          Опис             Сума
    --------------------------------------
    12.10.2026    Оплата            500 грн
    13.10.2026    Повернення        100 грн

Важливо:
- вирівнювати числові значення послідовно;
- використовувати зрозумілі формати дат;
- не змішувати різні одиниці вимірювання;
- чітко позначати валюту;
- відрізняти доходи від витрат.

### 3.4. Action Table — таблиця з діями

Окрім даних, кожен рядок може містити кнопки для роботи із записом.

Приклад:

    Ім'я      Роль          Дії
    --------------------------------
    Олена     Адміністратор [Переглянути] [Редагувати]
    Іван      Редактор      [Переглянути] [Редагувати]

Можливі дії:
- переглянути;
- редагувати;
- видалити;
- відкрити деталі;
- змінити статус.

Не розміщуй забагато кнопок у кожному рядку. Рідкісні або другорядні дії можна винести в меню.

### 3.5. Hierarchical Table — ієрархічна таблиця

Відображає дані з вкладеною структурою.

Приклади:
- дерево категорій;
- організаційна структура;
- папки та файли;
- групи й підгрупи;
- вкладені записи.

Для таких таблиць важливо візуально показувати зв'язки між рівнями.

---

## 4. Візуальна ієрархія таблиці

Таблиця може містити десятки або сотні записів. Тому користувач повинен швидко розуміти її структуру.

### 4.1. Заголовки мають відрізнятися від даних

Заголовки можна виділити за допомогою:
- більшої насиченості шрифту;
- фонового кольору;
- нижньої межі;
- достатніх відступів;
- фіксованого розташування.

Приклад CSS:

    .table th {
      font-weight: 600;
      text-align: left;
      padding: 12px 16px;
      background-color: #f8fafc;
      border-bottom: 1px solid #e2e8f0;
    }

### 4.2. Використовуй достатні відступи

Занадто щільна таблиця ускладнює читання.

    .table td {
      padding: 12px 16px;
    }

Для таблиць із великою кількістю рядків можна використовувати компактніші відступи, але не жертвувати читабельністю.

### 4.3. Розділення рядків

Для відокремлення рядків використовують:
- горизонтальні межі;
- чергування кольорів фону;
- відступи;
- виділення при наведенні.

Не потрібно одночасно використовувати всі засоби, якщо таблиця вже добре читається.

### 4.4. Zebra Stripes — чергування фону

Кожен другий рядок отримує трохи інший фон.

Приклад CSS:

    .table tbody tr:nth-child(even) {
      background-color: #f8fafc;
    }

Це може полегшити відстеження рядків у широких таблицях.

Проте для невеликих таблиць із чіткими межами чергування кольорів може бути зайвим.

### 4.5. Hover State — стан наведення

Під час наведення курсора рядок може змінювати фон.

    .table tbody tr:hover {
      background-color: #f1f5f9;
    }

Це допомагає зрозуміти, з яким рядком взаємодіє користувач.

Hover не повинен бути єдиним способом показу важливої інформації, адже на сенсорних пристроях наведення відсутнє.

---

## 5. Вирівнювання даних

Правильне вирівнювання полегшує сканування таблиці.

### 5.1. Текстові значення

Зазвичай текст вирівнюють ліворуч.

    Ім'я
    ----------------
    Олена Коваленко
    Іван Петренко

Це зручно для читання слів і речень.

### 5.2. Числові значення

Числа часто вирівнюють праворуч, особливо якщо їх потрібно порівнювати.

    Кількість
    ----------
           8
          12
         105

Так легше порівнювати розряди чисел.

### 5.3. Грошові значення

Суми варто вирівнювати послідовно, щоб користувач міг швидко порівнювати їх.

Приклад CSS:

    .table .numeric {
      text-align: right;
      font-variant-numeric: tabular-nums;
    }

`font-variant-numeric: tabular-nums` допомагає використовувати цифри однакової ширини у шрифтах, які це підтримують.

### 5.4. Дати

Дати повинні мати послідовний формат.

Невдало:

    12.10.2026
    October 13, 2026
    2026/10/14

Краще обрати єдиний формат відповідно до мови та потреб користувачів.

### 5.5. Кнопки та іконки

Елементи керування повинні розташовуватися послідовно в усіх рядках.

Наприклад, колонка «Дії» може мати фіксовану ширину, щоб кнопки не змінювали положення залежно від довжини тексту.

---

## 6. Ширина стовпців і довгий текст

Не всі стовпці потребують однакової ширини.

Приклад:

    Ім'я          Email                    Статус
    -------------------------------------------------
    Олена         olena@example.com        Активний

Рекомендації:
- імена мають отримувати достатньо простору;
- довгі описи не повинні руйнувати структуру;
- короткі значення не потребують надмірної ширини;
- колонка з діями має залишатися передбачуваною;
- важливі дані не варто обрізати без можливості перегляду.

### 6.1. Перенесення тексту

Для довгих описів можна дозволити перенесення рядків.

    .table td {
      overflow-wrap: anywhere;
    }

Це особливо корисно для довгих email-адрес, ідентифікаторів або посилань.

### 6.2. Обрізання тексту

Для таблиць із фіксованою шириною можна використовувати трикрапку.

    .table__description {
      overflow: hidden;
      white-space: nowrap;
      text-overflow: ellipsis;
      max-width: 240px;
    }

Обрізання доречне, якщо:
- повний текст не є необхідним для швидкого перегляду;
- користувач може відкрити деталі;
- існує доступний спосіб переглянути повне значення.

Не обрізай важливі дані без альтернативного способу їх прочитати.

## 7. Сортування (Sorting)

Сортування дозволяє змінювати порядок рядків за значеннями вибраного стовпця.

Наприклад:
- за ім'ям;
- за датою;
- за ціною;
- за кількістю;
- за статусом.

Типові напрямки:
- за зростанням;
- за спаданням.

Приклад:

    Дата ↑

Стрілка може показувати напрямок сортування, але потрібно також забезпечити доступне текстове пояснення.

### UX-принципи сортування

✔ Показуй, який стовпець використовується для сортування.

✔ Візуально позначай напрямок.

✔ Зберігай передбачувану поведінку при повторному натисканні.

✔ Для чисел використовуй числове, а не текстове сортування.

✔ Для дат враховуй реальні значення дат.

✔ За потреби підтримуй сортування клавіатурою.

Не всі стовпці мають бути сортувальними. Сортування за колонкою «Дії» зазвичай не має сенсу.

---

## 8. Фільтрація (Filtering)

Фільтрація залишає в таблиці лише записи, які відповідають заданим умовам.

Приклад:

    Статус: [Усі ▼]

Можливі фільтри:
- статус;
- дата;
- категорія;
- роль;
- діапазон цін;
- тип запису.

### Рекомендації

- показуй активні фільтри;
- дозволяй зрозуміло очистити фільтрацію;
- пояснюй, якщо результатів немає;
- не приховуй застосовані умови;
- поєднуй фільтри послідовно й передбачувано.

Приклад активних фільтрів:

    Статус: Активний  ×
    Роль: Редактор    ×
    [Очистити фільтри]

### Empty State після фільтрації

Якщо відповідних записів немає:

    За вибраними фільтрами нічого не знайдено.

    Спробуйте змінити умови пошуку.

Це не обов'язково означає, що в таблиці взагалі немає даних. Порожній результат може бути наслідком активних фільтрів.

---

## 9. Пошук у таблиці

Пошук дозволяє знайти конкретний запис за текстовим запитом.

Приклад:

    [🔍 Пошук за ім'ям або email...]

Пошук може охоплювати:
- ім'я;
- email;
- назву;
- ідентифікатор;
- номер замовлення.

### Хороший пошук

✔ Має зрозумілий placeholder.

✔ Пояснює, за якими полями виконується пошук.

✔ Не вимагає від користувача знання внутрішніх ідентифікаторів, якщо це не потрібно.

✔ Передбачає повідомлення про відсутність результатів.

✔ Дозволяє очистити запит.

Для великих наборів даних пошук може виконуватися на сервері, а не лише в браузері.

---

## 10. Пагінація (Pagination)

Пагінація розділяє велику кількість записів на сторінки.

Приклад:

    Показано 1–10 із 128 записів

    [Попередня]  1  2  3  ...  13  [Наступна]

Переваги:
- зменшує кількість одночасно відображених рядків;
- допомагає працювати з великими наборами даних;
- обмежує обсяг даних, який потрібно завантажити за один раз.

### Основні елементи

- поточна сторінка;
- перехід до попередньої сторінки;
- перехід до наступної сторінки;
- вибір кількості рядків;
- загальна кількість записів.

### Page Size — кількість рядків на сторінці

Приклад:

    Рядків на сторінці: [10 ▼]

Можливі значення:
- 10;
- 25;
- 50;
- 100.

Значення залежать від типу даних і сценарію використання.

### UX-принципи пагінації

✔ Чітко позначай поточну сторінку.

✔ Не дозволяй перейти на неіснуючу сторінку.

✔ Відображай загальну кількість записів, якщо вона відома.

✔ Продумай, що відбувається після застосування фільтра.

✔ Зберігай пошук і фільтри під час переходу між сторінками, якщо це відповідає сценарію.

Для деяких сценаріїв замість пагінації доречне поступове завантаження даних.

## 11. Sticky Header — закріплений заголовок

Sticky Header залишається видимим під час прокручування довгої таблиці.

Приклад CSS:

    .table thead th {
      position: sticky;
      top: 0;
      background-color: #f8fafc;
      z-index: 1;
    }

Переваги:
- користувач не забуває значення стовпців;
- легше читати великі таблиці;
- зручніше порівнювати віддалені рядки.

Важливо:
- забезпечити непрозорий фон заголовка;
- перевірити, чи не перекривається він іншими елементами;
- врахувати висоту фіксованої панелі навігації;
- перевірити роботу на малих екранах.

Sticky Header особливо корисний для довгих таблиць із багатьма рядками.

---

## 12. Sticky Column — закріплений стовпець

У широкій таблиці перший стовпець може залишатися на місці під час горизонтального прокручування.

Це корисно, коли перший стовпець містить:
- ім'я;
- назву товару;
- номер запису;
- ідентифікатор.

Приклад CSS:

    .table th:first-child,
    .table td:first-child {
      position: sticky;
      left: 0;
      background-color: #ffffff;
    }

Важливо:
- використовувати непрозорий фон;
- перевірити накладання на сусідні комірки;
- забезпечити правильний `z-index`;
- протестувати горизонтальне прокручування.

Не закріплюй багато стовпців без потреби: це зменшує простір для решти даних.

---

## 13. Вибір рядків (Row Selection)

Таблиця може дозволяти вибирати один або кілька рядків.

Приклад:

    [ ] Ім'я          Статус
    [ ] Олена         Активний
    [ ] Іван          Неактивний
    [ ] Марія         Активний

Вибрані записи можуть використовуватися для:
- групового видалення;
- експорту;
- зміни статусу;
- призначення категорії;
- масового редагування.

### Select All — вибрати всі

Чекбокс у заголовку може вибирати всі записи, які відповідають визначеному контексту.

Важливо чітко розрізняти:
- вибір усіх рядків на поточній сторінці;
- вибір усіх записів у результатах пошуку;
- вибір усіх записів у системі.

Це різні дії, і користувач має розуміти, які записи будуть змінені.

### Bulk Actions — групові дії

Після вибору рядків можна показати панель дій.

    Вибрано: 3

    [Змінити статус] [Експортувати] [Видалити]

Показуй кількість вибраних записів і чітко пояснюй дію, особливо якщо вона незворотна.

## 14. Статуси в таблицях

Статуси допомагають швидко оцінити стан запису.

Приклади:
- Активний;
- Неактивний;
- Очікує;
- Виконано;
- Скасовано;
- На перевірці.

Для статусів часто використовують Badge — компактну кольорову мітку.

Приклад HTML:

    <span class="status status--active">
      Активний
    </span>

    <span class="status status--pending">
      Очікує
    </span>

Приклад CSS:

    .status {
      display: inline-flex;
      align-items: center;
      padding: 4px 8px;
      border-radius: 999px;
      font-size: 0.875rem;
      font-weight: 500;
    }

    .status--active {
      color: #166534;
      background-color: #dcfce7;
    }

    .status--pending {
      color: #854d0e;
      background-color: #fef3c7;
    }

### Принципи дизайну статусів

✔ Використовуй зрозумілі текстові назви.

✔ Зберігай однакове значення кольорів у всьому продукті.

✔ Перевіряй контраст тексту й фону.

✔ Не покладайся лише на колір.

✔ Не створюй надто багато схожих кольорових міток.

Статус має бути зрозумілим навіть тоді, коли користувач не розрізняє кольори.

## 15. Дії в таблицях

Дії дозволяють працювати із записом без переходу на іншу сторінку.

Приклади:
- переглянути;
- редагувати;
- видалити;
- відкрити меню;
- змінити статус.

### Основна та другорядна дія

Не всі дії однаково важливі.

Наприклад:

    Ім'я       Статус       Дії
    ----------------------------------------
    Олена      Активний     [Редагувати] [⋯]

Кнопка «Редагувати» може бути основною дією, а меню `⋯` — містити додаткові операції.

### Іконки замість тексту

Іконки можуть заощадити простір, але їхнє значення не завжди очевидне.

Якщо використовується кнопка з іконкою, передбач:
- доступну назву для скринрідера;
- підказку за потреби;
- достатню область натискання;
- видимий стан фокуса.

### Небезпечні дії

Видалення або інша критична операція потребує особливої уваги.

Перед видаленням важливого запису можна показати діалог підтвердження.

Не варто робити небезпечну дію основною кнопкою, якщо користувачі можуть натиснути її випадково.

## 16. Empty State — порожня таблиця

Порожній стан з'являється, коли таблиця не має записів для показу.

Приклад:

    Записів поки немає.

    Створіть перший запис, щоб він з'явився в таблиці.

    [Створити запис]

Порожній стан повинен пояснювати:
- чому даних немає, якщо це відомо;
- що користувач може зробити далі;
- чи потрібно створити перший запис;
- чи активні фільтри або пошук.

### Розрізняй різні ситуації

**Немає даних:**

    Ви ще не створили жодного запису.

**Немає результатів пошуку:**

    За вашим запитом нічого не знайдено.

**Немає результатів через фільтри:**

    Записів із такими параметрами немає.

Ці ситуації потребують різних пояснень і, можливо, різних дій.

---

## 17. Loading State — завантаження таблиці

Під час отримання даних із сервера таблиця може тимчасово не мати готових записів.

Можливі варіанти:
- індикатор завантаження;
- Skeleton Rows;
- повідомлення про завантаження;
- часткове відображення вже отриманих даних.

Приклад:

    Завантаження даних...

### Skeleton Rows

Skeleton Rows — це тимчасові блоки, які імітують структуру майбутніх рядків.

Вони допомагають зберегти приблизне компонування сторінки під час завантаження.

Використовуй їх, якщо:
- завантаження помітне за тривалістю;
- структура таблиці передбачувана;
- важливо уникнути різких стрибків компонування.

Не показуй порожній стан «Записів немає», якщо дані ще не завантажені.

---

## 18. Error State — помилка завантаження

Якщо таблицю не вдалося завантажити, користувач має отримати зрозуміле пояснення.

Приклад:

    Не вдалося завантажити дані.

    Перевірте з'єднання та спробуйте ще раз.

    [Повторити]

Важливо:
- не залишати таблицю в незрозумілому порожньому стані;
- не показувати вигадані дані;
- пояснювати, чи можна повторити операцію;
- зберігати пошук і фільтри, якщо це можливо;
- не розкривати користувачеві внутрішні технічні повідомлення сервера.

Помилка завантаження не означає, що записів немає.

## 19. Responsive Tables — адаптивні таблиці

На великих екранах таблиці можуть відображати багато стовпців одночасно. На мобільних пристроях це часто стає проблемою.

Основні підходи:
- горизонтальне прокручування;
- приховування другорядних стовпців;
- скорочення вмісту;
- перетворення рядків на картки;
- показ деталей за запитом.

### 19.1. Горизонтальне прокручування

Зручно, коли важливо зберегти структуру рядків і стовпців.

    .table-wrapper {
      width: 100%;
      overflow-x: auto;
    }

Перевага — структура таблиці не змінюється.

Недолік — користувачеві потрібно прокручувати таблицю горизонтально.

Використовуй цей підхід, коли порівняння даних по стовпцях є важливим.

### 19.2. Приховування другорядних стовпців

На вузькому екрані можна приховувати менш важливі поля.

Приклад CSS:

    @media (max-width: 640px) {
      .table .column-secondary {
        display: none;
      }
    }

Цей підхід підходить лише тоді, коли приховані дані не потрібні для основного сценарію.

Якщо інформація важлива, передбач інший спосіб її перегляду.

### 19.3. Перетворення рядків на картки

Для мобільних пристроїв іноді краще показувати кожен запис як окрему картку.

    Олена Коваленко

    Email: olena@example.com
    Статус: Активний

    [Переглянути]

Картки можуть бути зручнішими для перегляду окремих записів, але гіршими для порівняння багатьох значень між собою.

**Вибирай адаптивний підхід відповідно до завдання користувача, а не лише до ширини екрана.**

## 20. Accessibility — доступність таблиць

Таблиця повинна бути зрозумілою для користувачів, які використовують клавіатуру, скринрідери та інші допоміжні технології.

### Основні правила

✔ Використовуй семантичні HTML-елементи.

✔ Додавай заголовки стовпців.

✔ За потреби використовуй назву таблиці.

✔ Забезпечуй видимий фокус для інтерактивних елементів.

✔ Не використовуй колір як єдиний спосіб передачі інформації.

✔ Перевіряй читабельність на малих екранах.

✔ Не перетворюй таблицю на набір довільних `div`, якщо потрібна таблична семантика.

### Семантичні елементи HTML

- `<table>` — таблиця;
- `<caption>` — назва таблиці;
- `<thead>` — заголовкова частина;
- `<tbody>` — основні рядки;
- `<tfoot>` — підсумкова частина;
- `<tr>` — рядок;
- `<th>` — заголовкова комірка;
- `<td>` — звичайна комірка.

### Приклад доступної таблиці

    <table>
      <caption>Список учнів</caption>

      <thead>
        <tr>
          <th scope="col">Ім'я</th>
          <th scope="col">Клас</th>
          <th scope="col">Оцінка</th>
        </tr>
      </thead>

      <tbody>
        <tr>
          <td>Олена Коваленко</td>
          <td>8-А</td>
          <td>10</td>
        </tr>

        <tr>
          <td>Іван Петренко</td>
          <td>8-Б</td>
          <td>8</td>
        </tr>
      </tbody>
    </table>

`scope="col"` допомагає визначити, що заголовок стосується відповідного стовпця.

Для складних таблиць із багаторівневими заголовками можуть знадобитися додаткові атрибути, наприклад `scope="row"` або `headers`.

### Таблиця чи інтерактивна сітка?

Звичайна HTML-таблиця призначена насамперед для представлення даних.

Якщо інтерфейс має складну клавіатурну взаємодію, редагування комірок стрілками та поведінку, подібну до електронної таблиці, може знадобитися інший шаблон доступності, наприклад ARIA Grid.

Не додавай `role="grid"` лише заради стилізації: він передбачає іншу модель взаємодії з клавіатури.

## 21. Вибір між таблицею, списком і картками

Не кожні дані потрібно представляти таблицею.

| Формат | Коли доречний |
|---|---|
| Таблиця | Багато структурованих даних, порівняння за стовпцями |
| Список | Послідовність елементів із простим описом |
| Картки | Окремі об'єкти з описом, зображенням і діями |
| Графік | Аналіз тенденцій і числових залежностей |
| Детальна сторінка | Глибоке вивчення одного запису |

### Приклад

**Таблиця** добре підходить для порівняння цін, дат і статусів десятків замовлень.

**Картки** можуть бути кращими для перегляду курсів, де важливі зображення, описи та кнопки запису.

**Список** може бути кращим для короткої історії повідомлень.

Головне запитання:

**Чи потрібно користувачеві порівнювати значення між різними записами?**

Якщо так, таблиця часто буде доречним рішенням.

## 23. Типові помилки дизайну таблиць

### Помилка 1. Забагато стовпців

Проблема: таблицю важко читати, особливо на невеликому екрані.

Рішення:
- визнач пріоритетні дані;
- прибери дублікати;
- приховай другорядні поля лише за наявності альтернативи;
- передбач перегляд деталей.

### Помилка 2. Незрозумілі заголовки

Проблема: користувач не розуміє значення колонок.

Рішення: використовуй конкретні назви, наприклад «Дата реєстрації» замість «Дата».

### Помилка 3. Усі значення вирівняні однаково

Проблема: числові дані важче порівнювати.

Рішення: текст вирівнюй переважно ліворуч, числа — послідовно, часто праворуч.

### Помилка 4. Надто щільні рядки

Проблема: важко стежити за рядком, особливо в таблицях із багатьма записами.

Рішення: збільш відступи або використай делікатне чергування фону.

### Помилка 5. Усі дії показані одночасно

Проблема: рядки перевантажені кнопками.

Рішення: залиш основну дію, а другорядні перемісти в меню.

### Помилка 6. Немає Loading State

Проблема: користувач не знає, чи завантажуються дані.

Рішення: додай індикатор або скелетон.

### Помилка 7. Порожня таблиця без пояснення

Проблема: користувач не знає, чи немає даних, чи виникла помилка.

Рішення: розрізняй Empty, No Results і Error States.

### Помилка 8. Таблиця не працює на мобільному пристрої

Проблема: стовпці обрізаються або текст виходить за межі екрана.

Рішення: використовуй горизонтальне прокручування, адаптивні картки або інший продуманий варіант.

### Помилка 9. Статус передається лише кольором

Проблема: значення незрозуміле без сприйняття кольору.

Рішення: завжди додавай текстову назву статусу.

### Помилка 10. Відсутня доступність

Проблема: скринрідер не може правильно визначити структуру даних.

Рішення: використовуй семантичні елементи, заголовки комірок і доступні назви інтерактивних елементів.

## 28. Мінішпаргалка

**Table** — компонент для організації та порівняння структурованих даних.

**Основні частини:**
- Header — заголовки стовпців;
- Row — рядок;
- Cell — комірка;
- Footer — підсумкова частина;
- Caption — назва таблиці.

**Основні можливості:**
- Sorting — сортування;
- Filtering — фільтрація;
- Search — пошук;
- Pagination — розбиття на сторінки;
- Row Selection — вибір рядків;
- Bulk Actions — групові дії;
- Sticky Header — закріплений заголовок;
- Sticky Column — закріплений стовпець.

**Стани таблиці:**
- Default — дані відображено;
- Loading — дані завантажуються;
- Empty — записів немає;
- No Results — пошук або фільтри не дали результатів;
- Error — дані не вдалося завантажити;
- Selected — рядки вибрано.

**Принципи дизайну:**
- зрозумілі заголовки;
- послідовне вирівнювання;
- достатні відступи;
- чітка ієрархія;
- помірна кількість дій;
- адаптивність;
- доступність.

**Основні HTML-елементи:**

    <table>
      <caption>Назва таблиці</caption>
      <thead>
        <tr>
          <th scope="col">Заголовок</th>
        </tr>
      </thead>
      <tbody>
        <tr>
          <td>Дані</td>
        </tr>
      </tbody>
    </table>

## Висновок

Таблиці — один із найважливіших компонентів інтерфейсів, у яких користувачі працюють зі структурованими даними.

Якісна таблиця:
- допомагає швидко знаходити інформацію;
- полегшує порівняння значень;
- забезпечує передбачувану взаємодію;
- підтримує пошук, сортування та фільтрацію;
- зберігає читабельність на різних екранах;
- враховує доступність;
- узгоджується з іншими компонентами продукту.

Під час проєктування завжди запитуй себе:

**«Чи зможе користувач швидко знайти потрібний запис, зрозуміти його значення та виконати необхідну дію?»**
