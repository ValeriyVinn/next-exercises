# 04. Validation — Валідація форм

> **Validation (валідація)** — це перевірка даних, які користувач вводить у форму, щоб визначити, чи відповідають вони заданим правилам і чи можуть бути прийняті системою.

Валідація допомагає користувачеві правильно заповнити форму, виявляє помилки до або під час відправлення даних і захищає систему від некоректних значень.

Наприклад, якщо користувач вводить електронну адресу `user@`, форма повинна повідомити, що адреса має неправильний формат, і допомогти виправити її.

Важливо розуміти: **валідація — це не просто повідомлення про помилку, а система правил, станів і зворотного зв'язку, яка допомагає користувачеві успішно виконати дію.**

---

## 1. Для чого потрібна валідація?

Валідація потрібна, щоб:

- ✔ Перевіряти правильність введених даних.
- ✔ Виявляти пропущені обов'язкові поля.
- ✔ Перевіряти формат електронної пошти, телефону, дати та інших значень.
- ✔ Перевіряти мінімальну й максимальну довжину введення.
- ✔ Перевіряти діапазони числових значень.
- ✔ Перевіряти взаємозалежні поля.
- ✔ Пояснювати користувачеві, як виправити помилку.
- ✔ Зменшувати кількість невдалих спроб відправлення форми.
- ✔ Забезпечувати коректність даних перед їх обробкою системою.

Наприклад, форма реєстрації може перевіряти:

    Ім'я:
        Поле не повинно бути порожнім.

    Електронна пошта:
        Значення повинно мати прийнятний формат.

    Пароль:
        Повинен відповідати заданим вимогам.

    Підтвердження пароля:
        Повинно збігатися з паролем.

    Згода з умовами:
        Повинна бути надана, якщо це обов'язкова умова реєстрації.

Валідація не повинна лише блокувати користувача. Її завдання — допомогти йому зрозуміти вимоги та виправити дані.

---

## 2. Основні поняття

### 2.1. Validation rule — правило валідації

Validation rule — це умова, якій повинні відповідати введені дані.

Приклади правил:

- Поле обов'язкове.
- Електронна адреса повинна мати прийнятний формат.
- Пароль повинен містити щонайменше 12 символів.
- Вік повинен бути в межах допустимого діапазону.
- Дата завершення не може передувати даті початку.
- Підтвердження пароля повинно збігатися з паролем.

Правила залежать від призначення форми.

Не варто додавати обмеження, які не потрібні бізнес-логіці або не пояснені користувачеві.

### 2.2. Valid state — коректний стан

Поле містить значення, яке відповідає правилам валідації.

Наприклад:

    Label: Електронна пошта
    Value: user@example.com
    State: Valid

Зверни увагу: формально правильний формат ще не гарантує, що адреса існує або належить конкретному користувачеві.

### 2.3. Invalid state — некоректний стан

Значення не відповідає одному або кільком правилам.

Наприклад:

    Label: Електронна пошта
    Value: user@
    State: Invalid
    Error: Введіть коректну електронну адресу.

Користувач повинен розуміти не лише те, що сталася помилка, а й те, як її виправити.

### 2.4. Error message — повідомлення про помилку

Error message пояснює, що саме не так із введеними даними.

❌ Незрозуміло:

    Помилка!

✔ Краще:

    Введіть коректну електронну адресу.

Ще один приклад:

    Помилка: Паролі не збігаються.

Повідомлення повинно бути конкретним, коротким і зрозумілим.

### 2.5. Validation feedback — зворотний зв'язок

Validation feedback — це інформація, яку інтерфейс надає користувачеві після перевірки даних.

Зворотний зв'язок може включати:

- повідомлення про помилку;
- коротку підказку;
- індикатор виконання вимог;
- повідомлення про успішну перевірку;
- підсвічування проблемного поля;
- загальне повідомлення про помилки форми.

Візуального індикатора недостатньо, якщо користувач не розуміє причину проблеми.

### 2.6. Client-side validation — клієнтська валідація

Перевірка даних на стороні клієнта, зазвичай у браузері.

Вона дозволяє швидко повідомити користувачеві про помилки, не відправляючи кожне значення на сервер.

Приклади:

- HTML-атрибут `required`;
- перевірка `minlength` і `maxlength`;
- перевірка формату за допомогою `type="email"`;
- власна перевірка за допомогою JavaScript.

### 2.7. Server-side validation — серверна валідація

Перевірка даних на сервері перед їх обробкою або збереженням.

Вона обов'язкова, тому що клієнтську перевірку можна обійти.

Наприклад, користувач може відправити запит безпосередньо через інший інструмент, змінивши дані або обійшовши інтерфейс.

**Клієнтська валідація покращує користувацький досвід, а серверна забезпечує перевірку даних на довіреній стороні системи.**

## 3. Основні типи валідації

### 3.1. Required validation — перевірка обов'язкових полів

Перевіряє, чи заповнив користувач поле, яке не можна залишити порожнім.

    Label: Ім'я
    Value: ""
    Error: Введіть ім'я.

У HTML для цього можна використати атрибут `required`.

    <label for="name">Ім'я</label>

    <input
        id="name"
        name="name"
        type="text"
        required
    >

Але атрибут `required` не замінює серверної перевірки.

### 3.2. Format validation — перевірка формату

Перевіряє, чи має значення очікувану структуру.

Приклади:

- електронна пошта;
- дата;
- номер телефону;
- поштовий індекс;
- ідентифікатор певного формату.

    <label for="email">Електронна пошта</label>

    <input
        id="email"
        name="email"
        type="email"
        required
    >

Браузер може перевірити базовий формат електронної пошти, але не може самостійно підтвердити існування поштової скриньки.

### 3.3. Length validation — перевірка довжини

Перевіряє мінімальну або максимальну кількість символів.

Наприклад:

    Label: Назва курсу
    Rule: Від 3 до 100 символів.

У HTML:

    <label for="course">Назва курсу</label>

    <input
        id="course"
        name="course"
        type="text"
        minlength="3"
        maxlength="100"
        required
    >

Потрібно заздалегідь визначити, що саме рахує система: символи, кодові одиниці або іншу міру довжини. Для користувача вимогу варто формулювати просто.

### 3.4. Range validation — перевірка діапазону

Перевіряє, чи входить числове значення в допустимі межі.

    Label: Кількість учнів
    Minimum: 1
    Maximum: 35

У HTML:

    <label for="students">Кількість учнів</label>

    <input
        id="students"
        name="students"
        type="number"
        min="1"
        max="35"
        required
    >

Якщо значення поза діапазоном, повідомлення повинно пояснити допустимі межі.

### 3.5. Pattern validation — перевірка за шаблоном

Перевіряє, чи відповідає введення заданому шаблону.

Наприклад, поле може приймати лише код із певною кількістю цифр.

    <label for="code">Код доступу</label>

    <input
        id="code"
        name="code"
        type="text"
        pattern="[0-9]{6}"
        inputmode="numeric"
        required
        aria-describedby="code-hint"
    >

    <p id="code-hint">
        Введіть шість цифр.
    </p>

Атрибут `pattern` використовує регулярний вираз. У цьому прикладі очікуються шість цифр.

Не використовуй складні шаблони без реальної потреби. Формат повинен відповідати правилам системи, а користувач має розуміти, що від нього очікується.

### 3.6. Match validation — перевірка збігу полів

Перевіряє, чи відповідають одне одному два або більше значень.

Приклад:

    Пароль: ************
    Підтвердження пароля: **********

    Error: Паролі не збігаються.

Інші приклади:

- дата початку й дата завершення;
- новий пароль і його підтвердження;
- два поля, що повинні містити однаковий код.

Такі правила зазвичай потребують JavaScript або серверної логіки.

### 3.7. Business-rule validation — перевірка бізнес-правил

Перевіряє правила, що залежать від призначення продукту.

Приклади:

- користувач не може записатися на завершений курс;
- кількість місць не може перевищувати доступний ліміт;
- дата бронювання повинна відповідати правилам сервісу;
- обрана категорія повинна підтримувати зазначений тип операції.

Такі перевірки не можна зводити лише до формату поля.

### 3.8. Cross-field validation — перевірка взаємопов'язаних полів

Перевіряє умови, які залежать від кількох полів одночасно.

Наприклад:

    Дата початку: 20.10.2026
    Дата завершення: 15.10.2026

    Error:
    Дата завершення не може бути раніше дати початку.

Це не просто перевірка окремого поля. Система повинна порівняти значення обох дат.

## 4. Коли запускати валідацію?

Валідацію можна виконувати в різні моменти взаємодії.

### 4.1. On input — під час введення

Перевірка відбувається, коли користувач змінює значення поля.

Переваги:

- швидкий зворотний зв'язок;
- помилки можуть виявлятися раніше;
- корисно для складних вимог, наприклад до пароля.

Недоліки:

- надто ранні помилки можуть відволікати;
- поле може показувати помилку ще до того, як користувач закінчив введення;
- часті повідомлення можуть створювати враження, що форма постійно «лається» на користувача.

Рекомендація: не показуй помилку лише через те, що користувач ще не закінчив вводити значення.

### 4.2. On blur — після виходу з поля

Перевірка виконується, коли користувач переходить до іншого елемента.

Переваги:

- користувач отримує зворотний зв'язок після завершення введення;
- менше передчасних повідомлень;
- добре підходить для багатьох простих полів.

Недоліки:

- користувач може не помітити помилку, якщо повідомлення розміщене далеко від поля;
- деякі помилки можуть виявитися лише наприкінці заповнення форми.

### 4.3. On submit — під час відправлення форми

Перевірка відбувається, коли користувач натискає кнопку відправлення.

Переваги:

- користувач може спочатку заповнити всю форму;
- підходить для загальної перевірки всіх полів;
- дозволяє показати повний список помилок.

Недоліки:

- користувач може отримати багато повідомлень одночасно;
- помилки можуть вимагати повернення до вже заповнених полів.

### 4.4. Комбінований підхід

У реальних інтерфейсах часто комбінують кілька способів.

Наприклад:

1. Під час введення не показувати помилку одразу.
2. Після виходу з поля перевірити введене значення.
3. Під час відправлення перевірити всю форму.
4. Після виправлення поля оновити повідомлення про помилку.
5. Перед збереженням повторно перевірити дані на сервері.

Вибір залежить від складності форми, характеру даних і очікувань користувачів.

## 5. Основні стани валідації

### 5.1. Default state — початковий стан

Користувач ще не взаємодіяв із полем.

    Label: Електронна пошта
    Placeholder: name@example.com
    State: Default

На цьому етапі не потрібно без причини показувати помилку.

### 5.2. Focus state — стан фокусу

Поле активне, користувач може вводити дані.

    Label: Електронна пошта
    State: Focus

Фокус повинен бути помітним. Не обов'язково одразу показувати повідомлення про помилку.

### 5.3. Filled state — заповнений стан

Користувач увів значення.

    Label: Електронна пошта
    Value: user@example.com
    State: Filled

Заповнене поле не обов'язково є валідним. Значення ще потрібно перевірити.

### 5.4. Valid state — коректний стан

Введене значення відповідає правилам.

    Label: Електронна пошта
    Value: user@example.com
    State: Valid

Позитивний індикатор може бути корисним для складних полів, але не кожне коректне поле потребує зеленої рамки або повідомлення про успіх.

### 5.5. Invalid state — некоректний стан

Значення не відповідає правилам.

    Label: Електронна пошта
    Value: user@
    State: Invalid
    Error: Введіть коректну електронну адресу.

Візуально помилка може позначатися рамкою, іконкою та повідомленням.

Не покладайся лише на колір: причина помилки повинна бути зрозумілою з тексту.

### 5.6. Disabled state — недоступний стан

Поле тимчасово недоступне для взаємодії.

    Label: Код підтвердження
    State: Disabled

Якщо поле недоступне, варто пояснити причину, коли вона не очевидна.

### 5.7. Pending state — перевірка триває

Деякі перевірки потребують запиту до сервера.

Наприклад, система перевіряє, чи доступне ім'я користувача.

    Username: learner2026
    State: Checking availability

Інтерфейс може показати ненав'язливий індикатор очікування.

Не показуй повідомлення «Ім'я доступне», доки сервер не підтвердить результат.

### 5.8. Success state — успішний стан

Перевірка або відправлення завершилися успішно.

    State: Success
    Message: Дані успішно збережено.

Не плутай успішну перевірку формату з успішним збереженням даних. Це різні події.

## 6. Як правильно показувати помилки?

### 6.1. Повідомлення має бути конкретним

❌ Погано:

    Некоректне значення.

✔ Краще:

    Введіть число від 1 до 35.

Користувач повинен зрозуміти, яке правило порушено.

### 6.2. Пояснюй, як виправити помилку

❌ Погано:

    Неправильний формат.

✔ Краще:

    Введіть дату у форматі ДД.ММ.РРРР.

Але формат потрібно вказувати лише тоді, коли система справді очікує саме його.

### 6.3. Розміщуй помилку біля відповідного поля

Користувач повинен легко пов'язати повідомлення з проблемним елементом.

Типова структура:

    Label
    Input
    Error message

Для довгих форм можна додатково показати загальний список помилок на початку форми.

### 6.4. Не стирай введені дані

Якщо поле містить помилку, зберігай значення, яке ввів користувач, якщо немає обґрунтованої причини його очистити.

Наприклад, якщо електронна адреса введена неправильно, користувач повинен мати змогу відредагувати її, а не вводити заново.

### 6.5. Не звинувачуй користувача

❌ Погано:

    Ви неправильно заповнили поле!

✔ Краще:

    Перевірте формат електронної адреси.

Мова інтерфейсу має бути нейтральною та допоміжною.

### 6.6. Не показуй усі помилки завчасно

Якщо користувач ще не почав заповнювати форму, десятки червоних повідомлень можуть створити зайве напруження.

Показуй помилки тоді, коли вони допомагають виконати наступний крок.

### 6.7. Не приховуй помилку лише кольором

Помітна червона рамка може бути корисною, але її потрібно доповнити текстовим поясненням або іншим доступним сигналом.

## 7. Як позначати поля з помилками?

Помилка зазвичай має кілька складових:

- візуальний стан поля;
- зрозумілий текст помилки;
- зв'язок повідомлення з полем;
- за потреби — загальний список помилок форми.

Приклад структури:

    Електронна пошта
    ┌──────────────────────────────┐
    │ user@                        │
    └──────────────────────────────┘
    Перевірте формат електронної пошти.

У CSS можна створити окремий стан помилки.

    .form-field input[aria-invalid="true"] {
        border-color: #b42318;
    }

    .form-field .error-message {
        color: #b42318;
        font-size: 0.875rem;
    }

Це лише приклад оформлення. Потрібно також перевірити контраст, видимість повідомлення та доступність стану для допоміжних технологій.

## 8. Доступність валідації (Accessibility)

### 8.1. Пов'язуй помилку з відповідним полем

Для цього можна використовувати `aria-describedby`.

    <label for="email">Електронна пошта</label>

    <input
        id="email"
        name="email"
        type="email"
        aria-invalid="true"
        aria-describedby="email-error"
        required
    >

    <p id="email-error">
        Введіть коректну електронну адресу.
    </p>

У цьому прикладі:

- `label` називає поле;
- `aria-invalid="true"` повідомляє про некоректний стан;
- `aria-describedby` пов'язує поле з поясненням;
- текст помилки пояснює, як виправити значення.

`aria-invalid="true"` потрібно встановлювати тоді, коли поле справді перебуває в стані помилки, а не на початку заповнення форми без причини.

### 8.2. Використовуй семантичний HTML

Для стандартних полів використовуй відповідні елементи:

- `<input>`;
- `<textarea>`;
- `<select>`;
- `<label>`;
- `<fieldset>`;
- `<legend>`.

Нативні HTML-елементи часто вже мають необхідну поведінку та доступність.

### 8.3. Не покладайся лише на колір

Якщо поле позначене червоною рамкою, повідомлення про помилку все одно повинно бути зрозумілим без кольору.

Наприклад:

    Error: Введіть коректний номер телефону.

### 8.4. Забезпечуй доступність клавіатурою

Користувач повинен мати змогу:

- перейти до поля клавішею Tab;
- змінити значення;
- побачити індикатор фокусу;
- дістатися повідомлення про помилку;
- виправити дані й повторно відправити форму.

Не переміщуй фокус несподівано після кожної зміни поля.

### 8.5. Повідомляй про помилки після відправлення

Для складних форм можна створити список помилок із посиланнями на відповідні поля.

Наприклад:

    У формі є 2 помилки:

    - Введіть коректну електронну адресу.
    - Оберіть дату початку курсу.

Для доступності можна передбачити перенесення фокусу до заголовка списку помилок або іншої логічної точки після невдалої відправки. Так користувач зрозуміє, що відбулося.

### 8.6. Обережно використовуй live regions

Для повідомлень, які з'являються динамічно, можуть бути корисними `aria-live` або `role="alert"`.

Проте не варто оголошувати кожну зміну поля як термінове повідомлення. Надмірні оголошення заважають роботі зі скринрідером.

Використовуй такі механізми відповідно до важливості та моменту появи повідомлення.

## 9. Клієнтська та серверна валідація

### 9.1. HTML-валідація

HTML має вбудовані механізми перевірки.

Приклад:

    <form>
        <label for="email">Електронна пошта</label>

        <input
            id="email"
            name="email"
            type="email"
            required
        >

        <button type="submit">Надіслати</button>
    </form>

Браузер перевірить обов'язковість поля та базовий формат електронної пошти.

Інші корисні атрибути:

- `required` — поле обов'язкове;
- `minlength` — мінімальна довжина;
- `maxlength` — максимальна довжина;
- `min` — мінімальне значення;
- `max` — максимальне значення;
- `step` — крок допустимих числових значень;
- `pattern` — шаблон для перевірки;
- `type="email"` — базова перевірка формату електронної пошти;
- `type="url"` — базова перевірка формату URL.

Вбудована валідація спрощує реалізацію, але її поведінку потрібно перевіряти в контексті конкретного інтерфейсу.

### 9.2. JavaScript-валідація

JavaScript потрібен для складніших правил і керування користувацьким досвідом.

Наприклад, можна перевірити, чи збігаються два поля.

    const password = document.querySelector("#password");
    const confirmPassword = document.querySelector("#confirmPassword");

    function passwordsMatch() {
        return password.value === confirmPassword.value;
    }

Цей приклад демонструє лише порівняння значень. У реальній формі потрібно додати обробку подій, повідомлення про помилку та перевірку наявності елементів.

### 9.3. Серверна валідація

Сервер повторно перевіряє дані, отримані від клієнта.

Наприклад, сервер може перевірити:

- чи дозволено створювати такого користувача;
- чи відповідає значення правилам продукту;
- чи доступний обраний ресурс;
- чи не порушено обмеження бази даних;
- чи має користувач право виконати дію.

Клієнтські перевірки можна обійти, тому сервер повинен самостійно перевіряти всі важливі правила.

### 9.4. Не змішуй валідацію та безпеку

Валідація допомагає визначити, чи відповідають дані очікуваному формату та правилам.

Але вона не замінює:

- автентифікацію;
- авторизацію;
- параметризовані SQL-запити;
- захист від XSS;
- обмеження доступу до ресурсів;
- інші необхідні заходи безпеки.

Навіть якщо поле проходить валідацію, сервер повинен безпечно обробляти його значення.

## 10. Візуальна ієрархія повідомлень

У формі можуть бути різні типи повідомлень:

| Тип | Призначення | Приклад |
|---|---|---|
| Hint | Пояснити вимогу заздалегідь | Використайте щонайменше 12 символів |
| Error | Повідомити про проблему | Паролі не збігаються |
| Success | Підтвердити успішну дію | Дані успішно збережено |
| Warning | Попередити про можливий наслідок | Після зміни курсу розклад буде оновлено |
| Info | Надати додаткову інформацію | Ви можете змінити ці дані пізніше |

Не використовуй повідомлення про помилку там, де достатньо звичайної підказки.

Наприклад, до введення пароля доречно показати вимоги. Не потрібно одразу повідомляти «Пароль неправильний», якщо користувач ще нічого не вводив.

## 11. Як працювати з валідацією в довгих формах?

У довгій формі користувач може заповнювати багато полів і розділів.

Щоб спростити процес:

- Групуй поля за логічними розділами.
- Показуй помилки біля відповідних полів.
- Не стирай коректні значення після помилки.
- Пояснюй, які поля обов'язкові.
- За потреби показуй загальний список помилок.
- Не блокуй користувача повідомленнями до початку взаємодії.
- Перевіряй дані до збереження.
- Після виправлення повідомляй про зміну стану.

Для багатокрокових форм важливо зберігати введені дані під час переходу між кроками, якщо це відповідає логіці продукту.

Якщо помилка знаходиться на попередньому кроці, інтерфейс має допомогти користувачеві знайти відповідне поле, виправити значення та повернутися до продовження процесу.

## 12. Практичний приклад: форма реєстрації

    <form>
        <div class="form-field">
            <label for="fullName">Повне ім'я</label>

            <input
                id="fullName"
                name="fullName"
                type="text"
                autocomplete="name"
                required
            >
        </div>

        <div class="form-field">
            <label for="email">Електронна пошта</label>

            <input
                id="email"
                name="email"
                type="email"
                autocomplete="email"
                aria-describedby="email-hint"
                required
            >

            <p id="email-hint">
                Використайте адресу, до якої маєте доступ.
            </p>
        </div>

        <div class="form-field">
            <label for="password">Пароль</label>

            <input
                id="password"
                name="password"
                type="password"
                autocomplete="new-password"
                minlength="12"
                required
            >
        </div>

        <button type="submit">Зареєструватися</button>
    </form>

У цьому прикладі:

- `required` позначає обов'язкові поля;
- `type="email"` забезпечує базову перевірку формату адреси;
- `minlength="12"` задає мінімальну довжину пароля;
- `autocomplete` допомагає браузеру заповнювати відповідні дані;
- `aria-describedby` пов'язує електронну пошту з додатковою підказкою.

Для реального застосунку потрібно також реалізувати серверну перевірку та продумати повідомлення про помилки.

## 13. Практичний приклад: повідомлення про помилку

    <div class="form-field">
        <label for="email">Електронна пошта</label>

        <input
            id="email"
            name="email"
            type="email"
            value="user@"
            aria-invalid="true"
            aria-describedby="email-error"
            required
        >

        <p id="email-error" class="error-message">
            Перевірте формат електронної пошти.
        </p>
    </div>

Приклад CSS:

    .form-field {
        display: flex;
        flex-direction: column;
        gap: 0.5rem;
        margin-bottom: 1rem;
    }

    .form-field input {
        padding: 0.75rem;
        border: 1px solid #767676;
        border-radius: 0.375rem;
        font: inherit;
    }

    .form-field input[aria-invalid="true"] {
        border-color: #b42318;
    }

    .error-message {
        margin: 0;
        color: #b42318;
        font-size: 0.875rem;
    }

Цей приклад показує структуру поля з помилкою. У реальному застосунку значення `aria-invalid` і повідомлення повинні залежати від результату перевірки, а не бути постійно заданими для всіх користувачів.

## 14. Практичний приклад: перевірка форми за допомогою JavaScript

    const form = document.querySelector("#registrationForm");
    const email = document.querySelector("#email");
    const emailError = document.querySelector("#email-error");

    form.addEventListener("submit", (event) => {
        if (!email.validity.valid) {
            event.preventDefault();

            email.setAttribute("aria-invalid", "true");
            emailError.textContent =
                "Введіть коректну електронну адресу.";

            email.focus();
            return;
        }

        email.removeAttribute("aria-invalid");
        emailError.textContent = "";
    });

Для цього прикладу в HTML потрібно передбачити елементи з відповідними `id`, зокрема `registrationForm`, `email` та `email-error`.

Пояснення:

- `addEventListener("submit", ...)` обробляє спробу відправлення форми.
- `event.preventDefault()` скасовує відправлення, якщо виявлено помилку.
- `email.validity.valid` перевіряє результат вбудованої браузерної валідації.
- `aria-invalid` повідомляє про некоректний стан поля.
- `email.focus()` переводить фокус до поля, яке потребує виправлення.

Це навчальний приклад. У повноцінній формі варто передбачити всі поля, правильне керування фокусом, обробку серверних помилок і відповідний сценарій успішного відправлення.

## 15. Поширені помилки дизайну валідації

### Помилка 1. Помилка без пояснення

    Invalid input.

Проблема: користувач не розуміє, що потрібно змінити.

Рішення: вказуй конкретне правило або дію.

### Помилка 2. Помилка з'являється до введення

Проблема: користувач бачить червоний стан, хоча ще не взаємодіяв із полем.

Рішення: обирай момент перевірки відповідно до сценарію.

### Помилка 3. Занадто суворі правила

Проблема: форма відхиляє коректні варіанти введення, які система могла б прийняти.

Рішення: перевіряй, чи справді кожне обмеження необхідне.

### Помилка 4. Різні правила на клієнті й сервері

Проблема: клієнт повідомляє, що значення коректне, але сервер його відхиляє через інше правило.

Рішення: узгоджуй правила перевірки на обох сторонах і зрозуміло обробляй серверні помилки.

### Помилка 5. Втрата введених даних

Проблема: після помилки користувач повинен заповнювати форму заново.

Рішення: зберігай введені значення, коли це безпечно та відповідає логіці форми.

### Помилка 6. Помилка позначена лише червоним кольором

Проблема: користувач не отримує достатнього пояснення.

Рішення: додай текстове повідомлення та доступний стан поля.

### Помилка 7. Надмірні повідомлення

Проблема: інтерфейс постійно показує помилки під час кожного натискання клавіші.

Рішення: показуй повідомлення у відповідний момент і не повторюй те саме пояснення без потреби.

### Помилка 8. Успіх повідомляється передчасно

Проблема: інтерфейс показує «Збережено», хоча сервер ще не підтвердив операцію.

Рішення: розрізняй локальну перевірку, відправлення запиту та успішне завершення операції.

### Помилка 9. Серверна перевірка відсутня

Проблема: дані можна передати в обхід браузерної форми.

Рішення: перевіряй усі важливі правила на сервері.

### Помилка 10. Немає сценарію виправлення

Проблема: система повідомляє про помилку, але не допомагає знайти поле або виправити значення.

Рішення: пов'язуй повідомлення з полем і зберігай логічний порядок взаємодії.

## 16. Чекліст перевірки валідації

### Правила

- [ ] Для кожного поля визначено, чи є воно обов'язковим.
- [ ] Визначено допустимі формати даних.
- [ ] Визначено межі та обмеження, якщо вони потрібні.
- [ ] Правила відповідають реальній логіці продукту.
- [ ] Клієнтська та серверна перевірки узгоджені.

### Повідомлення

- [ ] Кожна помилка пояснює конкретну проблему.
- [ ] Користувач розуміє, як виправити значення.
- [ ] Повідомлення розташоване біля відповідного поля.
- [ ] Введені дані не зникають без причини.
- [ ] Повідомлення не з'являються передчасно.
- [ ] Успішний результат показується лише після підтвердження відповідної операції.

### Візуальний дизайн

- [ ] Стан помилки відрізняється від звичайного стану.
- [ ] Помилка не позначається лише кольором.
- [ ] Текст достатньо контрастний і читабельний.
- [ ] Відступи між полем і повідомленням зрозумілі.
- [ ] Довгі повідомлення не руйнують адаптивний макет.

### Accessibility

- [ ] Кожне поле має доступний підпис.
- [ ] Помилки пов'язані з відповідними полями.
- [ ] Некоректний стан доступний допоміжним технологіям.
- [ ] Формою можна користуватися за допомогою клавіатури.
- [ ] Фокус залишається передбачуваним.
- [ ] Динамічні повідомлення не створюють зайвих оголошень.

### Технічна поведінка

- [ ] HTML-валідація працює очікувано.
- [ ] Складні правила перевіряються відповідною логікою.
- [ ] Сервер повторно перевіряє отримані дані.
- [ ] Обробляються помилки мережі та сервера.
- [ ] Після виправлення помилки стан поля оновлюється.
- [ ] Форма має зрозумілий сценарій успішного завершення.

## 17. Що потрібно запам'ятати

✔ Валідація перевіряє, чи відповідають дані заданим правилам.

✔ Помилка має пояснювати, що сталося і як це виправити.

✔ Клієнтська валідація допомагає користувачеві швидко виявляти проблеми.

✔ Серверна валідація обов'язкова для важливих правил і даних.

✔ Не показуй помилки без потреби до взаємодії користувача з полем.

✔ Не стирай введені дані лише через те, що одне з полів має помилку.

✔ Не використовуй лише колір для позначення некоректного стану.

✔ Повідомлення про помилку повинно бути пов'язане з відповідним полем.

✔ Не плутай коректний формат, успішну перевірку та успішне збереження даних.

✔ Валідація повинна допомагати користувачеві завершити дію, а не лише забороняти її.

## 18. Рівні знань

### Core — базовий рівень

- Розуміти поняття валідації.
- Розрізняти коректний і некоректний стани.
- Знати призначення повідомлень про помилки.
- Розуміти різницю між клієнтською та серверною валідацією.
- Знати основні правила: required, format, length і range.

### Junior — практичний рівень

- Проєктувати стани полів із помилками.
- Визначати, коли показувати повідомлення про помилку.
- Створювати зрозумілі тексти помилок.
- Використовувати HTML-атрибути валідації.
- Пов'язувати помилки з полями через доступні механізми.
- Продумувати сценарії виправлення даних.
- Перевіряти форму на мобільних пристроях і клавіатурою.

### Middle — системний рівень

- Проєктувати послідовну систему валідації для продукту.
- Враховувати залежності між полями.
- Узгоджувати клієнтські та серверні правила.
- Продумувати поведінку довгих і багатокрокових форм.
- Визначати оптимальний момент перевірки для різних полів.
- Розробляти загальні компоненти полів і повідомлень про помилки.
- Перевіряти доступність динамічного зворотного зв'язку.

### Senior — експертний рівень

- Визначати загальну стратегію валідації продукту.
- Балансувати суворість правил і зручність користування.
- Аналізувати, які помилки найчастіше заважають користувачам.
- Координувати правила між frontend, backend і бізнес-логікою.
- Проєктувати обробку помилок у складних багатокрокових сценаріях.
- Забезпечувати узгодженість валідації в дизайн-системі.
- Враховувати доступність, локалізацію, безпеку та якість даних.

## 20. Мінішпаргалка

| Ситуація | Рішення |
|---|---|
| Поле обов'язкове | `required` і серверна перевірка |
| Потрібно перевірити email | `type="email"` і відповідна перевірка на сервері |
| Потрібно обмежити довжину | `minlength`, `maxlength` або відповідна логіка |
| Потрібно перевірити числовий діапазон | `min`, `max` та серверна перевірка |
| Потрібно перевірити складне правило | JavaScript і серверна логіка |
| Два поля повинні збігатися | Cross-field validation |
| Користувач ввів неправильні дані | Конкретне повідомлення біля поля |
| Помилка вже виправлена | Оновити стан поля та прибрати застаріле повідомлення |
| Помилка виникла на сервері | Показати зрозуміле повідомлення й зберегти введені дані, якщо це можливо |
| Потрібно зробити помилку доступною | Пов'язати її з полем і повідомити про некоректний стан |
| Уся форма має помилки | Показати список помилок і допомогти перейти до відповідних полів |
| Дані перевірені на клієнті | Все одно перевірити їх на сервері |

## 21. Головний принцип

**Хороша валідація не просто виявляє помилку — вона допомагає користувачеві зрозуміти проблему, виправити дані та успішно завершити дію.**

Під час проєктування форми потрібно думати не лише про те, які значення система приймає, а й про те, як користувач дізнається про помилку, зрозуміє її причину та виправить її без зайвих зусиль.

Найкраща валідація поєднує зрозумілі правила, своєчасний зворотний зв'язок, доступний інтерфейс і надійну перевірку даних на сервері.
