# 05. Error Messages — Повідомлення про помилки

> **Error message (повідомлення про помилку)** — це текстовий зворотний зв'язок, який пояснює користувачеві, що під час введення даних, виконання дії або обробки запиту виникла проблема.

У дизайні інтерфейсів повідомлення про помилки допомагають користувачеві зрозуміти, що сталося, чому система не може виконати дію та як виправити ситуацію.

Наприклад, якщо користувач вводить некоректну електронну адресу, інтерфейс може показати повідомлення:

    Введіть коректну електронну адресу.

Хороше повідомлення не просто констатує проблему. Воно допомагає користувачеві рухатися далі.

**Головний принцип:** повідомлення про помилку повинно пояснювати проблему зрозумілою мовою та, коли це можливо, підказувати наступний крок.

---

## 1. Для чого потрібні повідомлення про помилки?

Error messages потрібні, щоб:

- ✔ Пояснювати, чому дія не вдалася.
- ✔ Допомагати виправляти некоректні дані.
- ✔ Повідомляти про пропущені обов'язкові поля.
- ✔ Пояснювати помилки під час відправлення форми.
- ✔ Повідомляти про проблеми з мережею або сервером.
- ✔ Допомагати відновити перерваний процес.
- ✔ Зменшувати невизначеність і розчарування користувача.
- ✔ Робити поведінку інтерфейсу передбачуваною.
- ✔ Підвищувати доступність і зрозумілість продукту.

Наприклад, у формі реєстрації можуть виникнути такі ситуації:

    Поле не заповнене:
        Введіть ім'я.

    Некоректний формат:
        Перевірте формат електронної адреси.

    Паролі не збігаються:
        Паролі не збігаються. Перевірте обидва поля.

    Помилка сервера:
        Не вдалося створити обліковий запис.
        Спробуйте ще раз пізніше.

Кожне повідомлення відповідає на конкретну проблему.

---

## 2. Основні поняття

### 2.1. Error message

Текст, який повідомляє про проблему.

    Введіть коректний номер телефону.

Це повідомлення пояснює, що саме потрібно виправити.

### 2.2. Validation error

Помилка, яка виникає, коли введені дані не відповідають установленим правилам.

Приклади:

- поле обов'язкове, але порожнє;
- електронна адреса має некоректний формат;
- значення виходить за допустимі межі;
- пароль не відповідає вимогам;
- дата завершення передує даті початку.

Наприклад:

    Label: Кількість учнів
    Value: 50
    Allowed range: 1–35
    Error: Введіть число від 1 до 35.

### 2.3. System error

Помилка, пов'язана з роботою системи, а не обов'язково з діями користувача.

Приклади:

- сервер тимчасово недоступний;
- не вдалося завантажити дані;
- виникла помилка під час збереження;
- запит завершився невдало;
- відбулося переривання мережевого з'єднання.

Приклад повідомлення:

    Не вдалося завантажити список курсів.
    Спробуйте оновити сторінку.

Не звинувачуй користувача в проблемі, причиною якої є система.

### 2.4. Inline error

Повідомлення про помилку, розміщене безпосередньо біля відповідного поля.

    Електронна пошта
    ┌──────────────────────────────┐
    │ user@                        │
    └──────────────────────────────┘
    Перевірте формат електронної пошти.

Inline error особливо корисний у формах, оскільки користувач одразу бачить, яке поле потребує виправлення.

### 2.5. Form-level error

Загальне повідомлення про помилку, що стосується всієї форми або процесу.

    Не вдалося відправити форму.
    Перевірте введені дані та спробуйте ще раз.

Такий тип повідомлення доречний, коли проблема не стосується одного конкретного поля або потрібно повідомити про загальний результат відправлення.

### 2.6. Error state

Error state — це стан компонента, у якому інтерфейс повідомляє про наявність проблеми.

Він може включати:

- змінену рамку поля;
- текстове повідомлення;
- іконку;
- доступні для допоміжних технологій атрибути;
- індикатор помилки у списку полів.

Важливо: **error state і error message — не одне й те саме.** Error state описує загальний стан компонента, а error message пояснює проблему текстом.

### 2.7. Recovery — відновлення після помилки

Recovery — це можливість користувача продовжити роботу після невдалої дії.

Наприклад:

    Не вдалося зберегти зміни.

    [Спробувати ще раз]

Повідомлення інформує про проблему, а кнопка допомагає виконати наступний крок.

Не кожна помилка потребує кнопки повторної спроби. Спосіб відновлення залежить від ситуації.

---

## 3. Основні типи повідомлень про помилки

### 3.1. Required field error — незаповнене обов'язкове поле

Виникає, коли користувач не заповнив поле, яке потрібно заповнити.

    Error: Введіть ім'я.

Або:

    Error: Оберіть дату початку курсу.

Повідомлення має прямо називати необхідну дію.

### 3.2. Format error — неправильний формат

Значення введене, але не відповідає очікуваному формату.

    Error: Введіть коректну електронну адресу.

    Error: Введіть дату у форматі ДД.ММ.РРРР.

    Error: Введіть шестизначний код.

Формат потрібно вказувати лише тоді, коли він справді визначений правилами системи.

### 3.3. Length error — неправильна довжина

Значення має замало або забагато символів.

    Error: Введіть щонайменше 8 символів.

    Error: Максимальна довжина назви — 100 символів.

Коли вимога відома заздалегідь, її варто показати в підказці до поля, щоб зменшити кількість помилок.

### 3.4. Range error — значення поза діапазоном

    Error: Введіть число від 1 до 35.

Таке повідомлення корисне для чисел, дат, кількості учасників та інших значень із допустимими межами.

### 3.5. Mismatch error — значення не збігаються

    Error: Паролі не збігаються.

Інші приклади:

- дата завершення раніше дати початку;
- підтвердження електронної адреси не збігається;
- введений код не відповідає коду підтвердження.

Повідомлення має пояснювати, які значення потрібно перевірити.

### 3.6. Availability error — значення недоступне

Наприклад, ім'я користувача вже зайняте.

    Це ім'я користувача вже зайняте.
    Спробуйте інший варіант.

Не показуй таке повідомлення, доки система не перевірить доступність значення.

### 3.7. Network error — мережева помилка

    Не вдалося підключитися до сервера.
    Перевірте з'єднання та спробуйте ще раз.

Якщо причина невідома, не стверджуй, що проблема точно в інтернет-з'єднанні. Краще описати те, що система справді знає.

Наприклад:

    Не вдалося отримати дані.
    Спробуйте ще раз.

### 3.8. Server error — помилка сервера

    Не вдалося зберегти зміни.
    Спробуйте ще раз пізніше.

Повідомлення не повинно розкривати внутрішні технічні деталі, конфіденційну інформацію або текст системного винятку.

### 3.9. Permission error — недостатньо прав

    У вас немає дозволу редагувати цей курс.

Якщо можливо, поясни, що користувач може зробити далі, наприклад звернутися до адміністратора або вибрати доступний ресурс.

### 3.10. Not found error — ресурс не знайдено

    Не вдалося знайти цей курс.
    Перевірте посилання або поверніться до списку курсів.

Це повідомлення повинно допомагати користувачеві зрозуміти, як продовжити роботу.

---

## 4. Принципи хорошого повідомлення про помилку

### 4.1. Будь конкретним

❌ Погано:

    Помилка введення.

✔ Краще:

    Введіть коректну електронну адресу.

Перше повідомлення лише констатує проблему. Друге пояснює, що потрібно виправити.

### 4.2. Використовуй зрозумілу мову

❌ Погано:

    Некоректний параметр валідації.

✔ Краще:

    Введіть число від 1 до 35.

У повідомленнях для звичайних користувачів уникай технічних термінів, якщо їх можна замінити простими словами.

### 4.3. Пояснюй, як виправити помилку

❌ Погано:

    Неправильний формат.

✔ Краще:

    Введіть номер телефону у форматі +380 67 123 45 67.

Проте не нав'язуй один формат, якщо система підтримує декілька варіантів.

### 4.4. Будь коротким

Повідомлення має передавати головну думку без зайвого тексту.

❌ Занадто довго:

    На жаль, введене вами значення не відповідає вимогам
    системи, тому ми не можемо продовжити виконання операції.

✔ Краще:

    Перевірте введені дані.

Якщо користувачеві потрібно знати конкретну причину, назви її прямо.

### 4.5. Не звинувачуй користувача

❌ Погано:

    Ви неправильно заповнили форму!

✔ Краще:

    Перевірте обов'язкові поля.

Нейтральний тон допомагає зберегти довіру до продукту.

### 4.6. Не створюй невиправданої тривоги

❌ Погано:

    Критична помилка! Негайно повторіть дію!

✔ Краще:

    Не вдалося зберегти зміни. Спробуйте ще раз.

Серйозність повідомлення повинна відповідати реальним наслідкам проблеми.

### 4.7. Не приховуй важливу інформацію

Якщо через помилку користувач може втратити дані, повідомлення має пояснювати це до виконання потенційно руйнівної дії.

Наприклад:

    Не вдалося зберегти зміни.
    Ваші останні зміни ще не збережені.

Використовуй таке формулювання лише тоді, коли воно відповідає фактичному стану даних.

### 4.8. Пропонуй наступний крок

Якщо це можливо, поясни, що робити далі.

    Не вдалося завантажити курси.
    [Спробувати ще раз]

    У вас немає доступу до цього розділу.
    Зверніться до адміністратора.

Не додавай дію, яка не допомагає розв'язати проблему.

---

## 5. Структура повідомлення про помилку

Хороше повідомлення може складатися з трьох частин:

1. **Проблема** — що сталося.
2. **Причина або вимога** — чому дія не вдалася, якщо це відомо.
3. **Наступний крок** — що можна зробити.

Наприклад:

    Проблема:
        Паролі не збігаються.

    Пояснення:
        Переконайтеся, що обидва поля містять однаковий пароль.

    Наступний крок:
        Перевірте пароль і його підтвердження.

Не потрібно використовувати всі три частини в кожному повідомленні. Для простих помилок достатньо одного короткого речення.

### Формула повідомлення

    [Що не так] + [Що зробити]

Приклади:

    Введіть коректну електронну адресу.

    Оберіть дату початку курсу.

    Назва повинна містити щонайменше 3 символи.

    Не вдалося завантажити дані. Спробуйте ще раз.

---

## 6. Inline errors — помилки біля полів

Inline error розташовується поруч із полем, до якого належить.

Типова структура:

    Label
    Input
    Error message

Наприклад:

    Електронна пошта
    ┌──────────────────────────────┐
    │ user@                        │
    └──────────────────────────────┘
    Введіть коректну електронну адресу.

Переваги:

- користувач одразу бачить проблемне поле;
- не потрібно шукати пояснення в іншій частині сторінки;
- легше виправити конкретне значення;
- помилку можна пов'язати з полем програмно.

### Рекомендації

- Розміщуй повідомлення близько до відповідного поля.
- Використовуй короткий текст.
- Зберігай введене значення, якщо немає причини його видаляти.
- Не дозволяй повідомленню перекривати інші елементи.
- Передбачай достатньо місця для тексту на мобільних пристроях.
- Не покладайся лише на червоний колір.
- Не показуй застаріле повідомлення після виправлення поля.

---

## 7. Form-level errors — загальні помилки форми

Іноді проблема стосується не одного поля, а всієї форми.

Наприклад:

- сервер відхилив запит;
- сталася мережева помилка;
- форма не може бути відправлена;
- деякі поля не можна перевірити без додаткової інформації.

Приклад:

    Не вдалося створити курс.
    Перевірте дані та спробуйте ще раз.

Якщо проблема стосується кількох полів, можна показати загальний список помилок:

    Не вдалося відправити форму.

    - Введіть коректну електронну адресу.
    - Оберіть дату початку.
    - Вкажіть кількість учнів від 1 до 35.

Для довгих форм список помилок допомагає швидко побачити обсяг проблеми.

### Коли використовувати загальне повідомлення?

Використовуй form-level error, якщо:

- помилка не має одного конкретного поля;
- сервер відхилив усю операцію;
- потрібно підсумувати кілька помилок;
- користувач повинен зрозуміти, чому форму не відправлено.

Не замінюй загальним повідомленням помилки конкретних полів, якщо користувачеві потрібно виправити саме їх.

## 8. Коли показувати повідомлення про помилку?

Час появи помилки впливає на зручність форми.

### 8.1. On input — під час введення

Помилка оновлюється, коли користувач змінює значення.

Переваги:

- швидкий зворотний зв'язок;
- зручно для складних правил;
- користувач може бачити, як значення відповідає вимогам.

Недоліки:

- надто ранні повідомлення можуть відволікати;
- користувач може ще не завершити введення;
- повідомлення можуть часто змінюватися.

Приклад доречного використання — індикатор виконання вимог до пароля.

### 8.2. On blur — після виходу з поля

Повідомлення з'являється, коли користувач залишає поле.

Переваги:

- користувач має час завершити введення;
- помилки не обов'язково з'являються після першого натискання клавіші;
- добре підходить для багатьох звичайних полів.

### 8.3. On submit — під час відправлення

Помилки показуються після спроби відправити форму.

Переваги:

- користувач може спочатку заповнити форму;
- можна перевірити всі поля разом;
- можна показати загальний список проблем.

Недолік: якщо помилок багато, користувачеві може знадобитися більше часу на їх виправлення.

### 8.4. Комбінований підхід

У багатьох формах доречно використовувати комбіновану поведінку:

1. До взаємодії не показувати помилку без потреби.
2. Після виходу з поля перевіряти введене значення.
3. Під час відправлення перевіряти всю форму.
4. Після виправлення оновлювати повідомлення.
5. Якщо сервер відхилив запит, показувати відповідну помилку.

Вибирай момент перевірки відповідно до конкретного сценарію.

---

## 9. Error states — візуальні стани помилки

Повідомлення про помилку є частиною загального стану компонента.

### 9.1. Default state

Користувач ще не взаємодіяв із полем.

    Label: Електронна пошта
    State: Default

Не показуй помилку лише через те, що поле порожнє, якщо користувач ще не намагався його заповнити й не настав відповідний момент перевірки.

### 9.2. Focus state

Поле перебуває у фокусі.

    Label: Електронна пошта
    State: Focus

Фокус повинен залишатися видимим навіть тоді, коли поле має помилку.

### 9.3. Invalid state

Поле не відповідає правилам.

    Label: Електронна пошта
    Value: user@
    State: Invalid
    Error: Введіть коректну електронну адресу.

Зазвичай використовують помітну рамку й текстове повідомлення.

### 9.4. Corrected state

Користувач виправив значення.

    Label: Електронна пошта
    Value: user@example.com
    State: Corrected

Після повторної перевірки потрібно прибрати застаріле повідомлення, якщо помилку виправлено.

### 9.5. Pending state

Система перевіряє дані на сервері.

    Username: learner2026
    State: Checking...

Не показуй повідомлення про успішну перевірку до отримання результату.

### 9.6. Success state

Перевірка або операція завершилася успішно.

    Дані успішно збережено.

Не плутай успішну валідацію поля з успішним збереженням усієї форми.

---

## 10. Візуальний дизайн повідомлень про помилки

### 10.1. Колір

Для помилок часто використовують червоний або інший колір із системи семантичних кольорів.

Колір повинен допомагати розпізнавати стан, але не бути єдиним способом передавання інформації.

### 10.2. Типографіка

Повідомлення зазвичай менше за основний текст форми, але повинно залишатися читабельним.

Не зменшуй текст настільки, щоб користувачеві було складно його прочитати.

### 10.3. Відступи

Повідомлення має бути візуально пов'язане з відповідним полем.

Приклад структури:

    Label
        ↓
    Input
        ↓
    Error message

Надто великий проміжок між полем і помилкою може створити враження, що текст стосується іншого елемента.

### 10.4. Іконки

Іконка може допомагати швидко розпізнати помилку.

Проте вона не замінює текстового пояснення.

Наприклад:

    [!] Введіть коректну електронну адресу.

Не використовуй іконку, значення якої незрозуміле без контексту.

### 10.5. Розміри й адаптивність

На вузьких екранах повідомлення можуть займати кілька рядків.

Перевіряй:

- довгі повідомлення;
- збільшений розмір тексту;
- вузькі екрани;
- масштабування сторінки;
- темну тему, якщо вона підтримується;
- розташування повідомлень у багатоколонкових формах.

Не фіксуй висоту поля або контейнера так, щоб довге повідомлення обрізалося.

## 11. Доступність повідомлень про помилки (Accessibility)

### 11.1. Пов'язуй повідомлення з полем

Для цього можна використовувати `aria-describedby`.

    <label for="email">Електронна пошта</label>

    <input
        id="email"
        name="email"
        type="email"
        aria-invalid="true"
        aria-describedby="email-error"
        required
    >

    <p id="email-error">
        Введіть коректну електронну адресу.
    </p>

У цьому прикладі:

- `label` визначає призначення поля;
- `aria-invalid="true"` повідомляє про некоректний стан;
- `aria-describedby` пов'язує поле з текстом помилки;
- `id="email-error"` визначає елемент із поясненням.

Застосовуй `aria-invalid="true"` лише тоді, коли поле справді перебуває в стані помилки.

### 11.2. Не використовуй колір як єдиний сигнал

Якщо помилка позначена червоною рамкою, текстове повідомлення все одно має пояснювати проблему.

Користувач повинен розуміти помилку навіть без сприйняття кольорів.

### 11.3. Забезпечуй керування клавіатурою

Користувач повинен мати змогу:

- перейти до поля клавішею Tab;
- побачити фокус;
- прочитати повідомлення;
- виправити значення;
- повторно відправити форму.

Не переміщуй фокус несподівано після кожного введеного символу.

### 11.4. Повідомляй про помилки всієї форми

Для складної форми можна показувати список помилок на початку.

    У формі є 2 помилки:

    - Введіть коректну електронну адресу.
    - Оберіть дату початку.

Кожне повідомлення може вести до відповідного поля, якщо це реалізовано доступним способом.

Після невдалої відправки форми можна перевести фокус до заголовка списку помилок або до першого поля з помилкою — залежно від сценарію.

### 11.5. Обережно використовуй live regions

Для динамічних повідомлень можуть бути корисними `aria-live` та `role="alert"`.

Однак не потрібно оголошувати кожну зміну поля як термінове повідомлення. Це може створювати надмірний шум для користувачів програм читання з екрана.

Вибирай механізм відповідно до важливості повідомлення та моменту його появи.

## 12. Повідомлення про помилки й інші типи тексту

Не всі повідомлення біля поля є повідомленнями про помилки.

| Тип | Призначення | Приклад |
|---|---|---|
| Label | Називає поле | Електронна пошта |
| Placeholder | Показує приклад | name@example.com |
| Hint text | Пояснює вимогу | Використайте щонайменше 12 символів |
| Error message | Пояснює проблему | Паролі не збігаються |
| Success message | Підтверджує успіх | Дані збережено |
| Warning | Попереджає про наслідок | Після зміни курсу розклад оновиться |

Не використовуй error message для інформації, яка не є помилкою.

Наприклад, якщо пароль повинен містити певну кількість символів, ці вимоги краще показати заздалегідь у hint text, а не чекати, поки користувач отримає помилку.

## 13. Повідомлення про помилки в різних сценаріях

### 13.1. Реєстрація

    Email:
        Введіть коректну електронну адресу.

    Password:
        Використайте щонайменше 12 символів.

    Confirm password:
        Паролі не збігаються.

Важливо зберігати вже введені значення, якщо це безпечно та відповідає логіці форми.

### 13.2. Вхід до системи

    Не вдалося увійти.
    Перевірте введені дані або скористайтеся відновленням пароля.

У сценаріях автентифікації потрібно враховувати безпеку. Не розкривай зайвих деталей, які можуть допомогти зловмисникам визначати, чи існує певний обліковий запис.

### 13.3. Пошук

    Не вдалося виконати пошук.
    Спробуйте ще раз.

Якщо пошук просто не знайшов результатів, це не обов'язково помилка.

    За вашим запитом нічого не знайдено.

Стан «немає результатів» відрізняється від стану «помилка пошуку».

### 13.4. Збереження даних

    Не вдалося зберегти зміни.
    Спробуйте ще раз.

Якщо система не зберегла дані, не показуй повідомлення про успішне збереження.

### 13.5. Завантаження файлу

    Не вдалося завантажити файл.
    Перевірте формат і розмір файлу.

Таке повідомлення доречне, якщо формат або розмір справді є причиною помилки.

Якщо причина невідома, краще використати нейтральне повідомлення та надати можливість повторити спробу.

### 13.6. Видалення даних

Якщо видалення не вдалося:

    Не вдалося видалити курс.
    Спробуйте ще раз.

Якщо видалення є незворотним, попередження про наслідки потрібно показати до підтвердження дії, а не після помилки.

### 13.7. Завантаження сторінки

    Не вдалося завантажити дані.
    [Спробувати ще раз]

Якщо можливо, зберігай іншу доступну інформацію на сторінці, щоб помилка одного запиту не блокувала весь інтерфейс.

## 14. Практичний приклад: поле з повідомленням про помилку

    <div class="form-field">
        <label for="email">Електронна пошта</label>

        <input
            id="email"
            name="email"
            type="email"
            value="user@"
            aria-invalid="true"
            aria-describedby="email-error"
            required
        >

        <p id="email-error" class="error-message">
            Введіть коректну електронну адресу.
        </p>
    </div>

Пояснення:

- `<label>` називає поле.
- `value` демонструє вже введене значення.
- `aria-invalid="true"` повідомляє про некоректний стан.
- `aria-describedby` пов'язує поле з поясненням.
- `error-message` використовується для стилізації тексту.

Це демонстраційний приклад стану помилки. У реальному застосунку значення `aria-invalid` і видимість повідомлення повинні залежати від результату валідації.

## 15. Практичний приклад: CSS для помилок

    .form-field {

## 16. Практичний приклад: показ повідомлення через JavaScript

HTML:

    <form id="registrationForm">
        <div class="form-field">
            <label for="email">Електронна пошта</label>

            <input
                id="email"
                name="email"
                type="email"
                aria-describedby="email-error"
                required
            >

            <p id="email-error" class="error-message"></p>
        </div>

        <button type="submit">Зареєструватися</button>
    </form>

JavaScript:

    const form = document.querySelector("#registrationForm");
    const email = document.querySelector("#email");
    const emailError = document.querySelector("#email-error");

    form.addEventListener("submit", (event) => {
        if (!email.validity.valid) {
            event.preventDefault();

            email.setAttribute("aria-invalid", "true");
            emailError.textContent =
                "Введіть коректну електронну адресу.";

            email.focus();
            return;
        }

        email.removeAttribute("aria-invalid");
        emailError.textContent = "";
    });

Пояснення:

- `submit` запускає обробник під час відправлення форми.
- `email.validity.valid` перевіряє результат вбудованої браузерної валідації.
- `preventDefault()` зупиняє відправлення, якщо значення некоректне.
- `aria-invalid` позначає поле як некоректне.
- `textContent` задає повідомлення про помилку.
- `focus()` переводить фокус до поля, яке потрібно виправити.

Це навчальний приклад для одного поля. У реальній формі потрібно обробити всі поля, серверні помилки, успішне відправлення та повторне використання повідомлень.

## 17. Поширені помилки в дизайні Error Messages

### Помилка 1. Незрозуміле повідомлення

    Щось пішло не так.

Проблема: користувач не розуміє, що сталося.

Рішення: назви проблему точніше, якщо система має достатньо інформації.

### Помилка 2. Немає наступного кроку

    Не вдалося зберегти дані.

Проблема: користувач не знає, що робити далі.

Рішення: якщо це доречно, додай можливість повторити спробу або поясни наступну дію.

### Помилка 3. Надто технічний текст

    HTTP 500: Internal Server Error.

Проблема: повідомлення незрозуміле більшості користувачів.

Рішення: використовуй зрозумілий текст інтерфейсу, а технічні деталі залишай для журналів і засобів діагностики.

### Помилка 4. Помилка без прив'язки до поля

Проблема: користувач не розуміє, яке значення потрібно виправити.

Рішення: розміщуй inline error біля відповідного поля та програмно пов'язуй їх.

### Помилка 5. Лише червона рамка

Проблема: візуальний стан не пояснює причину помилки.

Рішення: додай текстове повідомлення.

### Помилка 6. Втрата введених даних

Проблема: після помилки користувач змушений заповнювати форму заново.

Рішення: зберігай введені дані, коли це можливо та безпечно.

### Помилка 7. Застаріле повідомлення

Проблема: користувач виправив значення, але повідомлення продовжує стверджувати, що поле некоректне.

Рішення: повторно перевіряй значення та оновлюй стан поля.

### Помилка 8. Надмірні повідомлення

Проблема: інтерфейс показує помилки після кожного натискання клавіші.

Рішення: вибирай відповідний момент перевірки та не створюй зайвих переривань.

### Помилка 9. Відсутність серверної обробки

Проблема: інтерфейс обробляє лише помилки введення, але не мережеві та серверні проблеми.

Рішення: передбачай різні типи помилок і відповідні сценарії відновлення.

### Помилка 10. Передчасне повідомлення про успіх

Проблема: система показує, що дані збережено, хоча запит ще не завершився.

Рішення: показуй успіх після підтвердження операції.

### Помилка 11. Розкриття конфіденційної інформації

Проблема: повідомлення містить внутрішні деталі сервера, приватні дані або зайву інформацію про обліковий запис.

Рішення: показуй користувачеві лише інформацію, необхідну для розуміння ситуації та подальшої дії.

### Помилка 12. Відсутність сценарію відновлення

Проблема: користувач знає про помилку, але не може продовжити роботу.

Рішення: передбачай повторну спробу, редагування значення, повернення до попереднього кроку або іншу доречну дію.

## 18. Чекліст перевірки повідомлень про помилки

### Зміст

- [ ] Повідомлення пояснює конкретну проблему.
- [ ] Текст зрозумілий цільовій аудиторії.
- [ ] Повідомлення не містить зайвих технічних термінів.
- [ ] Користувач розуміє, як виправити помилку.
- [ ] Наступний крок запропонований, якщо це доречно.
- [ ] Текст не звинувачує користувача.
- [ ] Повідомлення відповідає реальній причині помилки.

### Візуальний дизайн

- [ ] Помилку можна помітити без надмірного акценту.
- [ ] Колір не є єдиним сигналом.
- [ ] Текст має достатній контраст.
- [ ] Повідомлення розташоване біля відповідного поля.
- [ ] Довгий текст не обрізається.
- [ ] Макет залишається зрозумілим на мобільних пристроях.
- [ ] Фокус поля залишається помітним.

### Поведінка

- [ ] Повідомлення з'являється у відповідний момент.
- [ ] Після виправлення помилки повідомлення оновлюється.
- [ ] Введені дані не втрачаються без причини.
- [ ] Серверні помилки обробляються окремо від помилок введення.
- [ ] Користувач може повторити дію, якщо це можливо.
- [ ] Успіх не повідомляється до завершення операції.

### Accessibility

- [ ] Поле має зрозумілий label.
- [ ] Повідомлення програмно пов'язане з полем.
- [ ] Некоректний стан доступний допоміжним технологіям.
- [ ] Формою можна користуватися клавіатурою.
- [ ] Фокус після помилки поводиться передбачувано.
- [ ] Динамічні повідомлення не створюють надмірних оголошень.
- [ ] Для складних форм передбачено доступний список помилок.

### Технічна надійність

- [ ] Валідація працює для всіх необхідних полів.
- [ ] Серверні помилки перетворюються на зрозумілі повідомлення.
- [ ] Технічні деталі не розкриваються користувачеві без потреби.
- [ ] Після повторної спроби стан інтерфейсу оновлюється.
- [ ] Обробляються помилки мережі та тайм-аути.
- [ ] Введені дані зберігаються відповідно до логіки продукту.

## 19. Рівні знань

### Core — базовий рівень

- Розуміти, що таке error message.
- Розрізняти помилки введення та системні помилки.
- Знати різницю між inline error і form-level error.
- Формулювати короткі й зрозумілі повідомлення.
- Розуміти, чому повідомлення має пояснювати проблему.

### Junior — практичний рівень

- Проєктувати поля з error states.
- Визначати, коли показувати повідомлення про помилку.
- Створювати тексти для required, format, length і range errors.
- Пов'язувати повідомлення з полями.
- Враховувати клавіатурну навігацію та скринрідери.
- Проєктувати загальні повідомлення про помилки форми.
- Передбачати сценарії виправлення даних.

### Middle — системний рівень

- Розробляти узгоджену систему повідомлень у продукті.
- Створювати багаторазові компоненти error states.
- Узгоджувати тексти повідомлень із правилами валідації.
- Проєктувати обробку помилок у багатокрокових формах.
- Враховувати локалізацію та різну довжину повідомлень.
- Розробляти доступні сценарії відновлення.
- Узгоджувати поведінку frontend і backend.

### Senior — експертний рівень

- Визначати загальні принципи обробки помилок у продукті.
- Балансувати точність повідомлення, безпеку й зрозумілість.
- Аналізувати типові помилки користувачів.
- Визначати пріоритети для критичних і некритичних проблем.
- Проєктувати поведінку складних систем і багатокрокових процесів.
- Забезпечувати послідовність повідомлень у дизайн-системі.
- Перевіряти якість сценаріїв відновлення за реальними користувацькими ситуаціями.

## 20. Питання для самоперевірки

1. Що таке error message?
2. Чим error message відрізняється від error state?
3. Що таке inline error?
4. Коли потрібне загальне повідомлення про помилку форми?
5. Які характеристики має хороше повідомлення про помилку?
6. Чому повідомлення «Щось пішло не так» часто недостатнє?
7. Коли потрібно показувати помилку: під час введення, після виходу з поля чи під час відправлення?
8. Чому не можна покладатися лише на червоний колір?
9. Як пов'язати повідомлення про помилку з полем у HTML?
10. Для чого використовують `aria-invalid`?
11. Для чого використовують `aria-describedby`?
12. Як поводитися з помилками, які виникають на сервері?
13. Чому не можна показувати успіх до завершення операції?
14. Як допомогти користувачеві відновити роботу після помилки?
15. Чим помилка валідації відрізняється від системної помилки?
16. Чому потрібно зберігати введені дані після помилки?
17. Як показувати помилки в довгих формах?
18. Чому не варто розкривати технічні деталі сервера?
19. Як перевірити доступність повідомлень про помилки?
20. Як зрозуміти, що повідомлення справді допомагає користувачеві?

## 21. Мінішпаргалка

| Ситуація | Рішення |
|---|---|
| Обов'язкове поле порожнє | «Введіть ім'я» |
| Некоректна електронна адреса | «Введіть коректну електронну адресу» |
| Значення поза діапазоном | «Введіть число від 1 до 35» |
| Паролі не збігаються | «Паролі не збігаються. Перевірте обидва поля» |
| Помилка стосується одного поля | Використовуй inline error |
| Помилка стосується всієї форми | Використовуй form-level error |
| Не вдалося завантажити дані | Повідом про проблему й запропонуй повторити спробу, якщо можливо |
| Користувач виправив значення | Повторно перевір поле та онови повідомлення |
| Помилка позначена лише кольором | Додай текстове пояснення |
| Повідомлення незрозуміле | Назви конкретну проблему та наступний крок |
| Помилка виникла на сервері | Покажи зрозумілий текст без зайвих технічних деталей |
| Дані ще не збережені | Не повідомляй про успіх до підтвердження операції |
| Форма має багато помилок | Покажи доступний список помилок і допоможи знайти відповідні поля |
| Користувач не може продовжити | Передбач сценарій відновлення |

## 22. Головний принцип

**Хороше повідомлення про помилку пояснює проблему, зберігає довіру та допомагає користувачеві зробити наступний крок.**

Під час проєктування інтерфейсу важливо думати не лише про те, як виглядає помилка, а й про те:

- коли вона з'являється;
- що саме повідомляє;
- чи зрозуміло її причину;
- як користувач може виправити ситуацію;
- чи зберігаються його дані;
- чи доступне повідомлення всім користувачам;
- чи відповідає текст реальному стану системи.

Найкращий дизайн помилок не приховує проблем і не звинувачує користувача. Він допомагає зрозуміти ситуацію, виправити її та продовжити роботу з мінімальними зусиллями.
