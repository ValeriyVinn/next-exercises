# 01. Semantic HTML

Semantic HTML (семантичний HTML) — це підхід до написання HTML, за якого елементи вибираються відповідно до їхнього змісту, призначення та ролі на сторінці.

Семантична розмітка допомагає браузерам, пошуковим системам, допоміжним технологіям і розробникам правильно розуміти структуру вебсторінки.

Semantic HTML є однією з основ accessibility (доступності вебінтерфейсів), оскільки програми читання з екрана використовують семантику HTML для визначення заголовків, навігації, посилань, кнопок, форм та інших елементів інтерфейсу.

Semantic HTML використовується, коли потрібно:

- визначити структуру вебсторінки;
- позначити заголовки та текстові розділи;
- відокремити основну навігацію від вмісту;
- позначити основний вміст сторінки;
- створити доступні кнопки, посилання та форми;
- забезпечити зрозумілу структуру для screen readers;
- зробити HTML зрозумілішим для інших розробників;
- покращити індексацію сторінки пошуковими системами;
- зменшити кількість зайвих ARIA-атрибутів;
- створити інтерфейс, яким можна користуватися без миші.

## Що потрібно пам'ятати

• Semantic HTML — це використання HTML-елементів відповідно до їхнього призначення.

• Семантика допомагає браузеру та допоміжним технологіям визначати роль елемента.

• `<div>` і `<span>` самі по собі не передають спеціального змістового призначення.

• `<header>`, `<nav>`, `<main>`, `<section>`, `<article>`, `<aside>` і `<footer>` допомагають описати структуру сторінки.

• `<main>` позначає основний вміст сторінки. Зазвичай на сторінці має бути один видимий основний `main`-регіон.

• `<nav>` використовується для важливих блоків навігації, а не для будь-якої групи посилань.

• `<section>` позначає тематичний розділ. Зазвичай він має заголовок.

• `<article>` позначає самостійний, змістовно завершений фрагмент вмісту.

• `<aside>` використовується для додаткового або побічного вмісту, пов'язаного з основним.

• `<h1>`–`<h6>` визначають рівні заголовків, а не просто розмір тексту.

• Рівень заголовка потрібно вибирати за структурою документа, а не за зовнішнім виглядом.

• `<a>` використовується для переходу за посиланням.

• `<button>` використовується для виконання дії.

• Не потрібно замінювати нативні HTML-елементи елементами `<div>` або `<span>` без вагомої причини.

• Нативні HTML-елементи часто вже мають необхідну роль, поведінку та підтримку клавіатури.

• ARIA доповнює семантику HTML, але не замінює правильний вибір елементів.

• Атрибут `alt` допомагає передати текстову альтернативу змістовному зображенню.

• Атрибут `lang` допомагає браузерам і допоміжним технологіям визначати мову вмісту.

• Семантична розмітка покращує доступність, але сама по собі не гарантує повної accessibility.

• Потрібно перевіряти не лише HTML, а й клавіатурну навігацію, фокус, контраст, форми та поведінку компонентів.

# Що таке Accessibility

Accessibility (доступність) — це властивість вебсайту або застосунку, яка дозволяє якомога більшій кількості людей користуватися ним незалежно від особливостей зору, слуху, рухливості, когнітивних можливостей або способу взаємодії з пристроєм.

Доступний інтерфейс має бути зрозумілим і функціональним для людей, які використовують:

    mouse
    keyboard
    screen reader
    screen magnification
    voice control
    switch devices
    other assistive technologies

Наприклад, користувач може взаємодіяти з інтерфейсом за допомогою клавіатури, не використовуючи мишу.

Інший користувач може слухати вміст сторінки через screen reader.

Семантичний HTML допомагає обом користувачам розуміти структуру інтерфейсу.

# Accessibility (a11y)

Accessibility часто скорочують до `a11y`.

Літера `a`, одинадцять пропущених літер і літера `y` утворюють скорочення:

    a + 11 letters + y = a11y

Інші поширені терміни:

    UX       → User Experience
    UI       → User Interface
    a11y     → Accessibility
    AT       → Assistive Technology
    SR       → Screen Reader
    ARIA     → Accessible Rich Internet Applications

Accessibility є частиною якісного UI/UX-дизайну та веброзробки.

---

# Semantic HTML

Semantic HTML — це розмітка, у якій назва та призначення HTML-елемента відповідають його змісту.

Наприклад:

    <header>
        <h1>Моя бібліотека</h1>
    </header>

    <main>
        <section>
            <h2>Улюблені книги</h2>

            <p>Список книг для читання.</p>
        </section>
    </main>

    <footer>
        <p>© 2026 Моя бібліотека</p>
    </footer>

Тут кожен елемент має зрозуміле призначення:

    header   → вступний вміст сторінки або розділу
    h1       → заголовок сторінки
    main     → основний вміст
    section  → тематичний розділ
    h2       → заголовок розділу
    p        → абзац
    footer   → завершальний вміст сторінки або розділу

Браузер і допоміжні технології можуть використовувати цю структуру для навігації та інтерпретації сторінки.

---

# Semantic vs Non-Semantic HTML

## Semantic elements

Семантичні елементи мають визначене призначення.

Приклади:

    <header>
    <nav>
    <main>
    <section>
    <article>
    <aside>
    <footer>
    <button>
    <a>
    <form>
    <table>

Наприклад:

    <button type="button">
        Зберегти
    </button>

Елемент `<button>` повідомляє браузеру, що це кнопка.

Він також підтримує стандартну взаємодію з клавіатурою.

## Non-semantic elements

Найпоширеніші неспеціалізовані контейнерні елементи:

    <div>
    <span>

Приклад:

    <div class="card">
        <span class="card-title">Книга</span>
    </div>

`div` і `span` не визначають спеціального змістового призначення самі по собі.

Їх можна використовувати для групування елементів, стилізації та компонування інтерфейсу.

Проте якщо для задачі існує відповідний семантичний елемент, зазвичай краще використати його.

Наприклад:

    <!-- Менш семантичний варіант -->
    <div class="button" onclick="saveData()">
        Зберегти
    </div>

    <!-- Кращий варіант -->
    <button type="button">
        Зберегти
    </button>

Другий варіант має нативну семантику кнопки та стандартну клавіатурну поведінку.

# Чому Semantic HTML важливий

Семантичний HTML допомагає вирішувати кілька завдань одночасно.

## 1. Accessibility

Screen readers можуть визначати типи елементів і повідомляти користувачеві, де він перебуває.

Наприклад:

    <button>Відкрити меню</button>

Програма читання з екрана може визначити, що це кнопка, і повідомити її доступну назву.

## 2. Keyboard navigation

Нативні інтерактивні елементи зазвичай мають стандартну клавіатурну поведінку.

Наприклад:

    <a href="/books">
        Книги
    </a>

Посилання можна активувати за допомогою клавіатури.

## 3. Maintainability

Семантична розмітка полегшує читання HTML іншими розробниками.

Наприклад:

    <nav>
        <a href="/">Головна</a>
        <a href="/about">Про нас</a>
        <a href="/contacts">Контакти</a>
    </nav>

Призначення блоку зрозуміле без додаткових пояснень.

## 4. SEO

Пошукові системи можуть використовувати структуру HTML для кращого розуміння вмісту сторінки.

Однак семантичні елементи не гарантують вищих позицій у пошуку.

## 5. Native browser behavior

Нативні елементи вже мають багато вбудованих можливостей.

Наприклад:

    <button>
    <input>
    <select>
    <textarea>
    <details>
    <summary>

Вони можуть забезпечувати стандартну поведінку, доступність і взаємодію без додаткового JavaScript.

# HTML Document Structure

Типова структура HTML-документа:

    <!DOCTYPE html>
    <html lang="uk">
        <head>
            <meta charset="UTF-8">
            <meta
                name="viewport"
                content="width=device-width, initial-scale=1.0"
            >
            <title>Моя бібліотека</title>
        </head>

        <body>
            <header>
                <h1>Моя бібліотека</h1>
            </header>

            <nav aria-label="Головна навігація">
                <a href="/">Головна</a>
                <a href="/books">Книги</a>
            </nav>

            <main>
                <section>
                    <h2>Рекомендовані книги</h2>
                    <p>Добірка книг для читання.</p>
                </section>
            </main>

            <footer>
                <p>© 2026 Моя бібліотека</p>
            </footer>
        </body>
    </html>

Основні частини:

    <!DOCTYPE html> → режим сучасного HTML
    html            → кореневий елемент документа
    head            → метадані документа
    body            → видимий вміст сторінки
    header          → вступний вміст
    nav             → навігація
    main            → основний вміст
    section         → тематичний розділ
    footer          → завершальний вміст

---

# lang Attribute

Атрибут `lang` визначає мову документа або окремого фрагмента тексту.

Наприклад:

    <html lang="uk">
        ...
    </html>

Для англійської сторінки:

    <html lang="en">
        ...
    </html>

Для документа українською мовою з англійським фрагментом:

    <html lang="uk">
        <body>
            <p>Ласкаво просимо!</p>

            <p lang="en">
                Welcome to our website!
            </p>
        </body>
    </html>

Чому це важливо:

- screen readers можуть правильно вибирати вимову;
- браузери можуть коректніше обробляти текст;
- допоміжні технології можуть визначати мову окремих фрагментів;
- переклад та інші мовні інструменти можуть краще розуміти вміст.

Важливо:

    lang="uk"

позначає українську мову, а не країну перебування користувача.

---

# Header

`<header>` визначає вступний вміст сторінки або окремого розділу.

У ньому часто розташовують:

    logo
    site title
    introductory content
    search
    navigation-related content

Приклад:

    <header>
        <a href="/" aria-label="На головну">
            Моя бібліотека
        </a>

        <p>Книги для навчання та відпочинку</p>
    </header>

`header` не обов'язково є заголовком усієї сторінки.

Його можна використовувати і всередині `article` або `section`, якщо він є вступною частиною відповідного розділу.

---

# Nav

`<nav>` визначає блок важливої навігації.

Приклад:

    <nav aria-label="Головна навігація">
        <a href="/">Головна</a>
        <a href="/books">Книги</a>
        <a href="/contacts">Контакти</a>
    </nav>

Якщо на сторінці кілька навігаційних блоків, їх варто розрізняти за призначенням.

Наприклад:

    <nav aria-label="Головна навігація">
        ...
    </nav>

    <nav aria-label="Навігація в підвалі">
        ...
    </nav>

`aria-label` у цьому випадку надає навігаційному регіону доступну назву.

Не кожен набір посилань повинен бути всередині `nav`.

Наприклад, посилання в абзаці можуть залишатися звичайними посиланнями.

---

# Main

`<main>` позначає основний вміст документа.

Приклад:

    <body>
        <header>
            <h1>Онлайн-бібліотека</h1>
        </header>

        <nav aria-label="Головна навігація">
            <a href="/">Головна</a>
            <a href="/books">Книги</a>
        </nav>

        <main>
            <h2>Каталог книг</h2>
            <p>Знайдіть книгу для читання.</p>
        </main>

        <footer>
            <p>© 2026 Онлайн-бібліотека</p>
        </footer>
    </body>

`main` допомагає користувачам допоміжних технологій швидко переходити до основного вмісту.

Важливо:

- зазвичай на сторінці має бути один видимий основний `main`-регіон;
- `main` не повинен містити загальний вміст, який повторюється на всіх сторінках, наприклад глобальну навігацію;
- `main` не можна розміщувати всередині `header`, `footer`, `nav`, `article`, `aside` або `section`;
- для прихованих альтернативних областей існують окремі нюанси, але для звичайної сторінки достатньо одного `main`.

---

# Section

`<section>` позначає тематично об'єднаний розділ документа.

Приклад:

    <section>
        <h2>Популярні книги</h2>

        <p>
            Добірка найпопулярніших книг цього місяця.
        </p>
    </section>

Інший приклад:

    <section>
        <h2>Нові надходження</h2>

        <article>
            <h3>Книга про JavaScript</h3>
            <p>Основи мови JavaScript.</p>
        </article>

        <article>
            <h3>Книга про CSS</h3>
            <p>Основи стилізації вебсторінок.</p>
        </article>
    </section>

Зазвичай `section` повинен мати заголовок.

Не варто використовувати `section` лише для того, щоб отримати контейнер для CSS.

Якщо потрібне просте групування без окремого змістового розділу, можна використати `div`.

---

# Article

`<article>` позначає самостійний фрагмент вмісту, який може мати сенс окремо від решти сторінки.

Приклади:

    blog post
    news article
    forum post
    product review
    standalone comment

Приклад:

    <article>
        <h2>Як вивчати JavaScript</h2>

        <p>
            JavaScript дозволяє створювати
            інтерактивні вебінтерфейси.
        </p>

        <a href="/articles/javascript">
            Читати далі
        </a>
    </article>

Кілька статей:

    <section>
        <h2>Останні статті</h2>

        <article>
            <h3>Основи HTML</h3>
            <p>Вивчаємо структуру вебсторінки.</p>
        </article>

        <article>
            <h3>Основи CSS</h3>
            <p>Вивчаємо стилізацію елементів.</p>
        </article>
    </section>

Різниця:

    section  → тематичний розділ
    article  → самостійний матеріал

Ці елементи можна вкладати один в одного, якщо цього вимагає структура документа.

---

# Aside

`<aside>` використовується для додаткового або побічного вмісту, пов'язаного з основним.

Приклади:

    related articles
    sidebar
    additional information
    supplementary notes

Приклад:

    <main>
        <article>
            <h1>Основи JavaScript</h1>

            <p>
                JavaScript використовується
                для створення інтерактивних сайтів.
            </p>
        </article>

        <aside>
            <h2>Читайте також</h2>

            <a href="/html">
                Основи HTML
            </a>
        </aside>
    </main>

`aside` не обов'язково має бути бічною панеллю візуально.

Його семантичне значення залежить від зв'язку додаткового вмісту з основним матеріалом.

---

# Footer

`<footer>` визначає завершальний вміст сторінки або розділу.

У ньому часто розміщують:

    copyright
    contact information
    related links
    author information
    legal information

Приклад:

    <footer>
        <p>© 2026 Онлайн-бібліотека</p>

        <a href="/privacy">
            Політика конфіденційності
        </a>
    </footer>

`footer` може належати не лише всій сторінці, а й окремому `article` або іншому відповідному розділу.

---

# Header, Main, Footer — базова структура

Типовий шаблон:

    <body>
        <header>
            <h1>Навчальний портал</h1>
        </header>

        <nav aria-label="Головна навігація">
            <a href="/">Головна</a>
            <a href="/courses">Курси</a>
        </nav>

        <main>
            <h2>Наші курси</h2>

            <section>
                <h3>Frontend</h3>
                <p>HTML, CSS, JavaScript.</p>
            </section>

            <section>
                <h3>Backend</h3>
                <p>Node.js та бази даних.</p>
            </section>
        </main>

        <footer>
            <p>© 2026 Навчальний портал</p>
        </footer>
    </body>

Зверни увагу:

- заголовок сайту розташований у `header`;
- навігація винесена в `nav`;
- основний вміст розташований у `main`;
- тематичні групи позначені через `section`;
- завершальна інформація розташована у `footer`.

# Heading Hierarchy

Заголовки HTML визначають ієрархію вмісту.

Доступні рівні:

    <h1>
    <h2>
    <h3>
    <h4>
    <h5>
    <h6>

`h1` — найвищий рівень заголовка.

`h6` — найнижчий рівень заголовка.

Приклад:

    <main>
        <h1>Курси програмування</h1>

        <section>
            <h2>Frontend</h2>

            <h3>HTML</h3>
            <p>Основи структури сторінок.</p>

            <h3>CSS</h3>
            <p>Основи оформлення сторінок.</p>
        </section>

        <section>
            <h2>Backend</h2>

            <h3>Node.js</h3>
            <p>Основи серверної розробки.</p>
        </section>
    </main>

Структура:

    h1 Курси програмування
        ↓
        h2 Frontend
            ↓
            h3 HTML
            h3 CSS
        ↓
        h2 Backend
            ↓
            h3 Node.js

Заголовки допомагають користувачам:

- зрозуміти структуру документа;
- швидко знайти потрібний розділ;
- переміщатися між розділами за допомогою screen reader;
- переглядати сторінку без послідовного читання всього тексту.

## Правила заголовків

• Вибирай рівень заголовка відповідно до ієрархії змісту.

• Не використовуй `h1`, `h2` або `h3` лише через бажаний розмір шрифту.

• Не пропускай рівні без потреби.

• Підрозділ `h3` зазвичай повинен належати до розділу `h2`.

• Кожен заголовок має описувати вміст відповідного розділу.

• Кілька `h1` технічно дозволені HTML, але для зрозумілої структури сторінки зазвичай зручно мати один головний заголовок документа.

• Не потрібно змінювати рівень заголовка тільки через те, що він розташований усередині `section` або `article`.

• Візуальний розмір заголовків краще змінювати за допомогою CSS.

Приклад:

    <h2 class="section-title">
        Наші послуги
    </h2>

    <style>
        .section-title {
            font-size: 2rem;
        }
    </style>

Семантика визначається елементом `h2`, а не його розміром.

# Paragraph

`<p>` визначає абзац тексту.

Приклад:

    <p>
        HTML визначає структуру вебсторінки.
    </p>

Не потрібно використовувати `div` для кожного звичайного текстового абзацу.

Менш семантично:

    <div>
        HTML визначає структуру вебсторінки.
    </div>

Краще:

    <p>
        HTML визначає структуру вебсторінки.
    </p>

Для заголовків використовуй `h1`–`h6`, для абзаців — `p`, для списків — відповідні спискові елементи.

# Lists

HTML має кілька типів списків.

## Unordered list

`<ul>` — маркований список.

    <ul>
        <li>HTML</li>
        <li>CSS</li>
        <li>JavaScript</li>
    </ul>

Використовується, коли порядок елементів не є суттєвим.

## Ordered list

`<ol>` — нумерований список.

    <ol>
        <li>Створити HTML.</li>
        <li>Додати CSS.</li>
        <li>Підключити JavaScript.</li>
    </ol>

Використовується, коли важливий порядок кроків.

## Description list

`<dl>` — список термінів та їхніх описів.

    <dl>
        <dt>HTML</dt>
        <dd>Мова розмітки вебсторінок.</dd>

        <dt>CSS</dt>
        <dd>Мова стилізації вебсторінок.</dd>
    </dl>

Списки допомагають передавати структуру та взаємозв'язки між елементами.

---

# Links

`<a>` — елемент для створення посилань.

Приклад:

    <a href="/courses">
        Переглянути курси
    </a>

Посилання використовуються для переходу:

    to another page
    to another website
    to a section of the current page
    to an email address
    to another supported destination

## Meaningful link text

Текст посилання має пояснювати, куди воно веде або яку інформацію відкриває.

Поганий приклад:

    <a href="/courses">
        Натисніть тут
    </a>

Кращий приклад:

    <a href="/courses">
        Переглянути курси програмування
    </a>

Screen reader може дозволяти користувачеві переглядати список усіх посилань на сторінці окремо від навколишнього тексту.

Тому назва посилання повинна залишатися зрозумілою навіть без контексту абзацу.

## Посилання із зображенням

Якщо зображення є єдиним вмістом посилання, його `alt` може визначати доступну назву посилання.

    <a href="/home">
        <img src="logo.svg" alt="На головну">
    </a>

Якщо зображення та текст разом утворюють одне посилання, уникай зайвого дублювання доступної назви.

## Відмінність між посиланням і кнопкою

    <a href="/profile">
        Відкрити профіль
    </a>

    <button type="button">
        Відкрити меню
    </button>

Правило:

    navigation → a
    action     → button

Посилання переміщує користувача до ресурсу або адреси.

Кнопка виконує дію в поточному інтерфейсі.

Не використовуй `<a href="#">` замість кнопки для дій.

---

# Button Semantics

`<button>` — нативний елемент для інтерактивних дій.

Приклад:

    <button type="button">
        Відкрити меню
    </button>

Кнопка за замовчуванням підтримує:

    keyboard activation
    focusability
    button role
    accessible name

Для кнопки всередині форми важливо визначати тип.

## type="button"

    <button type="button">
        Відкрити меню
    </button>

Не запускає стандартне надсилання форми.

## type="submit"

    <button type="submit">
        Надіслати
    </button>

Надсилає форму, до якої належить кнопка.

## type="reset"

    <button type="reset">
        Скинути
    </button>

Скидає значення полів форми до початкових значень.

Важливо:

Якщо атрибут `type` не вказано, кнопка всередині форми зазвичай поводиться як кнопка надсилання.

Тому для кнопок, які не повинні надсилати форму, краще явно вказувати:

    type="button"

## Чому не варто створювати кнопку через div

Поганий приклад:

    <div onclick="saveData()">
        Зберегти
    </div>

Такий елемент сам по собі не має нативної семантики кнопки, стандартної активації клавіатурою чи відповідної поведінки фокуса.

Кращий варіант:

    <button type="button" onclick="saveData()">
        Зберегти
    </button>

Якщо використовуєш React, принцип той самий:

    function SaveButton() {
        function handleSave() {
            console.log("Saved");
        }

        return (
            <button
                type="button"
                onClick={handleSave}
            >
                Зберегти
            </button>
        );
    }

# Images and alt

Для зображень використовується елемент `<img>`.

Приклад:

    <img
        src="/images/library.jpg"
        alt="Книжкові полиці в бібліотеці"
    >

Атрибут `alt` надає текстову альтернативу зображенню.

Цей текст може використовуватися screen readers, коли користувач не бачить зображення.

## Змістовне зображення

    <img
        src="/images/book.jpg"
        alt="Книга з відкритими сторінками на столі"
    >

Текст описує важливу інформацію зображення.

## Декоративне зображення

    <img
        src="/images/decorative-line.svg"
        alt=""
    >

Порожній `alt` означає, що зображення є декоративним і не повинно створювати зайвий текстовий вміст для допоміжних технологій.

## Зображення як посилання

    <a href="/books">
        <img
            src="/images/books.jpg"
            alt="Переглянути каталог книг"
        >
    </a>

Текст альтернативи допомагає зрозуміти призначення посилання.

## Не використовуй назву файлу як alt

Погано:

    <img
        src="/images/book-01.jpg"
        alt="book-01.jpg"
    >

Краще:

    <img
        src="/images/book-01.jpg"
        alt="Відкрита книга на дерев'яному столі"
    >

## Не кожне зображення потребує довгого опису

Альтернативний текст залежить від контексту та призначення зображення.

Якщо зображення лише декорує сторінку, використовуй порожній `alt`.

Якщо зображення передає важливу інформацію, опиши цю інформацію.

Якщо складне зображення містить графік або діаграму, може знадобитися докладне пояснення у звичайному тексті поруч.

# Figure and Figcaption

`<figure>` використовується для самостійного вмісту, наприклад ілюстрації, фотографії, схеми або діаграми.

`<figcaption>` надає цьому вмісту підпис.

Приклад:

    <figure>
        <img
            src="/images/library.jpg"
            alt="Книжкові полиці у читальній залі"
        >

        <figcaption>
            Читальна зала міської бібліотеки.
        </figcaption>
    </figure>

Ці елементи допомагають пов'язати зображення з його поясненням.

Важливо:

`figcaption` не замінює `alt`.

    alt         → текстова альтернатива зображення
    figcaption  → підпис або пояснення вмісту figure

У деяких випадках підпис і `alt` можуть передавати частково схожу інформацію, але їхнє призначення відрізняється.

---

# Semantic Forms

Форми мають використовувати відповідні нативні HTML-елементи.

Основні елементи:

    form
    label
    input
    textarea
    select
    option
    button
    fieldset
    legend

Приклад:

    <form action="/subscribe" method="post">
        <div>
            <label for="email">
                Електронна пошта
            </label>

            <input
                id="email"
                name="email"
                type="email"
                autocomplete="email"
                required
            >
        </div>

        <button type="submit">
            Підписатися
        </button>
    </form>

Тут:

    form         → форма
    label        → назва поля
    input        → поле введення
    id           → ідентифікатор елемента
    for          → зв'язок label з полем
    name         → ім'я поля для передавання даних
    type="email" → поле для електронної пошти
    required     → обов'язкове поле
    button       → надсилання форми

Правильна семантика форми допомагає користувачам розуміти, які дані потрібно ввести.

Детальніше форми розглядаються у розділі:

    06-form-accessibility

---

# Label

`<label>` визначає назву або пояснення поля форми.

Приклад:

    <label for="username">
        Ім'я користувача
    </label>

    <input
        id="username"
        name="username"
        type="text"
    >

Атрибут `for` має відповідати значенню `id` відповідного поля.

Альтернативний варіант — розмістити поле всередині `label`:

    <label>
        Ім'я користувача

        <input
            name="username"
            type="text"
        >
    </label>

Не варто покладатися лише на placeholder як на назву поля.

Поганий приклад:

    <input
        type="email"
        placeholder="Електронна пошта"
    >

Кращий варіант:

    <label for="email">
        Електронна пошта
    </label>

    <input
        id="email"
        name="email"
        type="email"
        placeholder="name@example.com"
    >

Label залишається зрозумілим навіть після введення значення, коли placeholder може зникнути.

---

# Fieldset and Legend

`<fieldset>` групує пов'язані поля форми.

`<legend>` визначає назву цієї групи.

Приклад:

    <fieldset>
        <legend>Спосіб отримання новин</legend>

        <label>
            <input
                type="radio"
                name="news"
                value="email"
            >
            Електронною поштою
        </label>

        <label>
            <input
                type="radio"
                name="news"
                value="sms"
            >
            SMS
        </label>
    </fieldset>

Це особливо корисно для:

    radio buttons
    related checkboxes
    grouped form controls

`fieldset` і `legend` допомагають передавати контекст групи полів користувачам допоміжних технологій.

---

# Tables

Таблиці використовуються для представлення табличних даних, а не для компонування всієї сторінки.

Основні елементи:

    table
    caption
    thead
    tbody
    tfoot
    tr
    th
    td

Приклад:

    <table>
        <caption>
            Оцінки студентів
        </caption>

        <thead>
            <tr>
                <th scope="col">Студент</th>
                <th scope="col">Інформатика</th>
                <th scope="col">Математика</th>
            </tr>
        </thead>

        <tbody>
            <tr>
                <th scope="row">Олена</th>
                <td>95</td>
                <td>88</td>
            </tr>

            <tr>
                <th scope="row">Андрій</th>
                <td>90</td>
                <td>92</td>
            </tr>
        </tbody>
    </table>

Призначення:

    caption  → назва таблиці
    thead    → група заголовків
    tbody    → основні рядки даних
    tr       → рядок
    th       → заголовкова комірка
    td       → комірка з даними
    scope    → напрямок зв'язку заголовка з даними

`scope="col"` визначає заголовок стовпця.

`scope="row"` визначає заголовок рядка.

Для складних таблиць може знадобитися додаткове явне пов'язування заголовків і комірок.

Семантична структура таблиці допомагає screen readers правильно визначати взаємозв'язок між заголовками та значеннями.

---

# Details and Summary

`<details>` створює інтерактивний блок, який можна розгортати та згортати.

`<summary>` визначає видимий заголовок цього блоку.

Приклад:

    <details>
        <summary>
            Що таке HTML?
        </summary>

        <p>
            HTML — мова розмітки вебсторінок.
        </p>
    </details>

Ці елементи мають нативну інтерактивну поведінку.

Вони можуть бути корисними для:

    FAQ
    additional information
    expandable content
    supplementary explanations

Не потрібно створювати простий розгортальний блок на основі `div`, якщо нативного `details` достатньо.

Для складних інтерактивних компонентів, наприклад меню або діалогового вікна, можуть знадобитися інші семантичні елементи та керування станом.

---

# Landmarks

Landmarks — це важливі області сторінки, які допомагають користувачам допоміжних технологій швидко переходити між основними частинами документа.

Нативні HTML-елементи можуть створювати відповідні landmark-регіони.

Приклади:

    <header>
    <nav>
    <main>
    <aside>
    <footer>

Типові відповідності:

    header сторінки  → banner
    nav              → navigation
    main             → main
    aside            → complementary
    footer сторінки  → contentinfo

Ці відповідності залежать від контексту та правил HTML Accessibility API Mappings.

Наприклад, `header` усередині `article` не обов'язково створює landmark `banner`.

А `footer` усередині окремого розділу не обов'язково створює landmark `contentinfo`.

## Навіщо потрібні landmarks

Користувач screen reader може переходити безпосередньо до:

    main content
    navigation
    complementary content
    page header
    page footer

Це особливо корисно на великих сторінках із повторюваними елементами.

## Приклад

    <body>
        <header>
            <h1>Навчальний портал</h1>
        </header>

        <nav aria-label="Головна навігація">
            ...
        </nav>

        <main>
            ...
        </main>

        <aside>
            ...
        </aside>

        <footer>
            ...
        </footer>
    </body>

Правильна структура допомагає користувачам зрозуміти, де знаходиться основний вміст.

---

# Accessible Name

Accessible name — це назва, яку допоміжні технології використовують для ідентифікації інтерактивного елемента або іншого об'єкта інтерфейсу.

Наприклад, для кнопки:

    <button type="button">
        Зберегти зміни
    </button>

Доступна назва:

    Зберегти зміни

Для поля форми:

    <label for="email">
        Електронна пошта
    </label>

    <input
        id="email"
        type="email"
    >

Доступна назва поля:

    Електронна пошта

Назва допомагає зрозуміти призначення елемента без необхідності бачити його зовнішній вигляд.

## Назва кнопки з іконкою

Поганий приклад:

    <button type="button">
        <svg>
            ...
        </svg>
    </button>

Якщо іконка не має текстового представлення для допоміжних технологій, кнопка може не мати зрозумілої доступної назви.

Кращий варіант:

    <button
        type="button"
        aria-label="Закрити вікно"
    >
        <svg aria-hidden="true">
            ...
        </svg>
    </button>

Тут:

    aria-label="Закрити вікно"
        → accessible name кнопки

    aria-hidden="true"
        → приховує декоративну SVG-іконку від accessibility tree

Для звичайної кнопки з видимим текстом `aria-label` зазвичай не потрібний.

---

# Accessible Description

Accessible description — додатковий текст, який пояснює елемент або надає більше контексту.

Наприклад:

    <label for="password">
        Пароль
    </label>

    <input
        id="password"
        name="password"
        type="password"
        aria-describedby="password-help"
    >

    <p id="password-help">
        Пароль має містити щонайменше 12 символів.
    </p>

Тут:

    label
        → accessible name

    password-help
        → accessible description

`aria-describedby` пов'язує поле з текстом, який його пояснює.

Це корисно для:

    instructions
    hints
    validation messages
    supplementary information

Для помилок форми важливо не лише вивести текст, а й зробити так, щоб користувач міг зрозуміти, до якого поля він належить.

---

# Native Semantics

Native semantics — це семантика та стандартна поведінка, які HTML-елементи мають від початку.

Наприклад:

    <button>Зберегти</button>

Браузер уже знає, що це кнопка.

Натомість:

    <div role="button" tabindex="0">
        Зберегти
    </div>

потребує додаткової реалізації поведінки.

Для другого варіанта можуть знадобитися:

    keyboard focus
    Enter activation
    Space activation
    disabled behavior
    focus styling
    event handling

Навіть якщо додати `role="button"`, браузер не перетворить `div` на повноцінну нативну кнопку.

Тому основне правило:

    Prefer native HTML elements.

Використовуй нативний HTML, якщо він відповідає задачі.

ARIA та JavaScript додавай лише тоді, коли це дійсно потрібно.

---

# ARIA

ARIA означає Accessible Rich Internet Applications.

Це набір атрибутів, які допомагають описувати ролі, стани, властивості та зв'язки елементів інтерфейсу для допоміжних технологій.

Приклади:

    role
    aria-label
    aria-labelledby
    aria-describedby
    aria-hidden
    aria-expanded
    aria-controls
    aria-current
    aria-live
    aria-invalid
    aria-required

## Приклад aria-label

    <button
        type="button"
        aria-label="Закрити меню"
    >
        ×
    </button>

## Приклад aria-expanded

    <button
        type="button"
        aria-expanded="false"
        aria-controls="menu"
    >
        Відкрити меню
    </button>

`aria-expanded` повідомляє поточний стан розгортання.

Але атрибут потрібно оновлювати відповідно до реального стану компонента.

## Основне правило ARIA

    No ARIA is better than bad ARIA.

Це означає, що неправильне застосування ARIA може зробити інтерфейс менш доступним, ніж використання простого нативного HTML.

Порядок пріоритетів:

    1. Використати відповідний нативний HTML.
    2. Перевірити, чи достатньо його вбудованої семантики.
    3. Додати ARIA, якщо потрібна додаткова інформація.
    4. Реалізувати необхідну клавіатурну поведінку.
    5. Перевірити поведінку з допоміжними технологіями.

ARIA не замінює:

    semantic HTML
    keyboard support
    focus management
    visible instructions
    accessible interaction
    proper form labels

---

# Implicit Role vs Explicit Role

## Implicit role

Implicit role — роль, яка визначається самим HTML-елементом.

Наприклад:

    <button>Зберегти</button>

Браузер визначає елемент як кнопку.

Інші приклади:

    <nav>      → navigation
    <main>     → main
    <button>   → button
    <a href="/">...</a> → link

## Explicit role

Explicit role — роль, яку явно вказують через атрибут `role`.

Наприклад:

    <div role="button" tabindex="0">
        Зберегти
    </div>

Але роль не створює всю необхідну поведінку.

Для такого елемента розробник повинен забезпечити коректну взаємодію з клавіатурою та інші необхідні властивості.

Тому краще:

    <button type="button">
        Зберегти
    </button>

Не додавай `role="button"` до справжньої кнопки без потреби.

    <button role="button">
        Зберегти
    </button>

У цьому випадку роль уже забезпечена самим HTML-елементом.

---

# HTML Semantics vs CSS Appearance

Зовнішній вигляд елемента не визначає його семантичну роль.

Наприклад:

    <h2 class="small-heading">
        Наші курси
    </h2>

Можна зробити заголовок невеликим за допомогою CSS.

А можна створити великий текст через `div`:

    <div class="large-title">
        Наші курси
    </div>

Але другий елемент не стає заголовком автоматично.

Важливо розрізняти:

    HTML → structure and meaning
    CSS  → presentation
    JS   → behavior and interaction

Це не абсолютне розділення всіх можливостей технологій, але корисна базова модель.

У контексті accessibility правильна семантика HTML має бути основою інтерфейсу.

---

# Семантичний HTML у картках

Розглянемо картку книги.

Неоптимальний варіант:

    <div class="card">
        <div class="title">
            Основи JavaScript
        </div>

        <div class="description">
            Книга для початківців.
        </div>

        <div class="button">
            Детальніше
        </div>
    </div>

Проблеми:

    title       → не позначений як заголовок
    description → не позначений як абзац
    button      → не є справжньою кнопкою або посиланням

Кращий варіант:

    <article class="book-card">
        <h2>Основи JavaScript</h2>

        <p>
            Книга для початківців.
        </p>

        <a href="/books/javascript">
            Детальніше про книгу
        </a>
    </article>

Якщо картка є самостійним матеріалом, `article` може бути доречним.

Якщо це лише група елементів для компонування, можна використати `div`.

Вибір залежить від змісту, а не від дизайну картки.

---

# Семантичний HTML для навігаційного меню

Приклад доступної базової навігації:

    <header>
        <a href="/" aria-label="Навчальний портал — головна">
            Навчальний портал
        </a>

        <nav aria-label="Головна навігація">
            <ul>
                <li>
                    <a href="/courses">
                        Курси
                    </a>
                </li>

                <li>
                    <a href="/articles">
                        Статті
                    </a>
                </li>

                <li>
                    <a href="/contacts">
                        Контакти
                    </a>
                </li>
            </ul>
        </nav>
    </header>

Список `ul` доречний, коли посилання утворюють групу навігаційних пунктів.

Водночас не кожне меню обов'язково повинно використовувати однакову HTML-структуру.

Важливо забезпечити зрозуміле призначення посилань і доступну навігацію.

Для позначення поточної сторінки можна використати:

    <a href="/courses" aria-current="page">
        Курси
    </a>

`aria-current="page"` повідомляє допоміжним технологіям, що це посилання відповідає поточній сторінці.

---

# Семантичний HTML у React

У React діють ті самі правила семантичного HTML.

Приклад компонента:

    export default function CoursesPage() {
        return (
            <>
                <header>
                    <h1>Навчальні курси</h1>
                </header>

                <nav aria-label="Головна навігація">
                    <a href="/">Головна</a>
                    <a href="/courses">Курси</a>
                </nav>

                <main>
                    <section>
                        <h2>Frontend</h2>

                        <article>
                            <h3>HTML та CSS</h3>

                            <p>
                                Основи створення вебсторінок.
                            </p>

                            <a href="/courses/html-css">
                                Переглянути курс
                            </a>
                        </article>
                    </section>
                </main>

                <footer>
                    <p>© 2026 Навчальний портал</p>
                </footer>
            </>
        );
    }

У JSX:

- HTML-подібна структура зберігає семантичне значення елементів;
- `class` записується як `className`;
- обробники подій записуються як `onClick`, `onChange` тощо;
- атрибути доступності, наприклад `aria-label`, використовуються у звичайному вигляді.

Не потрібно створювати окремий компонент для кожного HTML-елемента.

Компоненти варто виділяти тоді, коли це покращує повторне використання, структуру або підтримку коду.

---

# Семантичний HTML у Next.js

У Next.js App Router сторінки також повинні мати правильну семантичну структуру.

Наприклад:

    export default function Page() {
        return (
            <main>
                <h1>Наші курси</h1>

                <section>
                    <h2>Frontend</h2>
                    <p>HTML, CSS та JavaScript.</p>
                </section>

                <section>
                    <h2>Backend</h2>
                    <p>Node.js та бази даних.</p>
                </section>
            </main>
        );
    }

Якщо глобальний `layout` уже містить спільні `header`, `nav` і `footer`, сторінка може містити лише власний основний вміст.

Важливо не створювати випадково кілька видимих `main`-регіонів через вкладені компоненти.

Наприклад:

    RootLayout
        ├── Header
        ├── Navigation
        ├── Main
        │   └── Page
        └── Footer

У такій структурі `Page` зазвичай не повинна додавати ще один `main` усередину основного `main`.

# Document Title

Елемент `<title>` визначає назву документа.

Приклад:

    <head>
        <title>Курси JavaScript | Навчальний портал</title>
    </head>

Назва документа важлива для:

    browser tab
    bookmarks
    browser history
    assistive technologies
    search results in some contexts

Кожна сторінка повинна мати зрозумілу назву, яка відповідає її вмісту.

У Next.js назву можна визначити через Metadata API.

Наприклад:

    export const metadata = {
        title: "Курси JavaScript",
        description: "Навчальні матеріали з JavaScript",
    };

`title` і заголовок `h1` — різні речі.

    title → назва документа
    h1    → головний заголовок вмісту сторінки

Вони можуть містити схожий текст, але виконують різні функції.

# Hidden Content and Accessibility

Не весь вміст, який візуально прихований, однаково обробляється допоміжними технологіями.

Наприклад:

    .visually-hidden {
        position: absolute;
        width: 1px;
        height: 1px;
        padding: 0;
        margin: -1px;
        overflow: hidden;
        clip: rect(0, 0, 0, 0);
        white-space: nowrap;
        border: 0;
    }

Такий клас часто використовують для тексту, який має бути доступним допоміжним технологіям, але не повинен бути видимим на екрані.

Приклад:

    <button type="button">
        <svg aria-hidden="true">
            ...
        </svg>

        <span class="visually-hidden">
            Відкрити меню
        </span>
    </button>

Це дає кнопці текстову назву, яку можуть використовувати допоміжні технології.

Важливо:

    display: none
    visibility: hidden
    hidden

зазвичай приховують елемент і від допоміжних технологій.

Не використовуй такі способи, якщо вміст повинен залишатися доступним screen readers.

Також не потрібно приховувати весь змістовний текст лише для того, щоб зробити його доступним програмам читання з екрана. Основна інформація повинна бути зрозумілою всім користувачам.

---

# Semantic HTML and Keyboard Accessibility

Семантичний HTML полегшує роботу з клавіатурою.

Нативні інтерактивні елементи зазвичай мають стандартну підтримку фокуса й активації.

Наприклад:

    <a href="/books">
        Книги
    </a>

    <button type="button">
        Відкрити меню
    </button>

Користувач може переходити між такими елементами за допомогою `Tab` та активувати їх відповідними клавішами.

Типова поведінка:

    Tab
        → перейти до наступного доступного елемента

    Shift + Tab
        → перейти до попереднього елемента

    Enter
        → активувати посилання або кнопку

    Space
        → активувати кнопку

Точна поведінка залежить від типу елемента та браузера.

Не всі інтерактивні елементи мають однакову поведінку клавіш.

Наприклад, для кнопок стандартно підтримуються `Enter` і `Space`, а посилання зазвичай активуються клавішею `Enter`.

Для складних компонентів, таких як вкладки, меню або діалогові вікна, потрібне додаткове дотримання відповідних interaction patterns.

Детальніше клавіатурна навігація розглядається у розділі:

    04-keyboard-navigation

# Semantic HTML and Screen Readers

Screen reader — це допоміжна технологія, яка озвучує або іншим способом представляє вміст екрана.

Приклади screen readers:

    NVDA
    JAWS
    VoiceOver
    TalkBack

Screen readers використовують інформацію про:

    element role
    accessible name
    accessible description
    states
    properties
    document structure

Наприклад:

    <h2>Популярні книги</h2>

Програма читання з екрана може визначити, що це заголовок другого рівня.

Для кнопки:

    <button type="button">
        Додати книгу
    </button>

Вона може повідомити назву та роль кнопки.

Для навігації:

    <nav aria-label="Головна навігація">
        ...
    </nav>

Користувач може розпізнати навігаційний регіон і його призначення.

Семантичний HTML дозволяє screen reader надавати користувачеві більше інформації, ніж просто послідовність текстових фрагментів.

# Типові помилки Semantic HTML

## Помилка 1 — використовувати div замість заголовка

Погано:

    <div class="title">
        Каталог книг
    </div>

Краще:

    <h1>Каталог книг</h1>

Якщо текст є заголовком сторінки, познач його відповідним елементом.

## Помилка 2 — використовувати div замість кнопки

Погано:

    <div onclick="openMenu()">
        Відкрити меню
    </div>

Краще:

    <button type="button">
        Відкрити меню
    </button>

## Помилка 3 — використовувати посилання для дії

Погано:

    <a href="#" onclick="saveData()">
        Зберегти
    </a>

Краще:

    <button type="button">
        Зберегти
    </button>

Якщо елемент виконує дію, використовуй кнопку.

## Помилка 4 — використовувати кнопку для навігації

Неоптимально:

    <button type="button">
        Відкрити сторінку курсів
    </button>

Якщо потрібно перейти на іншу сторінку, краще:

    <a href="/courses">
        Відкрити сторінку курсів
    </a>

## Помилка 5 — використовувати заголовки лише для стилізації

Погано:

    <h3>Цей текст просто великий</h3>

Якщо текст не є заголовком відповідного рівня, вибери семантично правильний елемент і стилізуй його через CSS.

## Помилка 6 — пропускати рівні заголовків без потреби

Неоптимально:

    <h1>Книги</h1>
    <h4>Нові надходження</h4>

Краще, якщо це підрозділ першого рівня:

    <h1>Книги</h1>
    <h2>Нові надходження</h2>

## Помилка 7 — створювати кілька main

Неоптимально:

    <main>
        <main>
            <h1>Каталог</h1>
        </main>
    </main>

Краще:

    <main>
        <h1>Каталог</h1>
    </main>

## Помилка 8 — використовувати section лише як контейнер

Неоптимально:

    <section class="container">
        <div>...</div>
    </section>

Якщо елемент не представляє окремого тематичного розділу, `div` може бути доречнішим.

## Помилка 9 — використовувати порожній текст посилання

Погано:

    <a href="/courses"></a>

Краще:

    <a href="/courses">
        Переглянути курси
    </a>

Якщо посилання містить тільки зображення або іконку, воно все одно повинно мати доступну назву.

## Помилка 10 — не додавати alt до зображень

Погано:

    <img src="/images/book.jpg">

Краще для змістовного зображення:

    <img
        src="/images/book.jpg"
        alt="Відкрита книга на столі"
    >

Краще для декоративного зображення:

    <img
        src="/images/decoration.svg"
        alt=""
    >

## Помилка 11 — використовувати placeholder замість label

Погано:

    <input
        type="email"
        placeholder="Електронна пошта"
    >

Краще:

    <label for="email">
        Електронна пошта
    </label>

    <input
        id="email"
        name="email"
        type="email"
    >

## Помилка 12 — додавати ARIA без потреби

Неоптимально:

    <button role="button">
        Зберегти
    </button>

Краще:

    <button type="button">
        Зберегти
    </button>

Нативна кнопка вже має відповідну роль.

## Помилка 13 — створювати інтерактивний div без клавіатурної підтримки

Погано:

    <div onclick="openDialog()">
        Відкрити діалог
    </div>

Навіть якщо додати:

    role="button"

це не забезпечить автоматично всю поведінку кнопки.

Для звичайної дії краще використати нативний `button`.

## Помилка 14 — не вказувати мову документа

Неоптимально:

    <html>

Краще:

    <html lang="uk">

Мова документа допомагає допоміжним технологіям правильно інтерпретувати текст.

## Помилка 15 — використовувати таблиці для layout

Не варто використовувати:

    <table>
        ...
    </table>

лише для розташування елементів сторінки.

Для компонування інтерфейсу використовуй CSS:

    Flexbox
    Grid

Таблиці призначені передусім для табличних даних.

## Помилка 16 — вважати семантику гарантією повної доступності

Навіть правильний HTML може мати проблеми з доступністю через:

    missing focus styles
    poor color contrast
    inaccessible custom widgets
    incorrect dynamic updates
    inaccessible validation errors
    misleading link text

Semantic HTML — це фундамент accessibility, але не вся accessibility.

# Практичний приклад — доступна сторінка бібліотеки

    <!DOCTYPE html>
    <html lang="uk">
        <head>
            <meta charset="UTF-8">

            <meta
                name="viewport"
                content="width=device-width, initial-scale=1.0"
            >

            <title>Бібліотека | Каталог книг</title>
        </head>

        <body>
            <header>
                <h1>Міська бібліотека</h1>

                <p>
                    Книги для навчання та відпочинку.
                </p>
            </header>

# Semantic HTML Checklist

Перед завершенням сторінки перевір:

## Document structure

    [ ] HTML має коректну базову структуру.
    [ ] Вказано правильний lang.
    [ ] Визначено змістовний title.
    [ ] Основний вміст розташовано в main.
    [ ] Навігаційні області позначені nav, коли це доречно.
    [ ] Повторювані структурні елементи мають зрозуміле призначення.

## Headings

    [ ] Заголовки відповідають структурі документа.
    [ ] Рівні заголовків не вибираються лише за розміром шрифту.
    [ ] Кожен заголовок описує відповідний розділ.
    [ ] Основні розділи легко знаходити за заголовками.

## Links and buttons

    [ ] Посилання використовуються для навігації.
    [ ] Кнопки використовуються для дій.
    [ ] Текст посилань має зрозуміле призначення.
    [ ] Кнопки мають доступні назви.
    [ ] Кнопки всередині форм мають правильний type.

## Images

    [ ] Змістовні зображення мають відповідний alt.
    [ ] Декоративні зображення мають alt="".
    [ ] Зображення-посилання мають зрозумілу доступну назву.
    [ ] Для складних графіків передбачено текстове пояснення, якщо воно потрібне.

## Forms

    [ ] Поля мають доступні назви.
    [ ] Label пов'язаний із відповідним полем.
    [ ] Групи полів мають зрозумілу структуру.
    [ ] Обов'язкові поля позначені не лише кольором.
    [ ] Інструкції та помилки доступні користувачам.

## ARIA

    [ ] Нативний HTML використовується там, де це можливо.
    [ ] ARIA не дублює без потреби нативну семантику.
    [ ] Інтерактивні елементи мають коректні ролі та назви.
    [ ] Стани ARIA оновлюються відповідно до реального стану компонента.
    [ ] ARIA не використовується замість клавіатурної поведінки.

## Testing

    [ ] Сторінку можна переглянути за допомогою клавіатури.
    [ ] Фокус переходить між інтерактивними елементами.
    [ ] Візуальні стани фокуса помітні.
    [ ] Структура заголовків зрозуміла.
    [ ] Перевірено автоматичним accessibility checker.
    [ ] За можливості перевірено зі screen reader.

# Інструменти для перевірки Semantic HTML

## 1. Browser DevTools

Інструменти розробника браузера допомагають перевірити:

    HTML structure
    DOM tree
    element attributes
    accessibility properties
    computed styles
    focus behavior

Вони корисні для пошуку неправильних атрибутів, вкладеності елементів і проблем із доступною назвою.

## 2. Accessibility tree

Accessibility tree — це представлення елементів інтерфейсу, їхніх ролей, назв, станів та інших властивостей, доступних допоміжним технологіям.

Він допомагає зрозуміти, як браузер представляє інтерфейс для assistive technologies.

Перевіряй:

    role
    name
    description
    state
    properties

## 3. W3C Nu Html Checker

Nu Html Checker допомагає знаходити проблеми та помилки в HTML-розмітці.

Посилання:

    https://validator.w3.org/nu/

Важливо: валідний HTML не означає автоматично доступний HTML.

Валідатор не перевіряє всі аспекти accessibility.

## 4. axe DevTools

axe DevTools допомагає знаходити багато поширених проблем доступності.

Посилання:

    https://www.deque.com/axe/devtools/

Автоматичні перевірки можуть знаходити частину проблем, але не замінюють ручного тестування.

## 5. Lighthouse

Lighthouse містить автоматичні accessibility-перевірки.

Його можна запускати через Chrome DevTools.

Важливо:

    automated checks
        ≠
    complete accessibility audit

## 6. Screen readers

Для практичного тестування можна використовувати:

    NVDA       → Windows
    JAWS       → Windows
    VoiceOver  → Apple devices
    TalkBack   → Android

Перевіряй, чи можна зрозуміти структуру сторінки, знайти потрібний розділ і скористатися основними елементами інтерфейсу.

# Зв'язок із WCAG

WCAG — Web Content Accessibility Guidelines.

Це міжнародні рекомендації щодо доступності вебконтенту, розроблені W3C.

WCAG побудовані навколо чотирьох основних принципів:

    POUR

    P → Perceivable
    O → Operable
    U → Understandable
    R → Robust

Українською:

    Perceivable    → сприйманість
    Operable       → керованість
    Understandable → зрозумілість
    Robust         → надійність

Semantic HTML підтримує всі чотири принципи, особливо зрозумілість структури та сумісність із допоміжними технологіями.

Наприклад:

    <button type="button">
        Відкрити меню
    </button>

допомагає зробити дію розпізнаваною та доступною для клавіатури.

А:

    <h2>Налаштування профілю</h2>

допомагає користувачам зрозуміти структуру документа.

Семантичний HTML також сприяє виконанню вимог WCAG, пов'язаних із програмним визначенням ролі, назви та значення елементів.

Однак правильна семантика — лише частина відповідності WCAG.

# Головне

• Semantic HTML — це основа доступної структури вебсторінки.

• HTML-елементи потрібно вибирати відповідно до їхнього призначення.

• `header`, `nav`, `main`, `section`, `article`, `aside` і `footer` допомагають структурувати сторінку.

• Заголовки `h1`–`h6` визначають ієрархію змісту, а не просто розмір тексту.

• `a` призначений для навігації, а `button` — для дій.

• `label` допомагає визначити назву поля форми.

• `alt` надає текстову альтернативу змістовним зображенням. Декоративні зображення зазвичай мають `alt=""`.

• `lang` допомагає браузерам і допоміжним технологіям визначати мову документа.

• Landmark-регіони допомагають користувачам швидко переходити до основних частин сторінки.

• Accessible name визначає, як елемент називається для допоміжних технологій.

• Accessible description надає додаткову інформацію про елемент.

• Нативні HTML-елементи зазвичай забезпечують кращу базову семантику та стандартну поведінку, ніж саморобні інтерактивні `div`.

• ARIA потрібно використовувати обережно. Вона доповнює HTML, але не замінює семантику, клавіатурну підтримку чи керування фокусом.

• Семантичний HTML полегшує роботу з screen readers, клавіатурою та іншими допоміжними технологіями.

• Правильна семантика не гарантує повної доступності. Потрібно також перевіряти контраст, фокус, форми, інтерактивні стани та динамічний вміст.

• Валідний HTML не обов'язково є повністю доступним.

• Автоматичні інструменти допомагають знаходити проблеми, але не замінюють ручного тестування.

• У React і Next.js потрібно дотримуватися тих самих принципів семантичного HTML.

• Основний принцип:

    Use the right HTML element for the job.

• Найкращий порядок роботи:

    1. Визначити зміст і призначення елемента.
    2. Вибрати відповідний семантичний HTML.
    3. Додати CSS для потрібного вигляду.
    4. Додати JavaScript для необхідної поведінки.
    5. Додати ARIA лише за потреби.
    6. Перевірити клавіатурну навігацію.
    7. Перевірити доступні назви, ролі та стани.
    8. Протестувати сторінку автоматичними й ручними методами.

• Semantic HTML — це не просто чистий код. Це спосіб зробити інтерфейс зрозумілішим, передбачуванішим і доступнішим для різних користувачів.
