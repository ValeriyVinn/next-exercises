# 06. Form Accessibility — Доступність форм

Форми — один із найважливіших елементів доступного інтерфейсу. Користувач повинен розуміти, яку інформацію потрібно ввести, як взаємодіяти з полями, як виправити помилки та чи успішно відправлено дані.

Доступна форма має бути зрозумілою для користувачів, які:
- використовують клавіатуру замість миші;
- працюють зі скринрідерами;
- мають порушення зору або сприйняття кольорів;
- мають рухові обмеження;
- використовують збільшення екрана;
- мають когнітивні особливості або труднощі з читанням;
- заповнюють форму на мобільному пристрої.

Мета доступності форм — зробити введення даних зрозумілим, передбачуваним і зручним для всіх.

---

## 1. Основні принципи доступних форм

✔ Кожне поле має зрозумілу назву — `label`.

✔ Інструкції розташовані поруч із відповідним полем.

✔ Обов'язкові поля позначені не лише кольором.

✔ Помилки пояснюють, що саме потрібно виправити.

✔ Користувач може пройти форму за допомогою клавіатури.

✔ Фокус клавіатури завжди помітний.

✔ Скринрідер може визначити назву, тип і стан поля.

✔ Поля мають відповідні HTML-типи.

✔ Дані не втрачаються через випадкову помилку.

✔ Успішне надсилання форми зрозуміле користувачеві.

**Головний принцип:** доступність форми починається з правильного HTML, а не з додавання ARIA.

---

## 2. Семантична структура форми

HTML має спеціальні елементи для створення доступних форм.

| Елемент | Призначення |
|---|---|
| `form` | Контейнер форми |
| `label` | Назва поля |
| `input` | Поле введення |
| `textarea` | Багаторядкове введення |
| `select` | Вибір зі списку |
| `option` | Варіант у списку |
| `button` | Кнопка |
| `fieldset` | Групування пов'язаних полів |
| `legend` | Назва групи полів |
| `output` | Результат обчислення |
| `datalist` | Список підказок для введення |

Приклад базової форми:

    <form action="/register" method="post">
      <label for="name">Ім'я</label>
      <input
        id="name"
        name="name"
        type="text"
        autocomplete="given-name"
        required
      />

      <button type="submit">Зареєструватися</button>
    </form>

Тут:
- `form` об'єднує елементи форми;
- `label` пояснює призначення поля;
- `for="name"` пов'язує назву з полем `id="name"`;
- `name="name"` визначає ім'я параметра, який надсилається на сервер;
- `type="text"` визначає тип введення;
- `autocomplete="given-name"` підказує браузеру, які дані можна підставити;
- `required` указує, що поле обов'язкове.

Не потрібно замінювати семантичні HTML-елементи звичайними `div`, якщо вже існує відповідний елемент форми.

---

## 3. Label — назва поля

`label` — один із найважливіших елементів доступності форми.

Користувач повинен розуміти, що саме потрібно ввести в кожне поле.

### 3.1. Правильний зв'язок через `for` та `id`

    <label for="email">Електронна пошта</label>
    <input
      id="email"
      name="email"
      type="email"
    />

Значення `for` у `label` має збігатися зі значенням `id` відповідного поля.

Коли користувач активує назву поля, браузер переводить фокус на пов'язаний елемент. Це також збільшує зручну для натискання область на сенсорних пристроях.

### 3.2. Label як батьківський елемент

HTML також дозволяє вкладати поле безпосередньо в `label`.

    <label>
      Електронна пошта
      <input
        name="email"
        type="email"
      />
    </label>

Обидва варіанти коректні. У першому варіанті явний зв'язок через `for` та `id` часто зручніший для читання й підтримки коду.

### 3.3. Placeholder не замінює label

❌ Неправильно:

    <input
      type="email"
      placeholder="Електронна пошта"
    />

Коли користувач починає вводити текст, підказка зникає. Крім того, placeholder зазвичай має слабший візуальний контраст і не замінює доступну назву поля.

✔ Правильно:

    <label for="email">Електронна пошта</label>
    <input
      id="email"
      name="email"
      type="email"
      placeholder="name@example.com"
    />

Тут `label` називає поле, а `placeholder` показує приклад формату.

### 3.4. Коли label має бути візуально прихованим

Іноді дизайн передбачає компактне поле без видимої назви. Але назва все одно повинна залишатися доступною для допоміжних технологій.

    <label for="search" class="visually-hidden">
      Пошук по сайту
    </label>

    <input
      id="search"
      name="q"
      type="search"
    />

CSS-клас `visually-hidden` має приховувати елемент візуально, не видаляючи його з дерева доступності.

Приклад CSS:

    .visually-hidden {
      position: absolute;
      width: 1px;
      height: 1px;
      padding: 0;
      margin: -1px;
      overflow: hidden;
      clip: rect(0, 0, 0, 0);
      white-space: nowrap;
      border: 0;
    }

Не використовуйте для такого label `display: none` або `visibility: hidden`, адже ці властивості зазвичай прибирають його і з дерева доступності.

**Запам'ятай:** placeholder — це підказка, а label — назва поля.

---

## 4. Інструкції та додаткові пояснення

Назви поля іноді недостатньо. Користувачеві може знадобитися пояснення формату або вимог.

Наприклад:
- пароль має містити щонайменше 12 символів;
- номер телефону потрібно ввести з кодом країни;
- дата народження вводиться у форматі день, місяць, рік.

Для цього можна використовувати звичайний текст і `aria-describedby`.

    <label for="password">Пароль</label>

    <p id="password-help">
      Використайте щонайменше 12 символів.
    </p>

    <input
      id="password"
      name="password"
      type="password"
      aria-describedby="password-help"
    />

`aria-describedby` пов'язує поле з елементом, який містить додатковий опис.

Важливо:
- `label` відповідає на запитання «Що це за поле?»;
- `aria-describedby` відповідає на запитання «Які додаткові відомості потрібно знати?»;
- `aria-labelledby` дозволяє вказати інший елемент як доступну назву, коли це необхідно.

Не потрібно додавати ARIA до кожного поля без потреби. Звичайний видимий текст та семантичний HTML часто вже забезпечують необхідну інформацію.

---

## 5. Обов'язкові та необов'язкові поля

Користувач повинен розуміти, які поля необхідно заповнити.

### 5.1. Атрибут `required`

    <label for="email">Електронна пошта (обов'язково)</label>

    <input
      id="email"
      name="email"
      type="email"
      required
    />

Атрибут `required` повідомляє браузеру, що поле обов'язкове, і бере участь у вбудованій перевірці форми.

Але сам по собі він не завжди достатній для зрозумілого інтерфейсу. Варто також позначити обов'язковість у видимому тексті або чітко пояснити її на початку форми.

### 5.2. Позначення зірочкою

Можна використовувати зірочку, якщо її значення пояснено користувачеві.

    <p>Поля, позначені *, обов'язкові для заповнення.</p>

    <label for="name">
      Ім'я <span aria-hidden="true">*</span>
    </label>

    <input id="name" name="name" required />

`aria-hidden="true"` у цьому прикладі приховує декоративну зірочку від допоміжних технологій. Обов'язковість поля все одно передається через `required`, а її значення пояснюється текстом.

Не покладайтеся лише на:
- червоний колір;
- зірочку без пояснення;
- положення поля у формі;
- припущення, що користувач знає правила.

### 5.3. Коли краще позначати необов'язкові поля

Якщо більшість полів обов'язкові, а кілька — ні, іноді простіше позначити саме необов'язкові поля.

Наприклад:

    <label for="middle-name">
      По батькові (необов'язково)
    </label>

    <input id="middle-name" name="middleName" />

Обирайте один зрозумілий підхід і використовуйте його послідовно в усій формі.

## 6. Правильні типи полів

Атрибут `type` допомагає браузеру визначити очікувані дані, показати відповідну клавіатуру на мобільному пристрої та виконати базову перевірку.

| Тип | Призначення |
|---|---|
| `text` | Звичайний текст |
| `email` | Електронна пошта |
| `password` | Пароль |
| `tel` | Номер телефону |
| `url` | URL-адреса |
| `number` | Числове значення |
| `search` | Пошуковий запит |
| `date` | Дата |
| `time` | Час |
| `checkbox` | Незалежний вибір або перемикач |
| `radio` | Один варіант із групи |
| `file` | Вибір файлу |
| `range` | Вибір значення в діапазоні |
| `hidden` | Приховане поле даних |

Приклад:

    <label for="phone">Номер телефону</label>
    <input
      id="phone"
      name="phone"
      type="tel"
      autocomplete="tel"
    />

`type="tel"` не гарантує автоматичної перевірки правильності номера. Він лише повідомляє браузеру про характер даних і може впливати на мобільну клавіатуру.

### 6.1. Не використовуйте `number` для всіх числових рядків

Номер телефону, поштовий індекс і номер документа — не обов'язково математичні числа. Вони можуть містити нулі на початку, символи або пробіли.

Для таких даних зазвичай краще `type="text"` або `type="tel"` залежно від призначення.

### 6.2. Автозаповнення

Атрибут `autocomplete` допомагає браузеру розпізнавати тип інформації.

    <label for="given-name">Ім'я</label>
    <input
      id="given-name"
      name="givenName"
      type="text"
      autocomplete="given-name"
    />

    <label for="family-name">Прізвище</label>
    <input
      id="family-name"
      name="familyName"
      type="text"
      autocomplete="family-name"
    />

    <label for="email">Електронна пошта</label>
    <input
      id="email"
      name="email"
      type="email"
      autocomplete="email"
    />

Автозаповнення зменшує кількість повторного введення та ризик помилок. Використовуйте відповідні значення для конкретних полів.

---

## 7. Групування полів: fieldset і legend

Коли кілька полів стосуються одного питання, їх потрібно логічно згрупувати.

Наприклад, вибір способу оплати або контактних уподобань.

    <fieldset>
      <legend>Спосіб отримання повідомлень</legend>

      <label>
        <input
          type="radio"
          name="notification"
          value="email"
        />
        Електронна пошта
      </label>

      <label>
        <input
          type="radio"
          name="notification"
          value="sms"
        />
        SMS
      </label>
    </fieldset>

`fieldset` створює групу полів, а `legend` надає їй назву.

Це особливо корисно для скринрідерів: користувач може зрозуміти, до якого питання належать варіанти.

Застосовуйте `fieldset` і `legend`, коли групування має зміст, а не лише для візуального оформлення.

---

## 8. Checkbox і radio

Ці елементи схожі зовні, але мають різну поведінку.

### 8.1. Checkbox — незалежний вибір

Checkbox дозволяє вибрати один або кілька варіантів.

    <fieldset>
      <legend>Які теми вас цікавлять?</legend>

      <label>
        <input
          type="checkbox"
          name="topics"
          value="html"
        />
        HTML
      </label>

      <label>
        <input
          type="checkbox"
          name="topics"
          value="css"
        />
        CSS
      </label>

      <label>
        <input
          type="checkbox"
          name="topics"
          value="javascript"
        />
        JavaScript
      </label>
    </fieldset>

Кожен checkbox може бути вибраний незалежно від інших.

### 8.2. Radio — один варіант із групи

Radio дозволяє вибрати лише один варіант у групі, якщо елементи мають однаковий `name`.

    <fieldset>
      <legend>Рівень досвіду</legend>

      <label>
        <input
          type="radio"
          name="experience"
          value="beginner"
        />
        Початківець
      </label>

      <label>
        <input
          type="radio"
          name="experience"
          value="intermediate"
        />
        Середній
      </label>

      <label>
        <input
          type="radio"
          name="experience"
          value="advanced"
        />
        Просунутий
      </label>
    </fieldset>

Для radio важливо:
- об'єднати варіанти спільною назвою;
- дати групі зрозумілий `legend`;
- зробити весь підпис доступною областю натискання;
- забезпечити навігацію клавіатурою.

Не замінюйте стандартні checkbox і radio саморобними елементами без потреби. Стандартні HTML-контроли вже мають багато вбудованих можливостей доступності.

## 9. Select і textarea

### 9.1. Select — список варіантів

    <label for="country">Країна</label>

    <select id="country" name="country">
      <option value="">Оберіть країну</option>
      <option value="ua">Україна</option>
      <option value="pl">Польща</option>
      <option value="de">Німеччина</option>
    </select>

Поради:
- використовуйте видимий `label`;
- не покладайтеся лише на placeholder-подібну першу опцію;
- додавайте зрозумілі назви варіантів;
- не використовуйте надто довгі списки без потреби;
- перевіряйте роботу клавіатури та скринрідера.

### 9.2. Textarea — багаторядковий текст

    <label for="message">Ваше повідомлення</label>

    <textarea
      id="message"
      name="message"
      rows="5"
      aria-describedby="message-help"
    ></textarea>

    <p id="message-help">
      Опишіть ваше запитання або проблему.
    </p>

`rows` задає початкову кількість видимих рядків, а не обмежує максимальну довжину тексту.

Якщо є обмеження за кількістю символів, повідомте про нього заздалегідь і зробіть залишок символів зрозумілим для користувачів.

## 10. Помилки валідації

Доступна форма не лише виявляє помилку, а й пояснює, як її виправити.

Погане повідомлення:
- «Помилка»;
- «Некоректно»;
- «Щось пішло не так».

Краще:
- «Введіть адресу електронної пошти»;
- «Перевірте формат електронної пошти»;
- «Пароль має містити щонайменше 12 символів».

### 10.1. Пов'язування помилки з полем

    <label for="email">Електронна пошта</label>

    <input
      id="email"
      name="email"
      type="email"
      aria-invalid="true"
      aria-describedby="email-error"
      required
    />

    <p id="email-error">
      Введіть адресу електронної пошти у форматі name@example.com.
    </p>

`aria-invalid="true"` повідомляє допоміжним технологіям, що значення поля не пройшло перевірку.

`aria-describedby="email-error"` пов'язує поле з текстом помилки.

Використовуйте `aria-invalid="true"` лише тоді, коли поле справді має помилку, а не за замовчуванням для кожного поля.

### 10.2. Не позначайте помилки лише кольором

❌ Погано:
- поле стало червоним;
- користувачеві не повідомили причину;
- скринрідер не отримав інформації про помилку.

✔ Добре:
- помітна візуальна ознака;
- текстове пояснення;
- зв'язок повідомлення з відповідним полем;
- зрозумілий спосіб виправлення.

Колір може бути додатковим сигналом, але не єдиним.

### 10.3. Перевірка введення

Для простої перевірки браузер може використовувати вбудовані HTML-атрибути.

    <label for="username">Ім'я користувача</label>

    <input
      id="username"
      name="username"
      type="text"
      minlength="3"
      maxlength="30"
      required
    />

Корисні атрибути:
- `required` — значення обов'язкове;
- `minlength` — мінімальна довжина тексту;
- `maxlength` — максимальна довжина тексту;
- `min` і `max` — межі для відповідних типів значень;
- `step` — крок для числових значень;
- `pattern` — шаблон перевірки рядка;
- `type="email"` — базова перевірка формату електронної пошти.

Вбудована перевірка не замінює перевірку даних на сервері. Клієнтська валідація допомагає користувачеві, але її можна обійти.

## 11. Відображення помилок після надсилання

Якщо помилок кілька, корисно показати їхній загальний список на початку форми.

Приклад структури:

    <div role="alert" aria-labelledby="error-title">
      <h2 id="error-title">
        Перевірте форму
      </h2>

      <ul>
        <li>
          <a href="#email">
            Введіть коректну електронну пошту.
          </a>
        </li>
        <li>
          <a href="#password">
            Пароль має містити щонайменше 12 символів.
          </a>
        </li>
      </ul>
    </div>

    <label for="email">Електронна пошта</label>
    <input id="email" name="email" type="email" />

    <label for="password">Пароль</label>
    <input id="password" name="password" type="password" />

Це приклад структури повідомлення про помилки, а не готова система валідації. Реальний інтерфейс повинен відображати список лише тоді, коли помилки справді є, а посилання мають вести до відповідних полів.

Переваги:
- користувач одразу бачить, скільки проблем потрібно виправити;
- кожна помилка пояснена;
- посилання дозволяють перейти до поля;
- користувач не мусить шукати помилки по всій формі.

Після надсилання форми з помилками можна перевести фокус на заголовок списку помилок або іншим надійним способом повідомити користувачеві про результат. Важливо, щоб зміна була доступна з клавіатури та допоміжних технологій.

Не переводьте фокус без потреби під час кожного введення символу: це може порушити робочий процес користувача.

---

## 12. `aria-live` та динамічні повідомлення

Деякі повідомлення з'являються без перезавантаження сторінки:
- «Залишилося 100 символів»;
- «Перевіряємо адресу електронної пошти»;
- «Файл завантажено»;
- «Дані успішно збережено».

Скринрідер не завжди автоматично повідомляє про зміну тексту в довільному елементі. Для відповідних динамічних повідомлень можна використовувати `aria-live`.

    <p aria-live="polite" id="status-message"></p>

Коли застосунок оновлює текст цього елемента, скринрідер може повідомити про зміну, не перериваючи поточну озвучку.

Основні значення:
- `aria-live="polite"` — повідомлення зазвичай озвучується у відповідний момент;
- `aria-live="assertive"` — термінове повідомлення може перервати поточну озвучку.

Не використовуйте `assertive` для звичайних підказок. Надмірна кількість термінових повідомлень заважає користувачеві.

Для коротких повідомлень про успіх або стан іноді доречний `role="status"`. Для важливих повідомлень про помилки, що потребують негайної уваги, може бути доречний `role="alert"`.

Не додавайте одночасно багато перекривних механізмів оповіщення без перевірки: одне повідомлення не повинно озвучуватися кілька разів.

## 13. Доступна кнопка надсилання

Кнопка має чітко пояснювати свою дію.

❌ Неоднозначно:
- «ОК»;
- «Далі» без контексту;
- «Натисни»;
- іконка без доступної назви.

✔ Зрозуміло:
- «Надіслати повідомлення»;
- «Створити обліковий запис»;
- «Зберегти зміни»;
- «Перейти до оплати».

Приклад:

    <button type="submit">
      Створити обліковий запис
    </button>

Використовуйте правильний тип кнопки:
- `type="submit"` — надсилає форму;
- `type="button"` — виконує іншу дію;
- `type="reset"` — скидає значення полів до початкових.

Якщо кнопка розташована всередині форми й не повинна надсилати її, явно вказуйте `type="button"`.

### 13.1. Стан завантаження

Після надсилання форми інтерфейс може показувати стан обробки.

Приклад:

    <button type="submit" disabled>
      Надсилання...
    </button>

Це лише статичний приклад стану завантаження. У реальному застосунку потрібно керувати станом кнопки через JavaScript або React.

Під час обробки:
- повідомте користувача, що відбувається;
- не допускайте випадкового повторного надсилання, якщо це важливо;
- не приховуйте результат операції;
- після завершення повідомте про успіх або помилку;
- не залишайте кнопку вимкненою назавжди.

Вимкнена кнопка через `disabled` зазвичай не отримує фокус клавіатури. Якщо користувачеві потрібно пояснити, чому дію неможливо виконати, повідомте причину доступним текстом.

## 14. Клавіатурна доступність форм

Усі функції форми мають бути доступні без миші.

Основні клавіші:
- `Tab` — перейти до наступного доступного елемента;
- `Shift + Tab` — перейти до попереднього елемента;
- `Space` — активувати checkbox або кнопку в типових випадках;
- стрілки — переміщатися між варіантами radio та елементами деяких списків;
- `Enter` — активувати посилання або виконати відповідну дію.

Точна поведінка залежить від типу елемента та браузера.

Перевір:
- чи можна дістатися до кожного поля;
- чи логічний порядок фокуса;
- чи не пропускаються важливі елементи;
- чи видно фокус;
- чи можна вибрати всі варіанти;
- чи можна надіслати форму;
- чи можна виправити помилки;
- чи немає клавіатурної пастки.

Не використовуйте `tabindex` зі значеннями більше нуля для створення штучного порядку переходу. У більшості випадків достатньо логічного порядку HTML-елементів.

---

## 15. Видимий фокус

Коли користувач переміщується клавішею `Tab`, активний елемент повинен бути помітним.

Приклад:

    input:focus-visible,
    textarea:focus-visible,
    select:focus-visible,
    button:focus-visible {
      outline: 3px solid #155eef;
      outline-offset: 3px;
    }

Не видаляйте стандартний контур фокуса без доступної альтернативи.

❌ Небезпечно:

    :focus {
      outline: none;
    }

Якщо дизайн передбачає власний індикатор, він повинен залишатися достатньо помітним на різних фонах.

Важливо:
- фокус не повинен губитися на межі поля;
- його не повинні перекривати інші елементи;
- контраст має бути достатнім;
- фокус має бути помітним у різних станах поля.

---

## 16. Помилки та збереження введених даних

Якщо користувач допустив помилку, не змушуйте його вводити всю форму заново без необхідності.

Хороший сценарій:
1. Користувач заповнює форму.
2. Надсилає дані.
3. Система знаходить помилку.
4. Пояснює, яке поле потрібно виправити.
5. Зберігає інші коректно введені значення.
6. Дозволяє виправити помилку та повторити надсилання.

Особливо важливо це для:
- довгих анкет;
- форм замовлення;
- реєстрації;
- медичних або освітніх форм;
- багатокрокових процесів.

Якщо дані можуть бути втрачені через завершення сесії або перезавантаження сторінки, за можливості попереджайте користувача й використовуйте безпечне збереження чернетки там, де це доречно.

Для чутливих даних не зберігайте інформацію бездумно в браузері. Потрібно враховувати приватність, безпеку та очікування користувача.

---

## 17. Допомога користувачеві під час введення

Хороший інтерфейс пояснює вимоги до введення до того, як користувач припуститься помилки.

Приклад поля пароля:

    <label for="password">Пароль</label>

    <p id="password-help">
      Використайте щонайменше 12 символів.
    </p>

    <input
      id="password"
      name="password"
      type="password"
      minlength="12"
      autocomplete="new-password"
      aria-describedby="password-help"
      required
    />

Рекомендації:
- пояснюйте вимоги до пароля до введення;
- не використовуйте незрозумілі скорочення;
- показуйте приклади форматів;
- не вимагайте зайвої інформації;
- не просіть повторно вводити ті самі дані без потреби;
- дозволяйте вставляти пароль із буфера обміну;
- підтримуйте автозаповнення там, де воно доречне.

Якщо додаєте функцію показу або приховування пароля, вона має бути доступною кнопкою з назвою, що відповідає поточній дії.

Приклад структури:

    <label for="password">Пароль</label>

    <input
      id="password"
      name="password"
      type="password"
      autocomplete="current-password"
    />

    <button type="button">
      Показати пароль
    </button>

Цей фрагмент показує лише HTML-структуру. Для реального перемикання потрібен JavaScript, який змінює `type` поля та оновлює доступну назву кнопки відповідно до її дії.

## 18. Доступні форми в React

У React застосовуються ті самі принципи семантичного HTML.

Приклад компонента:

    export default function ContactForm() {
      return (
        <form>
          <div>
            <label htmlFor="name">Ім'я</label>
            <input
              id="name"
              name="name"
              type="text"
              autoComplete="given-name"
              required
            />
          </div>

          <div>
            <label htmlFor="email">
              Електронна пошта
            </label>
            <input
              id="email"
              name="email"
              type="email"
              autoComplete="email"
              required
            />
          </div>

          <div>
            <label htmlFor="message">
              Повідомлення
            </label>
            <textarea
              id="message"
              name="message"
              rows={5}
              required
            />
          </div>

          <button type="submit">
            Надіслати повідомлення
          </button>
        </form>
      );
    }

У JSX:
- використовуй `htmlFor` замість `for`;
- використовуй `className` замість `class`;
- використовуй `autoComplete` у camelCase;
- використовуй `aria-*` атрибути з їхніми HTML-назвами, наприклад `aria-describedby`;
- стеж за унікальністю `id`;
- не забувай про обробку надсилання форми.

### 18.1. Повідомлення про помилки в React

Приклад умовного відображення помилки:

    {emailError && (
      <p id="email-error">
        {emailError}
      </p>
    )}

    <label htmlFor="email">
      Електронна пошта
    </label>

    <input
      id="email"
      name="email"
      type="email"
      aria-invalid={Boolean(emailError)}
      aria-describedby={
        emailError ? "email-error" : undefined
      }
    />

Це фрагмент JSX для ілюстрації принципу. Він передбачає, що `emailError` уже визначено в компоненті.

Важливо:
- `aria-invalid` має відображати реальний стан перевірки;
- `aria-describedby` повинен посилатися на наявний елемент;
- помилка має бути зрозумілою;
- повідомлення не повинно зникати до того, як користувач зможе його прочитати;
- фокус потрібно переміщувати лише тоді, коли це виправдано поведінкою форми.

Не використовуйте `any` у TypeScript лише для того, щоб спростити обробку подій. Визначайте конкретні типи подій і стану відповідно до задачі.

## 19. Доступні форми в Next.js

У Next.js компоненти форми можуть бути серверними або клієнтськими залежно від реалізації.

Основні принципи залишаються незмінними:
- семантичний HTML;
- пов'язані `label` і поля;
- зрозуміла валідація;
- доступні повідомлення;
- логічний фокус;
- перевірка даних на сервері.

Якщо форма використовує інтерактивний стан React, наприклад динамічну валідацію або показ пароля, відповідна частина інтерфейсу має бути клієнтською.

Не покладайся лише на клієнтську перевірку. Дані потрібно перевіряти й на сервері, оскільки користувач може відправити запит в обхід інтерфейсу.

## 20. Доступність і мобільні пристрої

Форма має бути зручною не лише на великому екрані.

Перевір:
- чи достатньо великі області натискання;
- чи не надто дрібний текст;
- чи не перекриває клавіатура важливі поля;
- чи зберігається видимість фокуса;
- чи можна збільшити сторінку;
- чи не потрібно прокручувати екран горизонтально для звичайного введення;
- чи не губиться повідомлення про помилку;
- чи працюють стандартні мобільні клавіатури для відповідних типів полів.

Приклад CSS:

    input,
    textarea,
    select,
    button {
      max-width: 100%;
      font: inherit;
    }

    input,
    textarea,
    select {
      box-sizing: border-box;
      width: 100%;
    }

Цей CSS допомагає контролам адаптуватися до контейнера, але не замінює повноцінного адаптивного тестування.

Не вимикайте масштабування сторінки через `user-scalable=no` або подібні налаштування viewport.

## 21. Контраст і візуальні стани полів

Поля повинні бути візуально відмінними від фону.

Перевір:
- контраст тексту;
- видимість меж поля;
- видимість фокуса;
- різницю між звичайним і помилковим станом;
- різницю між активним і вимкненим станом;
- читабельність підказок;
- видимість індикаторів обов'язковості.

Не покладайся лише на колір, щоб показати помилку або обов'язковість.

Для звичайного тексту WCAG 2.2 за критерієм 1.4.3 зазвичай вимагає контраст щонайменше 4.5:1, а для великого тексту — 3:1. Для важливих візуальних ознак компонентів та станів застосовується критерій 1.4.11 з вимогою контрасту 3:1 у відповідних випадках.

## 23. Тестування доступності форм

Автоматичні інструменти можуть знайти частину проблем, але не можуть повністю оцінити зрозумілість форми.

### 23.1. Перевірка вручну

Пройди форму без миші:
1. Перезавантаж сторінку.
2. Почни натискати `Tab`.
3. Перевір, чи видно фокус.
4. Переконайся, що кожне поле має назву.
5. Введи некоректні дані.
6. Надішли форму.
7. Перевір, чи зрозумілі повідомлення про помилки.
8. Виправ помилки.
9. Переконайся, що дані не втратилися.
10. Перевір повідомлення про успіх.

### 23.2. Перевірка зі скринрідером

Можна використовувати:
- NVDA у Windows;
- VoiceOver у macOS та iOS;
- TalkBack в Android;
- Orca в Linux.

Перевір:
- чи оголошується назва поля;
- чи повідомляється його тип;
- чи визначається обов'язковість;
- чи доступні підказки;
- чи повідомляється помилка;
- чи доступні стани checkbox і radio;
- чи озвучується результат надсилання.

### 23.3. Автоматизовані інструменти

Для початкової перевірки можна використовувати:
- axe DevTools;
- Lighthouse;
- Accessibility Insights;
- вбудовані засоби перевірки доступності браузера.

Автоматичні інструменти не гарантують повної відповідності WCAG. Наприклад, вони можуть знайти відсутній `label`, але не завжди визначать, чи зрозуміла його назва користувачеві.

## 24. Типові помилки розробників

### Помилка 1. Placeholder замість label

    <input placeholder="Ваше ім'я" />

Проблема: назва поля не залишається видимою після введення.

Виправлення: додати справжній `label`.

### Помилка 2. Поле без доступної назви

    <input id="email" type="email" />

Проблема: скринрідер може не мати зрозумілої назви для поля.

Виправлення: пов'язати поле з `label` або надати іншу коректну доступну назву.

### Помилка 3. Група radio без legend

    <input type="radio" name="delivery" value="home" />
    <label>Доставка додому</label>

    <input type="radio" name="delivery" value="office" />
    <label>Доставка у відділення</label>

Проблема: користувач може не розуміти, яке питання об'єднує варіанти.

Виправлення: використати `fieldset` і `legend`, наприклад «Спосіб доставки».

### Помилка 4. Помилка лише червоним кольором

Проблема: користувач може не помітити зміну або не зрозуміти її значення.

Виправлення: додати текстове пояснення та програмний зв'язок із полем.

### Помилка 5. Вимкнена кнопка без пояснення

Проблема: користувач не розуміє, чому дія недоступна.

Виправлення: пояснити, що потрібно зробити, і забезпечити доступність пояснення.

### Помилка 6. Фокус зникає після надсилання

Проблема: користувач не розуміє, що сталося, і може не знайти помилку.

Виправлення: забезпечити зрозуміле повідомлення про результат і логічне керування фокусом.

### Помилка 7. Усі помилки озвучуються надто часто

Проблема: скринрідер перериває користувача після кожного символу.

Виправлення: обирати момент валідації та тип повідомлення відповідно до ситуації.

### Помилка 8. Саморобні поля без клавіатурної підтримки

Проблема: кастомний компонент може не підтримувати фокус, клавіші, стани або доступну назву.

Виправлення: за можливості використовувати стандартні HTML-елементи й тестувати кастомні компоненти окремо.

## 25. Практичний приклад доступної форми

Нижче — базова HTML-форма з назвами, інструкцією, обов'язковими полями та групою радіокнопок.

    <form action="/contact" method="post">
      <h2>Зворотний зв'язок</h2>

      <p>
        Поля, позначені як обов'язкові, потрібно заповнити.
      </p>

      <div>
        <label for="name">Ім'я (обов'язково)</label>
        <input
          id="name"
          name="name"
          type="text"
          autocomplete="given-name"
          required
        />
      </div>

      <div>
        <label for="email">
          Електронна пошта (обов'язково)
        </label>
        <input
          id="email"
          name="email"
          type="email"
          autocomplete="email"
          required
        />
      </div>

      <fieldset>
        <legend>Тема повідомлення</legend>

        <label>
          <input
            type="radio"
            name="topic"
            value="question"
            required
          />
          Запитання
        </label>

        <label>
          <input
            type="radio"
            name="topic"
            value="suggestion"
          />
          Пропозиція
        </label>

        <label>
          <input
            type="radio"
            name="topic"
            value="other"
          />
          Інше
        </label>
      </fieldset>

      <div>
        <label for="message">
          Повідомлення (обов'язково)
        </label>
        <textarea
          id="message"
          name="message"
          rows="5"
          required
        ></textarea>
      </div>

      <button type="submit">
        Надіслати повідомлення
      </button>
    </form>

Цей приклад демонструє семантичну структуру, але ще не реалізує серверну обробку, спеціальні повідомлення про помилки або стан успішного надсилання. Їх потрібно додати відповідно до логіки застосунку.

## 26. Чекліст доступності форми

Перед завершенням роботи перевір:

### Структура
- [ ] Використано семантичний елемент `form`.
- [ ] Кожне поле має доступну назву.
- [ ] Назви полів пов'язані з ними програмно.
- [ ] Пов'язані поля логічно згруповані.
- [ ] Групи radio або checkbox мають зрозумілий контекст, де це потрібно.

### Інструкції
- [ ] Обов'язкові поля чітко позначені.
- [ ] Формат введення пояснено за потреби.
- [ ] Placeholder не замінює label.
- [ ] Вимоги до пароля або інших даних пояснені заздалегідь.
- [ ] Використано доречні типи полів та `autocomplete`.

### Помилки
- [ ] Помилки описані зрозумілим текстом.
- [ ] Помилки не позначаються лише кольором.
- [ ] Повідомлення пов'язані з відповідними полями.
- [ ] Користувач розуміє, як виправити помилку.
- [ ] Коректно введені дані зберігаються, коли це можливо.
- [ ] Після надсилання користувач розуміє результат.

### Клавіатура та скринрідер
- [ ] Усі елементи доступні з клавіатури.
- [ ] Порядок фокуса логічний.
- [ ] Фокус видимий.
- [ ] Немає клавіатурних пасток.
- [ ] Назви, інструкції та помилки доступні скринрідеру.
- [ ] Динамічні повідомлення озвучуються доречно.

### Візуальна доступність
- [ ] Текст має достатній контраст.
- [ ] Межі полів помітні.
- [ ] Стани помилки та фокуса зрозумілі.
- [ ] Інтерфейс працює зі збільшенням.
- [ ] Форма зручна на мобільних пристроях.

### Тестування
- [ ] Форма перевірена без миші.
- [ ] Форма перевірена зі скринрідером.
- [ ] Перевірено порожні, некоректні та коректні значення.
- [ ] Проведено автоматизовану перевірку доступності.
- [ ] Дані перевіряються на сервері.

## 27. Що потрібно запам'ятати

1. **Label — обов'язковий елемент доступної форми.** Placeholder не замінює назву поля.

2. **Семантичний HTML — основа доступності.** Використовуй `input`, `label`, `fieldset`, `legend`, `button` за призначенням.

3. **Інструкції мають бути зрозумілими.** Користувач повинен знати, що вводити, ще до виникнення помилки.

4. **Помилки потрібно пояснювати.** Повідомлення має називати проблему та, за можливості, підказувати спосіб її виправлення.

5. **Не покладайся лише на колір.** Важливі стани повинні мати текстове або інше доступне пояснення.

6. **Клавіатура — обов'язковий спосіб взаємодії.** Усі функції форми мають працювати без миші.

7. **Скринрідер повинен отримувати необхідну інформацію.** Назви, групи, стани й помилки мають бути програмно визначені.

8. **ARIA доповнює HTML, а не замінює його.** Не додавай ARIA без конкретної потреби.

9. **Перевіряй форму в реальних сценаріях.** Автоматизовані інструменти знаходять лише частину проблем.

10. **Доступність — це частина UX.** Зрозуміла форма допомагає всім користувачам, а не лише людям із порушеннями зору.

## 29. Практичне завдання

Створи доступну форму реєстрації користувача.

Форма повинна містити:
- ім'я;
- прізвище;
- електронну пошту;
- пароль;
- вибір рівня досвіду через radio;
- вибір тем через checkbox;
- поле додаткового повідомлення;
- checkbox згоди з умовами;
- кнопку створення облікового запису.

Реалізуй:
1. Семантичну HTML-структуру.
2. Зв'язок кожного поля з `label`.
3. Групування радіокнопок через `fieldset` і `legend`.
4. Пояснення вимог до пароля.
5. Позначення обов'язкових полів.
6. Валідацію введених даних.
7. Доступні повідомлення про помилки.
8. Помітний стан клавіатурного фокуса.
9. Повідомлення про успішне надсилання.
10. Перевірку форми з клавіатури та скринрідером.

**Критерій готовності:** користувач повинен мати змогу заповнити форму, зрозуміти кожне поле, виправити помилки та завершити реєстрацію без використання миші й без необхідності вгадувати призначення елементів.
