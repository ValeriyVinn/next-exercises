# Settings UI — інтерфейси налаштувань

> Шпаргалка з UI/UX-дизайну для папки `ui-design/14-modern-ui-patterns/05-settings`.

## 1. Що таке Settings UI

**Settings UI** — це інтерфейс, за допомогою якого користувач може налаштовувати поведінку застосунку, керувати обліковим записом, змінювати персональні параметри та контролювати приватність.

Основна мета — дати користувачеві зрозумілий контроль над продуктом, не перевантажуючи його складними параметрами.

Settings UI використовується в:
- вебзастосунках;
- мобільних застосунках;
- SaaS-платформах;
- освітніх системах;
- інтернет-магазинах;
- соціальних мережах;
- корпоративних системах;
- особистих кабінетах.

### Основні завдання Settings UI

- організувати налаштування за зрозумілими категоріями;
- дозволити змінювати параметри;
- пояснювати наслідки змін;
- показувати поточні значення;
- повідомляти про успішне збереження;
- обробляти помилки;
- забезпечувати контроль над приватністю;
- давати доступ до налаштувань безпеки;
- підтримувати зрозумілу навігацію;
- запобігати випадковим або небажаним змінам.

**Головний принцип:** користувач повинен розуміти, що саме він змінює, як це вплине на застосунок і чи збережено його вибір.

---

## 2. Основні поняття

- **Settings** — налаштування застосунку або облікового запису.
- **Preferences** — особисті вподобання користувача.
- **Account settings** — налаштування облікового запису.
- **General settings** — загальні налаштування.
- **Privacy settings** — налаштування приватності.
- **Security settings** — налаштування безпеки.
- **Notification settings** — налаштування сповіщень.
- **Display settings** — налаштування відображення.
- **Toggle / Switch** — перемикач стану увімкнено/вимкнено.
- **Checkbox** — прапорець для вибору одного або кількох параметрів.
- **Radio button** — перемикач для вибору одного варіанта з групи.
- **Select** — елемент вибору значення зі списку.
- **Slider** — повзунок для вибору числового значення або діапазону.
- **Dropdown** — меню, що розкривається.
- **Autosave** — автоматичне збереження змін.
- **Save changes** — явне збереження змін.
- **Reset settings** — повернення налаштувань до початкових значень.
- **Default value** — значення за замовчуванням.
- **Dirty state** — стан форми, у якій є незбережені зміни.
- **Confirmation dialog** — діалог підтвердження дії.
- **Destructive action** — дія з потенційно небажаними або незворотними наслідками.

### Settings UI та Profile UI — різниця

**Profile UI** зосереджується на інформації про користувача: ім'я, аватар, опис, дані профілю.

**Settings UI** зосереджується на поведінці продукту та керуванні параметрами: мова, тема, сповіщення, приватність, безпека.

У невеликих застосунках ці розділи можуть бути об'єднані. У великих продуктах їх зазвичай розділяють на логічні категорії.

## 3. Основні категорії налаштувань

Не кожен застосунок потребує всіх категорій. Вибирай їх відповідно до функцій продукту.

### 3.1. General settings — загальні

Можуть містити:
- мову інтерфейсу;
- часовий пояс;
- формат дати;
- формат часу;
- регіональні параметри;
- поведінку застосунку під час запуску.

### 3.2. Appearance settings — зовнішній вигляд

Можуть містити:
- світлу тему;
- темну тему;
- системну тему;
- розмір тексту;
- щільність інтерфейсу;
- анімації;
- налаштування відображення.

### 3.3. Notification settings — сповіщення

Можуть містити:
- email-сповіщення;
- push-сповіщення;
- сповіщення всередині застосунку;
- маркетингові повідомлення;
- нагадування;
- частоту сповіщень.

### 3.4. Privacy settings — приватність

Можуть містити:
- видимість профілю;
- видимість активності;
- дозволи на пошук користувача;
- керування персональними даними;
- налаштування збору даних;
- дозволи на використання певних функцій.

### 3.5. Security settings — безпека

Можуть містити:
- зміну пароля;
- багатофакторну автентифікацію;
- passkeys;
- активні сеанси;
- довірені пристрої;
- резервні коди;
- історію входів.

### 3.6. Account settings — обліковий запис

Можуть містити:
- зміну email;
- зміну імені;
- керування номером телефону;
- керування підпискою;
- експорт даних;
- видалення облікового запису.

### 3.7. Accessibility settings — доступність

Можуть містити:
- зменшення анімацій;
- збільшення тексту;
- налаштування контрасту;
- параметри читання;
- альтернативні способи взаємодії.

Такі параметри доповнюють, але не замінюють базову доступність самого інтерфейсу.

## 4. Anatomy of a settings page — будова сторінки

Типова сторінка налаштувань складається з кількох основних частин.

    ┌────────────────────────────────────────┐
    │ Settings                               │
    │ Manage your preferences                │
    ├────────────────────────────────────────┤
    │                                        │
    │ General                                │
    │ Language                    [English⌄] │
    │ Time zone                [Europe/Kyiv⌄]│
    │                                        │
    │ Appearance                             │
    │ Theme                       [System⌄]  │
    │                                        │
    │ Notifications                           │
    │ Email notifications           [ ON ]   │
    │ Product updates               [ OFF ]  │
    │                                        │
    │                    [Save changes]      │
    └────────────────────────────────────────┘

Основні складові:

1. **Page heading** — заголовок сторінки.
2. **Supporting text** — коротке пояснення призначення налаштувань.
3. **Navigation** — меню категорій.
4. **Settings sections** — тематичні групи параметрів.
5. **Setting rows** — окремі рядки налаштувань.
6. **Controls** — перемикачі, списки, поля та інші елементи.
7. **Descriptions** — пояснення параметрів.
8. **Save actions** — кнопки збереження або скасування.
9. **Feedback messages** — повідомлення про стан операції.
10. **Danger zone** — окремий блок для важливих або руйнівних дій, якщо він потрібен.

Не кожна сторінка повинна мати окрему кнопку Save. Для деяких налаштувань доречне автоматичне збереження.

## 5. Information architecture — організація налаштувань

**Information architecture (IA)** — організація інформації та навігації так, щоб користувач міг швидко знаходити потрібні параметри.

Погано організована сторінка змушує користувача шукати потрібний перемикач серед десятків не пов'язаних між собою опцій.

### Основні принципи

- групуй параметри за призначенням;
- використовуй зрозумілі назви категорій;
- розміщуй найчастіше потрібні налаштування на помітному місці;
- відокремлюй небезпечні дії;
- не створюй категорії заради категорій;
- уникай дублювання одного параметра в кількох місцях;
- підтримуй послідовну структуру на різних сторінках.

### Приклад структури

    Settings
    ├── General
    │   ├── Language
    │   ├── Region
    │   └── Time zone
    ├── Appearance
    │   ├── Theme
    │   └── Display
    ├── Notifications
    │   ├── Email
    │   └── Push
    ├── Privacy
    │   ├── Profile visibility
    │   └── Data preferences
    ├── Security
    │   ├── Password
    │   └── Active sessions
    └── Account
        ├── Personal information
        └── Delete account

Це приклад, а не універсальна структура. Для невеликого застосунку достатньо кількох добре організованих секцій.

## 6. Settings navigation — навігація

Вибір навігації залежить від кількості налаштувань і складності продукту.

### 6.1. Single-page settings

Усі параметри розміщені на одній сторінці й поділені на секції.

Підходить для:
- невеликих застосунків;
- кількох десятків простих параметрів;
- налаштувань, які не потребують складної навігації.

Переваги:
- усе можна переглянути на одній сторінці;
- менше переходів;
- легко шукати параметри за допомогою браузера.

Недоліки:
- сторінка може стати довгою;
- складніше орієнтуватися за великої кількості опцій.

### 6.2. Sidebar navigation

Категорії розміщені в бічному меню.

Приклад:

    Settings
    ├── General
    ├── Appearance
    ├── Notifications
    ├── Privacy
    ├── Security
    └── Account

Підходить для:
- SaaS-платформ;
- адміністративних панелей;
- складних облікових записів;
- застосунків із багатьма категоріями.

### 6.3. Tabs

Tabs використовуються для перемикання між близькими за змістом категоріями.

Приклад:

    General | Appearance | Notifications

Використовуй tabs, коли категорії належать до одного логічного рівня.

Не використовуй їх як заміну повноцінній навігації, якщо категорій багато або вони мають різні рівні вкладеності.

### 6.4. Nested settings

Вкладені сторінки підходять для складних налаштувань.

Приклад:

    Settings → Security → Two-factor authentication

Рекомендації:
- забезпечуй зрозумілий шлях назад;
- показуй заголовок поточної сторінки;
- не створюй надмірно глибоку ієрархію;
- не змушуй користувача проходити багато рівнів заради простої зміни.

---

## 7. Setting row — рядок налаштування

**Setting row** — окремий рядок із назвою параметра, поясненням і контролом.

Типова структура:

    Email notifications
    Receive updates and important messages.

                                  [ ON ]

Рядок може містити:
- назву;
- короткий опис;
- поточне значення;
- перемикач або інший контрол;
- посилання на додаткові налаштування.

### UX-принципи

- назва має бути короткою та зрозумілою;
- опис повинен пояснювати наслідки зміни;
- контрол має відповідати типу параметра;
- пов'язані рядки повинні мати послідовне компонування;
- відстань між елементами повинна полегшувати сканування;
- довгі описи мають коректно переноситися на вузьких екранах.

Не роби кожен рядок окремою карткою, якщо це створює візуальний шум.

---

## 8. Toggle / Switch — перемикач

Перемикач використовується для параметра, який має два стани: увімкнено або вимкнено.

Приклади:
- темна тема;
- email-сповіщення;
- автоматичне відтворення;
- певна необов'язкова функція.

### Приклад

    Dark mode

    Use a dark appearance throughout the app.

    [ OFF ]

### Коли використовувати

Switch доречний, якщо зміна стану відбувається одразу або має чітку двійкову логіку.

Не використовуй перемикач для вибору одного з кількох варіантів.

### UX-принципи

- пояснюй призначення перемикача;
- забезпечуй зрозуміле представлення поточного стану;
- не покладайся лише на колір;
- підтримуй клавіатурне керування;
- показуй помилку, якщо зміна не збереглася;
- якщо дія має серйозні наслідки, пояснюй їх до зміни стану.

### Switch та Checkbox — різниця

**Switch** зазвичай означає ввімкнення або вимкнення функції.

**Checkbox** використовується для вибору одного або кількох пунктів, особливо коли вибір підтверджується окремою кнопкою.

Це поширена конвенція, а не абсолютне правило. Важливо, щоб поведінка відповідала очікуванням користувача.

---

## 9. Checkbox — прапорець

Checkbox дозволяє вибрати або скасувати вибір окремого параметра.

Приклад:

    Preferences

    [✓] Send me product updates
    [ ] Include my profile in public search
    [✓] Remember my display preferences

### Коли використовувати

- для незалежних параметрів;
- для вибору кількох значень;
- для згоди або підтвердження, коли це відповідає юридичним і продуктовим вимогам;
- у формах, де зміни застосовуються після натискання Save.

### UX-принципи

- пов'язуй checkbox із текстовим підписом;
- роби всю область підпису зручною для натискання, якщо це доречно;
- не встановлюй згоду на необов'язкові маркетингові повідомлення автоматично;
- не приховуй важливі умови;
- розрізняй обов'язковий вибір і необов'язкові налаштування.

---

## 10. Radio buttons — вибір одного варіанта

Radio buttons використовуються, коли користувач повинен вибрати лише один варіант із невеликої кількості.

Приклад:

    Theme

    (●) Light
    ( ) Dark
    ( ) System default

### Коли використовувати

- коли всі варіанти мають бути видимими одночасно;
- коли кількість варіантів невелика;
- коли користувачеві потрібно легко порівняти опції.

### Коли краще використовувати Select

Якщо варіантів багато, випадаючий список може бути компактнішим.

### UX-принципи

- показуй усі важливі варіанти;
- пояснюй незрозумілі назви;
- забезпечуй клавіатурне керування;
- використовуй чіткий стан вибору;
- не змушуй користувача вгадувати наслідки кожного варіанта.

---

## 11. Select / Dropdown — вибір зі списку

Select дозволяє вибрати одне значення з набору варіантів.

Приклади:
- мова;
- часовий пояс;
- регіон;
- формат дати;
- частота сповіщень.

### Приклад

    Language

    [Ukrainian                         ▼]

### UX-принципи

- використовуй зрозумілі назви;
- сортуй варіанти логічно;
- не показуй надто довгий список без потреби;
- для великої кількості варіантів передбач пошук, якщо це допомагає;
- показуй поточне значення;
- забезпечуй клавіатурну доступність.

Якщо варіантів лише два або три й усі мають бути видимими, radio buttons можуть бути зрозумілішими за dropdown.

---

## 12. Slider — повзунок

Slider дозволяє вибрати числове значення або позицію в діапазоні.

Приклади:
- гучність;
- яскравість;
- масштаб;
- інтенсивність ефекту;
- інший безперервний параметр.

### Приклад

    Text size

    Small ───────●──────── Large

### UX-принципи

- показуй поточне значення, якщо воно важливе;
- позначай мінімум і максимум;
- забезпечуй керування клавіатурою;
- не використовуй slider для параметрів, де потрібна точність без можливості ввести значення;
- передбач числове поле, якщо це полегшує точний вибір.

Slider не є найкращим вибором для кожного числового налаштування. Якщо користувачеві потрібно встановити точне значення, поле введення може бути кращим.

---

## 13. Appearance settings — налаштування зовнішнього вигляду

Налаштування зовнішнього вигляду змінюють те, як користувач бачить застосунок.

Типові параметри:
- тема;
- розмір тексту;
- щільність інтерфейсу;
- анімації;
- контраст;
- спосіб відображення списків.

### Theme selector

Приклад:

    Appearance

    Theme

    (●) System
    ( ) Light
    ( ) Dark

### UX-принципи

- надавай системну тему як варіант, якщо це доречно;
- показуй результат зміни відразу, коли це безпечно;
- зберігай вибір користувача;
- забезпечуй достатній контраст у всіх темах;
- перевіряй усі стани компонентів у світлій і темній темах;
- не вважай темну тему автоматично доступнішою для всіх.

### Reduced motion

Налаштування зменшення анімацій може допомагати користувачам, чутливим до руху.

Важливо: базова реалізація також повинна враховувати системний параметр `prefers-reduced-motion`, а не покладатися виключно на власний перемикач у застосунку.

---

## 14. Notification settings — налаштування сповіщень

Користувач повинен мати контроль над типом і частотою повідомлень.

### Приклад структури

    Notifications

    Email notifications
    Receive important updates by email.

    [ ON ]

    Product announcements
    Receive news about new features.

    [ OFF ]

    Weekly summary
    Get a summary of your activity.

    [ ON ]

### Принципи дизайну

- розділяй типи сповіщень;
- пояснюй, що саме буде надсилатися;
- відрізняй важливі системні повідомлення від маркетингових;
- не використовуй незрозумілі назви;

- показуй поточні налаштування;
- повідомляй про помилки збереження.

## 15. Privacy settings — налаштування приватності

- забезпечуй зрозумілий поточний стан;
- не збирай зайві дані;

    ( ) Approved users only

    [Save changes]

Це лише приклад. Конкретні варіанти залежать від функцій продукту.

Не роби чутливу інформацію доступною всім за замовчуванням без чіткої потреби та належного інформування користувача.

## 17. Save changes vs Autosave — збереження змін

Це одне з ключових рішень у дизайні налаштувань.

### 17.1. Explicit save — явне збереження

Користувач змінює кілька параметрів, а потім натискає Save changes.

Приклад:

    Language
    [Ukrainian ▼]

    Time zone
    [Europe/Kyiv ▼]

    [Cancel] [Save changes]

Переваги:
- користувач контролює момент збереження;
- можна змінити кілька значень перед застосуванням;
- простіше скасувати незбережені зміни.

Недоліки:
- користувач може забути натиснути Save;
- потрібно обробляти незбережені зміни;
- результат не завжди видно одразу.

### 17.2. Autosave — автоматичне збереження

Зміни зберігаються автоматично після зміни параметра або завершення введення.

Приклад:

    Theme
    [Dark ▼]

    Changes saved.

Переваги:
- менше дій;
- швидкий зворотний зв'язок;
- зручно для незалежних налаштувань.

Недоліки:
- випадкову зміну можна зберегти відразу;
- помилка збереження може бути неочевидною;
- користувач може не розуміти, коли саме зміна застосувалася.

### Як вибрати

Використовуй явне збереження, коли:
- змінюється багато пов'язаних параметрів;
- зміни потрібно перевірити перед застосуванням;
- скасування є важливим.

Використовуй autosave, коли:
- параметри незалежні;
- результат легко перевірити;
- зміна може бути застосована відразу;
- система чітко показує стан збереження.

Не змішуй обидві моделі без пояснення. Користувач повинен розуміти, коли його зміни набувають чинності.

## 18. Unsaved changes — незбережені зміни

**Dirty state** — стан, коли користувач змінив значення, але зміни ще не збережені.

Типовий сценарій:

    Language
    [English ▼]

    Current value: Ukrainian
    New value: English

    [Cancel] [Save changes]

Якщо користувач намагається залишити сторінку, можна показати попередження, коли втрата змін справді має значення.

Приклад:

    You have unsaved changes.

    Leave this page without saving?

    [Stay on page] [Leave without saving]

### UX-принципи

- попереджай лише тоді, коли є незбережені зміни;
- не показуй попередження без причини;
- чітко розрізняй Stay і Leave;
- не змушуй користувача повторно вводити всі дані після помилки;
- якщо можливо, забезпечуй зрозуміле відновлення попереднього стану.

## 19. Reset settings — скидання налаштувань

Reset повертає параметри до початкових значень.

Ця дія може вплинути на багато налаштувань одночасно, тому її потрібно проєктувати уважно.

### Приклад

    Reset appearance settings

    This will restore the default theme and display preferences.

    [Cancel] [Reset settings]

### UX-принципи

- пояснюй, які саме параметри буде скинуто;
- не використовуй загальне Reset, якщо область дії незрозуміла;
- відокремлюй скидання від видалення даних;
- підтверджуй дію, якщо її наслідки значні;
- повідомляй про завершення операції;
- не скидай інші категорії налаштувань без потреби.

Для безпечних і легко зворотних параметрів окреме підтвердження може бути зайвим. Рішення залежить від масштабу наслідків.

## 20. Destructive actions — небезпечні дії

До таких дій можуть належати:
- видалення облікового запису;
- відкликання важливих дозволів;
- завершення всіх сеансів;
- видалення збережених даних;
- скидання критичних параметрів.

### Danger zone

У складному меню налаштувань такі дії можна групувати окремо.

Приклад:

    Danger zone

    Delete account

    Permanently remove your account and associated data,
    subject to the service's retention policies.

    [Delete account]

### UX-принципи

- відокремлюй небезпечні дії від звичайних;
- використовуй точні назви;
- пояснюй наслідки;
- забезпечуй підтвердження, якщо воно виправдане;
- не маскуй небезпечну дію під звичайне збереження;
- не використовуй неоднозначні кнопки на кшталт Continue без контексту;
- надавай зрозумілий шлях назад, якщо це можливо.

Підтвердження не повинно бути формальністю. Воно має допомагати користувачеві зрозуміти, що станеться.

## 21. Search settings — пошук налаштувань

У великому застосунку користувачеві може бути важко знайти конкретний параметр.

Пошук допомагає швидко перейти до потрібного налаштування.

Приклад:

    Search settings...
    [____________________________]

### Коли потрібен пошук

- категорій багато;
- налаштування розподілені між кількома сторінками;
- користувачі регулярно шукають конкретні параметри;
- назви параметрів можуть бути неочевидними.

## 22. Feedback states — зворотний зв'язок

Користувач повинен розуміти, що сталося після взаємодії з налаштуваннями.

### Default state

Параметр показує поточне значення.

### Changed state

Користувач змінив параметр, але результат ще не збережено.

### Saving state

Зміни надсилаються на сервер або застосовуються.

    Saving changes...

### Success state

Зміни успішно збережено.

    Settings saved.

### Error state

Зміни не вдалося зберегти.

    We couldn't save your settings.
    Please try again.

### Disabled state

Параметр тимчасово недоступний.

Якщо причина не очевидна, поясни її.

### UX-принципи

- повідомляй про важливі зміни;
- не показуй успіх до підтвердження операції;
- не залишай користувача з нескінченним завантаженням;
- не стирай введені значення після помилки;
- зберігай зрозумілий зв'язок між повідомленням і параметром.

## 25. Accessibility — доступність налаштувань

Settings UI часто містить багато інтерактивних елементів, тому доступність особливо важлива.

### Основні правила

- використовуй семантичні HTML-елементи;
- пов'язуй кожен контрол із назвою;
- додавай пояснення там, де вони потрібні;
- забезпечуй керування клавіатурою;
- підтримуй видимий фокус;
- не передавай стан лише кольором;
- забезпечуй достатній контраст;
- використовуй зрозумілі повідомлення про помилки;
- не змінюй стан без очікуваного зворотного зв'язку;
- перевіряй доступність діалогів підтвердження.

### Приклад доступного перемикача

    <div class="setting-row">
      <div>
        <label for="email-notifications">
          Email notifications
        </label>

        <p id="email-help">
          Receive important updates by email.
        </p>
      </div>

      <input
        id="email-notifications"
        name="emailNotifications"
        type="checkbox"
        aria-describedby="email-help"
      >
    </div>

У цьому прикладі використано звичайний checkbox. За допомогою CSS його можна оформити як switch, зберігаючи зрозумілу семантику та клавіатурну поведінку.

### Клавіатурна навігація

Користувач повинен мати змогу:
- переходити між контролами;
- змінювати значення;
- відкривати й закривати меню;
- активувати кнопки;
- працювати з діалогами;
- бачити фокус;
- зберігати або скасовувати зміни.

### Важливо

Візуально красивий перемикач не є доступним автоматично. Перевіряй його поведінку, семантику, стан і взаємодію з допоміжними технологіями.

## 29. Common mistakes — типові помилки

### UX-помилки

- усі налаштування розміщені без групування;
- назви параметрів незрозумілі;
- користувач не розуміє наслідків перемикання;
- немає повідомлення про збереження;
- autosave працює непомітно;
- кнопка Save губиться серед інших дій;
- скидання налаштувань не пояснює наслідків;
- небезпечні дії розміщені поруч зі звичайними;
- надто багато вкладених категорій;
- пошук налаштувань відсутній там, де він справді потрібний.

### UI-помилки

- контролі мають різні розміри без причини;
- відступи непослідовні;
- перемикачі надто дрібні;
- описи мають низький контраст;
- довгі тексти ламають компонування;
- відсутні стани завантаження та помилок;
- sidebar погано працює на мобільних пристроях;
- активна категорія не виділена;
- діалог підтвердження важко прочитати.

### Accessibility-помилки

- контрол не має зрозумілої назви;
- фокус клавіатури не видно;
- стан передається лише кольором;
- діалог не керує фокусом належним чином;
- помилки не пов'язані з відповідними полями;
- користувач не може змінити значення без миші.

### Privacy та security-помилки

- чутливі налаштування важко знайти;
- важливі зміни не мають зрозумілого зворотного зв'язку;
- небезпечні дії не пояснюють наслідків;
- користувач не розуміє, які дані доступні іншим;
- налаштування безпеки змішані з неважливими параметрами без логічного групування.

## 30. Settings UI checklist

Перед завершенням дизайну перевір:

### Information architecture

- [ ] Налаштування згруповані за призначенням.
- [ ] Назви категорій зрозумілі.
- [ ] Немає зайвого дублювання.
- [ ] Навігація відповідає кількості параметрів.
- [ ] Важливі параметри легко знайти.

### Controls

- [ ] Для кожного параметра використано відповідний контрол.
- [ ] Поточне значення зрозуміле.
- [ ] У перемикачів є зрозумілі стани.
- [ ] Вибір одного варіанта не плутається з вибором кількох.
- [ ] Кожен контрол має доступну назву.

### Saving

- [ ] Зрозуміло, коли зміни зберігаються.
- [ ] Є стан завантаження, якщо він потрібний.
- [ ] Успіх підтверджується після завершення операції.
- [ ] Помилки пояснюють, що робити далі.
- [ ] Незбережені зміни не втрачаються непомітно.

### Safety

- [ ] Скидання пояснює, які параметри зміняться.
- [ ] Небезпечні дії візуально відокремлені.
- [ ] Підтвердження відповідає реальному ризику.
- [ ] Налаштування приватності зрозумілі.
- [ ] Налаштування безпеки легко знайти.

### Responsive

- [ ] Сторінка працює на мобільному пристрої.
- [ ] Контролі не перекривають текст.
- [ ] Довгі описи коректно переносяться.
- [ ] Кнопки залишаються доступними.
- [ ] Немає горизонтального прокручування без потреби.

### Accessibility

- [ ] Інтерфейс працює з клавіатури.
- [ ] Фокус помітний.
- [ ] Контраст достатній.
- [ ] Стани не передаються лише кольором.
- [ ] Діалоги доступні.
- [ ] Підписи та пояснення пов'язані з контролами.

## 31. Як тренуватися на практиці

Створи три варіанти сторінки налаштувань для одного вигаданого застосунку.

### Варіант A — Minimal settings

Елементи:
- мова;
- тема;
- часовий пояс;
- email-сповіщення;
- кнопка збереження.

Мета: навчитися групувати параметри та працювати з різними контролами.

### Варіант B — SaaS settings

Елементи:
- sidebar;
- General;
- Appearance;
- Notifications;
- Privacy;
- Security;
- Account.

Мета: навчитися проєктувати інформаційну архітектуру й навігацію.

### Варіант C — Advanced settings

Елементи:
- пошук налаштувань;
- autosave;
- повідомлення про стан збереження;
- незбережені зміни;
- діалоги підтвердження;
- небезпечні дії;
- адаптивна навігація.

Мета: навчитися працювати зі складними сценаріями та станами.

### Що порівнювати

- наскільки швидко можна знайти потрібний параметр;
- чи зрозуміло, що він змінює;
- чи відповідає контрол типу налаштування;
- чи зрозуміло, коли зміни застосовуються;
- чи легко скасувати дію;
- чи зручно користуватися сторінкою на мобільному пристрої;
- чи доступні всі функції з клавіатури.

## 35. Головне, що потрібно запам'ятати

1. **Settings UI повинен давати користувачеві зрозумілий контроль над поведінкою застосунку.**
2. Групуй параметри за призначенням і використовуй звичні назви категорій.
3. Вибирай контрол відповідно до типу налаштування.
4. Пояснюй наслідки змін, особливо для приватності та безпеки.
5. Чітко визначай, коли застосунок зберігає зміни.
6. Передбачай loading, error, success і dirty states.
7. Не перевантажуй сторінку картками, вкладками та зайвими описами.
8. Небезпечні дії повинні бути відокремлені та зрозумілими.
9. Доступність і адаптивність потрібно враховувати від початку.
10. Найкраще налаштування — те, яке легко знайти, просто змінити й легко зрозуміти.

**Основний принцип:** хороший інтерфейс налаштувань дозволяє користувачеві знайти потрібний параметр, зрозуміти його вплив і впевнено змінити його без зайвих дій.
