# 02. Landing Page

Landing page (посадкова сторінка) — це вебсторінка, створена для презентації продукту, послуги, події або пропозиції та спонукання користувача виконати конкретну дію.

Landing page зазвичай має одну головну мету:

- зареєструвати користувача;
- продати продукт;
- отримати заявку;
- запропонувати безкоштовний пробний період;
- зібрати email;
- запросити користувача на подію;
- завантажити застосунок;
- пояснити цінність сервісу.

Landing page може бути окремою сторінкою сайту або головною сторінкою невеликого продукту.

Основні елементи landing page:

    Header
    Hero section
    Value proposition
    Features
    Benefits
    Social proof
    Testimonials
    How it works
    Pricing
    FAQ
    Call to action (CTA)
    Footer

Головне завдання дизайнера — організувати контент так, щоб користувач швидко зрозумів пропозицію, побачив її цінність і міг легко виконати цільову дію.

### Що потрібно пам'ятати

• Landing page створюється навколо конкретної мети, а не просто для демонстрації дизайну.

• Користувач повинен швидко зрозуміти, що пропонується, кому це потрібно та яку проблему вирішує продукт.

• Hero section — перша велика секція сторінки, яка представляє основну пропозицію.

• Headline повідомляє головну ідею сторінки.

• Subheadline доповнює заголовок і пояснює цінність пропозиції.

• CTA (Call to Action) — елемент, який спонукає користувача виконати дію.

• Primary CTA повинен візуально виділятися серед інших інтерактивних елементів.

• Value proposition пояснює, чому користувачеві варто обрати продукт.

• Features описують можливості продукту, а benefits — користь для користувача.

• Social proof допомагає сформувати довіру через відгуки, результати, статистику або відомі клієнтські компанії.

• Above the fold — частина сторінки, яку видно без прокручування на конкретному екрані.

• Важливий контент не обов'язково повинен повністю розміщуватися above the fold. Сторінка має спонукати до природного продовження перегляду.

• Кожна секція повинна підтримувати основну мету сторінки.

• Надмірна кількість CTA, анімацій, кольорів і конкуруючих повідомлень може відволікати від головної дії.

• Landing page повинна бути зрозумілою та зручною на мобільних пристроях.

• Висока конверсія залежить не лише від дизайну, а й від якості пропозиції, контенту, швидкості завантаження та відповідності очікуванням аудиторії.

# Landing Page vs Website

Landing page та звичайний багатосторінковий сайт мають різні цілі.

## Landing Page

Landing page зазвичай зосереджена на одній пропозиції та одній головній конверсійній меті.

Наприклад:

    Product
       ↓
    Value proposition
       ↓
    Benefits
       ↓
    Social proof
       ↓
    CTA
       ↓
    Conversion

Приклади цілей:

    Sign up
    Buy now
    Start free trial
    Book a demo
    Download app

## Multi-page Website

Багатосторінковий сайт може мати декілька рівнозначних цілей.

Наприклад:

    Home
    About
    Services
    Blog
    Pricing
    Contact

Користувач може переходити між різними розділами та досліджувати компанію.

## Основна різниця

    Landing page → focused conversion

    Multi-page website → multiple user goals

Landing page може входити до складу великого сайту.

---

# Conversion Goal

Conversion goal — конкретна дія, яку бізнес або продукт хоче отримати від користувача.

Приклади:

    Purchase
    Registration
    Email subscription
    Contact form submission
    Demo booking
    App download

Перед створенням дизайну потрібно визначити основну конверсійну мету.

Наприклад, для освітньої платформи:

    Goal:
        Register for a free course

    Primary CTA:
        Start learning

    Secondary CTA:
        Explore courses

У цьому випадку дизайн повинен допомагати користувачеві зрозуміти цінність навчання та перейти до реєстрації.

## Primary Conversion

Primary conversion — головна цільова дія сторінки.

Наприклад:

    Start free trial

## Secondary Conversion

Secondary conversion — додаткова дія для користувачів, які ще не готові виконати основну.

Наприклад:

    View demo
    Learn more
    Explore features

Вторинна дія не повинна візуально конкурувати з головною без необхідності.

---

# Conversion Funnel

Conversion funnel — послідовність кроків, які користувач проходить до виконання цільової дії.

Приклад:

    User visits landing page
              ↓
    Understands the offer
              ↓
    Explores benefits
              ↓
    Trusts the product
              ↓
    Clicks primary CTA
              ↓
    Completes registration

На кожному етапі користувач може залишити сторінку.

Дизайн повинен зменшувати непотрібні перешкоди:

    unclear message
        ↓
    user confusion

    too many fields
        ↓
    form abandonment

    hidden CTA
        ↓
    fewer clicks

    missing trust signals
        ↓
    user hesitation

Важливо не робити висновки про причини низької конверсії лише за зовнішнім виглядом сторінки. Для цього використовують аналітику, дослідження та тестування.

---

# Landing Page Structure

Типова landing page може складатися з таких секцій:

    1. Header
    2. Hero
    3. Benefits
    4. Features
    5. How it works
    6. Product preview
    7. Social proof
    8. Pricing
    9. FAQ
    10. Final CTA
    11. Footer

Це не обов'язковий шаблон.

Набір секцій залежить від:

    product type
    target audience
    conversion goal
    user expectations
    complexity of the offer

Наприклад, проста сторінка реєстрації на подію може містити лише:

    Header
    Hero
    Event details
    Speakers
    Registration form
    Footer

А landing page складного SaaS-продукту може потребувати докладнішого пояснення можливостей, інтеграцій, тарифів і безпеки.

---

# Header

Header — верхня частина сторінки, яка зазвичай містить логотип, навігацію та доступ до головної дії.

Типова структура:

    Header
    ├── Logo
    ├── Navigation
    ├── Secondary link
    └── Primary CTA

Приклад:

    Logo | Features | Pricing | About | Sign up

## Основні елементи

### Logo

Логотип допомагає ідентифікувати продукт або компанію.

Зазвичай розташовується ліворуч у desktop layout.

### Navigation

Навігація дозволяє перейти до важливих секцій або сторінок.

Приклади:

    Features
    Pricing
    About
    Contact

На невеликій landing page навігація може використовувати anchor links.

    href="#features"
    href="#pricing"
    href="#faq"

### Header CTA

Header може містити кнопку головної дії.

Наприклад:

    Start free trial

## Правила дизайну

• Header не повинен відволікати від головної пропозиції.

• Кількість пунктів навігації варто обмежувати найважливішими.

• Логотип повинен мати зрозумілий зв'язок із головною сторінкою.

• На мобільних пристроях навігація може перетворюватися на компактне меню.

• Якщо сторінка має одну вузьку ціль, складна навігація може бути зайвою.

---

# Hero Section

Hero section — головна вступна секція landing page.

Зазвичай вона розташовується одразу після header і містить найважливіше повідомлення.

Типова структура:

    Hero
    ├── Eyebrow
    ├── Headline
    ├── Subheadline
    ├── Primary CTA
    ├── Secondary CTA
    ├── Trust indicator
    └── Visual

Приклад:

    Learn programming by building real projects.

    Practice JavaScript, React and Node.js
    with practical exercises and guided projects.

    [Start learning] [Explore curriculum]

## Eyebrow

Eyebrow — короткий текст над головним заголовком.

Він може позначати категорію продукту, нову функцію або коротку пропозицію.

Наприклад:

    NEW: Interactive learning platform

Eyebrow не повинен бути важливішим за headline.

## Headline

Headline — головний заголовок сторінки.

Він повинен передавати основну цінність продукту.

Слабкий варіант:

    Welcome to Our Platform

Більш інформативний варіант:

    Learn JavaScript by Building Real Projects

Другий варіант конкретніше повідомляє, що пропонує продукт і чим він відрізняється.

## Subheadline

Subheadline — додатковий текст, який розкриває headline.

Наприклад:

    Build practical web applications with guided exercises,
    code examples and step-by-step projects.

Subheadline може пояснювати:

    What the product does
    Who it is for
    How it helps
    What makes it different

## Hero Visual

Hero visual — основний візуальний елемент hero section.

Це може бути:

    Product screenshot
    Dashboard preview
    App mockup
    Illustration
    Photograph
    Video
    Abstract graphic

Візуал повинен підтримувати повідомлення, а не бути просто декорацією.

## Hero Layout

Поширені варіанти:

### Two-column layout

    ┌───────────────────┬───────────────────┐
    │                   │                   │
    │ Headline          │                   │
    │ Subheadline       │ Product preview   │
    │ CTA               │                   │
    │                   │                   │
    └───────────────────┴───────────────────┘

Цей варіант часто використовують для SaaS, освітніх продуктів та вебзастосунків.

### Centered layout

    ┌───────────────────────────────────────┐
    │                                       │
    │               Headline                │
    │              Subheadline              │
    │                  CTA                  │
    │                                       │
    │              Hero visual              │
    │                                       │
    └───────────────────────────────────────┘

Цей варіант добре підходить для простих пропозицій, продуктів і маркетингових сторінок.

### Full-width visual

    ┌───────────────────────────────────────┐
    │                Headline               │
    │               Subheadline             │
    │                   CTA                 │
    ├───────────────────────────────────────┤
    │                                       │
    │             Large visual              │
    │                                       │
    └───────────────────────────────────────┘

Великий візуал може демонструвати продукт або створювати сильний перший акцент.

## Що потрібно пам'ятати

• Hero повинен відповідати на питання «Що це?» і «Чому мені це потрібно?».

• Заголовок має бути помітним у візуальній ієрархії.

• CTA повинен бути зрозумілим і відповідати реальній дії.

• Не варто перевантажувати hero великою кількістю тексту.

• На мобільних пристроях текст і CTA повинні залишатися зручними для сприйняття.

# Value Proposition

Value proposition — чітке пояснення цінності продукту для користувача.

Вона відповідає на питання:

    What does the product offer?
    Who is it for?
    What problem does it solve?
    Why should the user care?

Приклад:

    Product:
        Online learning platform

    Audience:
        Beginner developers

    Problem:
        Difficulty applying theory in practice

    Value proposition:
        Learn web development by building practical projects.

Value proposition може бути представлена через headline, subheadline, benefits або окрему секцію.

## Unique Selling Proposition (USP)

USP — особлива перевага або характеристика, яка допомагає відрізнити продукт від альтернатив.

Наприклад:

    Generic:
        Learn programming online.

    More specific:
        Practice JavaScript through small projects
        with immediate feedback.

Не кожна перевага є унікальною. Формулювання USP має відповідати реальним можливостям продукту.

## Формула Value Proposition

Для початкового варіанта можна використовувати:

    We help [audience]
    achieve [desired outcome]
    through [product or method].

Наприклад:

    We help beginner developers build practical skills
    through guided programming projects.

Це робочий шаблон, а не обов'язкова формула.

# Features vs Benefits

Features — функції або можливості продукту.

Benefits — користь, яку отримує користувач від цих можливостей.

Наприклад:

    Feature:
        Progress tracking

    Benefit:
        Understand how much of the course
        has already been completed.

Інший приклад:

    Feature:
        Responsive dashboard

    Benefit:
        Check important information
        on desktop, tablet and mobile.

## Як показувати Features

Features часто оформлюють у вигляді карток.

    Features section
    ├── Feature card
    │   ├── Icon
    │   ├── Title
    │   └── Description
    ├── Feature card
    └── Feature card

Приклад:

    Project-based learning
    Practice concepts through complete applications.

    Progress tracking
    See completed lessons and remaining tasks.

    Guided exercises
    Follow practical steps from simple to complex.

## Правила дизайну

• Не обмежуйся переліком технічних можливостей.

• Пояснюй, чому кожна функція корисна.

• Використовуй однакову структуру карток.

• Не додавай багато непотрібних іконок.

• Виділяй найважливіші переваги, а не всі можливості одночасно.

---

# Benefits Section

Benefits section показує, як продукт допомагає користувачеві.

На відміну від простого переліку функцій, ця секція фокусується на результатах.

Наприклад:

    Learn at your own pace
    Build practical skills
    Track your progress
    Create a project portfolio

Поширені варіанти layout:

    3-column card grid
    2-column feature sections
    Icon + text list
    Alternating text and image
    Numbered benefits

## Alternating Layout

Контент і зображення можуть чергуватися між секціями.

    Section 1:
        Text | Image

    Section 2:
        Image | Text

    Section 3:
        Text | Image

Це створює ритм сторінки та допомагає уникнути монотонності.

Однак чергування не є самоціллю. Структура повинна допомагати сприймати інформацію.

# Call to Action (CTA)

CTA — елемент інтерфейсу, який пропонує користувачеві виконати конкретну дію.

Приклади:

    Get started
    Start free trial
    Create account
    Book a demo
    Download the app
    Buy now
    Join the course

CTA може бути кнопкою, посиланням або частиною форми.

## Primary CTA

Primary CTA — головна дія сторінки.

Приклад:

    [Start free trial]

Вона зазвичай має найвиразніший візуальний стиль серед кнопок у відповідному контексті.

## Secondary CTA

Secondary CTA — альтернативна дія.

Приклад:

    [Start free trial] [View demo]

Secondary CTA може мати outline, нейтральний фон або вигляд текстового посилання.

Не обов'язково використовувати два CTA. Якщо сторінка має одну очевидну дію, однієї кнопки може бути достатньо.

## CTA Copy

CTA copy — текст, який описує дію.

Менш конкретний варіант:

    Submit

Більш конкретні варіанти:

    Create account
    Book a demo
    Download guide

Текст повинен відповідати результату натискання.

## CTA Placement

CTA може розміщуватися:

    Header
    Hero
    After benefits
    After testimonials
    Pricing section
    Final CTA section

Повторення головного CTA в різних секціях може бути доречним для довгої сторінки.

Важливо, щоб кнопки вели до очікуваної дії, а не створювали суперечливі сценарії.

## CTA Visual Hierarchy

Для основного CTA важливі:

    Contrast
    Size
    Position
    Clear label
    Adequate spacing
    Visible focus state

Кнопка не повинна покладатися лише на колір для передавання свого призначення.

## CTA Accessibility

Необхідно забезпечити:

    Keyboard access
    Visible focus
    Sufficient contrast
    Clear accessible name
    Appropriate target size

Якщо елемент виконує дію, зазвичай доречний `<button>`.

Якщо елемент переходить на іншу сторінку або до секції, зазвичай доречний `<a>`.

---

# Above the Fold

Above the fold — область сторінки, яку користувач бачить без прокручування.

Вона залежить від:

    Screen size
    Viewport height
    Browser interface
    Device orientation
    Content size

Не існує одного універсального розміру above the fold.

## Що варто показувати

Зазвичай важливо, щоб у першій видимій області були доступні:

    Main headline
    Supporting message
    Primary CTA
    Relevant visual or context

Це не означає, що весь важливий контент повинен уміститися на одному екрані.

Користувачі прокручують сторінки, якщо бачать зрозумілу цінність і логічне продовження.

## Типові помилки

❌ Великий декоративний блок, який витісняє зміст.

❌ Заголовок без пояснення пропозиції.

❌ CTA, який не видно серед інших елементів.

❌ Надмірна кількість тексту у вступній секції.

❌ Приховування важливої інформації лише заради ефектного першого екрана.

---

# Below the Fold

Below the fold — контент, який стає видимим після прокручування сторінки.

Тут можна поступово пояснювати пропозицію.

Типовий сценарій:

    Hero
      ↓
    Benefits
      ↓
    Features
      ↓
    How it works
      ↓
    Product preview
      ↓
    Social proof
      ↓
    Pricing
      ↓
    FAQ
      ↓
    Final CTA

Послідовність може змінюватися.

Наприклад, якщо користувачеві потрібно швидко побачити вартість, pricing section може розташовуватися ближче до початку.

Головне — відповідати на питання користувача в логічному порядку.

---

# Social Proof

Social proof — елементи, які допомагають користувачеві оцінити надійність продукту через досвід інших людей або організацій.

Приклади:

    Customer testimonials
    Customer logos
    Verified reviews
    User statistics
    Case studies
    Ratings
    Customer success stories

## Testimonials

Testimonial — відгук користувача про продукт або послугу.

Типова структура:

    Testimonial
    ├── Quote
    ├── Person name
    ├── Role or context
    └── Photo, if appropriate

Приклад:

    "The platform helped me organize
    my learning and track my progress."

    — Example user, course participant

Для реального продукту відгуки мають бути справжніми та використаними з відповідним дозволом.

## Customer Logos

Логотипи клієнтів можуть показувати, хто використовує продукт.

Вони особливо поширені в B2B і SaaS landing pages.

Важливо не створювати хибного враження про співпрацю з компаніями.

## Statistics

Приклади:

    Number of active users
    Number of completed projects
    Customer satisfaction
    Number of supported integrations

Статистику потрібно підтверджувати реальними даними.

## Trust Signals

Trust signals — елементи, які допомагають зменшити невизначеність.

Наприклад:

    Clear pricing
    Contact information
    Privacy policy
    Security information
    Refund policy
    Transparent terms
    Real testimonials

Trust signals повинні бути релевантними продукту та не створювати неправдивих обіцянок.

# How It Works

How it works — секція, яка пояснює процес використання продукту.

Вона особливо корисна для сервісів зі складнішим сценарієм.

Приклад:

    1. Create an account
              ↓
    2. Choose a course
              ↓
    3. Build your first project

Кожен крок може містити:

    Number
    Title
    Description
    Icon or illustration

## Layout

Поширені варіанти:

    Horizontal steps
    Vertical steps
    Numbered cards
    Timeline
    Image + text

Для трьох кроків на desktop можна використовувати три колонки.

На мобільному пристрої ці кроки часто краще розмістити вертикально.

## Основне правило

Пояснюй процес настільки докладно, наскільки потрібно для прийняття рішення.

Не створюй складну інфографіку для дії, яку можна пояснити одним реченням.

# Product Preview

Product preview — візуальна демонстрація продукту.

Це може бути:

    Dashboard screenshot
    Application interface
    Mobile app mockup
    Video demonstration
    Interactive prototype
    Workflow illustration

## Для чого потрібен Product Preview

Він допомагає користувачеві зрозуміти:

    What the product looks like
    How the interface is organized
    What the product can do
    How the user will interact with it

Для цифрового продукту справжній скриншот інтерфейсу часто інформативніший за абстрактну ілюстрацію.

## Правила

• Використовуй зображення, які відповідають реальному продукту.

• Не показуй неіснуючі можливості.

• Не розміщуй текст на скриншоті настільки дрібним, щоб він став беззмістовним.

• Оптимізуй розмір зображень.

• Для декоративних зображень використовуй відповідний порожній `alt`, якщо вони не додають змісту.

• Для змістовних зображень надавай текстовий опис.

# Pricing Section

Pricing section показує вартість продукту або доступні тарифні плани.

Особливо важлива для SaaS, підписок, онлайн-курсів та цифрових сервісів.

Типова структура:

    Pricing
    ├── Free plan
    ├── Pro plan
    └── Business plan

Тарифна картка може містити:

    Plan name
    Price
    Billing period
    Short description
    Features
    CTA
    Additional terms

## Pricing Card

Приклад структури:

    Pro

    $19 / month

    For individual users

    ✔ Unlimited projects
    ✔ Progress tracking
    ✔ Priority support

    [Choose Pro]

Це умовний приклад структури, а не рекомендація конкретної ціни.

## Recommended Plan

Один тариф іноді виділяють як рекомендований.

Для цього використовують:

    Border
    Background
    Badge
    Stronger CTA

Однак виділення повинно відповідати реальній пропозиції та не вводити користувача в оману.

## Pricing UX

Користувач повинен розуміти:

    What is included
    How much it costs
    How often payment occurs
    Whether a trial is available
    How cancellation works
    What limitations apply

Приховані платежі та незрозумілі умови погіршують довіру.

## Коли Pricing не потрібен

Не кожна landing page повинна містити ціни.

Наприклад, сторінка запису на консультацію може мати CTA:

    Book a consultation

а вартість пояснюватися в іншому місці або під час контакту — якщо це відповідає очікуванням користувача.

# FAQ Section

FAQ (Frequently Asked Questions) — секція з відповідями на поширені запитання.

Вона допомагає усунути сумніви перед виконанням цільової дії.

Приклади запитань:

    Who is this product for?
    Is a free trial available?
    Can I cancel my subscription?
    What payment methods are supported?
    Do I need prior experience?
    How can I contact support?

## FAQ Layout

Поширені варіанти:

    Accordion
    Question-and-answer list
    Two-column FAQ
    Categorized questions

Accordion дозволяє показувати запитання постійно, а відповіді — за потреби.

## Accordion UX

Необхідно забезпечити:

    Clear question labels
    Visible expand/collapse state
    Keyboard interaction
    Appropriate semantic controls
    Understandable focus state

Не ховай за FAQ інформацію, без якої користувач не може зрозуміти основну пропозицію.

FAQ повинен доповнювати сторінку, а не замінювати необхідний основний контент.

Типова структура:

    Headline
    Supporting text
    Primary CTA

Приклад:

    Ready to start learning?

    your development skills step by step.

Final CTA може бути доречним після того, як користувач уже ознайомився з перевагами, відгуками та умовами.

Не потрібно створювати штучний тиск або вигадані обмеження.

## Основні правила

• Використовуй зрозумілі назви посилань.

# Visual Hierarchy

Visual hierarchy — принцип організації елементів за важливістю.

Вона допомагає користувачеві швидко визначити:

    What is most important?
    What should I read first?
    What can I do next?
    Where should I look?

Основні засоби:

    Typography
    Size
    Weight
    Color
    Contrast
    Spacing
    Position
    Alignment
    Grouping

Наприклад:

    1. Headline
    2. Supporting text
    3. Primary CTA
    4. Product visual
    5. Secondary information

Це один із можливих варіантів, а не універсальний порядок для всіх сторінок.

## Typography Hierarchy

Для тексту можуть використовуватися різні рівні:

    H1 → main headline
    H2 → section heading
    H3 → subsection heading
    Body → main content
    Small text → supporting information

Розмір і вага шрифту повинні підтримувати структуру документа.

## Contrast Hierarchy

Вищий контраст може привертати увагу до важливих елементів.

Наприклад:

    Primary CTA → strong contrast
    Secondary CTA → moderate contrast
    Supporting text → readable neutral color

Не знижуй контраст звичайного тексту лише для того, щоб зробити сторінку візуально легкою.

# Layout and Spacing

Layout — спосіб організації елементів у просторі.

Landing page зазвичай складається з вертикально розташованих секцій.

    Page
    ├── Header
    ├── Hero
    ├── Benefits
    ├── Features
    ├── Social proof
    ├── Pricing
    ├── FAQ
    └── Footer

## Container

Container обмежує ширину контенту та допомагає підтримувати читабельну структуру.

Приклад CSS:

    .container {
        width: min(100% - 2rem, 72rem);
        margin-inline: auto;
    }

Тут:

    100% - 2rem → залишає відступи з боків
    72rem        → максимальна ширина
    auto         → центрує контейнер

## Section Spacing

Відступи між секціями створюють візуальний ритм.

Приклад:

    .section {
        padding-block: 5rem;
    }

    .section__title {
        margin-bottom: 1.5rem;
    }

Значення потрібно адаптувати до контенту та розмірів екрана.

## Grid

Grid часто використовують для карток можливостей, тарифів і відгуків.

Приклад:

    .features {
        display: grid;
        grid-template-columns: repeat(3, minmax(0, 1fr));
        gap: 1.5rem;
    }

Для мобільних екранів:

    @media (max-width: 48rem) {
        .features {
            grid-template-columns: 1fr;
        }
    }

У production-проєкті breakpoint варто визначати відповідно до того, коли конкретний layout перестає бути зручним.

## Whitespace

Whitespace — вільний простір між елементами.

Він допомагає:

    Separate sections
    Group related content
    Improve readability
    Emphasize important elements
    Reduce visual clutter

Whitespace не обов'язково має бути білим. Це просто простір, вільний від контенту.

Колір допомагає сформувати візуальну ідентичність і розрізняти елементи за функцією.

На landing page можуть використовуватися:

    Brand colors

    Accent color
    Background colors

    Background:

    Surface:

    Text:

Основний CTA часто використовує primary або accent color.

Важливо перевіряти:

    Hover state
    Focus state

# Typography

Typography — система вибору та організації тексту.

Для landing page важливі:

    Font family
    Font size
    Font weight
    Line height
    Letter spacing
    Text width
    Heading hierarchy

## Headline

Заголовок повинен привертати увагу та залишатися читабельним на різних екранах.

Приклад:

    .hero__title {
        max-width: 12ch;
        font-size: clamp(2.25rem, 5vw, 4.5rem);
        line-height: 1.05;
        letter-spacing: -0.03em;
    }

`clamp()` дозволяє змінювати розмір шрифту залежно від ширини viewport у заданих межах.

`max-width: 12ch` обмежує ширину заголовка приблизно за шириною символів, що допомагає контролювати перенесення рядків.

Це приклад, який потрібно адаптувати до шрифту та конкретного тексту.

## Body Text

Основний текст повинен бути зручним для читання.

Важливо:

    Adequate font size
    Comfortable line height
    Readable line length
    Sufficient contrast
    Clear paragraph spacing

Не використовуй надто дрібний текст для важливої інформації.

## Typography Consistency

Заздалегідь визначені текстові стилі допомагають підтримувати узгодженість:

    Display
    H1
    H2
    H3
    Body large
    Body
    Small
    Caption

У design system ці стилі можна оформити як типографічні токени.

# Responsive Landing Page

Responsive design — адаптація інтерфейсу до різних розмірів екрана та умов використання.

Landing page повинна працювати на:

    Desktop
    Laptop
    Tablet
    Mobile

## Desktop

На великих екранах можна використовувати:

    Two-column hero
    Multi-column feature grid
    Wide product screenshots
    Horizontal navigation

## Tablet

Може знадобитися:

    Smaller column gaps
    Reduced heading size
    Two-column card layout
    Adjusted section spacing

## Mobile

Часто використовуються:

    Single-column layout
    Stacked CTA buttons
    Compact navigation
    Full-width form controls
    Smaller horizontal padding
    Simplified decorative visuals

## Responsive Hero

Desktop:

    ┌─────────────────┬─────────────────┐
    │ Text            │ Visual          │
    └─────────────────┴─────────────────┘

Mobile:

    ┌─────────────────┐
    │ Text            │
    │ CTA             │
    │ Visual          │
    └─────────────────┘

Порядок елементів залежить від змісту.

Іноді на мобільному пристрої доцільно розмістити візуал перед CTA, якщо це допомагає краще зрозуміти продукт.

## Mobile-first

Mobile-first — підхід, за якого спочатку проєктують інтерфейс для невеликих екранів, а потім розширюють його для більших.

Приклад:

    .features {
        display: grid;
        grid-template-columns: 1fr;
        gap: 1rem;
    }

    @media (min-width: 48rem) {
        .features {
            grid-template-columns: repeat(2, minmax(0, 1fr));
        }
    }

    @media (min-width: 72rem) {
        .features {
            grid-template-columns: repeat(3, minmax(0, 1fr));
        }
    }

Цей підхід допомагає почати з найважливішого контенту та поступово додавати можливості layout.

## Responsive Checklist

    [ ] No unintended horizontal scrolling
    [ ] Readable text
    [ ] Comfortable touch targets
    [ ] Responsive images
    [ ] Usable navigation
    [ ] Correct content order
    [ ] Accessible forms
    [ ] Visible CTA
    [ ] Consistent spacing

# Landing Page Forms

Форми часто використовують для збору інформації або реєстрації користувачів.

Приклади:

    Email subscription
    Contact form
    Signup form
    Demo request
    Event registration

## Простота форми

Кожне додаткове поле збільшує кількість дій, які повинен виконати користувач.

Тому запитуй лише ті дані, які справді потрібні для поточного сценарію.

Наприклад, для підписки на email-розсилку може бути достатньо:

    Email address
    [Subscribe]

Для замовлення консультації можуть знадобитися додаткові дані.

## Form UX

Необхідно передбачити:

    Clear labels
    Required field indicators
    Validation
    Helpful error messages
    Submission feedback
    Keyboard accessibility
    Privacy information where relevant

## Приклад HTML

    <form action="/subscribe" method="post">
        <label for="email">
            Email address
        </label>

        <input
            id="email"
            name="email"
            type="email"
            autocomplete="email"
            required
        >

        <button type="submit">
            Subscribe
        </button>
    </form>

Це базовий приклад форми. Реальна реалізація повинна також обробляти відправлення даних, помилки сервера та повідомлення про результат.

## Form Feedback

Після відправлення користувач повинен розуміти, що відбулося.

Приклад:

    Success:
        Your request has been submitted.

    Error:
        We couldn't submit your request.
        Please try again.

Не можна повідомляти про успіх, якщо дані фактично не були прийняті.

# Landing Page Accessibility

Accessibility — доступність сторінки для людей із різними можливостями та способами взаємодії.

Основні вимоги:

    Semantic HTML
    Keyboard navigation
    Visible focus
    Sufficient contrast
    Accessible forms
    Descriptive links
    Meaningful alt text
    Logical heading hierarchy
    Reduced motion support

## Semantic Structure

Приклад:

    <header>
        <nav aria-label="Main navigation">
            ...
        </nav>
    </header>

    <main>
        <section aria-labelledby="hero-title">
            <h1 id="hero-title">
                Learn by building projects
            </h1>
        </section>

        <section aria-labelledby="features-title">
            <h2 id="features-title">
                Features
            </h2>
        </section>
    </main>

    <footer>
        ...
    </footer>

Семантична структура допомагає браузерам, допоміжним технологіям і користувачам орієнтуватися на сторінці.

## Heading Hierarchy

Зазвичай:

    H1 → головна тема сторінки
    H2 → основні секції
    H3 → підрозділи

Заголовки повинні описувати структуру контенту, а не використовуватися лише для зміни розміру шрифту.

## Keyboard Accessibility

Перевір:

    Tab
    Shift + Tab
    Enter
    Space
    Escape, where appropriate

Інтерактивні елементи повинні мати доступний фокус і логічний порядок навігації.

## Motion

Анімації повинні бути помірними та не заважати користувачам.

За потреби враховуй системне налаштування зменшення руху:

    @media (prefers-reduced-motion: reduce) {
        *,
        *::before,
        *::after {
            scroll-behavior: auto;
            animation-duration: 0.01ms;
            animation-iteration-count: 1;
            transition-duration: 0.01ms;
        }
    }

У реальному проєкті правила потрібно адаптувати до типів анімацій і компонентів, які використовуються.

# Performance Optimization

Performance — швидкість завантаження та реакції сторінки.

Повільна landing page може погіршувати користувацький досвід і заважати виконанню цільової дії.

Основні напрямки оптимізації:

    Image optimization
    Font optimization
    JavaScript reduction
    CSS optimization
    Lazy loading
    Caching
    Responsive images
    Avoiding layout shifts

## Images

Великі зображення можуть суттєво збільшувати час завантаження.

Використовуй:

    Appropriate image dimensions
    WebP or AVIF where suitable
    Responsive image sources
    Lazy loading for below-the-fold images

Для головного зображення, яке відразу видно на екрані, не слід автоматично застосовувати lazy loading, якщо це затримує його появу.

## Fonts

Велика кількість варіантів шрифту збільшує обсяг ресурсів.

Варто:

    Limit unnecessary font files
    Use appropriate font weights
    Preload only critical fonts when justified
    Provide fallback fonts

## JavaScript

Для простої landing page не завжди потрібен великий JavaScript bundle.

Уникай непотрібних бібліотек, важких анімацій та скриптів, які блокують основний контент.

## Core Web Vitals

Для оцінювання користувацького досвіду Google використовує такі основні метрики:

    LCP → Largest Contentful Paint
    INP → Interaction to Next Paint
    CLS → Cumulative Layout Shift

LCP оцінює швидкість появи основного великого контенту.

INP оцінює реакцію сторінки на взаємодії користувача.

CLS оцінює несподівані зміщення елементів під час завантаження.

Ці метрики потрібно вимірювати, а не оцінювати лише візуально.

    Honest

Допомагають:

    Descriptive headings
    Short paragraphs
    Bullet lists
    Clear section boundaries
    Meaningful emphasis
    Informative links

Перевір узгодженість:

    Headline

    Pricing
    Testimonials
    Signup flow

Якщо реклама обіцяє одну функцію, а landing page демонструє іншу, користувач може втратити довіру.

# A/B Testing

A/B testing — метод порівняння двох варіантів сторінки або окремого елемента за визначеною метрикою.

Наприклад:

    Version A:
        Start free trial

    Version B:
        Try it free

Можна перевіряти:

    Headline
    CTA copy
    CTA placement
    Hero layout
    Form length
    Pricing presentation
    Product visual

## Як працює A/B Testing

    1. Define hypothesis
              ↓
    2. Choose primary metric
              ↓
    3. Create variants
              ↓
    4. Run experiment
              ↓
    5. Collect data
              ↓
    6. Analyze results
              ↓
    7. Make decision

## Hypothesis

Приклад:

    Hypothesis:
        A more specific CTA will help users
        understand the next action.

    A:
        Submit

    B:
        Create account

    Metric:
        Registration completion rate

## Важливі правила

• Визначай основну метрику до початку тесту.

• Не змінюй багато незалежних елементів одночасно, якщо потрібно зрозуміти вплив конкретної зміни.

• Враховуй розмір вибірки та випадкові коливання.

• Не оголошуй переможця лише за кількома випадковими конверсіями.

• Результат тесту може залежати від джерела трафіку та аудиторії.

• A/B testing не замінює якісні дослідження користувачів.

# Conversion Rate

Conversion rate — частка користувачів, які виконали визначену цільову дію.

Формула:

    Conversion Rate =
        Conversions / Visitors × 100%

Наприклад:

    Visitors = 1000
    Conversions = 50

    Conversion Rate =
        50 / 1000 × 100%

    Conversion Rate = 5%

У цьому прикладі конверсія становить 5%.

Важливо правильно визначити, що саме рахується:

    Unique visitors
    Sessions
    CTA clicks
    Completed registrations
    Purchases

Кількість натискань CTA не завжди дорівнює кількості завершених конверсій.

## Інші метрики

### Click-through rate (CTR)

Частка користувачів, які натиснули певне посилання або оголошення, серед тих, кому його показали.

    CTR =
        Clicks / Impressions × 100%

### Bounce Rate

Bounce rate — метрика взаємодії, визначення якої залежить від аналітичної системи.

У GA4 вона пов'язана з часткою сеансів, які не вважаються engaged sessions.

Не слід автоматично трактувати будь-який короткий візит як невдалий: користувач може швидко знайти потрібну інформацію.

## Важливо

Висока конверсія сама по собі не доводить, що сторінка має хороший UX.

Необхідно враховувати:

    User expectations
    Product quality
    Audience relevance
    Task completion
    Accessibility
    Long-term outcomes

# Design Process

Розробку landing page зручно організувати послідовно.

## Step 1 — Define the Goal

Визнач головну ціль:

    Purchase
    Registration
    Lead generation
    App download
    Demo booking

## Step 2 — Understand the Audience

З'ясуй:

    Who are the users?
    What problem do they have?
    What do they expect?
    What prevents them from taking action?

## Step 3 — Define the Value Proposition

Сформулюй:

    Main benefit
    Target audience
    Product difference
    Desired outcome

## Step 4 — Plan the Content

Підготуй список секцій.

Наприклад:

    Header
    Hero
    Benefits
    Features
    Testimonials
    Pricing
    FAQ
    CTA
    Footer

Не додавай секції лише тому, що вони є в популярних шаблонах.

## Step 5 — Create a Wireframe

Wireframe — спрощена схема сторінки без детального візуального оформлення.

Приклад:

    Header
    ───────────────────────────

    Headline       Product image
    Description
    CTA
    ───────────────────────────

    Benefits
    ───────────────────────────

    Features
    ───────────────────────────

    Testimonials
    ───────────────────────────

    CTA
    ───────────────────────────

    Footer

На цьому етапі важливі структура, ієрархія та послідовність контенту.

## Step 6 — Establish Visual Style

Визнач:

    Colors
    Typography
    Spacing
    Grid
    Buttons
    Cards
    Borders
    Shadows
    Image style

## Step 7 — Build the Page

Реалізуй дизайн за допомогою HTML, CSS та необхідного JavaScript.

## Step 8 — Make It Responsive

Перевір різні розміри viewport.

## Step 9 — Check Accessibility

Перевір клавіатурну навігацію, семантику, контраст і форми.

## Step 10 — Test Performance

Перевір завантаження сторінки, зображення, шрифти та інтерактивність.

## Step 11 — Evaluate Results

Використовуй:

    User testing
    Analytics
    Feedback
    Conversion metrics
    A/B testing

Змінюй дизайн на основі реальних проблем, а не лише особистих уподобань.

# Типові помилки

## 1. Нечіткий Headline

❌

    Welcome to the Future

Користувач не розуміє, що саме пропонується.

Краще:

    Manage Your Projects in One Place

Заголовок конкретніше описує призначення продукту.

## 2. Забагато CTA

❌

    Buy now
    Start free trial
    Contact sales
    Download app
    Subscribe
    Learn more

Якщо всі дії мають однакову візуальну вагу, користувачеві складніше визначитися.

Краще виділити основну дію та залишити релевантні альтернативи.

## 3. Features без Benefits

❌

    API
    Dashboard
    Analytics
    Notifications

Це лише перелік можливостей.

Краще пояснити їхню користь:

    Dashboard:
        See important information at a glance.

    Notifications:
        Stay informed about important updates.

## 4. Надмірний Hero

❌ Велика декоративна ілюстрація займає майже весь екран, а зміст і CTA стають малопомітними.

Краще забезпечити баланс між повідомленням, візуалом і дією.

## 5. Непослідовна візуальна ієрархія

❌ Усі заголовки, кнопки та картки мають однакову візуальну вагу.

Краще визначити чіткі рівні важливості.

## 6. Відсутність довіри

❌ Сторінка вимагає оплату або реєстрацію, але не пояснює умови, не показує контактів і не дає відповідей на важливі запитання.

Краще надати перевірену інформацію про продукт, оплату, підтримку та приватність.

## 7. Надмірна кількість секцій

❌ Сторінка містить багато повторюваних блоків, які не додають нової інформації.

Краще залишити секції, що допомагають зрозуміти пропозицію або прийняти рішення.

## 8. Поганий Mobile Layout

❌ Дві колонки залишаються надто вузькими на телефоні.

Краще перебудувати layout, адаптувати відступи та перевірити порядок контенту.

## 9. CTA не відповідає дії

❌ Кнопка `Start free trial` веде безпосередньо до сторінки оплати без пояснення умов.

Краще забезпечити відповідність між текстом кнопки та наступним кроком.

## 10. Вигадані відгуки

❌ Сторінка містить неіснуючих клієнтів або непідтверджені цифри.

Краще використовувати реальні відгуки та перевірені дані.

## 11. Недоступні інтерактивні елементи

❌ CTA працює лише при наведенні миші або не має видимого фокуса.

Краще перевірити клавіатурну навігацію та стани компонентів.

## 12. Важкі зображення

❌ Великі файли зображень завантажуються без оптимізації.

Краще використовувати відповідні формати, розміри та стратегію завантаження.

## 13. Надмірні анімації

❌ Ефекти відволікають від контенту або затримують доступ до важливої інформації.

Краще використовувати анімацію лише там, де вона допомагає зрозуміти взаємодію.

## 14. Прихована важлива інформація

❌ Ціна, умови підписки або обмеження доступні лише після реєстрації без попереднього пояснення.

Краще повідомляти умови в момент, коли вони потрібні користувачеві для прийняття рішення.

# Landing Page Checklist

## Goal and Content

    [ ] The primary conversion goal is defined.
    [ ] The target audience is understood.
    [ ] The value proposition is clear.
    [ ] The headline explains the main offer.
    [ ] The subheadline provides useful context.
    [ ] Features explain user benefits.
    [ ] The content is accurate and relevant.
    [ ] The CTA label describes the actual action.

## Layout and Visual Design

    [ ] The page has a clear visual hierarchy.
    [ ] The hero section communicates the main offer.
    [ ] The content follows a logical sequence.
    [ ] Sections have consistent spacing.
    [ ] Typography is readable.
    [ ] Colors are consistent.
    [ ] The primary CTA is easy to identify.
    [ ] Images support the content.
    [ ] Repeated components have consistent styling.

## Conversion and Trust

    [ ] The main CTA works correctly.
    [ ] Secondary actions do not distract unnecessarily.
    [ ] Trust signals are accurate.
    [ ] Testimonials are genuine.
    [ ] Pricing and terms are clear where relevant.
    [ ] Forms request only necessary information.
    [ ] Success and error states are provided.

## Responsive Design

    [ ] The page works on mobile.
    [ ] The page works on tablet.
    [ ] The page works on desktop.
    [ ] No unintended horizontal scrolling occurs.
    [ ] Text remains readable.
    [ ] Images scale correctly.
    [ ] Navigation is usable.
    [ ] CTA controls remain accessible.

## Accessibility

    [ ] Semantic HTML is used.
    [ ] Heading hierarchy is logical.
    [ ] Interactive elements work with a keyboard.
    [ ] Focus indicators are visible.
    [ ] Text contrast is sufficient.
    [ ] Form fields have labels.
    [ ] Images have appropriate alternative text.
    [ ] Motion is not essential to understanding content.

## Performance

    [ ] Images are optimized.
    [ ] Unnecessary JavaScript is avoided.
    [ ] Fonts are loaded efficiently.
    [ ] Layout shifts are minimized.
    [ ] Core Web Vitals are evaluated where appropriate.

# Головне

• Landing page — сторінка, спроєктована навколо конкретної пропозиції та цільової дії.

• Основне завдання — допомогти користувачеві зрозуміти цінність продукту та прийняти обґрунтоване рішення.

• Hero section повинен чітко представляти пропозицію.

• Headline повідомляє головну ідею, а subheadline додає важливі подробиці.

• Value proposition пояснює, яку цінність отримує користувач.

• Features описують можливості продукту, а benefits — користь від них.

• CTA повинен мати зрозумілий текст і вести до очікуваної дії.

• Primary CTA має виділятися, але не повинен бути нав'язливим.

• Above the fold — лише початкова видима область сторінки. Не потрібно вміщувати весь контент в один екран.

• Послідовність секцій залежить від продукту, аудиторії та цілі сторінки.

• Social proof і trust signals допомагають користувачеві оцінити надійність пропозиції, якщо вони правдиві та доречні.

• Pricing і умови використання повинні бути зрозумілими, коли вони важливі для прийняття рішення.

• Responsive design забезпечує зручне використання сторінки на різних пристроях.

• Accessibility необхідна для доступності контенту та інтерактивних елементів.

• Performance впливає на швидкість завантаження та загальний користувацький досвід.

• Conversion rate потрібно оцінювати разом з іншими метриками та якістю взаємодії.

• A/B testing допомагає перевіряти гіпотези, але потребує коректного дизайну експерименту.

• Хороший landing page design — це не просто красивий інтерфейс, а поєднання структури, контенту, візуальної ієрархії, доступності, продуктивності та зрозумілого користувацького сценарію.

• Основний принцип:

    Clear offer
         ↓
    Clear value
         ↓
    Relevant information
         ↓
    User trust
         ↓
    Clear action
         ↓
    Meaningful conversion
