# 06. E-commerce UI — Інтерфейси інтернет-магазинів

E-commerce UI (Electronic Commerce User Interface) — це дизайн інтерфейсів інтернет-магазинів, маркетплейсів та інших сервісів, у яких користувачі переглядають товари, порівнюють пропозиції, додають товари до кошика та оформлюють замовлення.

Головна мета e-commerce UI — допомогти користувачеві швидко знайти потрібний товар, зрозуміти його характеристики, оцінити умови покупки та завершити замовлення без зайвих труднощів.

E-commerce UI поєднує:
- інформаційну архітектуру;
- навігацію та пошук;
- картки товарів;
- фільтрацію та сортування;
- сторінки товарів;
- кошик і checkout;
- форми та валідацію;
- стани інтерфейсу;
- адаптивний дизайн;
- доступність;
- довіру, прозорість і зручність покупки.

**Шлях користувача:**

    Головна сторінка
        ↓
    Каталог товарів
        ↓
    Пошук або фільтрація
        ↓
    Сторінка товару
        ↓
    Додавання до кошика
        ↓
    Перевірка кошика
        ↓
    Оформлення замовлення
        ↓
    Підтвердження покупки

---

## 1. Основні поняття

### 1.1. E-commerce

E-commerce — електронна комерція, тобто продаж товарів або послуг через цифрові канали.

Основні типи платформ:

- **Online store** — інтернет-магазин одного продавця.
- **Marketplace** — маркетплейс із багатьма продавцями.
- **D2C (Direct-to-Consumer)** — бренд продає безпосередньо покупцеві.
- **B2B commerce** — електронна торгівля між компаніями.
- **Subscription commerce** — регулярна доставка товарів або послуг за підпискою.

### 1.2. Основні сторінки інтернет-магазину

Типова структура:

    Home
    ├── Categories
    │   └── Product listing
    │       └── Product details
    ├── Search results
    ├── Cart
    ├── Checkout
    ├── Order confirmation
    ├── Account
    │   ├── Profile
    │   ├── Orders
    │   ├── Addresses
    │   └── Settings
    ├── Wishlist
    └── Help / Returns / Delivery

Не кожен магазин повинен мати всі ці сторінки. Структура залежить від типу товарів, бізнес-моделі та потреб покупців.

### 1.3. Основні цілі e-commerce UI

Інтерфейс має допомагати користувачеві:

- знайти товар;
- зрозуміти, чи підходить товар;
- порівняти альтернативи;
- побачити актуальну ціну;
- зрозуміти вартість доставки;
- перевірити наявність;
- вибрати розмір, колір або комплектацію;
- додати товар до кошика;
- оформити замовлення;
- отримати підтвердження;
- знайти інформацію про повернення та підтримку.

### 1.4. UI та UX в e-commerce

**UI (User Interface)** — візуальні та інтерактивні елементи магазину.

Приклади:
- картки товарів;
- кнопки;
- поля пошуку;
- фільтри;
- перемикачі варіантів;
- індикатор кошика;
- форми оформлення замовлення.

**UX (User Experience)** — загальний досвід користувача під час покупки.

Приклади:
- наскільки легко знайти товар;
- чи зрозумілі умови доставки;
- чи можна виправити помилку у формі;
- чи не губиться кошик після переходу між сторінками;
- чи можна завершити покупку без створення акаунта.

Хороший e-commerce UI повинен не лише виглядати привабливо, а й допомагати користувачеві впевнено приймати рішення.

## 2. Структура головної сторінки

Головна сторінка має швидко пояснювати, що продає магазин, які товари доступні та як почати пошук.

### 2.1. Header — шапка сайту

Типові елементи:

- логотип;
- основна навігація;
- поле пошуку;
- кнопка або посилання акаунта;
- обране;
- кошик;
- перемикач мови або валюти, якщо потрібно.

Приклад структури:

    Header
    ├── Logo
    ├── Navigation
    ├── Search
    ├── Account
    ├── Wishlist
    └── Cart

Основні рекомендації:

- логотип повинен бути помітним і вести на головну;
- пошук має бути легко знайти;
- основні дії не повинні губитися серед другорядних посилань;
- на мобільних пристроях важливі елементи повинні залишатися доступними;
- кількість іконок у шапці потрібно обмежувати до необхідного мінімуму.

### 2.2. Navigation — навігація

Навігація допомагає користувачеві зрозуміти структуру каталогу.

Приклад:

    Каталог
    ├── Електроніка
    │   ├── Смартфони
    │   ├── Ноутбуки
    │   └── Навушники
    ├── Одяг
    │   ├── Чоловічий
    │   ├── Жіночий
    │   └── Дитячий
    └── Дім
        ├── Освітлення
        └── Кухня

Рекомендації:

- використовувати зрозумілі назви категорій;
- групувати споріднені товари;
- уникати надмірної глибини вкладених меню;
- не покладатися лише на колір для позначення активного пункту;
- на мобільних пристроях забезпечити зручне відкриття та закриття меню.

### 2.3. Hero section — головний промоблок

Hero section може містити:

- короткий заголовок;
- пояснювальний текст;
- зображення товару або колекції;
- основну кнопку;
- посилання на категорію чи акцію.

Приклад:

    Нові колекції для вашого дому

    Практичні речі для комфортного щоденного життя.

    [Переглянути товари]

Рекомендації:

- повідомлення повинно бути конкретним;
- головна кнопка має вести до відповідного каталогу або пропозиції;
- зображення не повинно заважати читанню;
- текст і кнопка повинні бути зрозумілими без зайвих пояснень;
- промоакції мають містити правдиві умови.

### 2.4. Інші блоки головної сторінки

Можливі секції:

- популярні категорії;
- новинки;
- рекомендовані товари;
- бестселери;
- спеціальні пропозиції;
- переваги магазину;
- інформація про доставку;
- відгуки;
- підписка на розсилку;
- footer із контактами та службовими сторінками.

Не потрібно додавати всі блоки одночасно. Кожна секція повинна виконувати зрозумілу функцію.

## 3. Product listing — сторінка каталогу

Product listing — сторінка, на якій користувач переглядає набір товарів у певній категорії або за результатами пошуку.

Основні елементи:

- назва категорії;
- короткий опис, якщо потрібен;
- кількість знайдених товарів;
- фільтри;
- сортування;
- картки товарів;
- пагінація або кнопка завантаження наступної порції;
- повідомлення про відсутність результатів.

Приклад структури:

    Category page
    ├── Breadcrumbs
    ├── Page title
    ├── Product count
    ├── Filters
    ├── Sort control
    ├── Product grid
    │   ├── Product card
    │   ├── Product card
    │   └── Product card
    └── Pagination

### 3.1. Breadcrumbs — навігаційний ланцюжок

Breadcrumbs показують шлях до поточної категорії.

Приклад:

    Головна / Електроніка / Навушники

Переваги:

- допомагають зрозуміти місце сторінки в каталозі;
- дозволяють перейти до батьківської категорії;
- особливо корисні у великих каталогах.

Рекомендації:

- поточну сторінку позначати як поточну;
- попередні рівні робити доступними для переходу;
- не замінювати breadcrumbs основною навігацією;
- не показувати їх, якщо структура сайту занадто проста і вони не додають користі.

### 3.2. Product grid — сітка товарів

Сітка повинна адаптуватися до ширини екрана.

Приклад:

    Desktop:    4 картки в ряд
    Tablet:     2–3 картки в ряд
    Mobile:     1–2 картки в ряд

Це орієнтовні варіанти, а не жорсткі правила. Кількість колонок залежить від ширини картки, довжини назв і складності товару.

Важливо:

- підтримувати однакові принципи компонування;
- забезпечувати читабельність назви й ціни;
- не робити картки занадто вузькими;
- залишати достатньо місця для натискання;
- уникати надмірної кількості товарів на одному екрані.

## 4. Product card — картка товару

Product card — компактний блок, який представляє товар у каталозі.

Типова структура:

    Product card
    ├── Product image
    ├── Badge (New, Sale)
    ├── Brand
    ├── Product title
    ├── Rating
    ├── Price
    ├── Availability
    ├── Variant preview
    └── Add to cart / View details

Не кожна картка потребує всіх елементів.

### 4.1. Зображення товару

Зображення допомагає користувачеві швидко ідентифікувати товар.

Рекомендації:

- використовувати якісні зображення;
- підтримувати узгоджене співвідношення сторін;
- показувати товар достатньо великим;
- не обрізати важливі деталі;
- використовувати зрозумілий фон;
- оптимізувати розмір файлів;
- передбачати альтернативний текст для змістовних зображень.

Якщо картки використовують однаковий контейнер, можна задати співвідношення сторін через CSS.

    .product-card__image {
      width: 100%;
      aspect-ratio: 1 / 1;
      object-fit: contain;
    }

`object-fit: contain` допомагає показати весь товар, не обрізаючи його. Для фотографій, які мають заповнювати контейнер, може підійти `cover`.

### 4.2. Назва товару

Назва повинна допомагати розрізняти товари.

Погано:

    Навушники

Краще:

    Бездротові навушники Sound Pro X2

Для технічних товарів назва може містити важливу характеристику, наприклад обсяг пам'яті або модель.

Рекомендації:

- використовувати зрозумілі назви;
- не перевантажувати картку всіма характеристиками;
- не обрізати текст так, щоб зникала ключова відмінність;
- за потреби обмежувати кількість рядків із коректним доступним способом перегляду повної назви.

### 4.3. Ціна

Ціна повинна бути помітною та однозначною.

Приклад:

    2 499 грн

Якщо діє знижка:

    2 499 грн
    2 999 грн — попередня ціна

Рекомендації:

- показувати актуальну ціну;
- стару ціну візуально відокремлювати;
- чітко позначати валюту;
- не створювати хибне враження про знижку;
- пояснювати додаткові обов'язкові платежі до завершення замовлення.

### 4.4. Badges — позначки товарів

Приклади:

- New — новинка;
- Sale — товар зі знижкою;
- Bestseller — популярний товар;
- Out of stock — немає в наявності;
- Limited offer — обмежена пропозиція, якщо це відповідає дійсності.

Рекомендації:

- використовувати позначки помірно;
- не розміщувати багато бейджів одночасно;
- не покладатися лише на колір;
- не створювати фальшивих повідомлень про дефіцит;
- використовувати короткі й зрозумілі слова.

### 4.5. Rating — рейтинг

Рейтинг може містити:

- оцінку;
- кількість відгуків;
- посилання на відгуки.

Приклад:

    ★ 4.7 (128 відгуків)

Важливо:

- показувати рейтинг лише за наявності реальних даних;
- не вигадувати оцінки;
- не плутати рейтинг товару з рейтингом продавця;
- забезпечувати текстове пояснення для зірок та інших графічних індикаторів.

### 4.6. Quick actions — швидкі дії

Картка може містити:

- додавання до кошика;
- додавання до обраного;
- швидкий перегляд;
- вибір кольору;
- перехід до сторінки товару.

Рекомендації:

- найважливіша дія повинна бути очевидною;
- іконки без тексту мають мати доступну назву;
- натискання на товар і натискання на кнопку не повинні конфліктувати;
- якщо для покупки необхідно вибрати розмір або інший варіант, потрібно чітко повідомити про це.

## 5. Search — пошук товарів

Пошук допомагає користувачеві знайти конкретний товар або групу товарів.

Основні функції:

- введення запиту;
- підказки;
- пошук за назвою;
- пошук за брендом або категорією;
- обробка помилок у запиті;
- результати пошуку;
- повідомлення про відсутність результатів.

### 5.1. Поле пошуку

Приклад:

    [ Знайти товар або бренд... ] [Пошук]

Рекомендації:

- розміщувати пошук у передбачуваному місці;
- використовувати зрозумілий placeholder;
- не покладатися лише на placeholder як на назву поля;
- підтримувати клавіатурне керування;
- на мобільних пристроях не робити поле надто малим;
- забезпечувати зрозумілий спосіб очистити запит.

### 5.2. Search suggestions — підказки

Підказки можуть показувати:

- популярні запити;
- назви товарів;
- категорії;
- бренди;
- нещодавні пошуки, якщо це доречно.

Рекомендації:

- відрізняти підказки від звичайного тексту;
- підтримувати клавіші зі стрілками та Enter;
- закривати список у передбачуваних ситуаціях;
- не перекривати важливі елементи без потреби;
- враховувати доступність для скринрідерів.

### 5.3. No search results — немає результатів

Погано:

    Нічого не знайдено.

Краще:

    За запитом «бездротова клавіатура» товарів не знайдено.

    Спробуйте:
    - перевірити написання;
    - використати коротший запит;
    - переглянути інші категорії.

Якщо можливо, запропонуйте корисні альтернативи, але не видавайте нерелевантні товари за точні результати.

## 6. Filters and sorting — фільтрація та сортування

Фільтри дозволяють звузити список товарів, а сортування — змінити порядок їх відображення.

### 6.1. Типові фільтри

Залежно від категорії це можуть бути:

- ціна;
- бренд;
- розмір;
- колір;
- матеріал;
- рейтинг;
- наявність;
- характеристики;
- сумісність;
- спосіб доставки.

Фільтри повинні відповідати реальним властивостям товарів.

### 6.2. Price filter — фільтр ціни

Приклад:

    Мінімальна ціна: [ 500 ]
    Максимальна ціна: [ 3000 ]

    [Застосувати]

Можна також використовувати повзунок, якщо він зручний для відповідного діапазону.

Рекомендації:

- показувати валюту;
- перевіряти, що мінімальна ціна не перевищує максимальну;
- давати змогу ввести точні значення;
- чітко пояснювати, коли фільтр застосовано.

### 6.3. Checkbox filters — фільтри з прапорцями

Приклад:

    Бренд
    [ ] Brand A
    [ ] Brand B
    [ ] Brand C

Checkbox підходить, коли користувач може вибрати декілька значень.

Radio button підходить, коли потрібно вибрати лише один варіант.

### 6.4. Sorting — сортування

Типові варіанти:

- за популярністю;
- за новизною;
- за ціною: від нижчої до вищої;
- за ціною: від вищої до нижчої;
- за рейтингом, якщо рейтинг є надійним і доречним.

Рекомендації:

- використовувати зрозумілі назви;
- показувати поточний варіант;
- зберігати вибір під час навігації, якщо це очікувано;
- не плутати фільтрацію із сортуванням.

### 6.5. Active filters — активні фільтри

Після застосування фільтрів корисно показувати їх у вигляді тегів.

Приклад:

    Ціна: 500–3000 грн  [×]
    Бренд: Brand A      [×]
    Колір: чорний       [×]

    [Очистити всі фільтри]

Користувач повинен розуміти, чому список товарів змінився, і мати змогу легко скасувати окремий фільтр.

### 6.6. Mobile filters — фільтри на мобільних пристроях

На вузькому екрані фільтри можуть відкриватися в панелі або модальному вікні.

Важливо:

- показувати кількість активних фільтрів;
- забезпечити кнопку закриття;
- не втрачати вибрані значення без попередження;
- дозволяти застосувати або скасувати зміни;
- повертати фокус у логічне місце після закриття;
- не блокувати доступ до критично важливих дій.

## 7. Product details — сторінка товару

Сторінка товару допомагає користувачеві оцінити конкретний товар і вирішити, чи варто його купувати.

Типова структура:

    Product details
    ├── Breadcrumbs
    ├── Product gallery
    ├── Product title
    ├── Rating and reviews
    ├── Price
    ├── Availability
    ├── Product variants
    ├── Quantity selector
    ├── Add to cart
    ├── Delivery information
    ├── Returns information
    ├── Description
    ├── Specifications
    └── Reviews

### 7.1. Product gallery — галерея товару

Може містити:

- головне зображення;
- мініатюри;
- додаткові ракурси;
- зображення деталей;
- фотографії товару в контексті використання;
- відео, якщо воно справді корисне.

Рекомендації:

- головне зображення має бути помітним;
- мініатюри повинні бути доступними для вибору;
- активне зображення потрібно візуально позначати;
- не приховувати критичні деталі товару;
- передбачати текстові альтернативи для змістовних зображень.

### 7.2. Product title — назва товару

Назва повинна бути точною та інформативною.

Приклад:

    Настільна лампа Nordic, чорна, 12 Вт

Не потрібно перевантажувати заголовок рекламними фразами. Основні характеристики краще розміщувати в окремому блоці.

### 7.3. Availability — наявність

Приклади:

    Є в наявності

    Залишилося мало товарів

    Немає в наявності

    Очікується з 25 жовтня

Статус повинен відповідати актуальним даним.

Якщо товар відсутній, можна запропонувати:

- повідомлення про появу;
- схожі товари;
- інші доступні варіанти.

Не можна показувати кнопку покупки так, ніби товар доступний, якщо це не відповідає фактичним умовам.

### 7.4. Product variants — варіанти товару

Варіанти можуть включати:

- колір;
- розмір;
- обсяг пам'яті;
- комплектацію;
- матеріал;
- тип упаковки.

Приклад:

    Колір:
    [Чорний] [Білий] [Сірий]

Рекомендації:

- чітко показувати вибраний варіант;
- візуально відрізняти доступні й недоступні варіанти;
- не використовувати лише колір для позначення вибору;
- оновлювати ціну, зображення та наявність, якщо вони залежать від варіанта;
- не додавати товар до кошика, якщо обов'язковий варіант не вибрано.

### 7.5. Quantity selector — вибір кількості

Приклад:

    [−]  1  [+]

Важливо:

- кількість не повинна бути меншою за мінімально дозволену;
- кількість не повинна перевищувати доступний ліміт;
- кнопки мають доступні назви;
- поточне значення повинно бути зрозумілим;
- потрібно враховувати товари, які продаються лише комплектами.

### 7.6. Add to cart — додавання до кошика

Основна кнопка повинна бути помітною.

Приклад:

    [Додати до кошика]

Після натискання користувачеві потрібно повідомити результат:

    Товар додано до кошика.

Можливі додаткові дії:

    [Продовжити покупки]
    [Перейти до кошика]

Не слід автоматично перенаправляти користувача до оформлення замовлення, якщо це порушує очікуваний сценарій.

### 7.7. Product description — опис товару

Опис допомагає зрозуміти призначення, властивості та переваги товару.

Рекомендації:

- використовувати короткі абзаци;
- виділяти важливі характеристики;
- не дублювати без потреби всі дані з таблиці специфікацій;
- уникати необґрунтованих тверджень;
- описувати обмеження та сумісність, якщо це важливо для покупки.

### 7.8. Specifications — характеристики

Приклад:

    Потужність: 12 Вт
    Матеріал: метал
    Колір: чорний
    Висота: 42 см
    Живлення: USB-C

Для технічних товарів структурована таблиця характеристик часто зручніша за довгий текст.

### 7.9. Delivery and returns — доставка та повернення

Користувачеві важливо розуміти:

- доступні способи доставки;
- орієнтовні строки;
- вартість доставки;
- можливі обмеження;
- правила повернення;
- гарантійні умови.

Не потрібно приховувати суттєві умови до останнього кроку checkout.

## 8. Cart — кошик

Кошик дозволяє перевірити вибрані товари перед оформленням замовлення.

Типова структура:

    Cart
    ├── Product list
    │   ├── Product image
    │   ├── Product title
    │   ├── Selected variant
    │   ├── Unit price
    │   ├── Quantity
    │   └── Remove action
    ├── Subtotal
    ├── Discount
    ├── Delivery estimate
    ├── Total
    └── Checkout button

### 8.1. Cart item — товар у кошику

Для кожного товару бажано показувати:

- зображення;
- назву;
- вибраний варіант;
- ціну за одиницю;
- кількість;
- суму за позицію;
- дію видалення.

Якщо ціна або наявність змінилися після додавання, користувача потрібно повідомити про це до завершення покупки.

### 8.2. Quantity update — зміна кількості

Після зміни кількості потрібно коректно оновлювати:

- кількість товару;
- суму позиції;
- проміжну суму;
- знижки, якщо вони залежать від кількості;
- загальну суму.

Важливо показувати стан оновлення, якщо перерахунок відбувається асинхронно.

### 8.3. Remove item — видалення товару

Видалення повинно бути зрозумілим і передбачуваним.

Можна показати повідомлення:

    Товар видалено з кошика.

    [Скасувати]

Можливість скасування корисна, якщо її легко реалізувати та підтримувати коректно.

### 8.4. Empty cart — порожній кошик

Погано:

    Кошик порожній.

Краще:

    У вашому кошику поки немає товарів.

    Перегляньте каталог, щоб знайти те, що вам потрібно.

    [Перейти до каталогу]

Порожній стан повинен пояснювати ситуацію й пропонувати наступний крок.

### 8.5. Cart summary — підсумок кошика

Приклад:

    Товари:             2 500 грн
    Знижка:              -200 грн
    Доставка:             100 грн
    --------------------------------
    До сплати:          2 400 грн

    [Оформити замовлення]

Це лише приклад структури, а не формула для всіх магазинів.

Важливо:

- правильно обчислювати підсумок;
- показувати валюту;
- пояснювати застосовані знижки;
- не приховувати обов'язкові платежі;
- чітко відрізняти попередню оцінку від остаточної суми.

### 8.6. Promo code — промокод

Приклад:

    Промокод: [____________] [Застосувати]

Після застосування потрібно показати результат.

Успіх:

    Промокод застосовано.

Помилка:

    Цей промокод недійсний або більше не діє.

Якщо є обмеження, варто пояснити їх зрозуміло: наприклад, мінімальну суму замовлення або категорії, на які поширюється знижка.

## 9. Checkout — оформлення замовлення

Checkout — один із найважливіших сценаріїв інтернет-магазину. Його мета — допомогти користувачеві завершити покупку з мінімальною кількістю помилок.

Типова структура:

    Checkout
    ├── Contact information
    ├── Shipping address
    ├── Delivery method
    ├── Payment method
    ├── Order summary
    ├── Terms and confirmations
    └── Place order

Конкретна послідовність залежить від бізнес-моделі та способів оплати й доставки.

### 9.1. Guest checkout — покупка без акаунта

Якщо це можливо, варто дозволити оформлення замовлення без обов'язкової реєстрації.

Переваги:

- менше кроків;
- менше полів;
- нижчий бар'єр для нових покупців.

Створення акаунта можна запропонувати після покупки або як необов'язкову можливість під час checkout.

### 9.2. Contact information — контактні дані

Типові поля:

- ім'я;
- прізвище, якщо потрібно;
- телефон;
- електронна пошта.

Збирайте лише ті дані, які потрібні для виконання замовлення або іншої чітко визначеної мети.

Рекомендації:

- використовувати зрозумілі назви полів;
- позначати обов'язкові поля;
- пояснювати, для чого потрібні дані;
- не вимагати зайвої інформації;
- показувати помилки біля відповідних полів.

### 9.3. Shipping address — адреса доставки

Поля залежать від способу доставки.

Наприклад:

    Місто
    Відділення або адреса
    Індекс, якщо потрібен

Не потрібно вимагати адресу проживання, якщо замовлення доставляється у вибране відділення пошти.

Якщо адреса доставки збігається з іншими даними, можна запропонувати відповідний прапорець, але не припускати збіг без підтвердження користувача.

### 9.4. Delivery method — спосіб доставки

Приклад:

    ( ) Відділення пошти
    ( ) Поштомат
    ( ) Кур'єрська доставка

Для кожного варіанта, якщо дані доступні, варто показувати:

- вартість;
- орієнтовний строк;
- важливі умови;
- додаткові вимоги.

Не слід представляти приблизну дату як гарантовану, якщо магазин не може цього гарантувати.

### 9.5. Payment method — спосіб оплати

Можливі варіанти:

- банківська картка;
- оплата під час отримання;
- банківський переказ;
- інші підтримувані платіжні методи.

Рекомендації:

- показувати лише доступні способи;
- пояснювати важливі умови оплати;
- чітко позначати вибраний спосіб;
- не збирати платіжні дані, які магазин не повинен обробляти самостійно;
- для платіжних даних використовувати належним чином захищену платіжну інтеграцію.

### 9.6. Order summary — підсумок замовлення

Під час оформлення користувач повинен бачити:

- товари;
- кількість;
- вибрані варіанти;
- знижки;
- доставку;
- загальну суму.

На мобільних пристроях підсумок може бути компактним або розкриватися, але критично важлива інформація повинна залишатися доступною до підтвердження покупки.

### 9.7. Place order — підтвердження замовлення

Кнопка повинна мати однозначний текст:

    [Підтвердити замовлення]

Або:

    [Оплатити замовлення]

Конкретний текст залежить від дії.

Після натискання:

- перевірити введені дані;
- показати стан обробки;
- запобігти випадковому повторному надсиланню;
- повідомити про помилку, якщо операція не завершилася;
- показати підтвердження лише після успішного результату.

Не можна показувати повідомлення про успішне оформлення, якщо сервер не підтвердив створення замовлення.

    Замовлення оформлено!

    Номер замовлення: #10482

    Ми надіслали підтвердження на вашу електронну пошту.

Сторінка може містити:

- номер замовлення;
- короткий підсумок;
- спосіб доставки;
- спосіб оплати;
- поточний статус;
- наступні кроки;
- посилання на підтримку.

Важливо:

- не показувати конфіденційні дані без потреби;
- не розкривати повні платіжні реквізити;
- повідомляти лише підтверджений статус;
- пояснювати, що робити далі.

- зберігати список відповідно до можливостей сервісу;
- не обіцяти синхронізацію, якщо вона не реалізована;
- враховувати зміну ціни та наявності товарів.

## 12. Account and orders — акаунт і замовлення

- профіль;
- історію замовлень;

- збережені способи оплати, якщо це підтримується;

- налаштування;

### 12.1. Order history — історія замовлень

Приклад:

    №10482

    Статус: В обробці
    Сума: 2 400 грн

Можливі статуси:

- оформлено;

- оплачене;
- в обробці;
- відправлене;
- доставлене;
- скасоване;
- повернуте.

Точний набір залежить від процесів магазину.

Статус має відповідати фактичному стану замовлення. Колір може допомагати розрізняти стани, але повинен доповнювати текст, а не замінювати його.

## 13. UI states — стани інтерфейсу

Кожен важливий компонент повинен мати передбачувані стани.

### 13.1. Основні стани

- Default — звичайний стан.
- Hover — наведення курсора.
- Focus — клавіатурний фокус.
- Active — натискання або активна взаємодія.
- Selected — вибраний варіант.
- Disabled — дія недоступна.
- Loading — виконується операція.
- Success — успішний результат.
- Error — помилка.
- Empty — немає даних.
- Out of stock — товар відсутній.

Не всі стани потрібні кожному компоненту, але важливі сценарії потрібно передбачити.

### 13.2. Loading state — завантаження

Приклади:

    Завантаження товарів…

    Додаємо товар до кошика…

    Оформлюємо замовлення…

Рекомендації:

- повідомляти про тривалу операцію;
- не створювати враження, що інтерфейс завис;
- блокувати повторне натискання лише там, де це потрібно;
- не очищати введені дані без причини;
- для великих списків використовувати skeletons, якщо вони покращують сприйняття очікування.

### 13.3. Error state — помилка

Приклади:

    Не вдалося завантажити товари.

    Перевірте підключення та спробуйте ще раз.

    [Повторити]

Або:

    Не вдалося додати товар до кошика.

    Ваш вибір збережено. Спробуйте ще раз.

Повідомлення повинно пояснювати:

- що сталося;
- що користувач може зробити;
- чи збережені його дані;
- чи потрібна додаткова дія.

Не показуйте користувачеві необроблені технічні помилки, stack trace або внутрішні повідомлення сервера.

### 13.4. Disabled state — недоступна дія

Кнопка може бути недоступною, коли:

- не вибрано обов'язковий варіант;
- товар відсутній;
- форма ще не готова до надсилання;
- виконується операція, яку не можна повторювати.

Важливо: якщо дія недоступна, користувач повинен розуміти причину. Не використовуйте disabled як єдиний спосіб повідомити про помилку.

## 14. Responsive e-commerce — адаптивний дизайн

Інтернет-магазин повинен залишатися зручним на:

- смартфонах;
- планшетах;
- ноутбуках;
- широких моніторах.

### 14.1. Mobile-first

Mobile-first — підхід, за якого інтерфейс спочатку проєктують для вузьких екранів, а потім розширюють для більших.

Це допомагає визначити справді важливі елементи.

Приклад:

    Mobile:
    - компактний header;
    - доступний пошук;
    - 1–2 картки в ряд;
    - фільтри в панелі;
    - помітна основна дія.

    Desktop:
    - повна навігація;
    - більше колонок;
    - фільтри в бічній панелі;
    - додаткова інформація поруч із товаром.

Це лише можливі рішення. Конкретний layout залежить від контенту та задач користувача.

### 14.2. Responsive product grid

Приклад CSS:

    .product-grid {
      display: grid;
      grid-template-columns: repeat(2, minmax(0, 1fr));
      gap: 1rem;
    }

    @media (min-width: 48rem) {
      .product-grid {
        grid-template-columns: repeat(3, minmax(0, 1fr));
      }
    }

    @media (min-width: 72rem) {
      .product-grid {
        grid-template-columns: repeat(4, minmax(0, 1fr));
      }
    }

`minmax(0, 1fr)` допомагає уникати переповнення колонок довгим контентом.

Ці breakpoint-и — приклад, а не універсальні значення. Їх потрібно перевіряти на реальному контенті.

### 14.3. Mobile checkout

На смартфоні важливо:

- використовувати зрозумілі вертикальні форми;
- мінімізувати непотрібне введення;
- не приховувати повідомлення про помилки;
- показувати підсумок замовлення;
- уникати горизонтального прокручування;
- залишати достатньо місця для натискання;
- враховувати екранну клавіатуру;
- не перекривати поля фіксованими елементами.

## 15. Accessibility — доступність

Доступний магазин повинен бути придатним для користувачів із різними можливостями та способами взаємодії.

### 15.1. Keyboard navigation

Користувач повинен мати змогу:

- переходити між інтерактивними елементами клавішею Tab;
- активувати кнопки клавішею Enter або Space відповідно до їх типу;
- працювати з полями форм;
- використовувати меню та діалоги;
- бачити поточний фокус.

Не прибирайте видимий focus без повноцінної заміни.

Приклад:

    button:focus-visible {
      outline: 3px solid #2457d6;
      outline-offset: 3px;
    }

### 15.2. Semantic HTML

Використовуйте елементи за їх призначенням:

    <header>
      <nav aria-label="Основна навігація">
        ...
      </nav>
    </header>

    <main>
      <h1>Навушники</h1>
      ...
    </main>

    <footer>
      ...
    </footer>

Для дій використовуйте `<button>`, а для переходів між сторінками — `<a>`.

Не створюйте клікабельні `div`, якщо для задачі підходить стандартний HTML-елемент.

### 15.3. Product images

Приклад:

    <img
      src="/images/headphones.jpg"
      alt="Чорні бездротові навушники"
    />

Альтернативний текст повинен передавати важливу інформацію про зображення. Якщо зображення суто декоративне й не додає змісту, доречним може бути порожній `alt=""`.

### 15.4. Accessible forms

Кожне поле повинно мати доступну назву.

Приклад:

    <label for="email">Електронна пошта</label>
    <input
      id="email"
      name="email"
      type="email"
      autocomplete="email"
      required
    />

Не використовуйте placeholder замість повноцінного label.

### 15.5. Touch targets

На сенсорних екранах кнопки, іконки й інші інтерактивні елементи повинні мати достатню область натискання.

Рекомендації:

- не розміщувати дії надто близько одна до одної;
- не робити важливі кнопки занадто малими;
- перевіряти зручність використання однією рукою;
- дотримуватися відповідних критеріїв WCAG для цільових областей.

### 15.6. Color contrast

Текст і важливі елементи повинні мати достатній контраст.

Для звичайного тексту WCAG 2.2 AA зазвичай вимагає коефіцієнт контрастності не менше 4.5:1, а для великого тексту — не менше 3:1.

Не позначайте стан товару лише кольором. Наприклад, замість одного зеленого індикатора використовуйте текст «Є в наявності».

## 16. Trust and transparency — довіра та прозорість

Під час онлайн-покупки користувач не завжди може побачити товар фізично. Тому інтерфейс повинен допомагати перевірити інформацію та зменшувати невизначеність.

### 16.1. Елементи довіри

Корисними можуть бути:

- реальні фотографії;
- точні характеристики;
- правдиві відгуки;
- зрозуміла інформація про продавця;
- умови доставки;
- правила повернення;
- гарантійні умови;
- безпечний процес оплати;
- контактні дані;
- доступна служба підтримки.

### 16.2. Dark patterns — маніпулятивні патерни

Dark patterns — дизайн-рішення, які підштовхують користувача до дій усупереч його інтересам або ускладнюють свідомий вибір.

Приклади:

- приховані обов'язкові платежі;
- попередньо вибрані необов'язкові доповнення;
- неправдиві таймери зворотного відліку;
- фальшиві повідомлення про дефіцит;
- складне скасування підписки;
- приховані умови повернення;
- кнопки, які вводять в оману.

Хороший e-commerce UI допомагає прийняти обґрунтоване рішення, а не маніпулює поведінкою користувача.

## 17. Visual hierarchy — візуальна ієрархія

Візуальна ієрархія допомагає користувачеві швидко зрозуміти, на що звернути увагу.

У картці товару часто важливі:

1. Зображення.
2. Назва товару.
3. Ціна.
4. Наявність або ключовий варіант.
5. Основна дія.

На сторінці товару пріоритети можуть змінюватися залежно від категорії.

### 17.1. Typography

Використовуйте різні рівні тексту:

- назва сторінки;
- назва товару;
- ціна;
- характеристики;
- допоміжна інформація;
- повідомлення про стан.

Не потрібно робити весь текст однаково великим або виділяти кожен елемент жирним.

### 17.2. Spacing

Відступи допомагають відокремлювати групи інформації.

Приклад системи:

    4px   — мінімальний відступ
    8px   — малий
    16px  — середній
    24px  — великий
    32px  — між великими групами

Це приклад шкали. Важливо підтримувати послідовність, а не використовувати саме ці значення за будь-яких умов.

### 17.3. Primary and secondary actions

Основна дія повинна бути помітнішою за другорядні.

Приклад:

    [Додати до кошика]  — primary
    [До обраного]       — secondary

Якщо всі кнопки мають однакову візуальну вагу, користувачеві складніше зрозуміти пріоритети.

Не створюйте багато варіантів, якщо вони не вирішують реальних задач.

## 19. UX metrics — оцінювання якості магазину

Інтерфейс потрібно оцінювати не лише за зовнішнім виглядом.

Можливі показники:

- **Conversion rate** — частка відвідувачів, які виконали цільову дію.
- **Add-to-cart rate** — частка відвідувачів або переглядів товару, що призвели до додавання в кошик; точне визначення залежить від аналітики.
- **Checkout completion rate** — частка користувачів, які завершили оформлення серед тих, хто його почав.
- **Cart abandonment rate** — частка кошиків, що не завершилися покупкою, за визначеним методом підрахунку.
- **Search success rate** — частка пошукових сценаріїв, що привели до корисного результату.
- **Task completion time** — час виконання користувацького завдання.
- **Error rate** — частота помилок під час виконання сценарію.

Ці метрики потрібно трактувати в контексті. Наприклад, низька конверсія не обов'язково означає поганий дизайн: на неї також впливають ціни, асортимент, сезонність, доставка та якість трафіку.

### 19.1. Usability testing

Запропонуйте користувачеві виконати конкретні завдання:

- знайти товар за заданими характеристиками;
- відфільтрувати товари за ціною;
- вибрати потрібний розмір;
- додати товар до кошика;
- змінити кількість;
- знайти умови доставки;
- оформити тестове замовлення.

Спостерігайте:

- де користувач зупиняється;
- які елементи не помічає;
- що розуміє неправильно;
- де робить помилки;
- які кроки виконує зайвий раз.

Не підказуйте рішення завчасно. Мета тестування — виявити проблеми інтерфейсу.

## 20. Типові помилки в e-commerce UI

### 20.1. Перевантажена головна сторінка

Проблема:
- багато банерів;
- надто багато кольорів;
- десятки одночасних закликів до дії.

Рішення:
- визначити головну мету сторінки;
- виділити пріоритетні категорії;
- прибрати зайві промоблоки;
- підтримувати чітку ієрархію.

### 20.2. Непомітна ціна

Проблема:
- ціна губиться серед опису;
- знижка показана незрозуміло;
- валюта не вказана.

Рішення:
- виділити актуальну ціну;
- пояснювати попередню ціну;
- показувати валюту;
- уникати двозначності.

### 20.3. Недостатня інформація про товар

Проблема:
- незрозумілі характеристики;
- немає даних про сумісність;
- не вказані важливі обмеження.

Рішення:
- додати структуровані характеристики;
- надати якісні зображення;
- пояснити сумісність;
- не замінювати конкретні дані рекламними фразами.

### 20.4. Складна фільтрація

Проблема:
- багато неочевидних параметрів;
- незрозуміло, які фільтри активні;
- складно очистити вибір.

Рішення:
- залишити корисні фільтри;
- групувати параметри;
- показувати активні значення;
- додати зрозуміле очищення.

### 20.5. Надто довгий checkout

Проблема:
- зайві поля;
- обов'язкова реєстрація;
- незрозумілі вимоги;
- повторне введення тих самих даних.

Рішення:
- збирати лише необхідну інформацію;
- використовувати автозаповнення;
- показувати зрозумілу послідовність;
- дозволяти виправити дані;
- не приховувати обов'язкові умови.

### 20.6. Незрозумілі помилки

Проблема:

    Error 400

Рішення:

    Не вдалося оформити замовлення.
    Перевірте контактні дані та спробуйте ще раз.

Повідомлення повинно бути зрозумілим, не розкривати внутрішні технічні подробиці та не звинувачувати користувача.

### 20.7. Поганий мобільний інтерфейс

Проблема:
- дрібні кнопки;
- горизонтальне прокручування;
- поля перекриваються;
- фільтри складно закрити;
- основна дія не помітна.

Рішення:
- тестувати реальні сценарії на вузькому екрані;
- перевіряти поведінку клавіатури;
- використовувати гнучкі сітки;
- забезпечувати достатні області натискання;
- перевіряти доступність.

## 21. Практичний проєкт: Mini E-commerce UI

Мета — спроєктувати навчальний інтерфейс інтернет-магазину з основними сценаріями покупки.

### 21.1. Мінімальний набір сторінок

    mini-ecommerce/
    ├── Home
    ├── Catalog
    ├── Product details
    ├── Cart
    ├── Checkout
    └── Order confirmation

Додатково, якщо дозволяє час:

    ├── Search results
    ├── Wishlist
    ├── Account
    └── Order history

### 21.2. Крок 1 — визначити користувача та товар

Виберіть одну предметну область:

- книги;
- одяг;
- електроніка;
- товари для дому;
- канцелярія;
- спортивні товари.

Визначте:

- хто купує;
- що користувач хоче знайти;
- які характеристики важливі;
- які питання виникають перед покупкою;
- які умови доставки та повернення потрібно показати.

### 21.3. Крок 2 — побудувати інформаційну архітектуру

Намалюйте структуру сторінок.

Приклад:

    Home
      ↓
    Catalog
      ↓
    Product details
      ↓
    Cart
      ↓
    Checkout
      ↓
    Confirmation

Перевірте, чи можна повернутися до каталогу, змінити вибір або виправити дані без втрати прогресу.

### 21.4. Крок 3 — створити wireframes

Wireframe — спрощений макет без детального візуального оформлення.

Спочатку визначте:

- розташування блоків;
- ієрархію інформації;
- основні дії;
- порядок кроків;
- поведінку на мобільному екрані.

Не починайте з декоративних деталей, якщо ще не зрозуміло, як працюватиме сценарій покупки.

### 21.5. Крок 4 — визначити UI components

Підготуйте компоненти:

    Header
    SearchField
    CategoryNavigation
    ProductCard
    ProductGrid
    FilterPanel
    SortSelect
    PriceDisplay
    Rating
    QuantitySelector
    CartItem
    CartSummary
    FormField
    OrderSummary
    StatusMessage
    EmptyState

Для кожного компонента визначте:

- призначення;
- структуру;
- основний стан;
- інтерактивні стани;
- адаптивну поведінку;
- доступність.

### 21.6. Крок 5 — створити дизайн-систему

Визначте:

- кольори;
- типографіку;
- відступи;
- ширину контейнера;
- радіуси;
- стилі кнопок;
- стилі полів;
- стани помилок;
- стани завантаження;
- правила сітки.

Переконайтеся, що компоненти виглядають як частини одного продукту.

### 21.7. Крок 6 — спроєктувати всі стани

Для каталогу:

- товари завантажуються;
- товари відображені;
- результатів немає;
- сталася помилка.

Для товару:

- є в наявності;
- немає в наявності;
- потрібно вибрати варіант;
- додавання до кошика виконується;
- товар успішно додано;
- виникла помилка.

Для кошика:

- порожній кошик;
- кошик із товарами;
- оновлення кількості;
- видалення товару;
- зміна ціни або наявності.

Для checkout:

- форма порожня;
- помилки валідації;
- обробка замовлення;
- успіх;
- помилка сервера або оплати.

### 21.8. Крок 7 — перевірити адаптивність і доступність

Перевірте:

- вузький смартфон;
- широкий смартфон;
- планшет;
- ноутбук;
- великий екран;
- клавіатурну навігацію;
- видимий фокус;
- контраст;
- назви полів;
- зрозумілість повідомлень;
- відсутність горизонтального прокручування без потреби.

### 21.9. Крок 8 — провести usability testing

Попросіть іншу людину виконати завдання:

    1. Знайти конкретний товар.
    2. Відфільтрувати каталог.
    3. Вибрати потрібний варіант.
    4. Додати товар до кошика.
    5. Змінити кількість.
    6. Перейти до оформлення.
    7. Знайти умови доставки.
    8. Завершити тестовий сценарій.

Записуйте проблеми й виправляйте найважливіші з них перед додаванням декоративних деталей.

## 22. Checklist — перевірка e-commerce UI

- [ ] Основна навігація зрозуміла.
- [ ] Пошук легко знайти.
- [ ] Категорії мають логічну структуру.

### Каталог

- [ ] Назви й ціни читаються.
- [ ] Фільтри зрозумілі.
- [ ] Сортування працює передбачувано.
- [ ] Активні фільтри видно.

- [ ] Є стан помилки й завантаження.

- [ ] Ціна зрозуміла.
- [ ] Наявність показана коректно.
- [ ] Варіанти можна вибрати.
- [ ] Характеристики структуровані.
- [ ] Умови доставки й повернення доступні.
- [ ] Основна дія помітна.
- [ ] Результат додавання до кошика зрозумілий.

- [ ] Кількість можна змінити.
- [ ] Товар можна видалити.
- [ ] Підсумок розрахований правильно.
- [ ] Порожній кошик має корисний стан.
- [ ] Зміни ціни або наявності пояснюються.

### Checkout

- [ ] Форма містить лише необхідні поля.
- [ ] Обов'язкові поля позначені.
- [ ] Помилки пояснюють, що виправити.
- [ ] Способи доставки зрозумілі.
- [ ] Способи оплати доступні та чітко позначені.
- [ ] Підсумок замовлення видно.

- [ ] Є зрозумілий екран підтвердження.

### Responsive та accessibility

- [ ] Інтерфейс працює на смартфоні.
- [ ] Немає небажаного горизонтального прокручування.
- [ ] Кнопки мають достатню область натискання.
- [ ] Усі інтерактивні елементи доступні з клавіатури.
- [ ] Фокус помітний.
- [ ] Поля мають доступні назви.
- [ ] Зображення мають доречний альтернативний текст.
- [ ] Контраст достатній.
- [ ] Стани не передаються лише кольором.
- [ ] Повідомлення про помилки зрозумілі.

## 23. Що потрібно запам'ятати

1. E-commerce UI — це не лише картки товарів, а повний шлях від пошуку до підтвердження замовлення.
2. Каталог повинен допомагати знаходити товари, а не просто демонструвати їх.
3. Картка товару має показувати головну інформацію: зображення, назву, ціну та доступну дію.
4. Сторінка товару повинна допомагати прийняти обґрунтоване рішення.
5. Фільтри й сортування вирішують різні задачі.
6. Кошик має забезпечувати контроль над товарами, кількістю та сумою.
7. Checkout повинен бути простим, передбачуваним і прозорим.
8. Потрібно проєктувати не лише успішні сценарії, а й помилки, порожні стани та завантаження.
9. Мобільний інтерфейс повинен підтримувати повний сценарій покупки.
10. Доступність потрібна для пошуку, вибору товару, форм і всіх інших етапів.
11. Довіра залежить від точності інформації, зрозумілих умов і чесної поведінки інтерфейсу.
12. Дизайн-система допомагає підтримувати узгодженість магазину.
13. Usability testing допомагає виявляти проблеми, які неочевидні дизайнеру.
14. Конверсія — важливий показник, але її не можна оцінювати без контексту.
15. Хороший магазин допомагає користувачеві зробити власний вибір, а не маніпулює ним.

## 24. Рівні навчання

### Core — базовий рівень

Я повинен уміти:

- пояснити призначення e-commerce UI;
- назвати основні сторінки магазину;
- побудувати просту структуру каталогу;
- створити картку товару;
- пояснити різницю між пошуком, фільтрами та сортуванням;
- спроєктувати кошик;
- визначити основну дію на сторінці;
- врахувати базові стани інтерфейсу.

### Junior — початковий практичний рівень

Я повинен уміти:

- спроєктувати каталог товарів;
- створити систему карток товарів;
- продумати сторінку товару;
- спроєктувати фільтри та сортування;
- побудувати сценарій кошика й checkout;
- створити адаптивні макети;
- передбачити помилки та порожні стани;
- перевірити базову доступність;
- провести простий usability test.

### Middle — середній рівень

Я повинен уміти:

- проєктувати складні каталоги;
- враховувати різні типи товарів і варіантів;
- будувати узгоджену дизайн-систему;
- оптимізувати складні форми;
- аналізувати проблеми користувацького шляху;
- обґрунтовувати рішення результатами тестування;
- працювати з edge cases;
- оцінювати взаємодію UI, UX та бізнес-логіки.

### Senior — просунутий рівень

Я повинен уміти:

- проєктувати e-commerce досвід для різних бізнес-моделей;
- оцінювати вплив UX-рішень на бізнес-метрики;
- планувати експерименти та A/B-тестування;
- знаходити баланс між бізнес-цілями та інтересами покупців;
- забезпечувати узгодженість дизайн-системи;
- враховувати доступність, приватність і безпеку;
- виявляти маніпулятивні патерни;
- формувати обґрунтовані рішення на основі досліджень і даних.
