# 01. Dashboard

Dashboard (панель керування) — це тип інтерфейсу, який збирає важливу інформацію, показники, статистику та інструменти керування в одному місці.

Dashboard допомагає користувачу швидко зрозуміти поточний стан системи, оцінити результати, знайти проблеми та виконати потрібні дії.

Dashboard використовується, коли потрібно:

- показати ключові показники системи;
- відобразити статистику та аналітику;
- контролювати стан бізнесу або проєкту;
- переглядати активність користувачів;
- керувати замовленнями, товарами або контентом;
- відстежувати задачі, повідомлення та сповіщення;
- працювати з великими обсягами даних;
- швидко переходити до основних функцій застосунку.

Типові приклади dashboard:

    Admin dashboard
    Analytics dashboard
    Business dashboard
    Project management dashboard
    E-commerce dashboard
    Financial dashboard
    SaaS dashboard
    Education dashboard
    Healthcare dashboard
    Personal dashboard

Dashboard — це не просто набір карток зі статистикою. Це інтерфейс, який повинен допомагати користувачу приймати рішення та виконувати конкретні завдання.

### Що потрібно пам'ятати

• Dashboard об'єднує найважливішу інформацію та основні дії в одному інтерфейсі.

• Основна мета dashboard — допомогти користувачу швидко зрозуміти ситуацію та діяти.

• KPI — показник, за яким оцінюють досягнення певної цілі.

• Metric — вимірювана величина, наприклад кількість замовлень або відвідувань.

• Widget — окремий функціональний блок dashboard.

• Summary card — картка з коротким підсумком певного показника.

• Chart — графічне представлення даних.

• Table — спосіб показати точні значення та детальні записи.

• Sidebar часто використовується для основної навігації.

• Filters допомагають показувати тільки потрібні дані.

• Date range дозволяє вибрати період, за який потрібно показати інформацію.

• Information hierarchy визначає, що користувач побачить і зрозуміє насамперед.

• Не всі показники однаково важливі. Найважливіші повинні бути візуально помітнішими.

• Надмірна кількість графіків, карток і кольорів ускладнює сприйняття інформації.

• Dashboard повинен показувати не тільки дані, а й їхній контекст: одиниці вимірювання, період, порівняння та статус.

• Loading, empty та error states потрібно проєктувати так само, як і звичайний стан інтерфейсу.

• Responsive dashboard повинен залишатися зрозумілим на різних розмірах екрана.

• Дані потрібно подавати відповідно до потреб користувача, а не просто тому, що їх можна показати.

• Хороший dashboard відповідає на запитання: «Що відбувається?», «Чи є проблема?» та «Що потрібно зробити?».

# Що таке Dashboard

Dashboard — це оглядовий інтерфейс, який показує найважливішу інформацію про систему, процес або діяльність користувача.

Наприклад, dashboard інтернет-магазину може показувати:

    Total revenue
    Total orders
    Average order value
    Conversion rate
    Recent orders
    Best-selling products
    Inventory status
    Sales chart

Користувач відкриває сторінку й одразу отримує загальне уявлення про стан магазину.

## Dashboard vs Website

Website зазвичай призначений для представлення інформації, контенту або послуг відвідувачам.

Dashboard призначений для огляду показників, контролю стану системи та виконання завдань.

Наприклад:

    Website
        ↓
    Read content
    Explore services
    Browse products
    Contact a company

    Dashboard
        ↓
    Review metrics
    Monitor activity
    Analyze data
    Manage operations

Це не абсолютне правило: dashboard може бути частиною великого website або web application.

## Dashboard vs Admin Panel

Admin panel — інтерфейс для керування користувачами, контентом, налаштуваннями та іншими ресурсами системи.

Dashboard — оглядова частина інтерфейсу, яка показує ключову інформацію.

Наприклад:

    Admin panel
        ├── Dashboard
        ├── Users
        ├── Products
        ├── Orders
        ├── Reports
        └── Settings

Dashboard часто є головною сторінкою admin panel, але ці поняття не тотожні.

## Dashboard vs Analytics

Analytics — аналіз даних для виявлення тенденцій, закономірностей і результатів.

Analytics dashboard — dashboard, орієнтований на аналітику.

Наприклад:

    Website analytics dashboard
        ├── Visitors
        ├── Traffic sources
        ├── Conversion rate
        ├── User behavior
        └── Traffic trends

# Dashboard Layout

Dashboard layout — структура розташування навігації, заголовка, показників, графіків, таблиць та інших елементів.

Типова структура:

    Dashboard
        ├── Sidebar
        │   ├── Logo
        │   ├── Main navigation
        │   └── User menu
        │
        ├── Main area
        │   ├── Header
        │   ├── Page title
        │   ├── Filters
        │   ├── KPI cards
        │   ├── Charts
        │   ├── Data tables
        │   └── Activity feed
        │
        └── Footer (optional)

Не кожен dashboard потребує всіх цих частин.

Структура залежить від кількості даних, основних завдань користувача та розміру екрана.

## Основні зони

### Header

Header розташовується у верхній частині інтерфейсу.

Може містити:

    Page title
    Breadcrumbs
    Global search
    Notifications
    Help
    User avatar
    Account menu

Header повинен забезпечувати швидкий доступ до глобальних функцій.

### Sidebar

Sidebar — бічна панель навігації.

Може містити:

    Dashboard
    Analytics
    Users
    Orders
    Products
    Reports
    Settings

Важливо:

- логічно групувати посилання;
- використовувати зрозумілі назви;
- позначати активний розділ;
- не перевантажувати навігацію;
- підтримувати клавіатурну навігацію;
- передбачити адаптивну поведінку.

### Main Content

Main content — основна робоча область dashboard.

Тут розміщуються:

    Page title
    Summary cards
    Charts
    Tables
    Filters
    Actions
    Reports

Основний контент повинен мати чітку візуальну ієрархію.

### Toolbar

Toolbar містить інструменти для роботи з даними.

Наприклад:

    Search
    Filters
    Sort
    Date range
    Export
    Add new item

Toolbar доцільно розміщувати поруч із тією таблицею або секцією, якою він керує.

# Grid Layout

Dashboard часто використовує CSS Grid для розташування карток, графіків та інших блоків.

Приклад HTML:

    <main class="dashboard">
        <section class="dashboard__stats">
            <article class="stat-card">
                <h2>Total Users</h2>
                <p>1,250</p>
            </article>

            <article class="stat-card">
                <h2>Active Users</h2>
                <p>830</p>
            </article>

            <article class="stat-card">
                <h2>Revenue</h2>
                <p>$24,500</p>
            </article>
        </section>

        <section class="dashboard__content">
            <article class="panel panel--chart">
                <h2>Revenue Overview</h2>
            </article>

            <article class="panel panel--activity">
                <h2>Recent Activity</h2>
            </article>
        </section>
    </main>

CSS:

    .dashboard {
        display: grid;
        gap: 1.5rem;
        padding: 1.5rem;
    }

    .dashboard__stats {
        display: grid;
        grid-template-columns:
            repeat(auto-fit, minmax(min(100%, 14rem), 1fr));
        gap: 1rem;
    }

    .dashboard__content {
        display: grid;
        grid-template-columns:
            minmax(0, 2fr)
            minmax(16rem, 1fr);
        gap: 1rem;
    }

    .stat-card,
    .panel {
        min-width: 0;
        padding: 1.25rem;
        border: 1px solid #e5e7eb;
        border-radius: 0.75rem;
        background: #ffffff;
    }

    @media (max-width: 48rem) {
        .dashboard__content {
            grid-template-columns: 1fr;
        }
    }

Тут:

    display: grid
        → створює grid container

    grid-template-columns
        → визначає колонки

    repeat()
        → повторює шаблон колонок

    minmax()
        → задає мінімальний і максимальний розмір

    auto-fit
        → розміщує доступну кількість колонок

    gap
        → задає проміжки між елементами

    min-width: 0
        → дозволяє grid item стискатися без переповнення

Важливо: адаптивність залежить не тільки від кількості колонок, а й від ширини тексту, таблиць, графіків та інших внутрішніх компонентів.

# Sidebar Layout Patterns

Існує кілька поширених способів організації sidebar.

## Fixed Sidebar

Sidebar має фіксовану ширину й залишається на місці під час прокручування основного контенту.

    .sidebar {
        position: fixed;
        inset: 0 auto 0 0;
        width: 16rem;
        overflow-y: auto;
    }

    .main {
        margin-left: 16rem;
    }

Переваги:

- навігація постійно доступна;
- зручно для великих систем;
- підходить для інтерфейсів із багатьма розділами.

Недоліки:

- займає частину екрана;
- потребує окремої адаптивної поведінки;
- може перекривати контент, якщо неправильно налаштований.

## Collapsible Sidebar

Collapsible sidebar можна згорнути до компактного стану.

Наприклад:

    Expanded
        [icon] Dashboard
        [icon] Analytics
        [icon] Users
        [icon] Settings

    Collapsed
        [icon]
        [icon]
        [icon]
        [icon]

Переваги:

- звільняє місце для контенту;
- корисний на ноутбуках і невеликих екранах;
- дозволяє користувачу керувати робочим простором.

Важливо:

- іконки повинні бути зрозумілими;
- для іконок без тексту потрібні доступні назви;
- кнопка згортання повинна мати зрозумілий стан;
- стан sidebar можна зберігати, якщо це виправдано UX.

## Overlay Sidebar

Sidebar відкривається поверх контенту.

Такий підхід часто використовується на мобільних пристроях.

    Menu button
        ↓
    Sidebar opens
        ↓
    User selects a section
        ↓
    Sidebar closes

Якщо панель працює як модальне вікно, потрібно передбачити керування фокусом, закриття клавішею Escape та повернення фокусу до кнопки відкриття.

# KPI Cards

KPI card — картка, яка показує ключовий показник.

Типова структура:

    Label
        ↓
    Main value
        ↓
    Comparison
        ↓
    Context

Наприклад:

    Monthly Revenue

    $24,500

    +12.5%

    Compared with previous month

KPI card може містити:

    Metric label
    Metric value
    Unit
    Trend
    Comparison period
    Icon
    Supporting description

## Metric Label

Label пояснює, що саме вимірюється.

Наприклад:

    Total Revenue
    Active Users
    Completed Orders
    Average Response Time

Не використовуй неоднозначні назви.

Наприклад, замість:

    Total: 1,250

краще:

    Total Users: 1,250

## Metric Value

Основне значення повинно бути візуально помітним.

Приклад:

    Active Users

    830

Не потрібно використовувати надмірно великий шрифт для кожного числа. Розмір залежить від важливості показника та загальної композиції.

## Comparison

Порівняння допомагає зрозуміти, чи змінилося значення.

Наприклад:

    Revenue: $24,500
    +12.5% compared with last month

Важливо вказувати період порівняння.

Зростання не завжди означає позитивний результат.

Наприклад:

    Expenses increased by 12.5%

Для витрат збільшення може бути небажаним.

## Trend Indicator

Trend indicator показує напрямок зміни.

Наприклад:

    ↑ Revenue increased
    ↓ Error rate decreased
    → No significant change

Не покладайся тільки на колір або стрілку.

Потрібно також показувати текстове значення або інше доступне пояснення.

## Приклад KPI Card

    <article class="stat-card">
        <h2>Total Orders</h2>

        <p class="stat-card__value">
            1,284
        </p>

        <p class="stat-card__trend">
            <span aria-hidden="true">↑</span>
            <span>8.2% compared with last month</span>
        </p>
    </article>

CSS:

    .stat-card__value {
        margin-block: 0.75rem;
        font-size: clamp(1.75rem, 3vw, 2.5rem);
        font-weight: 700;
        line-height: 1.1;
        font-variant-numeric: tabular-nums;
    }

    .stat-card__trend {
        margin: 0;
        color: #166534;
        font-size: 0.875rem;
    }

У production-інтерфейсі текст тренду повинен відповідати реальному значенню. Не можна показувати позитивну стрілку або зелений колір для показника, який погіршився.

# Metrics

Metric — числове значення, яке описує певний аспект системи.

Приклади:

    Revenue
    Number of users
    Number of orders
    Conversion rate
    Average session duration
    Error rate
    Completion rate

## Metric vs KPI

Metric — будь-який вимірюваний показник.

KPI — показник, який пов'язаний із конкретною ціллю або результатом.

Наприклад:

    Metric:
        Number of website visitors

    KPI:
        Conversion rate for a sales goal

Один і той самий показник може бути звичайною метрикою в одному контексті та KPI в іншому.

## Absolute Value

Абсолютне значення показує конкретну кількість.

    Total Users: 1,250
    Total Orders: 480
    Revenue: $24,500

## Percentage

Відсоток показує частку або відносне значення.

    Conversion Rate: 3.4%
    Completion Rate: 82%
    Error Rate: 0.8%

Завжди потрібно розуміти, від чого обчислюється відсоток.

## Rate

Rate показує частоту або співвідношення за певний період.

Наприклад:

    Requests per second
    Orders per day
    Errors per hour

## Average

Average — середнє значення.

Наприклад:

    Average Order Value
    Average Response Time
    Average Session Duration

Середнє може приховувати відмінності між окремими значеннями. Для деяких задач корисно показувати також медіану або розподіл.

# Data Visualization

Data visualization — графічне представлення даних, яке допомагає швидко побачити порівняння, зміни та закономірності.

Основні типи візуалізацій:

    Line chart
    Bar chart
    Column chart
    Pie chart
    Donut chart
    Area chart
    Scatter plot
    Histogram
    Progress bar
    Gauge
    Heatmap

Вибір типу графіка залежить від запитання, на яке повинен відповісти користувач.

---

## Line Chart

Line chart — лінійний графік.

Найчастіше використовується для показу змін у часі.

Наприклад:

    Revenue over time
    Website visitors over time
    Daily active users
    Average response time

Line chart допомагає побачити:

    Trends
    Growth
    Decline
    Peaks
    Seasonal patterns

Для часових даних потрібно чітко позначати вісь часу.

Не використовуй лінійний графік для категорій, між якими немає змістовної послідовності.

---

## Bar Chart

Bar chart — горизонтальна стовпчикова діаграма.

Підходить для порівняння категорій.

Наприклад:

    Sales by category
    Users by country
    Orders by status
    Revenue by product

Горизонтальні смуги особливо корисні для категорій із довгими назвами.

---

## Column Chart

Column chart — вертикальна стовпчикова діаграма.

Підходить для порівняння категорій або періодів.

Наприклад:

    Monthly sales
    Orders by month
    Revenue by region

Не варто розміщувати надто багато категорій, якщо через це підписи стають нерозбірливими.

---

## Pie Chart

Pie chart — кругова діаграма.

Використовується для показу частин цілого.

Наприклад:

    Traffic sources
    Budget distribution
    Order categories

Кругова діаграма найкраще підходить для невеликої кількості категорій, які разом становлять ціле.

Якщо потрібно порівнювати багато категорій або дуже близькі значення, bar chart зазвичай легше читати.

---

## Donut Chart

Donut chart — кругова діаграма з отвором у центрі.

Може показувати:

    Completion rate
    Resource allocation
    Distribution by category

У центрі можна розмістити загальне значення.

Наприклад:

    78%

    Tasks Completed

Не перевантажуй donut chart великою кількістю сегментів.

---

## Area Chart

Area chart — графік із зафарбованою областю під лінією.

Використовується для демонстрації зміни значення в часі.

Може бути корисним для:

    Total revenue
    Cumulative users
    Traffic volume

Потрібно уважно використовувати прозорість і накладання областей, особливо коли на графіку кілька серій даних.

---

## Progress Bar

Progress bar показує виконання завдання або досягнення певного значення.

Наприклад:

    Course progress: 65%
    Storage used: 72%
    Tasks completed: 8 of 10

HTML:

    <label for="course-progress">
        Course progress: 65%
    </label>

    <progress
        id="course-progress"
        value="65"
        max="100"
    >
        65%
    </progress>

Важливо:

- передбачити доступну назву;
- показувати числове значення, якщо воно важливе;
- не використовувати progress bar для значень без визначеної цілі;
- пояснювати, що саме вимірюється.

# Chart Design Principles

## 1. One Chart — One Main Question

Кожен графік повинен мати зрозумілу мету.

Наприклад:

    Question:
        How has revenue changed?

    Chart:
        Line chart

Інший приклад:

    Question:
        Which category has the most orders?

    Chart:
        Bar chart

Якщо графік намагається одночасно відповісти на багато різних запитань, його стає складніше читати.

## 2. Clear Labels

Графік повинен пояснювати:

    What is measured?
    What is the unit?
    What is the period?
    What do the categories mean?

Наприклад:

    Revenue by Month
    Revenue (USD)
    January — June 2026

## 3. Avoid Decorative Noise

Не потрібно додавати:

    Excessive gridlines
    Unnecessary 3D effects
    Too many colors
    Decorative shadows
    Unnecessary labels

Декоративні елементи не повинні відволікати від даних.

## 4. Use Color Meaningfully

Колір можна використовувати для розрізнення серій або позначення статусу.

Але:

- не покладайся тільки на колір;
- використовуй підписи та легенди;
- перевіряй контраст;
- не використовуй забагато кольорів одночасно;
- не змінюй значення кольору без причини.

## 5. Provide Context

Графік із числом без контексту часто малоінформативний.

Наприклад:

    Revenue: $24,500

Це значення саме по собі не відповідає на запитання, чи хороший це результат.

Корисний контекст:

    Revenue: $24,500
    Previous month: $21,000
    Change: +16.7%

Порівняння повинно використовувати однакові або чітко пояснені періоди.

# Tables in Dashboard

Table використовується, коли користувачу потрібно бачити точні значення, порівнювати записи або виконувати дії з даними.

Наприклад:

    Recent Orders

    Order ID | Customer | Status | Total
    #1024    | Anna    | Paid   | $120
    #1025    | Mark    | Pending| $85
    #1026    | Sofia   | Shipped| $240

Таблиці особливо корисні для:

    Orders
    Users
    Products
    Transactions
    Tasks
    Reports
    Audit logs

## Основні елементи таблиці

    Table title
    Column headers
    Rows
    Cells
    Sorting controls
    Filters
    Search
    Pagination
    Row actions

Не кожна таблиця потребує всіх цих елементів.

## Column Headers

Заголовки повинні чітко пояснювати значення колонок.

Наприклад:

    Customer
    Order Date
    Payment Status
    Total Amount

Уникай неоднозначних назв на зразок:

    Info
    Data
    Type
    Value

якщо контекст не пояснює їхнього значення.

## Row Actions

Row actions — дії над окремим записом.

Наприклад:

    View
    Edit
    Delete
    Download
    Approve

Дії потрібно розміщувати послідовно та робити зрозумілими.

Небезпечні дії, наприклад Delete, повинні мати відповідні запобіжники, якщо наслідки незворотні.

## Sorting

Sorting змінює порядок записів.

Наприклад:

    Name: A → Z
    Date: newest → oldest
    Revenue: highest → lowest

Потрібно показувати активний напрямок сортування та надавати зрозумілий спосіб його змінити.

## Pagination

Pagination розділяє великий набір записів на сторінки.

Наприклад:

    Showing 1–10 of 248
    Previous | 1 | 2 | 3 | ... | 25 | Next

Важливо:

- показувати поточну сторінку;
- позначати недоступні дії;
- зберігати зрозумілий порядок переходів;
- повідомляти, скільки записів показано;
- не створювати надто дрібні сторінки без потреби.

Pagination детальніше розглядається в розділі `09-forms-and-data-ui/11-pagination`.

# Filters and Search

Filters дозволяють обмежити набір даних за певними умовами.

Наприклад:

    Status: Paid
    Date: Last 30 days
    Category: Electronics
    Country: Ukraine

Search використовується для пошуку записів за текстом або іншими параметрами.

## Search Input

Приклад:

    <label for="order-search">
        Search orders
    </label>

    <input
        id="order-search"
        type="search"
        placeholder="Search by order ID or customer"
    >

Підказка в полі введення не замінює label.

## Date Range

Date range дозволяє вибрати часовий проміжок.

Наприклад:

    Today
    Last 7 days
    Last 30 days
    This month
    Custom range

Після зміни періоду важливо оновити дані й показати, до якого проміжку вони належать.

## Active Filters

Якщо фільтр застосовано, користувач повинен бачити його стан.

Наприклад:

    Status: Paid
    Date: Last 30 days

Можна використовувати filter chips із можливістю видалення окремих фільтрів.

## Clear Filters

Потрібно передбачити можливість скинути фільтри.

Наприклад:

    Clear all filters

Це особливо важливо, коли через комбінацію фільтрів таблиця не показує жодного результату.

# Information Hierarchy

Information hierarchy — організація інформації відповідно до її важливості.

У dashboard користувач повинен швидко знаходити:

    1. Main status
    2. Important metrics
    3. Problems and alerts
    4. Trends
    5. Detailed records
    6. Secondary actions

Це не універсальний порядок для кожної системи. Ієрархія залежить від основних завдань користувача.

Наприклад, dashboard служби підтримки може показувати прострочені звернення вище за загальну кількість користувачів.

Dashboard інтернет-магазину може ставити продажі та невиконані замовлення на перший план.

## Visual Hierarchy

Visual hierarchy допомагає відрізнити важливу інформацію від другорядної за допомогою:

    Typography
    Font weight
    Font size
    Spacing
    Contrast
    Position
    Grouping
    Color
    Shape

Приклад:

    Page title
        ↓
    Key metrics
        ↓
    Main chart
        ↓
    Detailed table
        ↓
    Secondary information

Не потрібно робити кожен елемент великим, яскравим і контрастним. Якщо все привертає увагу, ієрархія зникає.

# Data Density

Data density — кількість інформації, яку інтерфейс показує в певній області.

Dashboard може мати низьку, середню або високу щільність даних.

## Low Density

Мало елементів, великі відступи, багато вільного простору.

Підходить для:

    Personal dashboards
    Simple SaaS products
    Beginner-friendly interfaces
    Small screens

Перевага — інформація легко сприймається.

Недолік — користувачеві може знадобитися більше прокручування.

## High Density

Багато показників, таблиць і даних на одному екрані.

Підходить для:

    Trading interfaces
    Monitoring systems
    Complex admin panels
    Professional analytics tools

Перевага — досвідчений користувач може бачити більше інформації одночасно.

Недолік — інтерфейс стає складнішим для новачків.

## Як вибирати Data Density

Потрібно враховувати:

    User expertise
    Frequency of use
    Screen size
    Task complexity
    Data volume
    Decision urgency

Не потрібно прагнути показати максимум даних на одному екрані.

Головне — показувати достатньо інформації для виконання завдання.

# Dashboard Widgets

Widget — окремий блок інтерфейсу, який виконує певну функцію.

Наприклад:

    KPI widget
    Chart widget
    Table widget
    Activity widget
    Calendar widget
    Notification widget
    Task widget
    Weather widget

## Widget Structure

Типова структура:

    Widget header
        ├── Title
        ├── Optional description
        └── Actions

            </button>
        </header>

        <div class="widget__content">

Widget може мати локальні дії:

    Refresh
    Expand
    Open report
    Change period
    Configure
    Remove

Наприклад, кнопка Refresh повинна справді оновлювати дані, а не просто змінювати вигляд інтерфейсу.

## Widget Customization

У деяких dashboard користувач може:

    Reorder widgets
    Hide widgets
    Resize widgets
    Add widgets
    Change widget settings

Однак не кожен dashboard потребує складного редактора компонування.

Спочатку варто забезпечити хороше стандартне компонування.

- показувати релевантний час;
- не перевантажувати стрічку другорядними подіями;
- враховувати права доступу та конфіденційність.

# Notifications and Alerts

Notifications інформують про події, які можуть потребувати уваги користувача.

Alerts повідомляють про важливий стан, проблему або необхідну дію.

Приклади:

    Success:
        Report generated successfully.

    Warning:
        Storage usage is above 80%.

    Error:
        Unable to load the report.

    Information:
        A new version is available.

## Notification vs Alert

Notification зазвичай повідомляє про подію.

Alert акцентує увагу на стані, ризику або проблемі.

На практиці ці поняття можуть перетинатися.

## Alert Priority

Можна виділити:

    Informational
    Success
    Warning
    Error
    Critical

Рівні повинні відповідати реальній важливості ситуації.

Не потрібно показувати критичне попередження для звичайної інформаційної події.

## Accessible Alerts

Не покладайся тільки на колір.

Використовуй текстові повідомлення та зрозумілі назви.

Для динамічних повідомлень у web-інтерфейсі можуть бути доречними ARIA live regions.

Наприклад:

    <div role="status" aria-live="polite">
        Report generated successfully.
    </div>

Для термінових повідомлень іноді підходить:

    <div role="alert">
        Unable to save changes.
    </div>

Не використовуй `role="alert"` для кожного повідомлення: надмірні оголошення заважають користувачам скринрідерів.

# Dashboard States

Dashboard повинен передбачати не тільки успішне завантаження даних, а й інші стани.

Основні стани:

    Loading state
    Success state
    Empty state
    Error state
    Partial data state
    Offline state
    No permission state

---

## Loading State

Loading state показує, що система завантажує дані.

Варіанти:

    Spinner
    Skeleton
    Loading message
    Progress indicator

Приклад:

    Loading dashboard...

Для великих dashboard можна показувати skeleton окремих карток і таблиць, щоб користувач розумів структуру сторінки.

Не потрібно без необхідності блокувати весь інтерфейс, якщо окремі секції можуть завантажуватися незалежно.

## Skeleton Loading

Skeleton — тимчасовий placeholder, який імітує форму майбутнього контенту.

Наприклад:

    [████████████]
    [██████]

    [████████████████]
    [████████]

Skeleton допомагає зрозуміти, де з'являться дані.

Він не повинен виглядати як справжня інформація або вводити користувача в оману.

## Empty State

Empty state показує, що даних немає.

Наприклад:

    No projects yet.

    Create your first project to get started.

    [Create project]

Empty state може виникати, коли:

    No data exists
    No search results found
    No items match filters
    No activity has occurred

Потрібно розрізняти ці ситуації.

Наприклад, відсутність проєктів і відсутність результатів пошуку — різні стани, які можуть вимагати різних дій.

## Error State

Error state повідомляє, що система не змогла виконати операцію.

Наприклад:

    Unable to load dashboard data.

    Please try again.

    [Retry]

Повідомлення повинно пояснювати:

    What happened
    What the user can do
    Whether the action can be retried

Не показуй технічні деталі або конфіденційну інформацію, яка не потрібна користувачу.

## Partial Data State

Іноді одна частина dashboard завантажується успішно, а інша — ні.

Наприклад:

    Revenue chart:
        Loaded

    Recent orders:
        Failed to load

У такому випадку доцільно показати доступну інформацію й окремо повідомити про проблему з таблицею.

## No Permission State

Користувач може не мати доступу до певної секції.

Інтерфейс повинен пояснити ситуацію відповідно до правил безпеки системи.

Наприклад:

    You don't have permission to view this report.

Приховування елементів в UI не замінює перевірку прав доступу на сервері.

# Real-Time Dashboard

Real-time dashboard відображає дані, які оновлюються під час роботи системи або з невеликою затримкою.

Наприклад:

    Server monitoring
    Live orders
    Support queue
    System alerts
    Active sessions

Можливі способи оновлення:

    Manual refresh
    Polling
    Server-Sent Events
    WebSockets

## Manual Refresh

Користувач сам запускає оновлення.

Перевага — простота та контроль.

Недолік — дані можуть застарівати, якщо користувач забуває оновити сторінку.

## Polling

Клієнт регулярно надсилає запит до сервера.

Наприклад:

    Fetch data
        ↓
    Wait
        ↓
    Fetch again
        ↓
    Update UI

Polling підходить для задач, де достатньо періодичного оновлення.

## Server-Sent Events

Server-Sent Events (SSE) дозволяє серверу надсилати події клієнту через постійне HTTP-з'єднання.

Може використовуватися для:

    Live notifications
    Progress updates
    Monitoring events

## WebSockets

WebSockets забезпечують двосторонній обмін повідомленнями між клієнтом і сервером через постійне з'єднання.

Можуть використовуватися для:

    Real-time collaboration
    Live monitoring
    Chat
    Frequently updated dashboards

Не кожен dashboard потребує real-time оновлення.

Потрібно враховувати затримку, навантаження, вартість реалізації та важливість актуальності даних.

        dateRange: "last-30-days",

Це звичайний приклад об'єкта JavaScript для опису стану, а не обов'язкова структура кожного застосунку.

Наприклад:

    /dashboard/orders?status=paid&page=2

Переваги:

- працює навігація Back і Forward;
- сторінку легше відновити після перезавантаження.

Не кожен стан потрібно зберігати в URL. Наприклад, тимчасове відкриття dropdown зазвичай не потребує окремого параметра.

# Responsive Dashboard

Responsive dashboard — dashboard, який адаптує компонування до ширини екрана та способу взаємодії.

Типові пристрої:

    Desktop
    Laptop
    Tablet
    Mobile

Desktop dashboard часто використовує кілька колонок.

На мобільному пристрої потрібно переосмислити порядок і пріоритет інформації.

## Desktop Layout

Наприклад:

    Sidebar | Main content

    KPI 1 | KPI 2 | KPI 3 | KPI 4

    Main chart        | Activity

    Recent orders table

## Tablet Layout

Наприклад:

    Sidebar or compact navigation

    KPI 1 | KPI 2

    KPI 3 | KPI 4

    Main chart

    Activity

    Recent orders

## Mobile Layout

Наприклад:

    Header

    Main KPI

    Other KPI cards

    Main chart

    Activity

    Recent orders

На мобільному пристрої важливо визначити, які показники та дії потрібні першими.

Не обов'язково просто зменшувати desktop layout.

## Responsive Sidebar

Можливі варіанти:

    Desktop:
        Expanded sidebar

    Tablet:
        Collapsible sidebar

    Mobile:
        Drawer or compact navigation

Вибір залежить від складності системи та частоти переходів між розділами.

## Responsive Cards

Приклад:

    .dashboard__stats {
        display: grid;
        grid-template-columns:
            repeat(auto-fit, minmax(min(100%, 14rem), 1fr));
        gap: 1rem;
    }

Такий підхід дозволяє карткам адаптуватися до доступної ширини.

## Responsive Charts

Графіки повинні залишатися читабельними на вузьких екранах.

Можна:

- скорочувати підписи;
- зменшувати кількість видимих міток;
- змінювати компонування легенди;
- використовувати горизонтальне прокручування, коли воно справді потрібне;
- показувати спрощену версію графіка;
- надавати альтернативну таблицю даних.

Не варто просто зменшувати весь графік до розміру, на якому неможливо прочитати підписи.

# Accessibility in Dashboard

Accessibility — доступність інтерфейсу для людей із різними можливостями та способами взаємодії.

Dashboard часто містить багато інформації, таблиць, графіків і елементів керування, тому доступність потрібно враховувати з самого початку.

## Semantic HTML

Використовуй елементи відповідно до їхнього призначення.

    <header>
        <!-- Page header -->
    </header>

    <nav aria-label="Main navigation">
        <!-- Navigation links -->
    </nav>

    <main>
        <h1>Dashboard</h1>

        <section aria-labelledby="metrics-title">
            <h2 id="metrics-title">
                Key metrics
            </h2>

            <!-- KPI cards -->
        </section>
    </main>

## Heading Hierarchy

Заголовки повинні відображати структуру сторінки.

Наприклад:

    h1 — Dashboard

        h2 — Key metrics

        h2 — Revenue overview

        h2 — Recent orders

            h3 — Order details (if appropriate)

Не вибирай рівень заголовка тільки через його візуальний розмір.

## Keyboard Navigation

Користувач повинен мати змогу працювати з інтерфейсом за допомогою клавіатури.

Перевір:

    Tab
    Shift + Tab
    Enter
    Space
    Escape
    Arrow keys (where appropriate)

Усі інтерактивні елементи повинні мати видимий focus state.

## Color Contrast

Текст і важливі елементи повинні мати достатній контраст.

Не використовуй занадто світлий текст на світлому фоні.

Для графіків перевіряй, чи можна розрізнити серії даних без покладання виключно на колір.

## Accessible Charts

Для графіка потрібно передбачити:

    Clear title
    Axis labels
    Units
    Legend
    Text summary
    Accessible data alternative when needed

Складний графік може потребувати таблиці з відповідними значеннями.

## Screen Reader Support

Використовуй доступні назви для кнопок, полів та іконок.

Наприклад:

    <button
        type="button"
        aria-label="Refresh dashboard"
    >
        <!-- Refresh icon -->
    </button>

Для кнопок із видимим текстом додатковий `aria-label` часто не потрібний.

Не додавай ARIA без потреби, якщо семантичний HTML уже надає правильну інформацію.

## Reduced Motion

Якщо dashboard використовує анімації, враховуй налаштування користувача.

Наприклад:

    @media (prefers-reduced-motion: reduce) {
        *,
        *::before,
        *::after {
            animation-duration: 0.01ms !important;
            animation-iteration-count: 1 !important;
            transition-duration: 0.01ms !important;
            scroll-behavior: auto !important;
        }
    }

У production-коді краще обмежувати такі правила відповідними компонентами, якщо глобальне вимкнення анімацій не є обґрунтованим рішенням.

# Dashboard Typography

Типографіка допомагає відрізняти назви розділів, показники, підписи та другорядні дані.

Приклад ієрархії:

    Page title
        2rem

    Section title
        1.25rem

    KPI value
        2rem

    Card label
        0.875rem

        0.875rem

Ці значення не є обов'язковими. Вони залежать від шрифту, щільності інтерфейсу та розміру екрана.

## Numeric Typography

Для таблиць і KPI корисно використовувати:

    font-variant-numeric: tabular-nums;

Це дозволяє цифрам займати однакову ширину в шрифтах, які підтримують цю функцію.

Форматування залежить від мови та локалі продукту.

Для грошових значень також потрібно враховувати валюту.

# Dashboard Performance

Dashboard може завантажувати великі обсяги даних, графіки та таблиці.

Тому важливо враховувати продуктивність.

## Load Important Content First

Спочатку завантажуй інформацію, яка потрібна користувачу для першого огляду.

Наприклад:

    Page shell
        ↓
    Main metrics
        ↓
    Primary chart
        ↓
    Secondary widgets
        ↓
    Large historical table

Це концептуальна послідовність. Реальний порядок залежить від залежностей між даними та потреб користувача.

## Avoid Unnecessary Requests

Не потрібно повторно завантажувати дані без причини.

Можна використовувати:

    Request caching
    Pagination
    Server-side filtering
    Debounced search
    Lazy loading
    Incremental updates

Вибір залежить від архітектури застосунку.

## Pagination for Large Datasets

Не обов'язково завантажувати тисячі записів одразу.

Можна отримувати дані частинами.

Наприклад:

    GET /api/orders?page=1&limit=20

Сервер повинен перевіряти параметри запиту та обмежувати допустимий обсяг даних.

## Avoid Layout Shifts

Різка зміна розміру карток після завантаження графіка може порушувати сприйняття сторінки.

Можна резервувати місце для графіків:

    .chart-container {
        min-height: 18rem;
    }

Для графіків із фіксованим співвідношенням сторін можна використовувати `aspect-ratio`.

# Dashboard Data Architecture

У web-застосунку dashboard зазвичай складається з кількох рівнів.

    Database
        ↓
    Backend API
        ↓
    Frontend data layer
        ↓
    UI components
        ↓
    Dashboard

Наприклад:

    PostgreSQL
        ↓
    Node.js / NestJS API
        ↓
    Fetch or data library
        ↓
    React components
        ↓
    Dashboard UI

Це один із можливих варіантів архітектури.

## Database

База даних зберігає вихідні дані.

Наприклад:

    users
    orders
    products
    payments
    events

## Backend API

Backend може повертати агреговані показники.

Наприклад:

    GET /api/dashboard/summary

Умовна відповідь:

    {
        "totalUsers": 1250,
        "activeUsers": 830,
        "totalOrders": 480,
        "revenue": 24500
    }

Це приклад структури відповіді, а не реальні дані.

## Frontend

Frontend отримує дані та відображає їх у компонентах.

Наприклад:

    Dashboard
        ├── DashboardHeader
        ├── DashboardFilters
        ├── StatsGrid
        │   ├── StatCard
        │   ├── StatCard
        │   └── StatCard
        ├── RevenueChart
        └── RecentOrdersTable

## UI Components vs Business Logic

Компоненти UI відповідають за представлення інформації.

Business logic відповідає за правила обчислень і поведінку системи.

Наприклад:

    API
        → provides revenue

    Dashboard component
        → displays revenue

Якщо показник має важливе бізнес-значення, не слід покладатися тільки на розрахунок у браузері.

Права доступу та критичні правила потрібно перевіряти на сервері.

# Dashboard in React

У React dashboard зазвичай складається з невеликих компонентів.

Приклад структури:

    src/
    └── components/
        └── dashboard/
            ├── Dashboard.tsx
            ├── DashboardHeader.tsx
            ├── DashboardStats.tsx
            ├── StatCard.tsx
            ├── RevenueChart.tsx
            ├── RecentOrders.tsx
            └── dashboard.module.css

Приклад компонента KPI:

    type StatCardProps = {
        title: string;
        value: string;
        description?: string;
    };

    export function StatCard({
        title,
        value,
        description
    }: StatCardProps) {
        return (
            <article className="stat-card">
                <h2>{title}</h2>

                <p className="stat-card__value">
                    {value}
                </p>

                {description && (
                    <p>{description}</p>
                )}
            </article>
        );
    }

Приклад використання:

    const stats = [
        {
            title: "Total Users",
            value: "1,250",
            description: "All registered users"
        },
        {
            title: "Active Users",
            value: "830",
            description: "Active this month"
        },
        {
            title: "Total Orders",
            value: "480",
            description: "Orders received"
        }
    ];

    function DashboardStats() {
        return (
            <section aria-labelledby="stats-title">
                <h2 id="stats-title">
                    Key metrics
                </h2>

                <div className="dashboard__stats">
                    {stats.map((stat) => (
                        <StatCard
                            key={stat.title}
                            title={stat.title}
                            value={stat.value}
                            description={stat.description}
                        />
                    ))}
                </div>
            </section>
        );
    }

Це демонстраційний приклад. У реальному застосунку дані можуть надходити з API, а типи та форматування можуть бути винесені в окремі модулі.

Важливо:

    Dashboard
        → assembles page sections

    StatCard
        → displays one metric

    RevenueChart
        → displays chart data

    RecentOrders
        → displays order records

Такий поділ робить компоненти простішими для повторного використання та тестування.

# Dashboard in Next.js

У Next.js dashboard може складатися із серверних і клієнтських компонентів.

Типова структура:

    src/
    └── app/
        └── dashboard/
            ├── page.tsx

            └── components/

                └── RecentOrders.tsx

Це приклад можливої структури, а не обов'язкова схема.

## Server Components

Server Components підходять для компонентів, яким не потрібні браузерні події або локальний клієнтський стан.

Наприклад, вони можуть отримувати дані на сервері й передавати їх до UI.

## Client Components

Client Components потрібні, коли компонент використовує:

    useState
    useEffect
    Event handlers
    Browser APIs
    Interactive chart controls

Не потрібно робити весь dashboard клієнтським без необхідності.

## Loading UI

Файл `loading.tsx` може визначати UI, який показується під час завантаження сегмента маршруту.

## Error UI

Файл `error.tsx` використовується для обробки помилок у відповідному сегменті маршруту. У стандартному підході Next.js такий компонент має бути клієнтським.

Файли `loading.tsx` та `error.tsx` не замінюють обробку помилок окремих API-запитів, якщо dashboard складається з незалежних секцій.

# Dashboard Security

Dashboard часто містить важливі бізнес-дані, тому безпека є частиною дизайну та архітектури.

Основні поняття:

    Authentication
    Authorization
    Role-based access control
    Data privacy
    Secure API
    Audit log
    Session management

## Authentication

Authentication відповідає на запитання:

    Who are you?

Наприклад, користувач входить до системи за допомогою облікових даних.

## Authorization

Authorization відповідає на запитання:

    What are you allowed to do?

Наприклад:

    Admin
        → manage users

    Editor
        → manage content

    Viewer
        → read reports

Це лише приклад ролей.

## Role-Based Dashboard

Різні ролі можуть бачити різні набори функцій.

Наприклад:

    Admin Dashboard
        → users, settings, reports

    Teacher Dashboard
        → courses, students, assignments

    Student Dashboard
        → courses, grades, schedule

Важливо: приховування кнопок на frontend не є достатнім захистом. Backend повинен перевіряти права доступу до кожного захищеного ресурсу.

## Sensitive Data

Не показуй персональні, медичні, фінансові або інші конфіденційні дані користувачам, які не мають права їх переглядати.

Також не потрібно включати секретні дані до frontend-коду або публічних API-відповідей.

# Dashboard UX Principles

## 1. Start with User Goals

Перед створенням dashboard визнач:

    Who uses it?
    What decisions do they make?
    What tasks do they perform?
    Which metrics matter?
    How often do they use it?

Не починай із випадкового набору карток.

## 2. Prioritize Important Information

Розміщуй найважливіші показники у найбільш помітних місцях.

Але не існує універсального правила, що найважливіші дані завжди повинні бути зверху зліва. Це залежить від завдань користувача, мови, пристрою та структури інтерфейсу.

## 3. Group Related Information

Об'єднуй споріднені показники.

Наприклад:

    Sales
        ├── Revenue
        ├── Orders
        └── Average Order Value

    Users
        ├── Total Users
        ├── Active Users
        └── New Users

Групування допомагає користувачу зрозуміти зв'язки між показниками.

## 4. Reduce Cognitive Load

Не змушуй користувача щоразу розбиратися в новій структурі.

Використовуй послідовні:

    Layouts
    Labels
    Colors
    Icons
    Status patterns
    Interactions

## 5. Show Actionable Information

Dashboard повинен допомагати зрозуміти, що робити далі.

Наприклад:

    12 overdue tasks

    [View overdue tasks]

Число показує стан, а дія дозволяє перейти до відповідної роботи.

## 6. Avoid Unnecessary Widgets

Кожен блок повинен відповідати на реальне запитання або допомагати виконувати завдання.

Якщо віджет не допомагає користувачу, варто переглянути його необхідність.

## 7. Keep Terminology Consistent

Використовуй однакові назви для однакових понять у всьому застосунку.

Наприклад, не називай ту саму сутність одночасно:

    Customer
    Client
    User

якщо між цими поняттями немає змістовної різниці.

Послідовність створення dashboard може виглядати так:

    1. Understand users
            ↓
    2. Define user goals
            ↓
    3. Identify key metrics
            ↓
    4. Group information
            ↓
    5. Design information hierarchy
            ↓
    6. Create wireframe
            ↓
    7. Choose layout
            ↓
    8. Design components
            ↓
    9. Add visual styling
            ↓
    10. Design responsive states
            ↓
    11. Check accessibility
            ↓
    12. Test with users
            ↓
    13. Improve the interface

## Step 1 — Understand Users

Визнач:

    User roles
    Experience level
    Main tasks
    Usage frequency
    Devices
    Pain points

## Step 2 — Define Goals

Сформулюй, що користувач повинен зрозуміти або зробити.

Наприклад:

    Review recent activity.
    Open a detailed report.

Для кожної метрики визнач:

    Unit
    Time period
    Data source
    Comparison method

Не варто показувати метрику, значення якої користувач не може правильно інтерпретувати.

## Step 4 — Group Information

Наприклад:

    Overview
        → KPI cards

    Performance
        → Charts

    Operations
        → Tables

    Activity
        → Recent events

    Management
        → Quick actions

## Step 5 — Create Wireframe

Спочатку створи просту структуру без детального оформлення.

    ┌─────────────────────────────────────┐

Наприклад:

# Типові помилки Dashboard Design

## 1. Too Many Cards

❌ На сторінці десятки карток без чіткого пріоритету.

Проблема:

    Too many metrics
        ↓
    Weak hierarchy
        ↓
    Hard to identify important information

Краще:

- залишити основні KPI;
- згрупувати другорядні показники;
- перенести деталі до відповідних розділів;
- використовувати звіти для глибокого аналізу.

## 2. Unclear Metrics

❌

    Value: 250

Користувач не знає, що саме означає число.

Краще:

    Active Users: 250

Якщо потрібно, додай період і визначення метрики.

## 3. Missing Context

❌

    Revenue: $24,500

Невідомо, чи це значення за день, місяць або весь період роботи.

Краще:

    Revenue
    $24,500
    October 2026

## 4. Misleading Charts

❌ Графік використовує невідповідну шкалу або неправильний тип візуалізації.

Проблема:

    Distorted visual impression
        ↓
    Incorrect interpretation

Краще:

- вибирати графік відповідно до типу даних;
- правильно позначати осі;
- не приховувати важливий контекст;
- перевіряти масштаб;
- не використовувати декоративні ефекти, які спотворюють сприйняття.

## 5. Excessive Colors

❌ Кожна картка має інший яскравий колір.

Проблема:

    Too many visual accents
        ↓
    Reduced hierarchy

Краще використовувати нейтральну основу та обмежену кількість осмислених акцентів.

## 6. Desktop-Only Design

❌ Dashboard добре виглядає на великому моніторі, але не працює на мобільному пристрої.

Проблема:

    Overflow
    Tiny text
    Unreadable charts
    Inaccessible actions

Краще проєктувати адаптивні компоненти та перевіряти їх на реальних розмірах екрана.

## 7. Missing Empty States

❌ Порожня картка без пояснення.

Користувач не знає, чи немає даних, чи сталася помилка.

Краще:

    No data available for this period.

    Try selecting another date range.

## 8. Loading Forever

❌ Spinner без пояснення, який ніколи не зникає.

Краще:

- показувати стан завантаження;
- обробляти помилки;
- надавати можливість повторити запит;
- не приховувати доступні дані без потреби.

## 9. Color-Only Status

❌ Червоний і зелений індикатори без тексту.

Користувач може не зрозуміти їхнє значення.

Краще:

    Paid
    Pending
    Failed

Колір може доповнювати текстовий статус.

## 10. Unnecessary Real-Time Updates

❌ Усі показники оновлюються щосекунди, хоча користувачеві це не потрібно.

Можливі наслідки:

    Extra network traffic
    Unnecessary rendering
    Distracting changes
    Increased system load

Краще визначити, які дані потребують негайного оновлення, а які можуть оновлюватися періодично.

## 11. Hiding Important Actions

❌ Основна дія прихована серед другорядних кнопок або в незрозумілому меню.

Краще розміщувати важливу дію там, де користувач очікує її побачити.

## 12. Dashboard Without a Clear Purpose

❌ Dashboard показує дані, але не допомагає виконувати завдання.

Краще пов'язувати кожну основну секцію з конкретним запитанням або потребою користувача.

# Головне

• Dashboard — це інтерфейс для огляду важливої інформації, контролю стану системи та виконання завдань.

• Dashboard повинен відповідати реальним потребам користувача, а не просто показувати багато даних.

• KPI — показник, пов'язаний із певною ціллю. Metric — загальна вимірювана величина.

• KPI cards повинні містити зрозумілі назви, значення, одиниці вимірювання та контекст.

• Порівняння метрик має враховувати період, визначення показника та характер бажаної зміни.

• Графік потрібно вибирати відповідно до типу даних і запитання, на яке він повинен відповісти.

• Line chart зручний для тенденцій у часі.

• Bar chart зручний для порівняння категорій.

• Pie chart і donut chart можуть показувати частини цілого, але стають менш читабельними за великої кількості категорій.

• Таблиці підходять для точних значень, детальних записів і дій над ними.

• Search, filters, sorting і pagination допомагають працювати з великими наборами даних.

• Sidebar і header забезпечують навігацію та доступ до глобальних дій.

• Information hierarchy визначає, яку інформацію користувач помічає насамперед.

• Data density потрібно адаптувати до досвіду користувача, складності завдань і розміру екрана.

• Widgets повинні мати зрозумілу мету та послідовну структуру.

• Quick actions дозволяють швидко виконувати поширені завдання.

• Activity feed показує останні події, а notifications та alerts привертають увагу до важливої інформації.

• Dashboard повинен мати loading, empty та error states.

• Responsive dashboard повинен адаптувати не тільки розміри, а й пріоритети контенту.

• На мобільному пристрої таблиці, графіки та навігація потребують окремої уваги.

• Accessibility включає семантичний HTML, keyboard navigation, focus states, достатній контраст і доступні альтернативи графікам.

• Не можна позначати важливий статус тільки кольором.

• Для великих наборів даних можуть знадобитися pagination, server-side filtering, caching та агрегування.

• Real-time оновлення потрібно використовувати тоді, коли актуальність даних справді важлива.

• У React dashboard зручно будувати з невеликих повторно використовуваних компонентів.

• У Next.js потрібно обирати між Server Components і Client Components відповідно до потреб компонента.

• Дані, отримані з API, повинні мати зрозумілі стани завантаження, успіху та помилки.

• Безпека dashboard залежить від перевірки прав доступу на сервері, а не тільки від приховування елементів інтерфейсу.

• Перед створенням dashboard потрібно визначити користувачів, їхні цілі, ключові показники та основні сценарії роботи.

• Хороший dashboard допомагає відповісти на три основні запитання:

    1. Що зараз відбувається?
    2. Що потребує уваги?
    3. Яку дію потрібно виконати?

• Головний принцип dashboard design:

    Show the right information
    to the right user
    at the right time
    in a clear and actionable way.
