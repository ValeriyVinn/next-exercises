# Mobile Interface — Мобільний інтерфейс

> Шпаргалка з UI Design: принципи проєктування мобільних інтерфейсів, адаптація компонентів для смартфонів, навігація, жести, сенсорні елементи керування, форми та responsive design.

---

## 1. Що таке Mobile Interface

**Mobile Interface (мобільний інтерфейс)** — це інтерфейс користувача, спроєктований для взаємодії з вебсайтом або застосунком на смартфонах та інших мобільних пристроях.

Мобільний інтерфейс враховує:

- невелику ширину екрана;
- сенсорне керування пальцями;
- обмежений простір для контенту;
- різні орієнтації екрана;
- змінні умови використання: рух, яскраве світло, нестабільний інтернет;
- особливості мобільних браузерів;
- потребу швидко виконувати основні завдання.

### Основна мета

Допомогти користувачу виконати потрібну дію швидко, зрозуміло та без зайвих перешкод.

Наприклад, мобільна сторінка інтернет-магазину повинна дозволяти:

- переглянути товар;
- прочитати ціну та характеристики;
- вибрати кількість;
- додати товар у кошик;
- перейти до оформлення замовлення.

На маленькому екрані всі ці дії мають залишатися доступними без надмірного масштабування, горизонтального прокручування та складних жестів.

---

## 2. Mobile-first design

**Mobile-first** — підхід, за якого інтерфейс спочатку проєктують для маленьких екранів, а потім поступово розширюють для планшетів і комп'ютерів.

Це допомагає визначити найважливіший контент і не перевантажувати інтерфейс другорядними елементами.

### Послідовність роботи

1. Визначити основне завдання користувача.
2. Вибрати найважливіший контент.
3. Спроєктувати простий мобільний макет.
4. Перевірити навігацію та сенсорні елементи.
5. Додати адаптацію для ширших екранів.
6. Перевірити поведінку інтерфейсу на різних розмірах.

### Mobile-first і desktop-first

| Mobile-first | Desktop-first |
|---|---|
| Спочатку маленький екран | Спочатку великий екран |
| Контент додається поступово | Складний макет спрощується |
| Пріоритет основним діям | Можлива надмірна кількість елементів |
| Зазвичай використовує `min-width` | Часто використовує `max-width` |

### Приклад CSS

    /* Базові стилі для мобільного екрана */

    .product-list {
      display: grid;
      grid-template-columns: 1fr;
      gap: 1rem;
    }

    /* Розширення для планшета */

    @media (min-width: 600px) {
      .product-list {
        grid-template-columns: repeat(2, minmax(0, 1fr));
      }
    }

    /* Розширення для широкого екрана */

    @media (min-width: 900px) {
      .product-list {
        grid-template-columns: repeat(3, minmax(0, 1fr));
      }
    }

**Важливо:** конкретні точки перелому залежать від контенту та поведінки макета, а не лише від назв пристроїв.

## 3. Основні принципи мобільного інтерфейсу

### 3.1. Простота

На мобільному екрані кожен елемент повинен мати зрозумілу функцію.

- Прибирай декоративні елементи, які заважають виконанню завдання.
- Не показуй усі можливості одночасно.
- Групуй пов'язані функції.
- Використовуй зрозумілі назви кнопок.
- Залишай достатньо вільного простору.

### 3.2. Пріоритет контенту

Найважливіша інформація повинна бути доступна першою.

Наприклад, на сторінці товару:

1. Назва товару.
2. Фото.
3. Ціна.
4. Наявність.
5. Основна кнопка дії.
6. Характеристики та додаткова інформація.

Порядок може змінюватися залежно від конкретного завдання користувача.

### 3.3. Передбачуваність

Інтерфейс повинен поводитися так, як очікує користувач.

- Однакові дії мають виглядати однаково.
- Кнопки повинні мати зрозумілі підписи.
- Навігація повинна бути послідовною.
- Після виконання дії потрібно показувати результат.
- Не використовуй незрозумілі жести як єдиний спосіб керування.

### 3.4. Мінімум введення

Набирати текст на смартфоні складніше, ніж на клавіатурі комп'ютера.

Тому варто:

- скорочувати кількість полів;
- використовувати відповідні типи введення;
- автоматично підставляти відомі дані, коли це доречно;
- пропонувати вибір замість ручного введення;
- не просити повторно інформацію, яка вже доступна.

### 3.5. Зрозумілий зворотний зв'язок

Після натискання кнопки користувач повинен розуміти, що сталося.

Наприклад:

- кнопка показує стан завантаження;
- товар додається в кошик;
- форма повідомляє про успішне надсилання;
- поле пояснює помилку;
- після видалення показується відповідне повідомлення.

## 4. Viewport — область перегляду

**Viewport** — видима область вебсторінки у вікні браузера.

На мобільних пристроях ширина viewport може бути значно меншою, ніж ширина сторінки, тому потрібно правильно налаштувати масштабування.

### Meta viewport

У HTML-документі зазвичай використовують:

    <meta
      name="viewport"
      content="width=device-width, initial-scale=1"
    />

Цей тег допомагає браузеру використовувати ширину пристрою як ширину viewport.

Не слід без потреби забороняти масштабування користувачем через `user-scalable=no` або обмеження `maximum-scale`. Такі обмеження можуть погіршувати доступність.

### Адаптивна ширина

Не прив'язуй основний контент до фіксованої ширини, яка може перевищувати екран.

    .page-container {
      width: min(100% - 2rem, 70rem);
      margin-inline: auto;
    }

У цьому прикладі:

- `100% - 2rem` залишає простір по краях;
- `70rem` обмежує максимальну ширину;
- `margin-inline: auto` центрує контейнер.

### Не допускай випадкового горизонтального прокручування

    * {
      box-sizing: border-box;
    }

    img,
    video {
      display: block;
      max-width: 100%;
    }

    body {
      margin: 0;
    }

Не приховуй горизонтальне прокручування через `overflow-x: hidden` як універсальне виправлення. Спочатку знайди елемент, який виходить за межі viewport.

## 5. Responsive design

**Responsive design (адаптивний дизайн)** — підхід, за якого макет автоматично пристосовується до доступної ширини екрана.

Адаптувати потрібно не тільки ширину блоків, а й структуру, порядок контенту та спосіб взаємодії.

### Що може змінюватися

- кількість колонок;
- розташування навігації;
- розмір заголовків;
- відступи;
- розташування кнопок;
- спосіб показу таблиць;
- видимість другорядних елементів;
- розміщення панелей фільтрів;
- порядок блоків.

### Приклад адаптивного макета

    .page-layout {
      display: grid;
      grid-template-columns: 1fr;
      gap: 1.5rem;
    }

    @media (min-width: 800px) {
      .page-layout {
        grid-template-columns: 16rem minmax(0, 1fr);
      }
    }

На вузькому екрані блоки розташовані один під одним. На широкому — меню розміщується поруч з основним контентом.

### Breakpoints

**Breakpoint** — точка, у якій стилі змінюються відповідно до доступного простору.

Приклад:

    /* Мобільний макет — базові стилі */

    .navigation {
      display: flex;
      flex-direction: column;
    }

    /* Ширший екран */

    @media (min-width: 768px) {
      .navigation {
        flex-direction: row;
      }
    }

Число `768px` тут є прикладом, а не обов'язковим стандартом.

**Правило:** додавай breakpoint тоді, коли макет перестає бути зручним, а не лише тому, що певний пристрій має популярну ширину.

## 6. Сенсорні елементи керування

На смартфоні користувач натискає елементи пальцем, а не точним курсором миші.

Тому кнопки, посилання, перемикачі та інші інтерактивні елементи повинні мати достатню площу для натискання.

### Розмір touch target

**Touch target** — область, у межах якої користувач може активувати інтерактивний елемент.

Практичний орієнтир — приблизно `44 × 44 CSS px` для важливих сенсорних елементів. WCAG 2.2, критерій 2.5.8, встановлює мінімум `24 × 24 CSS px` за визначених умов і передбачає винятки. Критерій 2.5.5 рівня AAA використовує `44 × 44 CSS px`.

Не варто плутати видимий розмір і фактичну область натискання.

### Приклад кнопки

    .icon-button {
      display: inline-grid;
      place-items: center;
      min-width: 44px;
      min-height: 44px;
      padding: 0.5rem;
      border: 0;
      border-radius: 0.5rem;
      cursor: pointer;
    }

### Відстань між елементами

Не розташовуй маленькі кнопки надто близько одна до одної.

Особливо це стосується:

- кнопок видалення;
- кнопок підтвердження та скасування;
- елементів керування кількістю;
- посилань у списках;
- перемикачів;
- кнопок у нижній навігації.

Для небезпечних дій, наприклад видалення, потрібно також передбачати зрозумілий контекст і захист від випадкових натискань.

## 7. Mobile navigation — мобільна навігація

На вузькому екрані повне горизонтальне меню часто займає надто багато місця. Тому навігацію адаптують відповідно до кількості розділів і частоти їх використання.

### 7.1. Bottom navigation

**Bottom navigation** — панель основних розділів унизу екрана.

Підходить для застосунків, у яких користувач регулярно переходить між кількома головними розділами.

Наприклад:

- Головна;
- Пошук;
- Обране;
- Профіль.

Переваги:

- основні розділи легко знайти;
- елементи зручно натискати великим пальцем;
- поточний розділ можна чітко виділити.

Недоліки:

- займає вертикальний простір;
- не підходить для великої кількості пунктів;
- може перекривати контент, якщо неправильно врахувати нижній відступ.

### 7.2. Hamburger menu

**Hamburger menu** — кнопка, яка відкриває приховане меню.

Підходить для другорядних розділів або великої кількості пунктів навігації.

Переваги:

- економить місце;
- дозволяє організувати багато розділів.

Недоліки:

- користувач не бачить усіх пунктів одразу;
- потрібна додаткова дія для переходу;
- може приховувати важливі можливості.

Не ховай основні дії за hamburger menu лише заради компактності, якщо вони повинні бути постійно доступними.

### 7.3. Tab navigation

**Tabs** — перемикачі між пов'язаними розділами одного рівня.

Приклад:

- Опис;
- Характеристики;
- Відгуки.

На мобільному екрані вкладки можуть:

- переноситися на наступний рядок;
- прокручуватися горизонтально;
- замінюватися іншим компонентом, якщо структура стає незручною.

Активну вкладку потрібно візуально відрізняти від неактивних.

### 7.4. Navigation drawer

**Navigation drawer** — бокова панель навігації, яка відкривається поверх контенту або поруч із ним.

Для мобільного інтерфейсу важливо:

- забезпечити зрозуміле відкривання та закривання;
- не перекривати панеллю критичні повідомлення;
- підтримувати клавіатурну навігацію;
- за потреби керувати фокусом;
- повертати фокус до кнопки відкриття після закриття.

### Приклад HTML

    <nav aria-label="Основна навігація">
      <ul>
        <li>
          <a href="/" aria-current="page">Головна</a>
        </li>
        <li>
          <a href="/courses">Курси</a>
        </li>
        <li>
          <a href="/profile">Профіль</a>
        </li>
      </ul>
    </nav>

`aria-current="page"` позначає поточну сторінку для допоміжних технологій.

## 8. Навігація великим пальцем

На смартфоні користувач часто керує інтерфейсом однією рукою.

Тому розташування основних дій має значення.

### Практичні правила

- Розміщуй часті дії в легкодоступних місцях.
- Не став важливі кнопки впритул до країв екрана.
- Ураховуй положення системних панелей.
- Не розміщуй єдину кнопку продовження далеко від основного контенту.
- Не змушуй користувача постійно переміщати руку через увесь екран.

Ці принципи не означають, що кожна кнопка повинна бути внизу. Розташування залежить від контексту та звичок користувача.

## 9. Sticky elements — закріплені елементи

**Sticky element** — елемент, який залишається видимим під час прокручування в межах визначеної області.

На мобільному пристрої це може бути:

- верхня панель;
- кнопка оформлення замовлення;
- панель основних дій;
- навігація;
- заголовок секції.

### Приклад

    .sticky-action {
      position: sticky;
      bottom: 1rem;
      margin: 1rem;
      z-index: 10;
    }

### Коли використовувати

Sticky-елементи корисні, коли важлива дія повинна залишатися доступною під час перегляду довгого контенту.

Наприклад, на сторінці товару може бути доречно закріпити кнопку «Додати в кошик».

### Типові проблеми

- елемент перекриває текст;
- закриває поля форми;
- займає надто багато місця;
- конфліктує з клавіатурою;
- перекриває системні панелі;
- постійно відволікає користувача.

Перевіряй sticky-елементи на різних висотах екрана, під час прокручування та при відкритій клавіатурі.

## 10. Safe areas — безпечні області екрана

На деяких смартфонах частину екрана займають вирізи, індикатори системи або інші області, які потрібно враховувати при розміщенні контенту.

CSS надає змінні середовища `env(safe-area-inset-*)`.

### Приклад

    .mobile-footer {
      padding: 1rem;
      padding-bottom: calc(
        1rem + env(safe-area-inset-bottom, 0px)
      );
    }

Це допомагає уникнути розміщення кнопок надто близько до нижнього краю на підтримуваних пристроях.

Не додавай safe-area-відступи бездумно до всіх елементів. Вони потрібні там, де компоненти справді наближаються до відповідних країв екрана.

## 11. Mobile typography — типографіка мобільного інтерфейсу

Текст повинен залишатися читабельним без збільшення масштабу сторінки.

### Основні правила

- Використовуй достатній розмір основного тексту.
- Забезпечуй помітний контраст між текстом і фоном.
- Не роби довгі абзаци надто широкими.
- Розділяй інформацію на зрозумілі блоки.
- Використовуй короткі заголовки.
- Не передавай важливу інформацію лише кольором.
- Не зменшуй текст заради розміщення більшої кількості контенту.

Для багатьох мобільних інтерфейсів `16px` є практичною відправною точкою для основного тексту, але остаточний розмір залежить від шрифту, контексту та потреб користувачів.

### Приклад

    body {
      font-family: system-ui, sans-serif;
      font-size: 1rem;
      line-height: 1.5;
    }

    h1 {
      font-size: clamp(1.75rem, 5vw, 2.5rem);
      line-height: 1.2;
    }

    p {
      max-width: 65ch;
    }

`clamp()` дозволяє встановити мінімальний, гнучкий і максимальний розмір.

Одиниця `ch` допомагає обмежувати ширину текстового рядка приблизно за шириною символу.

## 12. Mobile forms — мобільні форми

Форми особливо важливі для мобільного UX, оскільки введення тексту на смартфоні потребує більше зусиль.

### Основні правила

- Використовуй одноколонкове розташування полів.
- Розміщуй підпис біля відповідного поля.
- Не використовуй placeholder як єдину назву поля.
- Позначай обов'язкові поля.
- Показуй помилки поруч із відповідними полями.
- Не очищай усю форму після помилки.
- Використовуй відповідний тип клавіатури.
- Не вимагай зайвих даних.
- Дозволяй вставляти скопійований текст, якщо це доречно.

### Правильні типи input

    <form>
      <div class="form-field">
        <label for="email">Електронна пошта</label>
        <input
          id="email"
          name="email"
          type="email"
          autocomplete="email"
          required
        />
      </div>

      <div class="form-field">
        <label for="phone">Номер телефону</label>
        <input
          id="phone"
          name="phone"
          type="tel"
          autocomplete="tel"
        />
      </div>

      <div class="form-field">
        <label for="birth-date">Дата народження</label>
        <input
          id="birth-date"
          name="birthDate"
          type="date"
        />
      </div>

      <button type="submit">Надіслати</button>
    </form>

### Атрибути, які варто знати

| Атрибут | Призначення |
|---|---|
| `type="email"` | Поле для електронної пошти |
| `type="tel"` | Поле для номера телефону |
| `type="number"` | Поле для числових значень |
| `type="date"` | Поле для вибору дати |
| `autocomplete` | Підказка браузеру щодо автозаповнення |
| `inputmode` | Підказка щодо типу екранної клавіатури |
| `required` | Позначає обов'язкове поле |
| `minlength` | Мінімальна довжина введення |
| `maxlength` | Максимальна довжина введення |

`type="number"` не підходить для всіх числових на вигляд даних. Наприклад, телефонні номери та поштові індекси зазвичай не є величинами для математичних операцій.

### Валідація

Валідація повинна пояснювати, що саме потрібно виправити.

    <label for="email">Електронна пошта</label>

    <input
      id="email"
      name="email"
      type="email"
      aria-describedby="email-error"
      aria-invalid="true"
    />

    <p id="email-error">
      Введіть адресу електронної пошти у правильному форматі.
    </p>

`aria-describedby` пов'язує поле з текстом помилки, а `aria-invalid` повідомляє про некоректний стан.

Для успішної відправки форми недостатньо лише клієнтської перевірки — сервер також повинен перевіряти отримані дані.

## 13. Mobile buttons — кнопки

Кнопки повинні чітко показувати, яку дію виконає користувач.

### Основні види

- **Primary button** — головна дія.
- **Secondary button** — додаткова дія.
- **Tertiary button** — менш акцентована дія.
- **Icon button** — кнопка з іконкою.
- **Destructive button** — небезпечна дія, наприклад видалення.
- **Floating action button** — плаваюча кнопка основної дії.

### Приклад CSS

    .button {
      display: inline-flex;
      align-items: center;
      justify-content: center;
      min-height: 44px;
      padding: 0.75rem 1rem;
      border: 0;
      border-radius: 0.625rem;
      font: inherit;
      cursor: pointer;
    }

    .button-primary {
      color: white;
      background: #2457d6;
    }

    .button-secondary {
      color: #2457d6;
      background: #eef2ff;
    }

    .button:disabled {
      cursor: not-allowed;
      opacity: 0.6;
    }

### Правила для мобільних кнопок

- Використовуй зрозумілі дієслова: «Зберегти», «Продовжити», «Надіслати».
- Не розташовуй дві небезпечні дії поруч без чіткого розрізнення.
- Показуй стан завантаження під час тривалих операцій.
- Запобігай повторній відправці форми.
- Не використовуй лише іконку, якщо її значення неоднозначне.
- Перевіряй вигляд кнопки при збільшеному масштабі тексту.

## 14. Жести та touch interactions

На мобільних пристроях поширені такі жести:

| Жест | Приклад використання |
|---|---|
| Tap | Натискання кнопки |
| Double tap | Подвійне натискання, якщо потрібне в конкретному контексті |
| Long press | Відкриття контекстних дій |
| Swipe | Переміщення між елементами |
| Drag | Перетягування об'єкта |
| Pinch | Масштабування зображення або карти |
| Scroll | Прокручування контенту |

### Принципи використання жестів

- Основні дії мають бути очевидними.
- Не роби важливу функцію доступною лише через жест.
- Не конфліктуй із системними жестами браузера та пристрою.
- Забезпечуй альтернативний спосіб керування.
- Не запускай небезпечну дію лише через випадкове торкання.
- Перевіряй поведінку на реальних пристроях.

Наприклад, картку можна видалити свайпом, але варто також надати видиму кнопку видалення або інший доступний спосіб виконати цю дію.

### Touch і hover

Мобільні пристрої часто не мають постійного стану наведення курсора.

Тому не можна покладатися виключно на `:hover`.

    .button {
      background: #2457d6;
      color: white;
    }

    @media (hover: hover) and (pointer: fine) {
      .button:hover {
        background: #1944ad;
      }
    }

Hover-ефекти можуть покращувати взаємодію з мишею, але основний функціонал повинен працювати без них.

## 15. Mobile cards — картки

- Уніфікуй розміри зображень.
- Не обрізай важливу інформацію.
- Не роби всю картку клікабельною, якщо всередині є кілька незалежних інтерактивних елементів без продуманого керування.

## 16. Mobile tables — таблиці

Таблиці з великою кількістю колонок важко читати на вузькому екрані.

Можливі рішення:

1. Дозволити горизонтальне прокручування таблиці.
2. Приховати другорядні колонки, якщо інформація доступна іншим способом.
3. Перетворити рядки на картки.
4. Показувати деталі окремою сторінкою.
5. Дозволити користувачу вибирати потрібні колонки.

    .table-wrapper {

    .data-table {
      width: 100%;
      min-width: 36rem;

### Важливо

- Не стискай текст до нечитабельного розміру.
- Зберігай зрозумілі заголовки колонок.
- Не приховуй важливі дані без альтернативного способу доступу.
- Переконайся, що прокручування таблиці не блокує прокручування сторінки.
- Якщо таблиця має багато даних, подумай про пошук, фільтри та деталізацію.

## 17. Mobile search and filters — пошук і фільтри

Пошук допомагає швидко знаходити інформацію, а фільтри — звужувати результати.

На мобільному екрані фільтри часто розміщують у висувній панелі або окремому діалозі.

### Практичні правила

- Розміщуй пошук у передбачуваному місці.
- Показуй активні фільтри.
- Дозволяй скидати фільтри.
- Показуй кількість результатів, якщо це корисно.
- Не втрачай уже введені значення після закриття панелі.
- Не змушуй користувача повторно відкривати фільтри для кожної зміни, якщо це можна спростити.

### Приклад інтерфейсу

    <form role="search" action="/search">
      <label for="site-search">Пошук курсів</label>

      <input
        id="site-search"
        name="q"
        type="search"
        placeholder="Назва курсу"
      />

      <button type="submit">Знайти</button>
    </form>

Placeholder тут є додатковою підказкою, а не заміною підпису поля.

## 18. Loading, empty та error states

Мобільний інтерфейс повинен пояснювати, що відбувається, навіть якщо дані завантажуються повільно або виникає помилка.

### Loading state

Показує, що система виконує операцію.

Приклади:

- індикатор завантаження;
- skeleton placeholders;
- текст «Завантаження курсів…»;
- кнопка з індикатором виконання.

Не показуй індикатор без потреби для кожної миттєвої операції.

### Empty state

Показує, що даних немає.

Приклад:

    <section aria-labelledby="empty-title">
      <h2 id="empty-title">Поки немає збережених курсів</h2>
      <p>Додай курс до обраного, щоб знайти його тут.</p>
      <a href="/courses">Переглянути курси</a>
    </section>

Хороший empty state пояснює ситуацію та пропонує наступну дію.

### Error state

Пояснює, що операція не вдалася.

Приклад:

    <div role="alert">
      Не вдалося завантажити дані.
      Перевір з'єднання та спробуй ще раз.
    </div>

Помилка повинна бути зрозумілою, але не повинна розкривати внутрішні технічні деталі чи конфіденційні дані.

## 19. Mobile dialogs and bottom sheets

**Dialog** — діалогове вікно, яке привертає увагу до певної дії або інформації.

**Bottom sheet** — панель, яка з'являється з нижнього краю екрана.

На мобільних пристроях bottom sheet часто використовують для:

- вибору фільтрів;
- налаштування параметрів;
- вибору сортування;
- коротких форм;
- контекстних дій.

### Коли вибирати bottom sheet

Він доречний, коли користувачу потрібно виконати невелику дію, залишаючись у поточному контексті.

Не варто використовувати його для будь-якої складної форми лише тому, що це популярний мобільний патерн.

### Важливі правила

- Передбачай зрозумілий спосіб закрити панель.
- Не закривай її випадково під час введення важливих даних.
- Забезпечуй достатню висоту для вмісту.
- Враховуй екранну клавіатуру.
- Для модального діалогу правильно керуй фокусом.
- Не дозволяй фокусу переходити до прихованого фонового контенту, поки діалог модальний.

## 20. Mobile images and media — зображення та медіа

Зображення повинні добре виглядати на різних екранах і не створювати зайвого навантаження.

### Основні правила

- Використовуй адаптивні розміри.
- Вибирай відповідне співвідношення сторін.
- Оптимізуй розмір файлів.
- Не завантажуй великі зображення без потреби.
- Додавай змістовний альтернативний текст для інформативних зображень.
- Для декоративних зображень використовуй порожній `alt=""`.
- Не передавай важливу інформацію лише через зображення.

### CSS

    .responsive-image {
      display: block;
      width: 100%;
      height: auto;
    }

Для карток із фіксованим співвідношенням сторін:

    .product-image {
      width: 100%;
      aspect-ratio: 4 / 3;
      object-fit: cover;
    }

`object-fit: cover` заповнює контейнер, але може обрізати частину зображення. Перевіряй, чи не втрачається важлива інформація.

## 21. Mobile performance — продуктивність

Мобільний інтерфейс повинен залишатися зручним навіть за повільного з'єднання або на пристроях із невисокою продуктивністю.

### Що оптимізувати

- розмір JavaScript;
- розмір зображень;
- кількість мережевих запитів;
- непотрібні анімації;
- надмірні перерендерення;
- блокування основного потоку;
- завантаження контенту поза видимою областю;
- обсяг даних, які передаються на пристрій.

### Lazy loading для зображень

    <img
      src="/images/course.jpg"
      alt="Навчальний курс"
      loading="lazy"
      width="640"
      height="420"
    />

`loading="lazy"` доречний для зображень, які не потрібні одразу під час першого відображення сторінки.

Не варто бездумно використовувати lazy loading для головного зображення, яке користувач повинен побачити відразу.

Атрибути `width` і `height` допомагають браузеру зарезервувати місце під зображення та зменшити несподівані зміщення макета.

### Основні показники Core Web Vitals

- **LCP** — швидкість відображення основного контенту.
- **INP** — швидкість реакції сторінки на взаємодії.
- **CLS** — стабільність макета під час завантаження.

Для хорошого користувацького досвіду орієнтуйся на рекомендовані порогові значення Core Web Vitals та перевіряй реальні польові дані.

## 22. Accessibility — доступність мобільного інтерфейсу

Мобільний інтерфейс повинен бути зручним для людей із різними можливостями та способами взаємодії.

### Основні правила

- Використовуй семантичний HTML.
- Забезпечуй достатній контраст.
- Не передавай інформацію лише кольором.
- Підтримуй керування клавіатурою.
- Забезпечуй видимий фокус.
- Додавай підписи до полів.
- Використовуй зрозумілі назви кнопок.
- Перевіряй інтерфейс зі screen reader.
- Не блокуй масштабування тексту.
- Дотримуйся вимог до розмірів інтерактивних елементів.
- Враховуй налаштування зменшення анімації.

### Зменшення анімації

    @media (prefers-reduced-motion: reduce) {
      *,
      *::before,
      *::after {
        scroll-behavior: auto;
        animation-duration: 0.01ms !important;
        animation-iteration-count: 1 !important;
        transition-duration: 0.01ms !important;
      }
    }

Це приклад загального підходу. У реальному проєкті краще вибірково вимикати непотрібні анімації, щоб не порушувати функціональність компонентів.

### Керування з клавіатури

Не створюй інтерактивні елементи лише на основі `div` або `span`, якщо можна використати семантичний елемент.

Для переходу на іншу сторінку використовуй посилання, для виконання дії — кнопку.

## 23. Orientation — орієнтація екрана

Мобільний інтерфейс може відображатися у вертикальній або горизонтальній орієнтації.

Не слід без потреби блокувати одну з орієнтацій.

Перевіряй:

- чи поміщаються основні кнопки;
- чи не обрізається контент;
- чи доступні поля форми;
- чи не перекриваються панелі;
- чи залишається навігація зрозумілою;
- чи працюють медіа та таблиці.

### Приклад CSS

    @media (orientation: landscape) and (max-height: 500px) {
      .hero {
        padding-block: 1rem;
      }
    }

Цей запит реагує на горизонтальну орієнтацію та невелику висоту viewport.

Він може бути корисним для компактнішого розташування великих верхніх блоків, але не замінює перевірку реального макета.

## 24. Native app patterns і mobile web

Мобільний вебсайт і нативний застосунок мають різні можливості, хоча багато принципів UI/UX у них спільні.

| Mobile web | Native app |
|---|---|
| Працює в браузері | Працює як встановлений застосунок |
| Використовує HTML, CSS, JavaScript | Використовує платформи та інструменти ОС |
| Навігація залежить від браузера та сайту | Може використовувати системну навігацію |
| Оновлюється через веброзгортання | Оновлюється через відповідний механізм поширення застосунку |
| Доступ до функцій пристрою залежить від API та дозволів | Може мати ширший доступ до системних можливостей |

### Що можна запозичити з нативного дизайну

- зрозумілі сенсорні елементи;
- чіткі стани компонентів;
- послідовну навігацію;
- природні для платформи патерни;
- правильну роботу з системними областями;
- короткий і зрозумілий зворотний зв'язок.

Не потрібно бездумно копіювати всі нативні патерни у вебінтерфейс. Важливо зважати на середовище, в якому працює користувач.

## 25. Mobile dashboard — мобільна панель керування

Dashboard на смартфоні повинен показувати найважливіші показники без надмірної кількості дрібних блоків.

### Практичні принципи

- Розташовуй ключові показники першими.
- Використовуй вертикальний список або компактну сітку.
- Не змушуй користувача читати складні таблиці на маленькому екрані.
- Винось другорядні фільтри в окрему панель.
- Забезпечуй зрозуміле відкриття деталей.
- Не перевантажуй графіки підписами.
- Показуй дату та одиниці вимірювання для показників.

### Приклад адаптивної сітки

    .stats-grid {
      display: grid;
      grid-template-columns: 1fr;
      gap: 1rem;
    }

    @media (min-width: 480px) {
      .stats-grid {
        grid-template-columns: repeat(2, minmax(0, 1fr));
      }
    }

    @media (min-width: 900px) {
      .stats-grid {
        grid-template-columns: repeat(4, minmax(0, 1fr));
      }
    }

Не намагайся вмістити всі елементи desktop-dashboard на один мобільний екран. Визнач, які дані потрібні найчастіше.

## 26. CSS units для мобільного дизайну

Різні CSS-одиниці розв'язують різні завдання.

| Одиниця | Використання |
|---|---|
| `px` | Точні розміри, межі, деталі інтерфейсу |
| `rem` | Шрифти, відступи, розміри відносно кореневого шрифту |
| `%` | Розміри відносно контейнера |
| `vw` | Розмір відносно ширини viewport |
| `vh` | Розмір відносно висоти viewport |
| `dvh` | Динамічна висота viewport |
| `clamp()` | Гнучкі значення з мінімумом і максимумом |
| `min()` | Найменше з кількох значень |
| `max()` | Найбільше з кількох значень |

### Гнучкий розмір заголовка

    .page-title {
      font-size: clamp(1.75rem, 4vw, 2.75rem);
    }

### Висота мобільного блоку

    .full-screen-section {
      min-height: 100vh;
      min-height: 100dvh;
    }

`100dvh` враховує динамічні зміни видимої області браузера в підтримуваних браузерах. Резервне значення `100vh` може бути корисним для сумісності.

Не використовуй `100vw` без потреби для блоків, які вже мають ширину `100%`: залежно від браузера це може спричинити горизонтальне прокручування.

## 28. Типові помилки в мобільному UI

### Помилка 1. Просто зменшити desktop-макет

Велика кількість колонок і дрібних елементів погано переноситься на смартфон.

**Рішення:** адаптуй структуру, пріоритети та взаємодію, а не тільки розміри.

### Помилка 2. Надто дрібні кнопки

Користувачу важко натиснути потрібний елемент без помилки.

**Рішення:** збільшуй фактичну область натискання та додавай відстань між елементами.

### Помилка 3. Використовувати hover як основний стан

На сенсорному екрані немає звичайного постійного наведення курсора.

**Рішення:** забезпечуй доступність основних дій через натискання.

### Помилка 4. Приховувати важливі функції в меню

Користувач може не помітити потрібну дію.

**Рішення:** залишай найважливіші дії видимими, а другорядні групуй у меню.

### Помилка 5. Використовувати placeholder замість label

Після введення тексту підказка зникає, і призначення поля може стати незрозумілим.

**Рішення:** додавай постійний видимий підпис.

### Помилка 6. Перевантажувати екран

Надмірна кількість карток, кнопок і панелей ускладнює пошук потрібної інформації.

**Рішення:** визначай пріоритети та показуй другорядний контент у відповідному контексті.

### Помилка 7. Ігнорувати екранну клавіатуру

Клавіатура може перекрити поле, повідомлення про помилку або кнопку надсилання.

**Рішення:** перевіряй форму на реальному пристрої з відкритою клавіатурою.

### Помилка 8. Приховувати горизонтальне переповнення замість виправлення

Контент може стати недоступним, якщо обрізати його без альтернативи.

**Рішення:** знайди причину переповнення та адаптуй відповідний компонент.

### Помилка 9. Робити всі дії однаково помітними

Користувачу важко визначити, що робити далі.

**Рішення:** створюй чітку візуальну ієрархію.

### Помилка 10. Перевіряти лише в емуляторі

Реальна поведінка може відрізнятися через клавіатуру, браузер, системні панелі та сенсорне керування.

**Рішення:** поєднуй емуляцію, DevTools і тестування на фізичних пристроях.

## 29. Чекліст перевірки мобільного інтерфейсу

### Макет

- [ ] Сторінка адаптується до вузьких екранів.
- [ ] Немає випадкового горизонтального прокручування.
- [ ] Контент не обрізається.
- [ ] Відступи залишаються послідовними.
- [ ] Перевірена вертикальна та горизонтальна орієнтація.
- [ ] Збільшення тексту не руйнує макет.

### Навігація

- [ ] Основні розділи легко знайти.
- [ ] Активний розділ чітко позначений.
- [ ] Меню легко відкрити й закрити.
- [ ] Усі основні дії доступні без складних жестів.
- [ ] Панелі не перекривають критичний контент.

### Сенсорна взаємодія

- [ ] Кнопки мають достатню область натискання.
- [ ] Між сусідніми елементами достатньо простору.
- [ ] Немає залежності від hover.
- [ ] Небезпечні дії захищені від випадкового запуску.
- [ ] Видно результат виконання дії.

### Форми

- [ ] У кожного поля є зрозумілий підпис.
- [ ] Використані відповідні типи введення.
- [ ] Помилки пояснюють, що потрібно виправити.
- [ ] Значення не губляться після помилки.
- [ ] Кнопка надсилання доступна при відкритій клавіатурі.
- [ ] Форма перевіряється і на клієнті, і на сервері.

### Доступність

- [ ] Контраст тексту достатній.
- [ ] Є видимий фокус.
- [ ] Інтерфейс доступний з клавіатури.
- [ ] Поля та кнопки мають зрозумілі назви.
- [ ] Важлива інформація не передається лише кольором.
- [ ] Анімації враховують `prefers-reduced-motion`.
- [ ] Масштабування сторінки не заблоковане без потреби.

### Продуктивність

- [ ] Зображення оптимізовані.
- [ ] Великі ресурси не завантажуються без потреби.
- [ ] Контент не зміщується несподівано під час завантаження.
- [ ] Кнопки швидко реагують на взаємодію.
- [ ] Перевірена поведінка за повільного з'єднання.

## 30. Що потрібно запам'ятати

✔ Mobile interface — це не просто зменшена desktop-версія.

✔ Mobile-first допомагає спочатку визначити найважливіший контент і функціональність.

✔ Responsive design адаптує макет до доступного простору.

✔ Breakpoints потрібно вибирати відповідно до поведінки макета.

✔ Сенсорні елементи повинні мати достатню площу для натискання.

✔ Навігація має залишатися зрозумілою та доступною.

✔ Hover не повинен бути єдиним способом взаємодії.

✔ Форми на мобільному екрані мають мінімізувати зайве введення.

✔ Sticky-панелі повинні враховувати клавіатуру, контент і системні області.

✔ Таблиці та складні панелі потрібно адаптувати, а не просто стискати.

✔ Доступність охоплює контраст, клавіатуру, screen reader, фокус і масштабування.

✔ Продуктивність особливо важлива на пристроях із повільним з'єднанням.

✔ Реальний мобільний пристрій залишається важливим середовищем для тестування.

## 31. Рівні володіння Mobile Interface

### Core — основа

- Розуміти mobile-first і responsive design.
- Використовувати media queries.
- Створювати адаптивні сітки.
- Правильно налаштовувати viewport.
- Забезпечувати читабельність тексту.
- Створювати зручні кнопки та поля форм.

### Junior — практичне застосування

- Адаптувати desktop-макет до смартфона.
- Проєктувати мобільну навігацію.
- Працювати зі станами loading, empty та error.
- Адаптувати картки, таблиці та фільтри.
- Ураховувати touch targets і safe areas.
- Перевіряти доступність та клавіатурну навігацію.

### Middle — системний підхід

- Визначати мобільні сценарії користувача.
- Обґрунтовувати вибір навігаційного патерна.
- Оптимізувати продуктивність.
- Проєктувати складні адаптивні компоненти.
- Перевіряти реальні проблеми UX на пристроях.
- Враховувати збільшений текст, альтернативні способи введення та різні умови використання.

### Senior — проєктування досвіду

- Визначати стратегію mobile-first для продукту.
- Пріоритезувати сценарії та функції.
- Узгоджувати мобільні патерни з дизайн-системою.
- Балансувати зручність, доступність і продуктивність.
- Використовувати дослідження та аналітику для перевірки рішень.
- Визначати системні проблеми мобільного UX і планувати їх усунення.

## Висновок

**Mobile Interface** — це проєктування інтерфейсу з урахуванням маленького екрана, сенсорного керування, обмеженого простору та реальних умов використання.

Головне завдання UI-дизайнера — не вмістити на смартфоні все, що є на комп'ютері, а зробити найважливіші дії зрозумілими, доступними та зручними.

Практична формула:

    Mobile Interface =
      пріоритет контенту
      + адаптивний макет
      + зручне сенсорне керування
      + зрозуміла навігація
      + доступність
      + продуктивність
      + тестування на пристроях
