# SaaS UI — Інтерфейси SaaS-застосунків

> **SaaS UI (Software as a Service UI)** — це проєктування інтерфейсів вебзастосунків, які надають користувачам доступ до програмних сервісів через інтернет. Типові приклади: CRM-системи, таск-менеджери, освітні платформи, сервіси керування проєктами, фінансові панелі, системи аналітики та інструменти для командної роботи.

Мета SaaS UI — допомогти користувачу швидко виконувати робочі завдання, керувати даними, розуміти стан системи, налаштовувати свій робочий простір і отримувати користь від продукту без зайвої складності.

SaaS-інтерфейс має бути не лише привабливим, а й зрозумілим, передбачуваним, ефективним і масштабованим.

---

## 1. Що таке SaaS UI

SaaS-продукт зазвичай працює у браузері та надає функціональність через інтернет.

Приклади SaaS-продуктів:

- CRM — керування клієнтами та продажами.
- Project Management — керування проєктами й завданнями.
- LMS — навчання, курси, уроки та прогрес студентів.
- Analytics Dashboard — перегляд показників і звітів.
- Accounting Software — фінанси, рахунки та платежі.
- Team Collaboration — спільна робота команди.
- HR Management — працівники, відпустки та кадрові процеси.
- Email Marketing — створення кампаній і керування підписниками.

### Особливості SaaS-інтерфейсу

✔ Користувачі регулярно повертаються до продукту.

✔ Інтерфейс часто містить багато даних.

✔ Функції можуть відрізнятися залежно від ролі користувача.

✔ Дані потрібно створювати, редагувати, фільтрувати та видаляти.

✔ Продукт може мати безкоштовний і платні тарифні плани.

✔ Користувачам потрібні налаштування, профілі та керування командою.

✔ Інтерфейс повинен підтримувати різні стани: завантаження, помилки, порожні списки та успішні операції.

✔ Продукт може поступово розширюватися, тому інтерфейс має бути масштабованим.

## 2. Основні складові SaaS-продукту

Типовий SaaS-застосунок можна умовно розділити на кілька функціональних зон.

### 2.1. Marketing Website

Публічна частина сайту, яка пояснює цінність продукту та допомагає користувачу почати роботу.

Зазвичай містить:

- Landing Page.
- Опис можливостей.
- Pricing Page.
- FAQ.
- Відгуки клієнтів.
- Документацію.
- Кнопки Sign Up, Log In, Get Started.

### 2.2. Authentication

Частина, яка відповідає за вхід користувача.

Типові екрани:

- Sign Up — реєстрація.
- Log In — вхід.
- Forgot Password — відновлення пароля.
- Reset Password — встановлення нового пароля.
- Email Verification — підтвердження електронної пошти.
- Two-Factor Authentication — додаткова перевірка входу.

### 2.3. Application Dashboard

Основний робочий простір після входу.

Може містити:

- Sidebar Navigation.
- Top Navigation Bar.
- Dashboard.
- Data Tables.
- Charts.
- Forms.
- Notifications.
- Search.
- User Menu.
- Settings.

### 2.4. Account and Workspace Settings

Налаштування облікового запису та робочого простору.

Наприклад:

- Profile.
- Account.
- Workspace.
- Team Members.
- Roles and Permissions.
- Billing.
- Integrations.
- Notifications.
- Security.

### 2.5. Billing and Subscription

Частина, яка відповідає за оплату сервісу.

Може містити:

- Поточний тариф.
- Порівняння планів.
- Історію платежів.
- Платіжний метод.
- Зміну тарифу.
- Скасування підписки.
- Ліміти використання.

## 3. Типова структура SaaS Dashboard

Dashboard — це робочий простір, у якому користувач отримує доступ до основних функцій продукту.

Приклад структури:

    SaaS Application
    ├── Sidebar
    │   ├── Logo
    │   ├── Dashboard
    │   ├── Projects
    │   ├── Tasks
    │   ├── Reports
    │   ├── Team
    │   └── Settings
    │
    ├── Topbar
    │   ├── Breadcrumbs
    │   ├── Search
    │   ├── Notifications
    │   └── User Menu
    │
    └── Main Content
        ├── Page Header
        ├── Page Description
        ├── Primary Actions
        ├── Filters
        ├── Data or Widgets
        └── Pagination

### Основний принцип

Користувач повинен розуміти:

1. Де він перебуває.
2. Які дані бачить.
3. Які дії може виконати.
4. Що відбувається після його дії.
5. Як повернутися до попереднього контексту.

## 4. Sidebar Navigation

Sidebar — бічна навігаційна панель, яка надає доступ до основних розділів застосунку.

<Приклад>

    ┌──────────────────────┐
    │ LOGO                 │
    │                      │
    │  ◉ Dashboard         │
    │  □ Projects          │
    │  ✓ Tasks             │
    │  ▤ Reports           │
    │  👥 Team             │
    │                      │
    │  ⚙ Settings          │
    │  ? Help              │
    └──────────────────────┘

### Призначення Sidebar

- Забезпечити швидку навігацію.
- Показати структуру продукту.
- Відобразити активний розділ.
- Зменшити кількість переходів між екранами.
- Надати доступ до другорядних розділів.

### Best practices

✔ Групуй пов'язані розділи.

✔ Розташовуй найважливіші пункти ближче до початку.

✔ Чітко показуй активний пункт.

✔ Використовуй зрозумілі назви.

✔ Не додавай багато рівнів вкладеності без потреби.

✔ Розміщуй рідко використовувані пункти в нижній частині або в меню налаштувань.

✔ Дозволяй згортати Sidebar, якщо робочій області потрібен додатковий простір.

### Активний пункт

Користувач повинен відразу розуміти, який розділ відкрито.

    Dashboard
    Projects  ← активний розділ
    Tasks
    Reports

Активний стан можна позначити фоном, кольором тексту, індикатором або комбінацією цих засобів.

Не покладайся лише на зміну кольору, якщо це погіршує доступність.

### Collapsible Sidebar

Collapsible Sidebar — панель, яку можна згорнути до вузької смуги з іконками.

Переваги:

- Більше простору для таблиць і графіків.
- Менше візуального шуму.
- Зручність на невеликих екранах.

Недоліки:

- Іконки без підписів можуть бути незрозумілими.
- Користувачеві складніше запам'ятовувати розташування пунктів.

Якщо підписи приховано, передбач підказки та доступні назви для допоміжних технологій.

## 5. Topbar — верхня панель

Topbar містить глобальні елементи керування застосунком.

Типовий склад:

    ┌─────────────────────────────────────────────────────┐
    │ Projects / Website     Search...     🔔     Profile │
    └─────────────────────────────────────────────────────┘

### Типові елементи

- Breadcrumbs.
- Глобальний пошук.
- Перемикач робочого простору.
- Notifications.
- Help.
- User Avatar.
- User Menu.

### Breadcrumbs

Breadcrumbs показують шлях до поточного розділу.

    Dashboard / Projects / Website Redesign

Вони особливо корисні в застосунках зі складною вкладеною структурою.

Не потрібно додавати Breadcrumbs на кожну сторінку автоматично. Якщо навігація проста, вони можуть створювати зайвий шум.

### User Menu

Меню користувача зазвичай містить:

- Profile.
- Account Settings.
- Workspace Settings.
- Billing.
- Switch Account.
- Log Out.

Не змішуй глобальну навігацію з діями облікового запису без зрозумілої структури.

- Welcome Message.
- Summary Cards.
- Charts.
- Recent Activity.
- Upcoming Tasks.

### KPI Cards

KPI (Key Performance Indicator) — показник, який допомагає оцінити стан або результат роботи.

Приклади:

- Total Projects.
- Active Users.
- Revenue.
- Completed Tasks.
- Conversion Rate.

1. Назву показника.
2. Значення.

✔ Групуй показники за змістом.

✔ Не перевантажуй головну сторінку всіма можливими графіками.

✔ Додавай період, одиниці вимірювання та контекст до метрик.

✔ Не використовуй колір як єдиний спосіб передати позитивну або негативну зміну.

✔ Дозволяй перейти від загального показника до детальної інформації.

✔ Не показуй вигадані дані як реальні показники користувача.

## 7. Page Header

Page Header — заголовкова область сторінки.

Зазвичай містить:

- Назву сторінки.
- Короткий опис.
- Primary Action.
- Secondary Actions.
- Breadcrumbs або контекст розділу.

Приклад:

    Projects

    Manage your team's projects and progress.

                                      [+ New Project]

### Принципи

- Назва повинна точно описувати розділ.
- Опис пояснює призначення сторінки, якщо це необхідно.
- Основна дія має бути помітною.
- Другорядні дії не повинні конкурувати з основною.
- Розташування заголовка й дій має бути послідовним на різних сторінках.

### Primary Action

Primary Action — головна дія сторінки.

Приклади:

- New Project.
- Create Task.
- Invite Member.
- Export Report.
- Add Customer.

Не роби всі кнопки однаково помітними. Коли кожна дія виглядає головною, користувачеві складніше визначити пріоритет.

Data Table — таблиця для перегляду й керування структурованими даними.

Таблиці часто використовуються для:

- Користувачів.
- Клієнтів.
- Проєктів.

- Замовлень.
- Платежів.
- Документів.

    │                                                           │
    │ Showing 1–3 of 24                    Previous   Next      │
    └───────────────────────────────────────────────────────────┘

### Основні складові таблиці

- Column Headers.
- Rows.
- Cells.
- Sorting.
- Filtering.
- Search.
- Row Actions.
- Pagination.
- Selection.
- Empty State.

### Правила проєктування таблиць

✔ Використовуй зрозумілі назви колонок.

✔ Розташовуй найважливіші дані ближче до початку.

✔ Вирівнюй однотипні значення послідовно.

✔ Передбачай довгі назви й великі значення.

✔ Не приховуй критичну інформацію лише через брак простору.

✔ Показуй, які колонки можна сортувати.

✔ Забезпечуй клавіатурну доступність елементів керування.

✔ Для великих наборів даних використовуй пошук, фільтри та пагінацію.

### Row Actions

Дії над окремим рядком можуть містити:

- View.
- Edit.
- Duplicate.
- Archive.
- Delete.

Необов'язкові дії можна розмістити в меню `More actions`.

Однак найважливіші дії не варто ховати, якщо це змушує користувача робити зайві переходи.

### Вибір рядків

Якщо таблиця підтримує масові операції, використовуй чекбокси.

    [ ] Select all

    [ ] Project A
    [ ] Project B
    [ ] Project C

    3 selected       Archive       Delete

Після вибору рядків показуй кількість вибраних елементів і доступні дії.

Небезпечні масові операції повинні мати відповідний захист.

## 9. Search, Filters and Sorting

Пошук, фільтри та сортування допомагають швидко знаходити потрібні дані.

### Search

Search — пошук за текстом або іншими параметрами.

Приклади:

- Search projects.
- Search customers.
- Search documents.
- Search team members.

Рекомендації:

- Використовуй конкретний placeholder.
- Показуй стан завантаження результатів, якщо пошук асинхронний.
- Передбачай повідомлення, якщо нічого не знайдено.
- Дозволяй очистити запит.
- Зберігай пошуковий контекст, коли це корисно для повернення назад.

Placeholder на кшталт `Search projects...` зазвичай корисніший за загальне `Search...` у локальному пошуку сторінки.

### Filters

Filters — інструменти обмеження набору даних.

Приклади:

- Status.
- Owner.
- Date Range.
- Category.
- Priority.
- Department.

Приклад:

    Status: [All statuses ▼]
    Owner:  [Anyone ▼]
    Date:   [Last 30 days ▼]

### Active Filters

Користувач повинен розуміти, які фільтри зараз застосовано.

    Status: Active ×
    Owner: Anna ×
    [Clear all]

Після видалення фільтра результати мають оновитися відповідно до обраної поведінки.

### Sorting

Sorting — впорядкування даних.

Наприклад:

- Name: A–Z.
- Created: Newest first.
- Revenue: Highest first.
- Due Date: Earliest first.

Візуально показуй напрямок сортування та доступність цієї функції.

Не плутай сортування з фільтрацією: сортування змінює порядок, а фільтрація — склад результатів.

## 10. Forms in SaaS

Форми використовуються для створення й редагування даних.

Приклади:

- Create Project.
- Add Customer.
- Invite Member.
- Create Task.
- Edit Profile.
- Configure Integration.

### Типова структура форми

    Create Project

    Project Name
    [________________________]

    Description
    [________________________]
    [________________________]

    Start Date
    [________________________]

    Status
    [Select status          ▼]

    [Cancel]          [Create Project]

### Основні правила

✔ Використовуй видимі підписи полів.

✔ Групуй пов'язані поля.

✔ Показуй обов'язкові поля.

✔ Пояснюй формат введення, якщо він неочевидний.

✔ Перевіряй введені значення.

✔ Показуй помилки біля відповідних полів.

✔ Зберігай введені дані, якщо це можливо й безпечно, після помилки.

✔ Блокуй повторне надсилання під час обробки, якщо повторна операція може створити проблеми.

✔ Показуй результат збереження.

### Inline Editing

Inline Editing дозволяє змінювати значення без відкриття окремої сторінки.

Наприклад, користувач може натиснути на назву проєкту та відредагувати її безпосередньо в таблиці.

Переваги:

- Менше переходів.
- Швидше редагування.
- Зручність для невеликих змін.

Недоліки:

- Менш очевидний спосіб початку редагування.
- Складніша клавіатурна взаємодія.
- Ризик випадкових змін.

Забезпечуй зрозумілі стани редагування, збереження, скасування та помилки.

## 11. Modals and Drawers

### Modal

Modal — діалогове вікно поверх поточного інтерфейсу.

Використовується для:

- Підтвердження важливої дії.
- Короткої форми.
- Швидкого перегляду інформації.
- Невеликого налаштування.

Приклад:

    ┌───────────────────────────────────┐
    │ Create Project                [×] │
    │                                   │
    │ Project Name                      │
    │ [___________________________]     │
    │                                   │
    │ [Cancel]          [Create]        │
    └───────────────────────────────────┘

### Drawer

Drawer — панель, яка виїжджає збоку екрана.

Підходить для:

- Деталей запису.
- Фільтрів.
- Редагування об'єкта.
- Контекстних налаштувань.

### Modal чи Drawer?

Використовуй Modal, коли користувач повинен зосередитися на короткій окремій дії.

Використовуй Drawer, коли важливо зберегти контекст основної сторінки та паралельно переглядати її вміст.

Для складних багатокрокових процесів іноді краще окрема сторінка.

### Важливі правила

- Дозволяй закрити діалог передбачуваним способом.
- Підтримуй клавіатурну навігацію.
- Керуй фокусом відповідно до вимог доступності.
- Не дозволяй фокусу випадково перейти до заблокованого фонового інтерфейсу.
- Не закривай форму після помилки, втрачаючи введені дані.
- Для незбережених змін передбачай зрозумілу поведінку.

## 12. Empty States

Empty State — стан інтерфейсу, у якому немає даних для відображення або ще не виконано потрібну дію.

Це не просто порожнє місце. Такий стан повинен пояснювати ситуацію й допомагати користувачеві продовжити роботу.

### Основні типи Empty States

#### 12.1. First-Use Empty State

Користувач ще не створив жодного об'єкта.

    No projects yet

    Create your first project to organize
    your team's work.

    [+ Create Project]

#### 12.2. No Search Results

Пошук не знайшов збігів.

    No projects found

    Try a different search term or
    clear your filters.

    [Clear Filters]

#### 12.3. No Data for Current Filters

Загальні дані існують, але вибрані фільтри не повернули результатів.

    No tasks match these filters.

    [Reset Filters]

#### 12.4. Completed State

Користувач завершив певний процес.

    All tasks completed

    There are no pending tasks.

#### 12.5. Unavailable Data

Дані тимчасово недоступні через помилку або проблему з підключенням.

У цьому випадку не можна створювати враження, що список справді порожній. Потрібно повідомити про проблему й запропонувати повторити дію.

### Правило

Не плутай:

- Відсутність даних.
- Відсутність результатів пошуку.
- Завантаження.
- Помилку сервера.
- Відсутність дозволу на перегляд.

Кожен стан потребує відповідного повідомлення.

## 13. Loading States

Loading State — стан інтерфейсу під час отримання або обробки даних.

SaaS-застосунки часто працюють з API та базами даних, тому завантаження є звичайною частиною UX.

### Основні варіанти

- Spinner.
- Skeleton.
- Progress Indicator.
- Inline Loading.
- Button Loading.
- Page Loading.

### Skeleton

Skeleton — спрощена форма майбутнього вмісту.

    ┌──────────────────────────────┐
    │ ███████████████              │
    │ ███████████████████████      │
    │                              │
    │ ████████     ███████         │
    └──────────────────────────────┘

Skeleton допомагає зберігати структуру сторінки, поки дані завантажуються.

### Коли використовувати

- Skeleton — коли відома приблизна структура майбутнього вмісту.
- Spinner — для короткої операції або невеликої області.
- Progress Indicator — коли можна показати реальний прогрес.
- Button Loading — коли користувач запускає конкретну дію.

### Best practices

✔ Не блокуй увесь інтерфейс через завантаження невеликої секції без потреби.

✔ Зберігай стабільну геометрію сторінки.

✔ Показуй стан кнопки після натискання.

✔ Не вигадуй точний відсоток прогресу, якщо система його не знає.

✔ Якщо завантаження затягнулося, надай користувачу зрозумілу інформацію.

## 14. Error States

Error State — стан інтерфейсу, який повідомляє про невдалу операцію або неможливість отримати дані.

Приклади:

- Network Error.
- Server Error.
- Validation Error.
- Permission Error.
- Payment Error.
- Integration Error.
- Session Expired.

### Хороше повідомлення про помилку

Повинно пояснювати:

1. Що сталося.
2. Як це впливає на користувача.
3. Що можна зробити далі.

Приклад:

    We couldn't load your projects.

    Check your internet connection and try again.

    [Try Again]

### Погане повідомлення

    Error 500

Таке повідомлення може бути корисним для технічного журналу, але недостатньо зрозуміле для звичайного користувача.

### Правила

- Не показуй внутрішні технічні деталі без потреби.
- Не звинувачуй користувача.
- Не приховуй помилку, якщо операція не виконалася.
- Не повідомляй про успіх до підтвердження результату.
- Дозволяй повторити операцію, якщо це безпечно.
- Не втрачай введені дані без попередження.
- Для критичних помилок пояснюй доступні наступні кроки.

## 15. Success and Feedback States

Після дії користувач повинен розуміти, чи виконано її успішно.

Приклади:

- Project created successfully.
- Changes saved.
- Invitation sent.
- Report exported.
- Password updated.

### Toast Notifications

Toast — коротке повідомлення, яке з'являється поверх інтерфейсу та зникає автоматично або після взаємодії.

Приклад:

    ✓ Project created successfully.

Toast підходить для короткого підтвердження операції, яка не потребує додаткових дій.

### Inline Feedback

Повідомлення безпосередньо в області, де виконується операція.

Наприклад:

    Changes saved.

### Коли не варто покладатися лише на Toast

Не використовуй коротке повідомлення як єдине джерело критичної інформації, якщо користувач може його пропустити.

Важливі результати, наприклад зміна тарифу, помилка платежу або скасування підписки, повинні залишатися доступними для перевірки.

### Важливо

Feedback повинен відповідати реальному результату операції.

Якщо сервер ще не підтвердив створення запису, не показуй повідомлення `Created successfully`.

### Best practices

✔ Чітко називай дію.

✔ Пояснюй наслідки, якщо вони неочевидні.

✔ Використовуй конкретний текст кнопки.

✔ Виділяй небезпечну дію візуально, але не покладайся лише на колір.

✔ Не додавай підтвердження для кожної дрібної дії.

✔ Для особливо небезпечних операцій можна вимагати додаткового підтвердження.

## 20. Workspace and Multi-Tenancy

Workspace — робочий простір, у якому користувачі організовують дані, учасників і налаштування.

У SaaS-продукті один користувач може працювати з кількома робочими просторами.

Приклад:

    Workspace: Acme Inc. ▼

    My Workspaces
    ├── Acme Inc.
    ├── Personal Workspace
    └── Marketing Team

### Перемикання Workspace

Під час перемикання робочого простору потрібно чітко показувати, де зараз перебуває користувач.

Це особливо важливо, якщо різні робочі простори містять різні клієнтські дані.

### Multi-Tenancy

Multi-Tenancy — архітектурний підхід, за якого одна система обслуговує кількох незалежних клієнтів або організацій.

З погляду UI важливо:

- Показувати поточний Workspace.
- Відокремлювати дані різних організацій.
- Не плутати персональні та командні налаштування.
- Показувати відповідний тариф і ліміти.
- Чітко визначати контекст дії.

Ізоляція даних між організаціями повинна забезпечуватися серверною архітектурою та перевірками доступу, а не лише інтерфейсом.

## 21. Onboarding

Onboarding — процес першого знайомства користувача з продуктом.

Мета — допомогти людині отримати першу реальну користь від сервісу.

### Типовий сценарій

    Sign Up
       ↓
    Verify Email
       ↓
    Create Workspace
       ↓
    Complete Profile
       ↓
    Create First Project
       ↓
    Invite Team
       ↓
    Start Working

Не кожен продукт потребує всіх цих кроків.

### Основні принципи

✔ Запитуй лише необхідні дані.

✔ Пояснюй, навіщо потрібен кожен крок.

✔ Дозволяй пропускати необов'язкові етапи.

✔ Показуй прогрес, якщо процес має кілька кроків.

✔ Допомагай користувачу швидко виконати першу корисну дію.

✔ Не змушуй проходити довгий вступ, якщо можна одразу почати роботу.

### Progressive Disclosure

Progressive Disclosure — поступове відкриття функцій та інформації в міру потреби.

Замість того щоб показувати всі налаштування відразу, починай із найважливіших.

Наприклад, при створенні проєкту спочатку попроси назву. Додаткові параметри можна розмістити в секції Advanced Settings.

## 22. Pricing and Subscription UI

Pricing UI допомагає користувачу зрозуміти відмінності між тарифними планами та обрати відповідний варіант.

Типові елементи:

- Plan Name.
- Price.
- Billing Period.
- Features.
- Usage Limits.
- Trial Information.
- Current Plan.
- Upgrade.
- Downgrade.
- Cancel Subscription.

### Приклад тарифних карток

    Starter
    $0 / month

    - Basic features
    - Limited projects
    - Community support

    [Current Plan]


    Pro
    $19 / month

    - All Starter features
    - More projects
    - Team collaboration

    [Upgrade Plan]

Це лише умовний приклад. Реальні ціни та функції повинні відповідати продукту.

### Best practices

- Чітко вказуй період оплати.
- Пояснюй ліміти тарифу.
- Розрізняй щомісячну й річну оплату.

Хороший prompt пояснює:

- Яке обмеження спрацювало.
- Яка функція недоступна.
- Який тариф її підтримує.
- Що станеться після оновлення.

Не перетворюй кожну дію користувача на рекламу платного тарифу.

## 23. Usage Limits

Приклади:

- Кількість проєктів.
- Кількість учасників.
- Обсяг сховища.
- Кількість API-запитів.
- Кількість створених звітів.

Приклад:

    Storage Usage

    7.2 GB of 10 GB used

    ████████████████░░░░ 72%

### Правила

- Показуй використане й доступне значення.
- Додавай одиниці вимірювання.
- Пояснюй, коли оновлюється ліміт.
- Попереджай про важливі обмеження завчасно, якщо це можливо.
- Не повідомляй про вичерпання ліміту, якщо сервер ще не підтвердив цей стан.
- Пропонуй доступні наступні кроки.

Для прогрес-барів важливо використовувати не лише колір, а й текстові значення.

### Mobile

На вузьких екранах варто:

- Використовувати компактну навігацію.
- Залишати найважливіші дії доступними.
- Перетворювати складні таблиці на картки або інші відповідні подання.
- Дозволяти горизонтальне прокручування там, де таблицю необхідно зберегти.
- Робити поля та інтерактивні елементи зручними для дотику.
- Уникати переповнення контенту.

### Важливо

Responsive Design — це не просто зменшення ширини елементів.

Потрібно перевіряти, чи залишається сценарій роботи зручним на кожному розмірі екрана.

## 27. Accessibility у SaaS

Accessibility — проєктування інтерфейсу, яким можуть користуватися люди з різними можливостями та способами взаємодії.

### Основні правила

✔ Використовуй семантичний HTML.

✔ Забезпечуй клавіатурну навігацію.

✔ Показуй видимий focus state.

✔ Пов'язуй поля форм із підписами.

✔ Забезпечуй достатній контраст тексту.

✔ Не передавай інформацію лише кольором.

✔ Використовуй зрозумілі назви кнопок.

✔ Забезпечуй доступні назви іконок-кнопок.

✔ Повідомляй про помилки зрозумілим текстом.

✔ Для динамічних повідомлень враховуй потреби допоміжних технологій.

### Приклад доступної кнопки

    <button type="button" aria-label="Open notifications">
      <svg aria-hidden="true" viewBox="0 0 24 24">
        <!-- Іконка сповіщень -->
      </svg>
    </button>

Якщо кнопка вже містить видимий текст `Notifications`, окремий `aria-label` зазвичай не потрібен.

### Keyboard Navigation

Користувач повинен мати можливість виконувати основні дії без миші.

Перевір:

- Tab.
- Shift + Tab.
- Enter.
- Space.
- Escape.
- Стрілки — для компонентів, де вони очікувані.

Для складних компонентів, наприклад меню, діалогів і таблиць, дотримуйся відповідних моделей взаємодії.

## 29. Dark Mode

Dark Mode — темна кольорова схема інтерфейсу.

У SaaS-продуктах темна тема може бути корисною для тривалої роботи, особливо в інструментах для розробників і аналітичних системах.

### Основні правила

- Використовуй окремі токени для темної теми.
- Перевіряй контраст тексту.
- Не інвертуй усі кольори механічно.
- Перевіряй кольори графіків і статусів.
- Зберігай читабельність меж і розділювачів.
- Перевіряй hover, focus, disabled та error states.
- Забезпечуй узгодженість усіх компонентів.

Приклад:

    :root {
      color-scheme: light;

      --color-bg: #f9fafb;
      --color-surface: #ffffff;
      --color-text: #111827;
      --color-border: #e5e7eb;
    }

    [data-theme="dark"] {
      color-scheme: dark;

      --color-bg: #111827;
      --color-surface: #1f2937;
      --color-text: #f9fafb;
      --color-border: #374151;
    }

Це базова ілюстрація. Для повноцінного Dark Mode потрібні додаткові токени для тексту, станів, поверхонь, графіків та інтерактивних компонентів.

## 30. UI States — повний набір станів

Кожна важлива сторінка SaaS повинна мати продуману поведінку в різних ситуаціях.

| Стан | Що відбувається | Приклад |
|---|---|---|
| Default | Звичайний стан | Таблиця з даними |
| Hover | Наведення курсора | Підсвічування рядка |
| Focus | Клавіатурний фокус | Контур навколо кнопки |
| Active | Елемент активовано | Натиснута вкладка |
| Selected | Елемент вибрано | Вибраний рядок |
| Disabled | Дія недоступна | Неактивна кнопка |
| Loading | Дані завантажуються | Skeleton |
| Empty | Даних немає | Create your first project |
| Error | Операція не вдалася | Try again |
| Success | Операція виконана | Changes saved |
| Read-only | Дані лише для перегляду | Disabled editing |
| Permission denied | Недостатньо прав | Contact administrator |

### Правило

Не проєктуй лише ідеальний стан із заповненими даними.

Перевіряй, як виглядає інтерфейс, якщо:

- Користувач нічого ще не створив.
- Назва об'єкта дуже довга.
- Список містить тисячі записів.
- Мережа повільна.
- Сервер повернув помилку.
- Користувач не має потрібних прав.
- Сесія завершилася.
- Дані змінено іншим учасником команди.

## 31. Information Density

Information Density — кількість інформації, яку інтерфейс показує в певній області.

SaaS-продукти часто потребують вищої щільності інформації, ніж звичайні маркетингові сайти.

### Low Density

Більше простору, великі картки, менше елементів.

Підходить для:

- Простих Dashboard.
- Початкового знайомства.
- Невеликої кількості даних.
- Мобільних екранів.

### High Density

Компактні рядки, більше колонок, менші відступи.

Підходить для:

- Адміністративних панелей.
- Великих таблиць.
- CRM.
- Фінансових інструментів.
- Систем моніторингу.

### Баланс

Занадто низька щільність змушує користувача багато прокручувати.

Занадто висока щільність ускладнює читання й пошук важливих даних.

Правильна щільність залежить від завдання, типу даних, розміру екрана та досвіду користувача.

## 32. Microcopy для SaaS

Microcopy — короткі тексти інтерфейсу, які допомагають користувачу зрозуміти функцію або наслідок дії.

Приклади:

- Create project.
- Save changes.
- Invite member.
- No results found.
- Your changes have been saved.
- This field is required.
- You don't have permission to perform this action.

### Правила

✔ Використовуй конкретні дієслова.

✔ Уникай незрозумілих технічних термінів.

✔ Пояснюй причину обмеження, якщо це доречно.

✔ Використовуй однакові назви для однакових дій.

✔ Не звинувачуй користувача.

✔ Уникай зайвих слів.

### Приклад

Замість:

    Submit

Можна використати:

    Create Project

Замість:

    Operation failed

Краще:

    We couldn't save your changes. Try again.

Текст повинен відповідати конкретному контексту, а не бути універсальним для всіх ситуацій.

## 34. TypeScript для SaaS UI

TypeScript допомагає описувати структуру даних, які використовуються в інтерфейсі.

Приклад типу проєкту:

    type ProjectStatus =
      | "active"
      | "completed"
      | "archived";

    type Project = {
      id: string;
      name: string;
      ownerName: string;
      status: ProjectStatus;
      updatedAt: string;
    };

Такий тип допомагає підтримувати узгодженість даних між компонентами.

### Типізовані Props

    type ProjectTableProps = {
      projects: Project[];
      onEdit: (projectId: string) => void;
      onDelete: (projectId: string) => void;
    };

    function ProjectTable({
      projects,
      onEdit,
      onDelete,
    }: ProjectTableProps) {
      return (
        <table>
          <tbody>
            {projects.map((project) => (
              <tr key={project.id}>
                <td>{project.name}</td>
                <td>{project.ownerName}</td>
                <td>{project.status}</td>
                <td>
                  <button
                    type="button"
                    onClick={() => onEdit(project.id)}
                  >
                    Edit
                  </button>

                  <button
                    type="button"
                    onClick={() => onDelete(project.id)}
                  >
                    Delete
                  </button>
                </td>
              </tr>
            ))}
          </tbody>
        </table>
      );
    }

Це навчальний приклад. У реальному компоненті також потрібно продумати доступність таблиці, форматування дат, обробку порожнього списку, стани завантаження та підтвердження небезпечних дій.

### Що важливо типізувати

- Моделі даних.
- Props компонентів.
- Статуси.
- Параметри фільтрів.
- Результати операцій.
- Параметри обробників подій.

Не використовуй `any` без необхідності. Краще описати очікувану структуру даних або скористатися `unknown` із подальшою перевіркою.

    idle
      ↓

- Зрозуміла поведінка UI.

### Важливо

У реальному застосунку потрібно також враховувати:

- Повторне завантаження.
- Скасування застарілих запитів.
- Порожній результат.
- Авторизацію.
- Права доступу.
- Оновлення даних.
- Конфлікти під час одночасного редагування.

## 36. Performance та великі набори даних

Performance — швидкість і плавність роботи інтерфейсу.

У SaaS це особливо важливо для таблиць, Dashboard і великих робочих просторів.

### Основні підходи

- Pagination.
- Server-side Filtering.
- Server-side Sorting.
- Debounced Search.
- Lazy Loading.
- Virtualization для великих списків.
- Оптимізація зображень.
- Завантаження важких компонентів за потреби.
- Кешування там, де воно доречне.

### Pagination

Pagination ділить великий набір даних на сторінки.

Переваги:

- Менше даних одночасно.
- Простішій інтерфейс для великих списків.
- Потенційно менше навантаження на браузер.

### Virtualization

Virtualization — відображення лише тих елементів довгого списку, які потрібні для поточного видимого діапазону.

Це може покращити продуктивність дуже великих списків.

Однак віртуалізація ускладнює реалізацію доступності, пошук, вибір рядків і поведінку прокручування. Її варто використовувати тоді, коли вона справді потрібна.

## 37. Безпека та довіра в інтерфейсі

SaaS-продукти часто працюють із приватними, фінансовими або корпоративними даними.

Тому інтерфейс повинен підтримувати зрозумілу й безпечну взаємодію.

### Основні принципи

- Чітко показуй поточний обліковий запис і робочий простір.
- Не розкривай конфіденційні дані без необхідності.
- Не показуй секретні ключі повністю після їх створення, якщо це відповідає моделі безпеки продукту.
- Попереджай про небезпечні або незворотні операції.
- Пояснюй наслідки зміни прав доступу.
- Забезпечуй зрозумілий процес виходу із системи.
- Повідомляй про завершення сесії.
- Не імітуй успішні операції, які сервер відхилив.

### Security UI ≠ Security System

Інтерфейс допомагає користувачу безпечно взаємодіяти із системою, але не замінює:

- Серверну авторизацію.
- Перевірку дозволів.
- Валідацію вхідних даних.
- Захист сесій.
- Безпечне зберігання секретів.
- Контроль доступу до даних.

## 38. Типові помилки в SaaS UI

### Помилка 1. Перевантажений Dashboard

На головній сторінці розміщено десятки карток і графіків.

**Рішення:** показуй ключові показники, важливі завдання та найкорисніші переходи.

### Помилка 2. Надто складна навігація

У Sidebar забагато пунктів і вкладених рівнів.

**Рішення:** групуй розділи, переглядай їхню ієрархію та використовуй зрозумілі назви.

### Помилка 3. Таблиця без пошуку та фільтрів

Зі збільшенням кількості записів знайти потрібний стає складно.

**Рішення:** додавай інструменти пошуку, сортування, фільтрації та пагінації відповідно до потреб.

### Помилка 4. Відсутність Empty State

Новий користувач бачить порожню сторінку й не розуміє, що робити.

**Рішення:** пояснюй призначення розділу та пропонуй доречну першу дію.

### Помилка 5. Відсутність Loading State

Після натискання кнопки нічого не відбувається з погляду користувача.

**Рішення:** показуй, що операція виконується, і запобігай небажаним повторним діям.

### Помилка 6. Незрозумілі повідомлення про помилки

Користувач бачить лише технічний код.

**Рішення:** пояснюй проблему людською мовою й пропонуй наступний крок.

### Помилка 7. Невідповідність реальним правам доступу

Інтерфейс дозволяє натискати дію, яка згодом без пояснення відхиляється сервером.

**Рішення:** узгоджуй UI із правами користувача, але завжди перевіряй дозволи на сервері.

### Помилка 8. Погана мобільна адаптація

Таблиці, Sidebar і форми виходять за межі екрана.

**Рішення:** продумуй мобільні сценарії, а не лише зменшуй елементи.

### Помилка 9. Непослідовні компоненти

На різних сторінках однакові кнопки мають різний вигляд і поведінку.

**Рішення:** створи спільні компоненти та правила дизайн-системи.

### Помилка 10. Відсутність зворотного зв'язку

Після збереження користувач не розуміє, чи зміни застосовано.

**Рішення:** показуй реальний статус операції.

### Помилка 11. Надмірна кількість модальних вікон

Кожна дія відкриває новий діалог.

**Рішення:** використовуй окремі сторінки, inline editing або Drawer, коли вони краще зберігають контекст.

### Помилка 12. Неочевидні ліміти тарифу

Користувач дізнається про обмеження лише після невдалої операції.

**Рішення:** показуй використання ресурсів і пояснюй обмеження завчасно.

## 42. Що потрібно запам'ятати

1. **SaaS UI — це робочий інтерфейс, а не просто набір красивих карток.** Його завдання — допомагати користувачам ефективно виконувати регулярні операції.

2. **Навігація визначає зрозумілість продукту.** Sidebar, Topbar і структура сторінок повинні утворювати логічну систему.

3. **Дані потребують правильних інструментів.** Таблиці, пошук, фільтри, сортування та пагінація допомагають працювати зі складною інформацією.

4. **Кожна важлива операція повинна мати зворотний зв'язок.** Користувач має розуміти, чи виконується дія, чи завершилася вона успішно або сталася помилка.

5. **Empty State — це частина UX.** Порожня сторінка повинна пояснювати ситуацію й допомагати зробити наступний крок.

6. **UI не замінює серверну безпеку.** Права доступу та захист даних повинні перевірятися на backend.

7. **Responsive Design повинен зберігати сценарії роботи.** На мобільному екрані важливо не просто зменшити компоненти, а забезпечити зручну взаємодію.

8. **Design System допомагає масштабувати продукт.** Спільні компоненти, токени та правила забезпечують узгодженість інтерфейсу.

9. **Не всі функції потрібно показувати одночасно.** Progressive Disclosure допомагає зменшити складність і показувати додаткові можливості тоді, коли вони потрібні.

10. **Якісний SaaS UI враховує реальні сценарії.** Завантаження, помилки, відсутність прав, довгі назви, великі таблиці та повільна мережа — це частина продукту, а не винятки.
