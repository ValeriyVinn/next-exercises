# 08. Mobile vs Desktop — Проєктування для мобільних пристроїв і комп'ютерів

Mobile vs Desktop — це тема про відмінності в проєктуванні інтерфейсів для смартфонів, планшетів і настільних комп'ютерів.

Мобільний і настільний інтерфейси можуть використовувати однакові кольори, типографіку, компоненти та контент, але відрізнятися компонуванням, навігацією, розмірами інтерактивних елементів і способом взаємодії.

Головна мета — не просто зменшити настільний інтерфейс для смартфона, а зберегти зручність, зрозумілість і доступність продукту в різних умовах використання.

✔ Mobile-first — проєктування з пріоритетом вузьких екранів.

✔ Desktop-first — проєктування з пріоритетом широких екранів.

✔ Responsive Design — адаптація інтерфейсу до різних розмірів екрана.

✔ Adaptive Layout — використання різних варіантів компонування залежно від умов.

✔ Touch Interaction — взаємодія через сенсорний екран.

✔ Pointer Interaction — взаємодія за допомогою миші або іншого вказівного пристрою.

✔ Content Priority — визначення важливості інформації.

✔ Progressive Disclosure — поступове показування додаткової інформації.

✔ Responsive Navigation — адаптація навігації до доступного простору.

✔ Cross-device Consistency — збереження узгодженого досвіду на різних пристроях.

---

# 1. Що означає Mobile vs Desktop

## 1.1. Мобільний інтерфейс

Мобільний інтерфейс — це інтерфейс, оптимізований для використання на смартфонах та інших пристроях із відносно вузьким екраном.

Типові особливості:

- обмежена ширина;
- вертикальне прокручування;
- взаємодія переважно дотиком;
- менша кількість елементів, видимих одночасно;
- потреба в компактній навігації;
- особлива увага до розміру інтерактивних областей;
- часте використання інтерфейсу однією рукою.

Наприклад, картки товарів можуть розташовуватися в одному стовпці, а навігація — відкриватися через кнопку меню.

## 1.2. Настільний інтерфейс

Настільний інтерфейс — це інтерфейс, оптимізований для широких екранів комп'ютерів і ноутбуків.

Типові особливості:

- більша ширина;
- можливість використовувати кілька колонок;
- більше елементів на екрані одночасно;
- зручна взаємодія мишею та клавіатурою;
- можливість розміщувати бічні панелі;
- ширші таблиці та складніші робочі області;
- можливість використовувати додаткові інструменти керування.

Наприклад, сторінка навчальної платформи може містити бічну навігацію, список курсів і панель особистого прогресу.

## 1.3. Основна відмінність

Мобільний і настільний інтерфейси — це не обов'язково два різні дизайни.

Часто це **одна система інтерфейсу, яка по-різному організовує інформацію залежно від доступного простору та способу взаємодії**.

Приклад:

    DESKTOP

    ┌──────────────────────────────────────────┐
    │ Logo       Navigation        Profile     │
    ├────────────┬─────────────────────────────┤
    │ Sidebar    │ Main content                │
    │            │                             │
    │ Courses    │  ┌────────┐  ┌────────┐     │
    │ Schedule   │  │ Card 1 │  │ Card 2 │     │
    │ Settings   │  └────────┘  └────────┘     │
    └────────────┴─────────────────────────────┘

    MOBILE

    ┌────────────────────┐
    │ Logo          Menu │
    ├────────────────────┤
    │ Main content       │
    │                    │
    │ ┌────────────────┐ │
    │ │ Card 1         │ │
    │ └────────────────┘ │
    │ ┌────────────────┐ │
    │ │ Card 2         │ │
    │ └────────────────┘ │
    └────────────────────┘

На мобільному екрані бічна панель може переміщуватися в меню, а картки — розташовуватися одна під одною.

# 2. Основні відмінності Mobile та Desktop

| Характеристика | Mobile | Desktop |
|---|---|---|
| Доступний простір | Обмежений | Зазвичай ширший |
| Компонування | Часто одна колонка | Можливі кілька колонок |
| Навігація | Компактна або прихована | Часто горизонтальна чи бічна |
| Взаємодія | Дотик | Миша, клавіатура, інші пристрої |
| Контент | Потрібна чітка пріоритизація | Більше інформації може бути видимою одночасно |
| Картки | Часто вертикальні | Можуть бути горизонтальними |
| Таблиці | Можуть прокручуватися | Часто відображають більше колонок |
| Форми | Зазвичай одна колонка | Можливі кілька колонок |
| Відступи | Компактні, але достатні | Можуть бути просторішими |
| Наведення курсора | Не є основним способом взаємодії | Може використовуватися |
| Прокручування | Часто вертикальне | Вертикальне та іноді горизонтальне |
| Бічні панелі | Часто приховані або переміщені | Можуть бути постійно видимими |

Це типові тенденції, а не жорсткі правила. Наприклад, мобільний планшет може підтримувати клавіатуру та мишу, а настільний комп'ютер може мати сенсорний екран.

Тому орієнтуйся не тільки на назву пристрою, а й на доступний простір та спосіб взаємодії.

# 3. Mobile-first — спочатку мобільний інтерфейс

Mobile-first — це підхід, за якого проєктування починається з вузького екрана, а потім інтерфейс поступово розширюється для більших екранів.

Спочатку визначають найважливіші функції та інформацію, а потім додають можливості, які доцільні на ширшому екрані.

## 3.1. Чому Mobile-first корисний

На вузькому екрані простір обмежений. Це змушує чітко визначити:

- що користувач повинен побачити відразу;
- які дії є найважливішими;
- які елементи можна об'єднати;
- яку інформацію можна перемістити нижче;
- які компоненти потребують іншого компонування.

Цей підхід допомагає уникнути перевантаженого інтерфейсу.

## 3.2. Послідовність Mobile-first

    Визначення основного завдання
                ↓
    Вибір найважливішого контенту
                ↓
    Створення мобільного компонування
                ↓
    Перевірка читабельності та взаємодії
                ↓
    Додавання можливостей для ширших екранів
                ↓
    Тестування всіх варіантів

## 3.3. Mobile-first у CSS

У Mobile-first базові стилі описують компактний варіант, а media queries додають правила для ширших екранів.

    /* Базовий варіант: вузький екран */
    .product-grid {
      display: grid;
      grid-template-columns: 1fr;
      gap: 1rem;
    }

    /* Ширший екран */
    @media (min-width: 40rem) {
      .product-grid {
        grid-template-columns: repeat(2, minmax(0, 1fr));
      }
    }

    /* Ще ширший екран */
    @media (min-width: 64rem) {
      .product-grid {
        grid-template-columns: repeat(3, minmax(0, 1fr));
      }
    }

Базовий варіант працює без media queries. Наступні правила поступово розширюють компонування.

## 3.4. Коли використовувати Mobile-first

Mobile-first часто підходить для:

- публічних вебсайтів;
- блогів;
- новинних порталів;
- інтернет-магазинів;
- навчальних платформ;
- сервісів, якими часто користуються зі смартфона;
- проєктів, де важливо визначити основні функції без зайвого вмісту.

Однак Mobile-first не означає, що потрібно ігнорувати настільний інтерфейс. Його також потрібно повноцінно проєктувати та тестувати.

# 4. Desktop-first — спочатку настільний інтерфейс

Desktop-first — це підхід, за якого проєктування починається з широкого екрана, а потім компонування адаптується для вужчих.

Він може бути корисним для інтерфейсів, у яких основна робота відбувається на комп'ютері.

Наприклад:

- складні адміністративні панелі;
- редактори документів;
- системи керування навчанням;
- професійні інструменти;
- робочі середовища з багатьма таблицями;
- аналітичні панелі.

## 4.1. Особливості Desktop-first

Спочатку визначають:

- основну робочу область;
- бічні панелі;
- таблиці та списки;
- багатоколонкове компонування;
- розташування інструментів;
- можливість одночасного перегляду кількох блоків.

Потім визначають, як ці елементи повинні поводитися на вузьких екранах.

Наприклад:

- бічна панель стає висувним меню;
- таблиця отримує горизонтальне прокручування;
- дві колонки перетворюються на одну;
- другорядні панелі переміщуються нижче;
- інструменти групуються в компактну панель.

## 4.2. Desktop-first у CSS

    /* Базовий варіант: широкий екран */
    .dashboard {
      display: grid;
      grid-template-columns: 16rem minmax(0, 1fr);
      gap: 1.5rem;
    }

    /* Вузький екран */
    @media (max-width: 48rem) {
      .dashboard {
        grid-template-columns: 1fr;
      }
    }

У цьому прикладі початковий варіант має бічну колонку. На вузькому екрані компонування переходить в одну колонку.

## 4.3. Обмеження Desktop-first

Якщо просто стискати настільний інтерфейс, мобільна версія може стати незручною.

Проблеми:

- забагато інформації;
- занадто дрібні елементи;
- складна навігація;
- широкі таблиці;
- переповнення тексту;
- кнопки, які важко натискати;
- приховані або недоступні дії.

Тому Desktop-first також потребує переосмислення компонування, а не лише зміни розмірів.

# 5. Responsive Design і Adaptive Design

Ці поняття часто використовуються разом, але описують різні підходи.

## 5.1. Responsive Design

Responsive Design використовує гнучке компонування, яке пристосовується до доступного простору.

Типові інструменти:

- Flexbox;
- CSS Grid;
- відносні одиниці;
- `minmax()`;
- `clamp()`;
- Media Queries;
- Container Queries;
- гнучкі зображення.

Приклад:

    .content-grid {
      display: grid;
      grid-template-columns: repeat(
        auto-fit,
        minmax(min(100%, 18rem), 1fr)
      );
      gap: 1.5rem;
    }

Сітка автоматично розміщує картки відповідно до доступної ширини.

## 5.2. Adaptive Design

Adaptive Design може використовувати кілька заздалегідь визначених варіантів компонування для різних діапазонів ширини або сценаріїв використання.

Наприклад:

- вузький екран — компактна навігація;
- середній екран — скорочене меню;
- широкий екран — повна навігація з бічною панеллю.

Приклад:

    .navigation {
      display: flex;
      flex-direction: column;
    }

    @media (min-width: 48rem) {
      .navigation {
        flex-direction: row;
      }
    }

У практичній веброзробці адаптивний інтерфейс часто поєднує гнучке компонування та конкретні зміни структури.

## 5.3. Що вибрати

Не потрібно обирати тільки один підхід для всього сайту.

Використовуй гнучке компонування там, де воно працює природно, і окремі адаптивні варіанти там, де змінюється структура або спосіб взаємодії.

Наприклад:

- сітка карток може бути гнучкою;
- навігація може змінюватися через breakpoint;
- картка курсу може використовувати Container Queries;
- таблиця може зберігати структуру та прокручуватися горизонтально.

# 6. Навігація: Mobile vs Desktop

Навігація — одна з найпомітніших частин адаптивного інтерфейсу.

## 6.1. Desktop Navigation

На широкому екрані меню часто розміщується горизонтально.

    ┌─────────────────────────────────────────┐
    │ LOGO  Головна  Курси  Новини  Контакти  │
    └─────────────────────────────────────────┘

Переваги:

- основні розділи видно відразу;
- переходи доступні без відкриття меню;
- користувач швидко оцінює структуру сайту.

Недоліки:

- потрібен горизонтальний простір;
- довгі назви можуть не поміщатися;
- додаткові кнопки ускладнюють компонування.

## 6.2. Mobile Navigation

На вузькому екрані меню може перетворюватися на кнопку відкриття панелі.

    ┌──────────────────────┐
    │ LOGO             ☰   │
    └──────────────────────┘

Після натискання відкривається список розділів.

Переваги:

- економія місця;
- компактна шапка;
- можливість розмістити більше пунктів.

Недоліки:

- посилання не видно відразу;
- користувач виконує додаткову дію;
- потрібно продумати відкриття та закриття меню.

## 6.3. Не приховуй усе автоматично

Якщо є лише два-три основні розділи, їх іноді можна залишити видимими і на смартфоні.

При виборі враховуй:

- кількість пунктів;
- довжину назв;
- важливість кожного розділу;
- наявність логотипа;
- кнопки входу та реєстрації;
- ширину доступного простору.

Головна мета — не просто зробити меню компактним, а зберегти швидкий доступ до важливих розділів.

# 7. Компонування: одна колонка чи кілька

## 7.1. Mobile: вертикальне компонування

На смартфонах часто використовують одну колонку.

    ┌──────────────────────┐
    │ Заголовок             │
    ├──────────────────────┤
    │ Card 1                │
    ├──────────────────────┤
    │ Card 2                │
    ├──────────────────────┤
    │ Card 3                │
    └──────────────────────┘

Переваги:

- достатня ширина тексту;
- зрозуміла послідовність;
- зручно прокручувати;
- простіше розташувати кнопки.

Однак одна колонка не завжди є найкращим рішенням. Для компактних карток, фотографій або коротких категорій можуть бути доречними дві колонки навіть на мобільному екрані.

## 7.2. Desktop: багатоколонкове компонування

На широкому екрані можна показати більше елементів одночасно.

    ┌───────────┬───────────┬───────────┐
    │ Card 1    │ Card 2    │ Card 3    │
    ├───────────┼───────────┼───────────┤
    │ Card 4    │ Card 5    │ Card 6    │
    └───────────┴───────────┴───────────┘

Переваги:

- ефективне використання простору;
- можливість порівнювати елементи;
- менша потреба у вертикальному прокручуванні;
- краща видимість груп пов'язаного вмісту.

## 7.3. CSS Grid для обох варіантів

    .card-grid {
      display: grid;
      grid-template-columns: 1fr;
      gap: 1rem;
    }

    @media (min-width: 40rem) {
      .card-grid {
        grid-template-columns: repeat(2, minmax(0, 1fr));
      }
    }

    @media (min-width: 64rem) {
      .card-grid {
        grid-template-columns: repeat(3, minmax(0, 1fr));
        gap: 1.5rem;
      }
    }

Кількість колонок змінюється в міру збільшення доступної ширини.

Значення `40rem` і `64rem` тут є прикладами. Для реального інтерфейсу breakpoint потрібно визначати на основі вмісту.

# 8. Взаємодія: Touch vs Pointer

Мобільні та настільні пристрої часто відрізняються способом взаємодії.

На смартфоні користувач зазвичай торкається екрана пальцем.

На комп'ютері він може використовувати мишу, клавіатуру, трекпад або інший пристрій.

## 8.1. Сенсорна взаємодія

Для сенсорних пристроїв важливі:

- достатні області натискання;
- відстань між сусідніми діями;
- зрозумілі кнопки;
- відсутність залежності від наведення курсора;
- передбачувана поведінка жестів;
- доступність основних дій без складних жестів.

Приклад:

    .action-button {
      min-height: 44px;
      padding: 0.75rem 1rem;
    }

Це практичний орієнтир для розміру інтерактивної області, але не універсальна вимога для всіх компонентів. Під час оцінювання доступності потрібно враховувати відповідні критерії WCAG та їхні винятки.

## 8.2. Взаємодія мишею

На настільних пристроях можна використовувати:

- `:hover`;
- підказки;
- додаткові індикатори;
- контекстні меню;
- компактні панелі інструментів.

Проте важливі функції не повинні бути доступними тільки через наведення курсора.

Приклад:

    .card-link:hover {
      text-decoration: underline;
    }

    .card-link:focus-visible {
      outline: 3px solid #2457c5;
      outline-offset: 3px;
    }

`hover` покращує взаємодію мишею, а `focus-visible` допомагає користувачам клавіатури.

## 8.3. Перевірка можливостей пристрою

Не завжди правильно визначати спосіб взаємодії лише через ширину екрана.

CSS підтримує media features, які описують доступні пристрої введення.

Наприклад:

    @media (hover: hover) and (pointer: fine) {
      .card:hover {
        box-shadow: 0 0.5rem 1.5rem rgb(0 0 0 / 12%);
      }
    }

Це правило застосовується, коли основний пристрій введення підтримує наведення та має точний вказівник.

Водночас пристрої можуть підтримувати кілька способів введення, тому базова функціональність повинна працювати без залежності від цього ефекту.

# 9. Контент: що показувати на різних екранах

Контент — одна з найважливіших частин Mobile vs Desktop.

Не можна автоматично приховувати інформацію лише тому, що екран вузький.

Спочатку визнач, що важливо користувачеві.

## 9.1. Content Priority

Content Priority — це визначення пріоритетності інформації.

Наприклад, картка курсу може містити:

1. Назву курсу.
2. Короткий опис.
3. Тривалість навчання.
4. Рейтинг.
5. Дату початку.
6. Додаткові характеристики.

На мобільному екрані назва, короткий опис і основна дія можуть отримати більше візуального пріоритету.

Додаткові характеристики можна перемістити нижче або показувати на сторінці деталей.

## 9.2. Progressive Disclosure

Progressive Disclosure — поступове показування додаткової інформації тоді, коли вона потрібна користувачеві.

Наприклад:

- короткий опис товару видно відразу;
- повні характеристики відкриваються в окремому блоці;
- розширені фільтри відкриваються за кнопкою;
- додаткові налаштування знаходяться в окремій панелі.

Цей підхід допомагає зменшити перевантаження інтерфейсу.

Проте не приховуй критично важливі відомості, такі як ціна, умови оплати або повідомлення про помилку, лише заради компактності.

## 9.3. Mobile Content ≠ Less Content

Мобільна версія не обов'язково повинна містити менше інформації.

Вона може показувати той самий контент, але по-іншому його організовувати.

Наприклад:

- замість трьох колонок — три послідовні блоки;
- замість бічної панелі — кнопка відкриття фільтрів;
- замість широкої таблиці — прокручувана таблиця;
- замість горизонтального меню — компактна навігація.

Важливо зберегти доступ до потрібної інформації.

Форми повинні залишатися зручними для введення інформації.

# 12. Адаптація таблиць і складних даних

Таблиці особливо важливі в навчальних системах, адміністративних панелях і сервісах із великою кількістю даних.

На широкому екрані користувач може бачити всі колонки одночасно.

На вузькому екрані таблиця може стати надто широкою.

## 12.1. Горизонтальне прокручування

Якщо важливо зберегти табличну структуру, можна дозволити прокручування по горизонталі.

    .table-wrapper {
      max-width: 100%;
      overflow-x: auto;
    }

    .table-wrapper table {
      width: 100%;
      min-width: 36rem;
      border-collapse: collapse;
    }

Це дає змогу зберегти зв'язок між заголовками та значеннями.

## 12.2. Інші варіанти

Залежно від завдання можна:

- показувати тільки найважливіші колонки;
- дозволити користувачеві вибирати колонки;
- перетворити рядки на картки;
- показувати деталі після вибору рядка;
- використовувати горизонтальне прокручування.

Не приховуй важливі дані без альтернативного способу їх перегляду.

# 13. Типографіка та відступи

Мобільний і настільний інтерфейси можуть використовувати різні розміри заголовків, відступів та міжрядкових інтервалів.

Однак адаптація не повинна робити текст надто дрібним.

## 13.1. Fluid Typography

Fluid Typography — це підхід, за якого розмір тексту змінюється залежно від доступного простору.

Приклад:

    .page-title {
      font-size: clamp(1.75rem, 4vw, 3rem);
      line-height: 1.2;
    }

    .section-title {
      font-size: clamp(1.25rem, 2.5vw, 2rem);
      line-height: 1.3;
    }

`clamp()` визначає мінімальний, бажаний і максимальний розмір.

## 13.2. Відступи

На широких екранах можуть бути доречними більші відступи між секціями.

На вузьких — компактніші, але достатні для розділення інформації.

    .section {
      padding-block: clamp(2rem, 5vw, 5rem);
      padding-inline: clamp(1rem, 4vw, 2.5rem);
    }

Не зменшуй усі відступи однаково. Важливо зберегти ієрархію:

- відстань між великими секціями;
- відстань між заголовком і текстом;
- відстань між пов'язаними елементами;
- внутрішні відступи компонентів.

---

# 14. Breakpoints: коли змінювати компонування

Breakpoint — це точка, у якій змінюється набір CSS-правил.

Важливо визначати breakpoint на основі потреб компонента, а не тільки назви пристрою.

## 14.1. Приклади змін

Breakpoint може бути потрібний, коли:

- навігація перестає поміщатися;
- картки стають надто вузькими;
- текстові колонки важко читати;
- кнопки починають перекриватися;
- бічна панель займає забагато простору;
- таблиця втрачає читабельність.

## 14.2. Приклад

    .profile-layout {
      display: grid;
      grid-template-columns: minmax(0, 1fr);
      gap: 1.5rem;
    }

    @media (min-width: 50rem) {
      .profile-layout {
        grid-template-columns: 16rem minmax(0, 1fr);
      }
    }

У вузькому варіанті профіль і основний вміст розташовані один під одним.

У широкому варіанті вони розміщуються в окремих колонках.

## 14.3. Не використовуй надто багато breakpoint

Якщо кожна невелика зміна ширини вимагає нового media query, можливо, базове компонування недостатньо гнучке.

Спочатку перевір:

- Flexbox;
- CSS Grid;
- відносні одиниці;
- `minmax()`;
- `clamp()`;
- `max-width`;
- Container Queries.

Додавай breakpoint тоді, коли потрібно змінити структуру або поведінку, а не просто компенсувати жорсткі розміри.

# 15. Перевірка інтерфейсу на різних пристроях

Не обмежуйся перевіркою на одному смартфоні та одному моніторі.

Потрібно протестувати різні розміри viewport і різні умови взаємодії.

## 15.1. Що перевіряти на мобільному екрані

- чи немає горизонтального переповнення сторінки;
- чи поміщається логотип;
- чи зручна навігація;
- чи можна натиснути на кнопки;
- чи читабельні заголовки;
- чи не обрізаються поля форм;
- чи зрозуміла послідовність контенту;
- чи не перекриває закріплена панель важливий вміст;
- чи доступні всі необхідні функції.

## 15.2. Що перевіряти на настільному екрані

- чи не розтягується текст на надто довгі рядки;
- чи не виглядає контент розрідженим;
- чи правильно використовуються колонки;
- чи зберігається візуальна ієрархія;
- чи зручні таблиці;
- чи не надто далеко розташовані важливі елементи;
- чи працюють hover-стани;
- чи всі дії доступні з клавіатури.

## 15.3. Що перевіряти на обох типах екранів

- читабельність;
- контраст;
- видимий фокус;
- правильний порядок заголовків;
- доступність посилань;
- повідомлення про помилки;
- логічну структуру;
- однакову доступність основних функцій.

## 15.4. Тестування проміжних ширин

Особливу увагу приділяй проміжним розмірам.

Наприклад, якщо мобільний варіант має одну колонку, а настільний — три, перевір ширину, на якій три колонки ще не поміщаються, а дві вже могли б працювати.

Інтерфейс повинен бути зручним не тільки на заздалегідь визначених breakpoint, а й між ними.

# 16. Типові помилки Mobile vs Desktop

## 16.1. Просто зменшити настільний інтерфейс

Проблема:

- елементи стають надто малими;
- текст важко читати;
- кнопки важко натискати;
- навігація перевантажена.

Рішення:

- переосмислити структуру;
- змінити компонування;
- визначити пріоритети контенту;
- передбачити інший спосіб взаємодії.

## 16.2. Приховувати функції на мобільному

Проблема: користувач смартфона не може виконати завдання, доступне на комп'ютері.

Рішення:

- зберігати доступ до основних функцій;
- за потреби переміщувати їх в інші місця;
- використовувати компактні панелі або меню;
- не приховувати важливі дії без альтернативи.

## 16.3. Орієнтуватися тільки на ширину

Проблема: мобільний інтерфейс передбачає лише дотик, а настільний — лише мишу.

Рішення:

- враховувати можливості пристроїв введення;
- підтримувати клавіатуру;
- не залежати виключно від hover;
- перевіряти різні способи взаємодії.

## 16.4. Надто широкі текстові блоки

Проблема: на великому моніторі рядки тексту стають занадто довгими.

Рішення:

    .content {
      width: 100%;
      max-width: 72rem;
      margin-inline: auto;
    }

Для звичайного тексту часто потрібне ще вужче обмеження ширини, ніж для всієї сторінки.

## 16.5. Різний зміст на різних пристроях

Проблема: мобільна версія втрачає важливу інформацію.

Рішення:

- визначити, чи справді інформація другорядна;
- перемістити її нижче;
- показувати її в розгортуваному блоці;
- забезпечити альтернативний доступ.

## 16.6. Ігнорування орієнтації

Проблема: компонент працює у вертикальній орієнтації, але ламається в горизонтальній.

Рішення:

- перевіряти різні пропорції viewport;
- не прив'язуватися лише до назви пристрою;
- використовувати гнучкі розміри;
- перевіряти компонування за реальним вмістом.

# 17. Практичний алгоритм Mobile vs Desktop

Використовуй цей алгоритм під час проєктування сторінки або застосунку.

## Крок 1. Визнач основне завдання

З'ясуй, що користувач повинен зробити.

Наприклад:

- знайти курс;
- прочитати статтю;
- заповнити форму;
- переглянути розклад;
- купити товар;
- відредагувати дані.

## Крок 2. Визнач пріоритети контенту

Запиши, що потрібно показувати відразу, а що можна перемістити нижче або розмістити в додатковій панелі.

## Крок 3. Створи базове компонування

Вибери Mobile-first або Desktop-first відповідно до типу продукту та основного сценарію використання.

## Крок 4. Визнач структуру для широкого екрана

Продумай:

- кількість колонок;
- ширину контейнера;
- навігацію;
- бічні панелі;
- розташування дій;
- взаємозв'язок компонентів.

## Крок 5. Визнач структуру для вузького екрана

Виріши:

- які блоки повинні перейти в одну колонку;
- які панелі потрібно перемістити;
- як зміниться навігація;
- як розташувати кнопки;
- як показати складні дані.

## Крок 6. Реалізуй адаптивність

Використовуй гнучкі розміри, Flexbox, Grid, Media Queries та Container Queries.

## Крок 7. Перевір взаємодію

Протестуй сенсорні області, клавіатурну навігацію, фокус, відкриття меню та поведінку форм.

## Крок 8. Перевір вміст

Використовуй реальні тексти, довгі назви, зображення різних пропорцій і різну кількість елементів.

## Крок 9. Перевір проміжні ширини

Не обмежуйся двома крайніми варіантами.

## Крок 10. Переконайся, що завдання можна виконати

Користувач повинен мати змогу виконати основні завдання незалежно від того, чи користується він смартфоном, планшетом або комп'ютером.

# 18. Практичний мініпроєкт: Mobile vs Desktop

Мета — створити сторінку навчальної платформи з адаптивним компонуванням.

## Вимоги

Сторінка повинна містити:

- логотип;
- навігацію;
- заголовок;
- короткий опис;
- сітку курсів;
- картки курсів;
- кнопки переходу;
- блок додаткової інформації.

### Desktop

- горизонтальна навігація;
- обмежена ширина основного контенту;
- сітка з кількох колонок;
- картки з узгодженими відступами;
- достатній простір між секціями.

### Mobile

- компактна навігація;
- одна або дві колонки залежно від вмісту;
- читабельні заголовки;
- зручні кнопки;
- вертикальна послідовність блоків;
- відсутність горизонтального переповнення сторінки.

## Структура файлів

    mobile-vs-desktop/
    ├── index.html
    ├── styles.css
    └── README.md

## Етапи виконання

1. Створи HTML-структуру сторінки.
2. Визнач основні завдання користувача.
3. Розстав пріоритети контенту.
4. Створи базове компонування.
5. Реалізуй сітку карток через CSS Grid.
6. Додай адаптивну навігацію.
7. Налаштуй типографіку та відступи.

# 20. Що потрібно запам'ятати

✔ Mobile-first означає починати з вузького екрана та поступово розширювати інтерфейс.

✔ Desktop-first може бути доречним для складних робочих середовищ, орієнтованих на комп'ютери.

✔ Responsive Design використовує гнучке компонування, яке пристосовується до доступного простору.

✔ Adaptive Design може передбачати окремі варіанти структури для різних умов.

✔ Мобільний інтерфейс не повинен бути просто зменшеною копією настільного.

✔ Навігація, картки, форми та таблиці можуть потребувати різних адаптивних рішень.

✔ Content Priority допомагає визначити, яка інформація повинна бути найпомітнішою.

✔ Progressive Disclosure дозволяє показувати додаткову інформацію тоді, коли вона потрібна.

✔ Сенсорна взаємодія потребує зручних областей натискання.

✔ Функціональність не повинна залежати виключно від наведення курсора.

✔ Breakpoint потрібно визначати на основі вмісту та компонування, а не тільки популярних розмірів пристроїв.

✔ Адаптивний інтерфейс потрібно перевіряти на проміжних ширинах і з реальним вмістом.

✔ Основні функції та важлива інформація повинні залишатися доступними на різних пристроях.

✔ Хороший адаптивний дизайн зберігає цілісність продукту, але дозволяє інтерфейсу змінюватися відповідно до умов використання.

# 21. Головна ідея

**Mobile vs Desktop — це не вибір між двома розмірами одного макета. Це проєктування єдиного користувацького досвіду, який залишається зручним за різних умов використання.**

Працюй послідовно:

    Завдання користувача
            ↓
    Пріоритети контенту
            ↓
    Базове компонування
            ↓
    Mobile та Desktop варіанти
            ↓
    Адаптивна навігація й компоненти
            ↓
    Взаємодія та доступність
            ↓
    Тестування різних ширин
            ↓
    Перевірка основних сценаріїв

Спочатку визнач, що користувач повинен зробити. Потім організуй інформацію так, щоб вона залишалася зрозумілою на вузькому екрані й ефективно використовувала простір на широкому.

Мета адаптивного дизайну — не зробити всі екрани однаковими, а забезпечити однаково якісний доступ до потрібного змісту та функцій.
