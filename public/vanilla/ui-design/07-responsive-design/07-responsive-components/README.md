# 07. Responsive Components — Адаптивні компоненти

Responsive Components (адаптивні компоненти) — це компоненти інтерфейсу, які змінюють своє компонування, розміри або спосіб взаємодії залежно від доступного простору, контексту використання та потреб користувача.

Компонент може виглядати по-різному на смартфоні, планшеті та комп'ютері, але його призначення, зміст і основна функціональність повинні залишатися зрозумілими.

Наприклад, картка курсу на великому екрані може містити зображення ліворуч, а текст праворуч. На вузькому екрані зображення може розташовуватися над текстом. При цьому назва курсу, опис і кнопка переходу залишаються доступними.

✔ Responsive Component — компонент, що адаптується до доступного простору.

✔ Component Layout — компонування внутрішніх елементів компонента.

✔ Component Variants — варіанти компонента для різних сценаріїв.

✔ Container Queries — адаптація компонента залежно від розміру його контейнера.

✔ Media Queries — адаптація стилів залежно від характеристик viewport або пристрою.

✔ Intrinsic Sizing — визначення розмірів на основі вмісту та доступного простору.

✔ Flexible Components — компоненти, які можуть розширюватися, стискатися або переносити вміст.

✔ Responsive Images — зображення, які адаптуються до розміру контейнера та роздільної здатності.

✔ Content Priority — визначення важливості інформації всередині компонента.

✔ Component Reusability — можливість повторно використовувати компонент у різних частинах інтерфейсу.

# 1. Що таке Responsive Components

## 1.1. Основна ідея

У сучасному вебдизайні компонент — це окремий елемент інтерфейсу, який має певну структуру, вміст і поведінку.

Приклади компонентів:

- кнопка;
- картка товару;
- картка курсу;
- форма входу;
- пошуковий рядок;
- блок профілю користувача;
- таблиця;
- навігаційна панель;
- модальне вікно;
- список новин.

Адаптивний компонент пристосовується до умов, у яких він використовується.

Наприклад, одна картка може розташовуватися:
- у вузькому стовпці мобільного інтерфейсу;
- у сітці з двох карток на планшеті;
- у сітці з трьох або чотирьох карток на широкому екрані.

При цьому сам компонент не обов'язково повинен знати, який саме пристрій використовує людина. Часто достатньо визначити, скільки простору він отримує від свого контейнера.

## 1.2. Responsive Layout і Responsive Components

Ці поняття пов'язані, але мають різні завдання.

**Responsive Layout** — адаптація загального компонування сторінки.

Наприклад:
- зміна кількості колонок;
- зміна ширини основного контейнера;
- зміна відстаней між секціями;
- зміна розташування основних блоків.

**Responsive Components** — адаптація окремих елементів інтерфейсу.

Наприклад:
- картка змінює розташування зображення;
- кнопки переносяться на наступний рядок;
- форма переходить із двох колонок в одну;
- панель дій стає вертикальною;
- таблиця отримує горизонтальне прокручування.

Приклад загальної сторінки:

    Desktop:
    ┌─────────────────────────────────────────┐
    │ Header                                  │
    ├─────────────────────────────────────────┤
    │ Sidebar │ Main content                  │
    │         │ ┌──────────┐ ┌──────────┐      │
    │         │ │ Card 1   │ │ Card 2   │      │
    │         │ └──────────┘ └──────────┘      │
    └─────────────────────────────────────────┘

    Mobile:
    ┌───────────────────┐
    │ Header            │
    ├───────────────────┤
    │ Main content      │
    │ ┌───────────────┐ │
    │ │ Card 1        │ │
    │ └───────────────┘ │
    │ ┌───────────────┐ │
    │ │ Card 2        │ │
    │ └───────────────┘ │
    └───────────────────┘

У цьому прикладі адаптується як загальне компонування, так і компоненти всередині сторінки.

## 1.3. Чому не достатньо просто зменшити компонент

Зменшення розмірів не завжди створює зручний інтерфейс.

Якщо зменшити картку без зміни її структури, можуть виникнути проблеми:

- текст стає занадто вузьким;
- кнопки не поміщаються;
- зображення займає забагато місця;
- заголовок переноситься на багато рядків;
- важливі дії стають малими;
- вміст втрачає візуальну ієрархію.

Тому адаптивний компонент повинен не лише змінювати розмір, а й за потреби змінювати внутрішню структуру.

**Головний принцип: компонент повинен залишатися зручним у доступному просторі, а не просто вміщуватися в нього.**

# 2. Основні підходи до адаптивності компонентів

## 2.1. Fluid Components — гнучкі компоненти

Fluid Component використовує доступний простір без жорстко заданої ширини.

Наприклад:

    .card {
      width: 100%;
      max-width: 24rem;
    }

Така картка може займати всю доступну ширину, але не розширюється більше за `24rem`.

Інший приклад:

    .search-field {
      width: 100%;
      min-width: 0;
    }

`width: 100%` дозволяє полю займати ширину контейнера.

`min-width: 0` особливо корисний для елементів усередині Flexbox і Grid, оскільки стандартний мінімальний розмір деяких елементів може перешкоджати їх стисканню.

## 2.2. Intrinsic Components — компоненти на основі вмісту

Intrinsic Sizing означає, що розмір компонента залежить від його вмісту та правил компонування.

Наприклад, кнопка може збільшуватися відповідно до довжини тексту.

    .button {
      padding: 0.75rem 1.25rem;
      width: fit-content;
      max-width: 100%;
    }

Проте `width: fit-content` не завжди підходить для кожного елемента.

Для довгого тексту потрібно передбачити перенесення:

    .button {
      white-space: normal;
      overflow-wrap: anywhere;
    }

Використовуй Intrinsic Sizing там, де компонент повинен природно пристосовуватися до вмісту.

## 2.3. Adaptive Variants — адаптивні варіанти

Іноді недостатньо змінити лише ширину або відступи.

Потрібно створити різні варіанти одного компонента.

Наприклад, картка профілю:

    Desktop:
    ┌────────────────────────────────┐
    │ [Avatar]  Name                 │
    │           Description          │
    │           [View profile]       │
    └────────────────────────────────┘

    Mobile:
    ┌───────────────────┐
    │      [Avatar]     │
    │        Name       │
    │     Description  │
    │   [View profile]  │
    └───────────────────┘

Це може бути один компонент із різними CSS-правилами, а не два окремі компоненти.

Адаптивні варіанти доцільні, коли змінюється:
- напрямок розташування;
- порядок елементів;
- кількість видимих деталей;
- спосіб взаємодії;
- розміщення кнопок;
- структура вмісту.

Не створюй окремий варіант для кожної ширини екрана. Визначай лише ті зміни, які справді потрібні.

# 3. Container Queries — адаптація за розміром контейнера

Container Queries дозволяють змінювати стилі компонента залежно від розміру його контейнера, а не лише від ширини всього viewport.

Це особливо корисно для повторно використовуваних компонентів.

Наприклад, картка курсу може відображатися в горизонтальному вигляді у широкій секції, але вертикально — у вузькій бічній панелі. Ширина браузера при цьому може залишатися однаковою.

## 3.1. Media Queries і Container Queries

**Media Query** перевіряє характеристики viewport або пристрою.

**Container Query** перевіряє розмір контейнера, який оголошено як контейнер для відповідних запитів.

Приклад Media Query:

    @media (min-width: 768px) {
      .card {
        display: grid;
        grid-template-columns: 1fr 2fr;
      }
    }

Такий стиль застосовується, коли ширина viewport досягає заданого значення.

Приклад Container Query:

    .card-container {
      container-type: inline-size;
    }

    .card {
      display: flex;
      flex-direction: column;
      gap: 1rem;
    }

    @container (min-width: 32rem) {
      .card {
        flex-direction: row;
        align-items: center;
      }
    }

Тут компонування картки змінюється, коли її контейнер стає достатньо широким.

## 3.2. Коли використовувати Container Queries

Container Queries корисні, коли компонент:
- повторно використовується в різних секціях;
- може розміщуватися в бічній панелі або основному вмісті;
- має різні варіанти компонування залежно від доступної ширини;
- не повинен залежати від загального розміру вікна браузера.

Приклади:

- картка товару;
- картка курсу;
- блок профілю;
- панель статистики;
- віджет календаря;
- картка новини;
- інформаційний блок.

## 3.3. Важливі особливості

Контейнер потрібно явно оголосити:

    .component-container {
      container-type: inline-size;
    }

Після цього дочірні елементи можуть реагувати на ширину цього контейнера через `@container`.

Не кожен елемент потрібно робити контейнером. Використовуй Container Queries там, де компонент справді повинен реагувати на розмір батьківської області.

# 4. Адаптивні картки (Responsive Cards)

Картки — один із найпоширеніших типів компонентів.

Вони використовуються для:
- товарів;
- курсів;
- новин;
- профілів;
- статей;
- подій;
- послуг.

## 4.1. Типова структура картки

Картка курсу може містити:

    ┌──────────────────────────────┐
    │          Image               │
    ├──────────────────────────────┤
    │ Назва курсу                  │
    │ Короткий опис                │
    │ Тривалість                   │
    │                              │
    │ [Докладніше]                 │
    └──────────────────────────────┘

Основні елементи:

- зображення;
- заголовок;
- опис;
- метадані;
- основна дія.

На мобільному екрані важливо зберегти читабельність тексту та доступність кнопки.

## 4.2. HTML картки

    <article class="course-card">
      <img
        class="course-card__image"
        src="/images/course.jpg"
        alt="Студент працює за ноутбуком"
      />

      <div class="course-card__content">
        <h2 class="course-card__title">
          Основи веброзробки
        </h2>

        <p class="course-card__description">
          Вивчення HTML, CSS та JavaScript
          для створення вебсторінок.
        </p>

        <a
          class="course-card__link"
          href="/courses/web-development"
        >
          Докладніше
        </a>
      </div>
    </article>

## 4.3. Базові стилі

    .course-card {
      display: flex;
      flex-direction: column;
      min-width: 0;
      overflow: hidden;
      border: 1px solid #ddd;
      border-radius: 0.75rem;
      background: white;
    }

    .course-card__image {
      display: block;
      width: 100%;
      aspect-ratio: 16 / 9;
      object-fit: cover;
    }

    .course-card__content {
      display: flex;
      flex-direction: column;
      align-items: flex-start;
      gap: 0.75rem;
      padding: 1rem;
      min-width: 0;
    }

    .course-card__title {
      margin: 0;
      overflow-wrap: anywhere;
    }

    .course-card__description {
      margin: 0;
      line-height: 1.6;
    }

    .course-card__link {
      display: inline-flex;
      align-items: center;
      justify-content: center;
      min-height: 44px;
      padding: 0.5rem 0.75rem;
    }

## 4.4. Горизонтальний варіант для широкого контейнера

    .course-card-container {
      container-type: inline-size;
    }

    @container (min-width: 36rem) {
      .course-card {
        display: grid;
        grid-template-columns: minmax(10rem, 1fr) 2fr;
        align-items: stretch;
      }

      .course-card__image {
        height: 100%;
        min-height: 12rem;
        aspect-ratio: auto;
      }

      .course-card__content {
        padding: 1.5rem;
      }
    }

У широкому контейнері картка стає горизонтальною.

У вузькому контейнері вона залишається вертикальною.

**Важливо:** `.course-card` повинна бути дочірнім елементом `.course-card-container`, інакше цей конкретний Container Query не матиме потрібного контейнера для перевірки ширини.

## 4.5. Адаптивна сітка карток

Адаптивність окремої картки та адаптивність сітки карток — різні завдання.

Сітка визначає, скільки карток розташовується в рядку.

    .course-grid {
      display: grid;
      grid-template-columns: repeat(
        auto-fit,
        minmax(min(100%, 16rem), 1fr)
      );
      gap: 1.5rem;
    }

Цей підхід дозволяє автоматично розміщувати доступну кількість колонок залежно від ширини контейнера.

Картка при цьому може додатково адаптувати власне внутрішнє компонування.

# 5. Адаптивні кнопки (Responsive Buttons)

Кнопка повинна залишатися зрозумілою та зручною для взаємодії на будь-якому екрані.

## 5.1. Типові проблеми

- текст не поміщається;
- кнопка виходить за межі контейнера;
- кнопки в рядку стискаються;
- кнопка має надто малу область натискання;
- на мобільному екрані кнопки розташовані занадто близько;
- довгий текст переноситься непередбачувано.

## 5.2. Гнучка кнопка

    .button {
      display: inline-flex;
      align-items: center;
      justify-content: center;
      gap: 0.5rem;
      max-width: 100%;
      min-height: 44px;
      padding: 0.75rem 1rem;
      border: 0;
      border-radius: 0.5rem;
      font: inherit;
      text-align: center;
      cursor: pointer;
    }

`inline-flex` дозволяє вирівнювати текст та іконку.

`max-width: 100%` обмежує ширину кнопки доступною областю, якщо контекст дозволяє це обмеження.

`min-height` допомагає створити достатню область натискання.

## 5.3. Кнопки в групі

На широкому екрані дві кнопки можуть стояти поруч.

    .button-group {
      display: flex;
      flex-wrap: wrap;
      gap: 0.75rem;
    }

На вузькому екрані можна розташувати їх вертикально:

    @media (max-width: 30rem) {
      .button-group {
        flex-direction: column;
        align-items: stretch;
      }

      .button-group .button {
        width: 100%;
      }
    }

Але не всі кнопки потрібно автоматично робити повноширинними. Для коротких другорядних дій це може створювати зайву візуальну вагу.

## 5.4. Ієрархія кнопок

Якщо компонент містить кілька кнопок, визнач їхні пріоритети:

- Primary — основна дія;
- Secondary — додаткова дія;
- Tertiary — менш помітна дія.

На вузькому екрані важливо не просто змінити розмір кнопок, а зберегти зрозумілу ієрархію.

# 6. Адаптивні форми (Responsive Forms)

Форми можуть містити:
- поля введення;
- підписи;
- підказки;
- повідомлення про помилки;
- кнопки надсилання;
- групи пов'язаних полів.

На широкому екрані деякі поля можуть розташовуватися у дві колонки. На вузькому — переходити в одну.

## 6.1. HTML форми

    <form class="registration-form">
      <div class="form-grid">
        <div class="form-field">
          <label for="first-name">Ім'я</label>
          <input
            id="first-name"
            name="firstName"
            autocomplete="given-name"
            required
          />
        </div>

        <div class="form-field">
          <label for="last-name">Прізвище</label>
          <input
            id="last-name"
            name="lastName"
            autocomplete="family-name"
            required
          />
        </div>

        <div class="form-field">
          <label for="email">Електронна пошта</label>
          <input
            id="email"
            name="email"
            type="email"
            autocomplete="email"
            required
          />
        </div>
      </div>

      <button class="button" type="submit">
        Зареєструватися
      </button>
    </form>

## 6.2. Адаптивна сітка полів

    .registration-form {
      width: 100%;
      max-width: 48rem;
    }

    .form-grid {
      display: grid;
      grid-template-columns: repeat(2, minmax(0, 1fr));
      gap: 1.25rem;
    }

    .form-field {
      display: flex;
      flex-direction: column;
      gap: 0.5rem;
      min-width: 0;
    }

    .form-field input {
      width: 100%;
      min-width: 0;
      padding: 0.75rem;
      font: inherit;
    }

    @media (max-width: 40rem) {
      .form-grid {
        grid-template-columns: 1fr;
      }
    }

## 6.3. Чому форми потребують особливої уваги

Під час адаптації форм потрібно перевірити:

- чи повністю видно підписи;
- чи не обрізаються довгі значення;
- чи можна натиснути на поле пальцем;
- чи помітний фокус;
- чи зрозумілі повідомлення про помилки;
- чи не зникають важливі підказки;
- чи доступна кнопка надсилання;
- чи не стає форма надто довгою та незручною.

Не приховуй підписи полів лише для економії простору, якщо через це користувач може втратити розуміння призначення поля.

# 7. Адаптивні таблиці (Responsive Tables)

Таблиці особливо складно адаптувати, тому що їхні колонки часто мають взаємозалежну ширину.

Приклади:
- розклад занять;
- список студентів;
- таблиця цін;
- результати оцінювання;
- адміністративні панелі.

## 7.1. Горизонтальне прокручування

Якщо всі колонки важливі, таблицю можна помістити в контейнер із горизонтальним прокручуванням.

HTML:

    <div
      class="table-wrapper"
      role="region"
      aria-label="Таблиця оцінок"
      tabindex="0"
    >
      <table>
        <thead>
          <tr>
            <th scope="col">Студент</th>
            <th scope="col">Математика</th>
            <th scope="col">Інформатика</th>
            <th scope="col">Англійська</th>
          </tr>
        </thead>

        <tbody>
          <tr>
            <th scope="row">Олена</th>
            <td>10</td>
            <td>12</td>
            <td>11</td>
          </tr>
        </tbody>
      </table>
    </div>

CSS:

    .table-wrapper {
      max-width: 100%;
      overflow-x: auto;
    }

    .table-wrapper table {
      width: 100%;
      min-width: 36rem;
      border-collapse: collapse;
    }

    .table-wrapper th,
    .table-wrapper td {
      padding: 0.75rem;
      border: 1px solid #ddd;
      text-align: left;
    }

Таблиця зберігає структуру, а користувач може прокручувати її по горизонталі.

`tabindex="0"` дозволяє сфокусувати контейнер клавіатурою, якщо потрібна доступна прокручувана область. Перевір таку взаємодію в цільових браузерах і допоміжних технологіях.

## 7.2. Альтернативні підходи

Залежно від завдання можна:

- залишити горизонтальне прокручування;
- приховати другорядні колонки, якщо це не позбавляє користувача важливих даних;
- дозволити вибір видимих колонок;
- перетворити кожний рядок на окрему картку;
- показувати деталі після вибору рядка.

Не перетворюй таблицю на картки лише тому, що екран вузький. Спочатку перевір, чи не стане складніше порівнювати значення між рядками.

# 8. Адаптивні зображення всередині компонентів

Зображення можуть мати різні пропорції та розміри. Якщо не контролювати їхню поведінку, компонент може втратити правильні пропорції або отримати несподівано велику висоту.

## 8.1. Зображення, яке заповнює контейнер

    .card-image {
      display: block;
      width: 100%;
      aspect-ratio: 16 / 9;
      object-fit: cover;
    }

`aspect-ratio` задає співвідношення сторін.

`object-fit: cover` заповнює область, зберігаючи пропорції зображення, але може обрізати його краї.

Це підходить для карток товарів, курсів і новин, коли важливо зберегти однакову форму зображень.

## 8.2. Зображення без обрізання

    .product-image {
      display: block;
      width: 100%;
      height: auto;
      object-fit: contain;
    }

Такий підхід корисний, коли важливо показати зображення повністю, наприклад фотографію товару на білому фоні.

## 8.3. Вибір зображення для різних екранів

Іноді на мобільному екрані краще використовувати інше зображення або інше кадрування.

Для цього HTML підтримує `<picture>` та `srcset`.

    <picture>
      <source
        media="(max-width: 40rem)"
        srcset="/images/course-mobile.jpg"
      />

      <img
        src="/images/course-desktop.jpg"
        alt="Студенти навчаються разом"
      />
    </picture>

Браузер вибирає відповідне джерело за умовами `source`.

Використовуй різні файли, коли це дає реальну перевагу. Не потрібно створювати окрему мобільну версію кожного зображення без причини.

# 9. Адаптивні компоненти за допомогою Flexbox

Flexbox допомагає створювати компоненти, які можуть змінювати напрямок і переносити дочірні елементи.

## 9.1. Компонент із текстом та дією

Наприклад, інформаційне повідомлення:

    .notice {
      display: flex;
      align-items: center;
      justify-content: space-between;
      flex-wrap: wrap;
      gap: 1rem;
      padding: 1rem;
      border: 1px solid #ddd;
      border-radius: 0.75rem;
    }

    .notice__content {
      flex: 1 1 16rem;
      min-width: 0;
    }

    .notice__action {
      flex: 0 0 auto;
    }

На вузькому екрані вміст може переноситися на наступний рядок.

`flex-wrap: wrap` дозволяє елементам переноситися, коли їм бракує місця.

`flex: 1 1 16rem` означає, що елемент може розширюватися та стискатися, використовуючи `16rem` як початкову основу розміру.

## 9.2. Коли використовувати Flexbox

Flexbox підходить для:

- рядка кнопок;
- групи тегів;
- картки з текстом і зображенням;
- рядка профілю;
- панелі дій;
- групи фільтрів;
- навігаційних елементів.

Якщо компонент має складну двовимірну структуру з рядками й колонками, може бути доцільнішим CSS Grid.

---

# 10. Адаптивні компоненти за допомогою CSS Grid

Grid зручний, коли компоненти мають структуру з кількох колонок або потрібно організувати повторювані елементи.

## 10.1. Автоматична сітка

    .stats-grid {
      display: grid;
      grid-template-columns: repeat(
        auto-fit,
        minmax(min(100%, 14rem), 1fr)
      );
      gap: 1rem;
    }

Картки статистики автоматично займають доступний простір.

Наприклад:

    Wide:
    ┌─────────┐ ┌─────────┐ ┌─────────┐
    │ Card 1  │ │ Card 2  │ │ Card 3  │
    └─────────┘ └─────────┘ └─────────┘

    Narrow:
    ┌───────────────────┐
    │ Card 1            │
    └───────────────────┘
    ┌───────────────────┐
    │ Card 2            │
    └───────────────────┘
    ┌───────────────────┐
    │ Card 3            │
    └───────────────────┘

## 10.2. `auto-fit` і `auto-fill`

Обидва значення використовуються для автоматичного створення колонок.

`auto-fit` дозволяє наявним колонкам розширюватися, займаючи доступний простір, коли частина потенційних колонок не використовується.

`auto-fill` зберігає потенційні колонки в сітці, навіть якщо частина з них залишається порожньою.

У більшості простих сіток карток `auto-fit` є зручним початковим вибором, але остаточний варіант залежить від бажаної поведінки компонування.

---

# 11. Адаптивна типографіка всередині компонентів

Текст повинен залишатися читабельним незалежно від ширини компонента.

Проблеми виникають, коли:

- заголовок занадто довгий;
- кнопка містить багато тексту;
- опис займає надто багато рядків;
- слова виходять за межі контейнера;
- текст має недостатню висоту рядка.

## 11.1. Гнучкий заголовок

    .card-title {
      font-size: clamp(1.125rem, 2vw, 1.5rem);
      line-height: 1.3;
      overflow-wrap: anywhere;
    }

`clamp()` обмежує розмір шрифту мінімальним і максимальним значеннями.

Не зменшуй текст настільки, щоб його було важко читати. Адаптивність повинна зберігати читабельність.

## 11.2. Довгі слова та URL

    .card-description {
      overflow-wrap: anywhere;
    }

Це може допомогти, якщо текст містить довгі URL або інші послідовності символів без пробілів.

Проте не застосовуй агресивне перенесення до всіх текстів автоматично. Спочатку перевір, чи справді проблема існує.

## 11.3. Обмеження кількості рядків

Іноді картки в одній сітці повинні мати приблизно однакову висоту тексту.

    .card-description {
      display: -webkit-box;
      -webkit-box-orient: vertical;
      -webkit-line-clamp: 3;
      overflow: hidden;
    }

Цей прийом обмежує видимий опис трьома рядками в браузерах, що підтримують відповідну поведінку.

Не приховуй важливу інформацію без альтернативи. Якщо користувачеві потрібно прочитати повний опис, передбач посилання на деталі або інший спосіб доступу до тексту.

# 12. Responsive Components і дизайн-система

У дизайн-системі компонент повинен мати зрозумілі правила використання.

Адаптивність не означає, що кожен компонент повинен мати десятки незалежних варіантів.

Краще визначити:

- базову структуру;
- допустимі розміри;
- адаптивну поведінку;
- внутрішні відступи;
- правила для довгого тексту;
- поведінку зображень;
- стани взаємодії;
- обмеження використання.

## 12.1. Приклад компонентної специфікації

**Component:** Course Card

**Purpose:** відображення навчального курсу.

**Content:**
- зображення;
- назва;
- короткий опис;
- тривалість;
- посилання на деталі.

**Responsive behavior:**
- вузький контейнер — вертикальне компонування;
- широкий контейнер — горизонтальне компонування;
- довгий заголовок переноситься;
- зображення зберігає визначені пропорції;
- кнопка залишається доступною.

**Accessibility:**
- змістовний альтернативний текст зображення, якщо воно передає інформацію;
- логічний порядок заголовка та посилання;
- видимий фокус;
- достатній контраст.

## 12.2. Компонентні токени

Для узгодженості можна використовувати CSS-змінні:

    :root {
      --space-1: 0.25rem;
      --space-2: 0.5rem;
      --space-3: 0.75rem;
      --space-4: 1rem;
      --space-6: 1.5rem;

      --radius-card: 0.75rem;
      --border-color: #ddd;
      --content-max-width: 72rem;
    }

Потім використовувати їх у компонентах:

    .course-card {
      gap: var(--space-4);
      border: 1px solid var(--border-color);
      border-radius: var(--radius-card);
    }

Перевага такого підходу — єдині правила відступів і стилів у всій системі.

# 13. Адаптивність компонентів і доступність

Адаптивний компонент повинен працювати для різних способів взаємодії, а не лише для різних розмірів екрана.

## 13.1. Сенсорні області

Кнопки, посилання та інші інтерактивні елементи повинні мати достатню область натискання.

    .action-button {
      min-height: 44px;
      padding: 0.75rem 1rem;
    }

Це поширений практичний орієнтир, а не універсальне нормативне значення для кожної ситуації. Для перевірки відповідності потрібно враховувати конкретні критерії WCAG та їхні винятки.

## 13.2. Видимий фокус

    .component a:focus-visible,
    .component button:focus-visible,
    .component input:focus-visible {
      outline: 3px solid #2457c5;
      outline-offset: 3px;
    }

Не прибирай індикатор фокуса без доступної альтернативи.

## 13.3. Контраст

Перевір контраст:

- тексту на фоні;
- підписів;
- меж полів;
- іконок керування;
- станів помилок;
- активних і неактивних елементів.

Адаптивний компонент може змінювати фон або кольори на різних екранах, але не повинен втрачати достатню видимість.

## 13.4. Масштабування тексту

Не розраховуй, що всі користувачі використовуватимуть однаковий розмір шрифту.

Перевір, що компонент не ламається, коли:

- текст збільшується;
- користувач змінює масштаб сторінки;
- назви стають довшими;
- вміст перекладається іншою мовою.

Не задавай фіксовану висоту текстового блока без потреби. Часто краще використовувати `min-height` або дозволити контейнеру збільшуватися.

# 14. Типові помилки під час створення Responsive Components

## 14.1. Фіксована ширина без обмежень

Проблема:

    .card {
      width: 400px;
    }

На вузькому екрані картка може виходити за межі контейнера.

Краще:

    .card {
      width: 100%;
      max-width: 25rem;
    }

## 14.2. Фіксована висота для змінного вмісту

Проблема:

    .card {
      height: 300px;
    }

Якщо текст стає довшим, він може не поміститися.

Краще:

    .card {
      min-height: 18rem;
    }

Навіть `min-height` потрібен не завжди. Якщо висота повинна повністю залежати від вмісту, не задавай її без необхідності.

## 14.3. Ігнорування `min-width: 0`

Проблема: довгий текст або вміст усередині Grid чи Flexbox розширює компонент більше, ніж потрібно.

Рішення:

    .card-content {
      min-width: 0;
    }

За потреби додатково налаштуй перенесення тексту.

## 14.4. Зменшення всіх елементів одночасно

Проблема: мобільна версія виглядає як зменшена копія настільної, а інтерактивні елементи стають незручними.

Рішення:
- переглянути компонування;
- змінити напрямок розташування;
- скоротити другорядні деталі;
- збільшити область натискання;
- зберегти основні дії доступними.

## 14.5. Надмірна кількість media queries

Проблема: компонент має багато окремих правил для майже однакових ширин.

Рішення:
- спочатку використовувати гнучкі розміри;
- використовувати Flexbox і Grid;
- додавати breakpoint лише тоді, коли змінюється потрібна поведінка;
- розглядати Container Queries для незалежних компонентів.

## 14.6. Приховування важливої інформації

Проблема: на мобільному екрані зникають ціна, умови, помилки або інші важливі дані.

Рішення:
- визначити інформаційну ієрархію;
- приховувати лише другорядний вміст;
- перевіряти, чи залишається потрібна інформація доступною;
- за необхідності створювати окремий спосіб перегляду деталей.

## 14.7. Дублювання компонентів без потреби

Проблема: створюються окремі Desktop Card і Mobile Card з однаковим змістом.

Це може призвести до:
- дублювання розмітки;
- різної поведінки компонентів;
- складнішого обслуговування;
- помилок під час оновлення.

Рішення: спочатку перевір, чи можна реалізувати адаптивність одним компонентом за допомогою CSS.

Окремі компоненти виправдані, коли структура або поведінка справді суттєво відрізняється.

# 15. Практичний алгоритм проєктування Responsive Component

## Крок 1. Визнач призначення компонента

Відповідай на запитання:

- Для чого потрібен компонент?
- Хто ним користується?
- Яку основну дію він підтримує?
- Яка інформація є обов'язковою?

## Крок 2. Визнач структуру

Запиши всі елементи компонента.

Наприклад, для картки курсу:

    Course Card
    ├── Image
    ├── Title
    ├── Description
    ├── Duration
    └── Action Link

## Крок 3. Розстав пріоритети

Визнач:
- основний вміст;
- другорядні деталі;
- важливі дії;
- елементи, які можна перемістити;
- інформацію, яку не можна приховувати.

## Крок 4. Створи базовий варіант

Спочатку зроби компонент читабельним у вузькому контейнері.

Використовуй:
- гнучку ширину;
- розумні обмеження;
- відступи;
- природну висоту;
- зрозумілу типографіку.

## Крок 5. Додай гнучке компонування

Використовуй:
- Flexbox для рядків і груп елементів;
- Grid для колонок і сіток;
- `minmax()` для гнучких колонок;
- `gap` для відстаней;
- `min-width: 0` для елементів, які повинні стискатися.

## Крок 6. Визнач точки зміни

Виріши, коли компонент повинен:
- змінювати напрямок;
- переходити в одну колонку;
- змінювати розмір зображення;
- переносити кнопки;
- змінювати розташування деталей.

## Крок 7. Вибери правильний механізм

Використовуй Media Queries, коли компонент залежить від ширини viewport.

Використовуй Container Queries, коли компонент повинен адаптуватися до власного контейнера.

Використовуй гнучкі властивості CSS, якщо окремий breakpoint не потрібен.

## Крок 8. Перевір різний вміст

Протестуй:
- короткі заголовки;
- довгі заголовки;
- відсутність необов'язкового опису;
- великі зображення;
- довгі назви кнопок;
- різну кількість елементів;
- локалізований текст.

## Крок 9. Перевір доступність

Перевір:
- клавіатурний фокус;
- контраст;
- сенсорні області;
- альтернативні тексти зображень;
- порядок читання;
- масштабування тексту.

## Крок 10. Протестуй у реальному інтерфейсі

Компонент може добре виглядати окремо, але погано працювати в реальній секції.

Перевір його:
- у вузькій колонці;
- у широкій колонці;
- у сітці;
- поруч з іншими компонентами;
- у контейнері з обмеженою шириною.

Мета — створити компонент картки курсу, який адаптується до доступного простору.

Структура:

- зображення;
- назва курсу;
- опис;
- тривалість;

Адаптивність:

- вузький контейнер — вертикальна картка;

- логічна структура заголовків;

# 18. Що потрібно запам'ятати

✔ Responsive Components адаптують внутрішню структуру та поведінку компонентів до доступного простору.

✔ Адаптивність компонента та адаптивність сторінки — пов'язані, але різні завдання.

✔ Гнучкі розміри часто допомагають уникнути зайвих breakpoint.

✔ Flexbox підходить для рядків, груп і одновимірного компонування.

✔ Grid підходить для колонок, сіток і двовимірного компонування.

✔ Media Queries реагують на характеристики viewport або пристрою.

✔ Container Queries дозволяють компоненту реагувати на розмір контейнера.

✔ `minmax()`, `min-width: 0`, `max-width: 100%` та `aspect-ratio` допомагають створювати гнучкі компоненти.

✔ Не кожен компонент повинен мати окрему мобільну та настільну версію.

✔ Довгі заголовки, описи та назви кнопок потрібно враховувати під час проєктування.

✔ Адаптивні компоненти повинні зберігати читабельність, доступність і зрозумілу ієрархію.

✔ Таблиці, форми та інтерактивні компоненти потребують особливо уважного тестування.

✔ Дизайн-система повинна визначати не лише зовнішній вигляд компонентів, а й правила їхньої адаптивності.

✔ Найкращий компонент — не той, що однаково виглядає на всіх екранах, а той, що зберігає зручність у різних умовах.

# 19. Головна ідея

**Responsive Components — це проєктування компонентів, які залишаються зрозумілими, функціональними та зручними незалежно від того, скільки простору їм доступно.**

Працюй послідовно:

    Призначення компонента
            ↓
    Структура та вміст
            ↓
    Пріоритети інформації
            ↓
    Гнучке компонування
            ↓
    Media Queries або Container Queries
            ↓
    Адаптація типографіки та зображень
            ↓
    Доступність
            ↓
    Тестування в реальному інтерфейсі

Спочатку визнач, що компонент повинен робити. Потім продумай його структуру та інформаційну ієрархію. І лише після цього вирішуй, як саме він має змінюватися на різних екранах і в різних контейнерах.
