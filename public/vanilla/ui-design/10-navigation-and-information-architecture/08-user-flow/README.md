# 08. User Flow — Потік користувача

## 1. Що таке User Flow

**User Flow (потік користувача)** — це послідовність кроків, які користувач проходить в інтерфейсі, щоб досягти певної мети.

User Flow показує, як користувач переходить від початкової точки до бажаного результату, які дії виконує, які рішення приймає та які екрани бачить.

Наприклад, користувач хоче зареєструватися на освітній платформі:

    Головна сторінка
        ↓
    Натискання «Зареєструватися»
        ↓
    Форма реєстрації
        ↓
    Заповнення полів
        ↓
    Натискання «Створити акаунт»
        ↓
    Перевірка даних
        ↓
    Акаунт створено
        ↓
    Особистий кабінет

Це простий User Flow, який показує шлях від наміру користувача до успішного завершення завдання.

**Головна ідея:** User Flow допомагає спроєктувати не просто окремі екрани, а зрозумілий шлях між ними.

---

## 2. Навіщо потрібен User Flow

User Flow допомагає дизайнеру зрозуміти, як людина буде користуватися продуктом.

Без продуманого потоку користувач може зіткнутися з такими проблемами:

- Не розуміє, з чого почати.
- Не може знайти потрібну функцію.
- Виконує зайві дії.
- Не розуміє, що робити після натискання кнопки.
- Не отримує зрозумілого повідомлення про помилку.
- Не знає, чи успішно завершив завдання.
- Втрачає введені дані під час переходу між екранами.

Продуманий User Flow допомагає:

- ✔ Зменшити кількість зайвих кроків.
- ✔ Зробити інтерфейс передбачуваним.
- ✔ Виявити проблеми до початку розробки.
- ✔ Врахувати помилки та альтернативні сценарії.
- ✔ Покращити користувацький досвід (UX).
- ✔ Узгодити роботу дизайнера, розробника та команди продукту.
- ✔ Підготувати основу для прототипу й тестування.

### Приклад

Поганий сценарій покупки:

    Головна
        ↓
    Каталог
        ↓
    Картка товару
        ↓
    Кошик
        ↓
    Форма реєстрації
        ↓
    Підтвердження email
        ↓
    Повернення до кошика
        ↓
    Оформлення замовлення

Якщо реєстрація не є обов'язковою, такий сценарій може створювати зайві перешкоди.

Кращий сценарій:

    Головна
        ↓
    Каталог
        ↓
    Картка товару
        ↓
    Кошик
        ↓
    Оформлення замовлення
        ↓
    Введення контактних даних
        ↓
    Оплата
        ↓
    Підтвердження замовлення

Реєстрацію можна запропонувати додатково, якщо вона справді корисна користувачу.

**Важливо:** найкоротший User Flow не завжди найкращий. Він має бути простим, але водночас зрозумілим, безпечним і достатнім для виконання завдання.

## 3. User Flow, User Journey та Task Flow

Ці терміни пов'язані між собою, але описують різні аспекти взаємодії з продуктом.

### 3.1. User Flow

**User Flow** показує шлях користувача через інтерфейс для досягнення конкретної мети, включно з можливими розгалуженнями.

Приклад:

    Головна
        ↓
    Вхід до акаунта
        ↓
    Введення email і пароля
        ↓
    Дані правильні?
        ├── Так → Особистий кабінет
        └── Ні → Повідомлення про помилку

User Flow може описувати як простий, так і складний сценарій.

### 3.2. Task Flow

**Task Flow** — послідовність кроків для виконання одного конкретного завдання.

Зазвичай Task Flow описує основний сценарій без великої кількості альтернатив.

Приклад: користувач хоче додати товар до кошика.

    Відкрити каталог
        ↓
    Вибрати товар
        ↓
    Натиснути «Додати до кошика»
        ↓
    Побачити підтвердження

Task Flow відповідає на запитання:

> Які кроки потрібні, щоб виконати це завдання?

### 3.3. User Journey

**User Journey (шлях користувача)** — ширше представлення досвіду людини під час взаємодії з продуктом або сервісом.

Він може охоплювати:

- Дії користувача.
- Його цілі.
- Думки та запитання.
- Емоції.
- Проблеми й перешкоди.
- Точки контакту з продуктом.
- Можливості для покращення досвіду.

Приклад:

    Усвідомлення потреби
        ↓
    Пошук освітньої платформи
        ↓
    Перегляд курсів
        ↓
    Порівняння програм
        ↓
    Реєстрація
        ↓
    Навчання
        ↓
    Оцінювання результату

User Journey може включати не тільки екрани сайту, а й рекламу, електронні листи, підтримку та інші точки контакту.

### 3.4. Порівняння

| Характеристика | Task Flow | User Flow | User Journey |
|---|---|---|---|
| Основний фокус | Одне завдання | Шлях у продукті | Загальний досвід |
| Деталізація | Послідовність кроків | Кроки та розгалуження | Дії, думки, емоції |
| Альтернативні сценарії | Зазвичай мінімум | Часто присутні | Залежать від карти |
| Контекст поза інтерфейсом | Зазвичай ні | Може враховуватися | Часто враховується |
| Приклад | Додати товар | Купити товар | Від потреби до отримання товару |

**Що запам'ятати:**

- Task Flow — як виконати конкретне завдання.
- User Flow — як користувач проходить сценарій у продукті.
- User Journey — як виглядає ширший досвід користувача.

У реальних командах терміни можуть частково перетинатися. Важливіше розуміти мету діаграми, ніж сперечатися про її назву.

## 4. Основні елементи User Flow

User Flow складається з кількох типових елементів.

### 4.1. Start Point — початкова точка

Показує, звідки починається сценарій.

Приклади:

- Головна сторінка.
- Сторінка входу.
- Email із посиланням.
- Push-сповіщення.
- Картка товару.
- Сторінка результатів пошуку.

Приклад:

    [Початок: головна сторінка]
                ↓
        [Вибір курсу]

Початкова точка залежить від сценарію. Не всі користувачі починають шлях із головної сторінки.

### 4.2. Action — дія користувача

Дія — це те, що користувач робить в інтерфейсі.

Приклади:

- Натискає кнопку.
- Вводить текст.
- Обирає фільтр.
- Відкриває меню.
- Завантажує файл.
- Підтверджує замовлення.

Приклад:

    [Каталог курсів]
            ↓
    [Користувач обирає курс]
            ↓
    [Сторінка курсу]

Назви дій краще формулювати конкретно.

Не дуже добре:

    [Взаємодія з інтерфейсом]

Краще:

    [Користувач обирає курс]

### 4.3. Screen / Page — екран або сторінка

Показує, де відбувається дія або який інтерфейс бачить користувач.

Приклади:

- Головна сторінка.
- Форма входу.
- Кошик.
- Сторінка оформлення замовлення.
- Особистий кабінет.

Екран і дія — не одне й те саме.

    [Сторінка входу]
            ↓
    [Користувач вводить пароль]
            ↓
    [Натискання «Увійти»]

Під час створення діаграми можна використовувати окремі блоки для екранів і дій або об'єднувати їх, якщо схема залишається зрозумілою.

### 4.4. Decision Point — точка прийняття рішення

Показує умову, від якої залежить подальший шлях.

Наприклад:

    [Користувач надсилає форму]
                ↓
        ◇ Дані коректні? ◇
           ↙         ↘
         Так           Ні
          ↓             ↓
    [Успіх]       [Помилки форми]

Decision Point особливо важливий для сценаріїв, у яких є:

- Перевірка даних.
- Авторизація.
- Вибір способу оплати.
- Доступність товару.
- Підтвердження дії.
- Різні ролі користувачів.

Питання в точці рішення потрібно формулювати так, щоб відповіді були однозначними.

Наприклад:

    ◇ Email підтверджено? ◇
        ├── Так
        └── Ні

### 4.5. Outcome — результат

Показує, чим завершився сценарій.

Приклади:

- Користувач увійшов до акаунта.
- Замовлення створено.
- Файл завантажено.
- Пароль змінено.
- Форму успішно надіслано.

Приклад:

    [Заповнення форми]
            ↓
    [Надсилання даних]
            ↓
    [Успішна реєстрація]

Не варто завершувати сценарій просто на кнопці «Надіслати». Потрібно визначити, що користувач побачить після виконання дії.

### 4.6. Error State — стан помилки

Показує, що відбувається, якщо щось пішло не так.

Приклад:

    [Форма входу]
          ↓
    [Натискання «Увійти»]
          ↓
    ◇ Дані правильні? ◇
       ├── Так → [Особистий кабінет]
       └── Ні  → [Повідомлення про помилку]
                         ↓
                  [Повторне введення]

Помилка не повинна бути тупиком, якщо користувач може виправити ситуацію.

### 4.7. Connector — з'єднання

Стрілки показують напрямок переходу між елементами.

    [Каталог]
        ↓
    [Картка товару]
        ↓
    [Кошик]

Для розгалужень підписуйте стрілки:

    ◇ Товар доступний? ◇
       ├── Так → [Додати до кошика]
       └── Ні  → [Повідомити про відсутність]

Стрілки мають бути логічними, не перетинатися без потреби та не створювати двозначності.

## 5. Як правильно побудувати User Flow

Розглянемо послідовний процес створення потоку користувача.

### Крок 1. Визнач мету користувача

Спочатку сформулюй, чого людина хоче досягти.

Приклади:

- Зареєструватися на платформі.
- Увійти до акаунта.
- Знайти потрібний курс.
- Купити товар.
- Відновити пароль.
- Записатися на консультацію.

Мета має бути конкретною.

Погано:

    Користувач взаємодіє із сайтом.

Добре:

    Користувач хоче записатися на консультацію.

### Крок 2. Визнач початкову точку

Звідки користувач починає шлях?

Наприклад:

    Початкова точка:
    сторінка послуги

Не припускай автоматично, що всі користувачі приходять на головну сторінку.

Користувач може перейти безпосередньо з пошукової системи, реклами, повідомлення або закладки.

### Крок 3. Опиши основний сценарій

Спочатку побудуй найпростіший логічний шлях до мети.

Наприклад:

    Сторінка послуги
        ↓
    Вибір спеціаліста
        ↓
    Вибір дати
        ↓
    Вибір часу
        ↓
    Введення контактних даних
        ↓
    Підтвердження запису

На цьому етапі не потрібно відразу деталізувати всі можливі помилки.

Спочатку переконайся, що основний сценарій логічний.

### Крок 4. Додай точки прийняття рішень

Визнач, де шлях може змінюватися.

Наприклад:

- Чи доступний вибраний час?
- Чи правильно заповнена форма?
- Чи підтверджений email?
- Чи успішно пройшла оплата?

Приклад:

    [Вибір часу]
          ↓
    ◇ Час доступний? ◇
       ├── Так → [Введення контактів]
       └── Ні  → [Вибір іншого часу]

### Крок 5. Додай альтернативні сценарії

Продумай, що відбувається, коли користувач:

- Вводить неправильні дані.
- Не знаходить потрібний товар.
- Забуває пароль.
- Змінює своє рішення.
- Натискає «Назад».
- Втрачає з'єднання.
- Не може завершити оплату.

Не обов'язково включати кожну можливу технічну ситуацію в одну діаграму. Важливо врахувати ті випадки, які впливають на користувацький досвід.

### Крок 6. Визнач кінцевий результат

Запитай себе:

- Чи зрозуміло користувачу, що завдання виконано?
- Чи отримує він підтвердження?
- Чи знає, що робити далі?
- Чи може повернутися до попереднього кроку, якщо потрібно?

Наприклад:

    [Підтвердження запису]
              ↓
    [Екран успішного запису]
              ↓
    [Інформація про дату й час]

### Крок 7. Перевір кількість кроків

Подивись, чи немає:

- Непотрібних екранів.
- Повторного введення тих самих даних.
- Необов'язкової реєстрації.
- Незрозумілих переходів.
- Кроків без очевидної користі.

Але не видаляй крок лише заради зменшення їх кількості. Наприклад, підтвердження важливої або незворотної дії може бути необхідним.

### Крок 8. Перевір сценарій з погляду користувача

Пройди шлях подумки або за допомогою інтерактивного прототипу.

Уяви, що користувач уперше відкрив продукт і нічого про нього не знає.

Перевір:

- Чи зрозуміло, з чого почати?
- Чи зрозумілі назви кнопок?
- Чи очевидний наступний крок?
- Чи зрозумілі повідомлення про помилки?
- Чи можна виправити помилку?
- Чи видно кінцевий результат?

## 6. Приклад User Flow: реєстрація користувача

Розглянемо реєстрацію на освітній платформі.

### 6.1. Основний сценарій

    [Головна сторінка]
            ↓
    [Натискання «Реєстрація»]
            ↓
    [Форма реєстрації]
            ↓
    [Введення імені, email і пароля]
            ↓
    [Натискання «Створити акаунт»]
            ↓
    ◇ Дані коректні? ◇
       ├── Ні → [Показати помилки]
       │              ↓
       │       [Виправити дані]
       │              ↓
       │       [Повторно надіслати форму]
       │
       └── Так → [Створити акаунт]
                         ↓
                 [Підтвердити email]
                         ↓
                 [Акаунт активовано]
                         ↓
                 [Особистий кабінет]

### 6.2. Що потрібно врахувати в UI

**Форма реєстрації:**

- Чіткі підписи полів.
- Зрозумілі вимоги до пароля.
- Видимий стан кнопки.
- Перевірка введених даних.
- Зрозумілі повідомлення про помилки.
- Збереження введених даних, якщо це безпечно й доречно.

**Після надсилання форми:**

- Повідомлення про успішну реєстрацію або необхідність підтвердити email.
- Інструкція щодо наступного кроку.
- Можливість повторно надіслати лист, якщо це потрібно.
- Захист від повторного створення акаунта з тим самим email.

**Після успішного завершення:**

- Чітке підтвердження.
- Перехід до особистого кабінету або іншої логічної сторінки.
- Відсутність неоднозначності щодо статусу акаунта.

### 6.3. Альтернативний сценарій: email уже використовується

    [Надсилання форми]
            ↓
    ◇ Email вільний? ◇
       ├── Так → [Створити акаунт]
       └── Ні  → [Повідомлення про проблему]
                          ↓
                 [Запропонувати вхід
                  або відновлення доступу]

Повідомлення має допомагати користувачу вирішити проблему, а не просто повідомляти про невдачу.

## 7. Приклад User Flow: вхід до акаунта

### Основний сценарій

    [Сторінка входу]
            ↓
    [Введення email і пароля]
            ↓
    [Натискання «Увійти»]
            ↓
    ◇ Дані правильні? ◇
       ├── Так → [Особистий кабінет]
       └── Ні  → [Повідомлення про помилку]
                         ↓
                  [Повторна спроба]

### Альтернативний сценарій: забутий пароль

    [Сторінка входу]
            ↓
    [Натискання «Забули пароль?»]
            ↓
    [Форма відновлення доступу]
            ↓
    [Введення email]
            ↓
    [Надсилання запиту]
            ↓
    [Повідомлення про наступні дії]

### UX-рекомендації

- Розмісти посилання «Забули пароль?» поруч із полем пароля або кнопкою входу.
- Не змушуй користувача повертатися на головну сторінку для відновлення доступу.
- Передбач зрозумілий шлях після невдалої спроби.
- Не видаляй введений email без потреби.
- Після відновлення доступу поясни, як повернутися до входу.

---

## 8. Приклад User Flow: покупка товару

Покупка товару зазвичай має більше розгалужень, ніж проста форма.

### Основний сценарій

    [Каталог товарів]
            ↓
    [Вибір товару]
            ↓
    [Сторінка товару]
            ↓
    [Додавання до кошика]
            ↓
    [Кошик]
            ↓
    [Оформлення замовлення]
            ↓
    [Введення контактних даних]
            ↓
    [Вибір доставки]
            ↓
    [Вибір способу оплати]
            ↓
    [Підтвердження замовлення]
            ↓
    [Результат оплати]
            ↓
    [Підтвердження замовлення]

### Можливі альтернативні сценарії

**Товар недоступний:**

    [Сторінка товару]
            ↓
    ◇ Товар доступний? ◇
       ├── Так → [Додати до кошика]
       └── Ні  → [Повідомлення про відсутність]
                          ↓
                  [Інші товари або сповіщення]

**Помилка оплати:**

    [Підтвердження замовлення]
                ↓
           [Оплата]
                ↓
        ◇ Оплата успішна? ◇
           ├── Так → [Замовлення підтверджено]
           └── Ні  → [Повідомлення про помилку]
                              ↓
                      [Повторити або змінити
                       спосіб оплати]

У цьому сценарії потрібно врахувати, що помилка оплати не завжди означає, що платіж точно не пройшов. Стан замовлення та платежу має визначатися системою, а інтерфейс повинен повідомляти користувачу достовірну інформацію.

### Що перевірити

- Чи можна переглянути склад кошика?
- Чи можна змінити кількість товарів?
- Чи зрозуміла повна вартість?
- Чи показано вартість доставки?
- Чи зрозумілий статус замовлення?
- Чи є зрозумілий шлях після помилки?
- Чи захищений користувач від випадкового повторного замовлення?

---

## 9. Основний, альтернативний та аварійний сценарії

Під час створення User Flow корисно розрізняти різні типи сценаріїв.

### 9.1. Happy Path — основний успішний сценарій

**Happy Path** — це шлях, у якому все працює очікувано.

Приклад:

    [Форма]
        ↓
    [Коректні дані]
        ↓
    [Успішне надсилання]
        ↓
    [Підтвердження]

Це найпростіший шлях до мети.

Його потрібно спроєктувати першим, але не можна обмежуватися тільки ним.

### 9.2. Alternative Flow — альтернативний сценарій

Альтернативний сценарій описує інший допустимий шлях до мети.

Наприклад, користувач може увійти за допомогою пароля або через доступний сторонній сервіс автентифікації.

    [Сторінка входу]
            ↓
       ◇ Спосіб входу ◇
         ↙          ↘
    [Пароль]     [Інший спосіб]
         ↘          ↙
       [Успішний вхід]

Альтернативний сценарій не обов'язково є помилковим. Це може бути повноцінний варіант використання продукту.

### 9.3. Error Flow — сценарій помилки

Описує шлях, який виникає через неправильні дані, недоступність ресурсу або іншу проблему.

    [Надсилання форми]
            ↓
    [Виявлено помилку]
            ↓
    [Пояснення проблеми]
            ↓
    [Виправлення]
            ↓
    [Повторна спроба]

Хороший Error Flow допомагає користувачу повернутися до основного сценарію.

### 9.4. Edge Cases — граничні випадки

Граничні випадки виникають за незвичних, але можливих умов.

Наприклад:

- Список результатів порожній.
- Назва товару дуже довга.
- Користувач двічі натиснув кнопку.
- Сесія завершилася під час заповнення форми.
- Мережа зникла під час надсилання.
- Файл перевищує допустимий розмір.
- Вибраний час щойно зайняв інший користувач.

Не всі Edge Cases потрібно показувати як окремі великі гілки діаграми. Їх можна описати в примітках або в окремих сценаріях.

**Правило:** спочатку спроєктуй Happy Path, потім найважливіші альтернативи та помилки.

---

## 10. User Flow та стани інтерфейсу

User Flow описує шлях між діями й результатами, але кожен екран може мати кілька станів.

Наприклад, форма може бути:

- Default — початковий стан.
- Focus — поле у фокусі.
- Filled — поле заповнене.
- Error — є помилка.
- Loading — дані надсилаються.
- Success — операція завершилася успішно.
- Disabled — дія тимчасово недоступна.

Приклад:

    [Форма]
        ↓
    [Заповнення]
        ↓
    [Надсилання]
        ↓
    ◇ Результат? ◇
       ├── Успіх → [Success State]
       ├── Помилка → [Error State]
       └── Очікування → [Loading State]

### Чому це важливо

Якщо User Flow передбачає надсилання форми, дизайнер має визначити не тільки наступну сторінку, а й те, що користувач побачить під час обробки.

Наприклад:

1. Користувач натискає кнопку.
2. Кнопка переходить у стан завантаження.
3. Повторне надсилання тимчасово блокується.
4. Після відповіді системи показується успіх або помилка.

Ці стани допомагають зробити потік передбачуваним і запобігти випадковим повторним діям.

---

## 11. User Flow та інформаційна архітектура

**Information Architecture (IA)** визначає, як організований і структурований контент продукту.

User Flow визначає, як користувач проходить шлях через цю структуру для виконання завдання.

Наприклад, інформаційна архітектура освітньої платформи:

    Головна
    ├── Курси
    │   ├── Категорії
    │   └── Сторінка курсу
    ├── Про платформу
    ├── Допомога
    └── Особистий кабінет

User Flow вибору курсу:

    [Головна]
        ↓
    [Курси]
        ↓
    [Вибір категорії]
        ↓
    [Список курсів]
        ↓
    [Сторінка курсу]
        ↓
    [Запис на курс]

Інформаційна архітектура відповідає на запитання:

> Як організований контент і де він розташований?

User Flow відповідає на запитання:

> Як користувач рухається між частинами продукту, щоб досягти мети?

Обидва інструменти доповнюють один одного.

---

## 12. User Flow та навігація

Навігація допомагає користувачу зрозуміти, де він перебуває та куди може перейти.

User Flow допомагає перевірити, чи достатньо навігаційних можливостей для виконання завдання.

Під час проєктування перевіряй:

- Чи є очевидний наступний крок?
- Чи може користувач повернутися назад?
- Чи зрозуміло, де він перебуває?
- Чи можна перейти до пов'язаного розділу?
- Чи не губиться контекст під час переходу?
- Чи зберігаються важливі дані?

Наприклад, у процесі оформлення замовлення корисно показувати етапи:

    Кошик → Доставка → Оплата → Підтвердження

Такий індикатор допомагає користувачу зрозуміти, на якому етапі він перебуває.

Проте не кожен потік потребує окремого покрокового індикатора. Для коротких сценаріїв він може бути зайвим.

---

## 13. Як зменшити тертя у User Flow

**Friction (тертя)** — це будь-яка перешкода, яка ускладнює виконання завдання.

Приклади:

- Забагато полів у формі.
- Незрозумілі назви кнопок.
- Неочікувана реєстрація.
- Відсутність підтвердження після дії.
- Втрата введених даних.
- Повторне введення інформації.
- Непрозорі вимоги до пароля.
- Немає пояснення причини помилки.

### Прийоми покращення

**1. Прибирай непотрібні кроки**

Залишай ті дії, які мають зрозумілу мету.

**2. Використовуй зрозумілі назви**

Замість «Продовжити» в неоднозначному контексті можна використати «Перейти до оплати».

**3. Показуй результат дії**

Після надсилання форми користувач має бачити, що сталося.

**4. Не змушуй повторювати роботу**

Якщо сталася виправна помилка, зберігай введені дані, коли це безпечно.

**5. Додавай пояснення в потрібний момент**

Пояснюй вимоги до полів до або під час введення, а не лише після помилки.

**6. Передбачай альтернативи**

Якщо користувач не може виконати основний сценарій, запропонуй реальний наступний крок.

**7. Не приховуй важливі умови**

Вартість, строки, обов'язкові поля та наслідки дій мають бути зрозумілими до підтвердження.

**Важливо:** зменшення тертя не означає приховування необхідної інформації чи пропуск важливих перевірок.

## 14. User Flow для різних типів продуктів

### 14.1. Освітня платформа

Мета: записатися на курс.

    [Головна]
        ↓
    [Каталог курсів]
        ↓
    [Фільтрація]
        ↓
    [Сторінка курсу]
        ↓
    ◇ Користувач авторизований? ◇
       ├── Так → [Запис на курс]
       └── Ні  → [Вхід або реєстрація]
                         ↓
                  [Запис на курс]
                         ↓
                  [Підтвердження]

Що перевірити:

- Чи зрозуміла програма курсу?
- Чи видно вимоги до навчання?
- Чи зрозуміла вартість, якщо курс платний?
- Чи зберігається вибраний курс після входу?
- Чи зрозуміло, як почати навчання?

### 14.2. Медичний або психологічний сервіс

Мета: записатися на консультацію.

    [Сторінка спеціаліста]
            ↓
    [Перегляд інформації]
            ↓
    [Вибір формату консультації]
            ↓
    [Вибір доступного часу]
            ↓
    [Введення контактних даних]
            ↓
    [Підтвердження запису]
            ↓
    [Інформація про консультацію]

Що перевірити:

- Чи зрозумілі послуга та формат консультації?
- Чи видно вартість і тривалість?
- Чи показані доступні часові слоти?
- Чи зрозуміло, які дані необхідно надати?
- Чи захищені персональні дані?
- Чи є зрозумілий спосіб скасувати або перенести запис?

Для чутливих даних особливо важливо збирати лише необхідну інформацію та пояснювати, як вона використовується.

### 14.3. Інформаційний сайт

Мета: знайти потрібну статтю.

    [Головна]
        ↓
    [Пошук або категорія]
        ↓
    [Результати]
        ↓
    ◇ Є потрібна стаття? ◇
       ├── Так → [Відкрити статтю]
       └── Ні  → [Змінити запит]
                         ↓
                    [Результати]

Що перевірити:

- Чи помітний пошук?
- Чи зрозумілі назви категорій?
- Чи інформативні результати?
- Чи є повідомлення про відсутність результатів?
- Чи можна перейти до пов'язаних матеріалів?

### 14.4. Адміністративна панель

Мета: створити новий запис.

    [Dashboard]
        ↓
    [Розділ записів]
        ↓
    [Створити запис]
        ↓
    [Заповнити форму]
        ↓
    [Зберегти]
        ↓
    ◇ Дані коректні? ◇
       ├── Так → [Запис створено]
       └── Ні  → [Показати помилки]

Що перевірити:

- Чи зрозуміла структура форми?
- Чи можна скасувати дію?
- Чи зрозумілий результат збереження?
- Чи не губляться дані при помилці?
- Чи враховані права доступу?
- Чи передбачено підтвердження для незворотних дій?

## 15. Візуальне оформлення User Flow

Діаграма повинна бути зрозумілою без довгих пояснень.

### 15.1. Використовуй послідовне розташування

Для простих сценаріїв найчастіше достатньо руху зверху вниз або зліва направо.

    [Початок]
        ↓
    [Дія]
        ↓
    [Рішення]
       ↙ ↘
    [Так] [Ні]

Не змінюй напрямок без потреби.

### 15.2. Відрізняй типи елементів

Можна використовувати прості домовленості:

- Овал — початок або кінець.
- Прямокутник — дія або екран.
- Ромб — рішення.
- Стрілка — напрямок переходу.
- Окремий стиль — помилка або особливий стан.

Це поширені умовні позначення, але єдиного обов'язкового стандарту для всіх UX-діаграм немає.

Головне — послідовність у межах однієї схеми.

### 15.3. Підписуй гілки

Не залишай стрілки з точки рішення без пояснення.

Погано:

    ◇ Дані правильні? ◇
         ↙     ↘
        ↓       ↓

Краще:

    ◇ Дані правильні? ◇
       ↙           ↘
     Так             Ні
      ↓               ↓
    [Успіх]       [Помилка]

### 15.4. Уникай зайвих перетинів

Якщо лінії перетинаються, читачеві складніше зрозуміти послідовність.

Спробуй:

- Перемістити блоки.
- Вирівняти елементи.
- Розділити складну діаграму на менші.
- Використати окрему схему для альтернативного сценарію.

### 15.5. Підписуй екрани конкретно

Замість:

    [Сторінка 1]
        ↓
    [Сторінка 2]

Краще:

    [Каталог курсів]
        ↓
    [Сторінка курсу]

Назви повинні передавати зміст, а не лише порядковий номер.

### 15.6. Використовуй колір як допоміжний сигнал

Наприклад:

- Нейтральний колір — звичайний крок.
- Зелений — успішне завершення.
- Червоний — помилка або критичний стан.
- Жовтий — попередження.

Не покладайся тільки на колір. Використовуй також текстові підписи та зрозумілі форми.

## 16. Інструменти для створення User Flow

User Flow можна створювати на різних етапах проєктування.

### Папір і ручка

Підходять для:

- Швидкого початкового планування.
- Обговорення ідей.
- Чернеток.
- Виявлення основних кроків.

### Figma

Підходить для:

- Створення діаграм.
- Поєднання схем з екранами.
- Командної роботи.
- Побудови інтерактивних прототипів.

### FigJam

Підходить для:

- Спільних обговорень.
- Мозкового штурму.
- Простих блок-схем.
- Побудови сценаріїв на онлайн-дошці.

### Miro

Підходить для:

- Великих карт процесів.
- User Journey.
- Командних воркшопів.
- Складних сценаріїв.

### Mermaid

Для розробника зручно описувати прості потоки текстом і зберігати їх у Markdown.

Приклад діаграми:

    flowchart TD
        A[Головна сторінка] --> B[Форма входу]
        B --> C[Введення email і пароля]
        C --> D{Дані правильні?}
        D -->|Так| E[Особистий кабінет]
        D -->|Ні| F[Повідомлення про помилку]
        F --> C

Це приклад синтаксису Mermaid. Якщо редактор підтримує Mermaid, діаграма може бути відображена графічно.

### Як обрати інструмент

Для початкового навчання достатньо паперу, FigJam або Figma.

Не витрачай багато часу на пошук ідеального інструмента. Важливіше навчитися логічно описувати сценарії.

## 17. User Flow та розробка інтерфейсу

User Flow може бути корисним не лише дизайнеру, а й розробнику.

Він допомагає визначити:

- Які сторінки потрібно створити.
- Які компоненти потрібні.
- Які стани інтерфейсу передбачити.
- Які дії виконує користувач.
- Які дані передаються між кроками.
- Де необхідна перевірка даних.
- Які помилки потрібно обробляти.
- Коли потрібен перехід на іншу сторінку.

Наприклад, для форми реєстрації:

    User Flow
        ↓
    Визначення екранів
        ↓
    Проєктування компонентів
        ↓
    Визначення станів
        ↓
    Реалізація логіки
        ↓
    Тестування сценаріїв

### Приклад зв'язку з frontend

У React потік реєстрації може включати такі стани:

    idle
        ↓
    submitting
        ↓
    ├── success
    └── error

Приблизний приклад TypeScript:

    type RegistrationStatus =
      | "idle"
      | "submitting"
      | "success"
      | "error";

    type RegistrationState = {
      status: RegistrationStatus;
      errorMessage: string | null;
    };

Тут `RegistrationStatus` визначає можливі стани, а `RegistrationState` — структуру даних для представлення стану форми.

Це не повна реалізація реєстрації, а приклад того, як рішення, зафіксовані в User Flow, можуть впливати на архітектуру інтерфейсу.

### Важливе розділення відповідальності

User Flow не замінює:

- Технічну архітектуру.
- API-контракти.
- Модель даних.
- Схему бази даних.
- Правила безпеки.
- Автоматизовані тести.

Він описує користувацький сценарій і допомагає визначити вимоги до цих частин системи.

## 18. Як перевірити User Flow

Після створення діаграми потрібно перевірити її логіку.

### 18.1. Перевір основний шлях

Чи може користувач пройти від початкової точки до бажаного результату?

Якщо ні, можливо, бракує кроку або переходу.

### 18.2. Перевір усі розгалуження

Для кожної точки рішення запитай:

- Які можливі результати?
- Чи підписані всі гілки?
- Чи веде кожна гілка до логічного наступного кроку?
- Чи є шлях назад після помилки?

### 18.3. Перевір завершення

Кожен сценарій повинен мати зрозумілий результат або чітко визначений стан очікування.

Наприклад:

- Запис створено.
- Дані збережено.
- Користувач повернувся до форми.
- Потрібно повторити дію.
- Потрібно звернутися до підтримки.

### 18.4. Перевір тупикові гілки

Тупик — це ситуація, у якій користувач не може продовжити шлях і не розуміє, що робити.

Наприклад:

    [Неправильний пароль]
            ↓
    [Помилка]

Це неповний сценарій.

Краще:

    [Неправильний пароль]
            ↓
    [Пояснення помилки]
            ↓
    [Повторний вхід]
            або
    [Відновлення пароля]

Іноді сценарій справді повинен завершуватися, але тоді потрібно пояснити причину та, якщо можливо, запропонувати альтернативу.

### 18.5. Перевір на реальних користувачах

Діаграма може виглядати логічною для дизайнера, але бути незрозумілою для людини, яка вперше бачить продукт.

Протестуй прототип і зверни увагу:

- Де користувач вагається?
- Де натискає не ту кнопку?
- Де не розуміє повідомлення?
- Де очікує іншої поведінки?
- Де припиняє виконання завдання?

Результати тестування допомагають удосконалити User Flow.

## 19. Типові помилки під час створення User Flow

### Помилка 1. Описувати тільки сторінки

Погано:

    Головна → Каталог → Товар → Кошик

Така схема показує переходи, але не завжди пояснює дії користувача й можливі проблеми.

Краще додати важливі дії та рішення:

    [Каталог]
        ↓
    [Вибір товару]
        ↓
    [Сторінка товару]
        ↓
    [Додавання до кошика]
        ↓
    [Кошик]

### Помилка 2. Ігнорувати помилки

Якщо діаграма показує тільки успішний сценарій, вона не пояснює, що відбувається при неправильних даних або невдалому запиті.

**Рішення:** додай найважливіші Error Flow.

### Помилка 3. Створювати надто складну діаграму

Спроба показати всі функції продукту на одній схемі робить її важкою для читання.

**Рішення:** розділяй сценарії за цілями або процесами.

Наприклад:

- Реєстрація.
- Вхід.
- Відновлення пароля.
- Покупка.
- Повернення товару.

### Помилка 4. Не підписувати рішення

Погано:

    ◇
    ↙ ↘

Краще:

    ◇ Дані правильні? ◇
       ├── Так
       └── Ні

### Помилка 5. Не визначати результат дії

Після натискання кнопки користувач повинен розуміти, що відбулося.

**Рішення:** передбачай повідомлення, зміну стану або перехід, які відповідають реальному результату операції.

### Помилка 6. Прибирати кроки заради мінімальної кількості

Не кожен додатковий крок є зайвим.

Підтвердження платежу, перевірка важливих даних або пояснення умов можуть бути необхідними.

**Рішення:** оцінюй користь і зрозумілість кожного кроку, а не тільки їхню кількість.

### Помилка 7. Не враховувати повернення назад

Користувач може захотіти змінити вибір або виправити помилку.

**Рішення:** перевіряй, чи може він повернутися до потрібного кроку без втрати важливих даних.

### Помилка 8. Не враховувати Loading State

Якщо після натискання кнопки немає жодного зворотного зв'язку, користувач може натискати її повторно.

**Рішення:** передбачай стан очікування, блокування повторної дії за потреби та зрозумілий результат.

### Помилка 9. Змішувати User Flow з технічною схемою

User Flow не повинен перетворюватися на повну діаграму серверів, API та баз даних.

**Рішення:** описуй користувацький шлях окремо, а технічну архітектуру — в іншій схемі.

### Помилка 10. Вважати діаграму остаточною

Після тестування можуть з'явитися нові проблеми або альтернативні сценарії.

**Рішення:** оновлюй User Flow відповідно до результатів досліджень і змін у продукті.

## 20. Практичний мініпроєкт: User Flow для запису на консультацію

Створи User Flow для сайту, де користувач може записатися на консультацію.

### Вихідні умови

На сайті є:

- Головна сторінка.
- Сторінка спеціаліста.
- Інформація про консультацію.
- Вибір дати й часу.
- Форма контактних даних.
- Підтвердження запису.

Можливі проблеми:

- Немає вільного часу.
- Користувач не заповнив обов'язкові поля.
- Вибраний час став недоступним.
- Сталася технічна помилка під час надсилання.

### Завдання 1. Визнач мету

Сформулюй мету одним реченням.

Наприклад:

    Користувач хоче записатися на консультацію
    у зручний для нього час.

### Завдання 2. Побудуй Happy Path

Визнач основні кроки від сторінки спеціаліста до підтвердження запису.

### Завдання 3. Додай точки рішень

Продумай:

- Чи доступний час?
- Чи правильно заповнені контактні дані?
- Чи вдалося створити запис?

### Завдання 4. Додай альтернативні гілки

Передбач:

- Вибір іншого часу.
- Виправлення форми.
- Повторну спробу після технічної помилки.

### Завдання 5. Визнач кінцеві стани

Наприклад:

- Запис успішно створено.
- Потрібно вибрати інший час.
- Потрібно виправити дані.
- Не вдалося створити запис; користувач може повторити спробу.

### Завдання 6. Перевір діаграму

Переконайся, що:

- Основний шлях працює логічно.
- Усі рішення мають підписані гілки.
- Помилки мають зрозумілий наступний крок.
- Користувач не потрапляє в непередбачений тупик.
- Після успішного запису видно дату й час консультації.

## 21. Чекліст готового User Flow

Перед завершенням роботи перевір кожен пункт.

### Мета та структура

- [ ] Мета користувача сформульована конкретно.
- [ ] Початкова точка визначена.
- [ ] Основний сценарій побудований.
- [ ] Кінцевий результат визначений.
- [ ] Кожен крок має зрозумілу мету.

### Логіка

- [ ] Усі важливі точки рішень позначені.
- [ ] Гілки рішень підписані.
- [ ] Альтернативні сценарії враховані.
- [ ] Основні помилки передбачені.
- [ ] Немає випадкових тупиків.
- [ ] Передбачено повернення до попередніх кроків, де це потрібно.

### UX

- [ ] Користувач розуміє наступний крок.
- [ ] Назви дій конкретні.
- [ ] Зайві кроки відсутні.
- [ ] Важлива інформація доступна в потрібний момент.
- [ ] Після дії є зрозумілий зворотний зв'язок.
- [ ] Передбачені стани завантаження, успіху та помилки, якщо вони потрібні.

### Візуальне оформлення

- [ ] Елементи розташовані послідовно.
- [ ] Стрілки читаються однозначно.
- [ ] Рішення візуально відрізняються від дій.
- [ ] Назви блоків зрозумілі.
- [ ] Схема не перевантажена деталями.
- [ ] Для складних процесів використано окремі діаграми.

### Перевірка

- [ ] Основний сценарій перевірено.
- [ ] Альтернативні гілки перевірено.
- [ ] Поведінка після помилки визначена.
- [ ] Сценарій можна пройти без додаткових пояснень.
- [ ] Результати тестування враховано, якщо тестування вже проводилося.

## 22. Питання для співбесіди

### Початковий рівень

**1. Що таке User Flow?**

User Flow — це схема послідовності кроків, які користувач проходить у продукті для досягнення конкретної мети.

**2. Навіщо потрібен User Flow?**

Щоб спроєктувати зрозумілий шлях користувача, виявити зайві кроки, передбачити помилки й узгодити логіку взаємодії до реалізації інтерфейсу.

**3. Чим User Flow відрізняється від User Journey?**

User Flow зосереджується на сценарії взаємодії з продуктом, а User Journey описує ширший досвід користувача, включно з діями, думками, емоціями та точками контакту.

**4. Що таке Happy Path?**

Це основний сценарій, у якому всі дії виконуються успішно й користувач досягає своєї мети.

**5. Що таке Decision Point?**

Це точка рішення, у якій подальший шлях залежить від умови, наприклад правильності введених даних.

### Середній рівень

**6. Чому недостатньо описати тільки переходи між сторінками?**

Тому що переходи не завжди показують дії користувача, альтернативні сценарії, помилки та результати операцій.

**7. Як обробляти помилки у User Flow?**

Потрібно визначити, як система повідомляє про проблему, що користувач може зробити далі та як він повернеться до основного сценарію.

**8. Як зрозуміти, що User Flow занадто складний?**

Якщо діаграму важко читати, кроки дублюються, гілки плутаються або різні цілі змішані в одній схемі, сценарій варто спростити чи розділити.

**9. Як User Flow пов'язаний із UI-дизайном?**

Він визначає послідовність екранів, необхідні дії, переходи та стани, які потрібно відобразити в інтерфейсі.

**10. Чи завжди потрібно зменшувати кількість кроків?**

Ні. Потрібно прибирати зайві перешкоди, але зберігати необхідні кроки для безпеки, зрозумілості та правильного виконання завдання.

### Просунутий рівень

**11. Як перевірити User Flow до розробки?**

Створити прототип, пройти сценарій самостійно та протестувати його з представниками цільової аудиторії.

**12. Як враховувати складні помилки, наприклад невизначений результат оплати?**

Не можна автоматично вважати платіж невдалим. Потрібно визначити достовірний статус операції, передбачити перевірку статусу й пояснити користувачу, що робити далі.

**13. Чим User Flow відрізняється від блок-схеми алгоритму?**

User Flow зосереджується на шляху користувача та його взаємодії з продуктом. Блок-схема алгоритму зазвичай описує логіку виконання процесу, яка може бути повністю технічною.

**14. Як пов'язати User Flow із компонентами React?**

Визначити екрани, дії, переходи та стани. Потім реалізувати їх за допомогою компонентів, маршрутизації, керування станом і обробки помилок.

**15. Як визначити, чи покращення User Flow справді працює?**

Перевірити його за допомогою користувацького тестування та відповідних метрик, наприклад успішного завершення завдання, часу виконання, кількості помилок і відмов на окремих етапах.

## 23. Рівні володіння темою

### Core — базовий рівень

Ти повинен уміти:

- Пояснити, що таке User Flow.
- Визначити мету користувача.
- Позначити початкову та кінцеву точки.
- Побудувати простий послідовний сценарій.
- Використовувати стрілки та блоки.
- Пояснити Happy Path.

### Junior — початковий професійний рівень

Ти повинен уміти:

- Побудувати User Flow для реєстрації, входу або покупки.
- Позначити точки рішень.
- Додати альтернативні сценарії.
- Передбачити основні помилки.
- Врахувати стани інтерфейсу.
- Створити зрозумілу діаграму у Figma або FigJam.
- Пояснити, як User Flow впливає на екрани та компоненти.

### Middle — середній рівень

Ти повинен уміти:

- Аналізувати складні багатокрокові сценарії.
- Виявляти зайві переходи та UX-проблеми.
- Розділяти великі потоки на зрозумілі частини.
- Ураховувати різні ролі та початкові точки входу.
- Проєктувати відновлення після помилок.
- Перевіряти сценарії за допомогою прототипів і тестування.
- Співпрацювати з розробниками та продуктовою командою.

### Senior — просунутий рівень

Ти повинен уміти:

- Проєктувати потоки для складних продуктів.
- Враховувати різні потреби користувачів і бізнес-обмеження.
- Аналізувати проблеми на основі досліджень та продуктових метрик.
- Узгоджувати взаємодію між різними частинами продукту.
- Визначати пріоритети UX-покращень.
- Перевіряти вплив змін на успішність виконання завдань.
- Допомагати команді підтримувати узгоджені сценарії в міру розвитку продукту.

## 24. Мінішпаргалка

### Основні поняття

- **User Flow** — шлях користувача до мети.
- **Task Flow** — кроки для виконання одного завдання.
- **User Journey** — ширший досвід взаємодії з продуктом.
- **Start Point** — початкова точка сценарію.
- **Action** — дія користувача.
- **Decision Point** — точка прийняття рішення.
- **Outcome** — кінцевий результат.
- **Happy Path** — основний успішний сценарій.
- **Alternative Flow** — альтернативний шлях.
- **Error Flow** — шлях після виникнення помилки.
- **Edge Case** — граничний або незвичний випадок.
- **Friction** — перешкода, що ускладнює виконання завдання.

### Алгоритм створення

    1. Визнач мету користувача.
    2. Визнач початкову точку.
    3. Побудуй основний сценарій.
    4. Додай точки рішень.
    5. Передбач альтернативні сценарії.
    6. Продумай помилки.
    7. Визнач кінцевий результат.
    8. Перевір кількість і логіку кроків.
    9. Створи прототип.
    10. Перевір сценарій на користувачах.

### Головні правила

- Один User Flow має чітку мету.
- Кожен крок повинен мати зрозумілий сенс.
- Рішення повинні мати підписані гілки.
- Помилки повинні мати логічне продовження.
- Після важливої дії користувач має розуміти результат.
- Не змішуй усі сценарії в одну перевантажену діаграму.
- Перевіряй потік на реальних сценаріях використання.

## 25. Підсумок

**User Flow — це інструмент проєктування логіки взаємодії користувача з продуктом.**

Він допомагає перейти від загальної ідеї інтерфейсу до конкретної послідовності дій, переходів, рішень і результатів.

Під час створення User Flow потрібно:

1. Починати з мети користувача, а не з переліку екранів.
2. Спочатку будувати основний успішний сценарій.
3. Додавати важливі альтернативи та помилки.
4. Визначати, що користувач бачить після кожної важливої дії.
5. Перевіряти логіку сценарію до початку розробки.

**Головне правило:** хороший User Flow не просто показує, куди користувач може перейти. Він допомагає зрозуміти, як користувач досягає своєї мети, що може піти не так і як інтерфейс допоможе йому продовжити шлях.
