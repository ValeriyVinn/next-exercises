# 01. Information Architecture

Information Architecture (IA, інформаційна архітектура) — це організація, структурування та класифікація інформації в цифровому продукті, щоб користувачі могли легко знаходити потрібний контент, розуміти його взаємозв'язки та орієнтуватися в інтерфейсі.

Information Architecture використовується під час проєктування:

    websites
    web applications
    mobile applications
    dashboards
    educational platforms
    e-commerce websites
    content management systems
    enterprise applications

Основна мета IA — зробити інформацію зрозумілою, передбачуваною та доступною для користувача.

Наприклад, в освітній платформі інформацію можна організувати так:

    LMS
    ├── Courses
    │   ├── Mathematics
    │   ├── Informatics
    │   └── English
    ├── Students
    ├── Teachers
    ├── Assignments
    └── Grades

Така структура допомагає користувачеві зрозуміти, які розділи існують і де шукати потрібну інформацію.

Information Architecture тісно пов'язана з:

    UX Design
    UI Design
    Navigation Design
    Content Strategy
    User Research
    Usability
    Search Design
    Interaction Design

## Що потрібно пам'ятати

• Information Architecture визначає, як інформація організована, згрупована, названа та пов'язана між собою.

• IA допомагає користувачеві зрозуміти, де він перебуває, що доступно та як знайти потрібну інформацію.

• Information Architecture — це не лише навігаційне меню. Вона охоплює всю структуру контенту цифрового продукту.

• Information Hierarchy визначає, які елементи є головними, а які підпорядкованими.

• Taxonomy — система класифікації інформації за категоріями та правилами.

• Labels — назви категорій, розділів, сторінок і навігаційних елементів.

• Sitemap показує структуру сторінок і зв'язки між ними.

• Content Inventory — перелік наявного контенту.

• Content Audit — оцінювання якості, актуальності, повноти та корисності контенту.

• Card Sorting допомагає зрозуміти, як користувачі групують інформацію.

• Tree Testing допомагає перевірити, чи можуть користувачі знайти потрібний елемент у запропонованій ієрархії.

• Findability — наскільки легко знайти потрібну інформацію.

• Discoverability — наскільки легко виявити доступні можливості, функції або контент.

• Хороша IA відповідає очікуванням користувача, а не лише внутрішній структурі організації.

• Інформаційна архітектура має бути масштабованою: нові розділи не повинні руйнувати наявну структуру.

• Зрозуміла IA полегшує створення навігації, сторінок, URL і UI-компонентів.

# Information Architecture vs UI Design vs UX Design

Ці поняття пов'язані між собою, але відповідають за різні аспекти продукту.

## Information Architecture

Визначає, як організована інформація.

Основні питання:

    Які розділи існують?
    Як згрупований контент?
    Які сторінки підпорядковані іншим?
    Як користувач може знайти інформацію?
    Які назви категорій зрозумілі користувачеві?

Приклад:

    Online School
    ├── Courses
    ├── Students
    ├── Teachers
    └── Grades

## UX Design

Визначає, як користувач взаємодіє з продуктом і наскільки зручно досягає своєї мети.

Основні питання:

    Хто користувач?
    Яка його мета?
    Який шлях веде до результату?
    Де виникають труднощі?
    Як зробити взаємодію простішою?

Приклад:

    Open course
        ↓
    Select lesson
        ↓
    Complete assignment
        ↓
    View result

## UI Design

Визначає, як інтерфейс виглядає та як його елементи представлені візуально.

Основні питання:

    Як виглядає меню?
    Які розміри та кольори компонентів?
    Як розташовані елементи?
    Як виглядає активний пункт?
    Як оформлена сторінка?

Приклад:

    Sidebar
    ├── Courses
    ├── Students
    └── Grades

    Active item:
        background: selected color
        text: emphasized
        icon: highlighted

## Коротке порівняння

    Information Architecture
        → organize information

    UX Design
        → make interaction useful and easy

    UI Design
        → design the visual interface

IA визначає структуру, UX допомагає спроєктувати зручну взаємодію, а UI представляє її через конкретні елементи інтерфейсу.

# Information Architecture та Navigation

Information Architecture і Navigation Design не є тотожними поняттями.

## Information Architecture

Визначає:

    структуру контенту
    категорії
    ієрархію сторінок
    зв'язки між розділами
    правила класифікації

## Navigation Design

Визначає, як користувач переміщується між розділами та сторінками.

Основні елементи:

    navbar
    sidebar
    breadcrumbs
    tabs
    pagination
    navigation links
    contextual links

Наприклад, IA визначає, що сторінка уроку належить до конкретного курсу.

    Courses
        └── Informatics
            └── Module 1
                └── Lesson 1

Navigation Design визначає, як користувач переходить до цього уроку через меню, посилання або список уроків.

Важливо:

    IA = structure of information

    Navigation = way to move through information

Навіть добре організована інформація може бути важкодоступною, якщо навігація спроєктована погано.

# Information Hierarchy

Information Hierarchy — це ієрархічна організація інформації, за якої одні елементи є батьківськими, а інші — дочірніми.

Наприклад:

    Website
    ├── About
    │   ├── Our Team
    │   └── History
    ├── Services
    │   ├── Web Development
    │   └── UI Design
    └── Contact

Тут:

    Website → root
    About → parent
    Our Team → child of About
    Services → parent
    Web Development → child of Services

Ієрархія дозволяє зрозуміти відносини між сторінками.

## Root

Root — найвищий рівень структури.

Наприклад:

    Website

Root часто відповідає головній сторінці або кореневому вузлу структури.

## Parent

Parent — елемент, який містить або об'єднує дочірні елементи.

Наприклад:

    Services
        ├── Web Development
        └── UI Design

## Child

Child — елемент, який підпорядкований іншому елементу.

Наприклад:

    Web Development

є дочірнім елементом:

    Services

## Sibling

Sibling — елементи одного рівня, які мають спільного батька.

Наприклад:

    Services
        ├── Web Development
        ├── UI Design
        └── Consulting

Три дочірні сторінки є siblings.

## Ancestor

Ancestor — будь-який предок елемента в ієрархії.

Наприклад:

    Website
        └── Courses
            └── Informatics
                └── Lesson 1

Для Lesson 1 предками є:

    Informatics
    Courses
    Website

## Descendant

Descendant — будь-який нащадок елемента.

Для Courses нащадками є:

    Informatics
    Lesson 1

якщо Lesson 1 належить до Informatics.

# Site Structure

Site Structure — організація сторінок і розділів вебсайту.

Основні типи структури:

    Hierarchical Structure
    Sequential Structure
    Matrix Structure
    Database-Driven Structure

На практиці один вебсайт може поєднувати кілька типів.

---

## Hierarchical Structure

Hierarchical Structure — ієрархічна структура, у якій сторінки організовані за рівнями.

    Home
    ├── Courses
    │   ├── Mathematics
    │   └── Informatics
    ├── Teachers
    └── About

Підходить для:

    educational platforms
    corporate websites
    documentation websites
    online stores
    content-heavy websites

Переваги:

    зрозумілі відносини між сторінками
    проста організація великих розділів
    зручна побудова меню
    можливість використовувати breadcrumbs

Недоліки:

    занадто глибока структура ускладнює навігацію
    користувач може не одразу знайти потрібну сторінку
    надмірна кількість категорій ускладнює вибір

---

## Sequential Structure

Sequential Structure — послідовна структура, у якій користувач проходить визначені кроки в певному порядку.

    Step 1
       ↓
    Step 2
       ↓
    Step 3
       ↓
    Completion

Підходить для:

    registration
    checkout
    onboarding
    application forms
    guided tutorials
    setup wizards

Наприклад:

    Create account
        ↓
    Verify email
        ↓
    Complete profile
        ↓
    Start learning

Переваги:

    зрозумілий порядок дій
    контроль послідовності
    зменшення складності багатокрокових процесів

Недоліки:

    користувач може відчувати обмеження
    повернення до попередніх кроків може бути складним
    зайві кроки збільшують тертя

Sequential Structure не завжди повинна бути суворо лінійною. Наприклад, користувач може повертатися до попереднього кроку для виправлення даних.

---

## Matrix Structure

Matrix Structure дозволяє користувачеві переміщатися між матеріалами за різними зв'язками, а не лише за однією ієрархією.

Наприклад, у бібліотеці матеріали можуть бути пов'язані за:

    subject
    author
    difficulty
    publication date
    topic

Один матеріал може належати до кількох категорій.

Підходить для:

    knowledge bases
    research platforms
    documentation
    content libraries
    reference websites

Переваги:

    гнучкий пошук
    кілька способів доступу до матеріалу
    зручність для різних потреб користувачів

Недоліки:

    складніше спроєктувати
    можливе дублювання навігаційних шляхів
    потрібні зрозумілі фільтри та мітки

---

## Database-Driven Structure

Database-Driven Structure — організація сторінок на основі даних, які зберігаються в базі даних або іншому джерелі контенту.

Наприклад:

    Courses
        ├── Course 1
        ├── Course 2
        └── Course 3

Кожна сторінка курсу використовує спільний шаблон, але отримує власні дані.

Приклад маршруту:

    /courses
    /courses/mathematics
    /courses/informatics

Підходить для:

    e-commerce
    blogs
    LMS
    directories
    product catalogs
    content management systems

Переваги:

    масштабованість
    повторне використання шаблонів
    централізоване керування контентом

Недоліки:

    потрібна продумана модель даних
    необхідно підтримувати узгодженість URL
    помилки класифікації впливають на багато сторінок

# Flat Structure vs Deep Structure

Це два важливі способи організації ієрархії.

## Flat Structure

Flat Structure — структура з невеликою кількістю рівнів і відносно великою кількістю елементів на одному рівні.

    Home
    ├── Courses
    ├── Teachers
    ├── Students
    ├── Assignments
    ├── Grades
    └── Settings

Переваги:

    невелика кількість переходів
    швидкий доступ до основних розділів
    проста структура для невеликих продуктів

Недоліки:

    надто багато пунктів у меню
    складніше знайти потрібний елемент серед багатьох варіантів
    структура може стати перевантаженою

## Deep Structure

Deep Structure — структура з більшою кількістю рівнів.

    Home
    └── Courses
        └── Informatics
            └── Module 1
                └── Lesson 1

Переваги:

    можна логічно групувати велику кількість матеріалів
    зручніше розділяти складні категорії
    менше елементів на кожному рівні

Недоліки:

    більше переходів до потрібної інформації
    користувач може втратити контекст
    потрібні breadcrumbs або інші засоби орієнтації

## Breadth and Depth

Breadth — кількість елементів на одному рівні.

Depth — кількість рівнів ієрархії.

Спрощено:

    Breadth → how many items per level

    Depth → how many levels

Наприклад:

    Home
    ├── Courses
    ├── Teachers
    ├── Students
    └── Settings

Має невелику depth і відносно велику breadth.

А структура:

    Home
    └── Courses
        └── Informatics
            └── Module 1
                └── Lesson 1

має більшу depth.

Важливо не встановлювати універсальне правило на кшталт «усі сайти повинні мати не більше трьох рівнів». Оптимальна структура залежить від кількості контенту, задач користувачів та складності продукту.

# Content Organization

Content Organization — організація контенту за категоріями, темами, типами та іншими характеристиками.

Наприклад, для навчальної платформи:

    Content
    ├── Courses
    ├── Lessons
    ├── Assignments
    ├── Tests
    └── Learning Materials

Контент можна організовувати за різними принципами.

## Organization by Topic

Групування за темою.

    Informatics
    ├── Algorithms
    ├── Databases
    └── Networks

Підходить для освітніх ресурсів і документації.

## Organization by Task

Групування за дією або метою користувача.

    Account
    ├── Create Account
    ├── Change Password
    └── Manage Profile

Підходить для довідкових центрів і сервісних порталів.

## Organization by Audience

Групування за типом користувача.

    Portal
    ├── For Students
    ├── For Teachers
    └── For Parents

Підходить для продуктів, якими користуються різні аудиторії.

Важливо: цей підхід доречний, коли аудиторії справді мають різні потреби. Не потрібно створювати окремий розділ для кожної групи, якщо інформація для них однакова.

## Organization by Format

Групування за типом контенту.

    Learning Materials
    ├── Articles
    ├── Videos
    ├── Documents
    └── Exercises

Підходить для медіабібліотек і контентних платформ.

## Organization by Time

Групування за датою або періодом.

    News
    ├── 2026
    ├── 2025
    └── 2024

Підходить для архівів, новинних сайтів і календарів.

## Organization by Location

Групування за географічним розташуванням.

    Locations
    ├── Ukraine
    │   ├── Vinnytsia
    │   └── Kyiv
    └── Poland
        └── Warsaw

Підходить для каталогів організацій, філій і локальних сервісів.

# Taxonomy

Taxonomy — система класифікації інформації за категоріями, підкатегоріями та правилами.

Наприклад:

    Programming
    ├── Frontend
    │   ├── HTML
    │   ├── CSS
    │   └── JavaScript
    └── Backend
        ├── Node.js
        ├── Databases
        └── APIs

Taxonomy допомагає:

    організовувати контент
    підтримувати послідовні назви категорій
    будувати навігацію
    створювати фільтри
    знаходити пов'язані матеріали
    масштабувати інформаційну структуру

## Category

Category — категорія, яка об'єднує споріднені елементи.

Наприклад:

    Frontend
        ├── HTML
        ├── CSS
        └── JavaScript

## Subcategory

Subcategory — підкатегорія, яка належить до ширшої категорії.

Наприклад:

    JavaScript Frameworks
        ├── React
        ├── Vue
        └── Angular

## Classification

Classification — процес або результат розподілу інформації за певними ознаками.

Наприклад, книги можна класифікувати за:

    genre
    author
    publication year
    language

## Controlled Vocabulary

Controlled Vocabulary — узгоджений набір термінів, які використовуються для позначення категорій і понять.

Наприклад, у всьому інтерфейсі використовується:

    Assignments

замість непослідовного набору:

    Assignments
    Homework
    Tasks
    Exercises

Це не означає, що ці слова завжди мають однакове значення. Головне — визначити їхні значення та послідовно використовувати відповідні терміни.

## Faceted Classification

Faceted Classification — класифікація, яка дозволяє описувати елемент за кількома незалежними характеристиками.

Наприклад, курс можна фільтрувати за:

    subject
    level
    duration
    language

Користувач може вибрати:

    Subject: Informatics
    Level: Beginner
    Duration: 4 weeks
    Language: Ukrainian

Це особливо корисно для великих каталогів.

# Taxonomy vs Ontology

Ці поняття пов'язані, але не тотожні.

## Taxonomy

Taxonomy описує категорії та їхню ієрархію.

    Animals
    ├── Mammals
    ├── Birds
    └── Reptiles

Основний акцент:

    categories
    hierarchy
    classification

## Ontology

Ontology — формалізований опис понять предметної області, їхніх властивостей і взаємозв'язків.

Наприклад:

    Student
        → enrolls in → Course

    Teacher
        → teaches → Course

    Course
        → contains → Lesson

Основний акцент:

    entities
    relationships
    properties
    constraints

Для звичайного UI-проєкту часто достатньо продуманої taxonomy та content model. Повноцінна ontology потрібна переважно тоді, коли продукт має складні предметні зв'язки, семантичний пошук або формалізовану модель знань.

# Labels

Labels — назви, за допомогою яких користувач розуміє призначення сторінки, категорії, дії або елемента інтерфейсу.

Приклади:

    Home
    Courses
    Students
    Settings
    Help
    Search

Labels впливають на те, наскільки швидко користувач може знайти потрібний розділ.

## Good Labels

Хороші labels мають бути:

    clear
    concise
    consistent
    meaningful
    familiar to users

Наприклад:

    Courses

часто зрозуміліше, ніж:

    Educational Resources Management

якщо розділ містить лише список курсів.

## Consistent Labels

Назви повинні бути послідовними.

Наприклад, якщо основний термін — `Courses`, не варто без потреби змінювати його на `Classes` в іншому меню, якщо йдеться про ту саму сутність.

Водночас не потрібно примусово використовувати однакові слова для різних понять.

Наприклад:

    Course → навчальний курс
    Lesson → урок
    Assignment → завдання

Це різні сутності, тому вони повинні мати різні labels.

## User Language

Labels повинні відповідати мові та поняттям користувачів.

Якщо користувачі шукають розділ під назвою «Оцінки», не варто без потреби називати його «Академічні результати».

Особливо це важливо для:

    educational platforms
    healthcare applications
    financial services
    public services

У складних предметних областях зрозумілість термінів має пріоритет над внутрішнім професійним жаргоном.

## Action Labels vs Content Labels

Content label називає розділ або тип інформації.

    Courses
    Students
    Documents

Action label називає дію.

    Create Course
    Add Student
    Download Document

Назва дії має допомагати користувачеві зрозуміти, що станеться після натискання.

# Sitemap

Sitemap — представлення структури сторінок вебсайту.

В інформаційній архітектурі sitemap зазвичай використовують для планування ієрархії та зв'язків між сторінками.

Приклад:

    Online School
    ├── Home
    ├── Courses
    │   ├── Mathematics
    │   │   ├── Course Overview
    │   │   └── Lessons
    │   └── Informatics
    │       ├── Course Overview
    │       └── Lessons
    ├── Teachers
    ├── About
    └── Contact

Sitemap допомагає:

    побачити всю структуру продукту
    виявити дублювання сторінок
    знайти відсутні розділи
    перевірити глибину ієрархії
    спланувати навігацію
    узгодити структуру з командою

## Sitemap vs XML Sitemap

Це два різні, хоча й пов'язані поняття.

### IA Sitemap

Візуальна схема структури сайту.

Використовується для:

    UX planning
    content organization
    navigation design
    product documentation

### XML Sitemap

XML-файл, який повідомляє пошуковим системам про URL, доступні для індексування.

Приклад:

    <?xml version="1.0" encoding="UTF-8"?>
    <urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
        <url>
            <loc>https://example.com/</loc>
        </url>
        <url>
            <loc>https://example.com/courses</loc>
        </url>
    </urlset>

XML Sitemap не є повноцінною схемою інформаційної архітектури.

Він не обов'язково описує батьківсько-дочірні зв'язки між сторінками.

# URL Structure

URL Structure — організація адрес сторінок.

URL можуть відображати ієрархію продукту.

Наприклад:

    /courses
    /courses/informatics
    /courses/informatics/lessons
    /courses/informatics/lessons/intro

Така структура дає зрозумілий контекст.

## Hierarchical URLs

Адреси відображають вкладеність ресурсів.

    /courses
    /courses/123
    /courses/123/lessons
    /courses/123/lessons/456

Це поширений підхід для вебзастосунків із пов'язаними ресурсами.

## Descriptive URLs

Адреси містять зрозумілі слова.

    /courses/javascript-basics

Зазвичай така адреса зрозуміліша, ніж:

    /page?id=123

Однак ідентифікатори можуть бути корисними для ресурсів із неунікальними назвами.

## URL vs Navigation

URL і навігація пов'язані, але не тотожні.

    URL → address of a resource

    Navigation → way to move between resources

Сторінка може бути доступною через кілька шляхів навігації, але мати одну канонічну URL-адресу.

## Важливі правила

• URL мають бути передбачуваними.

• Назви маршрутів повинні відповідати сутності або призначенню сторінки.

• Структура URL не повинна бути складнішою за необхідну.

• Зміна URL на опублікованому сайті може вимагати перенаправлень.

• Не кожен візуальний рівень навігації повинен точно повторювати структуру URL.

• У вебзастосунку URL можуть відображати ресурси, а не буквальне розташування сторінки в меню.

# Content Model

    Course

    які сутності пов'язані
    як контент повторно використовується
    як контент відображається на різних сторінках

Приклади:

    Course
    Lesson
    Article
    Product
    Event
    User Profile

## Content Fields

Fields — властивості конкретного типу контенту.

Наприклад:

    Article
        title

        body
        author
        publishedAt

## Content Relationships

Relationships — зв'язки між типами контенту.

Наприклад:

    Article → Author

Продумана Content Model допомагає уникати дублювання та підтримувати послідовність контенту.

# Information Architecture та Database Design

Information Architecture і Database Design можуть використовувати схожі поняття, але вирішують різні задачі.

## Information Architecture

Фокусується на тому, як люди знаходять і розуміють інформацію.

    categories
    labels
    pages
    hierarchy
    navigation
    findability

## Database Design

Фокусується на зберіганні, цілісності та обробці даних.

    tables
    columns
    primary keys
    foreign keys
    relationships
    constraints
    indexes

Наприклад, користувач бачить:

    Courses
        └── Informatics
            └── Lessons

А база даних може містити:

    courses
    lessons
    course_lessons

або іншу структуру, залежно від моделі даних.

Важливо:

    Information Architecture ≠ Database Schema

Вони повинні узгоджуватися на рівні предметної області, але не зобов'язані мати однакову структуру.

# Findability

Findability — здатність користувача знайти потрібну інформацію в цифровому продукті.

Findability залежить від:

    information architecture
    navigation
    labels
    search
    filters
    content organization
    consistency
    user expectations

Наприклад, користувач хоче знайти оцінки.

Якщо він бачить:

    Dashboard
    Courses
    Assignments
    Grades
    Settings

то розділ Grades може бути очевидним місцем пошуку.

Якщо ж оцінки приховані в незрозумілому розділі Administrative Information, findability погіршується.

## Як покращити Findability

• Використовувати знайомі назви.

• Групувати пов'язану інформацію.

• Не створювати надто багато рівнів ієрархії без потреби.

• Додавати пошук для великих обсягів контенту.

• Використовувати фільтри там, де користувачі порівнюють багато елементів.

• Показувати контекст поточної сторінки.

• Підтримувати послідовність у меню та заголовках.

• Перевіряти структуру на реальних користувачах.

# Discoverability

Discoverability — наскільки легко користувач може виявити доступні можливості, функції або інформацію.

Findability та Discoverability пов'язані, але мають різні акценти.

    Findability
        → знайти те, що шукаєш

    Discoverability
        → помітити те, про що можеш не знати

Наприклад, користувач шукає список курсів.

Findability забезпечує можливість знайти розділ Courses.

Discoverability допомагає помітити, що курс також має:

    downloadable materials
    practice exercises
    discussion forum
    progress tracking

## Як покращити Discoverability

• Використовувати зрозумілі назви та візуальні підказки.

• Розміщувати пов'язані функції поруч.

• Показувати доступні дії у відповідному контексті.

• Використовувати зрозумілі категорії.

• Не приховувати важливі можливості за неочевидними діями.

• Застосовувати progressive disclosure для складних інтерфейсів.

Важливо: не кожна функція повинна бути одночасно видимою. Надлишок елементів може перевантажувати інтерфейс.

# Mental Model

Mental Model — уявлення користувача про те, як працює система та як організована інформація.

Наприклад, користувач освітньої платформи може очікувати таку структуру:

    Courses
        └── Lessons
            └── Assignments
                └── Results

Якщо результати раптово розміщені в розділі Settings, це може суперечити його очікуванням.

## User Expectations

User Expectations — очікування щодо поведінки інтерфейсу та розташування інформації.

Користувачі часто очікують, що:

    логотип веде на Home
    назва Courses відкриває курси
    шестерня відкриває Settings
    breadcrumbs відображають шлях до сторінки
    пошук допомагає знаходити контент

Ці очікування не є абсолютними правилами, але їх порушення без зрозумілої причини може створювати труднощі.

## Як враховувати Mental Models

• Досліджувати, як користувачі описують свої задачі.

• Використовувати знайому термінологію.

• Перевіряти групування контенту.

• Не будувати структуру лише за внутрішньою організаційною схемою.

• Проводити card sorting та tree testing.

# Information Scent

Information Scent — сукупність підказок, які допомагають користувачеві оцінити, чи приведе певне посилання, назва або категорія до потрібної інформації.

Наприклад:

    View Grades

має сильний information scent для користувача, який хоче побачити оцінки.

А назва:

    Academic Center

може бути менш зрозумілою, якщо користувач не знає, що саме міститься в цьому розділі.

Information Scent залежить від:

    labels
    link text
    category names
    context
    visual cues
    user expectations

## Як покращити Information Scent

• Називати посилання відповідно до їхньої мети.

• Уникати неоднозначних формулювань.

• Додавати короткі описи там, де назви недостатньо.

• Показувати контекст переходу.

• Використовувати послідовну термінологію.

Наприклад:

    Courses

    Browse all available courses

Другий рядок пояснює, що саме користувач знайде в розділі.

        update

# Card Sorting

Card Sorting — метод дослідження, у якому учасники групують картки з назвами контенту, функцій або сторінок.

Мета — зрозуміти, як користувачі природно класифікують інформацію.

Наприклад, картки:

    Courses
    Lessons
    Grades
    Teachers
    Assignments
    Students
    Schedule

Учасникам пропонують згрупувати їх у логічні категорії.

Результати допомагають проєктувати:

    navigation
    categories
    information hierarchy
    labels
    site structure

## Open Card Sorting

Open Card Sorting — учасники самостійно створюють групи та називають їх.

Приклад:

    Group 1:
        Courses
        Lessons
        Assignments

    Group name:
        Learning

    Group 2:
        Teachers
        Students

    Group name:
        People

Підходить, коли потрібно зрозуміти, як користувачі самостійно групують інформацію.

## Closed Card Sorting

Closed Card Sorting — учасникам надають готові категорії, а вони розподіляють картки між ними.

Наприклад, категорії:

    Learning
    People
    Administration

Учасники розподіляють картки між цими категоріями.

Підходить для перевірки вже запропонованої класифікації.

## Hybrid Card Sorting

Hybrid Card Sorting — учасники отримують готові категорії, але можуть створювати додаткові.

Цей метод поєднує переваги open і closed card sorting.

## Коли використовувати Card Sorting

• Коли створюється новий продукт.

• Коли наявне меню незрозуміле.

• Коли потрібно переглянути категорії.

• Коли користувачі по-різному розуміють назви розділів.

• Коли сайт має велику кількість сторінок.

## Обмеження Card Sorting

Результат card sorting не є готовою інформаційною архітектурою.

Після дослідження необхідно:

    analyze patterns
        ↓
    identify categories
        ↓
    define labels
        ↓
    create structure
        ↓
    test the structure

Групування користувачів потрібно співвіднести з реальними задачами, обсягом контенту та вимогами продукту.

# Tree Testing

Tree Testing — метод перевірки інформаційної архітектури, який допомагає визначити, чи можуть користувачі знайти потрібну сторінку в ієрархічній структурі.

Учасники отримують задачу та дерево категорій без повного візуального інтерфейсу.

Наприклад:

    Home
    ├── Courses
    │   ├── Mathematics
    │   └── Informatics
    ├── Students
    ├── Teachers
    └── Administration

Завдання:

    Find the Informatics course.

Користувач обирає шлях:

    Home
        ↓
    Courses
        ↓
    Informatics

Після тесту аналізують, наскільки успішно та швидко користувачі знайшли потрібний пункт.

## Що можна перевірити

    findability
    category structure
    labels
    navigation paths
    information hierarchy
    user expectations

## Tree Testing vs Usability Testing

Tree Testing зосереджується на структурі та пошуку потрібних пунктів у дереві.

Usability Testing перевіряє ширший досвід взаємодії з інтерфейсом, зокрема:

    interactions
    forms
    visual hierarchy
    feedback
    navigation
    task completion

Tree Testing можна провести до створення повноцінного UI.

## Card Sorting vs Tree Testing

    Card Sorting
        → як користувачі групують інформацію?

    Tree Testing
        → чи можуть користувачі знайти інформацію
          у запропонованій структурі?

Ці методи доповнюють один одного.

Card sorting допомагає сформувати гіпотезу щодо структури, а tree testing — перевірити її.

---

# Orphan Pages

Orphan Page — сторінка, на яку немає внутрішніх посилань з інших сторінок сайту або яка практично не пов'язана з рештою структури.

Наприклад:

    Home
    ├── Courses
    ├── Teachers
    └── About

А сторінка:

    /old-course

існує, але на неї немає посилань із навігації чи інших сторінок.

Проблеми:

    користувачам складно знайти сторінку
    сторінка може випадково залишитися поза навігацією
    складніше підтримувати актуальність контенту

Orphan Page не завжди є помилкою. Наприклад, спеціальна landing page може бути доступною лише з рекламного посилання.

Важливо визначати, чи є відсутність внутрішніх посилань навмисною.

---

# Duplicate Content

Duplicate Content — повторення однакового або дуже схожого контенту в кількох місцях.

Наприклад:

    /courses/javascript
    /learning/javascript
    /materials/javascript

Якщо всі три сторінки містять ту саму інформацію без зрозумілої причини, структура може заплутувати користувача.

Потенційні проблеми:

    неоднозначність
    складніше підтримувати актуальність
    суперечливі версії інформації
    дублювання роботи редакторів

## Як уникати зайвого дублювання

• Визначати основне місце зберігання контенту.

• Повторно використовувати спільні компоненти та блоки контенту.

• Створювати посилання на першоджерело.

• Об'єднувати сторінки, якщо вони мають однакову мету.

• Розрізняти повторне використання контенту та непотрібне дублювання.

Не кожне повторення є помилкою. Наприклад, короткий опис курсу може з'являтися в каталозі та на сторінці курсу.

---

# Progressive Disclosure

Progressive Disclosure — принцип поступового розкриття інформації або функцій у міру потреби користувача.

Мета — не показувати всі деталі одночасно, якщо вони перевантажують інтерфейс.

Наприклад:

    Course Catalog
        ↓
    Select Course
        ↓
    Course Overview
        ↓
    Open Lesson
        ↓
    View Lesson Details

На кожному етапі користувач отримує інформацію, необхідну для поточної задачі.

Progressive Disclosure може використовуватися для:

    advanced settings
    filters
    detailed descriptions
    complex forms
    nested navigation
    optional information

Переваги:

    менше візуального перевантаження
    зрозуміліший інтерфейс
    поступове ознайомлення зі складними функціями

Недоліки:

    прихована інформація може бути важко помітною
    користувачеві доводиться робити додаткові переходи
    важливі функції можуть стати менш доступними

Важливо: поступове розкриття не повинно приховувати критично важливу інформацію або створювати зайві кроки.

# Information Architecture та User Flow

Information Architecture визначає структуру інформації, а User Flow описує шлях користувача для виконання конкретної задачі.

Наприклад, IA освітньої платформи:

    Courses
        └── Informatics
            └── Lessons
                └── Lesson 1

User Flow для відкриття уроку:

    Dashboard
        ↓
    Courses
        ↓
    Informatics
        ↓
    Lessons
        ↓
    Lesson 1

Інший User Flow може вести до того самого уроку через пошук:

    Search
        ↓
    Search Results
        ↓
    Lesson 1

Це означає, що одна інформаційна структура може підтримувати кілька шляхів до одного ресурсу.

Важливо:

    IA → what exists and how it is organized

    User Flow → how a user completes a task

User Flow розглядатиметься детальніше в окремому розділі:

    08-user-flow

# Information Architecture та Search

Пошук особливо важливий для продуктів із великою кількістю контенту.

Search допомагає користувачеві знаходити інформацію, коли він не знає її точного розташування в ієрархії.

Наприклад:

    Search: JavaScript arrays

    Results:
        Array Methods
        Array Iteration
        Array Reference

Якісний пошук залежить не лише від пошукового поля, а й від організації контенту.

Важливі чинники:

    meaningful titles
    metadata
    consistent terminology
    content categories
    relevant tags
    searchable text
    filters
    sorting

## Search vs Navigation

Navigation:

    допомагає рухатися між розділами

Search:

    допомагає знайти потрібну інформацію за запитом

У невеликому сайті може бути достатньо простої навігації.

У великій документації або каталозі зазвичай потрібні і навігація, і пошук.

## Filters

Filters — інструменти, які дозволяють звузити набір результатів за характеристиками.

Наприклад:

    Subject: Informatics
    Level: Beginner
    Language: Ukrainian

Фільтри особливо корисні, коли користувач має багато результатів і конкретні критерії вибору.

## Tags

Tags — мітки, які описують тематику або властивості контенту.

Наприклад:

    JavaScript
    Frontend
    Beginner
    Tutorial

Tags можуть створювати зв'язки між матеріалами, які належать до різних категорій.

Однак надмірна кількість непослідовних тегів може ускладнювати пошук і підтримку системи.

# Як створити Information Architecture

Розроблення IA — це процес, який починається з розуміння користувачів і контенту та завершується перевіркою структури.

## Step 1 — Understand Users

Визначити:

    target audience
    user needs
    user goals
    common tasks
    user terminology

Наприклад, в LMS користувачами можуть бути:

    Students
    Teachers
    Parents
    Administrators

Їхні задачі відрізняються, тому структура повинна враховувати ці відмінності.

## Step 2 — Define Content Scope

Визначити, яка інформація та функції повинні бути доступні.

Наприклад:

    courses
    lessons
    assignments
    grades
    schedules
    profiles

Не варто створювати категорії лише тому, що вони є в іншому продукті.

## Step 3 — Create Content Inventory

Зібрати перелік наявних сторінок і типів контенту.

Для нового продукту це може бути попередній список майбутнього контенту.

Для наявного продукту — інвентаризація поточного стану.

## Step 4 — Group Related Content

Згрупувати споріднені елементи.

Наприклад:

    Learning
        ├── Courses
        ├── Lessons
        └── Assignments

    People
        ├── Students
        └── Teachers

Групування потрібно перевіряти на відповідність задачам користувачів.

## Step 5 — Define Taxonomy and Labels

Визначити:

    categories
    subcategories
    labels
    metadata
    relationships

Наприклад:

    Courses
        ├── Mathematics
        ├── Informatics
        └── English

Назви повинні бути зрозумілими та послідовними.

## Step 6 — Build the Hierarchy

Визначити:

    root
    parent pages
    child pages
    sibling pages
    navigation depth

Приклад:

    Home
        └── Courses
            └── Informatics
                └── Lessons

Не потрібно робити структуру глибшою, ніж вимагає сам контент.

## Step 7 — Create a Sitemap

Візуалізувати сторінки та їхні ієрархічні зв'язки.

Sitemap допомагає виявити:

    missing pages
    duplicate sections
    unclear relationships
    unnecessary levels
    inconsistent grouping

## Step 8 — Design Navigation

На основі структури визначити:

    primary navigation
    secondary navigation
    sidebar
    breadcrumbs
    contextual links
    search

Не всі сторінки повинні бути присутні в головному меню.

## Step 9 — Validate with Users

Перевірити структуру за допомогою:

    card sorting
    tree testing
    usability testing
    user interviews

Мета — з'ясувати, чи відповідає структура очікуванням користувачів.

## Step 10 — Iterate

Після тестування:

    identify problems
        ↓
    revise labels
        ↓
    adjust categories
        ↓
    simplify hierarchy
        ↓
    test again

Information Architecture може змінюватися разом із розвитком продукту.

# Практичний приклад — Information Architecture для LMS

Розглянемо просту систему управління навчанням.

Мета користувача:

    знайти курс
    відкрити урок
    виконати завдання
    переглянути оцінку

Це попередня структура, яку потрібно перевірити з урахуванням реальних задач користувачів.

## 3. Створюємо Sitemap

    Чи потрібні пошук і фільтри?
    Чи потрібні різні ролі доступу?
    Як структура працюватиме на мобільному пристрої?

Хороша IA повинна підтримувати розвиток продукту без постійного перебудовування всіх категорій.

# Information Architecture Checklist

Перед переходом до детального UI-дизайну перевірити структуру.

## Users and Goals

- [ ] Визначено основні групи користувачів.
- [ ] Зрозумілі основні задачі користувачів.
- [ ] Враховано термінологію користувачів.
- [ ] Визначено найважливіші сценарії пошуку інформації.

## Content

- [ ] Визначено основні типи контенту.
- [ ] Зібрано Content Inventory, якщо продукт уже існує.
- [ ] Виявлено дублікати та застарілий контент.
- [ ] Визначено основні метадані.
- [ ] Встановлено логічні зв'язки між сутностями.

## Structure

- [ ] Створено ієрархію сторінок.
- [ ] Визначено parent і child relationships.
- [ ] Перевірено breadth і depth.
- [ ] Категорії мають зрозумілі межі.
- [ ] Немає зайвих рівнів вкладеності.
- [ ] Структура підтримує майбутнє розширення.

## Labels

- [ ] Назви зрозумілі користувачам.
- [ ] Однакові поняття мають послідовні назви.
- [ ] Різні сутності не змішані під одним неоднозначним терміном.
- [ ] Назви дій описують очікуваний результат.

## Navigation and Search

- [ ] Визначено основні розділи навігації.
- [ ] Користувач розуміє, де перебуває.
- [ ] Визначено, де потрібні breadcrumbs.
- [ ] Для великого обсягу контенту передбачено пошук.
- [ ] Фільтри відповідають реальним критеріям користувачів.
- [ ] Важливий контент доступний через зрозумілі шляхи.

## Validation

- [ ] Структуру перевірено на відповідність задачам користувачів.
- [ ] Проведено або заплановано card sorting.
- [ ] Проведено або заплановано tree testing.
- [ ] Проблемні labels та категорії переглянуто.
- [ ] Структуру можна підтримувати та розширювати.

# Типові помилки

## 1. Структура відображає організацію команди, а не потреби користувача

Наприклад:

    Internal Operations
        └── Academic Administration
            └── Student Results

Користувачеві потрібні оцінки, але їх важко знайти.

Краще назвати розділ відповідно до задачі користувача:

    Grades

---

## 2. Занадто багато пунктів у головному меню

    Home
    Courses
    Lessons
    Assignments
    Grades
    Students
    Teachers
    Parents
    Schedule
    Messages
    Documents
    Reports
    Settings
    Help

Надмірна кількість пунктів може ускладнювати вибір.

Що можна зробити:

    згрупувати споріднені розділи
    виділити основні задачі
    перенести допоміжні пункти до відповідних розділів
    перевірити структуру на користувачах

Однак не варто приховувати важливі розділи лише заради коротшого меню.

---

## 3. Занадто глибока ієрархія

    Home
        └── Resources
            └── Educational
                └── Subjects
                    └── Informatics
                        └── Materials
                            └── Lessons

Користувачеві доводиться проходити багато рівнів.

Можливі рішення:

    об'єднати логічно близькі рівні
    додати пошук
    використати контекстні посилання
    переглянути taxonomy
    додати breadcrumbs

---

## 4. Неоднозначні labels

Наприклад:

    Resources
    Center
    Workspace
    Portal
    More

Такі назви можуть бути доречними в певному контексті, але без пояснення часто не повідомляють, що саме міститься в розділі.

Використовувати їх потрібно лише тоді, коли значення зрозуміле цільовій аудиторії.

---

## 5. Дублювання категорій

    Courses
    Learning Materials
    Education Resources

Якщо всі три розділи містять однакові курси, користувач не розуміє, куди переходити.

Потрібно визначити призначення кожного розділу та прибрати непотрібні перетини.

---

## 6. Змішування категорій за різними принципами

Наприклад:

    Learning
    ├── Mathematics
    ├── Teachers
    ├── Videos
    └── 2026

Тут змішані предмет, аудиторія, формат і час.

Для однієї категорії це може бути нелогічно.

Краще розділити різні способи організації:

    Subjects
        └── Mathematics

    People
        └── Teachers

    Formats
        └── Videos

    Archives
        └── 2026

У реальних системах різні принципи можуть співіснувати, але користувачеві потрібно чітко пояснити їхні відмінності.

---

## 7. Створення IA без дослідження користувачів

Дизайнер може побудувати логічну на власну думку структуру, яка не відповідає ментальній моделі аудиторії.

Що робити:

    conduct user research
    use card sorting
    run tree testing
    observe user behavior
    revise the structure

---

## 8. Відсутність масштабованості

Структура може добре працювати з десятьма сторінками, але стати незручною після додавання сотень матеріалів.

Потрібно заздалегідь подумати про:

    new categories
    new content types
    filters
    search
    metadata
    relationships
    URL conventions

Не потрібно проєктувати надмірно складну систему наперед, але слід уникати рішень, які очевидно блокуватимуть розвиток продукту.

---

## 9. Ототожнення Sitemap із Navigation

Sitemap може містити всі сторінки, але меню зазвичай показує лише частину структури.

Наприклад:

    Sitemap
        ├── Courses
        │   ├── Course 1
        │   ├── Course 2
        │   └── Course 3
        ├── Terms of Use

## 10. Ігнорування мобільних користувачів

Складна ієрархія може бути особливо незручною на мобільному пристрої.

Потрібно перевірити:

    доступність основних розділів
    кількість переходів
    зрозумілість категорій
    поведінку пошуку
    можливість повернутися на попередній рівень

Водночас адаптація IA не завжди означає створення іншої структури для мобільної версії. Часто достатньо змінити спосіб її представлення.

# Міні-шпаргалка

## Information Architecture

    IA
        → organize information
        → group content
        → define categories
        → create hierarchy
        → improve findability

## Hierarchy

    Root
        ↓
    Parent
        ↓
    Child

    Siblings
        → elements with the same parent

## Structure

    Hierarchical
        → levels and categories

    Sequential
        → steps in order

    Matrix
        → multiple relationships or paths

    Database-driven
        → pages generated from structured data

## Breadth vs Depth

    Breadth
        → items per level

    Depth
        → number of levels

## Taxonomy

    Taxonomy
        → categories + hierarchy

    Ontology
        → concepts + relationships + properties

## Sitemap

    IA Sitemap
        → visual structure of pages

    XML Sitemap
        → URLs provided for search engines

## Content

    Content Inventory
        → what exists?

    Content Audit
        → what should change?

    Content Model
        → what types of content exist
          and how are they related?

    Metadata
        → information about content

## Research Methods

    Card Sorting
        → how do users group information?

    Tree Testing
        → can users find information
          in the proposed structure?

    Usability Testing
        → can users complete tasks
          in the interface?

## Findability

    Findability
        → find what you are looking for

    Discoverability
        → discover what is available

    Information Scent
        → clues about where a link leads

    Mental Model
        → user's understanding of the system

## IA vs Navigation

    IA
        → structure of information

    Navigation
        → movement between information

## IA Workflow

    Understand Users
        ↓
    Define Content
        ↓
    Group Information
        ↓
    Define Labels
        ↓
    Build Hierarchy
        ↓
    Create Sitemap
        ↓
    Design Navigation
        ↓
    Test with Users
        ↓
    Iterate

# Головне

• Information Architecture — це структура інформації, категорій, сторінок та зв'язків між ними.

• Основна мета IA — допомогти користувачам зрозуміти структуру продукту та знаходити потрібну інформацію.

• IA охоплює більше, ніж навігаційне меню.

• Information Hierarchy визначає відносини між батьківськими та дочірніми елементами.

• Flat Structure має меншу глибину, а Deep Structure — більшу.

• Breadth означає кількість елементів на рівні, а Depth — кількість рівнів.

• Taxonomy визначає систему класифікації та ієрархію категорій.

• Ontology описує поняття, властивості та зв'язки між ними.

• Labels повинні бути зрозумілими, послідовними та відповідати мові користувачів.

• Metadata допомагає організовувати, фільтрувати та знаходити контент.

• Sitemap показує структуру сторінок, але не обов'язково відображає всі шляхи навігації.

• Content Inventory описує наявний контент, Content Audit оцінює його якість, а Content Model описує типи контенту та їхні зв'язки.

• Findability відповідає за можливість знайти потрібну інформацію, а Discoverability — за можливість виявити доступні функції та контент.

• Mental Model описує уявлення користувача про те, як організована та працює система.

• Card Sorting допомагає зрозуміти, як користувачі групують інформацію.

• Tree Testing перевіряє, чи можуть користувачі знайти потрібний елемент у запропонованій ієрархії.

• Хороша IA повинна враховувати потреби користувачів, обсяг контенту, зрозумілість назв і майбутнє розширення продукту.

• Інформаційну архітектуру потрібно перевіряти на реальних користувачах, а не покладатися лише на інтуїцію дизайнера.

• IA впливає на навігацію, пошук, URL, Content Model та загальну зручність цифрового продукту.

• Найважливіший принцип:

    Organize information around users' needs,
    not only around the internal structure of the organization.
