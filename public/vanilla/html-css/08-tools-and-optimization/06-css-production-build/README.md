# CSS Production Build — підготовка CSS до production

> **CSS Production Build** — це процес підготовки CSS для production-середовища: обробка стилів, оптимізація, мінімізація, видалення непотрібного коду та формування готових файлів для розгортання вебзастосунку.
>
> Мета — отримати CSS, який правильно працює в цільових браузерах, завантажується ефективно та не містить зайвого коду.

---

## 1. Що таке CSS Production Build?

Під час розробки CSS зазвичай зручно писати у зрозумілому вигляді:

    .card {
        display: flex;
        flex-direction: column;
        gap: 16px;
        padding: 24px;
        background-color: white;
        border-radius: 12px;
    }

Такий код легко читати й редагувати.

Але production-версія сайту має бути підготовлена до використання реальними відвідувачами. Залежно від проєкту, процес збірки може:

- об'єднувати або розділяти CSS-файли;
- обробляти сучасний CSS-синтаксис;
- додавати потрібні браузерні префікси;
- мінімізувати CSS;
- видаляти невикористані стилі;
- створювати окремі файли для різних сторінок або компонентів;
- додавати хеші до назв файлів для кешування;
- генерувати source maps, якщо це передбачено конфігурацією.

### Приклад CSS до мінімізації

    .card {
        padding: 24px;
        color: #222222;
        background-color: white;
    }

### Можливий результат після мінімізації

    .card{padding:24px;color:#222;background-color:#fff}

Це ілюстрація: конкретний результат залежить від інструментів і налаштувань.

**Важливо:** production build — це не лише мінімізація CSS. Це весь процес підготовки стилів до розгортання.

---

## 2. Development і Production

Під час розробки та в production потрібні різні властивості збірки.

| Ознака | Development | Production |
|---|---|---|
| Читабельність CSS | Зазвичай важлива | Може бути меншою |
| Мінімізація | Зазвичай не потрібна | Часто використовується |
| Source maps | Корисні для налагодження | Залежить від політики проєкту |
| Перезбирання | Швидке, під час змін | Оптимізоване для фінального результату |
| Діагностика | Зручні повідомлення про помилки | Важливі перевірки та стабільний результат |
| Кешування | Залежить від dev-сервера | Часто використовуються хешовані файли |
| Видалення невикористаного CSS | Не завжди | Може виконуватися за потреби |

### Development

Під час розробки важливо швидко бачити зміни:

    npm run dev

### Production

Перед розгортанням створюється готова збірка:

    npm run build

Команди залежать від проєкту та інструментів. У звичайному проєкті HTML/CSS/JS вони можуть бути іншими.

## 3. Основні етапи CSS Production Build

Типовий процес можна подати так:

    Вихідні CSS-файли
        ↓
    Обробка CSS
        ↓
    Перетворення сучасного синтаксису, якщо потрібно
        ↓
    Додавання потрібних префіксів, якщо потрібно
        ↓
    Видалення невикористаних стилів, якщо налаштовано
        ↓
    Мінімізація CSS
        ↓
    Формування production-файлів
        ↓
    Розгортання сайту

Не кожен проєкт використовує всі ці етапи.

Порядок залежить від збірника, конфігурації та інструментів. Наприклад, Sass спочатку компілюється в CSS, а потім згенерований CSS може проходити через PostCSS та інші етапи обробки.

### Основні поняття

| Поняття | Призначення |
|---|---|
| Build | Формування готових файлів проєкту |
| Minification | Зменшення розміру CSS без зміни його передбачуваної поведінки |
| Autoprefixer | Додавання потрібних браузерних префіксів |
| PostCSS | Обробка CSS за допомогою плагінів |
| Purge CSS / видалення невикористаних стилів | Зменшення CSS шляхом вилучення стилів, які не використовуються в застосунку |
| Code splitting | Розділення коду на окремі частини |
| Cache busting | Оновлення URL ресурсів, щоб браузер не використовував застарілу версію з кешу |
| Source maps | Зв'язок між згенерованим кодом і вихідними файлами для налагодження |

## 4. Мінімізація CSS

**Мінімізація (minification)** — це зменшення розміру CSS-файлу шляхом видалення зайвих символів та виконання безпечних оптимізацій.

Залежно від інструмента можуть видалятися:

- зайві пробіли;
- переноси рядків;
- коментарі;
- непотрібні крапки з комою;
- зайві символи в кольорах;
- інші конструкції, які можна безпечно скоротити.

### До мінімізації

    .button {
        color: #ffffff;
        background-color: #0066cc;
        padding: 12px 20px;
        border-radius: 6px;
    }

### Після мінімізації

    .button{color:#fff;background-color:#06c;padding:12px 20px;border-radius:6px}

Приклад демонструє можливий результат, а не обов'язково точний вивід конкретного інструмента.

### Для чого це потрібно?

Менший CSS-файл зазвичай означає:

- менше даних для передавання мережею;
- менший обсяг завантажуваних ресурсів;
- потенційно швидше завантаження сторінки.

Проте фактичний ефект залежить від розміру CSS, мережі, кешування, способу завантаження та інших чинників.

### Чи потрібно мінімізувати CSS вручну?

Ні. У сучасних проєктах мінімізацію зазвичай виконує збірник або спеціальний оптимізатор.

Не варто вручну стискати CSS, щоб отримати production-файл.

## 5. Видалення невикористаного CSS

У проєкті можуть накопичуватися стилі, які більше не використовуються.

Наприклад:

    .old-banner {
        display: block;
        padding: 20px;
    }

    .unused-card {
        border: 1px solid #cccccc;
    }

Якщо відповідні класи більше не використовуються, їх можна розглядати як кандидатів на видалення.

Однак автоматичне видалення потребує обережності.

### Чому це складніше, ніж здається?

Деякі класи можуть створюватися динамічно:

    const className = isActive ? "button-active" : "button";

Або формуватися через шаблони:

    const className = `color-${color}`;

Інструмент аналізу CSS може не визначити всі можливі значення, якщо вони не присутні в коді у статичному вигляді.

### Ризики автоматичного видалення

- зникають стилі для динамічних класів;
- ламаються стани компонентів;
- зникають стилі модальних вікон або меню;
- порушується оформлення сторінок, які рідко відкриваються;
- вилучаються класи, що формуються сторонніми бібліотеками.

### Правильний підхід

1. Перевіряти, які файли аналізує інструмент.
2. Налаштовувати шляхи до шаблонів і компонентів.
3. За потреби використовувати safelist — перелік класів, які не можна видаляти.
4. Тестувати сторінки та інтерактивні стани після збірки.

**Запам'ятай:** видалення невикористаного CSS може суттєво зменшити файл, але помилкова конфігурація здатна зламати інтерфейс.

## 6. Autoprefixer у production-збірці

Autoprefixer — PostCSS-плагін, який додає потрібні браузерні префікси відповідно до цільових браузерів.

Наприклад, вихідний CSS:

    .container {
        display: flex;
        user-select: none;
    }

Після обробки для певного набору браузерів результат може містити додаткові варіанти властивостей.

Не всі властивості потребують префіксів, а результат залежить від Browserslist.

### Чому Autoprefixer корисний?

- автоматизує частину роботи із сумісністю;
- допомагає уникнути ручного дублювання властивостей;
- дає змогу централізовано визначати цільові браузери.

### Чи потрібно підключати його до кожного проєкту?

Не обов'язково.

Перед додаванням Autoprefixer перевір, які можливості вже забезпечують Vite, Next.js або інший збірник.

**Важливо:** Autoprefixer не є універсальним засобом підтримки старих браузерів. Він не реалізує всі CSS-властивості й не замінює тестування.

## 7. PostCSS у production-збірці

**PostCSS** — інструмент для обробки CSS за допомогою плагінів.

У production-збірці через нього можуть виконуватися різні перетворення:

- додавання браузерних префіксів;
- обробка деяких можливостей сучасного CSS;
- оптимізація CSS;
- інші перетворення, потрібні проєкту.

### Приклад конфігурації

Файл `postcss.config.mjs`:

    export default {
        plugins: {
            autoprefixer: {},
        },
    };

Ця конфігурація підключає Autoprefixer. Вона сама по собі не гарантує мінімізацію CSS.

### Приклад з оптимізацією

Якщо проєкт окремо використовує cssnano, конфігурація може виглядати так:

    export default {
        plugins: {
            autoprefixer: {},
            cssnano: {},
        },
    };

Для такого прикладу потрібно встановити обидва пакети:

    npm install -D postcss autoprefixer cssnano

**Зверни увагу:** цей конфіг не слід без перевірки копіювати в будь-який проєкт. Збірники можуть мати власні стандартні налаштування та інші плагіни. Додаткові плагіни варто підключати лише тоді, коли вони потрібні.

## 8. cssnano — оптимізація CSS

**cssnano** — інструмент мінімізації та оптимізації CSS, який зазвичай використовується як PostCSS-плагін.

### Встановлення

    npm install -D postcss cssnano

Якщо PostCSS уже встановлений, повторно встановлювати його не потрібно.

### Приклад використання

    import postcss from "postcss";
    import cssnano from "cssnano";

    const css = `
        .card {
            color: #ffffff;
            padding: 16px;
        }
    `;

    const result = await postcss([
        cssnano(),
    ]).process(css, {
        from: undefined,
    });

    console.log(result.css);

Це демонстраційний приклад програмного використання PostCSS і cssnano. У реальному проєкті частіше використовують налаштування збірника, а не запускають таку обробку вручну для кожного файлу.

### Autoprefixer і cssnano — різні інструменти

| Інструмент | Основне завдання |
|---|---|
| Autoprefixer | Додавання потрібних префіксів |
| cssnano | Мінімізація та оптимізація CSS |
| PostCSS | Запуск і координація плагінів |

Не плутай сумісність із браузерами та зменшення розміру файлів: це різні задачі.

## 9. CSS Production Build у звичайному HTML/CSS-проєкті

Для невеликого навчального проєкту не завжди потрібен складний збірник.

Якщо проєкт має таку структуру:

    my-project/
    ├── index.html
    ├── styles.css
    ├── script.js
    └── images/

Сайт може працювати без жодного build-інструмента.

Але якщо ти хочеш автоматизувати обробку CSS, можна додати npm і PostCSS.

### Приклад структури

    my-project/
    ├── src/
    │   ├── index.html
    │   ├── styles.css
    │   └── script.js
    ├── dist/
    ├── package.json
    └── postcss.config.mjs

Тут:

- `src/` — вихідні файли;
- `dist/` — підготовлені файли для розгортання;
- `package.json` — залежності та команди;
- `postcss.config.mjs` — конфігурація PostCSS.

Це лише один із можливих варіантів структури. У деяких проєктах HTML, CSS і JavaScript розташовуються інакше.

### Що може відбуватися під час збірки?

    src/styles.css
        ↓
    PostCSS
        ↓
    Autoprefixer
        ↓
    cssnano
        ↓
    dist/styles.css

Після цього production-версія HTML повинна посилатися на правильний згенерований CSS-файл.

Наприклад:

    <link rel="stylesheet" href="./styles.css">

Якщо готовий CSS розміщений у `dist/`, шлях у HTML потрібно визначити відповідно до структури опублікованого сайту.

Не копіюй шлях навмання: він залежить від того, яку теку ти публікуєш і як налаштований хостинг.

## 10. Production Build у Vite

Vite — інструмент розробки та збірки сучасних вебпроєктів.

Він може автоматично обробляти CSS, створювати production-файли та застосовувати оптимізації, передбачені конфігурацією.

### Типовий цикл роботи

    Написання HTML, CSS і JavaScript
        ↓
    npm run dev
        ↓
    Розробка та перевірка
        ↓
    npm run build
        ↓
    Production-файли в dist/
        ↓
    Розгортання

### Основні команди

Запуск сервера розробки:

    npm run dev

Створення production-збірки:

    npm run build

Перегляд готової збірки локально:

    npm run preview

Остання команда працює, якщо в `package.json` є відповідний скрипт. У типовому шаблоні Vite він зазвичай уже налаштований.

### Приклад `package.json`

    {
        "scripts": {
            "dev": "vite",
            "build": "vite build",
            "preview": "vite preview"
        }
    }

Це спрощений приклад. У реальному проєкті в `package.json` також будуть залежності та інші поля.

### Що створює Vite?

Зазвичай готові файли розміщуються в `dist/`.

Приблизна структура:

    dist/
    ├── index.html
    └── assets/
        ├── index-abc123.css
        └── index-def456.js

Назви файлів тут умовні. Фактичні назви, структура та кількість файлів залежать від збірки.

Хеші в назвах файлів допомагають браузерам відрізняти нові версії ресурсів від старих під час кешування.

### Чи потрібно окремо встановлювати cssnano?

Не обов'язково. Спочатку перевір стандартну production-збірку Vite та її документацію. Додавай окремі інструменти лише тоді, коли є конкретна потреба.

## 11. Production Build у Next.js

Next.js має власну систему production-збірки.

У типовому Next.js-проєкті команда:

    npm run build

запускає production-збірку застосунку.

Для розробки зазвичай використовується:

    npm run dev

А для запуску готового production-застосунку — скрипт на зразок:

    npm run start

Точні команди визначаються `package.json` і поточною конфігурацією проєкту.

### Приклад `package.json`

    {
        "scripts": {
            "dev": "next dev",
            "build": "next build",
            "start": "next start"
        }
    }

Це типовий спрощений приклад для проєкту Next.js; конкретна конфігурація може відрізнятися.

### Як обробляється CSS?

Залежно від способу підключення стилів, Next.js може обробляти:

- глобальні CSS-файли;
- CSS Modules;
- CSS, імпортований компонентами;
- стилі, які використовує інша інтегрована система.

Під час production-збірки CSS обробляється в межах інфраструктури Next.js.

### Чи потрібно самостійно створювати `dist/`?

Не обов'язково.

Next.js зазвичай використовує власну директорію `.next/` для результатів збірки. Не потрібно вручну копіювати туди CSS або змінювати файли збірки.

### Чи потрібно додавати Autoprefixer і cssnano?

Не автоматично.

Спочатку перевір стандартну поведінку поточної версії Next.js. Власна конфігурація PostCSS може змінити стандартний процес обробки, тому її потрібно налаштовувати обережно.

**Запам'ятай:** у Vite часто працюють із готовою текою `dist/`, а Next.js має власну структуру та процес production-збірки.

## 12. CSS Code Splitting

**Code splitting** — поділ коду на окремі частини, які можуть завантажуватися незалежно.

Для CSS це може означати формування окремих стилів для різних частин застосунку або маршрутів.

### Навіщо це потрібно?

У великому застосунку не завжди доцільно завантажувати всі стилі для всіх сторінок відразу.

Наприклад:

    Сторінка каталогу
        ├── загальні стилі
        └── стилі каталогу

    Сторінка профілю
        ├── загальні стилі
        └── стилі профілю

За правильної архітектури це може зменшити обсяг стилів, необхідних для першого завантаження певної сторінки.

### Чи потрібно вручну розділяти CSS?

Не завжди.

Сучасні збірники можуть керувати CSS-ресурсами автоматично. Результат залежить від того, як організовано імпорти, компоненти та маршрути.

### На що звернути увагу?

- чи не завантажуються ті самі стилі кілька разів;
- чи правильно працюють стилі після переходу між маршрутами;
- чи не зникають стилі компонентів під час навігації;
- чи відповідає фактична поведінка очікуваному розділенню коду.

## 13. Cache Busting і хешовані CSS-файли

Браузери можуть зберігати CSS у кеші, щоб не завантажувати його повторно під час кожного відвідування сайту.

Це корисно, але створює проблему: після оновлення стилів браузер може використати старий файл, якщо URL не змінився, а кеш налаштований неправильно.

### Приклад без хешу

    styles.css

Якщо вміст змінюється, URL залишається тим самим.

### Приклад із хешем

    styles-a1b2c3.css

Після зміни вмісту збірник може створити іншу назву:

    styles-d4e5f6.css

Тепер нова версія має інший URL.

Це один зі способів cache busting.

### Переваги

- браузер може довго кешувати файли з незмінним вмістом;
- після оновлення CSS новий URL допомагає завантажити актуальну версію;
- зменшується ризик використання старого CSS після розгортання.

### Чи потрібно перейменовувати CSS вручну?

Ні. У сучасних збірниках хешовані назви часто генеруються автоматично.

Не перейменовуй файли самостійно, якщо збірник уже керує їхніми назвами та посиланнями.

---

## 14. Source Maps у production

**Source maps** — файли, які допомагають пов'язати згенерований код із вихідними файлами.

Наприклад, після мінімізації CSS складніше визначити, звідки походить певне правило. Source map може допомогти інструментам розробника показати вихідний файл і відповідну позицію.

### Навіщо потрібні source maps?

- налагодження стилів;
- пошук джерела правила;
- діагностика помилок після обробки CSS;
- аналіз проблем, які виникають лише після збірки.

### Чи варто публікувати source maps?

Це залежить від політики проєкту.

Потрібно враховувати:

- чи є source maps необхідними для діагностики;
- чи містять вони шляхи або інформацію, яку не потрібно відкривати публічно;
- чи потрібно завантажувати їх до системи моніторингу помилок;
- як налаштовані сервер і хостинг.

Source maps не є обов'язково поганими для production, але їхню публікацію потрібно планувати.

---

## 15. Як перевірити production-збірку CSS?

Після виконання команди збірки не варто відразу вважати результат правильним.

Потрібно перевірити як файли, так і поведінку сайту.

### Крок 1. Запусти збірку

Для Vite:

    npm run build

Для Next.js:

    npm run build

Для іншого проєкту використовуй команду, визначену його `package.json`.

### Крок 2. Перевір результат

Для Vite переглянь вміст `dist/`.

Для Next.js враховуй його власну структуру збірки та інструменти.

Перевір:

- чи створилися потрібні файли;
- чи присутні стилі;
- чи немає очевидних помилок обробки;
- чи правильно працюють посилання на CSS;
- чи не залишилися непотрібні файли у теці, яку ти плануєш публікувати.

### Крок 3. Перевір сайт

Перевір щонайменше:

1. головну сторінку;
2. інші основні маршрути;
3. адаптивну версію;
4. мобільне меню;
5. форми;
6. модальні вікна;
7. інтерактивні стани;
8. сторінки, які використовують динамічні класи.

### Крок 4. Перевір інструменти розробника

У браузері відкрий Developer Tools.

Перевір:

- чи завантажуються CSS-файли без помилок;
- чи немає помилок 404;
- чи немає помилок у Console;
- чи правильно застосовуються стилі;
- чи не перекриваються стилі несподіваними правилами.

### Крок 5. Перевір поведінку після розгортання

Локальна збірка може працювати, але розгорнутий сайт — ні, якщо неправильно налаштовані шляхи, базова URL-адреса або кешування.

Тому перевіряй production-версію після публікації.

## 16. Аналіз розміру CSS

Оптимізація має сенс, коли ти можеш оцінити результат.

Не обов'язково намагатися зробити кожен CSS-файл якомога меншим. Важливо зрозуміти, який обсяг стилів реально завантажується і чи є очевидні проблеми.

### Що можна перевіряти?

- загальний розмір CSS;
- кількість CSS-файлів;
- чи немає дублювання великих блоків;
- чи завантажуються непотрібні стилі;
- чи не завеликий CSS для першого завантаження;
- як кешування впливає на повторні відвідування.

### Практична перевірка

1. Створи production-збірку.
2. Знайди CSS-файли.
3. Переглянь їхній розмір.
4. Перевір мережеві запити в Developer Tools.
5. За потреби порівняй результат до та після оптимізації.

### Не оптимізуй навмання

Наприклад, додавання додаткового плагіна може збільшити складність конфігурації, але не дати помітного виграшу.

Краще спочатку визначити проблему, потім обрати інструмент і перевірити результат.

## 17. Типові помилки під час production-збірки CSS

### Помилка 1. Вважати, що production build — це лише мінімізація

Збірка може включати багато інших процесів.

**Правильно:** розглядати build як увесь процес формування готових файлів.

### Помилка 2. Вручну редагувати згенеровані CSS-файли

Зміни можуть бути втрачені під час наступної збірки.

**Правильно:** редагувати вихідні файли й конфігурацію інструментів.

### Помилка 3. Видаляти невикористаний CSS без тестування

Динамічні класи або стилі окремих станів можуть зникнути.

**Правильно:** налаштувати аналіз і перевірити основні сценарії застосунку.

### Помилка 4. Додавати всі можливі плагіни

Зайві інструменти ускладнюють збірку та можуть конфліктувати між собою.

**Правильно:** додавати плагіни під конкретні вимоги.

### Помилка 5. Копіювати конфігурацію PostCSS з іншого проєкту без перевірки

Різні збірники мають різні стандартні налаштування.

**Правильно:** перевіряти документацію поточного інструмента та зберігати необхідні плагіни.

### Помилка 6. Плутати development і production

Dev-сервер не завжди поводиться так само, як готова збірка.

**Правильно:** регулярно перевіряти production build.

### Помилка 7. Не перевіряти шляхи до CSS

Після переміщення файлів або зміни базового шляху стилі можуть перестати завантажуватися.

**Правильно:** перевірити посилання у згенерованому HTML і мережеві запити.

### Помилка 8. Не перевіряти динамічні стани

Меню, модальні вікна й активні кнопки можуть використовувати класи, які неочевидні для статичного аналізу.

**Правильно:** перевіряти не лише початковий вигляд сторінки, а й інтерактивну поведінку.

### Помилка 9. Публікувати неправильну теку

Наприклад, статичний сайт може очікувати готові файли з `dist/`, а замість них публікується лише `src/`.

**Правильно:** перевірити вимоги хостингу й налаштувати публікацію саме результату збірки.

### Помилка 10. Не перевіряти кешування після розгортання

Користувачі можуть бачити старі стилі через невдалу конфігурацію кешу.

**Правильно:** використовувати відповідну стратегію кешування та хешовані назви ресурсів, якщо це підтримує збірник.

## 18. Практичні завдання

### Завдання 1. Розберися з різницею між Development і Production

Створи невеликий HTML/CSS/JS-проєкт.

Підготуй два сценарії:

- звичайна розробка;
- production-збірка.

Відповідай на запитання:

1. Які файли використовуються під час розробки?
2. Які файли публікуються?
3. Чи змінюється CSS під час збірки?
4. Чи створюються нові назви файлів?
5. Як перевірити, що опублікований сайт використовує правильні стилі?

### Завдання 2. Досліди мінімізацію CSS

Вихідний файл:

    .card {
        color: #ffffff;
        background-color: #000000;
        padding: 20px;
        margin: 0;
    }

1. Створи production-збірку.
2. Знайди готовий CSS.
3. Порівняй його з вихідним.
4. Запиши, які зміни відбулися.
5. Переконайся, що вигляд компонента не змінився.

### Завдання 3. Створи збірку для звичайного CSS-проєкту

Створи структуру:

    project/
    ├── src/
    │   ├── index.html
    │   └── styles.css
    ├── dist/
    ├── package.json
    └── postcss.config.mjs

Підключи PostCSS та Autoprefixer.

Додай скрипт обробки CSS і перевір результат.

Мета — зрозуміти, як створюється окремий production-файл.

### Завдання 4. Використай Vite

1. Створи проєкт Vite.
2. Додай кілька компонентів зі своїми стилями.
3. Запусти `npm run dev`.
4. Перевір вигляд сайту.
5. Виконай `npm run build`.
6. Знайди теку `dist/`.
7. Перевір готові CSS-файли.
8. Запусти `npm run preview`.
9. Порівняй production-перегляд із development.

### Завдання 5. Перевір видалення невикористаного CSS

Створи кілька класів:

    .used-card {
        padding: 16px;
    }

    .unused-card {
        padding: 24px;
    }

    .dynamic-active {
        color: green;
    }

Використай один клас у HTML, а інші залиш невикористаними.

Потім досліди, як конкретний інструмент визначає невикористані стилі.

Не видаляй CSS автоматично без перевірки динамічних класів.

### Завдання 6. Досліди хешовані файли

1. Створи production-збірку.
2. Знайди CSS-файл із хешем у назві, якщо збірник його генерує.
3. Зміни вихідний CSS.
4. Створи нову збірку.
5. Порівняй назви файлів.

Поясни, як це допомагає керувати кешуванням.

### Завдання 7. Перевір production-сайт

Після збірки перевір:

- усі основні сторінки;
- мобільне меню;
- форми;
- кнопки;
- модальні вікна;
- адаптивну верстку;
- шляхи до CSS;
- помилки в Console та Network.

Склади короткий чекліст, який можна використовувати перед кожним розгортанням.
