# 04. PostCSS — Обробка та трансформація CSS

> **PostCSS** — це інструмент для обробки CSS за допомогою JavaScript-плагінів. Він аналізує CSS-код, перетворює його на структуроване представлення, дозволяє плагінам змінювати це представлення та генерує результат.

PostCSS не є окремою мовою стилів і не замінює звичайний CSS. Це інструментальна платформа, яка допомагає автоматизувати роботу з CSS: від перевірки коду до оптимізації та перетворення сучасного синтаксису.

PostCSS використовують для:
- автоматичного додавання браузерних префіксів;
- перетворення сучасного CSS для сумісності з цільовими браузерами;
- мініфікації CSS;
- перевірки якості коду;
- використання CSS-інструментів у процесі збирання;
- роботи з плагінами;
- інтеграції з Vite, Next.js та іншими інструментами;
- автоматизації CSS-процесів у великих проєктах.

---

# 1. Що таке PostCSS

## 1.1. Основна ідея

Звичайний CSS описує зовнішній вигляд сторінки:

    .card {
        padding: 16px;
        border-radius: 8px;
        background-color: white;
    }

PostCSS дозволяє автоматично обробити цей код за допомогою спеціальних плагінів.

Наприклад, один плагін може додати необхідні браузерні префікси, інший — перевірити синтаксис, а ще один — мінімізувати результат.

Спрощена схема роботи:

    Вихідний CSS
        ↓
    PostCSS
        ↓
    CSS Parser
        ↓
    CSS AST
        ↓
    Плагіни обробляють CSS
        ↓
    Генерація результату
        ↓
    Оброблений CSS

**AST (Abstract Syntax Tree)** — абстрактне синтаксичне дерево, структуроване представлення коду, з яким можуть працювати інструменти.

Замість того щоб просто шукати та замінювати текст, PostCSS дозволяє плагінам аналізувати правила, селектори, декларації та інші частини CSS.

## 1.2. Чим PostCSS відрізняється від CSS

| CSS | PostCSS |
|---|---|
| Мова опису стилів | Інструмент обробки CSS |
| Визначає зовнішній вигляд | Допомагає автоматизувати роботу зі стилями |
| Інтерпретується браузером | Зазвичай працює під час розробки або збирання |
| Містить селектори, властивості та значення | Аналізує та може змінювати CSS |
| Не потребує PostCSS для звичайного використання | Може бути частиною інструментального ланцюжка |

PostCSS не обов'язково потрібен для кожної вебсторінки. Його користь зростає, коли проєкт потребує автоматизації, перетворень або перевірок CSS.

## 1.3. Для чого потрібен PostCSS

Уявімо, що в проєкті є багато CSS-файлів.

Розробник хоче:
- писати сучасний CSS;
- підтримувати визначені версії браузерів;
- автоматично додавати префікси там, де це потрібно;
- знаходити помилки;
- створювати компактний production CSS.

Замість виконання всіх операцій вручну можна побудувати процес обробки CSS за допомогою PostCSS і відповідних плагінів.

# 2. PostCSS — це платформа плагінів

## 2.1. Сам PostCSS не виконує всі оптимізації

PostCSS є ядром системи обробки. Конкретні можливості зазвичай забезпечують плагіни.

Наприклад:

| Завдання | Інструмент або плагін |
|---|---|
| Додавання браузерних префіксів | Autoprefixer |
| Мініфікація CSS | cssnano |
| Перевірка якості CSS | Stylelint |
| Перетворення сучасного CSS | PostCSS-плагіни, наприклад `postcss-preset-env` |
| Розширення синтаксису | Відповідні PostCSS-плагіни |
| Обробка файлів під час збирання | Vite, webpack або інший інструмент із PostCSS |

Не всі ці інструменти є плагінами PostCSS у вузькому значенні. Наприклад, Stylelint — окремий лінтер, який перевіряє CSS, а Vite — інструмент збирання, що може використовувати PostCSS у процесі обробки стилів.

## 2.2. Що означає plugin

**Plugin** — це модуль, який додає певну можливість до інструмента.

Наприклад, Autoprefixer аналізує CSS і за потреби додає префікси для цільових браузерів.

Вихідний CSS:

    .example {
        user-select: none;
    }

Залежно від налаштувань і цільових браузерів результат може містити додаткові декларації:

    .example {
        -webkit-user-select: none;
        user-select: none;
    }

Це лише ілюстрація. Фактичний результат залежить від версій інструментів і цільових браузерів.

## 2.3. Чому важливі цільові браузери

Інструменти обробки CSS повинні знати, для яких браузерів готується застосунок.

Наприклад, для сучасного навчального проєкту можуть бути достатніми актуальні версії браузерів.

Для корпоративного застосунку іноді потрібно підтримувати старіші браузери.

Цільові браузери впливають на те:
- які префікси можуть бути потрібні;
- які можливості потрібно трансформувати;
- який результат згенерує інструмент;
- наскільки складним буде CSS після обробки.

Не потрібно додавати всі можливі префікси вручну.

# 3. Встановлення PostCSS

PostCSS часто використовується разом із Node.js та npm.

Перевір, чи встановлені Node.js і npm:

    node -v
    npm -v

Якщо ти працюєш у звичайному статичному HTML/CSS-проєкті без Node.js-інструментів, PostCSS не потрібен для того, щоб браузер міг відображати CSS.

Він стає потрібним, коли ти хочеш автоматизувати обробку стилів.

## 3.1. Створення навчального проєкту

Приклад структури:

    04-postcss/
    └── practice/
        └── basic-postcss/
            ├── package.json
            ├── postcss.config.mjs
            ├── src/
            │   └── styles.css
            └── dist/

Перейди в теку проєкту:

    cd practice/basic-postcss

Ініціалізуй npm-проєкт:

    npm init -y

Встанови PostCSS та інструмент командного рядка:

    npm install -D postcss postcss-cli

Тут:
- `postcss` — основна бібліотека;
- `postcss-cli` — інструмент для запуску обробки через термінал;
- `-D` — скорочення для `--save-dev`, тобто залежність для розробки.

У реальному проєкті спосіб встановлення та запуску може відрізнятися залежно від того, чи використовуєш ти Vite, Next.js або інший збирач.

## 3.2. Перевірка залежностей

Після встановлення можна виконати:

    npm ls postcss postcss-cli

Команда покаже встановлені пакети та їхні версії.

# 4. Перший приклад PostCSS

## 4.1. Створення CSS-файлу

Файл `src/styles.css`:

    .card {
        padding: 16px;
        border-radius: 8px;
        background-color: white;
    }

    .button {
        user-select: none;
        padding: 12px 20px;
    }

Це звичайний CSS.

Сам по собі PostCSS не змінить його, якщо не налаштовано відповідних плагінів.

## 4.2. Запуск PostCSS без плагінів

Якщо конфігурація не потрібна, можна спробувати передати файл на обробку без додаткових плагінів:

    npx postcss src/styles.css -o dist/styles.css

Перед запуском переконайся, що тека `dist` існує. За потреби створи її:

    mkdir dist

Результат буде записаний у `dist/styles.css`.

Без плагінів, які виконують перетворення, вихідний CSS може залишитися практично таким самим.

## 4.3. Що ми вивчили

- PostCSS можна запускати через командний рядок.
- Вхідний і вихідний CSS можуть бути різними файлами.
- Для додаткових перетворень потрібні відповідні плагіни.
- PostCSS не є автоматичним оптимізатором без налаштування.

# 5. Конфігурація PostCSS

## 5.1. Для чого потрібен конфігураційний файл

Конфігурація визначає:
- які плагіни використовуються;
- у якому порядку вони запускаються;
- які параметри їм передаються;
- як обробляється CSS у конкретному проєкті.

Поширені назви конфігураційних файлів:
- `postcss.config.js`;
- `postcss.config.cjs`;
- `postcss.config.mjs`.

Конкретний формат залежить від системи модулів Node.js та інструмента збирання.

## 5.2. Приклад конфігурації з ESM

Створи `postcss.config.mjs`:

    export default {
        plugins: {},
    };

Це базова конфігурація без додаткових плагінів.

## 5.3. Приклад конфігурації з плагіном

Спочатку встанови Autoprefixer:

    npm install -D autoprefixer

Онови `postcss.config.mjs`:

    import autoprefixer from "autoprefixer";

    export default {
        plugins: [
            autoprefixer,
        ],
    };

Тепер PostCSS використовуватиме Autoprefixer під час обробки CSS.

Зверни увагу: сучасний CSS не завжди потребує префіксів. Якщо для цільових браузерів вони не потрібні, Autoprefixer може залишити код без змін.

## 5.4. Порядок плагінів

Плагіни зазвичай виконуються в порядку, визначеному конфігурацією, але конкретна поведінка залежить від API та реалізації плагінів.

Порядок має значення, якщо один плагін змінює код, який аналізує інший.

Наприклад, логічно спочатку виконати необхідні трансформації, а мініфікацію залишити наприкінці процесу.

Не потрібно додавати плагіни без чіткого завдання.

---

# 6. Autoprefixer — автоматичне додавання префіксів

## 6.1. Що таке vendor prefixes

Vendor prefixes — спеціальні префікси CSS-властивостей, які історично використовувалися браузерами для експериментальних або ще не стандартизованих можливостей.

Приклади:
- `-webkit-`;
- `-moz-`;
- `-ms-`.

Наприклад, у певних ситуаціях старі версії браузерів могли потребувати префіксованої декларації:

    .element {
        -webkit-user-select: none;
        user-select: none;
    }

Сьогодні потреба в префіксах значно менша для багатьох поширених властивостей, але в окремих випадках вони все ще можуть бути потрібні.

## 6.2. Чому не варто додавати префікси вручну

Ручне додавання префіксів:
- збільшує обсяг CSS;
- створює повторювані декларації;
- потребує знання сумісності кожної властивості;
- ускладнює підтримку.

Autoprefixer використовує дані про браузерну сумісність і цільові браузери, щоб додавати потрібні префікси автоматично.

## 6.3. Встановлення Autoprefixer

    npm install -D autoprefixer

Конфігурація:

    import autoprefixer from "autoprefixer";

    export default {
        plugins: [
            autoprefixer,
        ],
    };

Команда обробки:

    npx postcss src/styles.css -o dist/styles.css

## 6.4. Browserslist

Autoprefixer використовує налаштування цільових браузерів, які часто задають через Browserslist.

Наприклад, у `package.json` можна додати:

    {
        "browserslist": [
            "defaults"
        ]
    }

Якщо в `package.json` уже є інші поля, їх потрібно зберегти, а `browserslist` додати до наявного об'єкта.

Запис `defaults` означає використання стандартного набору цільових браузерів Browserslist. Це не гарантує підтримку всіх старих браузерів.

Інші приклади запитів Browserslist:

    "last 2 versions"

    "> 0.5%"

    "not dead"

Ці запити мають різний зміст. Перед використанням варто перевірити, чи відповідають вони вимогам проєкту.

## 6.5. Важливе обмеження Autoprefixer

Autoprefixer додає префікси, коли вони потрібні відповідно до цільових браузерів і наявних даних сумісності.

Він не перетворює автоматично будь-яку сучасну CSS-функцію на повністю еквівалентний код для будь-якого старого браузера.

Префікси та трансформації синтаксису — не одне й те саме.

# 7. postcss-preset-env — сучасний CSS

## 7.1. Призначення

`postcss-preset-env` дозволяє використовувати певні сучасні можливості CSS і трансформувати частину синтаксису для цільових браузерів.

Це не означає, що абсолютно всі нові CSS-функції можуть бути перетворені для будь-якого браузера.

Можливості залежать від:
- версії `postcss-preset-env`;
- доступних трансформацій;
- налаштувань;
- цільових браузерів;
- природи конкретної CSS-функції.

## 7.2. Встановлення

    npm install -D postcss-preset-env

Конфігурація:

    import postcssPresetEnv from "postcss-preset-env";

    export default {
        plugins: [
            postcssPresetEnv(),
        ],
    };

Це базовий приклад. Для реального проєкту параметри потрібно налаштувати відповідно до його потреб.

## 7.3. Чим він відрізняється від Autoprefixer

| Autoprefixer | postcss-preset-env |
|---|---|
| Зосереджується на браузерних префіксах | Дозволяє обробляти певні сучасні можливості CSS |
| Використовує дані про сумісність браузерів | Також може орієнтуватися на цільові браузери |
| Не є універсальним трансформатором CSS | Може включати різні трансформації синтаксису |
| Може використовуватися окремо | У певних конфігураціях може включати пов'язану роботу з префіксами |

Перед використанням варто перевірити документацію та конфігурацію конкретної версії інструмента.

## 7.4. Чи потрібен postcss-preset-env кожному проєкту

Ні.

Якщо застосунок використовує лише стандартний CSS і підтримує сучасні браузери, додаткові трансформації можуть бути непотрібними.

Для навчального проєкту достатньо спочатку зрозуміти звичайний CSS, а потім вивчати трансформації як окремий інструментальний рівень.

# 8. cssnano — мініфікація CSS

## 8.1. Що таке cssnano

cssnano — інструмент оптимізації та мініфікації CSS.

Він може:
- видаляти зайве форматування;
- оптимізувати певні значення;
- скорочувати безпечні конструкції;
- зменшувати розмір CSS-файлу.

Вихідний CSS:

    .card {
        margin: 0px;
        padding: 16px;
        color: #ffffff;
    }

Після обробки cssnano результат може виглядати компактніше:

    .card{margin:0;padding:16px;color:#fff}

Це ілюстрація можливого результату. Фактичний вихід залежить від версії та налаштувань cssnano.

## 8.2. Встановлення

    npm install -D cssnano

Конфігурація:

    import autoprefixer from "autoprefixer";
    import cssnano from "cssnano";

    export default {
        plugins: [
            autoprefixer(),
            cssnano(),
        ],
    };

У цьому прикладі Autoprefixer запускається перед cssnano.

## 8.3. Чому мініфікацію зазвичай виконують для production

Під час розробки зручніше працювати з форматованим CSS.

У production компактний CSS може зменшити обсяг переданих даних.

Зазвичай не потрібно вручну редагувати мініфікований файл. Варто підтримувати читабельні вихідні файли та автоматично створювати production-версію.

## 8.4. Чи гарантує cssnano швидший сайт

Ні.

Мініфікація зменшує розмір CSS, але не виправляє:
- надмірно складну архітектуру;
- невикористані стилі, якщо вони не видаляються окремим інструментом;
- проблеми layout;
- важкі анімації;
- повільне завантаження інших ресурсів.

Вона є лише одним із кроків оптимізації.

# 9. PostCSS і Stylelint

## 9.1. Що таке Stylelint

Stylelint — окремий інструмент статичного аналізу CSS.

Він допомагає перевіряти:
- синтаксичні проблеми;
- узгодженість стилю коду;
- порушення командних правил;
- потенційно проблемні конструкції.

Stylelint не потрібно плутати з PostCSS.

PostCSS обробляє CSS за допомогою плагінів, а Stylelint перевіряє код за набором правил.

Stylelint використовує екосистему CSS-парсингу, але його роль відрізняється від ролі PostCSS у процесі збирання.

## 9.2. Встановлення Stylelint

    npm install -D stylelint

Для більшості реальних проєктів також потрібна відповідна конфігурація та набір правил.

Наприклад, можна використовувати офіційний набір правил для стандартного CSS, якщо він сумісний із вибраною версією Stylelint.

## 9.3. Приклад запуску

Якщо конфігурацію вже створено:

    npx stylelint "src/**/*.css"

Команда перевіряє CSS-файли в теці `src`.

Формат шаблону залежить від оболонки та середовища. У різних системах шляхи й лапки можуть оброблятися по-різному.

## 9.4. Чому перевірка коду важлива

Автоматична перевірка допомагає знаходити проблеми раніше, ніж вони потраплять у production.

Проте лінтер не замінює:
- тестування інтерфейсу;
- перевірку адаптивності;
- аналіз браузерної сумісності;
- вимірювання продуктивності.

# 10. PostCSS і CSS Modules

## 10.1. Що таке CSS Modules

CSS Modules — підхід, за якого локальні класи CSS пов'язуються з конкретним модулем.

Наприклад, компонент може мати файл:

    Card.module.css

Вміст:

    .card {
        padding: 16px;
        border-radius: 8px;
        background: white;
    }

    .title {
        font-size: 20px;
    }

Під час обробки інструмент може створювати унікальні назви класів, щоб зменшити конфлікти між компонентами.

## 10.2. Як тут може використовуватися PostCSS

Інструмент збирання може обробляти CSS Modules і додатково запускати відповідні CSS-плагіни.

Наприклад:
- аналізувати CSS;
- застосовувати потрібні трансформації;
- мінімізувати результат;
- формувати production-файли.

Але CSS Modules і PostCSS — різні інструменти.

CSS Modules відповідають за локальність імен класів, а PostCSS — за обробку CSS через плагіни.

## 10.3. Чи потрібно вручну підключати PostCSS до CSS Modules

Не завжди.

Це залежить від того, який інструмент збирання використовується і як він налаштований.

У сучасних збирачах частина обробки CSS може бути інтегрована за замовчуванням.

Перед додаванням окремої конфігурації потрібно перевірити поточні можливості проєкту.

# 11. PostCSS у Vite

## 11.1. Що таке Vite

Vite — інструмент для розробки та збирання сучасних вебзастосунків.

Він може обробляти CSS і підтримує використання PostCSS.

Якщо ти працюєш із простими HTML/CSS/JS-практиками, Vite може бути зручним способом поступово перейти від окремих файлів до проєкту зі збіркою.

## 11.2. Приклад структури

    basic-postcss/
    ├── package.json
    ├── index.html
    ├── postcss.config.mjs
    └── src/
        ├── main.js
        └── styles.css

## 11.3. Встановлення Vite

У новому навчальному проєкті можна виконати:

    npm create vite@latest

Далі обери відповідний шаблон, наприклад Vanilla JavaScript, і виконай команди встановлення залежностей, які покаже інструмент.

Альтернативно, якщо в тебе вже є Vite-проєкт, не потрібно створювати новий.

## 11.4. Як Vite використовує PostCSS

Vite підтримує конфігурацію PostCSS. Якщо в проєкті є розпізнаний конфігураційний файл, Vite може застосувати його під час обробки CSS.

Наприклад, `postcss.config.mjs`:

    import autoprefixer from "autoprefixer";

    export default {
        plugins: [
            autoprefixer(),
        ],
    };

Після цього CSS може проходити відповідну обробку під час розробки та збирання.

Точний процес залежить від конфігурації й версії інструментів.

## 11.5. Запуск

У Vite-проєкті команди зазвичай визначені в `package.json`.

Типовий приклад:

    {
        "scripts": {
            "dev": "vite",
            "build": "vite build",
            "preview": "vite preview"
        }
    }

Якщо `package.json` уже містить інші скрипти, потрібно зберегти їх і додати потрібні команди.

Запуск розробки:

    npm run dev

Production-збирання:

    npm run build

Перегляд результату збирання:

    npm run preview

PostCSS не замінює Vite. Vite організовує процес розробки та збирання, а PostCSS може виконувати частину обробки CSS.

# 12. PostCSS у Next.js

## 12.1. Чи потрібен PostCSS у Next.js

Next.js має власний процес обробки CSS і підтримує інтеграцію з PostCSS.

У типовому проєкті не потрібно встановлювати PostCSS окремо лише для того, щоб використовувати звичайний CSS.

Окрема конфігурація може знадобитися, якщо ти хочеш додати конкретні плагіни або змінити стандартний процес обробки.

## 12.2. Приклад конфігурації

У відповідних конфігураціях Next.js може використовувати файл на кшталт `postcss.config.mjs`.

Наприклад:

    const config = {
        plugins: {},
    };

    export default config;

Це лише форма конфігурації, а не рекомендація замінити нею наявну конфігурацію Next.js.

Якщо в проєкті вже є PostCSS-плагіни, не видаляй їх без перевірки.

## 12.3. Важливо для Next.js

Перед зміною PostCSS-конфігурації:
1. Перевір поточну версію Next.js.
2. Перевір наявний конфігураційний файл.
3. З'ясуй, які плагіни використовуються.
4. Збережи потрібні налаштування.
5. Запусти development-сервер.
6. Виконай production-збирання.
7. Перевір CSS після збірки.

У сучасному фреймворку невдала конфігурація може вплинути на весь процес обробки стилів.

# 13. PostCSS і Tailwind CSS

## 13.1. Чи є Tailwind CSS частиною PostCSS

Ні. Tailwind CSS — окремий CSS-фреймворк, а PostCSS — інструментальна платформа.

Історично та в певних конфігураціях Tailwind інтегрується через PostCSS.

Однак спосіб інтеграції залежить від версії Tailwind CSS.

## 13.2. Чому важлива версія Tailwind

У різних основних версіях Tailwind відрізняються:
- спосіб підключення;
- конфігурація;
- пакет для інтеграції з PostCSS;
- процес генерування CSS.

Тому не варто копіювати конфігурацію з іншої версії без перевірки документації.

## 13.3. Головний висновок

Якщо ти поки вивчаєш HTML і CSS без Tailwind, не потрібно додавати Tailwind лише заради вивчення PostCSS.

Спочатку достатньо зрозуміти:
- навіщо існує PostCSS;
- як працюють плагіни;
- як виконується обробка CSS;
- як працюють Autoprefixer і мініфікація.

# 14. PostCSS і Sass

## 14.1. Що таке Sass

Sass — CSS-препроцесор, який додає власний синтаксис та інші можливості для організації стилів.

Наприклад, Sass дозволяє використовувати змінні в синтаксисі SCSS:

    $primary-color: #2563eb;

    .button {
        background-color: $primary-color;
    }

Це приклад SCSS, а не звичайного CSS.

## 14.2. Чим Sass відрізняється від PostCSS

| Sass | PostCSS |
|---|---|
| Препроцесор із власними можливостями | Платформа обробки CSS |
| Має синтаксиси Sass і SCSS | Зазвичай працює зі стандартним CSS та сумісними розширеннями |
| Компілює SCSS у CSS | Може трансформувати, перевіряти або мінімізувати CSS через плагіни |
| Має власні змінні та правила вкладеності | Підтримує плагіни, які можуть додавати відповідні можливості |

## 14.3. Чи можуть вони працювати разом

Так, але потрібно правильно організувати послідовність інструментів.

Спрощено:

    SCSS
      ↓
    Sass Compiler
      ↓
    CSS
      ↓
    PostCSS Plugins
      ↓
    Production CSS

Це концептуальна схема. Конкретний порядок залежить від збирача та конфігурації.

## 14.4. Чи потрібен Sass для PostCSS

Ні.

PostCSS може використовуватися з чистим CSS без Sass.

Для вивчення PostCSS краще почати зі звичайного CSS, щоб чітко розуміти, які зміни виконує кожен інструмент.

# 15. CSS Nesting і PostCSS

## 15.1. Що таке CSS Nesting

CSS Nesting дозволяє вкладати деякі CSS-правила всередину інших правил.

Наприклад:

    .card {
        padding: 16px;

        & .card-title {
            font-size: 20px;
        }

        &:hover {
            border-color: blue;
        }
    }

Підтримка CSS Nesting залежить від браузера та конкретного синтаксису.

## 15.2. Чи потрібен PostCSS для вкладеності

Не завжди.

Сучасні браузери підтримують стандартний CSS Nesting у відповідних версіях. Якщо цільові браузери підтримують потрібний синтаксис, додаткова трансформація може бути непотрібною.

Якщо проєкт повинен підтримувати браузери, які не розуміють певний синтаксис, можна розглянути відповідний PostCSS-плагін або інше рішення.

## 15.3. Чого варто уникати

Надмірно глибока вкладеність:

    .page {
        .content {
            .section {
                .card {
                    .title {
                        color: navy;
                    }
                }
            }
        }
    }

Навіть якщо інструмент може обробити такий код, він ускладнює розуміння стилів.

PostCSS не виправляє автоматично погану архітектуру CSS.

# 16. PostCSS і видалення невикористаного CSS

## 16.1. Чи видаляє PostCSS невикористані стилі самостійно

Ні. Для цього потрібні відповідні інструменти або плагіни.

Наприклад, PurgeCSS може аналізувати CSS і файли проєкту, щоб виявляти стилі, які, ймовірно, не використовуються.

Проте автоматичне очищення потребує обережності.

## 16.2. Чому видалення може бути небезпечним

CSS-клас може використовуватися:
- у компонентах на інших сторінках;
- після натискання кнопки;
- у відкритому модальному вікні;
- під час завантаження даних;
- у стані помилки;
- через динамічно сформоване ім'я класу.

Якщо аналізатор не може знайти використання, він може помилково позначити стиль як зайвий.

## 16.3. Правильний підхід

1. Визначити всі файли, які потрібно аналізувати.
2. Налаштувати інструмент відповідно до структури проєкту.
3. Врахувати динамічні класи.
4. Перевірити винятки.
5. Виконати production-збирання.
6. Перевірити всі важливі сторінки й стани компонентів.

# 17. Написання власного PostCSS-плагіна

## 17.1. Навіщо створювати власний плагін

У більшості навчальних і комерційних проєктів достатньо готових плагінів.

Але розуміння принципу роботи PostCSS допомагає зрозуміти, як створюються інструменти для автоматизації CSS.

Власний плагін може:
- знаходити певні декларації;
- перевіряти використання властивостей;
- трансформувати правила;
- додавати службові коментарі;
- перевіряти внутрішні домовленості проєкту.

## 17.2. Приклад простого плагіна

Нижче концептуальний приклад плагіна, який знаходить декларації `color`.

    const colorInspector = {
        postcssPlugin: "color-inspector",

        Declaration(decl) {
            if (decl.prop === "color") {
                console.log(
                    `Found color declaration: ${decl.value}`
                );
            }
        },
    };

    export default colorInspector;

Цей плагін не змінює CSS. Він лише знаходить декларації властивості `color` і виводить їхні значення.

Конкретний спосіб підключення залежить від API та версії PostCSS.

## 17.3. Як працює `Declaration`

`Declaration` — тип вузла CSS AST, який відповідає окремій декларації властивості.

Наприклад:

    .title {
        color: navy;
        font-size: 24px;
    }

У цьому правилі є дві декларації:
- `color: navy`;
- `font-size: 24px`.

Плагін може перевіряти кожну з них.

## 17.4. Плагін, який змінює значення

Для навчального прикладу можна створити плагін, який змінює значення конкретної властивості:

    const colorNormalizer = {
        postcssPlugin: "color-normalizer",

        Declaration(decl) {
            if (
                decl.prop === "color" &&
                decl.value === "navy"
            ) {
                decl.value = "#000080";
            }
        },
    };

    export default colorNormalizer;

Цей приклад демонструє зміну CSS AST. Для реального використання така заміна не обов'язково має практичну користь.

**Важливо:** не створюй власний плагін лише заради заміни одного значення, якщо це простіше зробити безпосередньо в CSS. Власні плагіни виправдані для повторюваних автоматизованих завдань.

# 18. Порядок обробки CSS у проєкті

## 18.1. Типовий процес

Умовний production-процес може виглядати так:

    Вихідний CSS
        ↓
    Парсинг CSS
        ↓
    Трансформації сучасного синтаксису
        ↓
    Додавання потрібних префіксів
        ↓
    Інші трансформації
        ↓
    Мініфікація
        ↓
    Production CSS

Це лише приклад. Реальний порядок залежить від конфігурації.

## 18.2. Чому порядок має значення

Якщо один інструмент змінює синтаксис, інший може отримати вже змінений код.

Наприклад, мініфікацію зазвичай зручно виконувати після основних трансформацій.

Проте не потрібно вважати наведений порядок універсальним правилом для кожного проєкту.

Важливо знати:
- які плагіни підключені;
- що саме вони змінюють;
- у якій послідовності працюють;
- який результат створюється.

## 18.3. Як перевірити результат

Після обробки:
- відкрий згенерований CSS;
- порівняй його з вихідним файлом;
- перевір, чи не зникли потрібні правила;
- запусти сторінку;
- перевір адаптивність;
- протестуй стани компонентів.

Не варто вважати, що успішне завершення команди автоматично означає правильність візуального результату.

# 19. Типові помилки під час роботи з PostCSS

## 19.1. Очікувати, що PostCSS автоматично оптимізує CSS

Сам PostCSS не додає всі можливі оптимізації.

Потрібно встановити та налаштувати відповідні плагіни.

## 19.2. Додавати плагіни без потреби

Кожен додатковий інструмент ускладнює конфігурацію та процес збирання.

Перед установленням плагіна сформулюй завдання, яке він має розв'язати.

## 19.3. Плутати PostCSS з Sass

Sass має власний синтаксис і компілятор.

PostCSS обробляє CSS через плагіни. Інструменти можуть працювати разом, але не є взаємозамінними.

## 19.4. Плутати Autoprefixer з повною підтримкою старих браузерів

Autoprefixer додає необхідні префікси відповідно до цільових браузерів.

Він не гарантує, що будь-яка сучасна CSS-функція працюватиме в будь-якому старому браузері.

## 19.5. Вважати, що cssnano видаляє весь невикористаний CSS

Мініфікація і видалення невикористаних правил — різні завдання.

Для очищення CSS потрібні відповідні інструменти та перевірка результату.

## 19.6. Копіювати конфігурації з різних версій інструментів

Плагіни та фреймворки можуть змінювати API, назви пакетів і способи конфігурації.

Перед використанням перевір сумісність версій.

## 19.7. Перезаписувати конфігурацію Next.js або Vite без перевірки

У проєкті вже можуть бути необхідні плагіни.

Перед зміною конфігурації збережи наявні налаштування та перевір результат збирання.

## 19.8. Перевіряти лише development-версію

Production-збирання може застосовувати додаткові трансформації та мініфікацію.

Тому потрібно перевіряти обидва режими.

## Крок 8. Порівняй результат

- чи створився `dist/styles.css`;
- чи змінився CSS;
- чи з'явилися префікси, якщо вони потрібні цільовим браузерам;

Не дивуйся, якщо результат майже не відрізняється від оригіналу. Для сучасних браузерів багато властивостей не потребують префіксів.

# 23. Запитання для співбесіди

## Рівень Junior

**1. Що таке PostCSS?**

PostCSS — це інструментальна платформа для обробки CSS за допомогою JavaScript-плагінів.

**2. Чи є PostCSS окремою мовою стилів?**

Ні. Це інструмент, який аналізує та трансформує CSS.

**3. Що таке PostCSS-плагін?**

Це модуль, який виконує певну операцію над CSS: перевіряє, аналізує або змінює його.

**4. Для чого потрібен Autoprefixer?**

Для автоматичного додавання потрібних браузерних префіксів відповідно до цільових браузерів.

**5. Для чого потрібен cssnano?**

Для мініфікації та оптимізації CSS.

**6. Чи потрібен PostCSS звичайній HTML-сторінці?**

Ні. Браузер може працювати зі звичайним CSS без PostCSS. PostCSS потрібен для автоматизованої обробки.

**7. Що таке Browserslist?**

Це система опису цільових браузерів, яку використовують різні інструменти обробки CSS та JavaScript.

## Рівень Middle

**8. Як працює PostCSS?**

Він парсить CSS, створює структуроване представлення, передає його плагінам і генерує оброблений результат.

**9. Чим відрізняються Autoprefixer і postcss-preset-env?**

Autoprefixer зосереджується на префіксах. postcss-preset-env може трансформувати певні сучасні можливості CSS для цільових браузерів.

**10. Чим відрізняються PostCSS і Sass?**

Sass — препроцесор із власним синтаксисом. PostCSS — платформа обробки CSS за допомогою плагінів.

**11. Чому важливий порядок плагінів?**

Тому що один плагін може змінити CSS, який отримує наступний плагін.

**12. Чому Autoprefixer не гарантує повної сумісності зі старими браузерами?**

Він додає префікси, але не реалізує всі відсутні CSS-функції.

**13. Для чого потрібна мініфікація?**

Щоб зменшити розмір CSS-файлу та обсяг переданих даних.

**14. Як перевірити результат PostCSS?**

Порівняти вихідний і згенерований CSS, перевірити розмір файлів та протестувати сторінку.

## Рівень Senior

**15. Як організувати обробку CSS у великому проєкті?**

Визначити цільові браузери, вибрати потрібні плагіни, налаштувати порядок обробки, інтегрувати процес зі збирачем і перевіряти production-результат.

**16. Як уникнути дублювання трансформацій?**

Перевірити, які операції вже виконує збирач, фреймворк або наявні плагіни, та не додавати зайві інструменти без потреби.

**17. Чому потрібно перевіряти версії плагінів?**

Тому що API, підтримка синтаксису й вимоги до конфігурації можуть змінюватися між версіями.

**18. Як безпечно очищати CSS від невикористаних правил?**

Використовувати відповідні інструменти, враховувати динамічні класи, перевіряти всі важливі стани й виконувати регресійні тести.

**19. Чи гарантує PostCSS покращення продуктивності?**

Ні. Він дозволяє автоматизувати обробку, але користь залежить від завдання, плагінів та результатів вимірювання.

**20. Коли варто створювати власний PostCSS-плагін?**

Коли потрібно автоматизувати повторювану трансформацію або перевірку, для якої немає відповідного готового інструмента.

# 26. Головне, що потрібно запам'ятати

1. **PostCSS — це інструмент обробки CSS, а не окрема мова стилів.**
2. **Плагіни визначають конкретні операції.** Сам PostCSS не виконує всі можливі оптимізації.
3. **Autoprefixer додає потрібні префікси** відповідно до цільових браузерів.
4. **Browserslist визначає цільові браузери** для інструментів, які його підтримують.
5. **cssnano допомагає мініфікувати CSS**, але не розв'язує всі проблеми продуктивності.
6. **postcss-preset-env може трансформувати певний сучасний CSS**, але не гарантує підтримку всіх можливостей у будь-якому браузері.
7. **Stylelint і PostCSS виконують різні ролі.** Один перевіряє код, інший обробляє його через плагіни.
8. **Sass і PostCSS не є взаємозамінними.** Вони можуть працювати разом.
9. **Потрібно перевіряти версії та конфігурацію.** Не копіюй налаштування без урахування середовища.
10. **Потрібно перевіряти production-результат.** Успішне збирання ще не гарантує правильного вигляду сторінки.
11. **Не встановлюй інструменти без конкретної потреби.** Кожна залежність має виконувати зрозуміле завдання.
12. **Оптимізація має бути вимірюваною.** Перевіряй розмір CSS, сумісність і поведінку інтерфейсу.

# 27. Підсумок

PostCSS — важлива частина сучасної CSS-екосистеми, особливо коли проєкт використовує інструменти збирання та автоматизовану обробку стилів.

Для початку достатньо зрозуміти три ключові речі:

- **PostCSS** — платформа для обробки CSS.
- **Autoprefixer** — автоматизація браузерних префіксів.
- **cssnano** — мініфікація CSS.

Пізніше можна перейти до `postcss-preset-env`, Stylelint, очищення невикористаних стилів і власних плагінів.

Для твоєї навчальної програми оптимальний шлях — спочатку впевнено писати звичайний CSS, потім навчитися перевіряти та оптимізувати його, а вже після цього інтегрувати PostCSS у Vite або Next.js.

**Основна формула:**

    PostCSS =
        CSS Parsing
        + Plugins
        + Transformations
        + Automation
        + Production CSS
