# 03. CSS Optimization — Оптимізація CSS

> **CSS Optimization** — це процес покращення CSS-коду, щоб він був зрозумілим, підтримуваним, ефективним і не створював зайвого навантаження під час завантаження та відображення вебсторінки.

Мета оптимізації CSS — не просто написати менше рядків коду. Важливо правильно організувати стилі, уникати непотрібних повторень, зменшувати розмір CSS-файлів, контролювати вплив стилів на рендеринг і забезпечувати стабільну роботу інтерфейсу.

CSS Optimization охоплює:
- оптимізацію структури CSS;
- усунення дублювання стилів;
- зменшення розміру CSS-файлів;
- оптимізацію селекторів;
- видалення невикористаного CSS;
- використання CSS-змінних;
- оптимізацію критичних стилів;
- правильне завантаження CSS;
- зменшення зайвих перерахунків стилів і компонування;
- оптимізацію анімацій;
- використання інструментів автоматизації;
- вимірювання реальної продуктивності.

---

# 1. Що таке CSS Optimization

## 1.1. Навіщо оптимізувати CSS

На невеликому навчальному проєкті кілька зайвих правил можуть майже не впливати на продуктивність.

Але зі збільшенням застосунку CSS може містити:
- сотні або тисячі правил;
- повторювані декларації;
- стилі компонентів, які більше не використовуються;
- надмірно складні селектори;
- конфліктні правила;
- великі CSS-файли;
- стилі, які блокують початкове відображення сторінки;
- дорогі для браузера анімації.

Оптимізація допомагає зробити код легшим для браузера та розробника.

## 1.2. Основні цілі оптимізації

| Ціль | Що робимо |
|---|---|
| Зменшення розміру | Видаляємо зайві пробіли, коментарі та непотрібні правила |
| Усунення дублювання | Повторно використовуємо спільні стилі |
| Підтримуваність | Організовуємо CSS у зрозумілу структуру |
| Швидке відображення | Оптимізуємо завантаження критичних стилів |
| Продуктивність | Уникаємо непотрібних змін layout і paint |
| Передбачуваність | Зменшуємо конфлікти каскаду та специфічності |
| Масштабованість | Використовуємо дизайн-токени й повторно використовувані компоненти |
| Надійність | Перевіряємо стилі в різних браузерах і розмірах екрана |

## 1.3. Оптимізація — це не лише мінімізація

Наприклад, можна скоротити CSS до одного рядка:

    .card{padding:1rem;background:#fff;border-radius:.5rem}.card h2{font-size:1.25rem;margin:0 0 .5rem}

Такий код компактний, але його складніше читати й підтримувати.

Краще зберігати зрозумілий формат у вихідних файлах:

    .card {
        padding: 1rem;
        background: #fff;
        border-radius: 0.5rem;
    }

    .card h2 {
        margin: 0 0 0.5rem;
        font-size: 1.25rem;
    }

Під час production-збирання спеціальний інструмент може автоматично створити компактну версію CSS.

**Основний принцип:** вихідний код має бути зручним для розробки, а production-код — ефективним для доставки користувачу.

# 2. Основні напрямки CSS Optimization

CSS Optimization можна розділити на кілька напрямків.

## 2.1. Source optimization — оптимізація вихідного коду

Покращення структури та якості CSS.

Приклади:
- видалення дубльованих правил;
- спрощення селекторів;
- зменшення надмірної специфічності;
- використання CSS-змінних;
- повторне використання компонентних класів;
- видалення застарілих стилів.

## 2.2. File optimization — оптимізація файлів

Зменшення обсягу CSS, який передається браузеру.

Приклади:
- minification;
- видалення невикористаного CSS;
- поділ стилів на відповідні частини;
- стиснення HTTP-відповідей;
- контроль розміру production-файлів.

## 2.3. Loading optimization — оптимізація завантаження

Допомагає браузеру швидше отримати стилі, потрібні для початкового відображення сторінки.

Приклади:
- правильне підключення CSS;
- уникнення зайвих блокувальних ресурсів;
- обережне використання критичного CSS;
- відкладене завантаження необов'язкових стилів, коли це справді виправдано.

## 2.4. Rendering optimization — оптимізація рендерингу

Зменшення непотрібної роботи браузера під час оновлення інтерфейсу.

Приклади:
- уникнення частих змін властивостей, які викликають layout;
- використання відповідних властивостей для анімації;
- зменшення зайвих перерахунків стилів;
- обережне використання великих тіней, фільтрів і складних ефектів.

## 2.5. Maintenance optimization — оптимізація підтримуваності

CSS повинен залишатися зрозумілим після додавання нових компонентів і функцій.

Приклади:
- послідовна система назв класів;
- логічний поділ файлів;
- дизайн-токени;
- CSS Modules або інша відповідна система ізоляції стилів;
- автоматичні перевірки та форматування.

# 3. Видалення дублювання CSS

## 3.1. Що таке дублювання

Дублювання виникає, коли однакові або майже однакові декларації повторюються в різних місцях.

Приклад неоптимального CSS:

    .primary-button {
        padding: 12px 20px;
        border-radius: 6px;
        font-weight: 600;
        background-color: #2563eb;
        color: white;
    }

    .secondary-button {
        padding: 12px 20px;
        border-radius: 6px;
        font-weight: 600;
        background-color: #64748b;
        color: white;
    }

    .danger-button {
        padding: 12px 20px;
        border-radius: 6px;
        font-weight: 600;
        background-color: #dc2626;
        color: white;
    }

Спільні властивості повторюються тричі.

## 3.2. Винесення спільних стилів

Можна створити базовий клас кнопки:

    .button {
        padding: 12px 20px;
        border: none;
        border-radius: 6px;
        font-weight: 600;
        color: white;
        cursor: pointer;
    }

    .button--primary {
        background-color: #2563eb;
    }

    .button--secondary {
        background-color: #64748b;
    }

    .button--danger {
        background-color: #dc2626;
    }

HTML:

    <button class="button button--primary">Зберегти</button>
    <button class="button button--secondary">Скасувати</button>
    <button class="button button--danger">Видалити</button>

Тепер:
- спільні стилі визначені в одному місці;
- варіанти кнопки мають лише відмінні властивості;
- змінювати загальний вигляд простіше;
- нові варіанти створювати легше.

## 3.3. Коли не потрібно об'єднувати стилі

Не варто об'єднувати правила лише тому, що вони схожі.

Наприклад, дві картки можуть мати однаковий `padding`, але належати до різних компонентів і розвиватися незалежно.

Надмірне об'єднання створює приховані залежності.

Погана ідея:

    .profile,
    .checkout,
    .article,
    .modal,
    .dashboard {
        padding: 24px;
        background: white;
        border-radius: 8px;
    }

Якщо ці компоненти мають різне призначення, спільний клас може бути виправданим лише тоді, коли вони справді представляють спільний дизайн-патерн.

**Правило:** усувай реальне дублювання, але не об'єднуй незалежні компоненти штучно.

# 4. CSS Variables — повторне використання значень

CSS custom properties, або CSS-змінні, дозволяють зберігати значення, які використовуються в різних правилах.

## 4.1. Без CSS-змінних

    .header {
        background-color: #1d4ed8;
    }

    .button {
        background-color: #1d4ed8;
    }

    .link {
        color: #1d4ed8;
    }

    .footer {
        border-top: 2px solid #1d4ed8;
    }

Якщо потрібно змінити основний колір, доведеться шукати всі відповідні декларації.

## 4.2. З CSS-змінними

    :root {
        --color-primary: #1d4ed8;
        --color-text: #1f2937;
        --color-surface: #ffffff;
        --radius-medium: 8px;
        --spacing-medium: 16px;
    }

    .header {
        background-color: var(--color-primary);
    }

    .button {
        background-color: var(--color-primary);
        border-radius: var(--radius-medium);
        padding: var(--spacing-medium);
    }

    .link {
        color: var(--color-primary);
    }

    .footer {
        border-top: 2px solid var(--color-primary);
    }

Тепер значення централізовані.

## 4.3. CSS-змінні для дизайн-системи

    :root {
        /* Colors */
        --color-primary: #2563eb;
        --color-success: #15803d;
        --color-danger: #dc2626;
        --color-text: #1f2937;
        --color-background: #f8fafc;

        /* Spacing */
        --space-1: 4px;
        --space-2: 8px;
        --space-3: 12px;
        --space-4: 16px;
        --space-6: 24px;
        --space-8: 32px;

        /* Typography */
        --font-body: Arial, sans-serif;
        --font-size-body: 16px;
        --font-size-heading: 24px;

        /* Borders */
        --radius-small: 4px;
        --radius-medium: 8px;
        --radius-large: 16px;
    }

Такі змінні допомагають зберігати узгодженість дизайну.

## 4.4. Fallback-значення

Якщо змінна не визначена, можна вказати запасне значення:

    .button {
        background-color: var(--color-primary, #2563eb);
    }

Якщо `--color-primary` недоступна, браузер використає `#2563eb`.

Важливо: fallback у `var()` не виправляє ситуацію, коли змінна існує, але її значення непридатне для конкретної властивості.

## 4.5. Чи прискорюють CSS-змінні сайт?

Не обов'язково. Їхня головна користь — підтримуваність, повторне використання значень і можливість динамічної темізації.

Надмірні залежності від змінних або зміни значень на великій кількості елементів можуть впливати на перерахунок стилів. Оптимізацію продуктивності потрібно перевіряти вимірюваннями.

# 5. Спрощення CSS-селекторів

## 5.1. Надмірно складні селектори

Приклад:

    body main .page .content section.article div.article-card h2.article-title {
        color: #1f2937;
    }

Селектор містить багато зайвих уточнень.

Якщо клас `article-title` достатньо однозначний, можна написати:

    .article-title {
        color: #1f2937;
    }

Це робить правило зрозумілішим і зменшує залежність від структури HTML.

## 5.2. Чому важлива простота

Прості селектори:
- легше читати;
- простіше повторно використовувати;
- менше залежать від вкладеності елементів;
- зручніше перевизначати;
- зменшують ризик випадкового впливу на інші компоненти.

Сучасні браузери добре оптимізують пошук елементів. Тому не варто припускати, що кожен складний селектор автоматично створює серйозну проблему продуктивності.

Найважливіше — підтримуваність, контроль області дії та відсутність зайвої складності.

## 5.3. Надмірна специфічність

Не варто підвищувати специфічність без потреби.

Неоптимально:

    #page main .content .card h2.title {
        color: navy;
    }

Простіше:

    .card-title {
        color: navy;
    }

Чим складніше перевизначити правило, тим частіше розробник змушений створювати ще складніші селектори або використовувати `!important`.

## 5.4. Не використовуй `!important` як звичайний спосіб оптимізації

Поганий приклад:

    .button {
        background-color: blue !important;
    }

    .button.button-primary {
        background-color: green !important;
    }

Такі правила ускладнюють керування каскадом.

Краще з'ясувати, чому виникає конфлікт, і виправити структуру стилів.

`!important` може бути виправданим у спеціальних випадках, але не повинен замінювати нормальну архітектуру CSS.

# 6. Видалення невикористаного CSS

## 6.1. Що таке unused CSS

Unused CSS — це стилі, які не застосовуються до елементів конкретної сторінки або застосунку.

Наприклад:

    .old-banner {
        background-color: orange;
        padding: 20px;
    }

    .unused-modal {
        position: fixed;
        inset: 0;
        background-color: rgb(0 0 0 / 50%);
    }

    .active-card {
        border: 2px solid blue;
    }

Якщо відповідні компоненти видалені, їхні стилі можуть залишитися в CSS-файлі.

## 6.2. Чому зайвий CSS небажаний

Невикористані стилі:
- збільшують розмір файлів;
- ускладнюють читання;
- створюють хибне враження про компоненти проєкту;
- можуть містити застарілі правила;
- збільшують вартість підтримки.

Однак невикористаний на одній сторінці клас не обов'язково є зайвим у всьому застосунку.

## 6.3. Чому не можна видаляти стилі лише за результатами одного перегляду

Клас може використовуватися:
- на іншій сторінці;
- у відкритому за взаємодією модальному вікні;
- після натискання кнопки;
- під час завантаження даних;
- у стані помилки;
- у компоненті, який створюється JavaScript;
- у CSS-класі, назва якого формується динамічно.

Наприклад, JavaScript може додавати клас:

    const menu = document.querySelector(".menu");

    button.addEventListener("click", () => {
        menu.classList.toggle("menu--open");
    });

Якщо інструмент аналізу не бачить динамічне використання `menu--open`, він може помилково позначити відповідний стиль як зайвий.

## 6.4. Як безпечно очищати CSS

1. Перевірити, де підключається CSS.
2. Знайти правила, які можуть бути застарілими.
3. Перевірити всі сторінки та компоненти.
4. Перевірити стани взаємодії: hover, focus, open, active, error.
5. Перевірити класи, які додаються JavaScript.
6. Використати автоматичний аналізатор невикористаного CSS.
7. Перевірити його результати вручну.
8. Запустити застосунок і виконати регресійне тестування.

**Важливо:** автоматичне видалення CSS потребує обережності, особливо у великих застосунках.

# 7. Minification — мінімізація CSS

## 7.1. Що таке minification

Minification — автоматичне зменшення розміру CSS-файлу без зміни його передбачуваної поведінки.

Мініфікатор може прибрати:
- зайві пробіли;
- переноси рядків;
- частину коментарів;
- зайві символи форматування;
- деякі безпечні синтаксичні надлишки.

Вихідний CSS:

    .card {
        padding: 16px;
        margin-bottom: 24px;
        background-color: white;
        border-radius: 8px;
    }

Мініфікований CSS може виглядати так:

    .card{padding:16px;margin-bottom:24px;background-color:#fff;border-radius:8px}

## 7.2. Переваги minification

- менший розмір CSS;
- менше даних для передавання мережею;
- можливе швидше завантаження за повільного з'єднання;
- менший обсяг тексту, який потрібно завантажити браузеру.

Фактичний виграш залежить від розміру файлу, стиснення на сервері, мережі та інших умов.

## 7.3. Minification не замінює gzip або Brotli

Це різні рівні оптимізації.

| Інструмент | Призначення |
|---|---|
| Minification | Видаляє зайве форматування та виконує безпечні скорочення |
| gzip | Стискає передані дані |
| Brotli | Виконує інше алгоритмічне стиснення даних |
| Bundling | Об'єднує ресурси, коли це потрібно конфігурації |
| Tree shaking / CSS pruning | Допомагає виключати непотрібний код або стилі залежно від інструментів |

Мініфікований CSS можна додатково стискати під час передавання мережею.

## 7.4. Чи потрібно вручну писати мініфікований CSS?

Ні.

Вихідні файли потрібно залишати читабельними. Мініфікацію варто виконувати автоматично під час production-збирання.

# 8. Організація CSS-файлів

## 8.1. Чому структура файлів важлива

У маленькому проєкті може вистачити одного файлу:

    styles.css

Але зі збільшенням проєкту є ризик створити файл, у якому складно знайти потрібні стилі.

Наприклад, структуру можна організувати так:

    src/
    └── styles/
        ├── reset.css
        ├── variables.css
        ├── base.css
        ├── layout.css
        ├── components.css
        └── utilities.css

Призначення:

- `reset.css` — базове скидання стилів, якщо воно потрібне;
- `variables.css` — дизайн-токени та CSS-змінні;
- `base.css` — базові стилі HTML-елементів;
- `layout.css` — структура сторінки;
- `components.css` — повторно використовувані компоненти;
- `utilities.css` — невеликі класи-утиліти.

Це лише один із можливих варіантів. Не кожному проєкту потрібні всі ці файли.

## 8.2. Організація за компонентами

Для компонентного застосунку може бути зручніше групувати стилі за компонентами:

    src/
    ├── components/
    │   ├── Button/
    │   │   ├── Button.tsx
    │   │   └── Button.module.css
    │   ├── Card/
    │   │   ├── Card.tsx
    │   │   └── Card.module.css
    │   └── Header/
    │       ├── Header.tsx
    │       └── Header.module.css
    └── styles/
        ├── variables.css
        └── global.css

Переваги:
- стилі легше знаходити;
- компоненти простіше переносити;
- менше ризику випадково змінити інші частини інтерфейсу;
- видалення компонента полегшує видалення його стилів.

CSS Modules можуть допомагати ізолювати імена класів, але не усувають автоматично всі проблеми каскаду, глобальних стилів або продуктивності.

## 8.3. Чи потрібно об'єднувати всі CSS-файли в один?

Не завжди.

Історично об'єднання файлів могло зменшувати кількість HTTP-запитів. Проте сучасні браузери, HTTP/2, HTTP/3 та інструменти збирання змінюють компроміси.

Надмірно великий загальний файл може змусити користувача завантажувати стилі, які йому не потрібні.

Рішення залежить від:
- розміру застосунку;
- кількості сторінок;
- способу завантаження ресурсів;
- можливостей збирача;
- кешування;
- виміряної продуктивності.

Не потрібно об'єднувати файли лише заради зменшення їхньої кількості.

# 9. CSS Reset і Normalize

## 9.1. Навіщо потрібні базові стилі

Браузери мають власні стилі за замовчуванням для HTML-елементів.

Наприклад:
- заголовки мають стандартні розміри;
- списки можуть мати відступи;
- кнопки можуть відрізнятися за зовнішнім виглядом;
- поля форми мають браузерні стилі.

CSS Reset або Normalize допомагає зробити початкову поведінку більш передбачуваною.

## 9.2. Приклад мінімального reset

    *,
    *::before,
    *::after {
        box-sizing: border-box;
    }

    body {
        margin: 0;
    }

    img,
    picture,
    video,
    canvas,
    svg {
        display: block;
        max-width: 100%;
    }

    input,
    button,
    textarea,
    select {
        font: inherit;
    }

Це приклад початкових правил, а не універсальний reset для всіх проєктів.

## 9.3. Чи робить reset сайт швидшим?

Не обов'язково.

Його основна користь — узгоджена та передбачувана початкова поведінка стилів.

Зайві або невдало підібрані reset-правила можуть створювати додаткову роботу й потребувати подальших перевизначень.

# 10. Critical CSS — критичні стилі

## 10.1. Що таке Critical CSS

Critical CSS — це мінімальний набір стилів, необхідних для відображення видимої частини сторінки на початку завантаження.

Наприклад, для першого екрана можуть бути потрібні стилі:
- шапки;
- головного заголовка;
- основного контейнера;
- першої кнопки;
- початкового розташування основного вмісту.

Стилі нижніх секцій можуть не бути критичними для першого кадру.

## 10.2. Як CSS впливає на початкове відображення

Браузеру потрібно знати стилі, щоб правильно відобразити сторінку.

Зовнішній CSS, підключений звичайним способом через `link rel="stylesheet"`, зазвичай може блокувати перше відображення сторінки, поки браузер отримує й обробляє таблицю стилів.

Приклад:

    <head>
        <link rel="stylesheet" href="/styles.css">
    </head>

Це нормальний і часто правильний спосіб підключення CSS.

Проблеми можуть виникати, коли файл дуже великий, повільно завантажується або містить багато стилів, які не потрібні для початкового відображення.

## 10.3. Критичні стилі в HTML

Для деяких сторінок критичні стилі можуть бути вбудовані в `head`:

    <head>
        <style>
            body {
                margin: 0;
                font-family: Arial, sans-serif;
            }

            .hero {
                padding: 48px 24px;
                background-color: #f8fafc;
            }

            .hero-title {
                max-width: 700px;
                font-size: 2rem;
            }
        </style>

        <link rel="stylesheet" href="/styles.css">
    </head>

Такий підхід може допомогти швидше відобразити важливий вміст, але має недоліки:
- HTML збільшується;
- стилі можуть дублюватися;
- кешування змінюється;
- обслуговування стає складнішим.

Не потрібно вручну вбудовувати всі стилі в HTML.

## 10.4. Коли використовувати Critical CSS

Має сенс розглядати його, коли:
- початкове відображення повільне;
- CSS-файл великий;
- вимірювання виявляють проблему з рендерингом;
- перший екран можна відокремити від стилів решти сторінки;
- інструменти проєкту підтримують автоматичне визначення критичних стилів.

Для невеликого навчального проєкту спочатку достатньо правильно підключити CSS, уникати зайвого коду та виміряти результат.

# 11. CSS і Core Web Vitals

Core Web Vitals — набір метрик, що оцінюють важливі аспекти користувацького досвіду.

CSS може впливати на ці показники, але не є єдиною причиною проблем.

## 11.1. LCP — Largest Contentful Paint

LCP вимірює, коли найбільший видимий елемент основного вмісту відображається в межах вікна перегляду.

CSS може впливати на LCP, якщо:
- таблиця стилів завантажується повільно;
- вона затримує перше відображення;
- стилі створюють додаткові затримки рендерингу;
- неправильний layout змушує браузер пізніше показати основний вміст.

Але LCP також залежить від:
- сервера;
- мережі;
- HTML;
- JavaScript;
- зображень;
- шрифтів;
- часу відповіді ресурсу LCP.

## 11.2. CLS — Cumulative Layout Shift

CLS оцінює несподівані зміщення елементів під час завантаження та взаємодії.

CSS може допомогти зменшити зміщення завдяки:
- резервуванню місця для зображень;
- стабільним розмірам компонентів;
- передбачуваному завантаженню шрифтів;
- уникненню раптової зміни геометрії елементів.

Приклад:

    .product-image {
        width: 100%;
        aspect-ratio: 4 / 3;
        object-fit: cover;
    }

Якщо контейнер має передбачуване співвідношення сторін, браузер може зарезервувати потрібне місце до завантаження зображення.

Для зображень також корисно задавати атрибути `width` і `height`, коли їхні розміри відомі.

## 11.3. INP — Interaction to Next Paint

INP оцінює затримку між взаємодією користувача та наступним відображенням результату.

CSS може впливати на неї, якщо взаємодія викликає:
- масштабні зміни стилів;
- дорогий layout;
- складне перемальовування;
- важкі анімації.

Однак INP часто залежить також від JavaScript, обробників подій і навантаження основного потоку.

**Висновок:** не можна вважати, що кожна проблема Core Web Vitals викликана CSS. Потрібно визначити фактичну причину.

# 12. Layout і Rendering Performance

## 12.1. Основні етапи рендерингу

Спрощено браузер може виконувати такі етапи:

1. Отримання HTML, CSS та інших ресурсів.
2. Побудова DOM і CSSOM.
3. Обчислення стилів.
4. Побудова дерева рендерингу.
5. Layout — визначення геометрії елементів.
6. Paint — промальовування.
7. Compositing — об'єднання шарів для відображення.

Це спрощена модель. У реальному браузері частина роботи може відбуватися паралельно, повторюватися або пропускатися залежно від змін.

## 12.2. Що таке Layout

Layout — визначення розміру та положення елементів.

Приклади властивостей, зміни яких часто можуть викликати layout:

    .box {
        width: 300px;
        height: 200px;
        margin: 20px;
        padding: 16px;
    }

Зміна геометрії одного елемента може вплинути на сусідні елементи та спричинити повторні обчислення.

Але не кожна зміна цих властивостей обов'язково призводить до однакового обсягу роботи: результат залежить від DOM, layout-контексту та оптимізацій браузера.

## 12.3. Що таке Paint

Paint — промальовування візуального вигляду елементів.

На нього можуть впливати:
- кольори;
- межі;
- тіні;
- фони;
- текст;
- деякі фільтри;
- зміни видимості.

Наприклад:

    .card {
        background-color: white;
        border: 1px solid #e5e7eb;
        box-shadow: 0 4px 12px rgb(0 0 0 / 10%);
    }

Тіні та фільтри можуть бути дорожчими за прості візуальні властивості, особливо якщо вони застосовуються до великих або численних елементів.

Це не означає, що тіні потрібно заборонити. Важливо перевіряти реальну продуктивність.

## 12.4. Compositing

Compositing — об'єднання підготовлених шарів для створення остаточного кадру.

Деякі трансформації та анімації можуть виконуватися ефективніше, якщо браузер обробляє їх на етапі compositing.

Проте це залежить від браузера, пристрою, структури сторінки та властивостей елемента.

Не потрібно примусово створювати окремий шар для кожного елемента.

# 13. Оптимізація анімацій

## 13.1. Властивості, які часто зручні для анімації

Для багатьох анімацій варто починати з:
- `transform`;
- `opacity`.

Приклад:

    .notification {
        opacity: 0;
        transform: translateY(12px);
        transition:
            opacity 200ms ease,
            transform 200ms ease;
    }

    .notification.is-visible {
        opacity: 1;
        transform: translateY(0);
    }

Це часто дозволяє уникнути постійної зміни геометрії елемента.

## 13.2. Анімація через геометричні властивості

Приклад:

    .panel {
        margin-left: 0;
        transition: margin-left 300ms ease;
    }

    .panel.is-open {
        margin-left: 200px;
    }

Зміна `margin-left` може впливати на layout та інші елементи.

Для певних інтерфейсів трансформація може бути кращим рішенням:

    .panel {
        transform: translateX(0);
        transition: transform 300ms ease;
    }

    .panel.is-open {
        transform: translateX(200px);
    }

Але ці два приклади не є повністю взаємозамінними: трансформація візуально переміщує елемент, не змінюючи його початкового місця в потоці документа.

## 13.3. Не анімуй усе підряд

Важкі анімації можуть створювати навантаження на пристроях із низькою продуктивністю.

Особливо уважно варто ставитися до:
- великих blur-фільтрів;
- великих тіней;
- складних масок;
- великої кількості одночасних анімацій;
- анімацій, що постійно змінюють layout.

## 13.4. `will-change`

Властивість `will-change` повідомляє браузеру, що певна властивість елемента може змінюватися.

Приклад:

    .animated-card {
        will-change: transform;
    }

Але не варто застосовувати її до всіх елементів:

    /* Не рекомендовано як глобальне правило */
    * {
        will-change: transform;
    }

Це може призвести до надмірного використання ресурсів.

Використовуй `will-change` лише тоді, коли є реальна проблема продуктивності та вимірювання підтверджують користь.

## 13.5. Підтримка зменшення руху

Деякі користувачі налаштовують операційну систему так, щоб зменшити анімацію.

CSS може враховувати цю настройку:

    .modal {
        transition:
            opacity 200ms ease,
            transform 200ms ease;
    }

    @media (prefers-reduced-motion: reduce) {
        .modal {
            transition: none;
        }
    }

Для складних інтерфейсів може бути доречним не просто прибрати перехід, а й переглянути інші види руху.

# 14. Оптимізація Flexbox і Grid

Flexbox і Grid самі по собі не є проблемою продуктивності. Важливі структура, кількість елементів, частота змін та вимоги інтерфейсу.

## 14.1. Використовуй правильний інструмент

Flexbox добре підходить для розташування елементів в одному основному напрямку.

Grid зручний для двовимірних сіток.

Приклад Grid:

    .product-grid {
        display: grid;
        grid-template-columns: repeat(3, minmax(0, 1fr));
        gap: 24px;
    }

Адаптивна версія:

    .product-grid {
        display: grid;
        grid-template-columns: repeat(
            auto-fit,
            minmax(min(100%, 240px), 1fr)
        );
        gap: 24px;
    }

Це дозволяє браузеру автоматично розміщувати картки відповідно до доступної ширини.

## 14.2. Не створюй зайву вкладеність

Не варто додавати десятки обгорток, якщо вони не потрібні для семантики, компонування або функціональності.

Надмірна вкладеність ускладнює:
- розуміння layout;
- підтримку стилів;
- пошук джерела переповнення;
- роботу з адаптивністю.

Однак обгортки можуть бути необхідними для доступності, структури компонентів або конкретного layout-рішення.

## 14.3. Не оптимізуй Grid чи Flexbox без вимірювання

Не потрібно замінювати Grid на Flexbox лише через припущення, що один із них завжди швидший.

Вибирай той механізм, який найкраще відповідає завданню. Якщо вимірювання показують реальну проблему, досліджуй її на конкретній сторінці.

# 15. CSS Containment

## 15.1. Що таке containment

CSS containment дозволяє обмежити вплив частини піддерева документа на інші частини сторінки для певних видів обчислень.

Приклад:

    .independent-widget {
        contain: layout;
    }

Це повідомляє браузеру, що layout цієї області має певні межі впливу.

## 15.2. `content-visibility`

Для великих сторінок із вмістом поза видимою областю може бути корисним:

    .long-section {
        content-visibility: auto;
        contain-intrinsic-size: auto 500px;
    }

Браузер може відкладати частину роботи з відображення вмісту, який ще не потрібний у видимій області.

`contain-intrinsic-size` допомагає зарезервувати приблизний розмір області.

## 15.3. Коли це доречно

Можливі сценарії:
- довгі статті;
- сторінки з великою кількістю секцій;
- великі списки;
- складні інформаційні панелі.

Не варто механічно додавати `content-visibility` до кожного елемента.

Потрібно перевірити:
- чи немає несподіваних змін розміру;
- чи правильно працює прокручування;
- чи не виникають проблеми з фокусом та пошуком вмісту;
- чи покращується продуктивність на реальних пристроях.

# 16. CSS і шрифти

## 16.1. Чому шрифти важливі

Шрифти можуть впливати на:
- швидкість відображення тексту;
- ширину текстових блоків;
- висоту рядків;
- перенесення слів;
- зміщення елементів після завантаження шрифту.

## 16.2. Підключення локального шрифту

    @font-face {
        font-family: "AppSans";
        src: url("/fonts/app-sans.woff2") format("woff2");
        font-style: normal;
        font-weight: 400;
        font-display: swap;
    }

    body {
        font-family: "AppSans", Arial, sans-serif;
    }

Формат WOFF2 зазвичай є хорошим вибором для сучасних вебшрифтів.

`font-display: swap` дозволяє спочатку показати текст із запасним шрифтом, а потім замінити його завантаженим.

Проте заміна шрифту може змінити геометрію тексту. Тому важливо обирати сумісні запасні шрифти й перевіряти layout.

## 16.3. Не завантажуй усі можливі накреслення

Якщо сайт використовує лише звичайне та напівжирне накреслення, не обов'язково завантажувати багато інших варіантів.

Водночас змінні шрифти можуть об'єднувати кілька накреслень в одному файлі, тому рішення залежить від реального розміру ресурсів і потреб дизайну.

## 16.4. `font-display`

Основні варіанти:
- `auto`;
- `block`;
- `swap`;
- `fallback`;
- `optional`.

Вони визначають, як браузер поводиться з текстом під час завантаження вебшрифту.

Не існує одного універсального значення для кожного проєкту. Вибір залежить від того, що важливіше: швидкий показ запасного шрифту, мінімізація видимої заміни або інша поведінка.

# 17. CSS і адаптивність

## 17.1. Уникай зайвих медіазапитів

Неоптимальний приклад:

    .card {
        padding: 16px;
    }

    @media (min-width: 600px) {
        .card {
            padding: 20px;
        }
    }

    @media (min-width: 900px) {
        .card {
            padding: 24px;
        }
    }

Це не обов'язково погано. Але якщо значення можна описати простіше, код можна зробити компактнішим.

Наприклад:

    .card {
        padding: clamp(16px, 2vw, 24px);
    }

`clamp()` задає мінімальне, бажане та максимальне значення.

## 17.2. Не замінюй усі медіазапити `clamp()`

Медіазапити потрібні, коли змінюється не тільки значення, а й структура компонування.

Наприклад:

    .navigation {
        display: flex;
        gap: 24px;
    }

    @media (max-width: 600px) {
        .navigation {
            flex-direction: column;
            gap: 12px;
        }
    }

Тут змінюється напрямок розташування елементів, тому медіазапит залишається доречним.

## 17.3. Контролюй дублювання адаптивних правил

Коли для одного компонента є багато медіазапитів у різних місцях, складно зрозуміти його поведінку.

Краще:
- тримати пов'язані правила поруч;
- використовувати послідовні точки перелому;
- не створювати медіазапит без потреби;
- перевіряти компонент на реальних розмірах екрана.

# 18. CSS Cascade Layers

## 18.1. Що таке Cascade Layers

Cascade Layers дозволяють явно визначати порядок шарів CSS-правил.

Це може полегшити керування каскадом у великих проєктах.

Приклад:

    @layer reset, base, components, utilities;

    @layer reset {
        *,
        *::before,
        *::after {
            box-sizing: border-box;
        }

        body {
            margin: 0;
        }
    }

    @layer base {
        body {
            font-family: Arial, sans-serif;
            color: #1f2937;
        }
    }

    @layer components {
        .button {
            padding: 12px 20px;
            border-radius: 8px;
        }
    }

    @layer utilities {
        .text-center {
            text-align: center;
        }
    }

## 18.2. Як це допомагає

Cascade Layers можуть:
- зменшити залежність від специфічності;
- визначити порядок груп правил;
- спростити інтеграцію стилів із різних джерел;
- зробити архітектуру більш передбачуваною.

Вони не зменшують автоматично розмір CSS і не гарантують швидшого рендерингу.

Їхня основна перевага — керування каскадом і підтримуваність.

## 18.3. Важливе правило каскаду

Для звичайних декларацій правила в пізнішому шарі мають перевагу над правилами в ранішому шарі, якщо інші відповідні умови каскаду однакові.

Але для декларацій `!important` порядок шарів працює у зворотному напрямку. Тому під час використання шарів потрібно розуміти повний порядок каскаду.

# 19. Автоматизація CSS

## 19.1. Навіщо потрібні інструменти

Автоматизація допомагає:
- форматувати CSS;
- перевіряти помилки;
- виявляти проблемні правила;
- мінімізувати CSS;
- видаляти непотрібні стилі;
- підтримувати однакові правила в команді.

## 19.2. Prettier

Prettier — форматувальник коду.

Він може привести CSS до узгодженого формату.

Наприклад, вихідний код:

    .card{padding:16px;background:white;border-radius:8px}

Після форматування:

    .card {
        padding: 16px;
        background: white;
        border-radius: 8px;
    }

Prettier насамперед відповідає за форматування. Він не є універсальним інструментом для видалення невикористаного CSS або оптимізації рендерингу.

## 19.3. Stylelint

Stylelint — інструмент статичного аналізу CSS.

Він може допомагати знаходити:
- синтаксичні помилки;
- порушення правил стилю;
- проблемні шаблони;
- невідповідність командним домовленостям.

Приклад команди в проєкті, де Stylelint уже встановлено й налаштовано:

    npx stylelint "**/*.css"

Конкретний шаблон файлів і правила потрібно адаптувати до структури проєкту.

## 19.4. PostCSS

PostCSS — інструментальна платформа для обробки CSS за допомогою плагінів.

Залежно від конфігурації вона може використовуватися для:
- перетворення синтаксису;
- автоматизації сумісності;
- інтеграції мініфікаторів;
- виконання інших операцій з CSS.

Сам по собі PostCSS не означає автоматичної оптимізації. Результат залежить від установлених плагінів та їхніх налаштувань.

## 19.5. PurgeCSS та інші інструменти очищення

PurgeCSS може аналізувати CSS і вміст файлів, щоб знаходити стилі, які, ймовірно, не використовуються.

Але результат залежить від того:
- які файли аналізуються;
- чи правильно налаштовані шляхи;
- чи враховано динамічні класи;
- чи задані потрібні винятки.

Після очищення потрібно перевіряти інтерфейс.

## 19.6. Vite, Next.js та інші збирачі

Сучасні інструменти збирання можуть автоматизувати частину оптимізації CSS.

Залежно від інструмента та конфігурації можливі:
- обробка CSS;
- мініфікація;
- поділ ресурсів;
- робота з імпортами;
- формування production-файлів.

Не варто припускати, що кожна оптимізація автоматично ввімкнена в будь-якому проєкті. Потрібно перевіряти конфігурацію та результат збірки.

# 20. Оптимізація CSS у production

## 20.1. Development і Production

Під час розробки важливі:
- читабельний код;
- швидкий зворотний зв'язок;
- зручне налагодження;
- source maps;
- зрозумілі повідомлення про помилки.

У production важливі:
- компактні файли;
- правильне кешування;
- передбачуване завантаження;
- стабільна робота;
- відсутність непотрібних ресурсів.

Тому development-файли можуть бути відформатованими, а production-файли — мініфікованими.

## 20.2. Source maps

Source maps допомагають пов'язати згенерований CSS із вихідними файлами.

Це корисно, коли:
- CSS об'єднується;
- код мініфікується;
- використовуються препроцесори;
- стилі обробляються збирачем.

Завдяки source maps розробник може простіше знайти вихідне правило, яке відповідає конкретному стилю.

Налаштування source maps для production потрібно узгоджувати з вимогами проєкту та політикою публікації вихідного коду.

## 20.3. Кешування CSS

CSS-файли можуть кешуватися браузером.

Для статичних ресурсів часто використовують імена з хешем вмісту, наприклад:

    styles.a1b2c3.css

Якщо вміст змінюється, змінюється і назва файлу. Це допомагає уникати ситуацій, коли браузер використовує застарілий CSS.

Конкретна стратегія залежить від інструмента збирання та налаштувань сервера.

## 20.4. Стиснення на сервері

Сервер або CDN може передавати CSS у стиснутому вигляді за допомогою gzip або Brotli.

Важливо перевірити:
- чи ввімкнене стиснення;
- чи правильно налаштовані заголовки;
- який розмір файлу до та після стиснення;
- чи відповідає кешування стратегії збирання.

# 21. Як вимірювати CSS Performance

## 21.1. Не оптимізуй лише за відчуттями

Сторінка може здаватися повільною через:
- великі зображення;
- повільний сервер;
- JavaScript;
- шрифти;
- мережеві затримки;
- довге виконання layout;
- складні анімації.

Перш ніж змінювати CSS, потрібно знайти справжню причину.

## 21.2. Chrome DevTools

У браузері можна використовувати:

### Elements

Допомагає:
- переглядати CSS-правила;
- бачити перевизначені декларації;
- змінювати стилі в реальному часі;
- досліджувати box model;
- перевіряти медіазапити та класи.

### Network

Допомагає:
- перевіряти розмір CSS-файлів;
- бачити час завантаження;
- визначати, які файли підключені;
- аналізувати кешування;
- порівнювати розміри переданих ресурсів.

### Performance

Допомагає:
- записувати взаємодію зі сторінкою;
- знаходити довгі завдання;
- досліджувати layout і paint;
- аналізувати затримки відображення;
- перевіряти, що відбувається під час анімацій.

### Lighthouse

Допомагає оцінювати:
- продуктивність;
- доступність;
- SEO;
- відповідність окремим найкращим практикам.

Lighthouse дає діагностичні підказки, але не замінює перевірку реального користувацького досвіду.

## 21.3. Що порівнювати до та після

Запиши початкові показники:
- розмір CSS;
- кількість CSS-файлів;
- час завантаження ресурсів;
- показники LCP, CLS та INP, якщо доступні;
- кількість і характер layout/paint у профілі;
- поведінку на мобільному пристрої.

Після оптимізації повтори тест у схожих умовах.

Інакше складно визначити, чи покращення спричинене саме зміною CSS.

## 21.4. Чому важливі повторні вимірювання

Результати можуть змінюватися через:
- кеш;
- стан мережі;
- температуру та навантаження пристрою;
- фонові процеси;
- різні розміри екрана;
- відмінності браузерів.

Для важливих змін варто виконувати кілька вимірювань і порівнювати результати, а не покладатися на один запуск.

# 22. Практичний приклад оптимізації CSS

Розглянемо умовний компонент картки.

## 22.1. Початковий CSS

    .page .content .product-card {
        padding: 20px;
        margin-bottom: 20px;
        background-color: #ffffff;
        border-radius: 8px;
        border: 1px solid #e5e7eb;
    }

    .page .content .product-card h2 {
        font-size: 24px;
        margin-bottom: 12px;
    }

    .page .content .product-card .button {
        padding: 12px 20px;
        border: none;
        border-radius: 6px;
        background-color: #2563eb;
        color: #ffffff;
        cursor: pointer;
    }

    .page .content .product-card .button:hover {
        background-color: #1d4ed8;
    }

Проблеми:
- зайва вкладеність селекторів;
- частина значень може дублюватися в інших компонентах;
- немає явної системи дизайн-токенів;
- стилі кнопки прив'язані до картки, хоча кнопка може використовуватися й деінде.

## 22.2. Оптимізований варіант

    :root {
        --color-primary: #2563eb;
        --color-primary-hover: #1d4ed8;
        --color-surface: #ffffff;
        --color-border: #e5e7eb;
        --radius-card: 8px;
        --radius-button: 6px;
        --space-card: 20px;
    }

    .product-card {
        padding: var(--space-card);
        margin-bottom: var(--space-card);
        background-color: var(--color-surface);
        border: 1px solid var(--color-border);
        border-radius: var(--radius-card);
    }

    .product-card__title {
        margin-bottom: 12px;
        font-size: 24px;
    }

    .button {
        padding: 12px 20px;
        border: none;
        border-radius: var(--radius-button);
        background-color: var(--color-primary);
        color: white;
        cursor: pointer;
    }

    .button:hover {
        background-color: var(--color-primary-hover);
    }

Покращення:
- селектори простіші;
- спільний стиль кнопки можна повторно використовувати;
- значення кольорів централізовані;
- компоненти менше залежать від вкладеності HTML;
- код легше розвивати.

Важливо: цей рефакторинг передусім покращує структуру та підтримуваність. Він не гарантує помітного приросту швидкості рендерингу.

# 23. Типові помилки під час CSS Optimization

## 23.1. Скорочувати код заради скорочення

Погано:

    .a{p:10px}

Цей приклад навіть некоректний: `p` не є скороченою назвою властивості `padding`.

Краще використовувати коректні властивості та автоматичну мініфікацію.

## 23.2. Видаляти стилі без перевірки

Стиль може бути потрібним на іншій сторінці або в динамічному стані компонента.

Спочатку перевіряй використання, потім видаляй.

## 23.3. Використовувати `!important` для розв'язання всіх конфліктів

Це приховує причину проблеми та ускладнює каскад.

Краще перевірити специфічність, порядок правил і архітектуру стилів.

## 23.4. Додавати `will-change` усюди

Це може збільшувати споживання ресурсів.

Використовуй властивість лише за потреби.

## 23.5. Об'єднувати всі CSS-файли в один без аналізу

Великий файл може містити стилі, які не потрібні поточній сторінці.

Орієнтуйся на архітектуру застосунку та результати вимірювань.

## 23.6. Вважати, що `transform` завжди безкоштовний

Трансформації можуть бути ефективними, але складні сцени, великі шари та інші ефекти також можуть створювати навантаження.

Потрібно вимірювати результат.

## 23.7. Використовувати CSS-оптимізацію замість правильної архітектури

Мініфікація не виправить:
- хаотичну структуру файлів;
- постійні конфлікти каскаду;
- надмірну вкладеність компонентів;
- дублювання бізнес-логіки;
- неправильний layout.

Спочатку потрібна зрозуміла структура, потім — оптимізація доставки та рендерингу.

## 23.8. Ігнорувати доступність

Анімації, які спричиняють дискомфорт, недостатній контраст або видалені індикатори фокусу не стають прийнятними лише тому, що код швидкий.

Оптимізація має зберігати доступність і зручність інтерфейсу.

## 23.9. Вимірювати лише на потужному комп'ютері

Сторінка може працювати добре на сучасному настільному ПК, але повільно на бюджетному телефоні.

Перевіряй інтерфейс у різних умовах.

# 24. Покроковий алгоритм CSS Optimization

Коли CSS починає розростатися, дій послідовно.

## Крок 1. Перевір поточний стан

- Чи є візуальні помилки?
- Чи є дубльовані правила?
- Чи багато перевизначень?
- Чи є невикористані стилі?
- Чи повільно завантажується сторінка?
- Чи помітні затримки під час взаємодії?

## Крок 2. Визнач головну проблему

Не намагайся оптимізувати все одночасно.

Приклади:
- великий CSS-файл — досліджуй його склад і розмір;
- повільне перше відображення — досліджуй ресурси, що блокують рендеринг;
- повільна анімація — досліджуй layout, paint і compositing;
- хаотичні стилі — покращуй архітектуру;
- нестабільний layout — перевір розміри, шрифти та адаптивність.

## Крок 3. Виправ очевидні проблеми

- видали підтверджені застарілі стилі;
- прибери реальне дублювання;
- спростити надмірно складні селектори;
- усунь непотрібні перевизначення;
- централізуй повторювані дизайн-значення.

## Крок 4. Перевір production-збирання

- чи виконується мініфікація;
- чи працює стиснення;
- чи правильно формуються CSS-файли;
- чи не потрапляють зайві стилі;
- чи коректно працює кешування.

## Крок 5. Виміряй продуктивність

Використовуй DevTools, Lighthouse та інші доступні інструменти.

Порівняй результати до та після.

## Крок 6. Перевір функціональність

Переконайся, що не зламалися:
- адаптивність;
- кнопки;
- форми;
- модальні вікна;
- hover і focus;
- анімації;
- різні сторінки;
- теми та стани компонентів.

## Крок 7. Зафіксуй результат

У робочому проєкті варто записати:
- яку проблему виявлено;
- що змінено;
- які метрики покращилися;
- які ризики перевірено.

Це допомагає зрозуміти, які оптимізації справді приносять користь.

    03-css-optimization/

            ├── styles.css

## Етап 1. Початкова версія

- заголовок сторінки;
- сітку карток;
- три картки товарів;
- заголовки карток;

- кнопки;
- адаптивний layout.

Навмисно повтори кілька CSS-декларацій у різних класах.

## Етап 2. Рефакторинг

Виконай такі завдання:

- [ ] Знайди дубльовані стилі.
- [ ] Винеси спільні стилі кнопок.
- [ ] Створи CSS-змінні для кольорів.
- [ ] Створи CSS-змінні для відступів.
- [ ] Спрости складні селектори.
- [ ] Прибери правила, які точно не використовуються.
- [ ] Перевір специфічність.
- [ ] Перевір адаптивність.
- [ ] Переконайся, що фокус клавіатури помітний.

## Етап 3. Production

Якщо проєкт використовує інструмент збирання:

- [ ] Перевір production-збирання.
- [ ] Перевір, чи мініфікується CSS.
- [ ] Перевір розмір CSS-файлів.
- [ ] Переконайся, що всі стилі компонентів збережені.
- [ ] Перевір роботу після production-збирання.

Для звичайної статичної сторінки без збирача цей етап можна виконати пізніше, коли з'явиться відповідна інфраструктура.

## Етап 4. Перевірка

Перевір сторінку:
- на вузькому екрані;
- на планшеті;
- на широкому екрані;
- за допомогою клавіатури;
- у різних станах кнопок;
- у DevTools.

Порівняй код до і після оптимізації.

## Критерії успіху

- CSS легше читати.
- Дублювання зменшилося.
- Спільні значення централізовані.
- Стилі компонентів не конфліктують.
- Адаптивність працює.
- Інтерфейс не втратив доступності.
- Production-версія працює так само, як очікувалося.

# 26. Запитання для співбесіди

## Рівень Junior

**1. Що таке CSS Optimization?**

Це покращення структури, розміру, завантаження та поведінки CSS для підвищення підтримуваності й продуктивності сайту.

**2. Чим відрізняється minification від gzip або Brotli?**

Minification змінює текстове представлення CSS, прибираючи зайве форматування та виконуючи безпечні скорочення. gzip і Brotli стискають дані під час передавання.

**3. Навіщо видаляти невикористаний CSS?**

Він збільшує розмір файлів і ускладнює підтримку. Але видаляти його потрібно після перевірки всіх сторінок і динамічних станів.

**4. Для чого потрібні CSS-змінні?**

Для повторного використання значень, централізованої зміни дизайну й підтримки темізації.

**5. Чому небажано використовувати багато `!important`?**

Тому що це ускладнює каскад і подальше перевизначення стилів.

**6. Як перевірити розмір CSS-файлу?**

За допомогою вкладки Network у DevTools або аналізу файлів production-збирання.

**7. Чи потрібно вручну мініфікувати CSS?**

Ні. Зазвичай це робиться автоматично інструментом збирання.

## Рівень Middle

**8. Як CSS впливає на Core Web Vitals?**

Він може впливати на час початкового відображення, стабільність layout і вартість візуальних оновлень. Але потрібно відокремлювати вплив CSS від JavaScript, мережі, сервера та інших ресурсів.

**9. Що таке Critical CSS?**

Це мінімальний набір стилів, необхідних для початкового відображення видимої частини сторінки.

**10. Чому `transform` часто використовують для анімацій?**

Тому що трансформації можуть виконуватися без постійного перерахунку layout. Але реальна ефективність залежить від ситуації.

**11. Що таке unused CSS і чому його складно безпечно видалити?**

Це CSS, який не застосовується до поточного набору елементів. Проблема в тому, що класи можуть додаватися динамічно або використовуватися на інших сторінках і в інших станах.

**12. Що таке Cascade Layers?**

Це механізм керування каскадом, який дозволяє організувати правила в окремі шари з визначеним порядком пріоритету.

**13. Чому не варто оптимізувати селектори лише за припущеннями про швидкість?**

Тому що сучасні браузери мають оптимізації, а реальний вплив залежить від DOM і характеру змін. Спрощення селекторів корисне передусім для підтримуваності.

**14. Як перевірити, що оптимізація дала результат?**

Порівняти вимірювання до та після за однакових умов, перевірити розмір ресурсів, профіль рендерингу й поведінку інтерфейсу.

## Рівень Senior

**15. Як визначити, чи проблема пов'язана з CSS, JavaScript або мережею?**

Потрібно аналізувати Network, Performance, час виконання JavaScript, події layout і paint, а також метрики завантаження. Одного загального показника недостатньо.

**16. Коли доречно використовувати Critical CSS?**

Коли вимірювання виявляють проблему початкового відображення і можна відокремити необхідні для першого екрана стилі від решти.

**17. Як безпечно видаляти невикористані стилі у великому застосунку?**

Аналізувати всі відповідні файли, враховувати динамічні класи, задавати винятки, перевіряти стани компонентів і виконувати регресійні тести.

**18. Як організувати CSS для великого застосунку?**

Використовувати послідовні правила архітектури, компонентні стилі, дизайн-токени, контроль каскаду та автоматичні перевірки.

**19. Коли варто застосовувати `content-visibility`?**

Коли сторінка має великі області вмісту, які не потрібні для початкового відображення, і вимірювання підтверджують потенційну користь.

**20. Чому не можна оцінювати якість CSS лише за розміром файлу?**

Тому що важливі також підтримуваність, правильність, доступність, стабільність layout і продуктивність взаємодії.

# 29. Основні правила, які потрібно запам'ятати

1. **Спочатку вимірюй, потім оптимізуй.** Не кожен CSS-проблемний фрагмент створює помітне навантаження.
2. **Пиши зрозумілий вихідний код.** Мініфікацію доручай інструментам.
3. **Усувай реальне дублювання.** Не об'єднуй незалежні компоненти штучно.
4. **Використовуй CSS-змінні для повторюваних значень.** Це покращує узгодженість і підтримуваність.
5. **Спрощуй селектори.** Не прив'язуй стилі до зайвої вкладеності HTML.
6. **Не видаляй CSS без перевірки.** Динамічні класи можуть бути непомітними статичним аналізаторам.
7. **Не зловживай `!important`.** Каскад повинен залишатися передбачуваним.
8. **Не вважай `transform` або `opacity` абсолютно безкоштовними.** Перевіряй складні анімації на реальних пристроях.
9. **Не плутай оптимізацію файлів з оптимізацією рендерингу.** Це різні завдання.
10. **Пам'ятай про доступність.** Продуктивний інтерфейс має залишатися зручним для різних користувачів.
11. **Перевіряй production-версію.** Результат збирання може відрізнятися від development.
12. **Порівнюй результати до та після.** Оптимізація повинна мати зрозумілу мету й перевірюваний результат.

# 30. Головне, що потрібно зрозуміти

CSS Optimization — це не змагання за найменшу кількість рядків.

Якісний CSS має бути:

- **зрозумілим** — інший розробник може швидко розібратися в коді;
- **підтримуваним** — зміни не вимагають виправляти десятки незалежних місць;
- **передбачуваним** — каскад і специфічність не створюють постійних конфліктів;
- **ефективним** — зайві ресурси та непотрібна робота браузера мінімізовані;
- **адаптивним** — компоненти працюють на різних розмірах екрана;
- **доступним** — оптимізація не погіршує взаємодію;
- **вимірюваним** — важливі рішення можна перевірити за допомогою інструментів.

Для початку достатньо навчитися прибирати дублювання, використовувати CSS-змінні, підтримувати прості селектори й перевіряти розмір файлів. Надалі варто переходити до production-збирання, аналізу рендерингу, Core Web Vitals та оптимізації складних інтерфейсів.

**Основна формула:**

    CSS Optimization =
        Clean Code
        + Reusable Styles
        + Efficient Delivery
        + Rendering Performance
        + Measurement
