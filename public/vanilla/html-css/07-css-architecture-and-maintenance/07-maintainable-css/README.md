# Maintainable CSS — CSS, який легко підтримувати

> **Maintainable CSS** — це підхід до написання CSS, за якого стилі залишаються зрозумілими, передбачуваними та зручними для змін у міру зростання проєкту. Мета — не просто зробити сторінку красивою, а побудувати систему стилів, яку можна безпечно розширювати, виправляти й повторно використовувати.

📁 `html-css/07-css-architecture-and-maintenance/07-maintainable-css/`

---

## 1. Що таке Maintainable CSS

CSS легко написати для однієї невеликої сторінки. Складніше підтримувати його, коли в проєкті з'являються десятки компонентів, багато сторінок, адаптивні макети, теми оформлення та кілька розробників.

**Maintainable CSS** — це CSS, який:

- легко читати;
- має зрозумілу структуру;
- використовує послідовні назви класів;
- мінімізує випадкові конфлікти;
- не дублює однакові правила без потреби;
- має передбачувану специфічність;
- дозволяє змінювати один компонент без поломки інших;
- підтримує адаптивність і доступність;
- не ускладнює прості завдання зайвими абстракціями.

### Приклад погано підтримуваного CSS

    .box {
        width: 300px;
        margin-left: 20px;
        color: #333;
    }

    .box2 {
        width: 300px;
        margin-left: 20px;
        color: #333;
    }

    .box3 {
        width: 300px;
        margin-left: 20px;
        color: #333;
    }

Проблеми:

- назви класів нічого не пояснюють;
- однакові правила дублюються;
- зміна відступу потребуватиме редагування декількох місць;
- складно зрозуміти призначення кожного блока.

### Кращий варіант

    .product-card {
        width: 300px;
        margin-inline-start: 20px;
        color: var(--color-text);
    }

    .article-card {
        width: 300px;
        margin-inline-start: 20px;
        color: var(--color-text);
    }

Якщо картки мають справді спільні правила, можна створити спільний клас або використати інший спосіб повторного використання.

    .card {
        width: 300px;
        margin-inline-start: 20px;
        color: var(--color-text);
    }

    .product-card {
        /* Лише особливості товарної картки */
    }

**Головний принцип:** код має пояснювати намір розробника, а не змушувати читача здогадуватися.

## 2. Основні принципи підтримуваного CSS

### 2.1. Читабельність

Код потрібно писати так, щоб його можна було швидко зрозуміти.

Не дуже добре:

    .card{padding:20px;background:#fff;border:1px solid #ddd;border-radius:10px}.card h2{font-size:24px;margin:0 0 10px}

Краще:

    .card {
        padding: 20px;
        background-color: #fff;
        border: 1px solid #ddd;
        border-radius: 10px;
    }

    .card__title {
        margin: 0 0 10px;
        font-size: 24px;
    }

Читабельність особливо важлива, коли потрібно швидко знайти причину помилки.

### 2.2. Послідовність

Обери правила написання CSS і дотримуйся їх у всьому проєкті.

Наприклад:

- однаковий стиль відступів у коді;
- послідовний порядок властивостей;
- зрозумілі назви класів;
- однаковий підхід до кольорів і відступів;
- однакова структура компонентів;
- зрозумілі правила медіазапитів.

Не так важливо, який саме стиль ти вибереш. Важливіше, щоб він був послідовним.

### 2.3. Повторне використання

Якщо однакові значення повторюються в багатьох компонентах, розглянь можливість винести їх у CSS custom properties або спільні класи.

    :root {
        --color-primary: #2563eb;
        --color-text: #1f2937;
        --color-border: #e5e7eb;

        --space-sm: 8px;
        --space-md: 16px;
        --space-lg: 24px;

        --radius-md: 10px;
    }

    .button {
        padding: var(--space-sm) var(--space-md);
        border-radius: var(--radius-md);
        background-color: var(--color-primary);
        color: white;
    }

    .card {
        padding: var(--space-lg);
        border: 1px solid var(--color-border);
        border-radius: var(--radius-md);
        color: var(--color-text);
    }

### 2.4. Низька зв'язаність

Зміна стилів одного компонента не повинна несподівано змінювати інші компоненти.

Наприклад, небажано без особливої причини задавати стилі всім заголовкам усередині всіх карток:

    .card h2 {
        color: red;
    }

Якщо різні картки мають різне призначення, такий селектор може бути надто широким.

Можна використати окремий клас:

    .product-card__title {
        color: var(--color-text);
    }

Або локальні стилі компонента, якщо проєкт використовує CSS Modules.

### 2.5. Мінімальна необхідна складність

Не потрібно створювати складну архітектуру для трьох простих стилів.

Використовуй абстракції тоді, коли вони вирішують реальну проблему:

- повторення;
- масштабування;
- конфлікти;
- командну роботу;
- підтримку великої кількості компонентів.

## 3. Зрозумілі назви класів

Назва класу повинна пояснювати роль елемента або його призначення.

### Погані назви

    .red
    .big
    .box1
    .left
    .text2
    .item3

Ці назви описують колір, розмір або випадковий номер, але не пояснюють, що саме представляє елемент.

### Кращі назви

    .product-card
    .navigation
    .article-title
    .user-avatar
    .form-error
    .search-button

Такі назви залишаються зрозумілими навіть після зміни дизайну.

Наприклад, клас `.red` стає незрозумілим, якщо елемент тепер має бути синім.

А клас `.form-error` зберігає сенс незалежно від кольору повідомлення.

### Називай за призначенням, а не за зовнішнім виглядом

Не дуже добре:

    .green-button {
        background-color: green;
    }

Краще:

    .button--success {
        background-color: var(--color-success);
    }

Другий варіант описує роль кнопки, а не її конкретний колір.

### Коли назва за зовнішнім виглядом допустима

Іноді утилітарні класи справді описують оформлення:

    .text-center {
        text-align: center;
    }

    .visually-hidden {
        position: absolute;
        width: 1px;
        height: 1px;
        padding: 0;
        margin: -1px;
        overflow: hidden;
        clip-path: inset(50%);
        white-space: nowrap;
        border: 0;
    }

Такі класи мають сенс, якщо вони є частиною узгодженої системи утиліт.

## 4. Методології іменування CSS-класів

Для підтримуваного CSS корисно вибрати зрозумілий підхід до назв класів.

### 4.1. Semantic naming

Назва описує зміст або роль елемента.

    .header
    .main-navigation
    .product-card
    .user-profile
    .form-message

Перевага: назви зрозумілі й не залежать від конкретного кольору чи розміру.

### 4.2. BEM

**BEM** означає Block, Element, Modifier.

Це методологія організації назв класів, яка допомагає зрозуміти структуру компонента.

Приклад:

    .card {
        padding: 20px;
    }

    .card__title {
        font-size: 24px;
    }

    .card__description {
        color: #666;
    }

    .card--featured {
        border: 2px solid royalblue;
    }

Основні частини:

- `card` — блок;
- `card__title` — елемент блока;
- `card__description` — ще один елемент;
- `card--featured` — модифікатор блока.

#### Block

Самостійний компонент.

    .card

#### Element

Частина блока, яка не має самостійного сенсу поза ним.

    .card__title

#### Modifier

Варіант або стан блока чи елемента.

    .card--featured

    .button--primary

    .button--disabled

### Приклад HTML

    <article class="card card--featured">
        <h2 class="card__title">CSS Architecture</h2>

        <p class="card__description">
            Як організувати стилі для великого проєкту.
        </p>

        <button class="button button--primary">
            Детальніше
        </button>
    </article>

### Коли BEM корисний

- У великих проєктах зі звичайним CSS.
- Коли працює декілька розробників.
- Коли потрібно швидко визначати належність класу до компонента.
- Коли стилі не ізольовані за допомогою CSS Modules.

### Чи обов'язково використовувати BEM?

Ні. Це один із підходів, а не єдино правильний спосіб.

У CSS Modules часто достатньо коротких локальних назв:

    .card {
        padding: 20px;
    }

    .title {
        font-size: 24px;
    }

Оскільки класи локальні для модуля, потреба в довгих префіксах може бути меншою.

## 5. Уникай надмірної специфічності

Специфічність визначає, яке CSS-правило має перевагу, коли кілька правил намагаються змінити одну властивість.

Чим складніший селектор, тим важче його перевизначити.

### Приклад проблемного CSS

    body .page main .content .card h2.title {
        color: navy;
    }

Щоб змінити колір, розробнику може знадобитися ще складніший селектор.

### Кращий варіант

    .card__title {
        color: navy;
    }

Простий селектор легше знайти та змінити.

### Приклад конфлікту

    .button {
        background-color: royalblue;
    }

    .page .button {
        background-color: crimson;
    }

Другий селектор має вищу специфічність, тому звичайний `.button` не зможе його перекрити лише за рахунок того, що оголошений пізніше.

### Правило

Намагайся:

- використовувати прості селектори;
- не додавати зайві рівні вкладеності;
- не зловживати `!important`;
- уникати непотрібних ID-селекторів для оформлення;
- підтримувати зрозумілу ієрархію стилів.

### Чому небажано зловживати `!important`

    .button {
        background-color: blue !important;
    }

    .button {
        background-color: red;
    }

Друге правило не змінить фон на червоний, оскільки перше використовує `!important`.

Якщо таких правил багато, керувати каскадом стає складніше.

`!important` іноді виправданий, але не повинен бути стандартним способом розв'язання конфліктів.

## 6. Не використовуй HTML-структуру як єдину основу стилів

CSS-селектори можуть залежати від структури документа.

Наприклад:

    header nav ul li a {
        color: navy;
    }

Такий селектор залежить від конкретної вкладеності елементів.

Якщо структура HTML зміниться, правило може перестати працювати.

Часто краще:

    .navigation__link {
        color: navy;
    }

HTML:

    <nav class="navigation">
        <a class="navigation__link" href="/">Головна</a>
        <a class="navigation__link" href="/about">Про нас</a>
    </nav>

Тепер стилі залежать від призначення елемента, а не від усіх його батьків.

### Чи потрібно повністю уникати селекторів елементів?

Ні.

Селектори елементів корисні для базових стилів:

    body {
        margin: 0;
        font-family: Arial, sans-serif;
    }

    h1,
    h2,
    h3 {
        line-height: 1.2;
    }

Проблема виникає тоді, коли вся архітектура залежить від довгих селекторів структури HTML.

## 7. Уникай дублювання CSS

Дублювання збільшує обсяг коду та ускладнює зміни.

### Приклад дублювання

    .primary-button {
        padding: 10px 16px;
        border-radius: 8px;
        font-size: 16px;
    }

    .secondary-button {
        padding: 10px 16px;
        border-radius: 8px;
        font-size: 16px;
    }

    .danger-button {
        padding: 10px 16px;
        border-radius: 8px;
        font-size: 16px;
    }

### Варіант зі спільним класом

    .button {
        padding: 10px 16px;
        border: none;
        border-radius: 8px;
        font-size: 16px;
    }

    .button--primary {
        background-color: royalblue;
        color: white;
    }

    .button--secondary {
        background-color: #e5e7eb;
        color: #111827;
    }

    .button--danger {
        background-color: crimson;
        color: white;
    }

HTML:

    <button class="button button--primary">Зберегти</button>

    <button class="button button--secondary">Скасувати</button>

    <button class="button button--danger">Видалити</button>

Тепер спільні властивості зберігаються в одному місці, а модифікатори описують відмінності.

### Коли не потрібно об'єднувати стилі

Не кожне повторення є проблемою.

Якщо два компоненти мають схожі стилі, але різні життєві цикли та призначення, передчасне об'єднання може створити зайву залежність.

**Принцип:** усувай змістовне дублювання, але не створюй абстракції лише заради скорочення кількості рядків.

## 8. CSS custom properties як основа дизайн-системи

CSS-змінні допомагають централізовано керувати кольорами, відступами, розмірами та іншими повторюваними значеннями.

### Приклад дизайн-токенів

    :root {
        /* Colors */
        --color-primary: #2563eb;
        --color-primary-hover: #1d4ed8;
        --color-text: #1f2937;
        --color-muted: #6b7280;
        --color-border: #e5e7eb;
        --color-surface: #ffffff;
        --color-danger: #dc2626;
        --color-success: #15803d;

        /* Spacing */
        --space-1: 4px;
        --space-2: 8px;
        --space-3: 12px;
        --space-4: 16px;
        --space-6: 24px;
        --space-8: 32px;

        /* Radius */
        --radius-sm: 4px;
        --radius-md: 8px;
        --radius-lg: 16px;

        /* Typography */
        --font-size-sm: 14px;
        --font-size-md: 16px;
        --font-size-lg: 24px;

        /* Shadows */
        --shadow-card: 0 4px 12px rgb(0 0 0 / 8%);
    }

### Використання токенів

    .card {
        padding: var(--space-6);
        border: 1px solid var(--color-border);
        border-radius: var(--radius-lg);
        background-color: var(--color-surface);
        box-shadow: var(--shadow-card);
    }

    .card__title {
        margin-bottom: var(--space-3);
        color: var(--color-text);
        font-size: var(--font-size-lg);
    }

    .card__description {
        color: var(--color-muted);
        font-size: var(--font-size-md);
    }

### Переваги

- Зміна основного кольору в одному місці.
- Єдина шкала відступів.
- Узгоджені радіуси та тіні.
- Простіше створювати теми.
- Менше випадкових значень у стилях.

### Не перетворюй кожне значення на токен

Не потрібно створювати змінну для кожного одноразового числа.

Токени найбільш корисні для значень, які повторюються або мають системне значення.

## 9. Організація CSS-файлів

Зрозуміла структура файлів допомагає швидко знаходити стилі.

### Варіант для невеликого статичного сайту

    css/
    ├── reset.css
    ├── variables.css
    ├── base.css
    ├── layout.css
    ├── components.css
    └── main.css

Призначення:

- `reset.css` — нормалізація або скидання вибраних стилів;
- `variables.css` — CSS custom properties;
- `base.css` — базові стилі HTML-елементів;
- `layout.css` — структура сторінки;
- `components.css` — компоненти інтерфейсу;
- `main.css` — головний файл, який підключає інші файли, якщо це передбачено обраною системою.

### Варіант для компонентного проєкту

    src/
    ├── styles/
    │   ├── reset.css
    │   ├── tokens.css
    │   └── globals.css
    ├── components/
    │   ├── Button/
    │   │   ├── Button.jsx
    │   │   └── Button.module.css
    │   ├── Card/
    │   │   ├── Card.jsx
    │   │   └── Card.module.css
    │   └── Header/
    │       ├── Header.jsx
    │       └── Header.module.css
    └── App.jsx

У компонентній архітектурі стилі компонента часто зберігають поруч із його кодом.

### Не потрібно створювати десятки файлів без потреби

Для маленької сторінки один `styles.css` може бути цілком достатнім.

Структура повинна допомагати навігації, а не створювати додаткову роботу.

## 10. Порядок CSS-властивостей

Єдиного обов'язкового порядку CSS-властивостей немає. Проте послідовна організація покращує читабельність.

Можна групувати властивості так:

1. Позиціювання.
2. Модель відображення.
3. Розміри.
4. Відступи.
5. Межі.
6. Фон і колір.
7. Типографіка.
8. Візуальні ефекти.
9. Анімація та переходи.

Приклад:

    .card {
        /* Positioning */
        position: relative;

        /* Layout */
        display: flex;
        flex-direction: column;
        gap: 16px;

        /* Sizing */
        width: 100%;
        max-width: 400px;

        /* Spacing */
        padding: 24px;

        /* Border */
        border: 1px solid var(--color-border);
        border-radius: var(--radius-lg);

        /* Colors */
        background-color: var(--color-surface);
        color: var(--color-text);

        /* Effects */
        box-shadow: var(--shadow-card);

        /* Animation */
        transition: box-shadow 0.2s ease;
    }

Цей порядок — рекомендація, а не стандарт.

Для невеликих правил не потрібно обов'язково додавати коментарі до кожної групи. Важлива загальна послідовність у проєкті.

## 11. Коментарі в CSS

Коментарі корисні, якщо пояснюють причину рішення, яке неочевидне з коду.

### Корисний коментар

    /*
     * Відступ збільшений для компенсації вбудованої висоти
     * стороннього віджета, яка не може бути змінена.
     */
    .external-widget-wrapper {
        padding-top: 24px;
    }

### Не дуже корисний коментар

    /* Колір тексту */
    .title {
        color: navy;
    }

Сама властивість `color` і так показує, що задається колір.

### Коментарі для секцій

    /* =========================
       Header
       ========================= */

    .header {
        display: flex;
        align-items: center;
        justify-content: space-between;
    }

Такі коментарі можуть допомогти у великому файлі.

### Коли коментар потрібний

- Є нетривіальне технічне обмеження.
- Використовується незвичайний обхідний шлях.
- Є залежність від сторонньої бібліотеки.
- Певне правило не можна очевидно спростити.
- Важливо пояснити, чому обрано саме таке рішення.

**Правило:** коментар має пояснювати «чому», якщо це неочевидно, а не просто повторювати «що» написано в коді.

---

## 12. Не зловживай `!important`

Використання `!important` часто приховує проблему каскаду.

Погано:

    .title {
        color: navy !important;
    }

    .page .title {
        color: crimson !important;
    }

Коли таких правил багато, стає складніше визначити, яке оформлення має застосовуватися.

Краще спочатку перевірити:

- специфічність селекторів;
- порядок підключення CSS;
- каскадні шари;
- глобальні стилі;
- стилі компонентів;
- чи справді потрібно перевизначати правило.

### Коли `!important` може бути виправданий

- Потрібно перевизначити зовнішній стиль, який неможливо змінити іншим способом.
- Створюється невеликий набір утиліт із навмисно високим пріоритетом.
- Є обґрунтована технічна причина.

У звичайних стилях компонентів краще використовувати зрозумілу структуру каскаду.

---

## 13. CSS Cascade Layers

Каскадні шари `@layer` допомагають явно організувати пріоритети груп стилів.

Це корисно, коли проєкт має глобальні стилі, компоненти та утиліти.

### Приклад

    @layer reset, base, components, utilities;

    @layer reset {
        * {
            box-sizing: border-box;
        }

        body {
            margin: 0;
        }
    }

    @layer base {
        body {
            font-family: Arial, sans-serif;
            color: #1f2937;
        }
    }

    @layer components {
        .button {
            padding: 10px 16px;
            border-radius: 8px;
        }
    }

    @layer utilities {
        .text-center {
            text-align: center;
        }
    }

### Для чого це потрібно

Шари дозволяють організувати CSS за категоріями:

- reset;
- base;
- components;
- utilities;
- themes.

Важливо: каскадні шари мають власні правила пріоритетів. Для звичайних декларацій пізніші шари мають перевагу над попередніми, коли інші умови каскаду рівні. Для `!important` порядок пріоритетів шарів протилежний.

Не додавай `@layer` лише заради моди. Він найбільш корисний, коли проєкт має багато незалежних груп стилів і потрібно явно керувати їхнім пріоритетом.

## 14. Адаптивний CSS, який легко підтримувати

Адаптивність краще організовувати системно, а не додавати випадкові медіазапити після кожної проблеми.

### Поганий підхід

    @media (max-width: 1000px) {
        .card {
            width: 90%;
        }
    }

    @media (max-width: 900px) {
        .card {
            width: 85%;
        }
    }

    @media (max-width: 800px) {
        .card {
            width: 80%;
        }
    }

Якщо кожен медіазапит лише змінює ширину на кілька відсотків, можливо, проблему можна вирішити простішим правилом.

### Кращий підхід

    .card {
        width: min(100%, 420px);
        padding: 20px;
    }

Або для контейнера карток:

    .card-list {
        display: grid;
        grid-template-columns: repeat(auto-fit, minmax(min(100%, 260px), 1fr));
        gap: 24px;
    }

Тут Grid сам підбирає кількість колонок відповідно до доступної ширини.

### Використовуй медіазапити, коли справді потрібно змінити поведінку

    .navigation {
        display: flex;
        gap: 24px;
    }

    @media (max-width: 640px) {
        .navigation {
            flex-direction: column;
            gap: 12px;
        }
    }

### Принципи підтримуваної адаптивності

- Починай із гнучкого макета.
- Використовуй Flexbox і Grid.
- Застосовуй `min()`, `max()` і `clamp()` за потреби.
- Не дублюй однакові медіазапити без причини.
- Обирай точки перелому відповідно до контенту.
- Перевіряй реальну поведінку на різних ширинах.

## 15. Доступність як частина підтримуваного CSS

Підтримуваний CSS повинен працювати не лише візуально, а й для людей, які використовують клавіатуру, екранні читачі або налаштування підвищеної контрастності.

### Видимий фокус

    .button:focus-visible {
        outline: 3px solid #2563eb;
        outline-offset: 3px;
    }

Не прибирай фокус клавіатури без доступної альтернативи.

### Не покладайся лише на колір

Якщо помилка позначається лише червоним кольором, частина користувачів може її не розпізнати.

Краще поєднувати колір із текстом або іншим візуальним індикатором.

    .form-error {
        color: #b91c1c;
        font-weight: 600;
    }

HTML:

    <p class="form-error">
        Помилка: перевір адресу електронної пошти.
    </p>

### Ураховуй зменшення руху

    .animated-card {
        transition: transform 0.2s ease;
    }

    .animated-card:hover {
        transform: translateY(-4px);
    }

    @media (prefers-reduced-motion: reduce) {
        .animated-card {
            transition: none;
        }

        .animated-card:hover {
            transform: none;
        }
    }

### Перевіряй контраст

Текст повинен бути достатньо контрастним відносно фону. Не оцінюй доступність лише на око — за потреби використовуй інструменти перевірки контрасту.

## 16. CSS і принцип DRY

**DRY** — Don't Repeat Yourself, тобто «не повторюй одне й те саме без потреби».

У CSS цей принцип означає, що спільні значення та правила варто організовувати так, щоб їх можна було змінювати в одному місці.

### Приклад із CSS custom properties

Без змінних:

    .header {
        background-color: #2563eb;
    }

    .button {
        background-color: #2563eb;
    }

    .link {
        color: #2563eb;
    }

Із токеном:

    :root {
        --color-primary: #2563eb;
    }

    .header {
        background-color: var(--color-primary);
    }

    .button {
        background-color: var(--color-primary);
    }

    .link {
        color: var(--color-primary);
    }

Тепер змінити основний колір можна в одному місці.

### DRY не означає «ніколи не повторюй код»

Надмірне прагнення до DRY може призвести до створення складних абстракцій.

Якщо два правила схожі лише випадково, об'єднання може зробити код менш зрозумілим.

Краще спочатку зрозуміти, чи справді повторюється одна й та сама концепція.

---

## 17. CSS і принцип KISS

**KISS** — Keep It Simple, тобто «зберігай простоту».

Підтримуваний CSS не повинен бути складнішим, ніж потрібно для завдання.

### Надмірна складність

    .page > .main > .content > .section > .card > .body > .title {
        font-size: 24px;
    }

### Простіший варіант

    .card__title {
        font-size: 24px;
    }

Так само не потрібно створювати окрему систему класів, препроцесор або складну структуру файлів для маленької статичної сторінки, якщо звичайного CSS достатньо.

### Практичне правило

Перед тим як додати складність, запитай себе:

- Яку проблему це вирішує?
- Чи стане код зрозумілішим?
- Чи спростить це майбутні зміни?
- Чи можна досягти того самого простішим способом?

---

## 18. CSS і принцип Single Responsibility

Принцип єдиної відповідальності означає, що компонент або клас має зрозуміле призначення.

У CSS це не жорстке правило, але корисний орієнтир.

### Надто універсальний клас

    .item {
        width: 100%;
        padding: 20px;
        background: white;
        color: navy;
        border: 1px solid gray;
        display: flex;
        align-items: center;
        justify-content: space-between;
        position: relative;
        text-transform: uppercase;
    }

Такий клас може одночасно визначати структуру, кольори, типографіку та поведінку різних елементів.

### Більш зрозумілий поділ

    .product-row {
        display: flex;
        align-items: center;
        justify-content: space-between;
        gap: 16px;
        padding: 20px;
    }

    .product-row__title {
        color: var(--color-text);
    }

    .product-row__price {
        font-weight: 700;
    }

Не потрібно механічно розділяти кожну властивість на окремий клас. Головне — щоб структура відповідала реальному призначенню компонента.

---

## 19. Не зловживай глобальними селекторами

Глобальні правила впливають на багато частин сторінки. Це корисно для базових стилів, але небезпечно для специфічних компонентів.

### Ризикований приклад

    h2 {
        color: crimson;
        margin-bottom: 30px;
    }

Таке правило змінює всі заголовки другого рівня, навіть якщо вони належать до різних компонентів.

### Більш контрольований варіант

    .article-title {
        color: crimson;
        margin-bottom: 30px;
    }

Для базових стилів можна залишити глобальні правила:

    body {
        font-family: Arial, sans-serif;
    }

    img {
        max-width: 100%;
        height: auto;
    }

Визначай, які правила мають діяти в усьому проєкті, а які — лише в окремому компоненті.

---

## 20. CSS Modules як інструмент підтримуваності

CSS Modules — один із способів зробити стилі більш ізольованими.

### Файл `Card.module.css`

    .card {
        padding: 20px;
        border: 1px solid #ddd;
        border-radius: 12px;
    }

    .title {
        margin-bottom: 8px;
        font-size: 24px;
    }

### Файл `Card.jsx`

    import styles from "./Card.module.css";

    export default function Card() {
        return (
            <article className={styles.card}>
                <h2 className={styles.title}>Назва картки</h2>
            </article>
        );
    }

Локальні класи допомагають зменшити ризик конфліктів з однойменними класами інших компонентів.

### Що CSS Modules не вирішує автоматично

- Не виправляє неправильну структуру CSS.
- Не усуває дублювання значень.
- Не гарантує доступність.
- Не скасовує каскад.
- Не робить будь-який компонент простим для підтримки.
- Не замінює дизайн-систему.

CSS Modules — це інструмент архітектури, а не повна архітектура сама по собі.

## 21. CSS і Sass/SCSS

Sass — це препроцесор, який додає можливості для організації стилів, наприклад змінні Sass, міксини, функції та модулі.

CSS custom properties і Sass variables — не одне й те саме.

### Змінна Sass

    $primary-color: #2563eb;

    .button {
        background-color: $primary-color;
    }

Значення обробляється під час компіляції Sass.

### CSS custom property

    :root {
        --primary-color: #2563eb;
    }

    .button {
        background-color: var(--primary-color);
    }

CSS custom properties доступні в браузері й можуть змінюватися під час виконання, наприклад залежно від теми.

### Коли корисний Sass

- Є складні повторювані шаблони стилів.
- Потрібні міксини або функції Sass.
- Проєкт має історично сформовану SCSS-архітектуру.
- Команда вже використовує Sass.

### Коли достатньо сучасного CSS

- Потрібні змінні для кольорів та відступів.
- Макет можна реалізувати через Grid і Flexbox.
- Вкладеність підтримується цільовими браузерами.
- Немає потреби в додаткових можливостях препроцесора.

Не варто додавати Sass лише для того, щоб мати змінні: CSS custom properties уже вирішують багато таких завдань.

## 22. Maintainable CSS у React і Next.js

У компонентних застосунках корисно розділяти стилі за відповідальністю.

### Приклад структури

    src/
    ├── app/
    │   ├── globals.css
    │   └── page.tsx
    ├── components/
    │   ├── Button/
    │   │   ├── Button.tsx
    │   │   └── Button.module.css
    │   ├── Card/
    │   │   ├── Card.tsx
    │   │   └── Card.module.css
    │   └── Header/
    │       ├── Header.tsx
    │       └── Header.module.css
    └── styles/
        └── tokens.css

### `globals.css`

    * {
        box-sizing: border-box;
    }

    html {
        color-scheme: light;
    }

    body {
        margin: 0;
        font-family: Arial, sans-serif;
        color: var(--color-text);
        background-color: var(--color-surface);
    }

### `tokens.css`

    :root {
        --color-primary: #2563eb;
        --color-text: #1f2937;
        --color-surface: #ffffff;
        --color-border: #e5e7eb;

        --space-sm: 8px;
        --space-md: 16px;
        --space-lg: 24px;

        --radius-md: 8px;
        --radius-lg: 16px;
    }

### `Button.module.css`

    .button {
        padding: var(--space-sm) var(--space-md);
        border: none;
        border-radius: var(--radius-md);
        background-color: var(--color-primary);
        color: white;
        cursor: pointer;
    }

    .button:focus-visible {
        outline: 3px solid #93c5fd;
        outline-offset: 3px;
    }

У Next.js глобальні стилі й токени потрібно імпортувати відповідно до структури та правил конкретного застосунку. У App Router глобальні стилі зазвичай імпортують у кореневому layout.

### Переваги

- Глобальні правила зібрані в одному місці.
- Дизайн-токени централізовані.
- Компоненти мають власні стилі.
- Зменшується ризик конфліктів.
- Структура проєкту стає передбачуваною.

## 23. Як знаходити й виправляти CSS-проблеми

Підтримуваний CSS передбачає не лише написання коду, а й системну діагностику.

### Алгоритм пошуку проблеми

1. Відкрий сторінку в браузері.
2. Знайди елемент через DevTools.
3. Перевір його класи та структуру DOM.
4. Відкрий вкладку Styles.
5. Знайди правило, яке задає проблемну властивість.
6. Перевір, чи правило перекрите іншим.
7. Перевір специфічність і порядок оголошень.
8. Перевір медіазапити та CSS custom properties.
9. Знайди джерело правила.
10. Виправ першопричину, а не додавай випадкове перевизначення.

### Приклад

Текст має бути синім, але відображається червоним.

    .title {
        color: royalblue;
    }

    .page .title {
        color: crimson;
    }

Проблема полягає в тому, що другий селектор має вищу специфічність.

Замість того щоб одразу додавати `!important`, перевір, чи справді правило `.page .title` потрібне.

### Корисні інструменти

- Browser DevTools.
- Вкладки Elements і Styles.
- Вкладка Computed.
- Перевірка адаптивного режиму.
- Перевірка доступності.
- Лінтери CSS.

## 24. Stylelint: автоматична перевірка CSS

Stylelint — інструмент статичного аналізу CSS, який допомагає виявляти помилки та підтримувати узгоджені правила стилю.

Він може допомагати з:

- неправильним синтаксисом;
- дубльованими деклараціями;
- неузгодженими правилами форматування;
- проблемними шаблонами коду;
- помилками в написанні властивостей;
- дотриманням правил команди.

### Встановлення

У Node.js-проєкті Stylelint можна встановити як dev-залежність.

    npm install --save-dev stylelint stylelint-config-standard

### Приклад конфігурації

Створи файл `.stylelintrc.json`:

    {
        "extends": ["stylelint-config-standard"]
    }

### Додавання скрипта

У `package.json`:

    {
        "scripts": {
            "lint:css": "stylelint \"**/*.css\""
        }
    }

Запуск:

    npm run lint:css

Це приклад базового налаштування. Для конкретного проєкту конфігурацію варто адаптувати до використовуваних інструментів, CSS Modules, Sass та інших особливостей.

### Важливо

Лінтер не замінює розуміння CSS. Він автоматизує перевірки, які можна формалізувати.

---

## 25. Prettier і форматування CSS

Prettier — інструмент автоматичного форматування коду.

Він допомагає підтримувати єдиний стиль оформлення:

- перенесення рядків;
- відступи;
- пробіли;
- форматування декларацій;
- форматування файлів конфігурації.

### Чим відрізняються Stylelint і Prettier

| Інструмент | Основне призначення |
|---|---|
| Prettier | Форматування коду |
| Stylelint | Перевірка CSS-правил і дотримання домовленостей |
| Browser DevTools | Діагностика фактичного відображення сторінки |

У командному проєкті їх можна використовувати разом.

Не потрібно встановлювати всі інструменти одразу в кожному навчальному завданні. Спочатку навчись писати зрозумілий CSS, а потім автоматизуй повторювані перевірки.

## 26. Перевірка CSS перед завершенням роботи

Перед тим як вважати компонент готовим, перевір:

### Структура

- Чи зрозумілі назви класів?
- Чи відповідає структура CSS призначенню компонента?
- Чи немає зайвих рівнів вкладеності?
- Чи немає випадкового дублювання?

### Каскад

- Чи не використовуються непотрібні `!important`?
- Чи зрозуміла специфічність селекторів?
- Чи немає конфліктів із глобальними стилями?
- Чи передбачуваний порядок стилів?

### Повторне використання

- Чи повторюються однакові значення?
- Чи потрібні CSS custom properties?
- Чи справді спільні стилі належать до одного компонента або системи?

### Адаптивність

- Чи працює компонент на вузькому екрані?
- Чи немає горизонтального прокручування без потреби?
- Чи не залежать розміри від випадкових фіксованих значень?
- Чи зрозумілі точки перелому?

### Доступність

- Чи є видимий фокус клавіатури?
- Чи достатній контраст?
- Чи не передається важлива інформація лише кольором?
- Чи враховується зменшення руху, якщо є анімації?

### Підтримуваність

- Чи легко знайти потрібне правило?
- Чи зрозуміє інший розробник код?
- Чи можна змінити компонент без неочікуваних побічних ефектів?
- Чи відповідає складність реальному розміру завдання?

## 28. Темна тема як приклад підтримуваної архітектури

CSS custom properties дозволяють створювати теми без переписування кожного компонента.

### Світла тема

    :root {
        color-scheme: light;

        --color-text: #1f2937;
        --color-surface: #ffffff;
        --color-border: #e5e7eb;
    }

### Темна тема

    [data-theme="dark"] {
        color-scheme: dark;

        --color-text: #f3f4f6;
        --color-surface: #111827;
        --color-border: #374151;
    }

### Компонент

    .card {
        padding: 24px;
        border: 1px solid var(--color-border);
        border-radius: 16px;
        background-color: var(--color-surface);
        color: var(--color-text);
    }

### HTML

    <html lang="uk" data-theme="dark">

Змінивши значення змінних, можна змінити вигляд усіх компонентів, які їх використовують.

Це приклад того, як дизайн-токени зменшують дублювання й роблять теми простішими для підтримки.

Для повноцінної темної теми потрібно перевірити не лише кольори тексту й фону, а й тіні, межі, зображення, фокус, стани помилок і контраст.

## 29. Як рефакторити CSS без зайвого ризику

Рефакторинг — це зміна внутрішньої структури коду без навмисної зміни його зовнішньої поведінки.

### Безпечний порядок роботи

1. Переконайся, що поточний інтерфейс працює.
2. Знайди конкретну проблему.
3. Зміни невелику частину CSS.
4. Перевір сторінку в браузері.
5. Перевір адаптивні стани.
6. Перевір, чи не зламалися інші компоненти.
7. Видали непотрібні правила лише після перевірки.
8. Збережи зрозумілий Git-коміт.

### Приклад

Було:

    .box1 {
        background-color: #2563eb;
        padding: 16px;
    }

    .box2 {
        background-color: #2563eb;
        padding: 16px;
    }

Стало:

    .highlight-box {
        background-color: var(--color-primary);
        padding: var(--space-md);
    }

Перед заміною переконайся, що обидва елементи справді мають однакове призначення та однакову поведінку.

Не варто перейменовувати всі класи, перебудовувати файли й змінювати дизайн одночасно: тоді складніше визначити причину помилки.

## 30. Типові помилки в підтримуваному CSS

### Помилка 1. Назви, що описують лише колір

    .blue
    .red
    .green

Краще використовувати назви за роллю:

    .button--primary
    .status--error
    .status--success

### Помилка 2. Випадкові числові назви

    .item1
    .item2
    .item3

Краще:

    .product-card
    .article-card
    .profile-card

### Помилка 3. Занадто довгі селектори

    .page .content .section .card .body .title {
        color: navy;
    }

Краще:

    .card__title {
        color: navy;
    }

### Помилка 4. Безконтрольне використання `!important`

Це ускладнює керування каскадом.

Спочатку перевір специфічність, порядок правил і джерело стилю.

### Помилка 5. Дублювання дизайн-значень

Якщо один колір змінюється в десяти місцях, це ознака того, що варто розглянути CSS custom properties.

### Помилка 6. Надмірна абстракція

Не потрібно створювати складну систему компонентів заради двох простих повторюваних правил.

### Помилка 7. Один гігантський CSS-файл без структури

Якщо файл великий, використовуй логічні секції, зрозумілі назви й, за потреби, розділення на файли.

### Помилка 8. Надто багато дрібних файлів

Надмірне розділення також може ускладнювати навігацію. Структура має відповідати розміру проєкту.

### Помилка 9. Ігнорування доступності

Стилі повинні забезпечувати видимий фокус, читабельний текст і зрозумілі стани інтерфейсу.

### Помилка 10. Виправлення симптомів замість причини

Якщо елемент має неправильний колір, спочатку знайди правило, яке його задає, замість того щоб додавати нове перевизначення навмання.

## 31. Питання на співбесіді

### 1. Що означає Maintainable CSS?

Це CSS, який легко читати, змінювати, розширювати та налагоджувати без непередбачуваних побічних ефектів.

### 2. Чому важливо правильно називати класи?

Зрозумілі назви показують призначення елемента й спрощують пошук стилів.

### 3. Що таке BEM?

Методологія іменування класів, яка розділяє назви на блоки, елементи та модифікатори.

### 4. Що таке CSS custom properties?

Користувацькі CSS-властивості, які дозволяють зберігати й повторно використовувати значення через `var()`.

### 5. Чому небажано зловживати `!important`?

Тому що це ускладнює керування каскадом і може змушувати додавати ще більше спеціальних перевизначень.

### 6. Що таке CSS-специфічність?

Це частина механізму каскаду, яка допомагає визначати пріоритет селекторів, коли правила конкурують за одну властивість.

### 7. Чи потрібно завжди уникати глобальних селекторів?

Ні. Вони корисні для базових стилів, але не повинні безконтрольно визначати оформлення всіх компонентів.

### 8. Що означає DRY у CSS?

Уникнення беззмістовного дублювання та повторне використання спільних значень і правил там, де це спрощує підтримку.

### 9. Чи завжди потрібно об'єднувати повторювані правила?

Ні. Якщо правила описують різні концепції, об'єднання може створити зайву зв'язаність.

### 10. Чим CSS Modules допомагає підтримуваності?

Він локалізує назви класів і зменшує ризик конфліктів між компонентами.

### 11. Для чого потрібні Stylelint і Prettier?

Prettier форматує код, а Stylelint перевіряє CSS-правила й допомагає дотримуватися узгоджених домовленостей.

### 12. Що таке CSS Cascade Layers?

Це механізм організації каскаду за допомогою `@layer`, який допомагає керувати пріоритетами груп стилів.

### 13. Як організувати CSS для великого проєкту?

Потрібно визначити правила іменування, межі компонентів, структуру файлів, дизайн-токени та підхід до глобальних стилів.

### 14. Чому підтримуваний CSS важливий у команді?

Він зменшує час на пошук помилок, робить зміни передбачуванішими та полегшує співпрацю між розробниками.

### 15. Чи означає підтримуваний CSS, що потрібно використовувати якомога більше інструментів?

Ні. Інструменти мають вирішувати реальні проблеми, а не створювати зайву складність.

## 35. Головне, що потрібно запам'ятати

1. **Підтримуваний CSS — це CSS, який легко змінювати без непередбачуваних наслідків.**
2. **Назви класів мають пояснювати призначення елемента, а не лише його колір або розмір.**
3. **Послідовність важливіша за конкретну методологію.** BEM, CSS Modules та інші підходи корисні тоді, коли команда використовує їх узгоджено.
4. **Уникай зайвої специфічності.** Прості селектори легше читати та перевизначати.
5. **Використовуй CSS custom properties для повторюваних системних значень.**
6. **Не прибирай глобальні стилі без потреби.** Базові правила та локальні стилі компонентів мають різні призначення.
7. **Не зловживай `!important`.** Спочатку розберися з каскадом і причиною конфлікту.
8. **Не створюй абстракції лише заради скорочення коду.** Вони мають спрощувати майбутні зміни.
9. **Доступність — частина якості CSS.** Враховуй фокус, контраст і налаштування зменшення руху.
10. **DevTools — важливий інструмент діагностики.** Знаходь джерело проблеми, перш ніж змінювати стилі.
11. **Автоматизація допомагає підтримувати якість.** Stylelint і Prettier можуть зменшити кількість повторюваних перевірок.
12. **Підтримуваний CSS починається з простих рішень.** Не потрібно ускладнювати код, якщо простіший варіант вирішує завдання.

> **Коротко:** підтримуваний CSS — це зрозумілі назви, передбачуваний каскад, повторно використовувані значення, логічна структура, доступність і мінімальна необхідна складність.
